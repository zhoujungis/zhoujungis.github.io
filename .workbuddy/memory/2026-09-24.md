### 两颗钉子（文章的核心卖点）
- **104 的钉子长在 111 上**：`1 + min(左, 右)` 是**错的**。
  **空子树不是叶子** —— `[1,2]` 错答 1（正确 2）、`[1,2,null,3]` 错答 1（正确 3）。
  `max` 侥幸掩盖了这个坑（`max(1,0)=1` 恰好淘汰 0），`min` 一下露馅。
  正确写法要把单侧空的两个分支先摘出来。
- **226 的钉子长在「交换的位置」上**：顺序确实无所谓，**唯独不能把交换夹在两个递归中间** ——
  因为交换改了 `root.left` 的指向，第二行递归进的是"从没翻过的那棵"，而翻好的那棵被翻第二次。
  交换要么放最前、要么放最后。

### LC 226 的核心洞察（决定了渲染层实现）
**翻转二叉树 ≡ 把每个节点从根到它的路径逐位取反（L↔R）。**
状态机因此不存"节点该画在哪"，只存每个节点的**相对左右角色** `sideOf`；
位置 = 沿 parent 链拼出路径 → 满二叉树槽位法算列号。交换一次 = 改一个 role，
节点 x 坐标自然跳到镜子里 —— **这就是"看到树在翻"的来源**。
推论：**翻转是自逆运算**（逐位取反两次 = 原值）。

### 文章立意（本题真正的难点）
**判据不是「这个字符出现过」，而是「它上次出现的位置还在窗口里」。**

```python
# ✅ 写法 A：显式写出「还在窗口内」
if ch in last and last[ch] >= left:
    left = last[ch] + 1
# ✅ 写法 B：等价的 max 保护
if ch in last:
    left = max(left, last[ch] + 1)
# ❌ 漏掉后半句 —— left 会倒退
if ch in last:
    left = last[ch] + 1
```

- **官方三个样例（`abcabcbb` / `bbbbb` / `pwwkew`）全部照样通过** —— 因为它们都是
  "重复字符就在窗口内"的情况。所以这个 bug 靠跑样例发现不了。
- **`"abba"` 是试金石**：走到下标 3 的 `a` 时 `last['a'] = 0`，但 `left` 已经是 2，
  `0 < 2` → 这个旧位置**已经在窗口外**，不构成重复，`left` 必须原地不动。
  漏判据的写法会算出 `left = 1`（**从 2 倒退**），窗口变成 `"bba"`，答案错成 3（正确 2）。
- 另一个反例 `"abcba"`：正确 3，漏判据错答 4。

### 两条不变量（状态机的骨架）
1. **窗口 `[left, right]` 内永远没有重复字符**；
2. **`left` 只往右走，绝不后退** —— 后退会把之前挤出去的字符又放回来，不变量 1 当场破掉。

### 「左指针为什么能一步跳」这个观察（写进变体节的收尾）
LC 3 能一步跳到 `last[ch] + 1`，是因为**冲突点有明确的坐标**。
159 / 340（至多 K 个不同字符）、76（最小覆盖子串）、209 都没有这个坐标，
只能 `while` 一格格缩。**这一个判据就是整个滑动窗口题库的分岔点。**

### 修复的坑
- **⚠️ done 帧不要复写语义字段（这次换了个更好的做法）**：
  LC 124 的 done 帧是"总结性复写"（把 `through` 改成 `best`），结果那一帧的逐帧不变量
  全部失效、测试到处要排除 `phase === 'done'`。LC 3 初版也照抄了这个做法
  （done 帧把 `left`/`right`/`windowLen` 改成最优窗口的样子），**4 个不变量测试立刻挂掉**。
  改法：**done 帧保留 left / right / windowLen 的真实值**（`right = n-1`、`left` 是最后的值），
  "最优窗口"单独由 `bestRange` 表达，**渲染层在 done 帧改用它来画窗口**。
  结果：所有逐帧不变量在收尾帧依然成立，测试里**一个 done 例外都不需要**。
  **这是比 LC 124 更干净的收尾帧设计，以后优先用这个。**
- **手写期望值被三方交叉验证打回**：trace 里 `"abacabadabacaba"` 我手写 `want = 4`，
  而状态机 / set+while 版 / 暴力枚举版**三个独立实现都说 3** —— 是我写错了。
  教训：**手写期望值必须让独立实现来校验**。
- **`**` 裸残留又踩一次（skill 坑 M）**：这次两处**都在代码块内部** ——
  ① 题目示例块里写了 `注意答案必须是**子串**`；② Python 注释里写了 `出现过 **并且** 那个位置`。
  两处都触发 "unbalanced bold" guard。**规则复述：代码块（含注释、示例数据）里绝对不许出现 `**`。**

### 渲染层修复的 4 个视觉 bug
1. **单格窗口时 `L=0` 和 `R=0` 完全重叠**（只看得到 `R=0`）→ `left === right` 时合并成 `L=R=n`；
2. **L / R 引出线和"最优窗口"线共用金色虚线样式**，画面上分不清谁是谁 →

### 文章立意（本题唯一的真难点）
**「先查再存」的顺序不能反。** 反过来写，当 `target == 2 * x` 时会查到**自己**：

```python
if need in seen:        # ✅ 先查 —— 此刻表里只有左边的东西
    return [seen[need], i]
seen[x] = i             # ✅ 再存

seen[x] = i             # ❌ 先存 → target == 2x 时 need 就是 x 自己
if need in seen:
    return [seen[need], i]      # 返回 [i, i]，同一个元素用了两次
```

- **触发条件精确**：`target == 2 * x`（当前元素恰好是目标值的一半）。
- **`[3, 3]` 配 `target = 6`** → 错误写法返回 `[0, 0]`。
- **⚠️ 官方第一组样例 `[2, 7, 11, 15]` 配 `9` 恰好不触发**（9 ÷ 2 = 4.5，数组里没有）——
  用错误写法跑它得到正确答案 `[0, 1]`，**会让你以为写对了**。
  但官方第二组 `[3, 2, 4]` 配 `6` 会暴露（6 ÷ 2 = 3 在下标 0）。
- **"先查再存"同时解决两件事**：① 查找 O(1)；② **"同一元素不重复使用"这条约束自动成立**
  —— 因为查表那一刻表里只有 `nums[0..i-1]`，任何命中下标必然 `< i`。

### 变体链条（写进文章第七/八节）
- **LC 167（有序数组）→ 双指针，空间 O(n) → O(1)**。对照表：同题在"有序"前提下信息量增加，
  可以用更省的办法。**"利用单调性让指针只往一个方向走"—— 和 LC 3 滑动窗口同源**。
- LC 170 数据结构设计 / LC 653 BST（中序后退化成 167）/ LC 15 三数（**必须排序 + 双指针，
  因为要去重，哈希反而麻烦**）/ LC 18 四数 / LC 454 分组哈希。
- 演化逻辑一句话：**固定的数增加一个 → 复杂度多一维；剩下的"两数"始终用 O(n) 的本方法收尾。**
