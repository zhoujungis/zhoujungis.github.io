### 文章立意
1. **四种解法是同一个问题的四种回答** —— 核心公式
   `water[i] = max(0, min(左最高, 右最高) - height[i])`，全部区别只在"怎么拿到这两个数"。
2. **双指针的正确性论证**（面试分水岭）：矮的一端的外侧上界已由对面的柱子保证；
   反证：若左侧高柱真是短板之外的那边，它当年经过时判据就不会选它，右侧会被一路收缩
   到出现更高的柱子为止。完整论证写在文章第六节。
3. **单调栈 = 横着切**：同一格的水会被分几次到账 —— 官方例下标 5 的 2 单位水
   是 `i=6` 加 1 层、`i=7` 再加 1 层。两个动画对此给出了最直观的对照
   （双指针一次画完 2 格水；单调栈画成上下两层）。
4. **三维版（LC 407）的推广**：一维的 `min(左最高, 右最高)` 其实就是
   "往左走"和"往右走"两条路径的瓶颈取 min；二维把"两条路径"换成"所有路径" ——
   **最小瓶颈路径 = 多源 Dijkstra**（最小堆 + BFS，从边界向内灌）。
   一维是二维的退化特例，这一对题放一起木桶原理才贯通。

### 校验结果
- **24 组输入**：双指针、单调栈、暴力参考解**三向交叉**，总水量与**逐格水量**都一致
- 不变量：双指针（l 只增 r 只减、LM/RM 单调不减、total 单调不减、
  结算侧别与判据一致、gained = 新 max - 高度）；单调栈（栈内高度递减、
  每个下标恰好按序入栈一次、settle 四公式 width/layerH/level/gained、
  **逐格增量之和 = gained**）
- 专门一条测试钉死"下标 5 分两次加水"（直接断言 water[5] 的两次变化 `0→1→2`）

### 修复的坑
- **⚠️ 代码注释里写 markdown 加粗（`**` 坑第 4 次，这次的根源变了）**：
  前三次分别是行内代码的幂运算符、引用块的脱敏星号、代码块示例的加粗；
  这次是**写 Python 注释时下意识用了 `# 存**下标**`** —— 我第一反应还是改措辞
  （改成"存的是**下标**"），结果**依然有 `**`**！真正的问题是：
  **代码块里根本不能出现任何星号，不是"换个写法"。** 已在 skill 里把坑 M 的表述升级。
- **双指针横幅文字重叠**：`segR` 的 x 写成 `BANNER_W - 150`（从右往左数），
  `rightMax = 0` 一长就和右边的「累计水量」标签叠上。改成固定偏移 `LABEL_X + 170`。
  **教训：横幅里多段文字的 x 都用从左往右的固定偏移，别混用两种坐标系。**
- **单调栈 init 帧横幅显示"结束 · 共 0 单位"**：横幅 if/else 链漏了 init 分支，
  落进了 else。修复顺带把 else 改成显式的"等待开始"。
- **"本帧新增的层"用半透明金色 + 虚线边框**：虚线在视觉语言里是"被排除/禁用"，
  而这里恰恰是"刚加上的水" —— **语义完全反了**；半透明叠在蓝水上又混成说不清的灰。
  改成不透明淡金填充 + 金色实线边框，和水（蓝）一眼分开。
- **封面橙卡代码 `h[栈顶]` 豆腐块**：中文"栈顶"整行用了 Consolas。
  按分段绘制规则拆成三段修复。**这是封面中文-in-Consolas 的又一次出现，规则没问题，是执行时漏了。**
- **派生发布脚本时 heredoc 里的正则转义**：写成 `\\n`（双反斜杠），在 raw string 里
  变成"匹配字面反斜杠 + n"，meta 块正则匹配失败。**教训：heredoc 里写 Python 正则，
  raw string 一律用单反斜杠**（`\n`、`\[`）；写完先跑一遍，别等 dry-run 才发现。
