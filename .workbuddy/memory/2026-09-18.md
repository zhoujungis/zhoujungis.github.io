## 关键实测数据（可复现）

- A 超时：无超时→下游 3s 恢复但服务 5s 零吞吐（p99 5034ms）；超时 200ms→p99 627ms、吞吐 +75%。**注意：超时组下游峰值并发 320 vs 20，超时保护自己不保护下游。**
- B 重试放大：retries 0/1/2/3 → 放大 ×1/×2/×3/×4，用户吞吐 128.3→15.0/s（-88.3%），下游调用只降 40%（双输）。
- C 抖动：固定退避恢复后峰值 1200 QPS / CV 1.43；全抖动 520 QPS（-57%）/ CV 0.23，均值几乎不变。
- D 熔断（开环 150/s）：拒绝率 36.2%→3.5%，故障期 p50 774ms→0ms，下游调用 -44%；**代价：恢复探测 32ms→731ms，且出现 4 次开合震荡。**
- E 重试预算：下游全挂时，无预算 ×4.00 / 26.7/s；预算 20% ×1.04 / 97.0/s（自身吞吐 ×3.6）。30% 错误率下预算几乎不触发（50% 档只拒绝 2 次）——这正是设计优点。
- F 舱壁：共享池 → 健康依赖 B p50 436ms、61.4/s；隔离 10+10 → 76ms、283.5/s（4.6 倍），慢依赖 A 吞吐 -40%（正确代价）。

## 踩过的坑（写 bench 时）

1. bash 工具在此环境 `ls`/`head` 等命令不可用（`dirname: command not found`），**用 Python 脚本代替 shell**。
2. 闭环压测（closed-loop）在"快速失败"下会疯狂自旋，两组请求量差 10 倍不可比 → **熔断实验必须改用开环定速 + 有界队列**（`open_loop()`）。
3. 聚合分位数会掩盖故障（p50 被恢复后请求稀释）→ **必须输出每秒完成数的时间线**。
4. 惊群实验若经过服务端线程池会被排队"抹平" → 客户端必须自己 sleep 退避、不走瓶颈池。
5. `Result.total` 要包含 fallback/rejected，否则降级量不计入分母。
6. `RetryBudget.__init__` 会立刻调用 clock()，必须先 `ds.start()` 再构造，否则 `t0=None` 报错。
