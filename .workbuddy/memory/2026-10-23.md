## 经验（Agent 工程 11）

- 写「注入」类文章不要从模型能力写起，从「字节进入上下文的位置」写起：system / user / tool / memory 四个位置的服从度不同，一张位置-权威表比任何攻击案例都更能说明问题。
- 论证「提示词防不住」不要靠断言，靠位置：把 `AGENTS.md` 的注入代码原样贴出来，读者自己会看到那句「follow it unless the user says otherwise」。这类源码自带说服力。
- 检查默认值时要把两个字段放在一起读：`auto_approve: true` 与 `ApprovalPolicy::Untrusted` 各自都合理，组合起来宽的那个先说话。安全配置的合并规则必须是「严的赢」，而不是「先出现的赢」。
- 测试把缺陷固化成规格是最坏情况：`approval_policy_decisions` 用注释「run everything」为自动批准背书，修正代码时必须同时改断言，否则修完就红。
- 「白名单只认程序不认参数」要举可验证的例子：`cat ~/.ssh/id_rsa` 能过、`git diff --output=FILE` 能过（Git 2.39+ 的写文件选项没被 `git_subcommand_is_read_only` 拦住）。程序级授权无法覆盖参数级副作用。
- 读写不对称是这类工程的通病：写有 `check_write` + canonicalize，读连工作区判断都没有。凡是「写加了边界」的地方，追问一句「读为什么不需要」。
- SSRF 防护与数据外泄防护方向相反：前者挡「往内打」，后者要挡「往外带」。`validate_target` 再严也拦不住 `?data=<凭据>`。
- 校验与使用必须是同一个对象：`ToSocketAddrs` 校验后再让 HTTP 客户端自行解析，中间就是 DNS rebinding 的窗口；解法是把校验放进 resolver 钩子。
- 语义标记要能活过压缩：`compact_with` 把摘要以 system 身份插回索引 1，信封在原始 tool 消息里再漂亮也会被摘要拆掉；摘要指令必须要求保留 source 与 trust。
- 封面里「2 / 3」这类数字比长句更有冲击力，但要配一行解释；`→` 仍必须交给中文字体，`assert_ascii()` 继续兜底。
- 线上轮询这次更慢：封面 6 次（约 90 s）、页面 10 次（约 200 s）才 200；不要在第 8 次就判失败，结构断言（h2=26）+ 连续两次同值仍是可靠跳出条件。
- 浏览器 agent 的视口在本环境持续异常（innerWidth/outerWidth/clientWidth 均为 0，第二次调用甚至取到 table=0），两次调用后即停；溢出结论改用 `body.scrollWidth`（320）与站点全局 `.table-scroll` 包裹规则佐证，并如实标记 BLOCKED。
