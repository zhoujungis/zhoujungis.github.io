# 【LC 215 / 347】TopK 双题：第 K 大选的是位置，前 K 高频选的是桶

> - **LC 215**：给定整数数组 `nums` 和整数 `k`，返回数组中第 `k` 个最大的元素。要求设计时间复杂度为 O(n) 的算法。示例：`[3,2,1,5,6,4]`, `k=2` → `5`。
> - **LC 347**：给定整数数组 `nums` 和整数 `k`，返回其中出现频率前 `k` 高的元素，要求时间复杂度**优于** O(n log n)。示例：`[1,1,1,2,2,3]`, `k=2` → `[1,2]`。

这两道题是腾讯、阿里、蚂蚁 TopK 方向的必考组合，而且它们共享同一个骨架：**数组、一个 k、要的是"按某种排序排好后的前一段"**。区别只在排序的键：

| | 排序的键 | 要的东西 | 对应算法 |
|---|---|---|---|
| LC 215 | **值** | 排序后的**一个位置**（第 k 大） | 快速选择 |
| LC 347 | **频率** | 排序后的**一段前缀**（前 k 高频） | 桶排序 |

这一篇把这两条轴一次讲透。两道题各配一个可回放的推演动画，最后一个追问 —— **10 亿个数找前 100 大** —— 会把两条轴合到工程视角再看一遍。

## 一、先把"第 k 大"翻译对：两道题各藏着一个语义陷阱

### 1.1 LC 215：第 k 大是"第 k 个位置"，不是"第 k 个不同的值"

官方给了两个例子，第二个就是用来钉死语义的：

> `nums = [3,2,3,1,2,4,5,5,6]`, `k = 4`，输出 `4`。

把它降序排好：`[6, 5, 5, 4, 3, 3, 2, 2, 1]`。第 4 个位置上是 **4**。

注意这里有两个 `5` —— 它们**各占各的位置**。如果你理解成"第 4 个**不同的**值"，会算出 3（不同值降序是 `[6,5,4,3,2,1]`，第 4 个是 3）。**题目要的是前者**：重复元素在排名里各算一个席位。

所以更准确的题面应该是：**"把它排好序之后，下标在第 k 位上的那个数"**。这句话直接给出了第一种解法：

```python
def findKthLargest(nums, k):
    nums.sort()
    return nums[len(nums) - k]
```

一行。时间 O(n log n)，能过，但面试官下一句一定是："题目要求 O(n)，怎么办？" —— 别急，先看清这行代码里那个最容易写错的**下标**。

### 1.2 索引换算：第 k 大 = 升序第 n-k 位

升序数组里，第 k 大是**倒数第 k 个**，也就是下标 `n - k`（0 基）：

```
nums = [3, 2, 1, 5, 6, 4], n = 6, k = 2
升序：[1, 2, 3, 4, 5, 6]
                            ↑
                     下标 n-k = 4，值 5 ✓
```

写成 `k - 1` 是最常见的错误 —— 那找的是**第 k 小**。这个 off-by-one 之所以高频，是因为"第 k 大"和"第 k 小"在代码里只差一个字符，而样例往往测不出来：`[3,2,1,5,6,4]` 配 `k=2`，如果数组恰好对称（比如 `[1,2,3,2,1]`），两种理解会给出同一个答案。

**这个系列反复出现一个模式：官方样例恰好掩盖 bug。** 这里的版本是——用对称数组的样例，验证不了你有没有把"大"写反。

### 1.3 LC 347 的语义陷阱：频率并列时怎么办

LC 347 题目保证**答案是唯一的**，所以频率并列卡在边界上的歧义不存在。但"出现频率前 k 高"里仍然有一个隐性约定：**返回的是 k 个不同的值**（每个值只出现一次），这与 LC 215 的"重复各占位置"正好相反。做 LC 215 时别把两题的语义搞串。

## 二、解法梯队总览

把两道题的所有主流解法放在一张表里：

| 解法 | 时间 | 空间 | 适用 |
|---|---|---|---|
| 排序后取下标 | O(n log n) | O(1)（原地） | 数据量小、追求一次写对 |
| 小根堆（容量 k） | **O(n log k)** | O(k) | **数据流、k 远小于 n、内存受限** |
| 快速选择 | **平均 O(n)**，最坏 O(n²) | O(1) | 一次性给全量、可以修改数组 |
| 桶排序（仅 LC 347 类） | **O(n)** | O(n) | 键是小整数范围（频率天然是） |
| BFPRT / 中位数的中位数 | 严格 O(n) | O(n) | 理论价值，工程几乎不用 |

题目要求的"O(n)"（215）和"优于 O(n log n)"（347）各对应表中的两行。下面按顺序讲：先快速选择，再堆，再桶排序，最后合到海量数据。

## 三、LC 215：快速选择 —— 分区之后，位置即排名

### 3.1 核心观察

快速排序做一次分区（partition）之后，有一件事是**确定**的：**枢轴（pivot）落在它最终排序位置上**。因为它左边的元素全部 `<=` 它，右边的全部 `>` 它 —— 无论数组最后怎么排，这个元素就在这一位。

而"落在最终排序位置上"有一个更重要的解读：**这个位置就是它的排名**。

于是"找第 k 大"变成一个判断题：

- 枢轴位置 == 目标位 → 它就是答案，结束；
- 枢轴位置 < 目标位 → 答案在右边，左边（含枢轴）全部淘汰；
- 枢轴位置 > 目标位 → 答案在左边，右边（含枢轴）全部淘汰。

**快排要递归两边，快速选择只进一边** —— 这就是从 O(n log n) 降到 O(n) 的全部原因。

### 3.2 逐帧推演

用官方例 1：`[3, 2, 1, 5, 6, 4]`，`k = 2`。`n = 6`，目标位 `n - k = 4`（升序下标）。分区用 Lomuto 方案：枢轴取区间最右端，`i` 指向"小于等于区"的下一个空位，`j` 从左往右扫。

| 13 | done | [4,5] | 5 | `[3,2,1,4,5,6]` | 2 轮分区，共 6 次扫描 |

两个值得盯住的瞬间：

- **第 8 帧**：枢轴 4 落在下标 3，但目标位是 4。`3 < 4`，说明答案在右边 —— 左边 4 个元素（含枢轴）**从此一眼都不看**。快速选择的"省"，全部省在这一步。
- **第 12 帧**：枢轴 5 落在下标 4，正好是目标位。左边 4 个都不比它大、右边 1 个都比它大 —— **排名确凿，不用再比任何东西**。

### 3.3 为什么敢只进一边（正确性）

"左边那 4 个以后再也不看"听起来太自信了。论证其实只有两句：

1. 分区之后，枢轴位置的**排名已经确定**：它就是升序数组的第 `pivotIdx` 位（0 基）。如果 `pivotIdx == target`，答案就是它，**其他任何元素都不可能在这个位置上**。
2. 如果 `pivotIdx < target`，目标位在枢轴右边 —— 而右边那些元素的**相对顺序虽然还乱着**，但它们**就是升序数组下标 `pivotIdx+1..n-1` 上的全部候选**。目标位 `target > pivotIdx` 落在这段里，左边那些元素排名全都 `<= pivotIdx < target`，**不可能出现在目标位上**。

所以淘汰不是"大概率的剪枝"，是**确定性的排除**。这个性质和 LC 3 滑动窗口里"left 只会右移"是同一类不变量：**每一步淘汰都不可逆，且不漏**。

### 3.4 迭代写法

收敛逻辑是"区间收缩"，用迭代写最自然，还省掉递归栈：

```python
import random

def findKthLargest(nums, k):
    target = len(nums) - k          # 第 k 大 = 升序下标 n-k
    left, right = 0, len(nums) - 1
    while True:
        pivot = nums[right]         # 生产代码应该随机化，见第五节
        i = left
        for j in range(left, right):
            if nums[j] <= pivot:
                nums[i], nums[j] = nums[j], nums[i]
                i += 1
        nums[i], nums[right] = nums[right], nums[i]
        if i == target:
            return nums[i]
        elif i < target:
            left = i + 1            # 答案在右边
        else:
            right = i - 1           # 答案在左边
```

## 四、复杂度：O(n) 是怎么来的

### 4.1 平均情形的几何级数

设每次分区能砍掉一半候选（期望意义下），总扫描量是：

```
n + n/2 + n/4 + ... = 2n ≈ O(n)
```

严格地说，随机枢轴下第 k 大的期望比较次数是 `2n + o(n)`（Blum-Floyd-Pratt-Rivest-Tarjan 的经典结论对快速选择的变体同样成立），常数 2 的来源正是这个级数。**分区本身每轮 O(区间长度)**，级数求和收敛在 2n。

### 4.2 最坏情形：不是理论装饰，是真实会踩的坑

两种输入会让"每轮砍一半"退化成"每轮只砍一个"：

**情形一：有序数组 + 固定取末尾当枢轴。** 升序数组 `[1,2,...,n]` 找最小值（k=n）时，枢轴恰好是区间最大值，每轮只能砍掉自己 —— n 轮、每轮扫一遍，**O(n²)**。我的状态机实测：

```
n = 6，升序 + pivot 取末尾 + 找最小：5 轮分区（随机枢轴只要 2 轮）
n = 8，同上：7 轮分区（随机枢轴 2 轮）
```

**情形二：全部元素相同 + Lomuto 分区。** 这个更反直觉 —— 就算你把比较写成 `<=`，全相同元素的数组依然是 Lomuto 的最坏情况：每个元素都 `<=` 枢轴，`i` 一路走到末尾，枢轴归位后落在原地，每轮还是只砍掉 1 个。实测 `[5,5,5,5,5,5]` 找最小值要 5 轮。

**两个修复**：

1. **随机化枢轴**：随机挑一个位置换到末尾再分区。最坏情况在理论上仍存在（运气差到底），但任何固定输入能触发它的概率随 n 超指数衰减，工程上视作不会发生；
2. **三路分区（荷兰国旗）**：把数组分成"小于 / 等于 / 大于"三段，枢轴这一段**一次性全部归位**。全相同元素时等于区间直接清空 —— 这也是 Java 里对重复元素多的输入的标准优化。

LeetCode 官方题解用的就是"随机化 + 三路划分"。工程库里的做法更进一步：C++ 的 `std::nth_element` 用 **introselect** —— 随机枢轴为主，递归深度超过 2·log n 就切换到 BFPRT（中位数的中位数），把最坏情况彻底钉死在 O(n)。面试时能主动说出"固定枢轴在最坏情况会退化，所以要随机化，全相同元素要三路"，比背出 O(n) 本身值钱。

### 4.3 四种解法放一起

| 写法 | 时间 | 空间 | 备注 |
|---|---|---|---|
| 暴力：k 趟选最大 | O(n·k) | O(1) | k 大时退化成 O(n²) |
| 排序 | O(n log n) | O(1) | 一行，但到不了 O(n) |
| 小根堆 | O(n log k) | O(k) | k 小时接近线性；流式友好 |
| **快速选择** | 平均 O(n)，最坏 O(n²) | O(1) | 全量一次性给、可修改数组时最快 |

## 五、堆解法：O(n log k) 什么时候比 O(n) 更好

### 5.1 算法

维护一个**容量为 k 的小根堆**，遍历数组：堆没满就压入；满了且当前元素比堆顶大，就弹出堆顶再压入。扫完后**堆顶就是第 k 大** —— 堆里始终装着"到目前为止最大的 k 个"，堆顶是其中最小的一个。

```python
import heapq

def findKthLargest(nums, k):
    heap = []
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)
    return heap[0]
```

### 5.2 一个常见误区：为什么是小根堆不是大根堆

直觉上"找最大的 k 个"该用大根堆，但那样必须把全部 n 个元素装进堆再弹 k 次，时间 O(n + k log n)、空间 O(n)。**小根堆装的是"k 个候选中最小的那个"**，它始终守在"第 k 大"这个门槛上：新元素想进前 k，先得打赢门槛。空间 O(k)、时间 O(n log k)。

（ LC 3 那篇说过"判据在 cur 身上不在 x 身上"，这里是同款思想：**门槛本身才是主角，新元素只是挑战者。**）

### 5.3 快速选择 vs 堆：四维对照

面试追问"这两个怎么选"时，比"谁快"更重要的是这四行：

| 维度 | 快速选择 | 小根堆 |
|---|---|---|
| 时间 | 平均 O(n)，最坏 O(n²) | 稳定 O(n log k) |
| 空间 | O(1)（原地） | O(k) |
| **能流式吗** | **不能**（要随机访问全量数据） | **能**（数据一个个来也行） |
| **改原数组吗** | **改**（原地交换） | 不改 |

两个"能/改"经常被忽略，却是工程选型的关键：数据是流式到达的，快速选择直接出局；调用方不允许你动它的数组，同理。**堆慢在渐近意义上从未发生 —— O(n log k) 在 k 接近 n 时确实退化成 O(n log n)，但换来的是稳定性和流式能力。** 反过来，面试白板上一道"写出来"的题，堆十行内写完且没有最坏情况，快速选择写错分区边界就死循环 —— 所以很多面试官建议：**先写堆，再主动提快速选择作为优化**。

## 六、LC 347：频率是天然的桶下标

### 6.1 从"要排序"到"不用排序"

LC 347 的骨架：先哈希计数（O(n)），然后按频率挑前 k 个。剩下的问题和 LC 215 同构 —— 又是 TopK，只是键从"值"换成了"频率"。

堆解法照样能用：按频率维护小根堆，O(n log k)。但题目要求"优于 O(n log n)"，而这里有一个堆没有的**结构性优惠**：

> 一个元素的出现频率**最多是 n**（全体都是它）、最少是 1。也就是说，**频率天然落在 `[1, n]` 这个小整数区间里。**

要排序的键恰好是一个范围已知的小整数 —— 这正是**计数排序**的前提。于是"按频率排序"免费：建 `n+1` 个桶，**频率是多少就丢进下标多少的桶**，一次比较都不用做。收集时从桶 `n` 往桶 `1` 扫，收满 k 个停。

### 6.2 逐帧推演

官方例：`[1,1,1,2,2,3]`，`k = 2`。

<div class="algo-viz algo-viz--lc347"></div>

13 帧（与状态机 `bucketTopKSteps.js` 逐行核对过）：

| 帧 | 阶段 | 动作 |
|---|---|---|
| 0 | init | 计划三步：计数、入桶、收集 |
| 1-3 | count | 数出 `1→3 次`、`2→2 次`、`3→1 次` |
| 4 | bucket | `1` 进桶 f=3 |
| 5 | bucket | `2` 进桶 f=2 |
| 6 | bucket | `3` 进桶 f=1 |
| 7 | collect | 扫 f=6：空桶，跳过 |
| 8 | collect | 扫 f=5：空桶，跳过 |
| 9 | collect | 扫 f=4：空桶，跳过 |
| 10 | collect | 桶 f=3 里的 `1` 收入 → 已收 1/2 |
| 11 | collect | 桶 f=2 里的 `2` 收入 → **收满 2/2，停** |
| 12 | done | 答案 `[1, 2]` |

看第 7-9 帧：**那三个空桶不是浪费** —— 它们是"从高频往低频扫"这个动作的字面展示。频率 6、5、4 都没有对应的值，说明这个数组里没有元素出现那么多次；收集指针扫过它们，正说明桶下标和频率一一对应、不重不漏。

```python
from collections import Counter

def topKFrequent(nums, k):
    freq = Counter(nums)
    buckets = [[] for _ in range(len(nums) + 1)]
    for v, f in freq.items():
        buckets[f].append(v)         # 频率即下标，O(1) 入桶
    ans = []
    for f in range(len(nums), 0, -1):
        for v in buckets[f]:
            ans.append(v)
            if len(ans) == k:
                return ans
    return ans
```

三步全是 O(n)，**总计 O(n)** —— 比题目划的红线还低一档。代价是 O(n) 的桶空间，以及一个前提：**键是小整数、范围已知**。频率满足，距离、得分这类连续值不满足 —— 那才轮到堆。

### 6.3 和 LC 215 的镜像关系

把两题的解法并排放，会看到一张有趣的对照表：

| | LC 215（按值） | LC 347（按频率） |
|---|---|---|
| 排序的键 | 值，范围任意 | 频率，天然在 [1, n] |
| 免费午餐 | 无 —— 值没有范围保证 | 有 —— 桶排序直接 O(n) |
| 选择问题 | 只选 1 个位置 | 选一段前缀 |
| 最佳工具 | 快速选择 | 桶排序 |

**键的范围决定能不能"用空间换排序"。** 这也是为什么 LC 347 出现后，面试官常追问一句"如果频率范围特别大怎么办" —— 那就回到堆。

## 七、海量数据 TopK：10 亿个数找前 100 大

腾讯那道变体原题（"统计海量数据中出现次数最多的前 K 个元素"）把上面的选择全部推倒重来 —— 前提变了：**单机内存装不下全部数据**。10 亿个整数约 4 GB（裸存），加上结构开销远超单机可用内存；如果是日志行，更是几十上百 GB。

### 7.1 前提一：单机能存下"k 个"就够了 —— 小根堆

10 亿找前 100 大，只需要维护一个 **100 容量的小根堆**：

- 内存：100 个元素，忽略不计；
- 扫描：**一遍**。文件顺序读（哪怕从磁盘、从多台机器汇聚），边读边喂给堆；
- 时间：O(n log k) = 10⁹ × log₂100 ≈ 10⁹ × 7，几十秒级。

**这就是第五节"堆能流式"的直接变现**：快速选择在这里完全出局 —— 它需要把数组整个握在手里做随机访问，而海量数据给不了。

### 7.2 前提二：连哈希表都装不下 —— 分桶分治

如果是"出现次数最多的前 K 个**词**"（LC 347 的海量版），麻烦升级：**去重后的词表本身可能就装不进内存**。1 亿个不同的 URL，平均 50 字节，就是 5 GB。

标准做法是**哈希分桶 + 局部 TopK + 归并**：

1. **分**：对每个元素算 `hash(x) % 1000`，写入 1000 个小文件。同一元素必然落进同一文件 —— 这是分治正确性的根据；
2. **治**：每个小文件平均只有 100 万条，单独建哈希计数 + 小根堆，各取自己的前 100；
3. **合**：1000 个局部 Top100 归并成全局 Top100（1000 × 100 = 10 万条，随便放）。

单机多进程就能做，天然可扩到多机 —— 每台机器负责一批桶。这个套路有一个更正式的名字：**外部排序的分治框架**，只不过把"排序"换成了"TopK"。

### 7.3 选型小结

| 场景 | 方案 | 关键依赖 |
|---|---|---|
| 单机内存装得下、一次性 | 快速选择（随机化） | 随机访问全量 |
| 单机内存装得下、可流式 | 小根堆 O(n log k) | 只需 k 的内存 |
| 去重后仍装不下 | 哈希分桶 + 局部堆 + 归并 | hash 分桶的正确性 |
| 值域很小（如年龄 0-150） | 计数数组 | 值域即下标（同 LC 347 的桶） |

最后这行和 LC 347 的桶排序是同一个思想：**发现"键是小整数范围"时，比较排序整个可以绕开。**

## 八、Java 版

```java
class Solution {
    public int findKthLargest(int[] nums, int k) {
        int target = nums.length - k;          // 第 k 大 = 升序下标 n-k
        int left = 0, right = nums.length - 1;
        while (true) {
            int idx = partition(nums, left, right);
            if (idx == target) return nums[idx];
            else if (idx < target) left = idx + 1;
            else right = idx - 1;
        }
    }

    private int partition(int[] a, int left, int right) {
        int r = left + (int) (Math.random() * (right - left + 1));  // 随机化
        swap(a, r, right);
        int pivot = a[right], i = left;
        for (int j = left; j < right; j++) {
            if (a[j] <= pivot) {
                swap(a, i, j);
                i++;
            }
        }
        swap(a, i, right);
        return i;
    }

    private void swap(int[] a, int i, int j) {
        int t = a[i]; a[i] = a[j]; a[j] = t;
    }
}
```

堆版用 `PriorityQueue`（默认就是小根堆，不用翻极性）：

```java
class Solution {
    public int[] topKFrequent(int[] nums, int k) {
        Map<Integer, Integer> freq = new HashMap<>();
        for (int x : nums) freq.merge(x, 1, Integer::sum);

        PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> a[1] - b[1]);
        for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
            heap.offer(new int[]{e.getKey(), e.getValue()});
            if (heap.size() > k) heap.poll();
        }
        return heap.stream().mapToInt(a -> a[0]).toArray();
    }
}
```

## 九、边界情况与常见坑

**坑一：`k - 1` 与 `n - k`。** 前文已讲，第三种确认方式：`k = n` 时答案应该是数组最小值 —— 用这个特例在脑子里过一遍你的下标公式。

**坑二：固定枢轴在有序输入上超时（TLE）。** LeetCode 215 的测试数据里有精心构造的有序大数组，固定取末尾的 Lomuto 提交会直接超时。随机化一行就能修。

**坑三：`<=` 还是 `<`。** Lomuto 分区写 `<` 的话，等于枢轴的元素会被甩到右边，全相同元素退化得更狠；标准写法是 `<=`，配合三路分区处理大规模重复。

**坑四：快排口径记混。** 快速选择平均 O(n) 的前提是**只递归一边**。如果你发现自己在两边都递归了，那写的是快排不是快速选择 —— O(n log n)，题目的 O(n) 要求就没满足。

**坑五：LC 347 用大根堆。** 全部元素入大根堆再弹 k 次，O(n + k log n)，题目"优于 O(n log n)"在 k 较小时其实能满足，但空间 O(n) 且弹出的顺序还要再处理 —— 小根堆（容量 k）或桶排序是更干净的两条路。

## 十、变体

| 题 | 变的是什么 | 怎么想 |
|---|---|---|
| **LC 973 最接近原点的 K 个点** | 键从"值"换成"到原点的距离平方" | 距离是连续值，没有桶 → 堆 O(n log k) 或快速选择（比较器换成距离） |
| **LC 692 前 K 个高频单词** | 频率并列时要按字典序 | 比较器加一层：频率相同比字符串；桶排序在并列桶内也要再排 |
| **LC 703 数据流中的第 K 大** | 数据无限流式到达 | **只能堆**（容量 k 的小根堆）—— 快速选择需要全量随机访问，流式场景直接出局 |
| **LC 451 根据字符出现频率排序** | 把"取前 k 个"换成"全部按频率重排" | 同样的桶，收集时不提前停 |
| **LC 295 数据流的中位数** | "第 k 大"里 k 在动（中位数） | 对顶堆：大根堆 + 小根堆各管一半 |

一图流的选择：**静态全量 + 想最快 → 快速选择；流式 / 只要前 k → 小根堆；键是小整数范围 → 桶排序。**

## 十一、面试怎么答

- **先给能跑的**：排序一行，或堆十行。主动说复杂度；
- **再给题目要的**：快速选择 O(n)，主动补一句"随机化枢轴避免有序输入退化，重复多可以三路分区"；
- **被追问海量数据**：内存装得下 → 堆流式；装不下 → 哈希分桶分治；值域小 → 计数；
- **自测两句话**：`findKthLargest([3,2,1,5,6,4], 2) == 5` 且 `findKthLargest([3,2,3,1,2,4,5,5,6], 4) == 4`（第二个能钉死"位置不是不同值"），以及 `topKFrequent([1,1,1,2,2,3], 2) == [1,2]`；
- **一句话总结**：LC 215 问"我排第几"—— 分区之后位置即排名；LC 347 问"谁排在前面"—— 频率自己就是排好序的桶下标。
