## 前言：上下文不是聊天记录

第一篇讲循环时，我们把消息列表当成一个整体：模型回什么，就往后追加什么。只要历史合法，循环就能一直转。

但历史不会免费。模型没有记忆，每一轮请求都要把完整历史重新发一遍。所谓「上下文窗口」，是一个每轮都被重新填充的容器，不是一份持久保存的聊天记录。

Agent 上下文的难点从来不是「存不下」，而是「带什么」。

这带来一个和普通程序完全不同的约束：**上下文的成本不是存储成本，而是每轮重复支付的输入成本。** 你把一段 20,000 字符的工具结果留在历史里，不是占了一次磁盘，而是让接下来的每一次模型请求都多带 20,000 字符。跑十轮，就是二十万字符的重复输入。

所以「留什么，丢什么」不是整理癖，而是 Agent 的核心算法之一。留得太多，模型抓不住重点，延迟和账单一起上涨；丢得太多，模型忘了目标、忘了改过哪个文件、忘了刚才哪条路走不通，开始原地打转。

这一篇的答案可以压成一句话：

> **留下来的是「下一步还需要的工作集」，不是「已经发生过的事」。**

判断标准也很简单：下一条消息里，模型会不会用到它？会，就留；不会，就丢；不确定，就压成一句摘要。

## 一次请求里到底装了什么

一次模型请求的 `messages` 数组，通常由七种东西组成。

| 内容 | 典型来源 | 体积特征 | 变化频率 |
| --- | --- | --- | --- |
| 系统提示词 | `prompt::system_prompt` | 固定，约 30 行 | 启动 / 改配置时 |
| 项目约定 | `AGENTS.md` 逐层拼接 | 最多 20,000 字符 | 改文件时 |
| 项目上下文 | `NANOHERMES.md` | 无单独上限 | 改文件时 |
| 技能清单 | `skills::listing` | 每个技能一行 | 启动时 |
| 记忆块 | `memory::render_block` | 最多 2,400 字符 | 每轮重检索 |
| 对话消息 | user / assistant / tool | 随轮次增长 | 每轮 |
| 压缩摘要 | `summarize_messages` | 最多 300 词 | 超预算时 |

前三项和技能清单都属于系统消息，只在启动或配置变化时重建。记忆块虽然也在系统消息里，但每轮都会按标记替换。对话消息是增长的主体，压缩摘要则是为了截住这个增长。

大多数人的直觉是「对话消息最多」，实际不一定。一个 `read_file` 返回 2,000 行，经 `clamp` 截到 20,000 字节；五次这样的读取就是 100,000 字节，已经接近整个会话预算。真正吃掉窗口的往往不是模型说的话，而是工具的输出。

| 内容 | 估算体积 | 占 120k 预算 |
| --- | --- | --- |
| 系统提示词 + 项目约定 | 2,000–22,000 字符 | 2%–18% |
| 记忆块 | ≤2,400 字符 | ≤2% |
| 一条普通工具结果 | 200–2,000 字符 | 0.2%–1.7% |
| 一条被截断的工具结果 | 20,000 字节 | ≈17% |
| 最近 10 条消息 | 5,000–40,000 字符 | 4%–33% |
| 压缩摘要 | 约 1,500–2,500 字符 | 1%–2% |

这张表解释了一个常见现象：**上下文爆炸通常不是因为聊得多，而是因为某几次工具调用返回了太多东西。** 一个没有上限的 `cat`、一次全仓库 `grep`、一个把整页 HTML 塞回来的 `web_fetch`，就能让预算瞬间见底。

## 四层预算：从单文件到整个会话

NanoHermes 没有用一个统一的「上下文管理器」，而是在四个层次上分别设上限。每一层负责不同的失败模式。

| 层次 | 上限 | 位置 | 超限行为 |
| --- | --- | --- | --- |
| 单文件读取 | 4 MB | `fs::MAX_FILE_BYTES` | 拒绝，提示用 `offset` / `limit` 分块 |
| 搜索扫描 | 单文件 1 MB、200 条命中、单行 240 字符 | `search.rs` | 跳过超大文件，命中数到顶就停 |
| glob 枚举 | 500 个文件 | `search.rs` | 截断并注明 capped |
| 单工具返回 | 20,000 字节 | `Ctx.max_output` + `clamp` | 截断并注明省略多少 |
| 命令捕获 | stdout / stderr 各 256 KB | `shell::CAPTURE_BYTES` | 继续读但丢弃多余部分 |
| 后台任务 | 512 KB | `tasks::CAPTURE_BYTES` | 保留前 512 KB，注明省略 |
| 网页响应 | 2 MB | `web::MAX_RESPONSE_BYTES` | 截断响应体，继续提取文本 |
| 网页正文 | 默认 20,000 字符 | `web_fetch.max_chars` | 截断并注明 |
| 项目文档 | 20,000 字符 | `prompt::MAX_PROJECT_DOCS` | 截断并注明 |
| 技能正文 | 20,000 字符 | `skills::MAX_BODY_CHARS` | 截断并注明 |
| 记忆注入 | 2,400 字符、最多 4 条 | `memory::INJECT_*` | 放不下的条目不注入 |
| 会话总量 | 120,000 字符 | `CONTEXT_CHAR_BUDGET` | 摘要旧消息 |

为什么要分四层，而不是只在会话层做一次压缩？

**第一，压缩太晚。** 如果只在 120,000 字符时才处理，模型已经为前面那些巨型结果付过很多轮输入费了。工具层的上限在结果产生时就生效，成本立刻被截住。

**第二，压缩太贵。** 压缩本身是一次模型请求。如果每次都要把 4 MB 的文件内容读进来再摘要，摘要请求本身就可能超窗。工具层先拒绝，压缩层才有机会处理「值得摘要」的内容。

**第三，压缩会丢信息。** 一个 20,000 字节的工具结果被截断，模型至少还能看到前 20,000 字节；如果整段被摘要掉，细节就没了。能在工具层解决的，不要留到压缩层。

这四层的关系可以概括成一句话：**越靠近产生点，越应该硬截断；越靠近会话层，越应该做摘要。** 硬截断便宜、无损于「存在性」，但会丢细节；摘要贵、保留语义，但会引入模型误差。两者不能互相替代。

## 一条工具结果为什么能吃掉半个窗口

假设模型调用 `read_file` 读一个 2,000 行的文件，每行平均 80 字符。原始内容约 160,000 字符。

`fs::read_file` 不会把 160,000 字符直接交给模型。它先按 `limit` 取前 2,000 行，再交给 `dispatch`；`dispatch` 的最后一步是 `clamp(s, ctx.max_output)`，默认 20,000 字节。所以模型最终看到的是前 20,000 字节，加上一行 `… output truncated (N chars omitted)`。

这 20,000 字节进入历史后，还会被 JSON 序列化一次。换行变成 `\n`，引号变成 `\"`，再套上 `{"role":"tool","tool_call_id":"...","content":"..."}` 的外壳。体积会再涨几个百分点。假设涨 3%，就是 20,600 字符。

在 120,000 字符的预算里，这一条结果占 17%。五次这样的读取，就是 85%。如果再叠加系统提示词、项目文档和模型自己的解释，预算很快就满了。

| 场景 | 原始体积 | 回灌体积 | 占 120k |
| --- | --- | --- | --- |
| 读 200 行小文件 | 16,000 字符 | 16,000 字符 | 13% |
| 读 2,000 行大文件 | 160,000 字符 | 20,000 字节 | 17% |
| 全仓库 grep 200 条 | 48,000 字符 | 20,000 字节 | 17% |
| `git diff` 一个大改动 | 可能 500,000 字符 | 20,000 字节 | 17% |
| `web_fetch` 一篇文章 | 最多 2 MB | 默认 20,000 字符 | 17% |

注意最后一行：`web_fetch` 自己还有一层 `max_chars`，默认也是 20,000。也就是说，网页抓取和工具截断的上限恰好撞在一起。这不是巧合，而是同一个预算在两层各设了一次闸。

这也解释了一个设计选择：**所有内置工具的结果都要经过 `dispatch` 的 `clamp`，而不是让每个工具自己决定要不要截断。** 单个工具可能忘记，也可能低估自己的输出；统一在出口截断，才能保证「任何工具都不会一次性灌爆上下文」。

## 稳定前缀：系统消息为什么应该只读

系统消息在 `messages[0]`，每一轮都排在最前面。它的内容直接影响两件事：模型的行为，和推理服务的缓存命中。

NanoHermes 的系统消息由 `system_content` 构建，包含内置提示词、`NANOHERMES.md` 项目上下文和技能清单。它在三种时机重建：

| 时机 | 动作 | 原因 |
| --- | --- | --- |
| 新建会话 | `default_messages` 构建 | 从零开始 |
| 恢复会话 | `refresh_system` 替换 | 配置可能已经变了 |
| `reset` | 重新构建 | 开新话题，保留规则 |

注意「恢复会话」这一行：加载会话文件时，NanoHermes 不会原样使用文件里的系统消息，而是用当前配置重新生成并替换。系统消息是配置，不是对话。用户的权限模式、人设、AGENTS.md 都可能变；原样恢复会让会话带着过期规则跑。

但系统消息也不是完全只读的。记忆块每轮都会被 `set_memory_block` 替换，而记忆块挂在系统消息的末尾。这意味着系统消息的**前半段稳定，后半段每轮变化**。

对推理服务来说，前缀缓存通常按 token 前缀匹配。稳定的前半段可以命中缓存，记忆块之后的部分则每轮重新计算。这是一个可以接受的折中：把变化的东西放在系统消息末尾，至少保住了前面那一大段稳定前缀。

反过来，如果把记忆块插在系统提示词中间，或者每轮在系统消息开头加时间戳，前缀缓存就会整段失效。**上下文设计不只是「放什么」，还包括「放在哪、多久变一次」。**

## 系统提示词：短，而且分层

第一篇已经讲过系统提示词的五个来源，这里从「体积」角度再看一遍。

| 来源 | 内容 | 上限 | 变化频率 |
| --- | --- | --- | --- |
| 内置提示词 | 身份、六条规则、工作区路径 | 约 30 行 | 启动时 |
| 权限模式提示 | Goal / Debug / Plan 的一行约束 | 一行 | 切换模式时 |
| 用户人设 | `system_prompt` 配置 | 无单独上限 | 启动时 |
| `AGENTS.md` | 全局 + 祖先目录逐层 | 20,000 字符 | 改文件时 |
| `NANOHERMES.md` | 工作区根目录的项目上下文 | 无单独上限 | 改文件时 |
| 技能清单 | 每个技能的名字 + 一句话描述 | 每个技能一行 | 启动时 |

这里有两个不对称，值得单独说。

**第一，`AGENTS.md` 有 20,000 字符上限，`NANOHERMES.md` 没有。** `prompt::project_docs` 会在拼接后截断，并追加 `… project guidance truncated`；`system_content` 读 `NANOHERMES.md` 时是整文件读入，没有单独的 cap。它最终会被 120,000 字符的会话预算兜住，但在那之前，它已经进入了每一次请求。这是一个真实的边界：项目上下文文件应该保持短，不要把它当成文档仓库。

**第二，技能清单只放名字和描述，正文按需加载。** `skills::listing` 为每个技能生成一行，真正的说明在模型调用 `skill` 工具时才读取，读取时还有 20,000 字符上限。这个设计把「知道有什么」和「读到全部」分开了。清单很便宜，正文很贵，只在需要时支付。

```rust
fn system_content(cfg: &Config, skills: &[crate::skills::Skill]) -> String {
    let mut system = prompt::system_prompt(cfg);
    let project_ctx = cfg.workspace.join("NANOHERMES.md");
    if let Ok(text) = std::fs::read_to_string(&project_ctx) {
        if !text.trim().is_empty() {
            system.push_str("\n\n=== Project context (NANOHERMES.md) ===\n");
            system.push_str(text.trim());
            system.push('\n');
        }
    }
    if !skills.is_empty() {
        system.push('\n');
        system.push_str(&crate::skills::listing(skills));
    }
    system
}
```

系统提示词每轮都重发。一段 2,000 token 的提示词，跑 20 轮就是 40,000 token 的输入。提示词里的每一句都要为「每轮都值得」辩护：身份和工具规则值得，项目约定值得，三千字的公司介绍不值得。

## 项目文档：拼接顺序与 20,000 字符截断

`AGENTS.md` 不是只读工作区根目录的那一个。NanoHermes 会从全局配置目录开始，沿着文件系统根到工作区，逐层收集。

```rust
fn project_docs(workspace: &Path) -> Option<String> {
    let mut candidates: Vec<PathBuf> = Vec::new();
    if let Some(home) = std::env::var_os("HOME") {
        candidates.push(PathBuf::from(home).join(".nanohermes").join("AGENTS.md"));
    }
    let mut chain: Vec<&Path> = workspace.ancestors().collect();
    chain.reverse();
    for dir in chain {
        for name in DOC_NAMES {
            candidates.push(dir.join(name));
        }
    }
    // canonicalize 去重，读文件，拼成 parts
    let mut joined = parts.join("\n\n");
    if joined.len() > MAX_PROJECT_DOCS {
        let mut end = MAX_PROJECT_DOCS;
        while end > 0 && !joined.is_char_boundary(end) {
            end -= 1;
        }
        joined.truncate(end);
        joined.push_str("\n… project guidance truncated");
    }
    Some(joined)
}
```

顺序有两层含义。

| 层级 | 读取顺序 | 效果 |
| --- | --- | --- |
| 全局 | `~/.nanohermes/AGENTS.md` 最前 | 所有项目共享的偏好 |
| 外层目录 | 文件系统根 → 工作区 | 越大范围越靠前 |
| 内层目录 | 工作区最具体 | 越具体越靠后，优先级越高 |

「越具体越靠后」不是形式主义。模型读长文本时，靠后的内容通常更容易被当成当前指令。把工作区自己的规则放在最后，等于让它覆盖上层的通用规则。这不是硬编码的优先级，而是通过顺序表达的软优先级。

去重则处理另一种情况：同一个文件通过符号链接或多条路径到达时，只读一次。`canonicalize` 失败时退回原路径，宁可重复也不漏读。

20,000 字符的截断发生在拼接之后，所以它截掉的是「最后面」的内容——也就是最具体的项目规则。这是一个有意的取舍：全局偏好和上层约定先保住，工作区规则如果太长，只能牺牲尾部。更好的做法当然是把工作区的 `AGENTS.md` 写短，而不是依赖截断。

## 记忆注入：2,400 字符的硬预算

记忆块是系统消息里唯一每轮变化的部分。它的预算很小，但很硬。

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `INJECT_TOP_K` | 4 | 最多注入 4 条记忆 |
| `INJECT_CHAR_BUDGET` | 2,400 | 注入块的总字符预算 |
| `MAX_TEXT` | 400 | 单条记忆的长度上限 |
| 标记 | `BLOCK_START` / `BLOCK_END` | 定位并整体替换旧块 |

```rust
pub fn render_block(entries: &[&Entry]) -> String {
    if entries.is_empty() {
        return String::new();
    }
    let mut out = String::from(BLOCK_START);
    out.push_str("\n以下是从过往会话中检索到的相关记忆（由对话自动提炼，仅供参考；用户当前指令优先）：\n");
    let mut used = 0usize;
    for e in entries {
        let line = format!("\n- [{}] {}", e.kind.label(), e.text);
        if used + line.chars().count() > INJECT_CHAR_BUDGET {
            break;
        }
        used += line.chars().count();
        out.push_str(&line);
    }
    out.push('\n');
    out.push_str(BLOCK_END);
    out
}
```

这段代码的关键是 `break`，不是 `continue`。预算不够时，它不会跳过这一条去尝试更短的后面几条，而是直接停止。原因很简单：检索结果已经按相关度排好序，越往后越不重要；为了塞进一条低相关记忆而跳过一条高相关记忆，是得不偿失的。

`set_block` 则负责替换。它先找到旧块的起止标记，删掉整段，再把新块追加到系统消息末尾；新块为空时只删除，不追加。这个「替换而不是追加」的设计，是第一篇里提过的那个坑：如果每轮追加，系统提示词会随轮次线性增长，几轮之后就吃掉整个预算。

记忆块的文案里有一句「仅供参考；用户当前指令优先」。这不是客套。检索是按相关度算的，相关不等于正确；一条过期的偏好可能比当前指令更「相关」。把优先级写进注入文本，是让模型在冲突时有明确的裁决规则。

## 工具输出：每个工具都必须有上限

一个不能限制输出的工具，就是一个上下文炸弹。它可能来自一次 `cat` 大文件、一次全仓库搜索、一次网页抓取，或者一条输出日志的构建命令。

NanoHermes 在每个可能产生大输出的地方都设了闸。

| 工具 / 层 | 上限 | 超限行为 |
| --- | --- | --- |
| `read_file` | 文件 4 MB；默认 2,000 行 | 超大文件直接拒绝，提示分块 |
| `grep` | 单文件 1 MB；200 条命中；单行 240 字符 | 跳过超大文件，命中到顶停止 |
| `glob` | 500 个文件 | 截断并注明 capped |
| `run_command` | stdout / stderr 各 256 KB | 继续读但丢弃，结果注明截断 |
| 后台任务 | 512 KB | 保留前 512 KB，注明省略字节 |
| `web_fetch` | 响应 2 MB；正文默认 20,000 字符 | 截断响应，正文按 `max_chars` 截断 |
| `web_search` | 结果条数与摘要长度受限 | 返回前几条 |
| 所有内置工具 | 20,000 字节 | `dispatch` 统一 `clamp` |

这些数字不是拍脑袋来的，它们对应不同的失败模式。

**4 MB 是「读不读」的边界。** 超过这个大小，读进来也没有意义：模型不可能在 20,000 字节的截断里看到全貌，不如直接告诉它「文件太大，用 offset/limit 分块读」。这是一个拒绝，不是截断。

**1 MB 是「搜不搜」的边界。** `grep` 会遍历整个工作区。单文件超过 1 MB 时跳过，避免把压缩包、打包产物、日志文件当源码扫描。跳过是静默的，但结果里会体现「没搜到」，模型可以通过 `glob` 或 `read_file` 再确认。

**200 条命中是「够不够」的边界。** 搜索的目的通常是定位，不是穷举。200 条足够让模型找到目标文件；再多，模型也读不完。到顶后停止，并在结果末尾注明，避免模型误以为只有这些。

**256 KB 是「命令能喊多大声」的边界。** 一条构建命令可能输出几 MB 日志。`read_capped` 只保留前 256 KB，剩下的一边读一边丢——必须继续读，否则管道会阻塞，子进程会卡住。这是「丢弃但不能停止读取」的典型场景。

**20,000 字节是「一条结果能占多少窗口」的边界。** 它不关心工具是什么，所有内置工具的结果都从这里过。它是最外层的保险，防止某个工具忘记自己的上限。

## 三种截断语义：拒绝、截断、摘要

「截断」不是一个动作，而是三种不同的语义。混用它们，模型就会收到自相矛盾的信号。

| 语义 | 例子 | 模型看到什么 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| 拒绝 | `read_file` 超过 4 MB | `... is N bytes (> 4194304); read it in chunks` | 明确，不浪费上下文 | 需要模型再发一次请求 |
| 硬截断 + 说明 | `dispatch` 的 `clamp` | 前 20,000 字节 + `N chars omitted` | 便宜，保留开头 | 尾部信息丢失 |
| 计数上限 + 说明 | `grep` 到 200 条 | 200 条 + `stopped after 200 matches` | 结果可预期 | 可能漏掉后面的命中 |
| 响应截断 + 说明 | `web_fetch` 超过 2 MB | 文本 + `response truncated at ...` | 仍能提取正文 | 页面可能不完整 |
| 摘要 | `compact` | 一段 300 词摘要 | 保留语义，体积小 | 多一次请求，有信息损失 |

三种语义的共同要求是：**必须留下痕迹。** 静默截断是最坏的选择。模型看不到「被截断」的提示，就会把不完整的结果当成完整结果，基于缺失的信息做决定。一个 `grep` 如果悄悄只返回前 200 条，模型可能以为仓库里只有这些匹配，然后改错文件。

NanoHermes 的每条截断路径都带说明：

- `clamp`：`… output truncated (N chars omitted)`
- `grep`：`… stopped after 200 matches`
- `glob`：`… capped at 500 files`
- `read_file`：`… N more lines (total M)`
- `shell`：`… stdout truncated (N bytes not shown)`
- 后台任务：`… output truncated (N bytes not shown)`
- `web_fetch`：`[response truncated at 2097152 bytes]`

这些说明本身也占体积，但它们是上下文里性价比最高的几十个字符。没有它们，模型会基于错误的完整性假设行动。

## `clamp` 的实现：字节、字符边界与省略说明

`clamp` 只有十几行，但它处理了三个容易出错的细节。

```rust
fn clamp(s: String, max: usize) -> String {
    if s.len() <= max {
        return s;
    }
    let mut end = max;
    while end > 0 && !s.is_char_boundary(end) {
        end -= 1;
    }
    format!(
        "{}\n… output truncated ({} chars omitted)",
        &s[..end],
        s.len() - end
    )
}
```

**第一，上限按字节算。** `s.len()` 返回字节数，不是字符数。对纯 ASCII 输出（日志、代码、命令结果）两者一致；对中文输出，一个汉字占 3 个字节，20,000 字节大约只能装 6,600 个汉字。

**第二，切点必须落在 UTF-8 字符边界。** 如果直接 `&s[..max]`，而 `max` 恰好落在某个三字节汉字的中间，Rust 会 panic。`while !s.is_char_boundary(end)` 往前退，最多退两个字节，保证切片合法。

**第三，省略说明按字节算，却写成 chars。** 这是代码里的一个小不一致：`s.len() - end` 是字节数，文案却写 `chars omitted`。对 ASCII 没问题，对中文会高估省略的字符数。这个不一致不影响安全，但会让模型对「还剩多少」判断偏保守。知道这一点，比假装它不存在好。

| 输入 | 上限 | 输出 | 实际保留 |
| --- | --- | --- | --- |
| 纯 ASCII 30,000 字节 | 20,000 | 前 20,000 字节 + 说明 | 20,000 字符 |
| 中文 30,000 字节（10,000 字） | 20,000 | 前 20,000 字节 + 说明 | 约 6,666 字 |
| 边界落在汉字中间 | 20,000 | 退到 19,998 字节 | 合法 UTF-8 |

这也是为什么 `max_output` 的单位在文档里应该写「字节」而不是「字符」。源码里 `Ctx.max_output` 是 `usize`，没有单位；`clamp` 用 `len()`，实际是字节。文章里说「20,000 字节」比说「20,000 字符」准确。

## 压缩触发：120,000 字符是怎么算的

压缩的入口是 `compact`，它在每轮工具结果回填之后调用。

```rust
fn compact_with(&mut self, force: bool) -> usize {
    let size: usize = self.messages.iter().map(|m| m.to_string().len()).sum();
    if !force && (size <= CONTEXT_CHAR_BUDGET || self.messages.len() <= KEEP_RECENT + 1) {
        return 0;
    }

    let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
    while start < self.messages.len() && self.messages[start]["role"] == "tool" {
        start += 1;
    }
    if start <= 1 {
        return 0;
    }

    let dropped: Vec<Value> = self.messages.drain(1..start).collect();
    let note = match self.summarize_messages(&dropped) {
        Some(summary) => format!("[Earlier conversation summary]\n{summary}"),
        None => "[Earlier conversation was omitted to keep the context small]".to_string(),
    };
    self.messages.insert(1, json!({ "role": "system", "content": note }));
    dropped.len()
}
```

这里有四个判定。

| 判定 | 条件 | 不满足时 |
| --- | --- | --- |
| 预算 | `size > 120_000` | 不压缩 |
| 消息数 | `messages.len() > 11` | 不压缩（没有足够旧消息可丢） |
| 强制 | `force == true`（`/compact`） | 忽略前两个判定 |
| 切点 | `start > 1` 且不在 tool 消息上 | 不压缩 |

`size` 的计算方式是 `messages.iter().map(|m| m.to_string().len()).sum()`。它量的是**序列化后的 JSON 长度**，不是消息内容的长度。

`/compact` 命令走的是 `compact_now()`，它调用 `compact_with(true)` 强制压缩，跳过预算判定；交互式用户可以在预算还没爆之前主动整理一次。

这很重要。一条 `tool` 消息的 JSON 包含 `role`、`tool_call_id`、`content` 三个键，加上引号、冒号和转义。内容里的每个换行会变成两个字符 `\n`，每个双引号会变成 `\"`。所以 `size` 总是比「所有 content 长度之和」大一些。对代码和日志这种换行密集的内容，差距可能到 5%–10%。

| 内容 | 原始字符 | 序列化后 | 膨胀 |
| --- | --- | --- | --- |
| 一段 1,000 行日志 | 50,000 | 约 52,000 | 4% |
| 一段 2,000 行代码 | 80,000 | 约 84,000 | 5% |
| 大量引号的 JSON | 20,000 | 约 24,000 | 20% |

这也意味着 `CONTEXT_CHAR_BUDGET` 的 120,000 是「JSON 字符数」，不是「模型 token 数」，也不是「对话内容字符数」。把它当成一个保守的近似值，而不是精确的窗口大小。

## 为什么按字符算，不按 token 算

精确的上下文管理应该按 token 算。每个模型有自己的 tokenizer，同样的文本在不同模型上 token 数不同。按 token 算，才能精确卡住窗口。

NanoHermes 选择按字符算，原因有三个。

**第一，tokenizer 是重依赖。** 一个模型对应一份词表，几十 MB 到几百 MB。引入 tokenizer 意味着要么绑定某个模型家族，要么为每个模型维护一份。NanoHermes 的依赖只有三个 crate，不想为了估算引入第四第五个。

**第二，字符数足够做保守近似。** 对英文和代码，大约 3–4 个字符一个 token；对中文，大约 1–2 个字符一个 token。120,000 字符大致落在 30,000–60,000 token 之间。只要预算取得比真实窗口小，误差方向就是安全的。

**第三，字符数可解释。** 用户看到「上下文 120,000 字符」，能直观理解；看到「上下文 37,842 token」，反而不知道还剩多少空间。对一个交互式 CLI 来说，可解释性比精确性更重要。

| 文本类型 | 字符 / token（近似） | 120k 字符约合 |
| --- | --- | --- |
| 英文散文 | 4 | 30,000 token |
| 源代码 | 3–3.5 | 34,000–40,000 token |
| 中文 | 1–1.5 | 80,000–120,000 token |
| 中英混合 + 代码 | 2–3 | 40,000–60,000 token |

注意中文那一行：如果上下文里全是中文，120,000 字符可能已经接近 120,000 token，超过很多模型的窗口。这是字符预算的盲区。NanoHermes 的主要场景是代码和英文技术文本，中文占比通常不高；如果你的场景以中文长文为主，应该把预算调低，或者换成 token 估算。

## 保留最近 10 条，而不是最近 10 轮

压缩保留的是最近 10 **条消息**，不是最近 10 轮对话。

这两个单位差别很大。一轮对话的消息数取决于模型调用了多少工具：

| 一轮里的动作 | 消息数 |
| --- | --- |
| 用户提问 + 模型纯文本回答 | 2 条（user + assistant） |
| 用户提问 + 模型调 1 个工具 + 总结 | 4 条（user + assistant + tool + assistant） |
| 用户提问 + 模型调 5 个工具 + 总结 | 7 条（user + assistant + 5 tool + assistant） |
| 用户提问 + 3 轮工具调用，每轮 2 个 | 1 + 3 × (1 + 2) + 1 = 11 条 |

如果按「最近 10 轮」保留，最后一种情况会保留 110 条，预算根本压不住。按「最近 10 条」，无论一轮调了多少工具，保留的消息数都有上限。

```rust
let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
while start < self.messages.len() && self.messages[start]["role"] == "tool" {
    start += 1;
}
```

`saturating_sub` 处理「消息数少于 10」的情况，结果是 0；后面的 `start <= 1` 会直接返回，不会误删系统消息。

保留 10 条的目的是保证「最近一次工具交互」还在。一次带 5 个工具调用的轮次会占 7 条；再加一条 user、一条 assistant，刚好 9 条。10 条足够覆盖一次完整的工具往返，让模型知道刚才发生了什么。

---

## 切点：为什么不能落在 tool 消息中间

切点的第一版逻辑是「从倒数第 10 条开始，前面的都丢掉」。这会产生一个致命问题：如果倒数第 10 条正好是一条 `tool` 消息，丢掉它前面的 assistant 工具调用、却保留这条结果，历史里就会出现一条没有对应调用的工具结果。

下一轮请求，API 会直接拒绝：

> messages with role 'tool' must be a response to a preceding message with 'tool_calls'

更隐蔽的情况是：某些兼容层不拒绝，但模型会看到一组对不上的结果，开始胡言乱语。

NanoHermes 的处理是把切点往后推，直到它不是 `tool` 消息：

```rust
while start < self.messages.len() && self.messages[start]["role"] == "tool" {
    start += 1;
}
```

这个循环最多推过整轮的工具结果。推过之后，被丢掉的区域里包含完整的 assistant 调用和它的全部结果；保留的区域从一条非 tool 消息开始，历史仍然合法。

| 切点位置 | 丢掉的内容 | 保留的历史 | 合法性 |
| --- | --- | --- | --- |
| 落在 user 上 | 旧的 user 及之前 | user + assistant + tool... | 合法 |
| 落在 assistant 上 | 旧的 assistant 及之前 | assistant + tool... | 合法 |
| 落在 tool 上（未调整） | assistant 调用，但保留 tool | 孤立的 tool | 非法 |
| 落在 tool 上（调整后） | 整轮调用与结果 | 下一条非 tool 消息 | 合法 |

还有一个边界：`start <= 1` 时直接返回。`messages[0]` 是系统消息，`messages[1]` 是摘要或第一条对话。如果切点落在 1 或更前，说明没有足够的旧消息可丢，压缩应该放弃，而不是把系统消息也丢掉。

这个「切点不能落在 tool 上」的规则，是第一篇里「历史必须合法」不变量的直接延伸。压缩不是随便删一段，它必须维持消息序列的配对关系。

## 摘要：一次额外的模型请求

压缩不是把旧消息删掉就完事。它要让模型用一段话概括被丢掉的内容，这段话再作为一条 `system` 消息插回历史。

```rust
fn summarize_messages(&self, messages: &[Value]) -> Option<String> {
    if messages.is_empty() {
        return None;
    }
    let mut excerpt = String::new();
    for m in messages {
        let role = m.get("role").and_then(|r| r.as_str()).unwrap_or("?");
        let content = match m.get("content") {
            Some(Value::String(s)) => s.clone(),
            Some(Value::Array(arr)) => arr
                .iter()
                .filter_map(|p| p.get("text").and_then(|t| t.as_str()))
                .collect::<Vec<_>>()
                .join(" "),
            _ => String::new(),
        };
        let content = content.trim();
        if content.is_empty() {
            continue;
        }
        excerpt.push_str(&format!("{role}: {}\n", content));
    }
    if excerpt.trim().is_empty() {
        return None;
    }
    match llm::summarize(&self.cfg, &excerpt) {
        Ok(s) if !s.is_empty() => Some(s),
        _ => None,
    }
}
```

这段代码先做一件事：把消息压成 `role: content` 的纯文本。多模态消息只取 `text` 部分，图片 URL 不进入摘要；内容为空的消息直接跳过。

然后调用 `llm::summarize`：

```rust
pub fn summarize(cfg: &Config, text: &str) -> Result<String, String> {
    let mut summarizer_cfg = cfg.clone();
    summarizer_cfg.stream = false;
    let system = "You are a conversation summarizer for a coding agent. Write a concise summary \
                  of the excerpt below, preserving: the user's goal, key decisions, file paths \
                  changed, and current task state. Use at most 300 words. Reply with the summary only.";
    let messages = vec![
        json!({ "role": "system", "content": system }),
        json!({ "role": "user", "content": text }),
    ];
    let turn = chat(&summarizer_cfg, &messages, &Value::Array(vec![]), |_| {})?;
    Ok(turn.content.trim().to_string())
}
```

注意三个参数：`stream = false`（摘要不需要流式）、`tools = []`（不允许摘要器调用工具）、`temperature` 沿用主配置（默认 0）。摘要是一次普通的、非流式的、无工具的模型请求。

## 摘要输入里有什么，没有什么

这是整篇文章最容易被忽略的一节。

`summarize_messages` 只读取每条消息的 `content`。它**不读取** `tool_calls` 里的 `function.name` 和 `function.arguments`。

| 消息类型 | 进入摘要的内容 | 不进入摘要的内容 |
| --- | --- | --- |
| user | 文本（多模态只取 text） | 图片数据 |
| assistant（纯文本） | `content` | 无 |
| assistant（工具调用） | 通常为空，整条跳过 | `tool_calls` 的 name、arguments、id |
| tool | 工具结果全文 | `tool_call_id`、对应的调用名 |

这意味着摘要器看到的序列可能是这样的：

```text
user: 把 README 里的安装命令改成 pnpm
assistant: 我先看看 README。
tool: 1→# Project
2→
3→## Install
4→npm install
...
assistant: 已经改成 pnpm。
```

它能看到「读了 README」「结果是这些行」，但看不到「调用的是 `read_file`，参数是 `path=README.md`」。如果工具结果本身没有包含文件名，摘要就会丢失「改的是哪个文件」这条关键信息。

这是一个真实的局限，也是摘要提示词要求「保留 file paths changed」的原因：既然结构化字段进不来，就只能靠工具结果里的路径和模型的文本描述来补。NanoHermes 的 `read_file` 输出不带文件名，所以摘要器只能从上下文推断；`edit_file` 的结果带路径，通常能补上。

如果你要改进这一点，有两个方向：

1. **在摘要输入里保留工具名和参数。** 把 assistant 消息的 `tool_calls` 渲染成 `assistant: [read_file] {"path":"README.md"}`，而不是跳过。
2. **让工具结果自带身份。** 每个工具返回时带上「我在哪个文件上做了什么」，例如 `read_file README.md`。

两种做法都会增加摘要输入的长度，但能显著减少「摘要后不知道改了哪个文件」的问题。

## 摘要提示词要求保留的四类信息

摘要提示词很短，只列了四类必须保留的信息：

> the user's goal, key decisions, file paths changed, and current task state. Use at most 300 words.

| 保留项 | 回答的问题 | 丢失后的症状 |
| --- | --- | --- |
| 用户目标 | 我们到底在做什么？ | 模型开始做无关的事，或者重复问需求 |
| 关键决策 | 为什么选这个方案？ | 模型推翻已定方案，来回改 |
| 改过的文件路径 | 动过哪些地方？ | 模型重复修改，或者漏掉某个文件 |
| 当前任务状态 | 进行到哪一步？ | 模型重复已完成的工作，或者不知道下一步 |

这四类信息有一个共同点：**它们都是「下一步」需要的，而不是「过去」的完整记录。** 摘要不保留逐字对话，不保留每个工具的输出，也不保留模型的解释过程。它保留的是能让下一个模型接上手的「工作交接单」。

300 词的上限也不是随便定的。一段 300 词的摘要大约 1,500–2,500 字符，占 120,000 预算的 1%–2%。如果摘要写到 2,000 词，它就变成了另一种上下文膨胀：压缩一次，塞回去一大段。

| 摘要长度 | 字符估算 | 占预算 | 适用 |
| --- | --- | --- | --- |
| 100 词 | 500–800 | <1% | 短任务 |
| 300 词 | 1,500–2,500 | 1%–2% | 默认 |
| 1,000 词 | 5,000–8,000 | 4%–7% | 长任务，但会挤占最近消息 |

摘要提示词里还有一句 `Reply with the summary only`。这是为了防止模型在摘要前后加「好的，以下是摘要」这类客套话。客套话也会进入上下文，而且没有任何信息量。

## 摘要失败时的降级

摘要是一次网络请求，可能失败：API 超时、限流、返回空内容、摘要器把内容全滤掉。`summarize_messages` 的返回类型是 `Option<String>`，失败就返回 `None`。

`compact_with` 对 `None` 的处理是插入一行占位说明：

```rust
let note = match self.summarize_messages(&dropped) {
    Some(summary) => format!("[Earlier conversation summary]\n{summary}"),
    None => "[Earlier conversation was omitted to keep the context small]".to_string(),
};
```

| 失败原因 | `summarize_messages` 的行为 | 最终结果 |
| --- | --- | --- |
| 被丢弃的消息为空 | 返回 `None` | 插入占位说明 |
| 所有消息 content 都为空 | 返回 `None` | 插入占位说明 |
| 摘要请求失败 | 返回 `None` | 插入占位说明 |
| 摘要返回空字符串 | 返回 `None` | 插入占位说明 |
| 摘要成功 | 返回 `Some` | 插入摘要 |

为什么失败也要插入一行，而不是什么都不插？

因为模型需要知道「有一段历史被省略了」。如果压缩后历史直接从系统消息跳到最近的工具结果，模型会以为自己一直只有这么点上下文，可能重复已经做过的工作，或者对用户的指令感到困惑。一行 `[Earlier conversation was omitted ...]` 至少告诉它：前面还有东西，只是没带过来。

这也是「截断必须留痕」原则在压缩层的体现。失败不可怕，静默失败才可怕。

## 摘要之后的消息序列

压缩前后的消息序列对比，能直观看出这套算法的效果。

压缩前（示意）：

| 序号 | role | 内容 |
| --- | --- | --- |
| 0 | system | 系统提示词 + 记忆块 |
| 1 | user | 第一轮指令 |
| 2 | assistant | 工具调用 A |
| 3 | tool | A 的结果 |
| 4 | assistant | 工具调用 B |
| 5 | tool | B 的结果 |
| ... | ... | ... |
| n-10 | user | 最近的指令 |
| n-9 | assistant | 工具调用 C |
| n-8 | tool | C 的结果 |
| n-7 | assistant | 总结 |

压缩后：

| 序号 | role | 内容 |
| --- | --- | --- |
| 0 | system | 系统提示词 + 记忆块 |
| 1 | system | `[Earlier conversation summary]` + 300 词摘要 |
| 2 | user | 最近的指令 |
| 3 | assistant | 工具调用 C |
| 4 | tool | C 的结果 |
| 5 | assistant | 总结 |

注意三点。

**第一，系统提示词仍然是 0。** 摘要插在 1，不替换系统提示词。这样配置、规则、记忆块都保留。

**第二，摘要是 `system` 角色，不是 `assistant`。** 它是「背景知识」，不是「模型说过的话」。用 system 角色能让模型把它当成指令性上下文，而不是对话历史。

**第三，最近 10 条原样保留。** 摘要负责旧历史，最近的消息负责「刚才发生了什么」。两者分工明确。

多次压缩时，旧摘要会被再次摘要。第二次压缩的 `dropped` 区域包含第一次插入的 system 摘要，`summarize_messages` 会把它的 content 也拼进 excerpt。这意味着摘要会「滚动合并」，不会越积越多，但也会有**摘要的摘要**带来的信息漂移：第一次摘要丢掉的细节，第二次无法恢复；第二次摘要还可能把第一次的错误结论继续放大。

## 什么该留：五类信息

把「下一步会不会用到」这个标准展开，可以落成五类信息。

| 类别 | 具体内容 | 为什么留 | 通常在哪 |
| --- | --- | --- | --- |
| 目标与约束 | 用户要什么、不许做什么、验收标准 | 决定方向，丢了就白干 | 最近的 user 消息、摘要 |
| 关键决策 | 选了什么方案、为什么否决另一个 | 防止反复横跳 | assistant 文本、摘要 |
| 改动路径 | 改过哪些文件、新增了哪些文件 | 防止重复修改、漏改 | 工具结果、摘要 |
| 失败尝试 | 哪条路走不通、报了什么错 | 防止重复踩坑 | 工具结果、assistant 文本 |
| 当前状态 | 做到哪一步、下一步做什么 | 接续任务 | 最近几条消息 |

这五类里，前四类可以进摘要，第五类必须留在最近消息里。原因是「当前状态」变化最快，摘要一次就可能过期；而目标、决策、路径、失败尝试相对稳定，适合压缩成一段话。

一个反例是「完整的文件内容」。很多人觉得「模型读过这个文件，应该留着」，于是把 2,000 行代码留在历史里。但模型下一步真正需要的是「这个文件里哪个函数要改」，而不是整份文件。完整内容应该留在磁盘上，需要时再读；上下文里留路径、行号和结论就够了。

---

## 什么该丢：四类内容

| 内容 | 为什么可丢 | 例外 |
| --- | --- | --- |
| 重复的寒暄与确认 | 「好的」「收到」「继续」不含决策信息 | 用户在这些话里加了新约束 |
| 完整文件内容 | 磁盘上有，需要时可重读 | 文件已被删除或外部修改 |
| 成功命令的长输出 | 退出码为 0 时，输出通常只是过程 | 输出里有测试结果、警告、关键日志 |
| 已摘要的中间步骤 | 摘要已经保留了结论 | 需要逐字复现某个步骤 |

「成功命令的长输出」这一条最容易判断错。`cargo build` 成功时输出几百行编译日志，模型通常只需要知道「成功了」；但如果输出里有 warning，warning 可能是下一步的线索。NanoHermes 的 shell 工具不会自动区分，它把退出码和输出一起返回，由模型自己判断。压缩时，摘要器可能会把成功的日志概括成「构建通过」，warning 就丢了。

这就是为什么「什么该丢」不能完全交给摘要器。摘要器只看 content，不懂任务；它可能把一条关键的 warning 当成噪音。更稳妥的做法是：在工具层就把「成功但啰嗦」的输出压短，比如只保留退出码和最后几行；而不是留给压缩层去猜。

## 上下文、记忆、会话：三个不同的东西

这三个概念经常被混为一谈，但它们的生命周期和用途完全不同。

| 维度 | 上下文 | 记忆 | 会话 |
| --- | --- | --- | --- |
| 存储 | 内存里的 `messages` | `~/.nanohermes/memory.json` | `--session` 指定的 JSON 文件 |
| 生命周期 | 一次请求 / 一个轮次 | 跨会话长期 | 一次会话 |
| 内容 | 完整消息序列 | 提炼后的短句 | 完整消息序列 |
| 体积 | 最多 120,000 字符 | 最多 500 条，每条 400 字符 | 不设上限 |
| 检索 | 无，全量发送 | BM25 + 中英文分词 | 无，启动时整体加载 |
| 注入 | 直接作为 `messages` | 最多 4 条、2,400 字符 | 不注入，恢复为 `messages` |

**上下文**是「这一次请求要带什么」，**记忆**是「跨会话值得记住什么」，**会话**是「这次对话的完整存档」。

会话文件不设上限，因为它保存在磁盘上，不参与每次请求。加载会话时，它会被读回 `messages`，然后由上下文预算接管。记忆则是另一个方向：它从会话里提炼，但不保存全文；下次会话按当前指令检索，只注入最相关的几条。

`replace_messages` 是这三个概念在 daemon 模式下的交汇点：一个 Agent 实例可以服务多个隔离会话，通过替换 `messages` 切换上下文。记忆和会话文件仍然是各自独立的。

```rust
pub fn replace_messages(&mut self, msgs: Vec<Value>) -> Vec<Value> {
    std::mem::replace(&mut self.messages, msgs)
}
```

这也解释了为什么 token 用量要上报增量而不是累计值：同一个 Agent 可能在不同会话之间切换，累计值会把这些互不相关的任务加在一起。上下文可以替换，账本必须按轮次分清。

## 压缩的代价：延迟、损失与漂移

压缩不是免费的。它至少有三类代价。

| 代价 | 表现 | 缓解 |
| --- | --- | --- |
| 延迟 | 压缩时多一次模型请求，用户多等一轮 | 只在超预算时触发；`/compact` 手动控制 |
| 信息损失 | 旧细节被 300 词摘要替代 | 保留最近 10 条；摘要要求保留路径与决策 |
| 摘要漂移 | 多次压缩后，摘要的摘要越来越抽象 | 尽量在任务边界压缩；不要频繁压缩 |
| 缓存失效 | 摘要插入 `messages[1]`，后续前缀变化 | 接受；压缩本来就不频繁 |
| 成本 | 摘要请求本身消耗 token | 摘要输入是旧历史，通常小于重发成本 |

延迟是最容易被低估的。压缩发生在工具结果回填之后、下一轮请求之前，用户会感觉「这一轮特别慢」。如果压缩又触发了一次摘要请求，延迟就是「工具时间 + 摘要时间 + 下一轮模型时间」。在长任务里，这可能多出几秒到十几秒。

信息损失则是结构性的。摘要器只看到 `role: content`，看不到工具名和参数；它可能把「改了 `src/main.rs` 的第 42 行」概括成「修改了主文件」。下一次模型想继续改，就得重新读文件。这不是摘要器的错，是输入里就没有这些信息。

摘要漂移更隐蔽。第一次摘要保留了「用户要求用 pnpm」，第二次摘要可能把它合并成「包管理器相关改动」，第三次就只剩「依赖调整」。每一轮压缩都在做有损压缩，损失会累积。缓解办法是：**在任务边界主动压缩，而不是等到预算爆掉；在摘要提示词里把「用户目标」放在第一位；关键约束不要只依赖摘要，放进 `AGENTS.md` 或记忆。**

## 一个 12 轮任务的示意账本

下面是一个按默认上限估算的账本，用来说明压缩在什么时候发生。数字是示意，不是某次真实运行的精确值。

| 轮次 | 消息数 | 序列化字符 | 动作 | 压缩后字符 |
| --- | --- | --- | --- | --- |
| 1 | 3 | 4,000 | 读一个文件 | 4,000 |
| 2 | 6 | 12,000 | 读两个文件 | 12,000 |
| 3 | 10 | 26,000 | grep + 读文件 | 26,000 |
| 4 | 14 | 38,000 | 编辑 + 跑测试 | 38,000 |
| 5 | 20 | 52,000 | 读测试输出 | 52,000 |
| 6 | 24 | 64,000 | 再改一处 | 64,000 |
| 7 | 30 | 78,000 | 读大文件（截断 20k） | 78,000 |
| 8 | 36 | 96,000 | 跑全量测试 | 96,000 |
| 9 | 42 | 118,000 | 再读一个文件 | 118,000 |
| 10 | 48 | 132,000 | 超过 120k，触发压缩 | 约 32,000 |
| 11 | 54 | 46,000 | 继续修改 | 46,000 |
| 12 | 60 | 60,000 | 完成 | 60,000 |

几个观察：

- **压缩不是均匀发生的。** 第 10 轮之前一直在增长，第 10 轮一次掉回 32,000，然后重新增长。
- **压缩后不是「很小」，而是「大约最近 10 条 + 摘要」。** 最近 10 条可能就有 20,000–30,000 字符，加上摘要 2,000，就是 30,000 左右。
- **总输入成本远大于最后的消息数。** 每一轮都要重发当时的历史。前 9 轮的平均历史约 60,000 字符，9 轮就是 540,000 字符的输入；压缩后又要重新累积。
- **压缩只能降低单次请求大小，不能降低总成本。** 总成本是各轮历史之和，压缩把曲线压下去一次，但曲线还会继续涨。

| 指标 | 数值（示意） |
| --- | --- |
| 单次请求峰值 | 约 132,000 字符 |
| 压缩次数 | 1 次 |
| 压缩后大小 | 约 32,000 字符 |
| 12 轮累计输入 | 约 700,000 字符 |
| 压缩节省的后续输入 | 每轮约 100,000 字符 × 剩余轮数 |

这也解释了为什么「工具输出上限」比「压缩」更重要：压缩只在超预算时发生一次，而工具输出上限在每一次工具返回时都生效。前者是消防栓，后者是防火门。

## 七个常见上下文陷阱

| 陷阱 | 症状 | 正确做法 |
| --- | --- | --- |
| 只截断，不留痕 | 模型以为结果完整，基于缺失信息行动 | 每条截断都带 `omitted` / `truncated` 说明 |
| 在 UTF-8 中间截断 | Rust panic，或者输出乱码 | 退到 `is_char_boundary` |
| 按「最近 N 轮」保留 | 一轮调 5 个工具，保留 10 轮就是 70 条 | 按消息条数保留 |
| 切点落在 tool 上 | 历史出现孤立工具结果，API 400 | 切点后移到非 tool 消息 |
| 摘要包含完整工具参数 | 摘要输入膨胀，甚至超过摘要器窗口 | 只取 content，或显式渲染关键字段 |
| 每轮追加记忆块 | 系统消息线性增长 | 按标记整体替换 |
| 纯聊天不触发压缩 | 长对话没有工具调用，历史只增不减 | 定期 `/compact`，或把压缩移到每次请求前 |

最后一条值得展开。`compact` 的调用点在工具结果回填之后；如果一轮对话没有工具调用，循环在 `turn.tool_calls.is_empty()` 处就 `break` 了，根本走不到 `compact`。所以纯聊天会话不会自动压缩，直到某一轮调用了工具，或者用户手动执行 `/compact`。

这是一个真实的边界。对 coding agent 来说，长任务几乎都伴随工具调用，所以影响不大；但如果你把 NanoHermes 当纯聊天用，就要知道这个限制。

还有一个更隐蔽的陷阱：**把压缩当成「删除」**。压缩不是删除，是替换成摘要；摘要本身也在上下文里占体积。如果摘要写得比原文还长，压缩就变成了负优化。300 词的上限就是防止这件事。

## 如何验证压缩没有坏

压缩是少数「看起来跑通了，其实已经坏了」的机制。它不会立刻报错，模型会在几轮之后开始重复劳动或答非所问。

可以用下面这组检查。

| 检查 | 方法 | 期望 |
| --- | --- | --- |
| 历史合法性 | 检查每条 tool 消息前是否有对应 `tool_call_id` 的 assistant 调用 | 一一配对 |
| 切点合法性 | 压缩后第一条非系统消息不是 tool | 不是 tool |
| 摘要存在 | 压缩后 `messages[1]` 是 system 摘要或占位说明 | 存在 |
| 预算生效 | 压缩后序列化总字符 < 120,000 | 小于预算 |
| 最近消息完整 | 最近 10 条与原历史尾部一致 | 未被改写 |
| 模型知道目标 | 压缩后问「我们在做什么」 | 能答出目标与当前状态 |
| 模型知道路径 | 问「改过哪些文件」 | 能答出关键路径 |

其中「模型知道目标」和「知道路径」是最实用的两项。它们直接检验摘要提示词的四类信息有没有被保留。如果模型答不出，说明摘要丢了关键内容，应该调整摘要提示词，而不是继续压缩。

自动化测试也可以覆盖前五项。NanoHermes 的 `memory.rs` 里有 `block_round_trip_replaces_instead_of_accumulating` 这样的测试，验证记忆块替换而不是追加；`compact` 也可以写类似的测试：构造 20 条消息，强制压缩，断言系统消息还在、最近 10 条没变、中间多了一条摘要、没有孤立 tool。

## 收尾：下一篇讲记忆

上下文解决的是「这一次请求带什么」，记忆解决的是「下一次会话还记得什么」。

两者共享同一个约束：**体积有限，必须选择。** 上下文的选择发生在每一轮，记忆的选择发生在会话结束和下一次会话开始。上下文用 120,000 字符的预算和 10 条最近消息；记忆用 4 条、2,400 字符的注入预算，以及 500 条、每条 400 字符的存储上限。
