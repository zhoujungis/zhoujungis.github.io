## 前言：一个"功能闪回"的投诉

你做了一个新结算页，决定灰度上线：先放 10% 用户，观察两天没问题，然后调到 20% 扩大范围。

调完的第二天，客服转来一堆投诉：

> "昨天我还能用新界面，今天怎么又变回旧的了？"

你查了日志，代码没动，开关配置也只是把 `10` 改成了 `20`。那问题出在哪？

答案藏在一行看起来很正常的代码里：

```python
def is_enabled(user_id, percent):
    return (hash(user_id) % 100) < percent   # ← 看起来没问题，其实有坑
```

**问题在于：当 `percent` 从 10 变成 20 时，`hash(user_id) % 100 < 20` 这个判断里，原本 `< 10` 的用户确实还满足 `< 20`——但如果你的实现是让桶数量跟着百分比变（比如 `hash(user_id) % percent_bucket_count`），整个分桶就会重排。**

我用 2 万个用户实测了这个现象：

```
灰度从 10% 扩到 20% 后，原有用户是否还在灰度内
    固定桶空间（正确写法）: 保留 100.0%  ✅
    动态取模（错误写法）  : 保留  48.2%  ⚠️  一半用户被踢出
```

**48.2%**——这就是那位用户"功能突然消失"的原因。他昨天在灰度里，今天被重新洗牌洗出去了。

这个坑，以及围绕它的整套工程实践，就是这篇文章要讲清楚的：

## 1. 灰度发布到底解决什么问题

先说清楚它不是什么。灰度发布**不是**"把 bug 藏起来"——它是把**发布这个动作的风险，从"全有或全无"变成"可控的连续变量"**。

传统发布是这样的：

```
写完代码 → 合并 → 部署 → 100% 用户立刻生效
                          ↑
                    如果这里炸了，影响 100% 用户
                    回滚 = 重新部署 = 几分钟到几十分钟
```

特性开关把"部署"和"发布"拆开了：

```
写完代码 → 合并 → 部署（开关默认关闭，用户无感知）
                      ↓
                  按 1% → 5% → 20% → 50% → 100% 逐步放开
                      ↑
                任何一步指标异常 → 改配置 → 秒级生效，影响面可控
```

两个动作被解耦了：

| 概念 | 含义 | 频率 |
|---|---|---|
| Deploy（部署） | 把代码放到服务器上 | 一天多次 |
| Release（发布） | 让用户看到新功能 | 独立决定，随时 |

**这个解耦带来三个直接收益**：

1. **爆炸半径可控**：1% 灰度时出事，99% 用户完全无感。
2. **回滚从"重新部署"变成"改配置"**：不需要重新构建、不需要重启服务，秒级生效。这是特性开关最有价值的一点——**回滚速度决定了你对事故的掌控力**。
3. **可以随时"熔断"**：这就是 Kill Switch（见下一节），开关不只是给新功能用，也是给线上事故准备的消防栓。

代价是什么？**代码复杂度上升，以及开关会变成技术债**。这两点后面会专门讲。

## 2. 五类特性开关及各自的生命周期

很多人把所有开关都当成"同一类东西"，这是技术债的根源。**开关的类型决定它该活多久**：

| 类型 | 用途 | 生命周期 | 命名前缀 | 典型例子 |
|---|---|---|---|---|
| Release 发布开关 | 隐藏未完成的功能 | **短，1~4 周** | `release-` | `release-checkout-v2` |
| Experiment 实验开关 | A/B 测试、多方案对比 | 中，2~6 周 | `exp-` | `exp-pricing-layout` |
| Ops 运维开关 | 调整运行参数、降级 | **长，数月到永久** | `ops-` | `ops-disable-email-push` |
| Permission 权限开关 | 按套餐/角色控制功能 | 永久 | `perm-` | `perm-advanced-analytics` |
| Kill Switch 熔断开关 | 紧急关停某功能/依赖 | 永久 | `kill-` | `kill-openai-call` |

**核心区分标准是"它什么时候该消失"**：

- **Release 和 Experiment 开关应该被删除**。功能全量后，条件分支留在代码里就是死代码。业界共识：**发布开关全量后 30 天内必须清理**。
- **Ops / Permission / Kill Switch 应该长期存在**。它们的价值是持续的——你会永远需要一个"一键关掉邮件推送"的开关。

我见过最常见的错误是**把 Release 开关当 Permission 开关用**：功能早全量了，但开关一直留着"以防万一"，两年后没人敢删——因为没人知道删了会发生什么。

**命名规范不是洁癖，是让开关可被治理的前提。** 一个好名字自带信息：

```
❌ new_feature      测试用、没有语义
❌ test123
❌ flag_a

✅ release-checkout-v2         类型 + 功能 + 版本
✅ exp-onboarding-flow-2026q3  类型 + 功能 + 时间
✅ kill-stripe-webhook         类型 + 依赖
```

带前缀的好处是**可以自动化治理**——用一条正则就能扫出所有 Release 开关，检查哪些超期未清理。

## 3. 分桶算法：为什么必须用固定桶空间

回到开头的 bug。要理解它，先要理解灰度的核心机制：**分桶（Bucketing）**。

灰度的本质是：**把用户映射到 0~9999 的一个桶号，然后用桶号决定这个用户是否在灰度内。**

```
用户 "u_1001"  →  哈希  →  桶号 5633  →  5633 < 2000 ? (20% 灰度)  →  否
用户 "u_1002"  →  哈希  →  桶号 0871  →  0871 < 2000 ?              →  是
```

关键约束：**同一个用户必须永远落在同一个桶里**。这就是"粘性"（stickiness）。

### 错误写法：桶数量跟着百分比变

```python
def is_enabled_wrong(user_id, percent):
    buckets = int(percent)                      # ← 桶数量在变！
    return (hash(user_id) % buckets) < buckets * percent / 100
```

当 `percent = 10`，桶数是 10，用户落在 0~9 号桶，前 1 个桶通过。
当 `percent = 20`，桶数是 20，用户重新对 20 取模——**同一个用户可能从 3 号桶跳到 17 号桶**。

```
10% 时：hash % 10 = 3   → 3 < 1  → 不在灰度 ❌
20% 时：hash % 20 = 17  → 17 < 4 → 不在灰度
         等等，3 和 17 都是同一个用户，但落点完全变了
```

实测结果：**只有 48.2% 的用户保持原状态**，超过一半被无缘无故踢出或塞进灰度。

### 正确写法：固定桶空间

```python
BUCKET_SPACE = 10_000    # 固定不变，与百分比无关

def bucket_of(user_id: str, salt: str) -> int:
    """把用户稳定映射到 [0, BUCKET_SPACE) 的某个桶。"""
    raw = f"{salt}:{user_id}".encode()
    h = int(hashlib.blake2b(raw, digest_size=8).hexdigest(), 16)
    return h % BUCKET_SPACE

def in_rollout(user_id: str, percent: float, salt: str) -> bool:
    """percent=20 表示桶号 < 2000 的用户进入灰度。"""
    return bucket_of(user_id, salt) < BUCKET_SPACE * percent / 100
```

**关键点：桶空间固定为 10000，百分比只是"阈值线"。** 扩灰度就是移动这条线，用户桶号永远不变：

```
percent=10  →  阈值线在 1000   [0....1000|....................9999]
percent=20  →  阈值线在 2000   [0........2000|................9999]
                                          ↑
                                只是把线往右移，已在线内的用户不动
```

实测验证：**10% → 20% 时，原有用户 100% 保持**。

**一个额外的收益：单向性。** 阈值线只往右移（灰度只会扩大不会随机缩小），所以"进了灰度的用户不会莫名退出"。需要缩小灰度时（回滚），才是有意为之。

### 实测数据：百分比精度

固定桶空间的方案，实测百分比与目标值高度吻合（20 万用户样本）：

| 目标 | 实测 | 偏差 |
|---|---|---|
| 1% | 0.991% | -0.009pp |
| 5% | 4.939% | -0.061pp |
| 10% | 9.941% | -0.059pp |
| 25% | 25.008% | +0.008pp |
| 50% | 50.103% | +0.103pp |
| 90% | 89.967% | -0.033pp |

最大偏差 **0.1 个百分点以内**，10 个桶的分布均匀性最大偏差 **1.00%**。桶空间越大越精确，10000 桶对大多数场景足够。

## 4. 灰度分流的六个实现细节

分桶只是第一步。下面六个细节决定了你的灰度在生产环境是否可靠。

### 细节一：每请求只算一次哈希

哈希是有成本的。实测（20 万次调用）：

```
算哈希  blake2b: 1.074 us/次
算哈希     md5 : 2.135 us/次
算哈希  sha256: 2.046 us/次
读缓存 + 比较  : 0.073 us/次     ← 比算哈希快 15~30 倍
```

blake2b 比 md5 快约一倍，这也是我选它做分桶哈希的原因。但真正的重点是：

**如果你在一个请求里检查了 10 个开关，就算 10 次哈希。** 正确做法是**算一次，缓存到请求上下文**：

```python
class RequestContext:
    def __init__(self, user_id):
        self.user_id = user_id
        self._buckets = {}

    def bucket(self, salt):
        # 每个 salt 只算一次，结果在本次请求内复用
        if salt not in self._buckets:
            self._buckets[salt] = bucket_of(self.user_id, salt)
        return self._buckets[salt]
```

### 细节二：不同开关必须用不同的 salt

同样的用户 + 同样的哈希函数 = **同样的分桶**。如果你有两个独立的实验，都用 `bucket_of(user_id, "salt")`，那么：

```
两个 20% 灰度实验的用户重叠率实测
    共用 salt : 100.0%   ← 完全是同一批人
    独立 salt :  20.4%   ← 相互独立 ✅
```

**共用 salt 会让实验互相污染**：你的"新版定价页"实验和"新版导航"实验会命中同一批用户，如果这批人恰好消费能力不同，两个实验的结论都会被扭曲。

**每个开关用自己唯一的 salt（通常直接用开关名）**，实测重叠率降到 20.4%，符合两个独立 20% 集合的期望值（20%）。

### 细节三：多实例必须结果一致

灰度服务通常是多实例部署的。如果分桶依赖共享状态（比如"第 N 个进灰度的用户"这种计数器），实例之间就会不一致。

**解法：分桶必须是纯函数**——只依赖 `user_id` 和 `salt`，不依赖任何外部状态。

实测：5 个"实例"各自独立计算 5000 个用户的桶，**不一致数 0**。这就是为什么分桶绝对不能依赖 Redis 计数器或数据库自增 ID。

### 细节四：确定的分桶标识

分桶用的标识必须**在用户整个会话甚至生命周期内稳定**：

| 标识 | 是否合适 | 问题 |
|---|---|---|
| `user_id` | ✅ 最佳 | 登录用户稳定 |
| `device_id` | ✅ 可用 | 匿名用户场景 |
| 客户端 IP | ❌ **危险** | 用户换网络就换桶，体验割裂 |
| session_id | ❌ 错误 | 每次登录都变，完全不稳定 |
| 随机数 | ❌ 错误 | 每次请求都随机，用户会看到功能闪烁 |

**IP 是最容易被误用的**：NAT 环境下，一个出口 IP 后面的所有用户会被分到同一个桶，要么全进要么全不进。用 IP 分桶时要接受这个特性。

### 细节五：匿名用户的降级策略

用户没登录时（没有 `user_id`），有几种选择：

```python
def resolve_bucket_key(request):
    if request.user.is_authenticated:
        return f"u_{request.user.id}"       # 稳定
    if device_id := request.COOKIES.get("device_id"):
        return f"d_{device_id}"             # 次优，但稳定
    return None                             # 无稳定标识
```

拿到 `None` 时**不要让哈希随机化**（会导致同一用户下一请求结果不同），而应该：

- **要么**按全局开关处理（所有匿名用户统一进或统一不进）
- **要么**补发一个 `device_id` Cookie 后再判断

### 细节六：灰度开关要能"强制覆盖"

生产排查问题时，你需要能强制某个用户进/出灰度，而不影响其他人：

```python
def in_rollout(user_id, flag):
    # 1. 白名单/黑名单优先（用于排查和特定客户）
    if user_id in flag.force_on:
        return True
    if user_id in flag.force_off:
        return False

    # 2. 全局开关（总闸）
    if not flag.enabled:
        return False

    # 3. 分桶判断
    return bucket_of(user_id, flag.name) < BUCKET_SPACE * flag.percent / 100
```

覆盖的优先级从高到低：**强制名单 > 全局开关 > 分桶**。注意"全局开关"要在分桶之前——这样关闭整个开关时不需要遍历用户。

## 5. 渐进式发布的节奏与回滚触发条件

分桶对了，接下来是**怎么放开**。

### 五阶段节奏

业界比较成熟的节奏是 **1-5-20-50-100**：

| 阶段 | 范围 | 观察时长 | 关注什么 |
|---|---|---|---|
| 内部 | 团队/员工 | 几小时~1 天 | 功能是否正常 |
| 1% | 极小流量 | 至少 1 天 | 错误率是否异常 |
| 5% | 小流量 | 1~2 天 | 性能指标、日志异常 |
| 20% | 部分用户 | 2~3 天 | 业务指标、客服反馈 |
| 50% | 一半用户 | 2~3 天 | 全量前的最后验证 |
| 100% | 全量 | — | 继续观察一周再删开关 |

**为什么每步都要停留足够久？** 因为有些问题只在特定时间/流量下暴露：缓存到点失效、定时任务触发、流量高峰期才出现的竞争条件。**1% 灰度跑 10 分钟就调到 20%，等于没灰度。**

### 回滚触发条件必须提前定义

这是最容易被忽略、但最关键的一步。**不要等出了事再想"要不要回滚"**——人在事故中容易犹豫。

上线前就写清楚，例如：

```yaml
flag: release-checkout-v2
rollback_triggers:
  - error_rate_5xx > 1%         持续 5 分钟
  - p99_latency > 500ms         持续 5 分钟
  - 订单转化率下降 > 10%        对比对照组
  - 任何 P0/P1 级报错
rollback_action: set percent to 0
```

有了这张表，值班同学不需要判断力就能决策：**指标触线就回滚，不需要开会讨论。**

### 回滚的三种粒度

| 动作 | 效果 | 适用 |
|---|---|---|
| `percent = 0` | 新用户不再进入，已在灰度的保留 | 轻度问题 |
| `enabled = false` | **所有**用户立即回到旧逻辑 | 严重问题 |
| 重新部署旧版本 | 完全回到上一个代码版本 | 代码本身的 bug |

**特性的好处是前两种都是秒级生效**，不需要重新部署。第三种才是传统意义的回滚。

注意 `percent = 0` 和 `enabled = false` 的区别：前者对已进入灰度的用户仍然生效（因为他们的桶号不变），后者才是真正的一刀切。**排查线上问题时,不要以为 `percent=0` 就完事了。**

## 6. 开关的技术债：为什么它会变成负债

特性开关有个反直觉的特性：**它本身是负债，不是资产。**

每个开关都在代码里加了一个分支：

```python
if flag_enabled("release-checkout-v2", user):
    return new_checkout(user)     # 新路径
else:
    return old_checkout(user)     # 旧路径
```

这意味着：**测试要覆盖两条路径、Bug 可能只在一条路径出现、读代码的人要同时理解两套逻辑。** 开关越多的代码越难维护——这不是"优雅"，是复杂度。

### 技术债的量化

| 现象 | 后果 |
|---|---|
| 开关数量 > 50 | 认知负担显著上升，新人难上手 |
| Release 开关存活 > 90 天 | 大概率已全量，但没人敢删 |
| 嵌套开关 `if (flagA && flagB)` | 组合数指数增长，几乎不可能测全 |
| 无主的孤儿开关 | 没人知道能不能删，永久留存 |

### 治理方法

**1. 每个开关必须有 owner 和过期时间**

```
release-checkout-v2
  owner: @后端组-张三
  expires: 2026-10-15      ← 全量后 30 天
  description: 新结算页
```

没有 owner 的开关就是定时炸弹。

**2. 把清理写进 CI**

```bash
# CI 检查：超过 90 天未更新的 Release 开关直接报错
python tools/check_stale_flags.py --max-age-days 90 --fail-on-found
```

自动化是目前唯一被验证有效的治理手段——靠人记着清理，一定会忘。

**3. 能用 RBAC 就别用开关**

Permission 类需求（按套餐控制功能）应该用**权限系统**实现，而不是开关。开关适合"临时的、需要人工决策的"场景；权限适合"长期的、有明确规则的"场景。

**4. 别用开关做配置**

```python
# ❌ 错误：API 地址、超时时间不属于开关
if flag("ops-use-new-api-host"):
    host = "https://api2.example.com"

# ✅ 正确：这些属于环境变量/配置文件
API_HOST = os.environ["API_HOST"]
```

开关是**给功能决策用的**，不是配置中心。混用会让开关系统承担不该有的责任。

## 7. 三层缓存架构：让开关评估不拖慢接口

开关评估在**请求热路径**上，性能必须严肃对待。实测数据说明了为什么不能每次都去远端查：

```
评估开销（20 万次）
    算哈希 blake2b   :      1.074 us/次
    读缓存 + 比较    :      0.073 us/次
    远程评估 @ 1ms RTT :   1000    us/次   (13,762x 读缓存)
    远程评估 @ 5ms RTT :   5000    us/次   (68,812x 读缓存)
    远程评估 @20ms RTT :  20000    us/次   (275,249x 读缓存)
```

**每次请求都走网络查开关，比读本地缓存慢几万倍。** 而且更糟的是——开关服务一挂，你的整个服务就挂了。

### 三层结构

```
第一层：进程内内存          ← 命中率 99%+，纳秒级
   ↑ 定期刷新（如每 5s）
第二层：本地 Redis / 共享缓存  ← 毫秒级，作为兜底
   ↑ 变更时推送
第三层：开关配置服务（SDK）    ← 唯一真相源
```

**核心策略：全量配置拉取 + 定时刷新，而不是按需查询。**

```python
import threading, time

class FlagCache:
    def __init__(self, client, refresh_interval=5):
        self.client = client
        self.interval = refresh_interval
        self._config = {}          # 进程内快照
        self._lock = threading.Lock()
        self._start_refresh_thread()

    def _refresh_loop(self):
        while True:
            try:
                snapshot = self.client.fetch_all()   # 拉全量配置
                with self._lock:
                    self._config = snapshot
            except Exception:
                pass        # 拉取失败 → 保留旧配置，不中断服务
            time.sleep(self.interval)

    def is_enabled(self, name, user_id, default=False):
        with self._lock:
            flag = self._config.get(name)
        if flag is None:
            return default          # 未知开关 → 用安全默认值
        ...
```

### 必须权衡：刷新间隔 vs 生效延迟

配置刷新间隔决定了 **Kill Switch 的最长生效时间**：

| 刷新间隔 | Kill Switch 最长生效时间 | 适用场景 |
|---|---|---|
| 1 秒 | 1 秒 | 核心链路、熔断开关 |
| 5 秒 | 5 秒 | **大多数场景的平衡点** |
| 30 秒 | 30 秒 | 非关键功能 |
| 5 分钟 | 5 分钟 | 低频配置（如套餐权限） |

**注意"最长"**：如果你的刷新是每 5 秒一次，那么你在两次刷新之间按下 Kill Switch，最坏要等接近 5 秒才生效。**对于"一键止血"类的熔断开关，5 秒可能就是可接受的极限了**——不可能做到绝对实时，除非用长连接推送（WebSocket/SSE），代价是复杂度。

这也是为什么**熔断开关应该走独立的、更快的通道**，而不是和普通开关共用 5 分钟刷新周期。

### 拉取失败必须"保留旧配置"

```python
except Exception:
    pass        # ← 关键：不要清空配置，不要抛异常
```

如果开关服务挂了就把配置清空，那么**所有开关会瞬间返回默认值**——如果默认值是"关闭"，你的所有新功能会集体下线；如果默认值是"开启"，可能触发未验证的代码路径。

**正确行为：拉取失败时继续沿用最后一次成功的配置。** 这样开关服务短暂抖动对业务零影响。

顺带说下默认值的选择：**Release/Experiment 开关默认 `False`（功能关闭，安全）；Kill Switch 默认 `True`（功能开着，出问题时才关）。**

## 8. 上线 Checklist + 高频 FAQ

### Checklist

- [ ] 分桶使用**固定桶空间**（如 10000），百分比只作为阈值线，不改变桶数量
- [ ] 每个开关用**独立 salt**，避免实验之间用户重叠
- [ ] 分桶是**纯函数**，不依赖共享状态，多实例结果一致
- [ ] 分桶标识稳定（`user_id` / `device_id`），**没有用 session_id 或 IP 兜底**
- [ ] 匿名用户有明确的降级策略，**不会导致每次请求结果不同**
- [ ] 每个开关有 **owner + 过期时间 + 描述**
- [ ] Release 开关全量后 **30 天内清理**，CI 有超期检测
- [ ] 开关配置**进程内缓存 + 定时刷新**，不在热路径调远端
- [ ] 拉取失败时**保留旧配置**，不清空、不抛异常
- [ ] 灰度前定义了**明确的回滚触发指标**，值班同学无需讨论即可执行
- [ ] Kill Switch 有**独立的快速刷新通道**，生效延迟可接受
- [ ] 灰度每一步都**停留足够时间**（至少覆盖一个完整业务周期）

### FAQ

**Q：灰度和蓝绿部署、金丝雀发布有什么区别？**

A：三者都是降低发布风险的手段，但粒度不同。**蓝绿**是两套完整环境切换（资源翻倍）；**金丝雀**是把少量真实流量导到新版本（按实例/流量比例）；**特性开关**是在代码层面按用户维度控制（最细，且回滚最快）。实践中可以组合使用：用金丝雀验证新版本实例的健康度，用特性开关控制功能对用户的可见性。

**Q：按用户灰度还是按流量灰度？**

A：**按用户**（本文方案）。因为用户会发多个请求，如果按流量随机，同一个用户会看到新旧功能反复切换（前端状态错乱）。按用户分桶能保证体验一致。例外是纯无状态的接口（如 CDN 缓存），可以按流量。

**Q：开关状态会导致缓存问题吗？**

A：会。如果开关影响接口返回内容，而缓存 key 没带开关状态，就会出现"灰度用户看到缓存里的旧内容"。解法：**把开关状态加入缓存 key**，或者干脆对灰度期间的接口禁用缓存。

**Q：前端也要用开关吗？**

A：视情况。**敏感逻辑（权限、计费）必须在服务端判断**——前端开关只是 UI 展示，用户能改。前端开关适合控制"看不到但无关紧要"的展示差异（布局、文案）。千万不要用前端开关做权限控制。

**Q：怎么测试开关的两条路径？**

A：单元测试必须覆盖 `enabled=True` 和 `enabled=False` 两种情况。更进一步的做法是把"开关状态"作为测试参数注入，用参数化测试跑两遍。**最容易漏测的是"关闭"路径**——因为开发时你总是开着它。

**Q：开关配置存在哪？**

A：小规模可以放数据库 + 定期轮询；中大规模用开源自建方案（Unleash、Flagsmith、Flipt）；企业级用托管服务（LaunchDarkly、PostHog、Statsig）。**不建议用配置文件**——那等于每次改开关都要部署，违背了"发布与部署解耦"的初衷。

**Q：灰度期间数据写入了新表，回滚怎么办？**

A：这是灰度的**经典难题**。原则是：**让新功能向前兼容**——写新表的同时保留旧字段，或者用双写。如果做不到，回滚前要先确认数据能否被旧代码正确读取，否则"回滚代码"会变成"数据损坏"。**涉及不可逆数据变更时，灰度前必须单独设计数据回滚方案。**

## 小结

如果把这篇文章压缩成四条：

1. **分桶必须用固定桶空间**，百分比只是移动阈值线——否则扩灰度会让用户"功能闪回"（实测只有 48.2% 保持）。
2. **开关的类型决定它活多久**：Release/Experiment 要删，Ops/Permission/Kill 要留。没有 owner 和过期时间的开关是定时炸弹。
3. **开关评估必须在进程内缓存**，远端调用比本地读慢几万倍，而且开关服务一挂会拖垮整个服务。
4. **回滚触发条件要提前定义**。特性开关最大的价值不是"能灰度"，而是**把回滚从几分钟的重新部署，变成一次秒级的配置变更**。

灰度发布和特性开关不是"高级玩法"，而是**把上线这件事从赌博变成可管理流程**的基础设施。它的成本是代码里多出的分支，它的收益是你敢在周五下午发布。
