前言：2 万行写了 136 秒

一个很普通的脚本：把 2 万条事件写进 SQLite。 
for row in events:
    conn.execute("INSERT INTO t (i, kind, payload) VALUES (?, ?, ?)", row)
    conn.commit()          # ← 问题就在这一行
体感上它"卡住了"。拆开算一下就明白：逐条提交时，2 万行就是 2 万次 fsync。这台机器上一次 fsync 实测 1.996 ms，光落盘就是 40 秒起步；再加上回滚日志的额外写与删除，实测是 6.82 ms/commit，2 万行就是 136 秒。 而同样的 2 万行，放进一个事务里提交，实测 0.036 秒。 同一台机器、同一个表、同一批数据，差了三千多倍。这篇文章就是把这三笔账算清楚：fsync 到底多贵、批量提交摊薄了什么、以及什么时候不能摊薄。

一、先量 fsync 的价格

不量这个数，后面所有讨论都是猜。用纯标准库直接打： 
fd, path = tempfile.mkstemp()
os.write(fd, b"x" * 4096)
for _ in range(200):
    os.write(fd, b"y" * 4096)
    os.fsync(fd)
取中位数： 
fsync median: 1.996 ms
一次落盘 2 毫秒。这个数字决定了后面的一切：
  • 逐行提交 = 每行 2 ms 起 → 上限约 500 行/秒；
  • 1000 行合并成一次提交 = 每 1000 行 2 ms → 上限约 50 万行/秒。
这就是 group commit 的全部原理：fsync 的次数跟"提交了几次"绑定，跟"写了多少行"没关系。

二、四组对照：提交粒度决定吞吐

固定 200 次提交、每行 120 字节负载、3 轮取中位数，跑两组日志模式。 rollback journal（SQLite 默认）+ synchronous=FULL：
每批行数 墙钟 行数 吞吐 每行
1 1.351 s 200 148 rows/s 6754.9 µs
10 1.313 s 2,000 1,524 rows/s 656.3 µs
100 1.366 s 20,000 14,642 rows/s 68.3 µs
1000 1.615 s 200,000 123,829 rows/s 8.1 µs
2 万行一个事务 0.036 s 20,000 552,811 rows/s 1.8 µs
WAL + synchronous=FULL：
每批行数 墙钟 行数 吞吐 每行
1 0.401 s 200 499 rows/s 2005.0 µs
10 0.400 s 2,000 5,001 rows/s 200.0 µs
100 0.404 s 20,000 49,509 rows/s 20.2 µs
1000 0.712 s 200,000 280,906 rows/s 3.6 µs
2 万行一个事务 0.032 s 20,000 625,274 rows/s 1.6 µs
三件事一眼可见：
  1. 每批行数翻 10 倍，吞吐也接近翻 10 倍，200 行一批时开始偏离——因为此时 fsync 已经不是瓶颈，插入本身成为瓶颈；
  2. WAL 比 rollback journal 快 3.4 倍（1 行/次提交时：499 vs 148 rows/s），因为每次提交只写一次顺序日志；
  3. 整批一个事务比逐行提交快 3,734 倍（rollback）/ 1,254 倍（WAL）。
注意第三项的差别：WAL 的加速比更小，不是因为它更差，而是因为它的逐行提交本来就没那么糟（2 ms vs 6.8 ms）。优化空间被 WAL 提前吃掉了一部分。

三、为什么回滚日志更贵：一次提交要碰几个文件

rollback journal 的提交路径大致是： 
1. 建 journal 文件（或 truncate）
2. 把原页写进 journal
3. fsync 一次 journal
4. 把新页写回主库
5. fsync 一次主库
6. 删除 journal
两次 fsync，再加上文件创建/删除的元数据操作。实测 6.82 ms/commit，而单次 fsync 是 2.0 ms——多出来的 2.8 ms 就是"建/删文件 + 两次落盘"的余量。 WAL 的提交路径是： 
1. 把新页追加到 -wal 文件
2. fsync 一次 -wal
一次 fsync，顺序写。实测 2.005 ms/commit，几乎就是一次 fsync 的价格。这也解释了为什么 WAL 下"1 行/次提交"就能做到 499 rows/s——瓶颈严格等于落盘次数。 一个容易忽略的副作用：WAL 模式下的 -wal 文件会越长越大，直到 checkpoint。批量写 20 万行时 -wal 会明显膨胀，这是"用空间换提交速度"的直接体现。

四、什么时候不能批量提交

这条最重要，因为"全部塞进一个事务"在生产里经常是错的。 1. 事务边界就是业务边界 一次事务覆盖 2 万行，意味着这 2 万行要么全成功要么全失败。如果每行代表一笔独立业务（订单、积分、扣款），你应该按业务单位提交，而不是图快合成一个巨型事务。 2. 长事务会持锁 写事务持有锁直到提交。2 万行一起提交时，整个库在这段时间里对其它写者是阻塞的——SQLite 尤其明显（单写者模型）。批量的收益，常常被并发度下降吃掉。 3. 崩溃会回滚一整批 逐行提交时崩在第 1 万行，前 9999 行是安全的；整批提交时崩在最后一刻，全部回滚。做数据导入这没问题（重跑即可），做在线业务就是事故。 4. 内存与 WAL 膨胀 批量越大，-wal 越大，checkpoint 越重。1000 行一批通常是甜点：吞吐已经接近整批，而内存和 WAL 增长可控。

五、这笔账在别的数据库上也成立

这不是 SQLite 的特性，是持久化语义的共性：
  • PostgreSQL：synchronous_commit=on 时每次提交等 WAL 落盘；批量 COPY 快一个数量级，原理完全一样。
  • MySQL InnoDB：innodb_flush_log_at_trx_commit=1 时每事务一次 fsync；改成 =2 是"每秒落盘"，本质是用"可能丢 1 秒"换吞吐。
  • Kafka：acks=all + flush.messages 的取舍也是同一件事——批量越大，单位落盘成本越低，但丢一批的影响面越大。
所以看到"批量写入比逐条快 100 倍"时，别急着骂库慢，先看清楚：你付的是落盘的次数，不是行数。

六、实测复现

set PYTHONIOENCODING=utf-8 && python tools/bench_sqlite_commit.py
脚本做的事：先测原始 os.fsync 的价格，再对 1 / 10 / 100 / 1000 行每次提交 和 2 万行一个事务 各跑 3 轮取中位数，rollback journal 与 WAL 各一遍。原始输出存在 tools/bench_sqlite_commit_output.txt。 三个方法论说明，避免把数字读歪：
  1. 固定提交次数（200 次）而不是固定行数——这样每一档的 fsync 次数可比，吞吐差异才归因清楚；
  2. 每行带 120 字节负载——空行会让页内压缩掩盖差异，看起来所有策略一样快；
  3. 数据库建在临时目录，同一块盘；换盘（比如网络盘）fsync 会贵一个数量级，但比例关系不变。

七、上线 Checklist

  • [ ] 批量导入用"一个事务 N 行提交"，而不是逐行 commit()
  • [ ] 批量大小按"落盘成本 ≈ 插入成本"取平衡点（本例 1000 行）
  • [ ] 事务边界与业务边界对齐，不为了吞吐合并无关业务
  • [ ] 评估写锁持有时间对并发的影响
  • [ ] 打开 WAL（PRAGMA journal_mode=WAL），并接受 -wal 文件增长
  • [ ] 想清楚 synchronous：FULL 不丢已提交事务，NORMAL 在断电时可能丢最近若干事务（但库不损坏）
  • [ ] 崩溃重跑是否幂等（批量回滚后重放不能产生重复数据）

八、高频 FAQ

Q：synchronous=NORMAL 到底丢什么？ A：WAL 模式下，NORMAL 不保证每次提交都落盘，操作系统崩溃或断电时可能丢掉最近的一批已提交事务；但数据库文件本身不会损坏。FULL 才保证"提交即持久"。 Q：为什么 1000 行一批不是 2000 行一批？ A：本例中 1000 行一批已到 123,829 rows/s，再往上 fsync 不再是瓶颈，收益迅速衰减，而锁持有时间和 WAL 体积线性增长。 Q：executemany 会替我批量提交吗？ A：不会。executemany 只减少 Python 侧往返，提交次数还是你 commit() 的次数。它和事务边界是两件事。 Q：把 commit() 从循环里挪出来，还能更快吗？ A：能，但要注意内存——2 万行的改动都在内存/WAL 里攒着。数据量大到放不下时，就要分批提交。 Q：为什么不是每个数据库都默认批量提交？ A：因为默认值要对正确性负责。批量的收益属于应用层，得由知道业务边界的人来定。

写在最后

"批量写入快"是常识，但常识背后的数字经常没算过：这台机器上一次 fsync 是 2 ms，逐行提交 2 万行要 136 秒，整批提交 0.036 秒。三千多倍的差距，全部来自"落盘次数"这一个变量。 所以下次看到类似的慢，先问一句：我到底提交了多少次？ 这个数字比"我写了多少行"重要得多。
