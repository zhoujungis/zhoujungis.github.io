# API 还在用 /v1、/v2？——接口版本管理的演进与实战策略

> 适用读者：正在维护多个版本 API、或者即将开始做接口版本管理的后端工程师
> 技术栈：原理与语言无关，文中涉及 REST / GraphQL / gRPC 三种风格的版本策略
> 阅读时间：约 22 分钟 | 难度：中级 | 收获：一套"什么时候该升版本、怎么升、升完怎么退"的决策框架

## 前言：一个"改了返回字段，客户端全崩"的事故

上个月，一个移动端同事跟我说："你们后端改了个字段名，我们 App 全白屏了。"

我去看了一下——一个用户详情接口，把 `nickname` 字段改成了 `display_name`。改动很小，语义更清晰，但旧版本 App 还在用 `nickname`，解析失败后整个页面崩溃。

复盘的时候发现：这个接口有**三个客户端**（iOS、Android、Web），三端的发版节奏完全不同。iOS 审核要两周，Android 灰度发布要一周，Web 是随时可以更新。你改了一个字段，等于同时要协调三个客户端的适配。

**这不是"改个字段"的问题，是"接口契约"的问题。**

API 版本管理要回答的核心问题是：**当你不可避免地要修改接口时，如何做到老客户端不崩溃、新客户端能用新功能、运维不爆炸？**

**目录**

- 为什么 API 必须有版本管理
- 四种版本控制策略：URL、Header、Content-Type、兼容性演进
- 什么时候该升大版本，什么时候不该升
- 版本的生命周期：发布、共存、废弃、下线
- gRPC 和 GraphQL 的版本策略差异
- 实战中的五个常见坑
- Checklist + 高频 FAQ

## 1. 为什么 API 必须有版本管理

### 1.1 接口是一种契约

API 是服务提供方和调用方之间的**契约**。契约一旦签订，双方都有预期：调用方预期"这个字段永远返回字符串"，提供方预期"调用方永远不会传这个参数"。

**版本管理 = 契约的变更管理。** 没有它，你改任何东西都是在"偷偷改契约"——调用方不知道契约已经变了，只能等崩溃来告诉你。

### 1.2 三个现实约束

为什么 API 必须改？三个改不动的原因：

1. **业务在演进**：产品加了新功能，需要新字段、新接口。比如用户详情页要显示会员等级，但老接口没这个字段。
2. **安全在升级**：旧接口有漏洞（比如返回了密码哈希），必须改掉。
3. **性能在优化**：旧接口的返回结构不合理（一次请求返回 500 个字段，客户端只用 10 个），需要拆分。

而为什么不能"直接改"？因为**客户端不受你控制**：

- App 用户可能三个月不更新
- 第三方合作伙伴的集成代码你改不了
- Web 端虽然可以随时部署，但老用户可能还在用缓存的旧 JS bundle

### 1.3 没有版本管理会怎样

| 后果 | 表现 |
|---|---|
| 客户端崩溃 | 改了字段名/类型，旧客户端解析失败 |
| 数据丢失 | 删了字段，旧客户端发的数据被静默忽略 |
| 安全漏洞 | 旧版本接口的安全缺陷无法单独修复 |
| 协作困难 | 前后端互相等对方改完才能发版 |

一句话：**没有版本管理的 API，等于在沙滩上盖房子——潮水一来什么都没了。**

## 2. 四种版本控制策略

### 2.1 策略一：URL 路径版本（最常见）

```
GET /v1/users/1001
GET /v2/users/1001
```

**优点**：

- 最直观：URL 里直接能看到版本号
- 最容易调试：浏览器、curl 直接能测
- 最容易路由：网关按路径前缀转发到不同服务

**缺点**：

- URL 变了，RESTful 的"资源唯一标识"语义被破坏（`/v1/users/1001` 和 `/v2/users/1001` 是同一个资源还是两个？）
- 版本号膨胀：三年后你可能有 `/v1/` 到 `/v8/` 八个前缀
- 客户端升级成本：URL 是硬编码的，升版本要改代码

**最佳实践**：

- 只用**主版本号**（v1、v2），不用 `v1.2`、`v1.3`
- 主版本号代表"不兼容变更"，兼容变更不加版本号
- 路径格式：`/v1/resource`（不是 `/api/v1/resource`，`/api` 是网关前缀，不属于版本）

### 2.2 策略二：Header 版本

```
GET /users/1001
X-API-Version: 2
```

或者用 `Accept` 头部：

```
GET /users/1001
Accept: application/vnd.myapp.v2+json
```

**优点**：

- URL 不变，RESTful 语义保持完整
- 可以按请求粒度切换版本

**缺点**：

- 不直观：你不能用浏览器直接测（浏览器地址栏不带上 Header）
- 调试困难：出问题时得看 Header 才知道调的是哪个版本
- 缓存复杂：CDN/缓存通常按 URL 区分，同一个 URL 不同 Header 需要额外的 `Vary: X-API-Version` 配置
- API 文档难以自动生成（Swagger/OpenAPI 对 Header 版本支持不统一）

**最佳实践**：

- 如果团队有较强的 HTTP 基础设施（统一的 API 网关、内部 RPC 框架），Header 版本更优雅
- 如果 API 面向外部开发者，别用 Header 版本——调试体验太差

### 2.3 策略三：Content-Type 版本（少见但规范）

```
GET /users/1001
Accept: application/vnd.myapp.v2+json

HTTP/1.1 200 OK
Content-Type: application/vnd.myapp.v2+json
```

**优点**：

- 符合 HTTP 内容协商（Content Negotiation）规范
- URL 不变，RESTful 语义完整
- 同一个资源可以有不同表示（Representation）

**缺点**：

- 跟 Header 版本一样的问题：不直观、调试困难
- `Content-Type` 的设计初衷是"数据格式协商"（JSON vs XML vs Protobuf），混进版本语义会让两者混淆
- 很多 HTTP 客户端库对自定义 MIME type 的处理不一致

**我的看法**：理论上最正确，实际上最不推荐。除非你在做超规范的 REST（HATEOAS），否则 Content-Type 版本带来的复杂度远超收益。

### 2.4 策略四：兼容性演进（不升版本）

这是被低估最多、但实际上最常用的策略：**只要变更保持向后兼容，就不升版本。**

```python
# 不兼容变更 → 升版本
# v1: {"nickname": "张三"}
# v2: {"display_name": "张三"}     # 字段改名 → 不兼容 → 升 v2

# 兼容变更 → 不升版本
# v1: {"nickname": "张三"}
# v1: {"nickname": "张三", "level": 3}   # 新增字段 → 兼容 → 不升
```

**核心原则：只加不减，只扩不改。**

| 变更类型 | 兼容？ | 要不要升版本 |
|---|---|---|
| 新增字段 | ✅ | 不升 |
| 新增接口 | ✅ | 不升 |
| 字段类型从 int 改成 string | ❌ | 升 |
| 字段改名 | ❌ | 升 |
| 删除字段 | ❌ | 升 |
| 修改字段语义（`status: 1` 从"正常"变"禁用"） | ❌ | 升 |
| 数值精度提升（float → decimal） | ⚠️ | 视客户端实现 |
| 数组排序变化 | ⚠️ | 视客户端是否依赖顺序 |

**这一条是版本管理的基石：大多数变更其实不需要升版本。** 先判断"这个改动是否破坏老客户端"，只在真正破坏时才升版本。

## 3. 什么时候该升大版本，什么时候不该升

### 3.1 必须升版本的场景

| 场景 | 例子 |
|---|---|
| 删除或重命名已有字段 | `nickname` → `display_name` |
| 修改字段类型 | `age: int` → `age: string` |
| 修改错误码语义 | 原来 `401` 表示"未登录"，现在表示"Token 过期" |
| 安全漏洞修复 | 旧接口返回了不该暴露的字段 |
| 接口拆分 | 一个聚合接口拆成多个专用接口 |
| 业务语义变化 | `status` 从"订单状态"变成"支付状态" |

### 3.2 不需要升版本的场景

| 场景 | 例子 |
|---|---|
| 新增字段 | 用户详情加 `avatar_url` |
| 新增可选参数 | 列表接口加 `sort_by` 参数，默认值兼容老行为 |
| 新增接口 | 新建一个 `/search` 接口，不影响旧接口 |
| 内部重构 | 改了实现但返回结构不变 |
| Bug 修复 | 修了个计算错误的 bug，返回值"更正确了" |

### 3.3 一个判断树

```
要改接口了
├── 是新增字段/接口吗？→ 不升版本，直接加
├── 是 Bug 修复吗？→ 不升版本，直接修
├── 是老字段"本来就该改"吗？（语义错了）
│   ├── 是 → 升版本，老版本保留
│   └── 不确定 → 当作"不兼容变更"，升版本
└── 是安全漏洞吗？→ 升版本，同时给老版本发安全补丁
```

## 4. 版本的生命周期：发布、共存、废弃、下线

### 4.1 发布：新版本上线不是终点

新版本上线时，**老版本必须继续运行**。两者共存期间，要点：

- **默认路由到最新版本**：老客户端显式请求老版本，新客户端用最新版
- **监控每个版本的调用量**：如果 v1 的调用量还在涨，说明还有大量老客户端没升级，不能下线
- **文档同步更新**：每个版本的接口文档都要可访问（哪怕只读）

### 4.2 共存：多版本并行是常态

```
请求 → 网关 ── v1（旧服务，运行中）
            ├── v2（当前主力）
            └── v3（灰度中）
```

共存的成本：

- **代码维护**：多份代码分支，bug 要修多处
- **测试成本**：每个版本都要回归测试
- **数据一致性**：v1 和 v2 写同一个数据库时，字段名不同可能出数据不一致

**控制共存版本数**：建议最多同时存在 **2-3 个活跃版本**。超过这个数，运维成本会指数上升。

### 4.3 废弃：提前通知 + 灰度下线

版本下线不是一封邮件就完事，是一个流程：

1. **标记废弃（Deprecated）**：在文档和响应头里标记
   ```
   HTTP/1.1 200 OK
   Deprecation: true
   Sunset: Sat, 01 Nov 2025 00:00:00 GMT
   Link: </docs/migration/v1-to-v2>; rel="migration"
   ```
2. **通知调用方**：发邮件、在 API Dashboard 上公告、通过调用方注册的联系信息通知
3. **监控调用量**：观察调用量是否降到接近零
4. **灰度下线**：先限速（比如 10 req/min），再返回 `410 Gone`，最后下线
5. **保留文档**：下线后文档仍然可查（只读），方便还在迁移的调用方

### 4.4 下线时间线建议

| API 类型 | 共存最短时间 |
|---|---|
| 内部服务间调用 | 1-2 周（所有服务都是你的） |
| 面向合作伙伴的 API | 3-6 个月（对方有自己的排期） |
| 公开 API（有大量外部开发者） | 6-12 个月（长尾效应严重） |

## 5. gRPC 和 GraphQL 的版本策略差异

### 5.1 gRPC：Protobuf 的向后兼容

gRPC 基于 Protobuf，它的版本策略和其他 API 风格**完全不同**：

```protobuf
// v1
message User {
  int32 id = 1;
  string nickname = 2;
}

// v2 —— 向后兼容的改动
message User {
  int32 id = 1;
  string nickname = 2;
  string display_name = 3;   // 新增字段，编号递增
  reserved 4;                 // 保留已删除的字段编号
  reserved "old_field";       // 保留已删除的字段名
}
```

Protobuf 的兼容性规则：

- **字段编号永远不能复用**：删除字段后要 `reserved` 它的编号，防止以后有人用同样的编号加新字段（语义完全不同）
- **字段名可以保留**：同样用 `reserved` 防复用
- **字段类型兼容**：`int32` 和 `int64` 互转兼容，`string` 和 `bytes` 兼容
- **字段规则兼容**：`optional` 和 `required` 互转要小心

**gRPC 的版本管理 ≈ Protobuf 的字段管理。** 因为 gRPC 天然通过字段编号而不是字段名来序列化，它的向后兼容能力比 JSON 强得多。很多情况下，gRPC 接口可以"永远不升版本"，只靠新增字段编号来演进。

### 5.2 GraphQL：一个端点，无版本

GraphQL 的官方立场是：**不做版本管理。**

```
POST /graphql       # 永远这一个端点
{
  user(id: "1001") {
    nickname
    level          # 新增字段，客户端按需查询
  }
}
```

GraphQL 的版本策略：

- **客户端按需查询**：客户端指定要哪些字段，服务端返回对应字段。新增字段不影响老客户端（老客户端不查就不返回）
- **字段废弃用指令标记**：
  ```graphql
  type User {
    nickname: String @deprecated(reason: "Use display_name instead")
    display_name: String
  }
  ```
- **删除字段是最后的手段**：GraphQL 社区强烈建议"只加不删"

**GraphQL 的优势**：从根本上避免了"版本爆炸"——一个端点，所有版本共存。
**GraphQL 的劣势**：当字段语义确实需要改变时（不是改名，是语义变了），你只能删掉旧的加新的，没有"版本"来隔离。

## 6. 实战中的五个常见坑

### 坑 1："先升版本再删老版本"的顺序反了

**错误做法**：上线 v2 → 立刻下线 v1 → 发现还有老客户端在用 → 紧急回滚。

**正确做法**：上线 v2 → 监控 v1 调用量 → 等 v1 调用量接近零 → 通知调用方 → 灰度下线 v1。

> 上线新版本只需要几分钟，下线老版本可能需要几个月。

### 坑 2：版本号变成了"日历版本"

`/v2024-01`、`/v2024-06`、`/v2024-12`——按日期打版本号。

问题：日期版本号没有语义。`v2024-06` 比 `v2024-01` 新，但**新在哪里？兼容还是不兼容？** 调用方无法从版本号判断"我需不需要改代码"。

**正确做法**：用 `v1`、`v2`、`v3`，版本号只代表"不兼容变更的次数"。发布日期写在文档里，不写在版本号里。

### 坑 3："兼容变更"做成了不兼容

```python
# 你以为的兼容变更
# 老版本：{"tags": "python,java"}      # 逗号分隔的字符串
# 新版本：{"tags": ["python", "java"]}  # 数组

# 老客户端代码
tags = response["tags"].split(",")   # 💥 数组没有 split 方法
```

**判断兼容性的黄金标准：老客户端代码能不能在不修改的情况下继续运行？** 如果不能，就是不兼容变更，必须升版本。

### 坑 4：版本管理只在网关层做

网关层做了 `/v1/` → 服务 A v1、`/v2/` → 服务 A v2，但**数据库没有版本意识**。

v1 和 v2 写同一个数据库表，v2 加了个字段 `display_name`，但 v1 不知道这个字段。v1 更新用户时，`display_name` 被覆盖成 NULL。

**解法**：

- 数据库字段只加不删（跟 API 一样的原则）
- 新字段必须有默认值，老版本写入时不会覆盖
- 如果 v2 改了字段的语义，考虑用新列而不是改旧列

### 坑 5：没有版本监控

上线了 v2，但不知道还有多少客户端在用 v1。直到 v1 出问题了才发现"原来还有人用"。

**必须监控的指标**：

- 每个版本的 QPS（按天/周看趋势）
- 每个版本的错误率
- 每个版本的客户端类型（App 版本号、Web 端版本号）
- 每个版本的调用方（哪个团队/哪个 App 在用）

这些数据是"能不能下线老版本"的唯一依据。

## 7. 上线 Checklist + 高频 FAQ

### Checklist

- [ ] 变更是否向后兼容？不兼容必须升版本
- [ ] 新版本上线前，老版本保持运行
- [ ] 网关路由配置正确（`/v1/` → 旧服务，`/v2/` → 新服务）
- [ ] 数据库变更只加不删，新字段有默认值
- [ ] 文档已更新，每个版本的文档都可访问
- [ ] 监控已配置（每个版本的 QPS、错误率、调用方）
- [ ] 调用方已通知（邮件/公告/迁移指南）
- [ ] 老版本下线计划已制定（时间线、通知策略、灰度步骤）
- [ ] 响应头标记了版本信息（`X-API-Version: v2`）
- [ ] 废弃版本返回了 `Deprecation` 和 `Sunset` 头

### FAQ

**Q：URL 版本和 Header 版本到底选哪个？**

A：**默认选 URL 版本。** 它直观、可调试、可缓存，适合绝大多数场景。只有当你的 API 面向内部服务、且有统一的网关/框架支持时，才考虑 Header 版本。

**Q：版本号从 v0 还是 v1 开始？**

A：**从 v1 开始。** v0 暗示"不稳定、随时会变"，但既然你做了版本管理，v1 就应该是稳定的。如果 API 还在快速迭代期，先不发正式版本，用 `/alpha/` 或 `/beta/` 前缀。

**Q：兼容变更要不要通知调用方？**

A：**要，但方式不同。** 不兼容变更必须提前通知+给迁移期。兼容变更（新增字段/接口）可以在 Changelog 里标注，让调用方知道"有新东西可以用"。

**Q：一个接口最多同时存在几个版本？**

A：**建议不超过 3 个。** 超过 3 个版本并行，维护成本会急剧上升。如果 v1 的调用量已经很低，推动调用方迁移到 v2，然后下线 v1。

**Q：第三方 API（比如微信、支付宝）是怎么做版本的？**

A：大多数第三方 API 用 URL 版本（`api.weixin.qq.com/cgi-bin/v3/`），且老版本会保留非常久（通常 1-2 年）。这是因为他们无法控制调用方的升级节奏。**如果你的 API 也是公开 API，做好"老版本长期共存"的心理准备。**

**Q：微服务内部调用需要版本管理吗？**

A：**看情况。** 如果服务间调用是"你写我写"（同一个团队），可以不做严格的版本管理，靠 CI/CD 保证同步发布。如果是跨团队的服务调用，必须做版本管理——你不知道对方什么时候升级。

**Q：GraphQL 真的不需要版本吗？**

A：大多数情况下不需要。但如果一个字段**语义确实变了**（不是改名，是含义变了），你只能删除旧字段加新字段。GraphQL 社区的建议是："如果字段语义要变，就当它是一个新字段，老字段标记 `@deprecated`，给调用方迁移时间。"

---

## 结语

回到开头那个"改了字段名导致 App 白屏"的事故。如果当时有版本管理：

1. 把 `nickname` → `display_name` 识别为"不兼容变更"
2. 上线 v2 接口（返回 `display_name`），v1 接口继续返回 `nickname`
3. 旧 App 继续调 v1，不受影响
4. 新 App 调 v2，用新字段
5. 等 v1 调用量降到接近零，通知 App 团队迁移
6. 迁移完成，下线 v1

整个过程可能需要 1-2 个月，但**没有任何用户会白屏**。

版本管理的本质不是"URL 里加个 /v2/"，而是一种**对调用方的承诺**：你调用的接口不会偷偷改变，如果必须改变，我会给你一个新的、稳定的版本，并给你足够的时间迁移。

**API 版本管理是技术问题，更是信任问题。** 你的调用方信任你的接口不会随意改变，这份信任，值得你用一套严格的版本管理流程来守护。
