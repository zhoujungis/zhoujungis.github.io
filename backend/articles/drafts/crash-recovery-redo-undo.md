## 一、四个故障，四种活法

先看四个真实发生过的场景：

1. **进程被 `kill -9`**：操作系统还活着，页缓存还在，文件描述符被内核关闭。数据库下次启动时，可能看到写了一半的 WAL、残留的 journal，也可能什么都没留下。
2. **机器突然断电**：内存里的页缓存没了，磁盘上可能只有一部分写成功；WAL 的最后一帧可能是半帧，数据页可能只写了一个扇区。
3. **WAL 中间坏了一帧**：磁盘坏道、bit flip、或者人为破坏。坏帧之后的所有帧可能都是好的，但数据库是否还愿意用它们？
4. **页只写了一半（torn page）**：4 KB 的页写进去 2 KB，剩下 2 KB 是旧数据、零或者垃圾。校验和能发现，但发现之后拿什么修？

这四个场景对应四套不同的机制：进程崩溃主要考验日志的**原子提交与恢复流程**；断电考验 **fsync 顺序与日志持久性**；坏帧考验**校验和与截断策略**；半页写考验 **doublewrite 或全页镜像**。

把它们混在一起谈，就会得到「数据库有 WAL 所以不会丢数据」这种似是而非的结论。下面逐个拆。

## 二、先把故障模型分清楚

做恢复实验最容易犯的错误，是用「拷贝文件」模拟断电。我们第一次就是这么做的：写进程还在跑，父进程把 `.db`、`-wal`、`-journal`、`-shm` 逐个复制到另一个目录，然后打开副本。结果 25 次里有多次直接报 `database disk image is malformed`。

这不是数据库的 bug，而是**跨文件拷贝本身不是原子快照**。真实断电时，文件系统保证每个 `write` 和 `fsync` 的顺序；拷贝时，主库、WAL、journal 是在不同时刻被读走的，可能组合出一个物理上从未存在过的状态。用这种副本去推断恢复逻辑，结论不可信。

所以我们把实验拆成三类：

- **进程崩溃**：先 `kill` 进程，等它退出，再复制文件。这模拟的是「进程没了，但操作系统缓存和文件都还在」，用来验证恢复流程和原子性。
- **日志损坏**：在已经写好的 WAL 上精确翻转一个字节，再打开数据库。这模拟坏道/bit flip，用来验证校验和与截断策略。
- **半页写**：用一个小型页/redo 模拟器，控制「哪一半写入成功、哪一半变成什么」，用来验证 doublewrite 的职责。

三类实验回答不同的问题，不能互相替代。下面所有数字都会标明属于哪一类。

## 三、恢复的三条基本规则

不管哪种数据库，崩溃恢复都绕不开三条规则。

**第一条：日志必须先于数据落盘。**

修改一页之前，描述这次修改的日志必须已经持久化。否则断电后，数据页是新的、日志是旧的，恢复时不知道这页为什么变成这样。SQLite 的 rollback journal 在写数据页之前先写旧页镜像；WAL 在提交前先把新页镜像追加到 WAL 并 fsync（`synchronous=FULL` 时）。InnoDB 在刷脏页之前，必须保证对应的 redo 已经写入日志文件。

**第二条：redo 必须幂等。**

同一条 redo 记录重放一次和重放十次，结果必须一样。物理日志通常记录「把页 P 的偏移 O 开始的 N 个字节改成 X」，天然幂等；逻辑日志记录「给账户 A 加 100」，重放两次就会多加一次，所以逻辑日志必须配合 LSN 或事务表去重。InnoDB 的 redo 是页级物理日志，记录页内变更；SQLite 的 WAL 是整页镜像，重放就是覆盖，也幂等。

**第三条：未提交的事务必须能回滚。**

恢复不仅要「向前滚」，还要「向后退」。崩溃时正在执行的事务，可能已经写了一部分数据页，也可能只写了日志。恢复流程必须能识别哪些事务提交了、哪些没有，然后把没提交的改动撤掉。SQLite 用 journal 里的旧页镜像回滚；InnoDB 用 undo log 回滚，并在回滚完成后由 purge 线程清理旧版本。

把这三条记住，再看具体实现就不会迷路。

## 四、SQLite 回滚日志：用旧页镜像做 undo

SQLite 默认的 rollback journal 模式，思路非常直接：**在改一页之前，先把这一页的旧内容写到 journal 文件里。**

一次事务的流程大致是：

1. 在数据库文件上加 RESERVED 锁，创建 `-journal` 文件。
2. 写 journal 头：magic、页数、校验和、数据库大小、扇区大小、页大小。
3. 对每个即将修改的页，追加一条记录：页号 + 旧页内容 + 校验和。
4. 把 journal 刷盘（`synchronous=FULL`），确保旧内容持久化。
5. 修改数据库文件中的页，提交时释放锁、删除 journal。
6. 如果中途崩溃，下次打开数据库时发现 journal 存在且没有对应的锁，就认为它是「热日志」，把旧页镜像逐页写回去，再删除 journal。

所以 journal 本质上是一份**物理 undo log**。它记录的是「改之前长什么样」，恢复时做的是回滚，而不是重放。它不需要知道事务逻辑，只要把页恢复成旧版本，未提交的改动就消失了。

这也解释了为什么 journal 的大小取决于「改了多少个已存在的页」，而不是「插入了多少行」。顺序追加时，大部分页是新的，旧页只有最右边那一两个，journal 只有 12.8 KB；随机更新 2000 条时，会碰到上千个已有页，journal 涨到 1–7 MB。

`PRAGMA synchronous` 控制 journal 的刷盘强度：`FULL` 在关键节点 fsync，`NORMAL` 减少同步次数，`OFF` 把顺序交给操作系统。`OFF` 在断电时可能留下损坏的数据库，因为 journal 可能还没落盘，数据页却已经写了。

## 五、SQLite WAL：用新页镜像做 redo

WAL 模式把方向反过来：**不写旧页，而是把新页追加到 WAL 文件。**

WAL 文件由 32 字节头和若干帧组成。每一帧是 24 字节帧头加一整页数据：

```text
WAL header (32 bytes)
├─ magic / version / page_size / checkpoint_seq / salt / checksum
Frame 1
├─ page number (4)
├─ database size after commit (4)   ← 非 0 表示这是一个提交帧
├─ salt1 / salt2 (8)
├─ checksum1 / checksum2 (8)
└─ page data (page_size)
Frame 2 ...
```

提交时，SQLite 把本事务修改的每个页作为一帧追加到 WAL，最后一帧的「database size after commit」写成非 0，标记事务结束。读取时，先查 WAL 索引（`-shm`），找到每个页在 WAL 中的最新帧；找不到才读主数据库文件。

恢复的规则在 SQLite 官方文档里写得很清楚：**从 WAL 开头单次顺序扫描，逐帧校验 checksum，遇到第一个无效 checksum 就停止；`mxFrame` 取最后一个有效提交帧。** 这意味着 WAL 的恢复具有「前缀性」：坏帧之前的提交有效，坏帧之后的帧即使字节完好，也不会被采用。下一节的实验会精确展示这一点。

`synchronous=FULL` 时，每次提交都 fsync WAL；`NORMAL` 时只在 checkpoint 等关键点同步。两者的差别在断电时体现为「最近若干 committed 事务是否丢失」，在进程崩溃时通常看不出来，因为操作系统缓存还在。

## 六、实测一：进程崩溃后的 55 次恢复

实验设置：写进程每 200 条提交一次，持续插入 120 字节的随机 value；父进程等它进入稳定写入后，随机延迟 0.15–1.2 秒，`kill` 掉，再复制数据库文件、WAL、journal，打开副本执行 `PRAGMA integrity_check` 和计数。

三组配置、共 55 次：

| 配置 | 事务大小 | 成功恢复 | 行数保持原子 | 恢复耗时中位数 | 日志大小中位数 |
|------|---------|---------|------------|--------------|--------------|
| rollback journal + FULL | 200 行 | 20/20 | 20/20 | 8.26 ms | journal 12.8 KB |
| WAL + FULL | 200 行 | 20/20 | 20/20 | 3.98 ms | WAL 4.13 MB |
| WAL + NORMAL | 200 行 | 20/20 | 20/20 | 6.76 ms | WAL 4.15 MB |
| rollback journal + FULL | 2000 行 | 15/15 | 15/15 | 6.53 ms | journal 12.8 KB |
| WAL + FULL | 2000 行 | 15/15 | 15/15 | 10.15 ms | WAL 4.29 MB |

「行数保持原子」指恢复后的行数始终是事务大小的整数倍——不会出现「一个事务只写进去一半」的情况。55 次全部通过，说明在**进程崩溃**这个故障模型下，SQLite 的 journal 回滚和 WAL 恢复都能保证原子性。

恢复耗时都不高：几毫秒到十几毫秒。WAL 的日志更大（4 MB 左右），恢复耗时并没有显著高于 journal；因为 WAL 的 `-shm` 索引还在时恢复很快，只有索引丢失才需要完整扫描。注意这里测的是「打开数据库并执行第一条语句」的时间，不包含后续的全表扫描和 `integrity_check`。

进程崩溃实验有一个重要局限：它没有模拟断电。`kill` 之后操作系统缓存仍然会把数据写回磁盘，SQLite 看到的文件和真实断电后可能不一样。要研究断电，必须控制日志损坏或使用具备掉电模拟的存储设备。

## 七、实测二：事务形态决定日志体积

第二组实验换一个变量：数据库里已经有 30 万行，事务不再追加，而是随机更新 2000 行。其他条件不变。

| 配置 | 恢复成功 | 行数正确 | 日志大小 | 恢复耗时中位数 |
|------|---------|---------|---------|--------------|
| rollback journal + FULL | 8/8 | 8/8 | 1.2–7.4 MB | 92.25 ms |
| WAL + FULL | 8/8 | 8/8 | 7.4–7.5 MB | 19.61 ms |

同一张表、同样的事务大小，只因为「改的是已有页」，journal 从 12.8 KB 涨到几 MB，恢复时间从 8 ms 涨到 92 ms。原因在第四节已经说过：journal 记录旧页镜像，随机更新会触碰大量已有页；顺序插入只改最右边的页，旧页镜像几乎为零。

WAL 的日志体积也涨了，但恢复时间反而比 journal 短。这不是「WAL 一定恢复更快」，而是两者的恢复动作不同：journal 要把几 MB 的旧页逐页写回主库，WAL 主要是扫描帧、重建索引，页的回填可以延后到 checkpoint。**日志体积和恢复时间不是简单的线性关系，要看恢复阶段做了什么。**

这组数据对容量规划很有用：如果一个服务以随机更新为主，undo/redo 的体积会远高于「插入量」给人的直觉。按插入行数估算日志空间，往往会低估一个数量级。

## 八、实测三：故意弄坏 WAL 的一帧

第三组实验直接破坏 WAL。先生成一个包含 40 个事务、每个事务 200 行的 WAL：共 379 帧、41 个提交帧（含建表）、1.56 MB。然后在三个位置各翻转一个字节：

- **首帧之后的第一帧**（第 2 帧）：破坏第一个数据帧。
- **中间帧**（第 189 帧）：破坏一半位置。
- **最后一帧**（第 378 帧）：破坏最后一个提交帧。

结果：

| 破坏位置 | 帧号 | 恢复后行数 | 应有多少行 | integrity_check | 恢复耗时 |
|---------|------|-----------|-----------|----------------|---------|
| 首帧之后 | 2 | 0 | 8000 | ok | 6.51 ms |
| 中间 | 189 | 3800 | 8000 | ok | 8.57 ms |
| 最后 | 378 | 7800 | 8000 | ok | 10.91 ms |

三个结果正好对应 WAL 的「前缀性」：

- 破坏第 2 帧，恢复只能看到建表提交（第 1 帧），后面所有数据帧全部丢弃，所以表存在、行数为 0。
- 破坏第 189 帧，恢复读到第 180 帧的提交（19 个事务 × 200 行 = 3800 行）就停止；第 190 帧之后的提交虽然字节完好，也不会被采用。
- 破坏最后一帧，前 39 个事务（7800 行）保留，只丢掉最后一个事务。

三次 `integrity_check` 都是 `ok`。这很关键：**数据库没有「损坏」，它只是选择了一个一致的历史版本。** WAL 的校验和让恢复可以明确地停在最后一个可信的提交点，而不是把坏帧之后的「看起来正常」的数据继续拼进去。

这也是为什么「WAL 坏了就全完了」和「WAL 有校验和所以不会丢数据」都不对：校验和保证的是一致性，不是完整性。坏帧之后已经提交的事务确实会丢，但数据库不会带着半条事务继续提供服务。

## 九、InnoDB：redo、undo 与恢复的三个阶段

SQLite 的实验只能说明「页镜像日志」这一类实现。InnoDB 的日志格式不同，恢复流程也更复杂。

InnoDB 的 redo log 是**页级物理日志**：记录「哪个表空间的哪个页、在什么偏移、改成了什么」，而不是整页镜像。修改先写 redo，再在合适的时机把脏页刷到数据文件。每个页有一个 LSN（日志序列号），checkpoint 记录「哪些 LSN 之前的改动已经落盘」。恢复时从 checkpoint 开始，把之后的 redo 全部重放。

官方文档把崩溃恢复拆成几个阶段：

1. **tablespace discovery**：扫描数据目录，找出 redo 里涉及的表空间。
2. **redo log application**：从 checkpoint 开始重放 redo，把数据页恢复到崩溃前的最新状态。如果崩溃时所有脏页已经刷盘，redo 重放会被跳过；如果 redo 文件缺失，也会跳过（但可能丢数据）。
3. **rollback of incomplete transactions**：重放完成后，撤销崩溃时未提交的事务。文档特别提醒：**回滚一个中断事务的时间可能是该事务执行时间的三到四倍**，取决于服务器负载；回滚过程不能取消。
4. **change buffer merge**：把二级索引的缓冲修改合并到叶子页。
5. **purge**：清理不再可见的旧版本记录。

这里能看到 redo 和 undo 的分工：**redo 负责「把已提交和未提交的物理改动都恢复出来」，undo 负责「把未提交的逻辑事务撤掉」。** 先向前滚到最新，再向后退掉不该存在的部分。这和 SQLite 的 rollback journal「直接恢复旧页」是两条不同的路线：journal 是 undo-only（不重放已提交事务，因为数据页本来就在原处），WAL 是 redo-only（提交过的事务都在日志里，未提交的不写提交帧）。

InnoDB 还需要 undo log 支持 MVCC：每行可能有多个历史版本，读操作根据 Read View 选择可见版本。崩溃恢复结束后，undo 不能立刻全删，必须等没有活跃事务再需要这些版本，purge 才能清理。这也是为什么长事务会阻止 purge、让 undo 表空间膨胀。

## 九点五、三种恢复路线放在一张表里

SQLite journal、SQLite WAL、InnoDB 代表三种不同的取舍。把它们按「提交前写什么、恢复往哪个方向走、坏页怎么修」排在一起，会更容易看清边界：

| 维度 | SQLite rollback journal | SQLite WAL | InnoDB |
|------|------------------------|------------|--------|
| 提交前写什么 | 旧页镜像 | 新页镜像 | redo（页内变更） |
| 提交标记 | journal 头 + 同步 | 提交帧（dbsize≠0） | redo 中的 commit LSN |
| 恢复方向 | 只 undo | 只 redo | 先 redo，再 undo |
| 未提交事务 | 旧页覆盖，自动消失 | 不写提交帧，不会被看到 | undo 回滚 |
| 坏页修复 | journal 中的旧页 | WAL 帧中的新页 | doublewrite + redo |
| 恢复成本主要取决于 | journal 大小 | WAL 帧数与索引状态 | checkpoint 之后的 redo 量 + 回滚量 |
| 典型弱点 | 随机更新时 journal 膨胀 | WAL 坏帧后提交丢失 | 长事务回滚慢、undo 膨胀 |

这张表解释了一个常见困惑：为什么 SQLite 的 journal 恢复不需要「判断事务提交没提交」？因为它根本不重放事务，它只把页恢复成事务开始前的样子。未提交的事务本来就没有完整的页修改，恢复旧页后自然消失；已提交的事务，journal 在提交后被删除，也不会被回滚。代价是：journal 必须在数据页之前落盘，而且 journal 越大，恢复写回越多。

WAL 的选择相反：它只记录新页，提交帧就是事务的边界。恢复时不需要「回滚」，因为未提交事务没有提交帧，`mxFrame` 不会越过它。代价是：WAL 会持续增长，必须靠 checkpoint 回填；坏帧会截断后续所有提交。

InnoDB 两者都要：redo 保证「已经发生的页修改不丢」，undo 保证「未提交的逻辑事务不生效」。这带来更强的能力（MVCC、回滚、崩溃后继续服务），也带来更高的复杂度（undo 表空间、purge、长事务）。

## 九点六、redo 是物理日志还是逻辑日志

InnoDB 的 redo 常被描述为「物理逻辑日志」，这个说法容易让人困惑。拆开看：

- **物理**：记录的是「哪个页、页内哪个偏移、改成什么字节」，不是「执行了哪条 SQL」。所以重放不需要查询优化器、不需要事务上下文，幂等且快。
- **逻辑**：在页内层面，它记录的是一组变更（插入记录、更新字段、修改页头），而不是整页镜像。恢复时要把这些变更应用到页上，而不是简单覆盖。

这和 SQLite WAL 的「整页镜像」形成对比：WAL 的一帧就是 4 KB 的新页，重放是覆盖；InnoDB 的一条 redo 可能只有几十字节，描述一次页内修改。前者写放大高、恢复简单；后者写放大低、恢复需要理解页结构。

物理日志的幂等性来自「记录的是最终值」：把偏移 O 的 N 个字节改成 X，执行一次和执行十次结果一样。逻辑日志则不一定幂等，比如「余额加 100」执行两次就错了。这也是为什么 InnoDB 的 redo 必须是物理/物理逻辑的，而 binlog 这种逻辑日志需要额外的 GTID、server_id、位点来去重。

还有一个容易忽略的细节：InnoDB 的 redo 以 mini-transaction（mtr）为单位写入，一个用户事务可能包含多个 mtr，每个 mtr 结束时把 redo 写入公共日志缓冲。恢复时按 LSN 顺序重放，不关心它属于哪个用户事务；事务边界由 undo 和提交记录决定。这种「物理层按 mtr、逻辑层按事务」的分层，是 InnoDB 能同时做到高并发和崩溃恢复的关键。

## 十、半页写：为什么有时 redo 能修，有时不能

现在看最容易被误解的一环：torn page。

假设页 P 的旧版本是 V0，新版本是 V1。事务修改了 P 的若干字节，redo 记录了这些字节的新值。刷脏页时，磁盘只写成功了一半：前 2 KB 是 V1，后 2 KB 还是 V0（或者变成零/垃圾）。断电后重启，恢复流程读到 P，校验和不匹配。

这时会发生什么？

**情况一：未写到的后半部分保留了 V0。** redo 重放会把「被修改的字节」写成 V1 的值；没有被修改的字节本来就是 V0，和 V1 一致。重放完成后，整页正好等于 V1，校验和通过。**redo 自己就能修复这种半页写。**

**情况二：未写到的后半部分变成了零或垃圾。** redo 只覆盖「被修改的字节」；那些没有被修改、但已经被写成零的字节，不在任何 redo 记录里。重放完成后，页仍然不完整，校验和失败。**redo 修不了，必须有一个完整的 V1 副本。**

doublewrite 就是为情况二准备的。InnoDB 刷脏页时，先把页顺序写进 doublewrite 区域并 fsync，再写到数据文件的真实位置。恢复时如果发现数据文件的页校验失败，就从 doublewrite 里找到完整副本，覆盖回去，再重放 redo。官方文档特别说明：doublewrite 是**大块顺序写 + 一次 fsync**，不是每页两次随机 I/O，所以开销远小于「写两遍」的字面印象。

我们用一个 4000 次/组的模拟器验证这个分工。模型是：4 KB 页带 CRC，redo 记录若干字节区间的 after-image，半页写把前半页写成 V1、后半页写成 V0 或零；恢复时重放 redo，比较结果是否等于 V1。

| 半页的另一半 | 无 doublewrite | 有 doublewrite |
|-------------|---------------|----------------|
| 保留旧字节 V0 | 0% 损坏 | 0% 损坏 |
| 变成零 | 100% 损坏 | 0% 损坏 |

这组数字说明：**doublewrite 防的不是「所有半页写」，而是「redo 无法覆盖的那部分字节被破坏」。** 如果磁盘保证未写入的扇区保持旧值，redo 就够了；如果可能返回零或垃圾，就必须有完整副本。真实硬件的扇区原子性、写缓存和掉电行为决定了你落在哪一格，所以生产环境默认开启 doublewrite 是合理的。

需要说明的是，这是一个模型，不是 InnoDB 本身。InnoDB 在页第一次被修改后还会记录 full-page image（整页镜像），这会改变「redo 能否自修」的边界；不同版本、不同 `innodb_flush_method` 的行为也有差异。模型的价值在于把「redo 覆盖范围」和「介质实际写入内容」这两个变量分开，而不是给出一个适用于所有引擎的百分比。

## 十一、配置、监控与恢复演练

把上面的机制落到日常运维，可以按这张清单检查：

**持久性配置**

- SQLite：`synchronous=FULL` 是断电安全的下限；`NORMAL` 在 WAL 模式下只保证一致性，最近提交可能丢；`OFF` 不适合任何不能丢数据的场景。
- InnoDB：`innodb_flush_log_at_trx_commit=1` 表示每次提交 fsync redo；`=2` 只写 OS 缓存，性能更好但可能丢最近一秒；`=0` 由后台线程每秒刷，风险更高。
- 日志文件大小：WAL/redo 太小会导致频繁 checkpoint，太大则恢复时间长。按写入速率和可接受的 RTO 反推。

**监控指标**

- WAL/redo 的增长速度与 checkpoint 频率；
- 恢复时间（启动到可服务）与日志大小；
- `integrity_check` / `CHECK TABLE` 的定期结果；
- 磁盘的掉电保护（PLP）、写缓存策略、扇区大小；
- InnoDB 的 purge lag、history list length、undo 表空间大小。

**恢复演练**

1. 备份 + 日志回放：从全量备份恢复到某个时间点，记录 RTO。
2. 模拟误删：删一张表，按 binlog/WAL 回放到误删前，验证数据完整。
3. 模拟坏帧：在测试库的 WAL 副本上翻转一个字节，确认数据库能启动、能报告丢失范围。
4. 模拟半页写：在支持注入的存储或模拟器上验证 doublewrite 路径。
5. 记录每次演练的「实际丢失多少事务」，而不是只看「能不能启动」。

恢复能力不是配置出来的，是演练出来的。一个从没恢复过的备份，不能算备份。

## 十二、源码地图与复现脚本

**SQLite**

- `pager.c`：`pager_write` 标脏页，`pager_playback` 回放 journal，`sqlite3PagerCommitPhaseOne` 处理提交阶段的日志写入。
- `wal.c`：`sqlite3WalFrames`/`walFrames` 追加帧，`walIndexRecover` 扫描 WAL、校验 checksum、设置 `mxFrame`。
- 官方文档：[WAL-mode File Format](https://www.sqlite.org/walformat.html)、[Database File Format](https://www.sqlite.org/fileformat2.html)。

**InnoDB**

- `log0recv.cc`：redo 恢复的主流程，从 checkpoint 开始扫描并重放。
- `buf0dblwr.cc`：doublewrite 的写入与恢复。
- `trx0rec.cc` / `trx0roll.cc`：undo 记录与事务回滚。
- 官方文档：[InnoDB Recovery](https://dev.mysql.com/doc/refman/8.4/en/innodb-recovery.html)、[Doublewrite Buffer](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)。

WAL 破坏实验的关键是解析帧布局：

```python
import struct

data = open('db-wal', 'rb').read()
magic, version, page_size = struct.unpack('>III', data[:12])
frame_size = 24 + page_size
frames = (len(data) - 32) // frame_size
for i in range(frames):
    off = 32 + i * frame_size
    pgno, dbsize = struct.unpack('>II', data[off:off + 8])
    # dbsize != 0 表示提交帧
```

踩过的坑：

1. **不要边写边拷贝**。跨文件拷贝不是原子快照，会造出物理上不存在的状态；先 kill，再复制。
2. **`integrity_check` 会全表扫描**。把它计入恢复时间，会得到「数据库越大恢复越慢」的错误结论；恢复时间应该只算打开数据库到第一条语句。
3. **WAL 帧的 checksum 是累积的**。破坏中间一帧，后面的帧即使字节完好也会被丢弃；这是设计，不是 bug。
4. **进程崩溃不等于断电**。想验证 fsync 语义，必须在真实掉电或可注入故障的存储上做。

## 十三、小结：恢复是一条时间链

把全文压缩成一条时间链：

1. 修改发生前，旧页（journal）或新页（WAL/redo）先落盘——**write-ahead**。
2. 提交时，日志里出现一个明确的提交点——事务要么整体可见，要么整体不可见。
3. 崩溃后，从 checkpoint 开始重放日志——**redo**，把物理状态推到最新。
4. 对未提交事务执行回滚——**undo**，把逻辑状态退回一致点。
5. 校验和发现坏页/坏帧；doublewrite 或完整副本修复半页写。
6. checkpoint 回填、purge 清理，数据库回到正常服务状态。

SQLite 的 journal 和 WAL 分别站在「undo-only」和「redo-only」两端，InnoDB 则是「redo + undo」的组合。它们的具体格式不同，但这六步的责任划分是一致的。

真正需要记住的，不是某个函数名或参数，而是三个问题：

- **我的日志在数据之前落盘了吗？**
- **我的恢复能明确说出「哪些事务算数」吗？**
- **我的存储能保证未写入的部分是什么吗？**

答完这三个问题，才谈得上「崩溃恢复」。
