Still shipping /v1 and /v2? The real work of API versioning

2026-10-28 · 16 min · Stack Frame

Who this is for: anyone maintaining several API versions, or about to start.

Language agnostic, covering REST, GraphQL and gRPC.

Reading time around 16 minutes. What you get: a framework for when to bump a version, how to add one, and how to retire it.

A renamed field took an app down

A mobile colleague reported that the app white-screened after a backend change. A user detail endpoint had renamed one field for clarity, and the old release still parsed the previous name, so the page failed to render.

The postmortem found three clients on that endpoint, iOS, Android and web, with three release cadences: two weeks of app review, a week of staged rollout, and instant deployment. Changing one field meant coordinating three adaptations at once.

That is not a field problem, it is a contract problem. Versioning answers one question: when you inevitably have to change an interface, how do old clients keep working, new clients get the new behaviour, and operations stay sane?

Why versioning is not optional

An API is a contract, and both sides hold expectations: the caller expects a field to always be a string, the provider expects a parameter never to appear. Versioning is change management for that contract. Without it, every change is a silent amendment, and the caller learns about it from a crash.

Three forces make change unavoidable. The product grows and needs new fields and endpoints. Security requires fixing an old response that exposes something it should not. And performance requires splitting a payload that returns five hundred fields to serve ten.

And direct change is impossible because the clients are not yours: users may not update for months, partner integrations cannot be edited on your schedule, and web clients may still be running a cached bundle.

ConsequenceHow it shows
Clients crashA renamed or retyped field fails to parse
Data lostA removed field makes old clients send data nobody reads
Security holesAn old version cannot be patched independently
Blocked teamsFront end and back end wait on each other to deploy

Four strategies

Path versioning

GET /v1/users/1001
GET /v2/users/1001

It is the most obvious, the easiest to test with a browser or a command-line client, and the easiest to route at a gateway by prefix. It also damages the REST idea that a URL identifies a resource, inflates into a wall of prefixes over the years, and hardcodes a version into every client.

Use major versions only, where the number means "there was an incompatible change". Compatible additions never bump it. And keep the prefix clean: the version segment belongs to the resource, not to a gateway namespace.

Header versioning

GET /users/1001
X-API-Version: 2

The URL stays stable and the version can be chosen per request. The costs are real: a browser address bar cannot set a header, so testing and debugging get harder; caches key on the URL, so the same URL with different headers needs explicit vary configuration; and generated documentation handles header versions inconsistently.

It suits teams with strong HTTP infrastructure and internal clients. It does not suit public APIs, where the debugging experience matters more than the elegance.

Media type versioning

GET /users/1001
Accept: application/vnd.myapp.v2+json

HTTP/1.1 200 OK
Content-Type: application/vnd.myapp.v2+json

This is the theoretically correct option, following content negotiation and allowing one resource to have several representations. It shares the header strategy's problems, and it overloads a header whose job is format negotiation with versioning, which confuses both. Most client libraries handle custom media types inconsistently.

Theoretically best, practically least recommended, unless you are building a genuinely hypermedia-driven API.

Compatible evolution

The most underrated and most used strategy is not to bump at all when the change stays backward compatible.

# incompatible, so bump
# v1: {"nickname": "Zhang San"}
# v2: {"display_name": "Zhang San"}

# compatible, so do not
# v1: {"nickname": "Zhang San"}
# v1: {"nickname": "Zhang San", "level": 3}

Add, never remove; extend, never alter.

ChangeCompatibleBump
New fieldYesNo
New endpointYesNo
Type changeNoYes
RenameNoYes
RemovalNoYes
Changed meaning of a valueNoYes
Numeric precision increaseDependsDepends on the client
Array ordering changeDependsDepends on whether clients rely on order

This is the foundation: most changes do not need a new version. Ask whether the change breaks an old client, and bump only when it does.

When to bump

Must bumpExample
Deleting or renaming a fieldA clearer name for the same value
Changing a typeAge from integer to string
Changing error semanticsAn unauthorised code now means an expired token
Fixing a leakThe old response exposed something it should not
Splitting an endpointOne aggregate endpoint becoming several
Changing business meaningA status field now describes payment rather than the order
 
about to change the interface
+-- a new field or endpoint?      -> add it, no version
+-- a bug fix?                    -> fix it, no version
+-- a field that was always wrong?
|   +-- yes                       -> bump, keep the old version
|   +-- unsure                    -> treat it as incompatible and bump
+-- a security hole?              -> bump, and patch the old version too

The lifecycle

Shipping a new version is the start, not the end, and the old one keeps running. Route new clients to the latest by default while old clients ask for the version they know. Monitor call volume per version, because a rising old version means migration has not happened. And keep documentation for every version readable.

request -> gateway -+-- v1 (old service, still running)
                    +-- v2 (current)
                    +-- v3 (canary)

Coexistence costs code maintenance across branches, regression testing per version, and data consistency risk when both versions write the same tables under different names. Keep two or three active versions at most; beyond that the cost grows faster than linearly.

Retirement is a process. Mark the version deprecated in documentation and in response headers, with a sunset date and a link to the migration guide. Notify the callers through every channel you have. Watch the volume fall. Then throttle it, return a gone response, and finally remove it. Keep the documentation available afterwards for whoever is still migrating.

HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Nov 2025 00:00:00 GMT
Link: </docs/migration/v1-to-v2>; rel="migration"
API typeMinimum coexistence
Internal servicesOne to two weeks, since every service is yours
Partner APIsThree to six months, since they have their own roadmap
Public APIsSix to twelve months, because the long tail is long

gRPC and GraphQL

message User {
  int32 id = 1;
  string nickname = 2;
  string display_name = 3;
  reserved 4;
  reserved "old_field";
}

In protobuf, field numbers must never be reused, so a removed number and name are reserved to prevent someone assigning them a new meaning. Types have their own compatibility rules, and optional versus required needs care. Because serialisation keys on numbers rather than names, compatibility is far stronger than JSON, and many gRPC APIs never bump a version at all.

{
  user(id: "1001") {
    nickname
    level
  }
}

GraphQL's official position is no versioning: there is one endpoint, clients ask for what they need, and adding a field affects nobody who did not ask for it. Change is expressed with a deprecation directive, and removal is a last resort. The strength is that version explosion cannot happen. The weakness is that a genuine semantic change has no version boundary to hide behind, so it becomes a new field plus a migration window.

Five traps

Retiring before migrating. Ship the new version, watch the old one's traffic fall, notify, then remove. Launching takes minutes and retiring can take months.

Calendar versions. A date in the path says when, not what: callers cannot tell whether it is compatible. A number that counts incompatible changes does, and the date belongs in the changelog.

A "compatible" change that is not. Turning a comma-separated string into an array breaks every client that splits it. The gold standard is whether old client code runs unmodified; if it does not, the change is incompatible.

Versioning only at the gateway. If two versions write the same table and only one knows a new column, the other's writes overwrite it with null. Apply the same rule to the database: add columns, never remove them, give new columns defaults, and prefer a new column over redefining an old one.

No per-version monitoring. Without volume, error rate, client type and caller per version, you cannot know when retirement is safe, and you find out someone still depends on it when it breaks.

Checklist and questions

  • Is the change backward compatible? If not, bump.
  • The old version keeps running when the new one ships.
  • Gateway routing is correct for both prefixes.
  • Database changes only add columns, with defaults.
  • Documentation is updated and every version stays readable.
  • Per-version monitoring exists for volume, errors and callers.
  • Callers have been notified with a migration guide.
  • A retirement plan exists with a timeline, notifications and staged removal.
  • Responses carry the version they served.
  • Deprecated versions return deprecation and sunset headers.

Path or header? Path by default: it is visible, testable, cacheable, and fits almost everything. Headers suit internal APIs behind uniform infrastructure.

Start at zero or one? One. Zero implies instability, and the point of versioning is stability. An API under rapid change should ship under an alpha or beta prefix instead.

Do compatible changes need announcing? Not with a migration window, but they belong in a changelog so callers know something new exists.

How many versions at once? Three at most; beyond that the maintenance cost climbs steeply, and pressure to migrate beats carrying them.

How do large public platforms do it? Mostly path versions, kept alive for a year or two, because they cannot control anyone's upgrade schedule. Expect the same if your API is public.

Do internal services need this? Only across team boundaries. Within one team, simultaneous deployment through continuous integration can replace formal versions.

Does GraphQL really avoid versions? Mostly, but a genuine semantic change still means a new field, a deprecation mark and a migration window.

Closing

With versioning in place, the incident has a script: recognise the rename as incompatible, ship a version that returns the new name while the old one keeps the old, let old apps keep calling the old, let new apps use the new, watch the old volume fall, notify, and remove.

It may take two months, and nobody sees a white screen.

The essence is not a segment in the URL. It is a promise to callers: this interface will not change behind your back, and if it must, you get a stable new version and time to move. That is a technical problem and a trust problem at once.
