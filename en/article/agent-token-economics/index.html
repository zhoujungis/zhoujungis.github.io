Token economics: a tenfold spread on the same task

2026-11-08 · 34 min · Stack Frame

Who this is for: people whose agent bills arrived and hurt; people who think cost equals unit price times tokens; people who want the bill down without changing models.

TL;DR: agent cost is not price times usage, it is context strategy times request count. A tenfold spread on one task comes from three levers: whether the prefix is stable, whether context gets compacted, and how many requests a task actually makes. Of the five budget constants in NanoHermes, three count bytes while their names say characters, and the memory block rewrites the system message every turn, which shortens exactly the part that should never change.

Two bills for the same task

Same repository, same request, fix three error handling sites in a Go service, same model. The two bills differ by an order of magnitude. The difference is not the model or the prompt. It is three things.

  • The first run used a client that rebuilt the system prompt on every request; the second kept the system prefix unchanged.
  • The first took 37 turns, the second took 14.
  • The first pasted go.mod and two 800 line files into the context; the second pasted only the three sites being changed.

If you decompose cost as price times tokens, you can only explain the price difference. Decomposed as prefix stability times context size times request count, you can explain ten times.

Three levers, one counterintuitive

LeverMechanismOrder of magnitude
Prefix stabilityThe provider's prompt cache matches token by token from the front; change one byte and everything after it misses3 to 20 times
Context compactionPushes history back from linear growth to a constant, cutting the quadratic term2 to 5 times
Request countEvery turn resends the entire context, so turns are a multiplierProportional to turns

The counterintuitive one: prefix stability affects the bill more than model choice does. A model three times the price with a stable prefix usually costs less than a cheap model that rewrites the system message every turn. Price is a linear factor; the cache is a discount applied to all of history, and history is what compounds.

That holds only if the provider really supports prefix caching, which the major ones do with different conditions: minimum prefix length, cache lifetime, and whether identical bytes are required. This post only covers the side you control, which is not putting anything volatile in the prefix.

Writing the cost formula down

cost ≈ Σ_t [ P_in × (S + H_t) + P_out × O_t ]

Where S is the stable prefix, system prompt plus tool schemas plus project docs. H is history at the start of turn t. O is output. Three things deserve attention.

S is resent every turn. Forty turns means forty copies. At 30,000 tokens of prefix that is 1.2 million tokens on prefix alone.

H accumulates. Turn one has one user message, turn forty has dozens. That is the source of the quadratic term.

O is charged once as output, and then becomes part of H, so it is charged again on every later turn.

total_in ≈ N × S + d × N × (N - 1) / 2

The second term is quadratic in N, which is why a long task is not slightly more expensive but wildly more expensive.

Four units: bytes, characters, tokens, dollars

UnitUsed byConversionError source
ByteString::len(), request bodiesOne Chinese character is three bytesJSON escaping, base64
CharacterHumans, chars().count(), truncation notesOne Chinese character is one characterFull-width punctuation, emoji
TokenProvider billingChinese is roughly one to one and a half characters per tokenTokenizer, model
DollarThe invoiceUnit price times tokensCache discounts, batching

There is no linear formula from bytes to tokens, but the ranges are stable: English about four characters per token, Chinese about one character per token, code about two characters per token. Enough for an order of magnitude, not for a budget.

Bytes to characters is simpler and more treacherous. JSON serialization turns a newline into two bytes and a quote into two bytes, so a serialized message is slightly larger than the original text, typically five to fifteen percent for a code file.

Which explains something important: the same number means different things at different layers. 120,000 is bytes in the context budget, bytes in the project docs cap, characters in the fetch parameter, tokens in the output limit. Four ceilings, four units, and three of the names imply a different one than they use.

A forty turn worked example

TermValueNote
S3,000 tokensAbout 1,200 of system, 1,800 of tool schemas
d1,200 tokensAverage added per turn
N40 turnsThe default iteration cap
O400 tokensCharged separately at the output price
CaseCalculationInput tokens
No cache40 × 3,000 + 1,200 × 7801,056,000
No cache, one compaction at turn 2040 × 3,000 + 1,200 × (190 + 190)576,000
Full prefix hit3,000 + 40 × 1,20051,000

The first and third rows differ by about twenty times, which is where the tenfold spread comes from. Look at the second: compaction did nothing to the 120,000 of prefix, it changed the slope of history. History restarts at turn 20, so one triangle of 780 becomes two triangles of 190, and the quadratic term halves. Compaction saves history, never prefix.

If cached input costs a tenth of normal input, the third row is worth about 48,300 full-price tokens against 1,056,000, roughly twenty-two times. That number is large enough to warrant the disclaimer: it is arithmetic, not an invoice. Real multiples get pulled down by cache minimums, cache expiry and the output share, but the direction holds.

The full byte bill of one request

ComponentSizeRepeatedNote
System prompt text1,200 bytesEvery turnFixed
Mode, persona, project docs20,000 bytesEvery turnThe project docs cap
Skill list1,000 bytesEvery turnEnabled skills
Tool schemas7,000 bytesEvery turnTwenty-odd built-ins

History240,000 bytesAccumulatesAbout 20 × 12,000 at turn 20
This turn's user message300 bytesOnceBecomes history afterwards

About 272,000 bytes, of which under 3,000 is genuinely new. The other 269,000 bytes are repetition.

Three conclusions. The stable prefix here is about 29,200 bytes, an order of magnitude below history at turn twenty, while in turns one through five it dominates, so prefix and history optimizations cross over somewhere around turn five to ten. Tool schemas are pure fixed overhead that never changes with the task and is paid every turn, so an agent with thirty MCP tools can spend more on schemas than on its system prompt. And history is 88% of the request, which is why invalidating history every turn is the most expensive mistake available: it pushes 88% of the content from cached price back to full price.

What compaction really does

Cutting the quadratic term. Without compaction the forty turn sum of history is 936,000. Compact once at turn twenty and it becomes two triangles of 190, so 456,000, almost half. Compact more often and the quadratic term shrinks further, but each compaction costs money, so there is an optimum.

Quantified: with compaction cost C, saving h per remaining turn, and k turns left, it pays when k × h > C. For a forty turn task that almost always holds; for a three turn task compaction is pure waste. Which means "when to compact" should depend on remaining turns, and NanoHermes does not look at that.

The five budget constants

Plus three defaults: an output limit of 4,096, temperature 0, forty iterations. Those eight numbers decide how expensive a task can get.

CONTEXT_CHAR_BUDGET does not mean what its name says

let size: usize = self.messages.iter().map(|m| m.to_string().len()).sum();

Serialization, then len(), which is UTF-8 bytes. The constant is named for characters.

In pure ASCII English the two are near enough that the name does no harm. In Chinese a character is three bytes, and serialization escapes newlines and quotes, so a budget of 120,000 "characters" actually holds about 40,000 Chinese characters.

That is not a naming nit, it is an observable cost bias. You think you compact at 120,000 characters and you compact at 40,000; and if you estimate tokens from "120,000 characters" you overestimate by three times and every cost projection is wrong.

Worse, it colludes with the tool output cap, which also uses len(). Three ceilings, all named characters, all counting bytes.

What 120,000 bytes is in Chinese

ContentBytesApproximate charactersRough tokens
English code120,000120,00030,000 to 35,000
Mixed English and Chinese120,00070,000 to 80,00040,000 to 50,000
Pure Chinese120,00040,00030,000 to 40,000

Note the code row: code has higher token density than prose, since symbol-heavy fragments often run one token per character. So the same byte budget runs out of tokens sooner in code-heavy work.

The practical rule: never convert a character budget into a token estimate. Use per-content-type rates instead.

Compaction fires on three conditions

if !force && (size <= CONTEXT_CHAR_BUDGET || self.messages.len() <= KEEP_RECENT + 1) {
    return 0;
}

Total bytes over 120,000, more than eleven messages, and not a forced compaction. The third condition is why manual compaction matters in practice: automatic compaction happens once when the threshold is crossed, then history grows again until it crosses again. A task oscillating around 100,000 bytes might never trigger, or might trigger repeatedly.

let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
while start < self.messages.len() && self.messages[start]["role"] == "tool" {
    start += 1;
}

The loop skips tool messages so it never splits a call from its result, which would make the next request illegal. The cost is that the cut point moves forward, so the amount actually dropped can be far less than expected. A turn with eight parallel calls produces nine messages, all of which must be kept, so "keep ten" can mean "keep less than one turn".

A floor of ten messages

[0] system with the memory block
[1] system with the summary
[2..] the last ten messages in full

If several of those ten are multi-kilobyte tool results, compaction barely changes the total: you dropped old history and kept the most expensive part. Which produces a counterintuitive conclusion: compaction does almost nothing for tool-heavy tasks, because the heavy part is inside the floor. To make compaction effective, either make tool output lighter or make the floor count bytes instead of messages.

Counting messages has another problem: ten short messages and ten long ones differ by tens of times. The same constant means two very different budgets.

Three ceilings on context

LayerSet byValue hereWhen exceeded
WindowThe modelProvider-dependentThe request fails with 400
BudgetThe client120,000 bytesCompaction fires
WalletYour toleranceNothingThe bill surprises you, silently

Window is largest, budget next, wallet smallest. A healthy design keeps the budget well under the window to absorb one huge tool result, and gives the wallet a soft cap with a warning before it is exceeded.

NanoHermes has the first two and not the third, which means a runaway task can burn a day's quota with no warning. The fix is twenty lines: a session token cap checked at the top of each turn, interrupting with a message. Controlled failure beats an uncontrolled invoice.

The compaction request has no per-message cap

excerpt.push_str(&format!("{role}: {}
", content));

Everything dropped goes in, unbounded per message, and the summary is asked for three hundred words, roughly four to five hundred tokens. So the trade is tens of thousands of input tokens for a few hundred output tokens, buying smaller requests afterwards.

Profitable on long tasks, pure loss on short ones. The only criterion used is context size, never remaining turns, so a task that crosses the threshold on its final turn pays for a compaction it will never use.

Is compaction an investment or a loss

k × h > C

With C the compaction cost, h the tokens saved per later turn, k the turns left. Drop 80,000 tokens of history, summarize into 500, and h is about 79,500 while C is about 80,500, so it pays from k of two onward.

Drop only 8,000 tokens, which happens when you compact the moment you cross the threshold, and k has to exceed eleven. Which is exactly the common case, because the trigger is "just crossed the threshold".

The inequality also shows a design opportunity: the threshold should be a function of remaining turns, not a constant.

Three alternatives to summarization

ApproachMethodCostInformation lossFits
SummarizeModel summarizes the dropped historyOne large requestMediumLong conversations, decisions to preserve
Hard cutDrop old messages outrightZeroHighClear task boundaries, genuinely stale context
Structured stateWrite progress into a todo list or task boardOne tool callLow, the state is explicitMulti-step tasks with a checklist

The third is the most underrated. NanoHermes already has a todo tool and a task board. If each turn writes done, pending and blocked into a structured list, old messages can simply be cut, because the list is the compressed state and is more accurate than a model's summary. A todo call costs a few hundred tokens, a summary costs tens of thousands.

The catch is architectural: state has to be separated from history. In practice, hard cut for short tasks, summarize for long ones, structured state for multi-step ones. NanoHermes has only summarization, and does not look at task type.

The first segment of the stable prefix

The system prompt is assembled in a fixed order, from most stable to least: identity, operating rules, workspace root, mode guidance, user persona, project guidance. Within one process that whole block never changes, which is friendly to prefix caching.

Two more segments are appended after it, the project context file and the skill list, both read once at startup. So up to that point the prefix is stable. The problem is the next section.

The tool list is part of the prefix

Tool schemas travel with every request, so the provider bills them as input. A built-in set runs 1,500 to 2,000 tokens, and MCP can double it.

What matters is order stability. Permission filtering removes some tools, MCP tools are appended in connection order, and as long as that order holds within a process the schema section is part of the stable prefix. Jitter, such as an MCP reconnect changing order, invalidates the cache from the jitter point onward.

Which makes "sort the tool list before sending" the most overlooked free optimization. Sorting by name does not change capability and makes the prefix identical across sessions, which is what cross-process cache sharing depends on.

Project docs at 20,000 characters

The loader reads the global file, then every ancestor directory down to the workspace, concatenating in that order. More specific rules come later, which is the right semantics for overriding. Truncation retreats to a character boundary, which is correct and necessary for UTF-8.

But the cap counts bytes, so a Chinese AGENTS.md injects about 6,600 characters. And the real cost is that those 20,000 bytes appear in every request: over forty turns that is 800,000 bytes of project documentation. An AGENTS.md that size contributes to the bill about as much as twenty extra turns. A nice cost counterexample to the intuition that more documentation is always better.

The memory block rewrites the cache every turn

let user_text = memory::content_text(&content);
if let Some(dir) = self.ctx.memory_dir.clone() {
    let block = memory::retrieve_block(&dir, &user_text);
    self.set_memory_block(&block);
}

Retrieval depends on this turn's input, so the block can differ every turn, and it is written into the first message. So before every request, the head of the context changes.

Inside the block replacement the implementation is fine: delete the old marked range, append the new one, no accumulation. For prefix caching it is the worst possible layout. The cache matches from the front, so a change at the end of the system message means the stable part still hits, and everything from the memory block onward, including the summary and all prior conversation, becomes new tokens.

In other words, re-retrieving memory every turn re-bills the entire history every turn, and history is the quadratic term. Trading 2,400 characters of memory for invalidating all history is a net loss on long tasks.

The right move places the variable segment just before the last user message, as its own message, leaving the first message byte-identical. The model sees a slightly weaker instruction position, and history hits the cache.

It is a clean example of local correctness producing global damage: the replacement function is right, the retrieval is right, and re-retrieving each turn is right, and three correct decisions combine into losing the most valuable optimization available.

Why the variable segment sits at the end

The placement is what matters, not the wording. Variable content at the tail of the system message invalidates everything after it; the same content in a separate message before the user turn leaves the prefix intact.

Tool output caps also count bytes

if s.len() <= max {
    return s;
}

Three observations. s.len() is bytes, and the cap is bytes, so a Chinese file hits the ceiling at about 6,600 characters. The note says characters omitted while the arithmetic is bytes, so it overstates by three times for Chinese. And the cap is applied at the dispatch layer, shared by every tool, which is reasonable for search and brutal for file reads: an 800 line file gets cut mid-way, and the model reads again.

Which is the cost: one truncation produces one extra request, and that request resends the entire context.

Two layers of truncation

let max_chars = args
    .get("max_chars")
    .and_then(|v| v.as_u64())
    .unwrap_or(20_000)
    .clamp(500, 200_000) as usize;

So the fetch tool can return up to 200,000 characters, which dispatch then cuts to 20,000 bytes. Two ceilings, two units, and both defaults happen to be 20,000, which is not a coincidence but the same habit growing independently in two modules. The practical consequence is that asking for more than 20,000 bytes has no effect at all: the parameter exists and is overridden.

A tiering strategy for tool output

TierToolsSensible capWhy
SmallWrites, todos, patchesA few hundred bytesOnly success and a summary are needed
MediumSearch, glob, web search2,000 to 5,000 bytesList results become unreadable beyond that
LargeFile read, shell, fetchPaginate rather than cutThe content is the material

The third tier needs the most design. File reads already have an offset and a line limit, so pagination exists at the parameter layer. The problem is the interaction with byte truncation: reading a Chinese file usually hits the byte ceiling before the line limit, and the tail note saying how many lines remain is generated before the cut, so it gets truncated too. The model cannot see how much is left and guesses an offset, and one truncation becomes one extra request.

The fix is to compute the safe line count from the byte budget and return an explicit next offset, so the model never guesses.

Images: base64 is a third larger and uncapped

Attachment encoding reads the file and base64-encodes it with no size check. A five megabyte screenshot becomes about 6.7 megabytes of string, which enters the messages and is then sent on turn one, turn two, and every turn until compaction drops it. Over a twenty turn visual task that is around 134 megabytes uploaded.

The image count limit bounds the number, not the size. Four five-megabyte images is a 27 megabyte request, past the ten megabyte body limit most gateways enforce, which produces a 413 that the ledger does not record.

A reasonable implementation checks the file size, scales rather than refuses, and records the bytes after scaling. The hard part is the first step: realizing that a count limit is not a cost limit.

Images are resent every turn

The real cost of any tool result is not one request, it is one request times how many turns it survives. A 20,000 byte result living twenty turns is 400,000 bytes of input, twenty times its original size. Which is why output caps are not only about drowning the model, they are about stopping compounding.

A useful corollary: large results that arrive early are the expensive ones. A file read on turn one is billed for forty turns; the same read on turn 39 is billed once. Overview first, then close reading, is a cost strategy as much as a cognitive one.

The hidden double cost of a small output budget

Where truncation landsSymptomCost
Tool arguments cut mid-JSONParse error, invalid argumentsThe model resends the whole call
Answer cut mid-sentenceThe user sees half a replyAnother turn to finish
Patch diff incompleteContext cannot be foundA regenerated diff

Failure happens on the output side and the retry resends the input side, so the saved output tokens are eaten by resent input, usually at a loss. The counterintuitive tuning advice: for tool-heavy tasks, raise the output budget rather than lowering it, because a patch can be hundreds of lines and one truncation costs far more than the headroom.

Retries resend the whole prompt

The retry loop rebuilds the request body each attempt, including the full message array, so one 503 costs about as much as another turn. With two retries the worst case is three times the input for that turn. A 429 is usually not billed; whether a 503 is, the client should not assume.

And fallback: a cheaper model is good for money, unless it is less capable, in which case the task takes more turns. Cheap price times more turns can end up more expensive.

Forty iterations and eight parallel calls

LimitValueCost meaning
max_iterations40Up to forty requests per user message
MAX_PARALLEL_TOOL_CALLS8Up to eight results entering context in one turn
MAX_PARALLEL_SUBAGENTS4Up to four sub-agents burning tokens at once

The worst case: forty turns of eight results at 20,000 bytes is 6.4 megabytes of theoretical context, unreachable because compaction fires at 120,000 bytes. But the turn before compaction can hold 120,000 plus eight times 20,000, about 280,000 bytes, because compaction runs between turns and not between tool results.

That is a real spike: one parallel tool turn can push the context to twice the budget, and every later turn pays for it.

Sub-agents are worse, since four of them at forty turns each resend their own full context, up to 160 requests that never enter the main account. A parallel investigation can cost ten times the main task while the cost command shows a fraction of it.

The cost model of a sub-agent

m × S + d × m × (m - 1) / 2

Each sub-agent carries its own system prompt close to the parent's S, and starts history from zero. With m of 15, S of 3,000 and d of 1,000, each sub-agent costs about 150,000 tokens, four of them 600,000, against 150,000 for the parent over the same period. The parent's own cost report shows only that last number.

The shape matters more than the numbers: sub-agent cost grows with delegations times turns squared. Letting four sub-agents run forty turns each is not a parallel optimization, it is a fortyfold invoice. A per-sub-agent iteration limit, around twelve, is worth more than any cache tuning because it cuts the quadratic term.

Measuring the cache hit rate

hit_rate = cached_tokens / prompt_tokens

NanoHermes does not read the cached token field, so the measured rate is zero, which means "unknown" rather than "no hits", and that difference is fatal during optimization: you conclude caching does not work and give up on it.

Without the field there is a proxy: hash the serialized message array per request and count how often the prefix is identical. That is an upper bound on the hit rate.

MetricMeaningHealthy value
Prefix stabilityShare of adjacent turns whose prefix is byte-identicalNear 100%
Average history lengthSum of history over turnsLinear growth means no compaction
Compaction frequencyTriggers per ten turnsOne or two

If the first is low, something volatile is in the prefix. Start by looking at the tail of the system message.

Five preconditions for caching

PreconditionTypical requirementIf violated
Prefix long enoughA minimum token count, hundreds to thousandsShort prompts are not cached, silently
Byte-identicalSame spaces, newlines, field orderOne extra space invalidates everything
Same modelSame model idA different model is a different cache pool
Within the windowMinutes to hoursAn overnight session starts cold
Same account or orgCaches do not cross tenantsA new API key loses the cache

Which explains "cached locally, not in production": locally you run back to back with identical prompts and one model; in production there is concurrency, long gaps and occasional model switches.

The third and fifth are easy to trip. Switching model once loses the whole prefix cache, and so does falling back. So the true cost of a model switch includes the cache you discard.

Why output costs more and is charged twice

Σ_t [ P_out × O_t + P_in × O_t × (N - t) ]

Output is generated token by token, so each one costs a forward pass, while input can be processed in parallel, which is why output runs three to five times the input price. For an agent it is amplified: a 400 token reply is charged once at the output price, then becomes history and is charged again at the input price on every later turn.

The second term dominates. A 400 token reply on turn five is resent thirty-five times. At four times the input price, the effective cost is 15,600 input tokens, thirty-nine times its sticker price.

So verbose intermediate narration costs far more than a verbose final answer. The instruction not to over-narrate is a cost control, not a style preference.

Three counterintuitive conclusions

A cheap model can be more expensive. Cheaper models follow instructions and format tool calls less reliably, which shows up as extra turns and repeated reads. Price down five times and turns up three is a small saving; turns up six is a loss. Judge by total tokens per completed task, not by unit price.

Longer context is not necessarily more expensive when caching works. Repeated history is billed at the cached rate, often a tenth. What is genuinely expensive is changing one byte per turn.

Retry can cost more than the failure. One 503 costs about another turn, and two retries make the worst case three times. Retry count is a cost parameter as much as a reliability parameter.

Five common estimation errors

Estimating per conversation rather than per turn, which badly underestimates long tasks. Treating context size as input tokens, which is off by two times from the start. Forgetting that output is re-billed as history, which is the dominant term on long tasks. Assuming retries are free, when only some error classes are. And ignoring sub-agents, which can be four times the main task.

One optimization, fourteen turns to nine

Start from a bug fix task: fourteen turns, 186,000 input tokens on the main agent, nineteen file reads, twelve searches. File reads averaged 11,200 bytes, 212,800 bytes total, more than the entire input. The cause: large reads were clamped, the truncated result carried no next offset, and the model guessed another offset.

The change was one thing: compute a safe line count from the byte budget and return an explicit next offset. No model change, no prompt change.

MetricBeforeAfterChange
Turns149down 36%
File reads197down 63%
Main input tokens186,000101,000down 46%
Cache hit rate0.710.78up 7 points

Three metrics moved together and caused each other: fewer turns, shorter history, better hit rate. Then check that capability did not drop, by rerunning the same batch and comparing the final diff. Saving money while shipping worse code is not saving.

The lesson is plain: most cost problems are not "using something expensive", they are "using too much". Nineteen reads of one file is not a dumb model, it is a tool that forced it. Tool granularity sets turn count, and turn count sets the bill. So the first place to optimize is not the billing dashboard, it is the tool description.

Five ways to look cheap and cost more

Lower the output limit to 512Cheaper outputArguments get truncated and the turn restarts

The last one deserves attention. The memory block does take 2,400 characters, and what it saves is the model re-asking what your project is and how far the last bug got. One repeated question is one turn, and one turn is tens of thousands of bytes of input. Swapping 2,400 for tens of thousands is a good trade every time, provided it is not placed where it breaks the cache.

Three experiments you can run in a day

Freeze the system message and watch the request bytes. Comment out the memory injection, run the same ten turn task twice, and record bytes per request. The bytes barely change, since memory is 2,400, but if you can read cached tokens the hit count jumps. Which shows the cost difference lives in the cache, not in request size.

Change file reads to a byte budget. Ask for a 1,500 line Chinese file with the current default line limit and it hits the byte clamp first, with no next offset, so the model blind-reads again. After the change, two targeted 8,000 byte reads replace one truncation plus one blind read. Expect 20 to 30 percent fewer bytes and one fewer turn. Which shows truncation is deferred payment, not saving.

Raise the output limit and watch the failure rate. Run ten tasks with large patches and count invalid argument errors. At 4,096 expect one or two truncations, at 8,192 expect none, with total output essentially unchanged. Which shows lowering the output limit is a false optimization.

All three need only byte counts and turn counts from recorded request bodies, available locally, faster and more reliable than waiting for an invoice.

Where budget constants come from

MeasurementHowTypical value
Tool result p50 and p95Run twenty real tasks, record bytes before the clamp3,000 and 18,000
Added bytes per turnTotal bytes divided by turns8,000 to 15,000
Stable prefix bytesSerialize the first message plus tool schemas25,000 to 30,000

From those, the caps follow. A tool result cap just above p95 is 20,000, which matches observation. The recent floor should hold at least a full turn, one assistant plus eight results, so ten is right. The context budget should leave several times the room in the model window. And the image count limit is meaningless without a per-image byte limit, which is the gap in the derivation: a count without a size is not a limit.

The method transfers to any agent. Every cap should answer which observation it corresponds to; a cap that cannot answer that is a guess, and guesses eventually meet a real task.

What to save and what not to

TargetSavesCostsVerdict
System promptHundreds to thousands of tokensInstruction following, tool rulesDo not cut, it is the cheapest capability you buy
Project docsUp to 20,000 bytesConventions, namingCan cut, but load on demand rather than delete
Tool schemasHundreds of tokens per toolThe capability disappearsDo not cut, removing a tool removes a limb

Output lengthHundreds of tokens per turnExplanatory qualityCan cut, intermediate narration first
Memory injection2,400 bytesPreferences, past lessonsDo not cut, it is what saves turns

Read the third column: if cutting something destroys a capability, do not cut it; if it only means one more turn, cut it. Tool schemas and the system prompt are the first kind, history and narration the second. Cutting cost at the memory block is the most common wrong optimization.

Making cost a regression metric

#[test]
fn a_fixed_task_costs_no_more_than_the_baseline() {
    let (agent, requests) = run_scripted_task();
    assert!(agent.usage().requests <= 6, "turn inflation");
    assert!(requests.iter().map(|r| r.len()).sum::<usize>() <= 180_000, "context inflation");
}

Bytes rather than tokens, since there is no real provider, and bytes correlate strongly enough. Add a prefix assertion: run two turns on one agent and require the first message to be byte-identical between them.

That test fails immediately, because the memory block is rewritten every turn. It should fail, and failing early is the point: it is exactly the cost defect we want exposed.

Closing

Cost is prefix times history times turns, not price times tokens. Price is linear, history is quadratic, and a forty turn task is roughly N times the prefix plus d times N squared over two.

Compaction cuts the quadratic curve into smaller segments. It is not about fitting, it is about turning one big N squared into several smaller ones, which means the optimal frequency comes from compaction cost against remaining turns, not from a threshold.

Prefix caching is the largest single optimization and the thing most easily destroyed by one changed byte per turn. Putting the re-retrieved memory block at the end of the first message invalidates the entire history every turn, which is the single most valuable fix available here and a textbook case of three correct decisions combining into one wrong one.

And three ceilings named for characters all count bytes, so in Chinese they are all three times smaller than the name promises. Nothing crashes; every cost estimate and every truncation just drifts from intuition, and the first requirement of observability is that numbers mean what you think they mean.
