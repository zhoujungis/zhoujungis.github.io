NanoQA: four hard boundaries in a test management system

2026-11-20 · 31 min · Stack Frame

Who this is for: full-stack engineers building internal tools; anyone who has been burned by "the test case changed but the old report didn't"; developers who want to see how optimistic locking, state machines and audit diffs look in real code.

TL;DR: NanoQA has 26 models, 67 routes, 73 view classes and 232 backend tests. The hard part is not moving Excel into a browser. It is four constraints: test cases must be versioned, execution results must bind to a version snapshot, concurrent edits must be detected, and every change must commit in the same transaction as the business write. Those four constraints decide whether this data is still usable as evidence in five years. The costs are equally explicit: permissions are not cached, so every request recomputes them; duplicate detection is O(n²) and takes 55.5 seconds at 800 cases; the AI layer is currently an offline mock.

Reading time around 32 minutes. Level: advanced.

This is not another CRUD app

"Test management system" sounds like the easiest category to build as CRUD: create, read, update, delete test cases, plans and defects. Any backend practice project can produce the screens in a week.

But when a real QA team starts using it, the first thing that breaks is not the UI. It is credibility. Three concrete failure scenes:

  • Someone changed step 3 yesterday. Pull up a test report from three months ago and the failure title has changed. Was it wrong then, or was it edited later?
  • Two test engineers open the same case. A changes the priority, B changes the steps. Who overwrote whom?
  • A defect goes straight from "Open" to "Closed", skipping "Resolved". The fix-duration metric will be zero forever.

All three share one root cause: the data model threw away traceability. It is not a UI problem. Everything that makes NanoQA's backend complicated is an answer to those three questions.

Start with scale. This is not a demo repository:

backend  211 py files   12,132 lines
frontend 36 views       17,395 lines (vue + ts)
26 models   67 routes   73 view classes   55 serializers   39 service files
19 migrations   232 backend tests

That 232 is not an estimate. It is a real count of def test_.

The data model: one loop, not six islands

The README says "requirement → case → plan → execution → defect → report". In the schema it is a directed chain, not six parallel modules:

Requirement ──covers──▶ TestCase ──selected──▶ TestPlan ──starts──▶ TestRun
     │                     │                                          │
     │                     │                                          ▼
     │                     │                                      TestResult
     │                     │                                          │
     │                     └──── TestCaseVersion ◀──binds─────────────┘
     │                                                                │
     └────────── RequirementDefect ◀── Defect ──▶ TestResultDefect ───┘
                                       │
                                       └──▶ TestCaseDefect

The important line is in the middle: TestResult points at both TestCase and TestCaseVersion. That single design decision gives you every traceability property downstream, and it is the comment that appears most often in the whole codebase: "pitfall 4".

Test cases must be versioned

Look at the main table first. TestCase stores only the current state; the content lives in a version table:

class TestCase(SoftDeleteModel):
    case_key = models.CharField(max_length=32, unique=True)
    title = models.CharField(max_length=255)
    precondition = models.TextField(blank=True, default="")
    priority = models.CharField(max_length=2, choices=PRIORITY_CHOICES, default="P1")
    case_type = models.CharField(max_length=16, choices=TYPE_CHOICES, default="functional")
    automation_status = models.CharField(max_length=16, choices=AUTOMATION_CHOICES, default="manual")
    status = models.CharField(max_length=16, choices=STATUS_CHOICES, default="draft")
    current_version = models.PositiveIntegerField(default=1, validators=[MinValueValidator(1)])

current_version is a cursor pointing at whichever row in TestCaseVersion is currently in force. The version table is where content actually lives:

class TestCaseVersion(models.Model):
    """Case version snapshot: historical results must bind a version (pitfall 4).
    steps is JSONB: [{order,action,expected}]."""

    test_case = models.ForeignKey(TestCase, on_delete=models.CASCADE, related_name="versions")
    version = models.PositiveIntegerField()
    title = models.CharField(max_length=255)
    steps = models.JSONField(default=list)
    expected_result = models.TextField(blank=True, default="")
    change_summary = models.CharField(max_length=255, blank=True, default="")

A version is not "a new row on every save". A new version is created only when a content field actually changes. Changing priority, owner or tags does not count:

content_changed = (
    new_title != case.title
    or new_precondition != case.precondition
    or new_description != case.description
    or new_steps != version.steps
    or new_expected != version.expected_result
)

That distinction matters. Otherwise moving a case from P1 to P0 leaves a "content changed" entry in the history, and the version number quickly stops meaning anything. The fields that trigger a version are pulled out into a constant:

CONTENT_FIELDS = ["title", "precondition", "steps", "expected_result", "description"]

So "how many times has this case changed" now has exactly one correct answer: current_version minus one. Not counting audit rows.

Execution binds a snapshot: so old reports cannot lie

Back to the first failure scene. If TestResult stored only test_case_id, the report would read the current case title when rendering a failed case. Someone edits the title three months later and the historical report changes with it, silently.

So when a run starts, the service pre-creates one not_run result per planned case, and pins the version object that is current at that moment:

version_map = {
    version.test_case_id: version
    for version in TestCaseVersion.objects.filter(
        test_case_id__in=case_ids, version=F("test_case__current_version")
    )
}
missing = [pk for pk in case_ids if pk not in version_map]
if missing:
    raise BusinessConflictError(f"case has no version snapshot: {missing}")

Then bulk-create the results:

TestResult.objects.bulk_create([
    TestResult(
        test_run=run,
        test_case_id=pk,
        test_case_version=version_map[pk],
        status="not_run",
    )
    for pk in case_ids
])

Note the filter uses version=F("test_case__current_version"). That is a cross-table comparison that only holds inside the query; there is no second filtering pass in Python.

There is an easy-to-miss choice here: pre-create not_run results instead of inserting at execution time. The payoff is threefold. The denominator is fixed the moment the run exists. "Not executed" and "executed but not submitted" stop being the same thing. And bulk submission can hit existing rows with filter(test_run=run, test_case_id=...) instead of doing an upsert.

The reporting side obeys the contract strictly:

def _failed_cases(results) -> list[dict]:
    failed = (
        results.filter(status="failed")
        .select_related("test_case", "test_case_version", ...)
    )
    return [
        {
            "result_id": result.id,
            "case_key": result.test_case.case_key,
            "title": result.test_case_version.title,   # snapshot, not current
            ...
        }
        for result in failed
    ]

result.test_case_version.title and result.test_case.title differ by one underscore, but they read two different tables. The first never changes.

Optimistic locking: two people editing one case

The second failure scene. The naive fix is "last write wins", and the cost is that someone silently loses work. NanoQA chooses explicit conflict instead.

The client receives updated_at with the data and sends it back untouched. The server puts it into the WHERE clause:

def save_with_lock(obj, expected_updated_at, update_fields: list[str]):
    """Update with optimistic locking: WHERE id=%s AND updated_at=%s, 0 rows -> conflict."""
    expected = parse_updated_at(expected_updated_at)
    new_updated_at = timezone.now()
    values = {field: getattr(obj, field) for field in update_fields}
    values["updated_at"] = new_updated_at

    rows = type(obj).objects.filter(pk=obj.pk, updated_at=expected).update(**values)
    if rows == 0:
        exists = type(obj).all_objects.filter(pk=obj.pk).exists() ...
        if not exists:
            raise NotFoundError("resource not found")
        raise OptimisticLockError("this record was modified by someone else; refresh and retry")
    obj.updated_at = new_updated_at
    return obj

Three details are worth calling out.

First, 0 rows has two meanings: a concurrent conflict, or the row is gone. The first should prompt a refresh; the second should say it does not exist. So after rows == 0 the code probes exists() and separates 404 from 409. It uses all_objects because after a soft delete objects cannot see the row, yet "exists but deleted" and "never existed" still need correct classification.

Second, the timestamp must round-trip untouched; the frontend is not allowed to format it. The comment on parse_updated_at is blunt:

"""Parse the client's updated_at (ISO microseconds, sent back verbatim; no frontend formatting)."""

The reason is practical. One toLocaleString on the client drops microseconds, and lock granularity degrades to milliseconds, where two writes in the same millisecond overwrite each other again.

Third, it uses .update() rather than save(). Django's save() writes updated_at itself, and then there is no WHERE condition left. You have to bypass the ORM's timestamp behavior so that updated_at is a condition, not a result.

The same lock is reused for defect updates: compare, write, then record the diff in the audit log.

State machines: write "who can become what" as a table

The third failure scene: a defect jumps from Open to Closed. The fix is not hiding the button in the UI — a frontend guard stops mistakes, not a direct API call. The fix is an explicit table of legal transitions in the service layer:

DEFECT_TRANSITIONS = {
    "Open": {"In Progress", "Rejected", "Duplicate", "Closed"},
    "In Progress": {"Resolved", "Open", "Rejected", "Duplicate"},
    "Resolved": {"Closed", "Reopened", "In Progress"},
    "Reopened": {"In Progress", "Resolved", "Open"},
    "Closed": {"Reopened"},
    "Rejected": {"Open"},
    "Duplicate": {"Open"},
}

Four tables: testcase, testplan, defect, requirement. One validator:

def validate_transition(entity: str, from_status: str, to_status: str):
    if from_status == to_status:
        return
    table = TABLES.get(entity)
    if table is None:
        raise InvalidTransitionError(f"unknown state machine: {entity}")
    allowed = table.get(from_status)
    if allowed is None:
        raise InvalidTransitionError(f"unknown state: {from_status}")
    if to_status not in allowed:
        raise InvalidTransitionError(f"cannot move from {from_status} to {to_status}")

A design note survives in the source and is worth copying more than the code itself:

D5 decision: on top of the documented chain transitions, allow the necessary
rollbacks (Deprecated->Active, Closed->Reopened, Rejected->Open) because they
match real QA workflows.

A pure chain state machine is beautiful in a textbook and infuriating in practice. A case marked deprecated by mistake must be recoverable. A defect that was closed and came back must reopen. A requirement that was rejected, revised, and resubmitted deserves another pass. Those rollback edges are a direct mapping of product requirements, and putting them in one table is far more readable than scattering them across a dozen if statements.

Timestamps come with it. When status changes, resolved_at and closed_at are stamped automatically, but only on the first entry:

if status_changed:
    now = timezone.now()
    if new_status == Defect.STATUS_RESOLVED and defect.resolved_at is None:
        defect.resolved_at = now
    if new_status == Defect.STATUS_CLOSED:
        defect.closed_at = now
    if new_status in REOPEN_STATUSES:
        defect.closed_at = None

The defect.resolved_at is None guard means Resolved → Closed → Reopened → Resolved does not overwrite the original fix time with the latest one. Metrics usually die exactly here.

Key generation: monotonic counters behind select_for_update

Business keys like SHOP-TC-000001 carry implicit requirements: no duplicates, no gaps, no regression under concurrency. Together those rule out "find max ID, add one" — two requests get the same value.

The implementation takes a row lock:

def next_key(project: Project, entity: str, width: int = 6) -> str:
    """Next business key, e.g. SHOP-TC-000001. Must be called inside the caller's transaction."""
    if entity not in {c[0] for c in NumberSequence.ENTITY_CHOICES}:
        raise ValueError(f"unknown entity: {entity}")
    with transaction.atomic():
        seq, _created = (
            NumberSequence.objects.select_for_update()
            .get_or_create(project=project, entity=entity, defaults={"next_value": 1})
        )
        value = seq.next_value
        seq.next_value = value + 1
        seq.save(update_fields=["next_value"])
    return format_key(project.key, entity, value, width=width)

select_for_update() becomes SELECT ... FOR UPDATE on PostgreSQL, holding that row until the transaction ends. Putting select_for_update inside get_or_create is slightly subtle: it only locks the existing-row path, and the create path relies on a unique constraint. That is why the concurrency test has to be a real transaction-level test:

Test isolation: every test database gets a unique name; TransactionTestCase's flush
truncates data-migration seeds (Role/Permission), and the test base has built-in
self-healing (ensure_rbac_seed); the concurrent key test enables serialized_rollback.

serialized_rollback deserves its own paragraph. Django's TransactionTestCase flushes the whole database by default. If seed data (27 permissions, 5 system roles) came from a data migration, the flush removes it, and every subsequent permission test fails with Role.DoesNotExist. The README keeps a dedicated FAQ entry about it, which tells you it has bitten someone.

Soft delete: quality assets are never physically deleted

TestCase inherits SoftDeleteModel, not TimestampedModel:

class SoftDeleteModel(TimestampedModel):
    """Soft-delete base: test data is a quality asset and is never physically deleted (§48)."""

    deleted_at = models.DateTimeField(null=True, blank=True, db_index=True)

    objects = SoftDeleteManager()
    all_objects = AllObjectsManager()

The split between the two managers is the whole point: objects sees only live rows, all_objects sees deleted ones too. Delete and restore are each a single field write:

def soft_delete(self):
    self.deleted_at = timezone.now()
    self.save(update_fields=["deleted_at", "updated_at"])

Why should test data never be physically deleted? Because it is evidence for three things at once: that a case existed (the coverage denominator), which case a failure belonged to (report context), and which cases covered a requirement at the time (review basis). Remove any one of those and historical reports develop holes.

The cost is that queries must be careful. If a case referenced by a TestResult is soft-deleted, select_related("test_case") will not find it (the default manager filters it out). This kind of problem only shows up in tests, which is why executions has a dedicated test_results.py.

RBAC: 27 permissions and a union of two role scopes

The full permission set is a list, used both as seed data and as a validation whitelist:

PERMISSION_CODENAMES = [
    "project.read", "project.create", "project.update", "project.delete",
    "requirement.read", "requirement.create", "requirement.update", "requirement.delete",
    "testcase.read", "testcase.create", "testcase.update", "testcase.delete",
    "testcase.execute", "testcase.review",
    "testplan.read", "testplan.create", "testplan.update", "testplan.delete", "testplan.execute",
    "defect.read", "defect.create", "defect.update", "defect.delete",
    "report.read",
    "user.manage", "role.manage", "audit.read",
]

That is 27. Five system roles (admin / pm / qa / dev / viewer) are different subsets of it.

The interesting part is resolution. A user's permissions in a project are the union of project-role permissions and organization-role permissions:

def permissions_for_user(user, project) -> set[str]:
    """Permissions in a project = project role permissions ∪ organization role permissions.

    v0.1 does not cache: membership/role changes must take effect immediately
    (a cache without invalidation causes a 60s permission lag).
    """
    ...
    role_ids: set[int] = set()
    if project is not None:
        role_ids.update(project.members.filter(user=user).values_list("role_id", flat=True))
        role_ids.update(project.organization.members.filter(user=user).values_list("role_id", flat=True))
    return _role_permissions(role_ids)

The comment captures a real trade-off: a cache without invalidation delays revocation by 60 seconds. A revoked test engineer can still delete cases for a minute after revocation, and that is unacceptable from an audit standpoint. Two extra queries per request is the cheaper price.

Permission checks hang off a view base class, mapped by HTTP method, instead of an if in every view:

class ProjectApiView(APIView):
    """Project-scoped view base that maps permission codes by HTTP method."""

    permission_classes = [IsAuthenticated, HasProjectPermission]
    method_permissions: dict = {}

    @property
    def permission_codename(self):
        return self.method_permissions.get(self.request.method, "")

Views then collapse to one dictionary:

class TestRunResultListCreateView(RunObjectMixin, ProjectApiView):
    method_permissions = {"GET": "testplan.read", "POST": "testcase.execute"}

GET needs plan-read, POST needs case-execute — two permissions for two methods on one URL, without writing two classes.

One more thing is easy to miss: how the project is resolved. Some views read project_id from the URL, some reverse it from an object (result.test_run.project), some override get_project(). The base class unifies all three with a cache and a fallback:

cached = getattr(request, "_nano_project", None)
if cached is not None:
    return cached
...
request._nano_project = project

Without the cache the same project would be queried three times per request: permission check, business logic, audit.

Audit: commit in the same transaction as the business write

The most common way to get auditing wrong is to record it asynchronously. The business write succeeds, the audit write fails, and now there is a change in the database with no evidence.

So the rule is: audit calls must live inside the same transaction.atomic() as the business write. Creating a case looks like this:

def create_case(project, data: dict, user, request=None) -> TestCase:
    """Create a case: key + case + v1 version + audit in one transaction."""
    with transaction.atomic():
        case = TestCase.objects.create(...)
        create_version(case, version=1, ...)
        set_tags(case, data.get("tag_ids"))
        AuditService.record(
            "create", case, request=request, user=user,
            new_data=_audit_snapshot(case, [...], data["steps"], data.get("expected_result") or ""),
        )
    return case

The audit stores a field-level diff, not a full row snapshot. On update, take an old snapshot, apply changes, take a new snapshot, and keep only the differences:

old_diff, new_diff = model_diff(old_snapshot, new_snapshot)
AuditService.record(
    "update", case, request=request, user=user,
    old_data=old_diff or None, new_data=new_diff or None,
)

old_data or None also has a purpose: no differences stores null rather than an empty dict. Otherwise "changed but nothing actually differed" and "clicked save" are indistinguishable when you query later.

An audit row records a dozen fields: organization / project / user / action / object_type / object_id / object_ref / old_data / new_data / ip_address / user_agent / request_id. There is also an adapter that papers over dirty input:

def record_audit(action, obj, request=None, **kwargs):
    """Audit adapter: fill an empty string when the request has no User-Agent
    (common/utils.user_agent returns None, but AuditLog.user_agent is non-null).
    Recommend fixing it in common/utils.py later."""

That kind of "patch at the call site and write down where to fix it properly" comment is far better than a silent or "".

The defect status timeline is derived from the audit log rather than a separate event table:

def defect_timeline(defect: Defect) -> list[dict]:
    """Status timeline: from AuditLog(object_type="defect"), ascending by time."""
    logs = (
        AuditLog.objects.filter(object_type="defect", object_id=defect.pk)
        .select_related("user")
        .order_by("created_at", "id")
    )

The second field in order_by("created_at", "id") is not decoration. Two audit rows can land in the same millisecond, and sorting by time alone is unstable. Adding the auto-increment key guarantees a strictly monotonic timeline.

Failures become defects: four tables in one transaction

Creating a defect from an execution result is the tightest link in the quality loop. It writes four tables at once: the defect itself, result↔defect, case↔defect, and the audit row. They must live and die together:

def create_defect_from_result(request, result: TestResult, data: dict) -> Defect:
    run = result.test_run
    case = result.test_case
    description = data.get("description") or _default_description(result)
    ...
    with transaction.atomic():
        defect = Defect.objects.create(
            organization=run.organization,
            project=run.project,
            key=next_key(run.project, "BUG"),
            title=(data.get("title") or f"[failed] {case.case_key} {case.title}")[:255],
            ...
        )
        TestResultDefect.objects.create(test_result=result, defect=defect)
        TestCaseDefect.objects.create(test_case=case, defect=defect)
        AuditService.record("create", defect, request=request, old_data=None, new_data={...})
    return defect

Note next_key(run.project, "BUG") is taken inside the transaction, matching the row-lock section above. Taking the key outside the transaction would leave a gap in the sequence when the transaction rolls back.

The default description is assembled from the version snapshot, not the current case:

def _default_description(result: TestResult) -> str:
    run = result.test_run
    version = result.test_case_version
    lines = [
        f"case: {result.test_case.case_key} {version.title}",
        f"run: {run.name} (env {run.environment or '-'} / build {run.build_version or '-'})",
        "",
    ]
    if version.precondition:
        lines += ["Precondition:", version.precondition, ""]
    lines.append("Steps:")
    for step in sorted(version.steps or [], key=lambda item: item.get("order", 0)):
        lines.append(f"{step.get('order', '')}. {step.get('action', '')}")
        if step.get("expected"):
            lines.append(f"   expected: {step['expected']}")

So the defect report carries the steps as they were at the time, and a developer can reproduce from the ticket without digging through version history. The sorted(..., key=order) is there because steps is a JSONB array with no database-level ordering guarantee.

The API layer also leaves a gentle warning: a non-failed result can still produce a defect, but it returns a warning:

warning = None
if result.status != "failed":
    warning = f"current result status is {result.status}, not a failure; the defect was still created and linked"

It deliberately does not block. Real teams do mark a case passed and then discover a problem manually; blocking would just push people to work around the process.

Import and export: dry_run first, then commit

Migrating off Excel is a mandatory gate for this category, and the easiest place to do it badly: a user uploads 500 rows, row 300 fails, and the first 299 are already in the database.

NanoQA runs the same validation twice, with dry_run deciding whether to write:

Import follows §61 strictly: upload -> field mapping -> data preview -> error check -> confirm.
Preview (dry_run=True) only parses and validates without writing; confirm
(dry_run=False) reuses the same validation, bulk-inserts valid rows (case + v1 version
snapshot + increasing key), skips invalid rows and reports them one by one.

"Reuses the same validation" is the point. If preview validates loosely and import validates strictly, users see "preview all green, import all red". One code path means the preview is a promise.

Export columns are data, not code, and their order is the header order:

EXPORT_COLUMNS = [
    ("case_key", "Case key"),
    ("title", "Title"),
    ("module_path", "Module path"),
    ("priority", "Priority"),
    ("case_type", "Type"),
    ("status", "Status"),
    ("precondition", "Precondition"),
    ("steps", "Steps"),
    ("expected_result", "Expected result"),
    ("tags", "Tags"),
    ("owner", "Owner"),
]

Steps export as readable text that parse_steps can read back, so the exported file is itself a valid import template. That one property makes "export → edit → import" a usable bulk-edit path.

Limits are enforced in the service layer, not just hinted in the UI: MAX_FILE_SIZE = 10 * 1024 * 1024 and ALLOWED_EXTENSIONS = {"csv", "xlsx"}. Frontend limits are UX; backend limits are boundaries.

Search: treating the q parameter as a query language

The list page exposes a q parameter that accepts key/value pairs:

q syntax: `priority:P0 status:active module:login tag:smoke automation:automated`.
Tokens are ANDed. Invalid tokens (unknown key / invalid value / empty value) degrade to
plain text.

"Invalid tokens degrade to plain text" is a pragmatic decision. A user typing login:timeout probably wants to search for content containing those two words, not to be interrupted by an error dialog. Lenient parsing beats strict rejection in a search box.

Values are validated against whitelists and only converted into filters on a hit:

PRIORITY_VALUES = {"p0": "P0", "p1": "P1", "p2": "P2", "p3": "P3"}
STATUS_VALUES = {"draft", "active", "deprecated", "archived"}
...
if key == "priority" and value.lower() in PRIORITY_VALUES:
    result.priority.append(PRIORITY_VALUES[value.lower()])
elif key == "status" and value.lower() in STATUS_VALUES:
    result.status.append(value.lower())
...
else:
    result.text.append(raw)

Text search must reach the current version's expected result, which does not live in the main table. It uses a subquery rather than a JOIN, avoiding row multiplication from one-to-many:

def _text_q(term: str) -> Q:
    matched = TestCaseVersion.objects.filter(
        test_case=OuterRef("pk"),
        version=OuterRef("current_version"),
        expected_result__icontains=term,
    ).values("test_case_id")
    q = Q(pk__in=Subquery(matched))
    for name in TEXT_FIELDS:
        q |= Q(**{f"{name}__icontains": term})
    return q

A final queryset.distinct() cleans up duplicates produced by many-to-many filters like tags__name__icontains.

The module tree has one more layer: checking "include submodules" requires recursively collecting all descendants. It uses breadth-first traversal rather than a recursive function, so deep trees cannot blow the stack:

ids = [module_id]
if include_descendants:
    frontier = [module_id]
    while frontier:
        children = list(Module.objects.filter(project=project, parent_id__in=frontier).values_list("id", flat=True))
        new_ids = [child_id for child_id in children if child_id not in ids]
        ids.extend(new_ids)
        frontier = new_ids

child_id not in ids is an O(n) membership test on a list, which should be a set. But each level holds only a handful of elements and it has never shown up in profiling. Leaving a known-but-not-worth-fixing trade-off visible beats pretending it is not there.

Routing: how project context reaches every page

The easiest thing to get wrong in a multi-project system is the URL. If routes were /testcases, "which project am I in" would live only in a global store — lost on refresh, wrong when shared.

NanoQA puts the project in the second path segment:

{
  path: '/p/:projectId',
  component: () => import('@/layouts/AppLayout.vue'),
  children: [
    { path: '', redirect: { name: 'project-overview' } },
    { path: 'overview', name: 'project-overview', ... },
    { path: 'testcases', name: 'testcases', ... },
    { path: 'testcases/:caseId', name: 'testcase-detail', ... },
    ...
  ],
}

So /p/7/testcases/42 is a complete context by itself: case 42 in project 7. Refresh-safe, shareable, correct with browser back and forward. That looks like a routing trick but actually determines how backend permission checks work — resolve_project can read view.kwargs["project_id"] directly and never trust a client-supplied project header.

The top of the router file records that the shape was fixed early:

/**
 * Route table (fixed upfront): later phases only implement views, this file's
 * structure does not change.
 */

That decision is valuable in team work. The route structure is the skeleton everyone shares; changing it mid-flight forces every in-progress branch to follow. Fixing it first lets pages be developed in parallel by name, shrinking the conflict surface from "the router file" to "each view".

The guard does exactly two things: redirect to login without a token, and fetch the user once if a token exists but the user is not loaded:

router.beforeEach(async (to) => {
  if (to.meta.public) return true
  const auth = useAuthStore()
  if (!tokenStore.access) {
    return { name: 'login', query: { redirect: to.fullPath } }
  }
  if (!auth.loaded) {
    try {
      await auth.fetchMe()
    } catch {
      tokenStore.clear()
      return { name: 'login', query: { redirect: to.fullPath } }
    }
  }
  return true
})

Note the !auth.loaded prefix check. Clicking through ten pages in one project triggers fetchMe once; returning in a new tab, where the store was rebuilt, triggers it again — the only place that confirms the token is still valid.

The redirect parameter is also handled correctly: after login you return to the page you wanted, instead of always landing on the home page. Small detail, but without it every deep link becomes "click, get bounced to login, land on home, find your way back".

The guard does not check permissions. That is deliberate, as the RBAC section said: a frontend guard stops mistakes, not API calls. So the frontend only answers "am I logged in". Whether a specific button is clickable comes from the permission set returned by /auth/me — and that is presentation only. The real decision lives in HasProjectPermission on the backend.

Page titles are set once in afterEach:

router.afterEach((to) => {
  const title = to.meta.title as string | undefined
  document.title = title ? `${title} · NanoQA` : 'NanoQA'
})

Using meta.title instead of setting document.title in each component means the title changes in the same frame as the navigation, and history entries are correct.

How the 232 tests are organized

That number has come up repeatedly. It is not one loud integration test; it is split by domain, each domain testing its own concern.

The directory structure is the test strategy:

backend/apps/testcases/tests/
  test_create.py        create: key + v1 version + audit in one transaction
  test_update.py        update: optimistic lock / version only on content change
  test_search.py        q parsing, invalid-token fallback, module recursion
  test_import_export.py preview and import share one validation path
backend/apps/executions/tests/
  test_results.py       pre-created not_run, overwrite submit, version binding
backend/apps/defects/tests/
  test_api.py           state machine, timestamps, archive permission
  test_links.py         link/unlink and audit
backend/apps/testplans/tests/test_plans.py
backend/apps/requirements/tests/test_api.py
backend/apps/attachments/tests/test_attachments.py
backend/apps/reports/tests/test_run_report.py

Two of them are worth calling out, because they test things that are easy to do correctly and very hard to notice when done wrong.

The first is updating a case. It has to verify four things at once: optimistic locking fails against a stale updated_at; no version bump when content is unchanged; a version bump when content changed; and both the full text and the diff land in the audit. If it only tested "read it back after saving", three of those four could pass while the broken one (say, unconditional version bumps) surfaces three months later as "why is this case on version 40".

The second is concurrent key allocation. It must use TransactionTestCase, because you need real commits to observe row-lock behavior. And that is precisely where the flush() truncating seed data problem lives — hence the README FAQ entry and the self-healing test base. This class of "the test framework itself polluted the test" problem is harder to debug than a business bug, because the error points at Role.DoesNotExist and has nothing to do with key allocation.

There is one more detail: serialized_rollback. It restores initial data after a TransactionTestCase flush, at the cost of speed, in exchange for "concurrent tests do not depend on execution order". Order dependence is the most expensive kind of debt in a test suite: it turns an unrelated change into a string of random failures.

Why export carries a module path

Import/export is easy to build as "if the columns line up, it works". But in real migrations the user's spreadsheet usually looks like this:

Case key | Title | Module path | Priority | Steps | Expected | Tags | Owner

Note module path, not module ID. People write "Login / Verification / SMS" in Excel, not module_id=17. So the import service must resolve the path back to a tree node, and decide whether to auto-create or report an error when the path does not exist.

That means import is not just field mapping; it is a tree resolution pass. And export must emit the same path format, or "export, tweak, import" is broken. Export's module_path column is therefore not a convenience field — it is part of the round-trip contract.

EXPORT_COLUMNS order is the header order, and column widths are declared separately:

COLUMN_WIDTHS = {
    "Case key": 18, "Title": 40, "Module path": 28, "Priority": 8, "Type": 10, "Status": 8,
    "Precondition": 30, "Steps": 60, "Expected result": 30, "Tags": 22, "Owner": 12,
}

Why does something as cosmetic as column width live on the backend? Because the XLSX is generated there. Computing widths on the frontend would duplicate the export logic into the browser, and browser XLSX libraries do not behave identically to Python's openpyxl. Whoever generates the file owns making it readable.

Step encoding deserves a mention too. It exports as readable text that parse_steps can read back. That looks like bilateral adaptation, but it is really defining a micro-format: readable and hand-editable in Excel, yet unambiguously machine-parseable. Formats like this are hard to change once set, because users already hold exported files.

Finally, the two limits:

MAX_FILE_SIZE = 10 * 1024 * 1024  # matches the frontend: 10MB
ALLOWED_EXTENSIONS = {"csv", "xlsx"}

The comment "matches the frontend" is the only synchronization mechanism. If the backend ever moves to 20MB while the frontend stays at 10MB, users see the odd situation where the frontend blocks a file the backend would happily accept. Inconsistencies like that never error; they just quietly erode trust.

The command palette: one search entry across modules

Ctrl+K opens a palette that searches four kinds of objects at once: pages, projects, cases and defects. It looks like a frontend feature, but the hard part is on the backend: the four search costs differ by two orders of magnitude.

  • Pages: a static frontend list, zero requests.
  • Projects: one light query, dozens of rows.
  • Defects: filtered by project, usually hundreds of rows.
  • Cases: potentially thousands, and must search title and key.

If all four used the same "request on every keystroke" strategy, each character would fire four requests including one heavy query. So the frontend debounces, and the backend exposes a separate lightweight endpoint per type — instead of one universal search endpoint.

That is a different trade-off from the q grammar in the search section. The list page's q is a full filtering language, good for "find every P0 case whose automation status is partial". The palette is fuzzy navigation, good for "I remember the title had 'refund' in it". The former allows complexity but must not run per keystroke; the latter is simple but must be fast.

Both entries share one query service, just with different parameters. That "one backend capability, two frontend entries" structure is far easier to maintain than writing a separate query path for the palette — because there is only one place to fix a bug.

Response envelope: what one code field carries

Every endpoint returns the same envelope rather than raw data:

/**
 * NanoQA API client
 * - Unified envelope: { code, message, data }, success only when code === 0
 * - 401/40002: single-flight token refresh, then replay the original request
 * - 40003: optimistic lock conflict, show a unified confirmation dialog
 */
export interface ApiEnvelope<T = unknown> {
  code: number
  message: string
  data: T
}

Only code === 0 counts as success. That looks redundant with HTTP status codes, but they serve different consumers: HTTP status is for middleboxes (caching, retries, monitoring), code is for the business layer (which error class, whether to show a dialog, whether to refresh a token).

The exception layer defines a full table of business codes:

# business error codes
CODE_SUCCESS = 0
CODE_PERMISSION_DENIED = 40001
CODE_UNAUTHENTICATED = 40002
CODE_CONFLICT = 40003          # optimistic lock conflict
CODE_INVALID_TRANSITION = 40004  # illegal state transition
CODE_NOT_FOUND = 40005
CODE_VALIDATION_ERROR = 40006
CODE_BUSINESS_CONFLICT = 40007  # business rule conflict (e.g. module still has cases)
CODE_SERVER_ERROR = 50000

The frontend reacts differently to each. 40002 refreshes the token and replays, and must guarantee only one refresh happens even with concurrent requests:

/** Endpoints excluded from auto-refresh (otherwise infinite loop) */
const NO_REFRESH_PATHS = ['/auth/login/', '/auth/refresh/', '/auth/logout/']

That line prevents the classic loop: the refresh request itself returns 40002, triggering another refresh, recursively forever. The blacklist is necessary, not pedantry.

40003 shows a unified confirmation dialog letting the user choose "refresh to the latest" or "discard my changes". That interaction detail matters — half the value of optimistic locking lives here. If the server detects a conflict and the frontend only says "save failed", the experience is no different from silent overwriting.

40004 and 40007 display the backend message directly, because it already states the reason precisely — "cannot move from draft to archived", or "module still has cases, cannot delete". Reassembling that in the frontend would only make it worse.

The exception layer also translates standard DRF exceptions into business codes, so the frontend only needs to know one set:

if isinstance(exc, (NotAuthenticated, AuthenticationFailed)):
    code, message = CODE_UNAUTHENTICATED, "not authenticated or session expired"
elif isinstance(exc, PermissionDenied):
    code, message = CODE_PERMISSION_DENIED, "permission denied"
elif isinstance(exc, NotFound):
    code, message = CODE_NOT_FOUND, "resource not found"
elif isinstance(exc, ValidationError):
    code, message = CODE_VALIDATION_ERROR, _format_validation_error(response.data)

_format_validation_error is worth a look too; it flattens DRF's nested validation dictionaries into one readable sentence:

def _format_validation_error(data) -> str:
    if isinstance(data, dict):
        if "detail" in data and isinstance(data["detail"], str):
            return data["detail"]
        parts = []
        for key, value in data.items():
            parts.append(f"{key}: {value[0] if isinstance(value, list) and value else value}")
        return "；".join(parts) if parts else "validation failed"

So the frontend never has to write "pull the first item out of {'title': [ErrorDetail(...)]}". Every message in the envelope is a sentence you can show a user. Unhandled exceptions carry a request_id too:

logger.exception("unhandled error, request_id=%s", request_id)
return Response(
    envelope(CODE_SERVER_ERROR, "internal server error", {"request_id": request_id}),
    status=status.HTTP_500_INTERNAL_SERVER_ERROR,
)

When a user sees "internal server error", that request_id on screen is the only lead. Putting it in the response body is far more useful than only logging it — otherwise the user sends a screenshot and you still cannot find the request.

The UI/backend contract: the version snapshot component

The backend has pinned down "historical results bind a version". The frontend must surface that explicitly, or users will not understand why a report title differs from the case they just saw.

CaseSnapshot.vue is that contract made visible. Its first line of comment is the conclusion:

<!-- Version snapshot marker: results bind the case version at execution time -->
<div class="snapshot-head">
  <span class="version-badge">version snapshot v{{ snapshot?.version ?? '—' }}</span>
  <span v-if="snapshot?.change_summary" class="change-summary">{{ snapshot.change_summary }}</span>

The component takes three props, two of which can be null:

defineProps<{
  snapshot: VersionSnapshot | null
  loading: boolean
  /** Current result (shows the last execution result and comments) */

result: RunResult | null is not arbitrary. It represents "the execution result for this run" — which may not exist yet, so it must be nullable. The three regions map to their data sources: the snapshot block (from TestCaseVersion), the steps table (snapshot.steps), and the last-result block (from TestResult). The first two never change; the third updates after every execution. Showing "the case as it was" and "this execution" on one page is the single most important UI convention in the system.

The steps table renders order / action / expected directly:

row.order uses the backend value rather than the array index. Because steps is JSONB, order is not guaranteed — the same constraint shows up in the defect description's sorted(..., key=order). The same constraint is reminded twice by the same data source.

AI: an offline mock is still acceptance-testable

The project description says "AI native", but the AI layer is currently an offline mock:

class MockLLMProvider(BaseLLMProvider):
    """Offline mock: rule-based structured JSON generation, so the whole flow is
    acceptance-testable without a network."""

That choice is correct engineering, and the reason is in the class comment: the whole flow stays acceptance-testable offline. AI features are the easiest to build as "impressive in a demo, skipped in tests". Abstracting a Provider interface and implementing the mock with rules means:

  • CI needs no API key, and all five AI-related test files still run;
  • the frontend can develop the entire "generate → review → accept" flow without a gateway;
  • swapping in a real gateway only changes what get_provider() returns.

Generation is table-driven, not random text:

scenarios = [
    ("happy path", "P1", "functional"),
    ("required parameter validation", "P1", "functional"),
    ("invalid input handling", "P2", "functional"),
    ("duplicate submission protection", "P2", "functional"),

if context.get("include_edge_cases"):
    scenarios.append(("boundary values", "P1", "functional"))
if context.get("include_security"):
    scenarios.append(("unauthorized access blocked", "P1", "security"))

Review is rule-based scoring too, and each deduction maps to a real case-quality problem:

if len(steps) < 2:
    score -= 25
    issues.append({"severity": "high", "message": "fewer than 2 steps, insufficient coverage"})
...
if not str(context.get("expected_result") or "").strip():
    score -= 15
    issues.append({"severity": "high", "message": "missing expected result, no pass criteria"})

It does not pretend to be clever; it performs deterministic checks. Trust in this kind of capability is actually higher, because every deduction can be explained.

It raises even when a key exists, instead of silently falling back to the mock. That avoids the worst case: "I configured a key but keep getting mock output".

Measured: 232 tests and the performance baseline

The backend test count is not a feeling:

232 tests covering cases / versions / plans / execution / defects / requirements /
import-export / concurrent key allocation / state machines / permissions, all passing.

Five endpoints' P95 baselines are in the README, with a script that reproduces them (auto-build a 1,000-case fixture, sample, and verdict):

case list (page size 20)   188 ms   < 500 ms   pass
case search                 98 ms   < 500 ms   pass
dashboard                  186 ms   < 1 s      pass
run report aggregation     171 ms   < 500 ms   pass
defect list (page size 20)  65 ms   < 500 ms   pass

The 171 ms behind report aggregation is a set of single-query aggregations, not a Python loop:

rows = (
    results.values("test_case__module_id", "test_case__module__name")
    .annotate(
        total=Count("id"),
        passed=Count("id", filter=Q(status="passed")),
        not_run=Count("id", filter=Q(status="not_run")),
    )
    .order_by("-total", "test_case__module_id")
)

Count(filter=Q(...)) is Django's conditional aggregation, which generates COUNT(*) FILTER (WHERE ...). Three counts finish in one scan instead of three.

The pass-rate definition is pinned in a comment, so frontend and backend do not each compute their own:

Definition: pass_rate = passed / executed (not_run is not in the denominator,
matching the dashboard).

executed = total - not_run. If the denominator were total, a fresh run with nothing executed would show 0%. With executed, a zero denominator returns 0.0, which reads far more clearly:

def _ratio(numerator: int, denominator: int) -> float:
    return round(numerator / denominator, 4) if denominator else 0.0

The O(n²) truth about duplicate detection

find_duplicates is the one place in this system where complexity gets away. It runs difflib.SequenceMatcher over "title + steps" for every pair of cases:

def find_duplicates(project) -> list[dict]:
    """Returns [{case_a, case_b, similarity}], only above threshold, descending,
    capped at 50 pairs."""
    texts = _case_texts(project)
    pairs = []
    for i in range(len(texts)):
        for j in range(i + 1, len(texts)):
            similarity = SequenceMatcher(None, texts[i][1], texts[j][1]).ratio()
            if similarity >= SIMILARITY_THRESHOLD:
                pairs.append({...})

Threshold 0.6, output capped at 50 pairs. The pair cap hides the scan cost — the cap is 50, but the number of comparisons is n(n-1)/2.

I lifted that loop (with the same text assembly) into a standalone bench and ran it at realistic sizes:

  cases  comparisons    seconds   ms/1k cmp  pairs>=0.6
    100        4,950      0.682     137.822          50
    200       19,900      3.887     195.305          50
    400       79,800     18.314     229.495          50
    800      319,600     55.534     173.760          50

quadratic growth check:
    100 ->   200 cases: 4.02x comparisons, 5.70x time
    200 ->   400 cases: 4.01x comparisons, 4.71x time
    400 ->   800 cases: 4.01x comparisons, 3.03x time

Comparisons grow at exactly 4x per doubling — the definition of quadratic. Time growth is noisier (3.03x to 5.70x), because SequenceMatcher cost depends on string length and shared-substring length, and the random fixture's similarity distribution is not uniform.

Extrapolating linearly from the 400/800 points:

   1600 cases:    1,279,200 comparisons ~=   198.5 s
   2000 cases:    1,999,000 comparisons ~=   310.3 s
   5000 cases:   12,497,500 comparisons ~=  1939.8 s

I tried 1,600 cases first and the command ran past five minutes without finishing, so I capped the sweep at 800 and extrapolated. The timeout is itself the conclusion: clicking "find duplicates" once in a 2,000-case project hangs the request for five minutes.

This is not an implementation bug; it is an algorithm choice. Making it work needs at least one of three changes: bucket by module or tag first (compare only within buckets), build an inverted index on titles to recall candidates (compare only lexically overlapping pairs), or move the whole thing to a background task with persisted results. The ai module already has an AITask model and a task queue sketch; what is missing is wiring duplicate detection into it.

Five tables carry the whole loop

The ER diagram is nice, but what actually decides whether the system works is a handful of columns. Walking them in order is the fastest way to see why this schema survives real use.

TestCase.case_key is unique across the entire installation, not per project. That means SHOP-TC-000001 and PAY-TC-000001 coexist, because the project key is part of the string. A single per-project counter can therefore be used without collisions, and a case can be referenced in a commit message, a Slack thread, or a defect title with one unambiguous token.

TestCase.current_version is the only mutable pointer in the content model. Everything else about a case is either an attribute of the case (priority, owner, tags) or immutable history in TestCaseVersion. When someone asks "what did this case look like on the day we shipped", the answer is a single indexed lookup: versions.get(test_case=case, version=N).

TestResult.test_case_version is a PROTECT foreign key, not CASCADE. That is deliberate. If someone tries to delete a version that a historical result depends on, the database refuses. Deleting history is exactly the operation you want to fail loudly rather than silently succeed.

TestResult has unique_together = [("test_run", "test_case")]. This is what makes the "pre-create not_run, then overwrite on submit" model safe. Submitting the same case twice in one run cannot create a duplicate row; the second write hits the existing one. Without that constraint, the pre-create model would produce phantom denominators after a retry.

NumberSequence(project, entity) is one row per project per entity type. Six entities mean six rows per project, all updated under a row lock. The table is tiny, and that is the point: a naming sequence should never be a hot spot for reads, only a serialized write.

Five columns, five decisions. None of them are clever in isolation. Together they mean that "what happened" is always recoverable from the database alone, without replaying application logs.

Concurrency, in checklist form

Concurrency bugs in this category are rarely exotic. They are the same six situations, and the value of the implementation is that each one has a named answer:

SituationAnswerWhere
Two people edit the same caseOptimistic lock, 409 with 40003save_with_lock
Two people create a case at onceselect_for_update on the sequence rownext_key
Same case submitted twice in one rununique_together (test_run, test_case)schema
Same case submitted twice in one requestBulk submit wraps the loop in one transactionsubmit_results_bulk
Role revoked mid-sessionNo permission cache, recomputed per requestpermissions_for_user
Business write vs audit writeSingle transaction, audit inside itevery service

Two of those deserve a note. Bulk submit wrapping the loop in one transaction is a real decision, not a formality: if item seven fails validation, items one through six must not persist. The audit-inside-the-transaction rule is the same reasoning applied to evidence rather than data.

What is notably absent from that table is a distributed lock, a Redis mutex, or a version vector. For a system at this scale, the database's own row lock and unique constraints cover every case. Reaching for infrastructure before exhausting the database is one of the most common ways an internal tool becomes an operational liability.

The deploy shape

The docker-compose.yml is short and tells you what the system actually needs at runtime:

services:
  db:       postgres:18, healthcheck pg_isready every 5s
  redis:    redis:7-alpine, healthcheck redis-cli ping
  backend:  build ./backend, waits for both healthchecks
  frontend: build ./frontend, nginx on :8080
volumes:
  pgdata:
  media:

PostgreSQL 18 rather than the more conservative 16 is a deliberate bet: JSONB for steps and index behavior matter more here than the broadest hosting compatibility. Redis is present for the production settings module but the business logic does not depend on it — a useful property, because it means losing Redis degrades performance rather than correctness.

The healthcheck pattern is worth copying. depends_on with condition: service_healthy is the difference between "the container started" and "the database can accept connections". Without it, the backend's first migration attempt races Postgres initialization and fails intermittently, usually on a cold machine, usually in CI, usually at the worst time.

Media lives on a named volume and MEDIA_ROOT points at it. Attachments and screenshots are files, not blobs, which keeps the database small enough that a full dump is a routine operation. The trade-off is that backing up the system now means "database plus volume", not just "database" — easy to forget until a restore drill.

What a QA lead asks first

A test management system is judged by the questions it can answer without someone opening Excel. Six that come up in practice, and how this schema handles them:

  • "How much of requirement X is covered?" RequirementDefect gives the defect side; coverage comes from cases linked to the requirement, plus the linked-case counts in the coverage panel. Requirements have a status machine too, so "done" means something.
  • "What is our pass rate this release?" passed / (total - not_run), aggregated per run and per module in a single query. The definition is pinned in a comment so nobody computes it differently on a slide.
  • "Which failures have no defect yet?" Failed results left-joined against TestResultDefect. This is the single most useful view in the product, because it is the gap between "we know it is broken" and "someone owns it".
  • "Why did this defect take nine days?" The audit log gives a status timeline with actor and timestamp, because transitions are auditable and resolved_at is only stamped on first resolution.
  • "Who changed this case and what exactly changed?" Field-level diffs, version history with change summaries, and a diff between snapshots. Not a reconstructed guess.
  • "Can we trust last quarter's report?" Yes, because every result binds the version object it was executed against. This is the question that most tools fail, and the one the whole design is built around.

That last question is the reason the article exists. Everything else — state machines, optimistic locking, RBAC — is table stakes for a serious internal tool. Snapshot-bound results are the part that is easy to skip and expensive to retrofit, because by the time you need it, you have already lost the history you were trying to preserve.

What I would change at ten times the size

Extrapolating the current implementation to a much larger installation, four things break first, and they are worth naming because they are the honest limits of this version.

Duplicate detection has to become a background job with blocking. The quadratic curve is not fixable by constants. Bucket by module, index titles, and persist results keyed by a content hash so a second run on unchanged cases is free. The AITask model already exists; duplicate detection is the obvious first tenant.

Permission resolution needs a cache with real invalidation. The current "no cache" choice is correct at this size, but it is O(memberships) per request. The right upgrade is not a TTL cache — that reintroduces the 60-second revocation window — but an explicit invalidation on membership and role writes. The cost is a small amount of write-path complexity in exchange for not paying on every read.

Soft delete needs a cascade policy and a purge path. Right now deleted cases are invisible to default queries, which is correct for history and annoying for joins. At scale you want a documented rule: results always resolve against all_objects, lists never do, and a scheduled purge exists for genuinely abandoned projects.

The import path needs a job queue. Ten megabytes of XLSX is fine synchronously. A hundred thousand rows is not, and the current design has no resume. The dry_run two-phase model is the right shape for an async job — the preview is already the plan.

None of those are rewrites. They are the natural next layer, and the fact that they can be described as deltas rather than redesigns is itself evidence the base model is sound.

One request, end to end

Following a single PATCH /api/v1/p/testcases/42/ from socket to audit row shows how the layers fit, and where the guarantees actually come from.

Step one, permission. ProjectApiView reads method_permissions["PATCH"], resolves the project from the URL, and computes the user's permission set. If testcase.update is missing, the request stops here with 403 and business code 40001. Nothing else runs. That ordering matters: authorization before deserialization means an unauthorized caller cannot probe the schema through validation errors.

Step two, deserialize. The serializer validates field types and choices, but deliberately does not enforce state transitions. Business rules belong in the service layer, because a serializer cannot see the current database state without duplicating queries.

Step three, load the object. The view loads the case, its current version, and the project in one or two queries with select_related. The current version is fetched by case.current_version, not by versions.first() — an important distinction once history exists.

Step four, the service. update_case opens a transaction, takes the old snapshot, applies the new values, decides whether content changed, conditionally creates a version, then calls save_with_lock with the client's updated_at. If the row was modified in between, this raises 409 and the transaction rolls back — including the version row that was just created. That rollback is the reason the version insert lives inside the same atomic block rather than before it.

Step five, tags. Tag updates happen after the locked write, and the service explicitly clears the prefetch cache before refreshing:

cache = getattr(case, "_prefetched_objects_cache", None)
if cache is not None:
    cache.pop("tags", None)
prefetch_related_objects([case], "tags")

Without that pop, the serializer would return stale tags because prefetch_related_objects skips instances that already have a cached result. This is the kind of bug that only appears when a test asserts on the response body immediately after a write.

Step six, audit. New snapshot, diff against the old one, write one audit row inside the same transaction. If the audit insert fails, the case update rolls back too. Evidence and data are never out of step.

The whole path touches three layers and one transaction boundary. There is no event bus, no eventual consistency, no compensating action. For an internal tool this is the right trade: a synchronous audit is simpler to reason about than a reliable queue, and it fails closed.

Why 27 permissions and five roles

A permission list of 27 sounds like over-engineering until you try to reduce it. Four resources times four verbs is already sixteen, and test management needs verbs the standard set does not have: testcase.execute is not update, and testcase.review is neither update nor execute.

The five roles are the interesting part, because they encode an opinion about how QA teams actually divide work:

  • admin holds everything, including role.manage and audit.read.
  • pm can create and delete plans and manage users, but cannot delete cases — the artifact of record is protected from the person with the schedule pressure.
  • qa can do everything on cases and plans, including delete, but cannot manage users or read the audit log beyond their project view.
  • dev can read cases and update defects. Notably, a developer can update a defect without being able to modify the case that produced it.
  • viewer is read-only across the board.

That distribution is not accidental. The person who owns the release calendar should not be able to quietly delete an inconvenient test case, and the person fixing a bug should not be able to edit the test that exposes it. Both restrictions are enforced by the permission set, not by convention.

Role permissions are also additive across scopes: a user who is qa on the project and viewer in the organization gets the union, which is the realistic case for someone who joined a project from a different team. The resolution function reflects that directly rather than requiring an explicit "project member overrides org role" rule, because the union is almost always what people mean.

The dashboard and its six numbers

The project overview shows six figures: cases, execution progress, pass rate, open defects, requirement coverage, and recent audit activity. Each one has a definition problem hiding behind it, and the value of the implementation is that the definitions are decided once rather than per view.

Cases counts live rows only. Soft-deleted cases disappear from the denominator, which is correct for "how much do we have" but wrong for "how much did we have last quarter" — that question has to go through history, not the dashboard.

Execution progress is (total - not_run) / total for the current run. Because results are pre-created at run start, this number is meaningful from the first second: zero percent rather than "unknown".

Pass rate is passed / executed, and the choice to exclude not_run from the denominator is the single most consequential metric decision in the product. Include it and a fresh run reads as a catastrophic failure; exclude it and a run with two results reads as a confident 100%. Neither is wrong if the label is honest, which is why the definition sits next to the number rather than in a wiki.

Open defects uses the state machine's notion of open: anything not in Closed, Rejected or Duplicate. That is deliberately not "status == Open", because a defect In Progress is still open work. Getting this wrong produces a dashboard that looks calm while the queue grows.

Requirement coverage is a ratio of requirements with at least one linked case to total requirements. A binary "covered or not" rather than a percentage of cases, because a requirement with one good case and a requirement with forty mediocre ones are both "covered" — and pretending otherwise invites gaming the metric.

Recent audit activity reads the same AuditLog table used for timelines, filtered to the project and ordered by created_at, id. No separate activity feed, no denormalised counter. One source of truth for "what happened", rendered twice.

The deeper point is that none of these figures is computed in the browser. They come from the backend already aggregated, with conditional Count(filter=Q(...)) so a single query produces several categories. That keeps the dashboard honest when the client caches, and it keeps the definitions in one place when a slide deck disagrees with the product.

Choosing JSONB for steps

The steps of a test case live in a JSONField array of {order, action, expected} rather than in a TestCaseStep table. That is a decision with real consequences on both sides, and it is worth being explicit about why it went this way.

The argument for a separate table is strong on paper. Steps would be queryable, so you could ask "which cases share this exact action", and each step would get its own identity for references. The argument against is equally strong in practice: steps have no identity that matters. Nobody links a defect to "step 3 of case 42" — they link to the case. Nobody edits a step outside the context of its case. And the case content is already versioned as a whole, so per-step rows would need their own versioning story or they would break the snapshot guarantee.

The decisive factor is the snapshot. A version must be an immutable, self-contained record of what the case looked like. If steps were rows in another table, "immutable" would have to be enforced across a join, and every historical result would depend on a second table staying intact. With JSONB, the version row is complete on its own. Copy it elsewhere and it still means the same thing.

The costs are real and known. Searching step text requires either a JSONB containment query or the subquery trick used for the current version's expected result. Ordering is not guaranteed by the database, so every consumer sorts by the order field — which shows up in three places: the steps table in the UI, the defect description builder, and the export. Each of those is a place someone can forget, and forgetting produces steps in the wrong order with no error.

It also makes structural validation a code concern rather than a schema concern. The database will happily accept [{"order": 1}] with no action. Normalisation has to happen in the serializer, and that means the guarantee is only as good as the serializer being used on every write path.

None of that is a reason to switch. It is a reason to know exactly what was traded away. The rule of thumb that follows: content that is always read as a whole, versioned as a whole, and never referenced by identity belongs in a document; content that is queried independently or referenced directly belongs in a table. Steps are the first kind. Results are the second, which is precisely why TestResult is a table and not a field on the run.

Boundaries that still exist

With all of that laid out, the boundaries are equally clear:

  • Duplicate detection has no bucketing. The quadratic curve above, plus the 50-pair cap that hides the cost, means it stalls at real scale.
  • The AI layer is mock only. The real gateway has an interface but raises immediately, so "AI-generated cases" is currently rule-based generation, not model generation.
  • Permissions are not cached. Deliberate, at the cost of two extra queries per request. With hundreds of project members this becomes the next hotspot.
  • Soft delete has no cascade policy. Deleting a case referenced by historical execution means report-side select_related cannot find it, and queries must fall back to all_objects.
  • child_id not in ids is an O(n) list lookup. Invisible at current scale, but it belongs in the "known, not yet changed" bucket.
  • Import/export is synchronous. Acceptable under the 10MB limit; beyond that it needs a background task.
  • 36 frontend views and 39 backend service files, with no single error-code dictionary visible in the repository; alignment relies on common/exceptions.py and a frontend convention.

These are not a TODO list. They are the current shape of this implementation.

Closing

If you only remember three things:

  1. Separate content from state. TestCase holds current state, TestCaseVersion holds content, current_version is the cursor. Every historical reference points at a version, never at the main table.
  2. Pin the version object, not the case ID. Execution, reports and defect descriptions all bind test_case_version. That one underscore decides whether a three-year-old report is still evidence.
  3. Audit must be part of the business transaction. Asynchronous audit is no audit; field-level diffs plus optional nulls make "it changed" and "someone clicked save" distinguishable.

Optimistic locking, state machines, key allocation under a row lock, soft delete — they are all sides of the same thing: keeping the system self-consistent across many people, many edits and many years. The real acceptance criterion for this kind of system is not the length of the feature list. It is whether, six months later, when someone asks "why was this report failing at the time", you can give an answer that will not change.
