Clustered and secondary indexes: where the second lookup actually costs

2026-11-04 · 14 min · Stack Frame

Who this is for: people who have read a query plan, seen a covering-index note and cannot say what it saved; people burned once by "I added an index and it got slower"; people deciding between an auto-increment key and a UUID.

TL;DR: an InnoDB table is itself a clustered index whose leaves hold entire rows. A secondary index's leaves hold the indexed columns plus the primary key. The extra lookup means fetching the primary key from the secondary index and then finding the row in the clustered index: one more tree search, usually a random page access. Covering indexes are fast because they delete that lookup entirely.

Reading time around 14 minutes. Level: advanced.

Two nearly identical selects

SELECT id, user_id FROM orders WHERE user_id = 42;
SELECT id, user_id, amount FROM orders WHERE user_id = 42;

Both use the same index, both hit a few dozen rows, and the only difference is one extra column. Yet the second does an implicit lookup back to the table, and under concurrency it can be an order of magnitude slower.

This is not the optimiser misbehaving. The second query needs a column that is not in the index, so the engine takes the primary key and fetches the row again. That action has a precise physical cost and a precise way to remove it.

All three share the same page structure: 16 KB pages, interior pages holding a child's smallest key and page number, leaf pages holding records and linked to each other. Only the leaf contents differ. Which also explains why table size and index size cannot simply be added into "total data": the clustered index leaves are the data, and the secondary indexes are additional copies carrying only indexed columns and keys.

What the clustered index leaf really holds

"The whole row" is too coarse. A record is several segments: a five byte record header with flags, owned count, heap number, record type and a pointer to the next record; six bytes of transaction id for MVCC visibility; seven bytes of roll pointer into the undo log; the column data with the primary key first; a NULL bitmap for nullable columns; and a length array for variable-length columns.

So the clustered leaf carries transaction and rollback information besides business data, which is why clustered pages are heavier than secondary pages: same 16 KB, fewer records.

Without an explicit primary key, InnoDB picks the clustered key in order: the declared primary key, otherwise the first unique index whose columns are all non-null, otherwise a generated six byte hidden row id. That third case matters: a table without a primary key does not lack a clustered index, it has one on a column you cannot see, which appears inside every secondary index leaf, cannot be queried, and whose generation order you cannot control.

Why a secondary leaf must carry the primary key

Because index columns can repeat. A single user id may correspond to hundreds of rows, and the tree needs the primary key appended to make each entry strictly ordered. Internally this is the count of fields that make an index record unique, which for a secondary index equals the indexed columns plus the primary key.

Two consequences follow. Selecting only the primary key from a secondary index is already a covering query, and the longer the primary key, the larger every secondary index entry becomes.

Why not store a row address, as MyISAM does

MyISAM's secondary leaves hold a file offset, making the table fetch a pointer dereference. InnoDB cannot, because rows move: page splits relocate records, rebuilds reorder pages, online DDL and tablespace reclamation change where records live, and a row that grows may overflow or force an in-page reorganise.

With physical addresses, every one of those moves would require updating every secondary index, turning a single row change into an index-wide rewrite. The primary key is a logical identifier: wherever the row moves, the key does not change. The price is that the table fetch cannot be a pointer hop and has to walk a tree again. InnoDB trades read amplification for much less write amplification, which is the right trade for OLTP.

The full journey of a table fetch

  1. Start at the secondary index root, branch on the value, descend.
  2. At the leaf, scan along the leaf chain collecting matching entries.
  3. Each entry carries the primary key.
  4. Take that key to the clustered index root.
  5. Branch again and descend to the right leaf.
  6. Locate the record there and read the missing column.
  7. Repeat steps four to six for the next key.

A hundred matching rows means steps four to six run a hundred times. Each is an independent tree search, not a continuation of the previous read.

Worse, those hundred primary keys are usually not contiguous in the clustered index. The secondary index is ordered by user id and the clustered index by primary key, and the two orders are unrelated, so the fetches jump around. Each miss in the buffer pool is a random disk read.

Where the cost shows up: three bills

Random page access. One tree lookup costs about one page access per level; with three levels and a warm cache, three memory reads, otherwise some number of disk reads. The table fetch turns one lookup into one plus N, where N is the number of matching rows. A sequential scan costs pages times per-page cost, while random fetches cost rows times per-lookup cost, so once the matching fraction is high enough, the optimiser abandons the index and scans. That is arithmetic, not a mood swing.

Buffer pool pollution. The cache is finite and hot. Fetches pull clustered pages in, pages that may be read once and never again, evicting genuinely hot ones. Once the hit rate drops, every later query slows down, way beyond the statement that caused it. Which is how a one-off export query takes production down: not CPU, but a rinse through the buffer pool.

CPU and locks. Every fetch re-walks branches, compares keys and decodes headers. Cheap once, and not negligible across hundreds of thousands of rows. And for locking reads or updates, the fetch also takes locks on clustered index records, changing lock granularity and order, and raising the chance of deadlock.

How primary key length amplifies every secondary index

Every secondary leaf entry carries the primary key. Going from an 8 byte integer to a 36 byte UUID adds 28 bytes per entry, multiplied by the number of secondary indexes, the number of rows, and the number of index pages maintained per write. The result is not "28 more bytes", it is every secondary index swelling, fewer entries per 16 KB page, possibly one more level in the tree, and one more page access per lookup.

There is a subtler problem too: a random UUID inserts at arbitrary positions, continuously triggering splits, lowering fill, and inflating the tablespace, while an auto-increment key always appends at the rightmost leaf.

If a UUID is genuinely required, two compromises exist: reorder the time bits to the front so the binary value is roughly ordered, or keep an auto-increment primary key and demote the UUID to an ordinary unique index.

Covering indexes: deleting the second lookup

SELECT id, user_id FROM orders WHERE user_id = 42;

Both columns live in the secondary leaf, so the engine returns the result from the index alone and the plan reports a covering scan. A simple test: list every column appearing in the select, where, order by and group by, and check whether they all live in one index. The primary key comes free, since InnoDB appends it.

Counting rows is also covering, because it needs no business columns; the optimiser will usually pick a small secondary index and report the same note. The one that is often misread is the middle case: adding one column that is not in the index turns a covering query into a fetching one.

An index condition is not a covering index

Plan noteMeaningStill fetches the table
Covering indexEvery needed column is in the indexNo
Index condition pushdownSome filters moved down to the engine layerYes

Pushdown reduces fetches, it does not remove them. With an index on the first column only, a filter on a second column is evaluated at the index layer, and only passing rows are fetched. If a plan shows only a pushed-down condition and no covering note, it is still fetching, just fewer times.

What a covering index costs

  • The index grows, so more pages and more buffer pool pressure.
  • Writes slow down, since each insert and update maintains one more column.
  • Schema changes get heavier, because altering a column rebuilds the whole index.
  • With too many indexes, the optimiser has more chances to choose badly.

So the order is: confirm with a plan that the fetch is the bottleneck, then consider adding columns. Do not stuff every column in to make it "look covering". Maintaining a wide index can cost more than the fetches it saves.

When to keep the fetch

Sometimes the extra lookup is correct: when the matching fraction is high, a sequential scan beats scanning an index and fetching row by row; when a query runs once, as in a report or an export, the fetch is affordable and a wide index is not; when a column is rarely queried, maintaining a permanent index for it has negative value; and when writes dominate reads, index maintenance outweighs the read benefit. The goal is not to eliminate every fetch, it is to make expensive fetches rare and to let cheap sequential scans happen.

Four kinds of evidence

The plan. Check which index was chosen, how many rows are expected, and whether the covering note appears. A covering note means no fetch; a pushed-down condition or a residual filter means a fetch.

Handler counters. Reset session status, run the query, and read the handler counters. Key reads far above the number of returned rows indicates fetching, and the session-scoped counters are ideal for before-and-after comparisons.

Buffer pool hit rate. The ratio of logical read requests to physical reads is the hit rate. When fetches lower it, physical reads rise. Take the difference between two samples rather than reading the absolute cumulative value.

Per-index usage. The performance schema reports how many times each index has been read. An index at zero for months is pure maintenance cost; hiding it first and watching is safer than dropping it immediately.

An index always makes things faster. It replaces a table scan with an index scan plus N fetches, and a large N is slower.

The primary key must be added to a composite index manually. It does not; InnoDB appends it to every secondary index.

A pushed-down index condition means the query is covered. It only means filtering moved down; the fetch remains.
