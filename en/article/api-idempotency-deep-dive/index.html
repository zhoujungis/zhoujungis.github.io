The user double-clicked and seven extra orders appeared

2026-11-01 · 20 min · Stack Frame

Who this is for: anyone who has written an order, payment or form endpoint and met a double click, a redelivered callback or a duplicated queue message.

Tested with Python and SQL, but no framework is assumed.

Reading time around 20 minutes. Level: intermediate to advanced.

A duplicate shipment

The user pressed submit, the network stalled for a second, and they pressed again. The next day the warehouse shipped two parcels.

SELECT * FROM orders WHERE user_id = 1001;
id=4242  user=1001  product=88  created_at=10:23:01.204
id=4243  user=1001  product=88  created_at=10:23:01.219   -- fifteen milliseconds later

The code had a duplicate check:

def create_order(request):
    if not Order.objects.filter(user=request.user, product_id=pid).exists():
        Order.objects.create(user=request.user, product_id=pid)

It still duplicated, because check then insert always has a window: both requests pass the check and both insert. Measured locally with eight concurrent submissions of the same order, that shape produced eight rows.

This is idempotency, the property that running an operation once and running it many times leaves the same result. It matters because duplicate requests cannot be prevented, and there are at least four sources.

SourceHowHow often
The userDouble clicks, or refreshes and resubmitsDaily
The clientAutomatic retry on timeoutCommon
Gateway or load balancerUpstream retry policiesHidden and lethal
Queues and callbacksAt-least-once delivery, which is the default everywhereGuaranteed

So the only option is to make repetition harmless.

What is naturally idempotent

OperationIdempotentWhy
Reading a resourceYesNothing changes
Full replacement of a resourceYesThe end state is the same
Deleting a resourceYesThe second attempt finds nothing, and nothing is the state
Creating an orderNoEvery call adds a row
Deducting a balanceNoEvery call removes money, the most dangerous case
Incrementing a counterNoTwo calls double the increment

Two misconceptions. A method being semantically idempotent says nothing about your handler: a replacement endpoint that increments a counter inside is still not idempotent, because idempotency is a property of the resulting state, not of the verb. And a disabled button on the front end improves the experience while doing nothing about retries, replays or scripts calling the API directly, so the boundary has to be server-side.

One more fact worth internalising: queues and payment callbacks are almost always at-least-once, whether because of rebalancing or because a gateway resends when no acknowledgement arrives. Your endpoint will be called twice. The only question is whether that is today or on the busiest day of the year.

Reproducing the failure

E1 double-click race: 8 threads submit the same order for user 1
  A no protection (check then insert)   orders   8   expected 1, seven duplicates

time   thread 1                    thread 2                   ... thread 8
-----------------------------------------------------------------------
t1     SELECT exists -> False
t2                                 SELECT exists -> False
t3     ... all threads pass the check inside the ten millisecond window
t4     INSERT order
t5                                 INSERT order
t6     ... eight rows

This is the textbook check-to-use race: the window is as wide as the work between the check and the write, and any validation, pricing or stock lookup in between guarantees a window.

A check in application code is information, not a constraint: it can tell you nothing existed a moment ago, and it cannot stop someone else inserting now. Mutual exclusion belongs to the database, the only thing that can see this instant.

Does a transaction fix it? On the default isolation level the same race survives, and a locking read on the row is not available everywhere; resting the design on isolation levels is the most common trap here.

First line: a uniqueness constraint

class Order(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE)
    product = models.ForeignKey(Product, on_delete=models.CASCADE)
    amount = models.DecimalField(max_digits=10, decimal_places=2)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["user", "product"], name="uniq_user_product"
            ),
        ]

CREATE TABLE orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL,
    amount TEXT NOT NULL,
    UNIQUE (user_id, product_id)
);

Then catch the conflict rather than checking first.

def create_order(request):
    try:
        order = Order.objects.create(user=request.user, product_id=pid, amount=amt)
        return JsonResponse({"order_id": order.id})
    except IntegrityError:
        order = Order.objects.get(user=request.user, product_id=pid)
        return JsonResponse({"order_id": order.id})

  B uniqueness constraint          orders   1   seven requests rejected by the database

That is the only defence where duplication is physically impossible regardless of how the code is written or how high concurrency goes.

Its success depends entirely on the business key: one entry per user per campaign for a flash sale, an outbound trade number for a payment record, a user and article pair for a like, a phone, code and scene for a verification message. An ordinary shop where a user may legitimately buy twice has no such key, which is exactly why the next line exists.

Its limits are honest. It only stops identical keys, so a user who edits the shipping address and resubmits creates a different key. It requires the business to be genuinely unique. And the conflict path has to return the existing record, or the user sees an error instead of their order.

Second line: an idempotency table

When no natural business key exists, invent one: the client sends a unique id for each intent, and the server executes a key it has never seen and replays the stored result for one it has. This is the pattern behind the idempotency header every payment API exposes, and the promise is that retrying the same key returns the same result rather than charging twice.

CREATE TABLE idempotency (
    idem_key      TEXT PRIMARY KEY,   -- client generated, a UUID
    request_hash  TEXT NOT NULL,      -- body fingerprint, stops key reuse with new content
    status        TEXT NOT NULL,      -- PROCESSING / SUCCESS / FAILED
    response      TEXT,               -- cached response body
    created_at    TIMESTAMP
);

def create_order(request):
    key = request.headers.get("Idempotency-Key")
    body_hash = sha256(request.body).hexdigest()[:16]

    with transaction.atomic():
        try:
            Idempotency.objects.create(
                idem_key=key, request_hash=body_hash, status="PROCESSING"
            )
        except IntegrityError:
            rec = Idempotency.objects.get(idem_key=key)
            if rec.request_hash != body_hash:
                return err(422, "this key is bound to a different body")
            if rec.status == "SUCCESS":
                return JsonResponse(json.loads(rec.response))
            return err(409, "the previous request is still processing")

    order = do_create_order(request)

    Idempotency.objects.filter(idem_key=key).update(
        status="SUCCESS", response=json.dumps({"order_id": order.id})
    )
    return JsonResponse({"order_id": order.id})

Three details, each of them a trap.

Claim by insert, never by select. Checking for the key first is the same race again; an insert colliding on the primary key is atomic in the database, so exactly one of eight concurrent requests wins.

The request fingerprint stops key reuse. The same key with a different body, which is what happens when a user edits a field and retries with the old key, must be rejected, or they receive the cached result of the previous attempt with the previous address. The measurement appears below.

What a late arrival does while the claim is processing. There are three options: wait and poll, return a conflict immediately, or return the previous result. Fast failure suits a flash sale, waiting suits an ordinary form.

  C idempotency table (claim by insert)   orders   1   all eight requests received id 1

What it adds over the constraint is response consistency: eight concurrent requests all get the same id, so a double click shows one order rather than an error on the second press.

Where the key comes fromHowFits
Issued on page loadA UUID fetched when the form opens, submitted with itForms, mobile web
Generated by the clientA random UUID in the browserModern browsers
Derived from the businessComposite of semantic fields, such as a trade numberPayment callbacks
Generated by the serverFingerprint of user, endpoint and parametersA coarse fallback

The table grows, so clean it: keeping successful records for a day covers any realistic retry window, which is what the payment APIs do. It is not a ledger.

Third line: a state machine with conditional updates

Many duplicates are not duplicate creations but the same document processed several times, such as a payment callback announcing success five times and firing notifications, accounting and stock updates each time.

# wrong: unconditional, so five callbacks mean five side effects
Payment.objects.filter(order_no=no).update(status="PAID", paid_at=now())
send_sms(...)

# right: only the pending-to-paid edge is legal
updated = Payment.objects.filter(
    order_no=no, status="PENDING"
).update(status="PAID", paid_at=now())

if updated == 0:
    current = Payment.objects.get(order_no=no).status
    if current == "PAID":
        return ok("already processed")
    return err(409, f"illegal transition: {current} to PAID")

send_sms(...)

A conditional update is an atomic read-modify-write: the database guarantees one transaction moves the row out of pending and every other affects zero rows. It is the same idea as pushing an expression into the statement instead of reading and then writing.

E2 payment callback replay: the same success callback delivered five times
  A unconditional   success logic ran 5 times (sms, accounting)   final PAID
  B conditional     success logic ran once, the rest skipped      final PAID
  C illegal jump    a paid callback on a shipped order            rejected

The third behaviour is the one neither a constraint nor an idempotency table can provide: a shipped order receiving a payment callback must be refused, and only the state machine knows that.

PENDING --paid--> PAID --shipped--> SHIPPED --received--> DONE
   |                |
   +--timeout--> CLOSED   +--refund--> REFUNDED

ALLOWED = {
    ("PENDING", "PAID"), ("PENDING", "CLOSED"),
    ("PAID", "SHIPPED"), ("PAID", "REFUNDED"),
    ("SHIPPED", "DONE"),
}

def transition(order_no, to_status):
    from_status = Payment.objects.get(order_no=order_no).status
    if (from_status, to_status) not in ALLOWED:
        raise IllegalTransition(f"{from_status} to {to_status}")
    updated = Payment.objects.filter(
        order_no=order_no, status=from_status
    ).update(status=to_status)
    return updated == 1

Optimistic locking is the generalised form: substitute a version counter for the state, compare it, increment it.

State machineVersion column
ExpressesBusiness semantics, including which jumps are illegalOnly whether anything changed
On conflictNaturally idempotent, zero rows means already doneRe-read and retry
FitsDocument lifecycles: orders, payments, ticketsConcurrent editing: documents, inventory rows

Use the state machine for documents and the version for edits, and do not mix them.

Fourth line: a one-shot token

1. open the form  -> GET /api/order/token -> issue a key with a ten minute TTL, return it
2. submit         -> POST /api/orders with a token header
3. server         -> deleting the key succeeds  = first submission, proceed
                  -> deleting the key affects 0 = duplicate submission, reject

Issuing and redeeming is atomic, and the whole idea is a variant of the distributed lock pattern with a shorter life.

def issue_token(request):
    token = uuid.uuid4().hex
    cache.add(f"order:token:{token}", 1, timeout=600)   # add is set-if-absent
    return JsonResponse({"token": token})

def create_order(request):
    token = request.headers.get("X-Token")
    if not token or not cache.delete(f"order:token:{token}"):
        return err(409, "do not submit twice")
    ...

It is the weakest layer, for three reasons: a script or an old client can call the endpoint without a token, tokens expire so a slow user is rejected on a legitimate second attempt, and a cache outage voids every ticket.

So treat it as experience rather than safety: it stops the ninety-nine percent who double click, and the database constraint stops the rest. An endpoint with a token and no constraint is unprotected.

Idempotency, deduplication and locks

ConceptSolvesLayerIf missing
IdempotencyRepeated execution is harmlessThe design of the write pathDuplicate orders, double charges
DeduplicationRepeated data does not persistThe data layer, unique keys and fingerprintsDirty rows, wrong counts
Distributed locksRepeated entry into a critical sectionRuntime coordinationConcurrent writes corrupting shared state

A lock blocks in advance and idempotency survives when blocking fails. Locks expire, get lost on failover and are broken by process pauses, so a lock can never be the only defence. Deduplication is a subset of idempotency: it ensures one row, while idempotency also requires a consistent response, consistent side effects and correct state transitions. Returning a 500 when the constraint catches a duplicate leaves the data correct and the user staring at an error. Combining them gives a complete answer: the lock shapes the experience, idempotency guarantees safety, and the payment callback chain is deliberately lock-free because duplicates there cross processes, time and systems, where no lock reaches.

ask of any write handler: what happens if this runs twice?
├─ read only, or pure overwrite      -> already idempotent
├─ an extra row or an extra charge   -> uniqueness where possible, idempotency table otherwise
├─ a state changed twice             -> conditional update inside a state machine
└─ an outbound side effect           -> the outside system must be idempotent too
the more expensive the side effect (money, then messages, then logs), the more layers

Three real combinations

Payment callbacks, the highest risk: verify the signature, then the idempotency table keyed on the trade number catches replays, then the conditional update serialises concurrency, then a uniqueness constraint on the ledger is the final backstop. Each layer does one job, and losing any of them costs sleep.

Queue consumers, the most deceptive: deduplicating on message ids does not work, because a rebalance redelivers with a new id and a producer resend also carries a new one. Use a business key constraint instead.

def on_message(msg):
    try:
        with transaction.atomic():
            PaymentFlow.objects.create(
                out_trade_no=msg["out_trade_no"], ...
            )
    except IntegrityError:
        return Ack
    return Ack

And mind the acknowledgement policy: genuine failures should be retried, while an already-processed conflict should be acknowledged immediately or the message redelivers forever.

Form submissions, the most common: a debounced and disabled button plus a key issued on page load, backed by an idempotency table for response consistency and a constraint as the backstop. The second click receives the first click's result and the interface shows nothing unusual.

ScenarioRequiredOptional
Payment callbackConstraint, state machine, idempotency tableSignature checks, amount reconciliation
Queue consumerBusiness key constraintConsumption log, dead letters
Form submissionA constraint where possibleIdempotency key, one-shot token
Balance deductionA conditional update guarded by the balanceVersion column, reconciliation

The measurements together

E1 double-click race: 8 threads on the same order
  A no protection        orders 8   seven duplicates
  B uniqueness           orders 1   seven rejected by IntegrityError
  C idempotency table    orders 1   all eight received id 1

E2 callback replay: the same success callback delivered five times
  A unconditional        success logic ran five times, final PAID
  B conditional          success logic ran once, final PAID
  C illegal jump         rejected

E3 key plus fingerprint: the same key a hundred times
  same key, same body x100 : one execution, 99 cache hits, identical responses
  same key, other body   x1 : rejected, the key is bound to another body

Three readings worth keeping. Eight concurrent requests produce eight orders, so the duplicate rate is not probabilistic, it is certain, since every request enters the window. The idempotency table gives all eight the same id, which is response consistency and something a constraint cannot do. And the fingerprint rejects a changed body under the same key, without which the key itself becomes a source of corruption.

Checklist and questions

  • Every creation endpoint has a uniqueness constraint where the business allows it, with the conflict path returning the existing record.
  • Where it does not, an idempotency table with client-generated keys.
  • That table stores a request fingerprint and returns a client error when the body differs.
  • It also has a cleanup job, deleting successes after a day.
  • Document lifecycles use conditional updates, branching on the affected row count.
  • Illegal transitions are rejected explicitly and alerted, not silently 500.
  • Queue consumers deduplicate on business keys rather than message ids.
  • Consumers distinguish retryable failure from already-processed success.
  • Payment callbacks use all four layers.
  • Front-end debouncing is accepted as experience only, with a database backstop behind it.
  • The three scenarios, double click, callback replay and edited retry, have been load tested.
  • A reconciliation job exists and actually runs.

Can the key live in a cache instead of a table? A cache is fast and losable, so anything where a lost key means a lost order belongs in the database. Use the cache for the first quick look and the table as the source of truth.

Is the record fetched after a conflict the same as the one just created? The response is the same. Telling which request created it requires storing the owner, which almost nothing needs.

How do incremental patches become idempotent? Change them to full replacements, or send a version and reject conflicts so the client re-reads.

How long should keys live? Long enough to cover the client's worst retry window; a day is the industry norm. Not forever, or storage explodes.

What if the business logic fails after the claim? Mark the record failed and either delete it or allow the same key to retry. Never leave a failed key as a permanent lock, and cover that path in tests.

How should the state machine look in code? Put the allowed transitions on the class, funnel every change through one function, and let views call it rather than writing filters of their own.

Is a balance-guarded deduction idempotent? It is correct rather than idempotent: the second attempt fails for insufficient funds, which prevents a double charge by accident, but the user may see a spurious error, so pair it with a key.

Who owns retry safety, the gateway or the service? The gateway retries anything it did not get a response for, so idempotency is the service's obligation. Always assume the gateway retries, and check the configuration, because some proxies retry POST by default.

Closing

Three sentences. The backstop is the database, since application checks are information and check-then-insert always has a window. Consistency comes from the idempotency table, which combines a claim, a fingerprint and a cached response so repeats see one result instead of an error. Lifecycles come from the state machine, which compresses read-modify-write into one statement, skipping replays and refusing illegal jumps.

Back to the double click: with a uniqueness constraint on user and product, a key on submission and a payment state machine that only accepts pending, the ticket never exists.

"The user submitted once" is the front end's worldview. "The endpoint will be called more than once" is the back end's.
