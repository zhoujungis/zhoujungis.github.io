The edges of an InnoDB lock: next-key and gap locks

2026-11-02 · 34 min · Stack Frame

Who this is for: engineers who have been asked why a single-row update blocks an insert; people who write locking reads without being able to say which slice of the index they hold; people about to switch from repeatable read to read committed and wondering what they give up.

TL;DR: an InnoDB lock attaches to an index record and to the gap before it. A record lock covers one record, a gap lock covers the open interval before it, and a next-key lock is both. An insert intention lock is a queue ticket that conflicts with only one of those. Everything here comes from lock0lock.h, lock0lock.cc, lock0wait.cc and row0sel.cc in MySQL 8.0.

Reading time around 34 minutes. Level: advanced.

What one UPDATE actually locks

CREATE TABLE t (
  id INT PRIMARY KEY,
  k INT NOT NULL,
  v VARCHAR(32),
  KEY idx_k (k)
) ENGINE=InnoDB;

INSERT INTO t (id, k, v) VALUES
  (1, 10, 'a'),
  (5, 20, 'b'),
  (10, 30, 'c'),
  (15, 40, 'd');

-- session A
BEGIN;
UPDATE t SET v = 'x' WHERE k = 20;

-- session B
INSERT INTO t (id, k, v) VALUES (7, 20, 'b2');

B blocks. The immediate reading is that A changed the row with id five and B wants to insert id seven, so they are different rows and should not collide.

But A did not lock a row. It locked a stretch of the index on k. The condition matched the secondary index entry (20, 5), which A covered with a next-key lock. The scan continued to (30, 10), found the condition no longer held, and placed a gap lock in front of it. B's (20, 7) falls inside that gap, so its insert intention lock conflicts with A's gap lock and it queues.

Three facts are easy to miss on that path. The address of a lock is an index record, not a primary key row, so one row occupies a different lock coordinate in the clustered index and in each secondary index. A scan that finds nothing still takes locks, because it stops on the first non-matching record and often locks the gap before it. And an ordinary select runs through MVCC and takes no locks at all; only locking reads enter the system described here.

Pages, records and heap numbers: the smallest coordinate

Locks live on pages, not on tables. A page holds a chain of records between two sentinels, and the source numbers those positions.

/** Page infimum */
constexpr ulint PAGE_HEAP_NO_INFIMUM = 0;
/** Page supremum */
constexpr ulint PAGE_HEAP_NO_SUPREMUM = 1;

/** First user record in creation (insertion) order, not necessarily collation
order; this record may have been deleted */
constexpr ulint PAGE_HEAP_NO_USER_LOW = 2;

That is why status output shows heap numbers like two and three: a heap number is a slot inside a page, not a primary key and not a row number, and user records start at two because the sentinels took zero and one.

A lock object is not one record either. It belongs to a page and carries a bitmap, where bit n says the lock covers the record at heap number n. Four accessors expose this: how many bits, is the nth bit set, set the nth bit, clear the nth bit.

So a next-key lock is semantically a record lock plus a gap lock, and in memory it is often one object with one bitmap. The source says so directly, and adds the reason the split only happens one way: gap locks do not conflict with each other, so narrowing a waiting next-key lock to a record lock would not remove the conflict, while the reverse check is worth doing.

There is a sentinel special case. Supremum is a virtual record pointing at infinity, and every lock on it is treated as a gap lock, so the code clears both the gap bit and the record-not-gap bit to save an object. Locking the unbounded interval after the last record therefore costs one bit at the supremum slot, and when pages split and records move, the bits move with them, which is why a lock structure is always bound to a space, page and heap number.

How a lock is encoded

constexpr uint32_t LOCK_GAP = 512;
/** this bit means that the lock is only on the index record and does NOT
   block inserts to the gap before the index record; this is used in the case
   when we retrieve a record with a unique key, and is also used in locking
   plain SELECTs (not part of UPDATE or DELETE) when the user has set the READ
   COMMITTED isolation level */

/** this bit is set when we place a waiting gap type record lock request in
   order to let an insert of an index record to wait until there are no

   remains set when the waiting lock is granted, or if the lock is inherited to
   a neighboring record */
constexpr uint32_t LOCK_INSERT_INTENTION = 2048;

LOCK_GAP512Only the open interval before the record, not the record
LOCK_REC_NOT_GAP1024Only the record, and inserts into the gap stay allowed
LOCK_INSERT_INTENTION2048A waiting gap request raised before an insert

That zero matters. A next-key lock is not a new bit; it is the default shape where gap and record were never separated. A lock covers the gap, the record, or both. The wait flag is not a shape at all but a state: the request has not been granted and sits in the queue.

Three words, three intervals

  • A record lock covers one index record. It does not cover the gap before it, so other transactions can still insert between the previous record and this one.
  • A gap lock covers the open interval between two records. It covers neither endpoint and only blocks inserts into that space. Several transactions can hold the same gap at once, because gap locks do not conflict.
  • A next-key lock covers the gap plus the record, and it is the default shape for range scans under repeatable read.

The two ends of a gap are neighbours in index order, not in primary key order. The secondary index stores composite entries, so the gap between two of them spans not only the difference in the indexed column but also the ordering of the primary key within equal values. That is why an insert of a value equal to an existing one falls into the gap after it rather than beside the row with a similar primary key.

Gap locks also do not block reads and do not block other gap locks. The conflict rule states it: a gap request without insert intention never waits, because different transactions can hold conflicting intentions over the same space. The semantics are to reserve a position against inserts, not to take exclusive ownership of an interval.

Consistent reads and locking reads

An ordinary select reads the MVCC version chain using a read view, and takes neither record nor gap locks. A locking read, whether a select for update, a select for share, an update or a delete, reads the latest version and locks what it reads.

Only a non-empty lock type gets past that gate into the range comparison, which is why a consistent read leaves no trace in the lock tables. It also explains a familiar scene: while A holds an uncommitted change, B's plain select still reads the old value and never blocks, but the moment B asks for a locking read it waits. Nothing appeared suddenly; B moved from MVCC into the lock system.

Update and delete are locking reads too, and they position and lock before deciding to modify. That order means an update that matches no row can still leave a gap lock where the row would have been.

Unique equality: why only a record lock remains

Four kinds of condition short-circuit here. The caller said not to lock gaps, as in a plain locking read at read committed. The transaction's isolation level skips gap locks entirely. The search is unique and the matched record is not delete-marked. Or the search is a greater-or-equal on the clustered index that lands exactly on the unique key, so nothing inserted into the preceding gap can fall inside the range.

  ulint lock_type;
  if (row_to_range_relation.row_can_be_in_range) {
    if (row_to_range_relation.gap_can_intersect_range) {
      lock_type = LOCK_ORDINARY;
    } else {
      lock_type = LOCK_REC_NOT_GAP;
    }
  } else {
    if (row_to_range_relation.gap_can_intersect_range) {
      lock_type = LOCK_GAP;
    } else {
      err = DB_RECORD_NOT_FOUND;
      goto normal_return;
    }
  }

Row in range and gap cannot intersect gives a record-only lock, which is the source of the familiar rule. The gap is unnecessary because a unique index cannot grow a second row with the same value: an insert of a different value cannot extend the result, and an insert of the same value fails on the uniqueness check, which locks it anyway.

Two exceptions matter. If the matched record is delete-marked, the condition fails, the gap stays in play, and the lock becomes an ordinary next-key, because delete-marked entries remain on the chain and uniqueness has to be conservative. And if nothing matches, the scan stops on the first greater record and takes a plain gap lock there, so a query for a missing value locks the position where it would appear, and inserts of anything that sorts into that gap will wait.

  /* If we are doing a 'greater or equal than a primary key
  value' search from a clustered index, and we find a record
  that has that exact primary key value, then there is no need
  to lock the gap before the record, because no insert in the
  gap can be in our search range. That is, no phantom row can
  appear that way.

  An example: if col1 is the primary key, the search is WHERE
  col1 >= 100, and we find a record where col1 = 100, then no
  need to lock the gap before that record. */

Note which gap is skipped: the one before the lower bound, not the one after the upper bound. The other end of the range is still handled.

Non-unique index: two indexes, two lock shapes

Switch the predicate to equality on a non-unique secondary index and everything gets harder, because another entry with the same value can be inserted after the matched one. The scan takes an ordinary next-key lock on the match, then continues to the first record with a different value and adds a gap lock in front of it.

Then comes the row fetch. The secondary index only yields a primary key, so the engine looks the row up in the clustered index under a unique condition, and takes a record-only lock there.

  if (prebuilt->select_lock_type != LOCK_NONE) {
    /* Try to place a lock on the index record; we are searching
    the clust rec with a unique condition, hence
    we set a LOCK_REC_NOT_GAP type lock */

    err = lock_clust_rec_read_check_and_lock(
        lock_duration_t::REGULAR, prebuilt->clust_pcur->get_block(), clust_rec,
        clust_index, *offsets, prebuilt->select_mode,
        static_cast<lock_mode>(prebuilt->select_lock_type), LOCK_REC_NOT_GAP,
        thr);

That comment is worth memorising: the secondary scan takes a next-key lock, the row fetch takes a record-only lock. Two indexes, two shapes.

  • Updating a column that appears in no index still requires scanning the secondary index to find the rows, so next-key and gap locks still land there. Do not assume a non-indexed update locks only the clustered index.
  • A covering query needs no row fetch, so no clustered locks appear and the footprint shrinks.
  • Updating an indexed column forces a delete-mark on the old entry and an insert of a new one, which widens the locked area and raises the chance of a deadlock.

Range scans: a three-state choice

A range scan is where next-key and gap locks earn their keep. The engine does not guess from the shape of the SQL. It asks, for each record on the scan, two questions: can this row be inside the range, and can the gap before it intersect the range. Both answers default to true when the question is hard, and the pair picks the lock.

Row in rangeGap intersectsLockMeaning
truetrueLOCK_ORDINARYRecord and gap both matter
truefalseLOCK_REC_NOT_GAPOnly the record matters
falsetrueLOCK_GAPOnly the gap matters
falsefalsenone, scan endsNeither matters

With keys one, five, ten and fifteen, the same statement produces different shapes at its edges. An inclusive range from five to ten locks the lower bound with a record-only lock because no insert before it can enter the range, the interior with a next-key lock, and the first record outside with a gap lock. An open-ended range from above ten locks the remaining records with next-key locks and finishes with a gap lock on the supremum. A range below five locks its interior and ends with a gap lock before five.

Those answers are conservative estimates, not geometry. The comment admits the heuristic covers the common, easily reasoned case of a forward scan on the clustered index, and falls back to "true" for descending scans, duplicate keys in a secondary index and other paths, which is why locking sometimes feels broader than the predicate. It did not miscount; it chose the safe answer.

Locking rows that do not exist

Under repeatable read, a locking read on a missing key finds nothing, lands on the next record, and answers the two questions as out of range but gap intersecting, so the lock is a gap lock placed before that next record. Nothing is locked on the missing value because it does not exist, and nothing is locked on the record itself. Every insert of a value that sorts into that interval queues.

That is the anti-phantom mechanism. Without it, a transaction could read an empty result, another could insert and commit, and the same transaction's next identical read would see a row, breaking repeatable read. The gap lock does not cover rows; it covers the positions where rows could appear.

At read committed the lock is absent, because the isolation level skips gap locks and the branch never runs. The empty result stays empty only for that statement, and a later read may see the new row. That is not a bug; it is what read committed means, where each statement sees the latest committed snapshot and phantoms are permitted.

So "an insert was blocked by a row that does not exist" has a three-part answer: the isolation level is repeatable read or serializable; some transaction performed a locking read on that position; and that transaction left a gap lock on the successor record. Check in that order, and look for gap and next-key modes in the lock tables before anything else.

Insert intention: conflicts with gaps only

    if (!lock_rec_has_any(lock_sys->rec_hash, block->get_page_id(), heap_no)) {
      *inherit = false;
    } else {
      *inherit = true;

      /* If another transaction has an explicit lock request which locks
      the gap, waiting or granted, on the successor, the insert has to wait.

      An exception is the case where the lock by the another transaction
      is a gap type lock which it placed to wait for its turn to insert. We
      do not consider that kind of a lock conflicting with our insert. This
      eliminates an unnecessary deadlock which resulted when 2 transactions
      had to wait for their insert. Both had waiting gap type lock requests
      on the successor, which produced an unnecessary deadlock. */

      const ulint type_mode = LOCK_X | LOCK_GAP | LOCK_INSERT_INTENTION;

      const auto conflicting =
          lock_rec_other_has_conflicting(type_mode, block, heap_no, trx);

      /* LOCK_INSERT_INTENTION locks can not be allowed to bypass waiting locks,
      because they allow insertion of a record which splits the gap which would
      lead to duplication of the waiting lock, violating the constraint that
      each transaction can wait for at most one lock at any given time */

      if (conflicting.wait_for != nullptr) {
        RecLock rec_lock(thr, index, block, heap_no, type_mode);

        trx_mutex_enter(trx);

        err = rec_lock.add_to_waitq(conflicting.wait_for);

        trx_mutex_exit(trx);
      }
    }

Four things to take from it. The intention lock is placed on the successor record, so the heap number in the wait is the record the new one will land before, which is why a waiting insert often shows the successor's value rather than the value being inserted. It conflicts only with gap locks and next-key locks, never with record-only locks and never with another intention lock. It may not bypass a waiting lock, because letting it split the gap would duplicate a waiting request and violate the rule that a transaction waits for at most one lock. And an insert can inherit gap locks from its successor, so the coverage can grow rather than shrink when a record arrives.

The classic insert deadlock is built here: two transactions each hold their own intention lock over the same gap, which is compatible, and then each needs the other's gap for a second insert, which is not.

In order: a gap request without insert intention waits for nothing, including at the supremum, because gap locks coexist. A record request never waits for a pure gap lock. A gap request never waits for a record-only lock, which promised it would not block inserts. And nothing waits for an insert intention lock, because it is a pending request rather than a granted exclusive claim, and waiting on it creates spurious deadlocks.

One special channel exists for high-priority transactions, which ignores a waiting non-high-priority lock. It exists for group replication and is not a tuning knob.

Implicit locks: nothing granted, yet others still wait

An insert does not create an explicit lock for its own row, so why does another transaction wait when it touches that row? Because of the implicit lock carried in the row header. Each row stores the id of the transaction that last modified it and a pointer into undo. A transaction that modified rows without committing may leave no lock object at all, only that id.

  if (index->is_clustered()) {

The clustered index reads the transaction id straight from the record; a secondary index checks a page-level maximum first and then walks entries. If the owning transaction is still active, the code materialises a record-only exclusive lock on its behalf, and the current transaction then proceeds through the normal conflict check. The update path does the same before requesting its own lock.

The design is pay-as-you-go. A freshly inserted row that nobody touches costs no lock object, and only contention turns an implicit lock into an explicit one. It also explains why a lock seems to appear from nowhere in the lock tables: it was just materialised.

An implicit lock equals a record-only lock and never covers a gap, so inserts do not stop neighbours by themselves. Explicit gap and next-key locks do that. Keeping the two apart is what makes the combination sensible: the intention lock reserves the space before the insert, and the implicit lock marks the row afterwards.

The lock queue is not first come, first served

  -# Granted locks are added at the HEAD of the queue.
  -# Waiting locks are added at the TAIL of the queue.

Granted locks enter at the head, waiting locks at the tail. A new request scans the whole queue, granted and waiting alike, finds a conflicting holder, and attaches at the tail. Comparing against waiting requests as well is what prevents starvation, since a steady stream of shared locks could otherwise starve a waiting exclusive request forever.

Grant order is not the physical order. Waiters are sorted by scheduling weight, heaviest first, ties broken by position, and each candidate is rechecked against the granted set before being passed over or granted.

The weight comes from contention-aware transaction scheduling, which estimates how many transactions a waiter is transitively blocking. The one blocking the most goes first, because releasing it unblocks the most work. So three conclusions follow: the queue is not FIFO, a large transaction holding many others up can overtake earlier waiters, and the physical order in the wait queue is arrival order rather than grant order.

And every transaction waits for at most one lock. That constraint appears repeatedly in the headers, and it is what makes each node in the wait-for graph have at most one outgoing edge, which is what makes deadlock detection cheap.

Why read committed has no gap locks

    /* It is a plain locking SELECT and the isolation

Read the condition literally: it applies to a plain locking select with a lock type set. A consistent read never gets here, and data dictionary tables are serialised by metadata locks instead.

Giving up gaps buys fewer waits and fewer deadlocks, and costs range scans their anti-phantom property. A locking range read at read committed does not stop inserts into its range, and the next read may see them. That is the definition of the level, not a defect.

  bool allow_semi_consistent() const { return (skip_gap_locks()); }
  /** Checks if this transaction releases locks on non matching records due to
  low isolation level.
  @return true iff in this transaction's isolation level locks on records which
               do not match the WHERE clause are released */
  bool releases_non_matching_rows() const { return skip_gap_locks(); }

Read committed also allows semi-consistent reads: a scan may release locks on rows that failed the predicate, which shrinks the covered set, at the cost of reading a newer committed version than the transaction's snapshot, with a re-read if a row changed mid-statement.

Record locks remain. Rows that an update touches, records that a uniqueness check inspects and rows that a foreign key check looks at all take locks. No gap locks does not mean no locks, a distinction that gets muddled in incident reviews.

Deadlock: find the cycle, verify it, pick a victim

      if (colors[id] == 0) {
        /* This node was never visited yet */
        colors[id] = current_color;
        continue;
      }
      /* This node was already visited:
      - either it has current_color which means we've visited it during current
        DFS descend, which means we have found a cycle, which we need to verify,
      - or, it has a color used in a previous DFS which means that current DFS
        path merges into an already processed portion of wait-for graph, so we
        can stop now */
      if (colors[id] == current_color) {
        /* found a candidate cycle! */
        lock_wait_extract_cycle_ids(cycle_ids, id, outgoing);
        if (lock_wait_check_candidate_cycle(cycle_ids, infos, new_weights)) {
          MONITOR_INC(MONITOR_DEADLOCK);
        } else {
          MONITOR_INC(MONITOR_DEADLOCK_FALSE_POSITIVES);
        }
      }
      break;

Because each node has at most one outgoing edge, a colouring depth-first walk finds cycles cheaply. But a candidate cycle is only a candidate, since the wait information is a snapshot and a waiter may have been granted, timed out, or had its slot reused. Verification checks that the slot is still the one the snapshot reserved, which guards against reuse, and that the transaction still has a wait lock.

    if (trx->lock.wait_lock == nullptr) {
      /* trx is on its way to being woken up, so this cycle is a false positive.
      As this particular cycle will resolve itself, we ignore it. */
      return false;
    }

    if (trx_weight_ge(chosen_victim, trx)) {
      /* The joining transaction is 'smaller',
      choose it as the victim and roll it back. */
      chosen_victim = trx;
    }

Weight approximates how much work a transaction has done, so the cheapest one is rolled back, and on a tie the traversal order makes the most recent joiner the loser. Two engineering choices, both leaning toward sacrificing the newcomer.

Beyond deadlock there is timeout, with a default of fifty seconds, and by default a timeout rolls back only the current statement rather than the transaction.

                         nullptr, nullptr, false);

The two failure modes need separate handling in the application. A deadlock rolls back the whole transaction, so the retry must start over. A timeout leaves the transaction alive with earlier statements still applied, so retrying only the failed statement continues inside a partially completed transaction, which is rarely what you want.

Deadlock detection is on by default. Turning it off leaves timeouts as the only escape, which turns lock resolution into fifty-second waits.

The root cause is almost never a wrong victim but inconsistent locking order, and two fixes cover most cases: make every transaction touch rows in the same order, and keep transactions short, preferring a unique equality over a wide locking range.

The data column names the index record the lock sits on, and a supremum entry means the unbounded interval after the last record. Read three things in order: which index, which shape, which successor record. With that, the opening question answers itself: there is a gap lock on the secondary index entry for value thirty, and the incoming row falls inside it.

Misconceptions and a checklist

  • A lock is not on a row. It is on an index record, and the same row has a distinct coordinate in every index, so updating a non-indexed column can still lock a secondary index.
  • Unique equality does not always end with one record lock. It does when the row is found and not delete-marked; a miss locks the gap before the successor, and a delete-marked match can become a next-key lock.
  • Gap locks do not conflict with each other, and neither do insert intention locks. What conflicts is an insert intention against a held gap.
  • A next-key lock is often one object with a bitmap, and when waiting it may narrow to just the gap if the record lock is already held.
  • Read committed has no gap locks, but it still has record locks from updates, uniqueness checks and foreign keys.
  • A lock timeout rolls back the statement by default, not the transaction, so the earlier statements still stand.
  • Deadlock victims are chosen by weight, smallest first, with ties going to the most recent joiner.
  • Reading an old value in a consistent read is MVCC, not an absence of locks.

Then the investigation order, without skipping. Confirm the isolation level, since it decides whether gap locks exist at all. Confirm the statement is a locking read. Read the current locks, looking for gap and next-key shapes before record-only ones. Read the waits table to reconstruct who waits for whom. Check the engine status output, where the latest deadlock section is the cheapest evidence available. Check the execution plan, because a wrong index widens the locked interval. Unify the locking order across statements. And narrow the locking read: unique equality over ranges, covering indexes over row fetches, and read committed where phantoms are tolerable.

In short, ask which index first, then which interval, then which isolation level. Reverse that order and you stay inside the intuition that only one row was touched.

Closing: where the edge is

Three sentences cover the system. The address of a lock is an index, not a row, so one statement can hold a record, a gap, or both, and a row fetch is a second lock. The shape follows from the isolation level and the access path, with repeatable read using next-key and gap locks for anti-phantom work and read committed trading that for concurrency, and every rule falling out of the same two questions about whether a row is in range and whether its gap intersects. And contention is settled by a queue and a wait-for graph, with weights deciding grant order and a verified cycle deciding the victim.

A next-key lock is not a bigger lock. It is a record and the gap before it written on the same line. A gap lock does not lock an absent row; it locks where a future row would go. With those two pictures, the lock tables stop being strings and become a map of an index: here is a point, here is a gap, here is who stands in it, and here is who is waiting for whom to move.
