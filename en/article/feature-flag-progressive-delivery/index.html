At twenty percent, half the users lost the feature

2026-09-16 · 22 min · Stack Frame

Who this is for: anyone who has shipped a backend change and met either an incident on deploy or a rollback that takes ten minutes.

Measured with plain Python. The bucketing is framework independent.

Reading time around 22 minutes. Level: intermediate to advanced.

A complaint about a feature reappearing and disappearing

A new checkout page ships behind a rollout: ten percent of users first, watched for two days, then twenty.

The next day the complaints arrive. "Yesterday I had the new page, today it is gone again."

Nothing was deployed and the configuration changed by one number, and the answer is in a line that looks fine:

def is_enabled(user_id, percent):
    return (hash(user_id) % 100) < percent

The bug is not in this line but in a variant of it that changes the modulus with the percentage. With 20,000 users simulated:

expanding 10 to 20 percent, do existing users stay in?
  fixed bucket space (correct): 100.0 percent retained
  dynamic modulus (wrong)     :  48.2 percent retained

Half the audience was reshuffled out of a feature they already had.

What progressive delivery solves

It is not a way to hide bugs. It is a way to turn the risk of releasing from all-or-nothing into a controllable variable.

write, merge, deploy -> 100 percent immediately
                          ^ if it breaks here, everyone is affected
                          and rollback means a redeploy

write, merge, deploy with the flag off -> 1%, 5%, 20%, 50%, 100%
                          ^ any stage looks wrong: change config, seconds, bounded blast radius

Deployment and release become separate decisions. Code reaches the servers several times a day; the decision about who sees it is independent and reversible.

Three benefits follow. The blast radius is bounded, since an incident at one percent leaves ninety-nine untouched. Rollback becomes a configuration change rather than a deploy, and how quickly you can roll back determines how much control you have during an incident. And a feature can be switched off as an emergency stop, not only switched on.

The cost is code complexity and technical debt, both covered below.

Five kinds of flag, and how long each should live

Treating every flag as the same kind is the root of the debt. The type decides the lifetime.

TypePurposeLifetimePrefix
ReleaseHide unfinished workShort, one to four weeksrelease-
ExperimentA/B tests and comparisonsTwo to six weeksexp-
OpsRuntime parameters, degradationLong, months or foreverops-
PermissionFeatures by plan or rolePermanentperm-
Kill switchEmergency stop for a dependencyPermanentkill-

Release and experiment flags should be deleted, because after full rollout the branch is dead code; a common rule is cleanup within thirty days. Ops, permission and kill switches persist, since you will always want a way to turn off email pushes.

The most common mistake is using a release flag as a permission flag: fully rolled out, kept "just in case", and two years later nobody dares delete it because nobody knows what happens.

bad:  new_feature, test123, flag_a
good: release-checkout-v2, exp-onboarding-flow-2026q3, kill-stripe-webhook

The prefix is not neatness, it is what makes governance possible: one regular expression finds every release flag and every flag past its expiry.

Bucketing: why the bucket space must be fixed

A rollout maps a user to a bucket between zero and some ceiling, then compares the bucket against a threshold line.

user u_1001 -> hash -> bucket 5633 -> below 2000? (20 percent) -> no
user u_1002 -> hash -> bucket 0871 -> below 2000?              -> yes

The constraint is stickiness: one user must always land in the same bucket.

def is_enabled_wrong(user_id, percent):
    buckets = int(percent)                      # the bucket count changes
    return (hash(user_id) % buckets) < buckets * percent / 100

At ten percent the modulus is ten and a user lands in bucket three. At twenty it is twenty and the same user may land in seventeen. The whole space is reordered, which is why only about half keep their previous state.

BUCKET_SPACE = 10_000    # fixed, independent of the percentage

def bucket_of(user_id: str, salt: str) -> int:
    raw = f"{salt}:{user_id}".encode()
    h = int(hashlib.blake2b(raw, digest_size=8).hexdigest(), 16)
    return h % BUCKET_SPACE

def in_rollout(user_id: str, percent: float, salt: str) -> bool:
    return bucket_of(user_id, salt) < BUCKET_SPACE * percent / 100

percent 10  -> threshold at 1000   [0....1000|....................9999]
percent 20  -> threshold at 2000   [0........2000|................9999]
                                            ^ only the line moves; nobody inside leaves

Measured, ten to twenty percent retains every existing user. There is a second benefit: the line only moves rightward, so being in a rollout is monotonic unless you deliberately shrink it for a rollback.

TargetMeasured over 200,000 usersDeviation
1 percent0.991-0.009
5 percent4.939-0.061
10 percent9.941-0.059
25 percent25.008+0.008
50 percent50.103+0.103
90 percent89.967-0.033

Worst deviation stays inside a tenth of a percentage point, and ten thousand buckets are enough for most products.

Six implementation details

Hash once per request. Measured over 200,000 calls, the chosen hash costs about one microsecond, md5 and sha256 about two, and a cache read about seventy nanoseconds, which is fifteen to thirty times cheaper. If one request evaluates ten flags, it should hash once and reuse the result for that request.

class RequestContext:
    def __init__(self, user_id):
        self.user_id = user_id
        self._buckets = {}

    def bucket(self, salt):
        if salt not in self._buckets:
            self._buckets[salt] = bucket_of(self.user_id, salt)
        return self._buckets[salt]

Every flag needs its own salt. The same user with the same hash and the same salt lands in the same bucket, so two experiments sharing a salt hit the same population.

shared salt    : 100.0 percent overlap
independent salt:  20.4 percent overlap

Shared salts contaminate experiments: a pricing layout test and a navigation test would measure the same users, and if that group happens to spend differently, both conclusions are wrong. With one salt per flag the overlap matches what two independent twenty percent samples should give.

Every instance must agree. If bucketing depends on shared state, such as a counter of "the Nth user to enter", instances disagree. Bucketing must be a pure function of the identifier and the salt. Five simulated instances bucketing the same five thousand users produced zero disagreements, which is why a cache counter or a database sequence must never be involved.

The identifier must be stable. A user id is best, a device id works for anonymous traffic, a session id is wrong because it changes on every login, and a random value is worse because the user sees the feature flicker between requests. An IP address is the most commonly misused: behind network address translation an entire office shares one bucket, so everyone enters or nobody does.

def resolve_bucket_key(request):
    if request.user.is_authenticated:
        return f"u_{request.user.id}"
    if device_id := request.COOKIES.get("device_id"):
        return f"d_{device_id}"
    return None

With no stable identifier, do not randomise, which would change the answer between requests. Either treat anonymous traffic as one global decision, or issue a device cookie first and then decide.

Overrides come first. During an investigation you need to force one user in or out without touching anyone else.

def in_rollout(user_id, flag):
    if user_id in flag.force_on:
        return True
    if user_id in flag.force_off:
        return False
    if not flag.enabled:
        return False
    return bucket_of(user_id, flag.name) < BUCKET_SPACE * flag.percent / 100

Priority is force lists, then the master switch, then bucketing. The master switch sits before bucketing so turning a flag off does not require iterating users.

Pace, and the triggers for rolling back

StageShareObservationWatch
InternalTeamHours to a dayDoes it work at all
1 percentMinimal trafficAt least a dayError rate
5 percentSmallOne to two daysLatency and log anomalies
20 percentPartialTwo to three daysBusiness metrics, support tickets
50 percentHalfTwo to three daysLast check before full
100 percentFullThen watch a weekBefore deleting the flag

Each stage has to last long enough for time-dependent problems to appear: a cache expiring, a scheduled job firing, a race appearing only at peak. Ten minutes at one percent is not a rollout.

flag: release-checkout-v2
rollback_triggers:
  - error_rate_5xx > 1%         for 5 minutes
  - p99_latency > 500ms         for 5 minutes
  - order conversion drop > 10% against control
  - any P0 or P1 error
rollback_action: set percent to 0

Write the triggers before shipping, because people hesitate during an incident. With the table, the on-call engineer acts without a meeting.

ActionEffectFits
Percent to zeroNo new entrants, current ones stayMild problems
Disable the flagEveryone returns to old behaviour immediatelySerious problems
Redeploy the old versionBack to the previous codeA bug in the code itself

The first two take effect in seconds. And the difference between them matters: setting the percentage to zero leaves already-bucketed users on the new path, so it is not a clean rollback, which is easy to assume at three in the morning.

The debt

A flag is a liability rather than an asset, because every one adds a branch: tests must cover both paths, a bug may live in only one, and readers must hold two mental models.

SymptomConsequence
More than fifty flagsCognitive load, slow onboarding
Release flags older than ninety daysProbably fully rolled out, and nobody dares delete it
Nested flagsCombinatorial explosion, untestable
Orphan flagsNobody knows whether it can go

Four countermeasures. Every flag needs an owner and an expiry, because an unowned flag is a time bomb. Cleanup belongs in continuous integration, since automation is the only governance that has been shown to work and memory always fails. Permission requirements should use a permission system rather than a flag, because flags are for temporary human decisions and permissions are for long-lived rules. And flags are not configuration: hosts and timeouts belong in the environment, or the flag system ends up owning something it should not.

Three layers of caching

evaluation cost, 200,000 calls
  hash only            :      1.074 us
  cache read and compare:     0.073 us
  remote call at 1ms   :   1000    us
  remote call at 5ms   :   5000    us
  remote call at 20ms  :  20000    us

A network call per evaluation is tens of thousands of times slower than a local read, and worse, the flag service becomes a dependency whose failure takes your service down.

layer 1: in-process memory      hit rate above 99 percent, nanoseconds
   ^ periodic refresh, every few seconds
layer 2: local shared cache     milliseconds, the fallback
   ^ pushed on change
layer 3: the flag service       the single source of truth

The strategy is to fetch the whole configuration periodically rather than query per key.

class FlagCache:
    def __init__(self, client, refresh_interval=5):
        self.client = client
        self.interval = refresh_interval
        self._config = {}
        self._lock = threading.Lock()
        self._start_refresh_thread()

    def _refresh_loop(self):
        while True:
            try:
                snapshot = self.client.fetch_all()
                with self._lock:
                    self._config = snapshot
            except Exception:
                pass        # keep the old snapshot, never break the request path
            time.sleep(self.interval)

    def is_enabled(self, name, user_id, default=False):
        with self._lock:
            flag = self._config.get(name)
        if flag is None:
            return default
        ...

The refresh interval sets the worst-case time for a kill switch to take effect: one second for critical paths, five as the usual balance, thirty for non-critical features, minutes for plan permissions. Note the word worst: pressing the switch just after a refresh waits almost a full interval, which is why emergency switches deserve their own faster channel rather than sharing a five minute cycle.

And on failure, keep the last known configuration. Clearing it on an error would make every flag fall back to its default at once, either switching every new feature off or, worse, running unvalidated code.

Defaults follow the same logic: release and experiment flags default to off, which is safe, while kill switches default to on, since they exist to be turned off when something breaks.

Checklist and questions

  • Bucketing uses a fixed bucket space with the percentage as a threshold.
  • Each flag has its own salt.
  • Bucketing is a pure function, identical on every instance.
  • The identifier is stable, and never a session id, an IP address or a random value.
  • Anonymous traffic has a defined policy that does not change between requests.
  • Every flag has an owner, an expiry and a description.
  • Release flags are removed within thirty days of full rollout, with a check in continuous integration.
  • Evaluation reads an in-process cache refreshed on a timer, never a network call on the hot path.
  • A failed refresh keeps the previous configuration.
  • Rollback triggers are written down before the rollout starts.
  • Kill switches use a faster channel than ordinary flags.
  • Each stage of the rollout lasts at least one business cycle.

How does this differ from blue-green or canary? All three reduce release risk at different granularity: blue-green swaps two complete environments, canary sends a little real traffic to new instances, and a flag decides per user in code, which is the finest and the fastest to reverse. They compose: canary checks instance health while flags decide who sees the feature.

Per user or per request? Per user, because one user makes many requests and a random per-request split makes the feature flicker within a session. Stateless endpoints behind a cache are the exception.

Do flags break caching? Yes, if a flag changes the response and the cache key does not include the flag state, so a rolled-out user receives an old cached body. Put the flag state in the key, or disable caching for that endpoint during the rollout.

Do front-end flags count? Only for presentation. Anything sensitive, permissions or billing, must be decided on the server, because a client-side flag is something the user can change.

How do you test both paths? Parameterise the flag state and run the test twice, and pay special attention to the off path, which is the one developers never exercise because it is turned on locally.

Where does the configuration live? A database with polling at small scale, a self-hosted service at medium scale, a managed service at enterprise scale. Not a file in the repository, since that reintroduces the deploy that flags exist to remove.

What if the rollout writes to a new table and you need to roll back? This is the hard case. Make the new path forward compatible, writing old fields or dual writing, and if that is impossible, confirm the old code can read the data before rolling back, or the rollback becomes corruption. Irreversible data changes need their own rollback plan, decided before the rollout.

Summary

Four points. Fixed bucket space, with percentages as a moving line, or users lose features they already had. The flag type decides its lifetime, and an unowned flag with no expiry is a time bomb. Evaluation belongs in process memory, because a remote call is thousands of times slower and makes the flag service a dependency. And rollback triggers are written in advance, because the real value of a flag is turning rollback from a deploy into a configuration change.

Progressive delivery is not an advanced technique. It is the infrastructure that turns shipping from a gamble into a process, at the cost of one branch per flag, and for one benefit that matters: being willing to deploy on a Friday afternoon.
