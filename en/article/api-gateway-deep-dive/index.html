API gateways: one door for auth, rate limiting and routing

2026-10-30 · 20 min · Stack Frame

Who this is for: anyone moving from a monolith to several services, or giving several backends one entrance.

Language agnostic, with a comparison of four common products.

Reading time around 20 minutes. Level: intermediate.

When every service implemented its own auth

A project three years ago had four backends, for users, orders, products and payments, and each one had implemented its own JWT check, its own rate limiter and its own request logging. The consequences were predictable. A key rotation meant four edits and four deploys. The order service had its threshold changed and the payment service forgotten, so payments fell over first during a sale. Routing rules lived in four repositories, so answering "which service handled this request" meant reading all four. And a new colleague wrote a fifth service without a limiter and it was scraped flat on its first day.

The common cause is that cross-cutting concerns were spread across every service. A gateway collects them into one entrance, so business services only do business.

before:
client -> users service    (own auth, own limiter, own logs)
client -> orders service   (own auth, own limiter, own logs)
client -> products service (own auth, own limiter, own logs)

after:
client -> gateway (auth, limiting, routing, logs, breakers) -> services (business only)

Why a gateway exists

ConcernImplemented N timesAt the gateway
AuthenticationN copies of token checkingOne
Rate limitingN thresholds that drift apartOne, managed centrally
TLSN certificates and configsOne termination point
Request logsN formats, hard to aggregateOne format into the log store
CORSConfigured per serviceAnswered once
BreakersN copies of resilience codeApplied uniformly

This is not about avoiding duplication for its own sake. The real cost is security holes and operational incidents: one service missing a limiter, one leaving debug logging on, one getting token validation subtly wrong, and any of them is a way into the whole system.

A gateway is a reverse proxy plus a pipeline of cross-cutting steps, where each step can reject or rewrite the request.

request -> gateway -+-- auth ----+-- limiting --+-- routing --+-- translation --> backend
                    |            |              |             |
                    v            v              v             v
                 401/403       429          target         protocol

When you do not need one

Honestly, not every system does. A single service gains nothing but a hop. Two services with no shared concerns are served by a plain reverse proxy. Internal service-to-service traffic belongs to a mesh rather than a gateway.

The value scales with the number of services times the number of shared concerns. Past three user-facing services, the returns start to be obvious.

Four of these are where projects get into trouble: authentication, limiting, routing and protocol translation.

Authentication

Do it at the gateway for two reasons. The gateway is the only entrance, so nothing slips past it. And the backends should trust nothing, including the gateway, in the sense that they verify an internal credential rather than re-authenticating: the gateway validates the caller and passes identity in a signed header or an internal token.

SchemeFitsStrengthWeakness
JWTWeb and mobile clientsStateless and scalableRevocation is hard without a blocklist or short TTLs
OAuth2 with PKCEThird-party access, open platformsStandard, fine-grained scopesComplex flow
API keysService-to-service, public APIsSimple, easy to rotateKey management overhead
Mutual TLSInternal service trafficThe strongest, both sides verifiedCertificate operations are heavy

The common pattern is to verify the token, extract the subject and inject it as a header that backends trust.

plugins:
  - name: jwt
    config:
      secret_is_base64: false
      claims_to_verify:
        - exp
      key_claim_name: iss
      strip_claim: false

Points worth remembering. The gateway verifies signature and expiry and leaves business authorisation to the backend. It does not forward the raw token, because a backend that receives it may skip validation and use it directly, which is the same as no authentication. Token lifetimes are short, with refresh handled at the gateway if possible. And revocation is a lookup, not local state.

MistakeConsequence
Gateway validates, and the backend validates againWasted work, and keys that drift become a hole
Backend trusts a client-supplied user idOne user can act as another
Day-long token lifetimesA leak is exploitable for a day
Forwarding the raw tokenBackends may bypass verification entirely

Rate limiting

GranularityTypical configurationProtects
GlobalA ceiling for the whole gatewayAgainst floods and denial of service
Per user or tenantA share per identityAgainst one caller saturating
Per endpointA tighter share for expensive routesA fragile endpoint in particular

The three stack: a user's payment request is checked against the global ceiling, their personal share and the endpoint's share, and the strictest wins.

A token bucket adds tokens at a fixed rate and spends one per request, so a full bucket allows a burst. A leaky bucket drains at a fixed rate and rejects when full, so the downstream sees a constant rate. Default to the token bucket, and use the leaky one when the downstream is an external API with a fixed capacity.

DimensionToken bucketLeaky bucket
BurstsAllowed, spending the accumulated balanceRejected, overflowing the bucket
Output rateVariableConstant
FitsNormal traffic that burstsA downstream with fixed capacity

Where to limit: the gateway rejects earliest and cannot tell request types apart; the service knows business meaning but only after the request has consumed a connection; the edge is fastest and only sees addresses and paths. The practical split is user and global limits at the gateway, business limits such as five items per customer inside the service.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1718700000

{
  "error": "rate_limit_exceeded",
  "message": "Too many requests, retry after 30 seconds"
}

Routing

KindExampleNote
Path prefixEverything under a prefix goes to one serviceThe common case
Exact matchA health endpoint goes to a probe serviceOperational routes
HeaderA version header selects a versionVersion routing
WeightNinety percent to one version, ten to anotherCanary releases
ParameterA tenant parameter selects a clusterTenant isolation

Two schools of path design. Prefixes such as `/api/v1/users/123` are clear, RESTful and trivial to configure, at the cost of putting a version in the URL that clients must follow. Subdomains such as `users.api.example.com` isolate services completely and route by name, at the cost of DNS management and awkward local development. Use prefixes; past fifty services the DNS approach becomes a burden, and a rewrite rule handles the rest.

routes:
  - uri: /api/orders/*
    upstream:
      nodes:
        - host: orders-v1.internal
          port: 8001
          weight: 90
        - host: orders-v2.internal
          port: 8001
          weight: 10

# internal staff to the new version, everyone else to the old one
routes:
  - uri: /api/orders/*
    vars:
      - ["http_x_internal_user", "==", "true"]
    upstream: orders-v2
  - uri: /api/orders/*
    upstream: orders-v1

Three rules for canaries. Start at one percent and watch for half an hour before widening. Keep rollback to seconds, which a weight change gives you without a deploy. And choose the dimension carefully: hashing on a user id keeps one user on one version, which is much less confusing than a random split where refreshing the page changes the experience.

Route conflicts need a deterministic rule: longest prefix wins, or first match wins, or an explicit priority field. Write tests for the ordering. Traffic that should have gone to one version reaching another is one of the hardest bugs to find, because no metric looks wrong and only the business result does.

Protocol translation

Backends increasingly speak gRPC while browsers speak JSON, and the gateway bridges the gap. That involves more than translation: status codes need mapping, JSON needs converting to and from protobuf, unary calls are easy while streaming is not, and metadata maps onto headers.

Do not hand-write those conversions inside the gateway. Use a transcoder that generates the mapping from the schema definitions; the maintenance cost of a manual table is prohibitive.

WebSockets are the awkward case, because a gateway assumes request and response while a socket is a long-lived connection. The default idle timeout cuts it, the default balancing strategy pins new connections to one machine, and per-request rate limiting has no obvious meaning for a thousand messages on one connection. Raise the timeouts in both directions and balance with address affinity so a reconnect lands where it left.

location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}

Server-sent events are the one-directional cousin and are easier, since the connection stays ordinary HTTP, but buffering turns a stream into batches, so disable it for those routes along with caching.

A Java team with fewer than ten services is best served by the Spring option, which needs no extra deployment. If performance and plugins both matter, the APISIX-class product is a reasonable default. If many authentication protocols must be supported, the most mature plugin ecosystem wins. Large systems that also run a mesh will use a C++ proxy in both roles. And a small team with a single service should use a reverse proxy or a managed gateway.

Traps

The gateway becomes the single point. Every request passes through it, so it failing means everything failing, which is both the most common objection and a real risk. Run at least two instances behind a balancer, keep them stateless with counters and revocation in a shared store, configure health checks so bad instances are removed, and accept that clients cannot fall back to direct connections, because the backends lack the gateway's protections. That is the price of centralising.

Added latency. A hop costs a millisecond or so in a fast implementation, and several things inflate it: token validation that queries a database, body conversion for large payloads, and crossing availability zones. Keep the gateway in the same network zone as the services.

State. Counters belong in a shared store so every instance agrees; session affinity is a routing decision rather than stored state; revocation lists are shared with a TTL. Nothing business-related should live in gateway memory, because per-instance counters make limiting meaningless.

Configuration is code. Export it, commit it, review it through pull requests, and apply it with a declarative tool rather than by hand, since a typo in routing is an outage.

Checklist and questions

  • At least two instances behind a balancer.
  • Secrets come from the environment or a secrets manager, never from configuration files.
  • Rate limiting counts in a shared store, not locally.
  • Rejections are 429 with a retry hint, not 500.
  • Socket timeouts are raised above an hour and buffering is off for streams.
  • Route priorities are ordered and unambiguous, with tests.
  • Canaries can roll back in seconds by changing a weight.
  • Access logs use one format and land in one store.
  • The gateway itself is monitored for CPU, memory, latency and error rate.
  • Configuration is versioned and reviewed.
  • Certificates renew automatically.
  • Backends trust only headers the gateway injected.

Is centralising not concentrating risk? It is, which is why the gateway itself needs redundancy. But ten services each doing authentication means any gap is a hole, while one gateway is a single availability risk that engineering can manage with replicas, health checks and automatic recovery.

Does a mesh replace this? No, they address different directions: a gateway handles traffic entering from outside, a mesh handles traffic between services. Large systems run both.

Can a gateway replace a reverse proxy? Most gateways are built on one, adding plugins and a control plane. Static files and proxying need only the proxy; authentication, limiting and canaries justify the gateway.

Does gateway limiting replace application-level limiting? No. The gateway rejects earliest and works at the granularity of address, user and path; a global business quota needs a shared counter in the application as well. The gateway is the first line, not the last.

Does a personal project need one? Usually not. One application behind a reverse proxy is enough, unless there really are several services or the point is to learn the configuration.

Closing

One sentence covers the idea: separate how requests arrive from what the service does. Business services handle what; the gateway handles who is calling, whether they may, how fast, which version and which protocol.

After the gateway went in, the four services dropped their authentication code, key rotation became one edit, and thresholds changed in one dashboard. A fifth service inherited authentication and limiting for free.

It is not a silver bullet either: it introduces a new single point, a new latency source and a new configuration surface. Whether to adopt one, which one, and with which features depends on scale and on the team.

A system without a gateway is not necessarily wrong. A system with one no longer has cross-cutting concerns scattered through it, and that alone tends to pay for the ticket.
