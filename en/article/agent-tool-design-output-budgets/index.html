Agent tool design: every output needs a ceiling

2026-10-24 · 34 min · Stack Frame

Who this is for: people adding tools to an agent and finding it gets more fragile with each one; people whose context was destroyed by a single cat on a large file; people who want a tool set that stays maintainable and auditable.

TL;DR: a tool has three contracts. Topology is which tools exist, shape is their arguments and descriptions, budget is how much comes back. The first two decide whether the model can use a tool correctly. The third decides whether using it destroys the context. NanoHermes caps every tool internally, then adds one global backstop: clamp(s, 20_000).

Tool boundaries are agent boundaries

What an agent can do is set not by how clever its model is but by which tools it holds. The tool set is the ceiling on capability: no edit_file and it cannot change code, no run_command and it cannot run tests, no web_fetch and it cannot read documentation.

The tool set also sets the floor on failure. A read-only tool that returns 3 MB of text destroys that turn, not because the model cannot answer but because the returned text fills the context and leaves no room for later results. That failure is sneakier than a wrong answer: the model treats the truncated fragment as the whole, and concludes confidently from incomplete information.

So tool design is not "write a few functions plus a JSON schema". Three layers need handling: what the model is shown (topology), how it calls (shape), and how much comes back (budget). The tool layer in NanoHermes is under 1,200 lines, and every layer has deliberate design.

The three-layer contract

LayerCarrierSymptom when wrong
TopologyThe array returned by build_toolsThe model calls a tool that does not exist, or a capability is missing
Shapename, description and parameters in specs()Wrong arguments, misleading descriptions, repeated trial and error
BudgetPer-tool caps plus clampOne call blows up the context
ErrorsResult<String, String>A single failure aborts the whole turn
Permissioncheck_tool and the approval policyA dangerous action runs unconfirmed

Of the five, budget is the layer most tutorials skip and most production incidents land in. Get topology or shape wrong and something errors immediately. Get budget wrong and nothing errors at all; the model just quietly sees half the data.

Topology: where 24 tools come from

The tool list is assembled, not hard-coded.

fn build_tools(&self) -> Value {
    let mut list = tools::specs().as_array().cloned().unwrap_or_default();
    // Only expose the skill tool when a skill was actually discovered.
    if !self.ctx.skills.is_empty() {
        list.push(skill_tool_spec());
    }
    if let Some(m) = &self.mcp {
        list.extend(m.all_tools());
        list.extend(mcp_aux_tools());
    }
    // Drop whatever the current configuration does not allow.
    list.retain(|t| { /* cfg.check_tool(name).is_ok() */ });
    if !self.cfg.subagents.is_empty() {
        list.push(subagent_tool_spec());
        list.push(agent_list_tool_spec());
    }
    Value::Array(list)
}

Then three conditional ones: skill when a skill was discovered, subagent and agent_list when sub-agents are configured. An MCP server adds its own tools plus four helpers, mcp_list_resources, mcp_read_resource, mcp_list_prompts and mcp_get_prompt.

The order is built-ins, then skills, then MCP, then sub-agents. That order becomes the order in the prompt, and models tend to favor what they see first. Built-ins leading is the right call: they are the most reliable and depend on nothing external.

Why the tool count grows on its own

The count is not a constant. The same binary can expose a dozen more or fewer tools depending on the workspace and the configuration.

SourceTriggerDeltaControlled by
Built-insAlways21The code
skillAt least one skill found+1Skill directories in the workspace
MCPAn MCP server configured+N, declared by the serverThe mcp section of config.json
MCP helpersAn MCP server configured+4The code

More tools means a higher chance of a wrong pick and a tiring /tools listing. NanoHermes does three things about it.

  1. Conditional tools are never exposed unconditionally. No skills, no skill; no sub-agents, no subagent. The model is never invited to call something that must fail.
  2. Tools the permissions disallow are filtered out, so the model cannot see a tool it would only be rejected for.
  3. Related capabilities collapse into one tool. todo_write replaces the whole list, which obviates add, update, remove and clear. run_command takes a background flag instead of a second tool.

That third one is debatable: merging complicates one schema. But understanding "the same run_command with a background boolean" costs a model less cognition than remembering two names.

Shape: the JSON schema is the only interface

The model sees three things: name, description, parameter schema. Those three are the whole contract. Nothing implicit gets guessed.

Two sentences in that description are deliberate. "Returns content with line numbers" tells the model the output format. "Use offset/limit for large files" tells it what to do with a big file, which is what decides whether it paginates instead of giving up.

A counterexample: grep's description says "Search file contents for a literal substring". The word literal matters, because it rules out regular expressions. Without it the model passes d+ or .*, gets no matches, and concludes the code does not contain what it plainly does. The include parameter says "Glob filter, e.g. '*.rs' or 'src/**/*.ts'", and two examples beat a grammar description every time.

A thinner example: task_list says only "List all background tasks with their id, command and status (running/finished)." Correct but thin, since it does not say what the output looks like and the model has to call once to learn. Acceptable for a low-frequency, low-risk read; worth fixing if it starts being misused.

The first gate: argument validation

A schema is advice to the model, not enforcement. It can omit a field, pass the wrong type, or send an empty string. Every tool entry point therefore validates.

fn req_str<'a>(args: &'a Value, key: &str) -> Result<&'a str, String> {
    args.get(key)
        .and_then(|v| v.as_str())
        .ok_or_else(|| format!("missing string field `{key}`"))
}

One line handles three cases: the field is absent, the type is wrong, or the value is null. All three become "missing string field" with the field name included, which is what lets the model fix it.

Optional parameters get defaults rather than becoming required, following one rule: cover the common case and never produce dangerous behavior. offset is 1, limit is 2,000, timeout_secs is 120, max_chars is 20,000. Dangerous values are blocked separately: timeout_secs clamps to 1 through 3,600, max_chars clamps to 500 through 200,000. The model cannot ask for a command that never times out, or for 100 MB of text.

ToolRejected inputError text
run_commandEmpty command after trimmingcommand must not be empty
grep, globEmpty patternpattern must not be empty
edit_fileEmpty old_stringold_string must not be empty; use write_file to create a file
apply_patchEmpty diffdiff must not be empty
git_commitEmpty messagemessage must not be empty
web_searchEmpty queryquery must not be empty

These checks look redundant. Why would the model send an empty string? They catch two real cases: a half-formed call emitted mid-reasoning, and a JSON parse failure that collapsed into an empty object, which makes every field missing at once.

Order matters too. The empty old_string check and the empty diff check both run before the file is touched. An argument error should surface before the filesystem is involved, which saves an IO round trip and stops "file not found" from masking "you forgot the argument".

Budget: why every output must be capped

The previous two layers cover how to call. This one covers how much comes back, and it is both the most overlooked and the most dangerous.

Counterintuitively, the biggest context killer is usually tool output, not user input. A typed line is dozens of characters; one run_command can emit megabytes. Without caps, three bad things happen.

  1. The context blows up. A single call exceeds the 120,000 character session budget, compaction fires, real history is dropped, and the summary costs another model request on top.
  2. The model drowns in noise. Of the thousands of lines from ls -R or npm install, three are useful, and the model has to read all of them.
  3. The request fails outright. Many providers cap tokens per request, and exceeding it returns an error after the whole turn's work.

A cap is also a compression signal: it tells the model "this is not everything", which pushes it to paginate, narrow the search, or switch tools. The cap is part of the prompt.

Three infinite sources

SourceWhy it can be unboundedWhere it gets capped
FilesA user may have a 500 MB log fileThe read_file admission gate, then clamp
Commandsnpm install and cargo build emit an unpredictable number of linesCapture limits while draining the pipe
NetworkA page can be any length, or a 100 MB archiveResponse byte cap plus character clipping
DirectoriesA directory can hold a hundred thousand entriesFile-count caps in grep and glob, then clamp

Four layers of capping correspond to that table: filter before enumerating (grep skips files over 1 MB), limit while reading (read_capped keeps the first 256 KB), clip after producing (clip trims each line to 240 characters), and backstop at the exit (clamp to 20,000 bytes). The order cannot be shuffled: skip the enumeration filter and one huge file slows the whole grep; skip the read limit and process memory dies before the backstop is ever reached.

Three observations.

  1. Units are inconsistent. Some are bytes, some are called characters but count bytes, some genuinely count characters. For English and code it barely matters; for Chinese and emoji the difference is a factor of three.
  2. Exceed behavior is inconsistent. Error, truncate-and-note, or skip silently.
  3. The magnitudes form a clean ladder. A file read is widest at 4 MB, then network at 2 MB, background at 512 KB, foreground commands at 256 KB, and everything funnels into 20,000 bytes. The gradient reflects where the data comes from: a local file is the most trusted and controllable, a web page the least.

The easiest one to overlook is RESULT_PREVIEW = 500, the length of a sub-agent result shown by agent_list. It decides how much a parent sees when it glances at the task board, and 500 characters is about two sentences, enough to tell finished from stuck.

One exit: the clamp at the end of dispatch

pub fn dispatch(name: &str, args: &Value, ctx: &Ctx) -> Result<String, String> {
    let r = match name {
        "read_file" => fs::read_file(args, ctx),
        // ... twenty-odd branches ...
        other => Err(format!("unknown tool `{other}`")),
    };
    r.map(|s| clamp(s, ctx.max_output))
}

That last line is valuable because it cannot be bypassed. A new tool may forget its own cap, but going through dispatch means clamp runs regardless. That is default safety: the unsafe version requires deliberate effort, not the safe one.

fn clamp(s: String, max: usize) -> String {
    if s.len() <= max {
        return s;
    }
    let mut end = max;
    while end > 0 && !s.is_char_boundary(end) {
        end -= 1;
    }
    format!(
        "{}
… output truncated ({} chars omitted)",
        &s[..end],
        s.len() - end
    )
}

Two details. Character boundary retreat: slicing at an arbitrary byte would panic, and the 20,000th byte very often lands inside a three-byte Chinese character, so the code walks back at most two bytes. Leave that out and the agent panics instead of truncating.

Omitted byte count: the note says (3600 chars omitted) but the number is bytes. For Chinese, the actual number of omitted characters is a third of what the note claims.

There is also an asymmetry: Result::map only touches the Ok branch, so errors pass through unclamped. In theory a tool could return a 100 KB error and inflate the context; in practice errors are short, but the asymmetry is worth remembering.

The comment says characters, the code counts bytes

/// Max characters of tool output fed back to the model (keeps context small).
pub max_output: usize,

The comment says characters. clamp uses s.len(), and in Rust String::len() returns bytes. So max_output = 20_000 means 20,000 bytes.

For Chinese content the difference is a factor of three: 20,000 bytes of ASCII is 20,000 characters, Chinese is about 6,666 characters, mixed text about 10,000. Reading Chinese comments, searching Chinese docs, fetching Chinese pages: the comparable capacity for Chinese is a third of English.

The same codebase contains the opposite: web_fetch's clip_chars, grep's MAX_LINE_CHARS and MAX_BODY_CHARS really do count characters. Two semantics in one project, depending on whether the author reached for len() or chars().count().

This is not a bug that must be fixed today; 20,000 bytes covers most situations. It is an inconsistency that must be documented, because any capacity estimate built on "max_output is characters" will be wrong. The cheap fix is renaming the comment to bytes. The intuitive fix is counting chars(), at the cost of walking the string every time.

Three truncation semantics

SemanticImplementationUsed byStrengthRisk
RefuseReturn Errread_file over 4 MB, todo_write over 50 itemsThe model immediately knows to change strategyOne extra failed round trip
Truncate with a noteKeep the prefix, state what was droppedclamp, clip, CAPTURE_BYTESUsable information, and the model knows it is partialThe note costs budget too
Skip silentlySkip without a wordgrep skipping files over 1 MBDoes not interrupt the flowThe model reads it as "no matches"

The third is the dangerous one.

let Ok(meta) = fs::metadata(path) else { return };
if meta.len() > MAX_FILE_BYTES {
    return;   // files over 1 MB are skipped with no error and no note
}

Search a string across a directory of small files, where the string only exists in one large file, and the model receives "no matches for ...". The conclusion is wrong and the model cannot tell, because it does not know a file was skipped.

Why keep the silent skip? Because in a full tree walk, printing a line per oversized file turns "no match" into dozens of lines of noise, which is worse. The middle ground costs one counter: append "N files skipped for size" to the final output, which removes a whole class of misjudgment for almost nothing.

The same shape appears in read_capped.

pub(crate) fn read_capped(mut r: impl Read) -> (Vec<u8>, usize) {
    let mut kept = Vec::new();
    let mut total = 0usize;
    loop {
        match r.read(&mut buf) {
            Ok(0) => break,
            Ok(n) => {
                total += n;
                if kept.len() < CAPTURE_BYTES {
                    let room = CAPTURE_BYTES - kept.len();
                    kept.extend_from_slice(&buf[..n.min(room)]);
                }
            }
            Err(ref e) if e.kind() == std::io::ErrorKind::Interrupted => continue,
            Err(_) => break,
        }
    }
    (kept, total)
}

It must keep reading to the end rather than stopping, because a child process writing into a full pipe blocks forever. So "discard" here means read and drop, never stop reading. total is what lets the note state how much was omitted. The function is reused in three places, shell.rs for foreground commands, tasks.rs for background tasks and git.rs for git output, each with a different cap.

read_file: a 4 MB gate and a 2,000 line window

let meta = fs::metadata(&full)?;
if meta.len() > MAX_FILE_BYTES {
    return Err(format!(
        "{} is {} bytes (> {}); read it in chunks with offset/limit",
        full.display(), meta.len(), MAX_FILE_BYTES
    ));
}

The error names the next action: read it in chunks with offset and limit. That is far more useful than "file too large", because it moves the model from "what do I do" straight to "use a window".

Where does 4 MB come from? It is not an output budget, it is a memory budget. The file is read whole and then split by line, so 4 MB means "allocating 4 MB at once is safe". The real output budget is handled by the 2,000 line default window and the 20,000 byte clamp at the exit.

Worth doing the arithmetic. A 3.5 MB log at 100 bytes a line is about 35,000 lines. The default reads the first 2,000, about 200 KB, and the exit clamp cuts that to 20,000 bytes, roughly 200 lines. So the model believes it asked for 2,000 lines and actually got 200 plus a truncation note. Miss the note and it concludes from the first 200 lines.

Two more thorough fixes exist: lower the default limit to match the output budget, so requested and received line counts roughly agree, or state in the note "this file has N lines; you are seeing the first M". NanoHermes does half of the second, with a note but an unchanged default, leaving the arithmetic to the model.

let end = (offset - 1 + limit).min(total);
let width = end.to_string().len();
for (i, line) in lines[(offset - 1)..end].iter().enumerate() {
    let n = offset + i;
    out.push_str(&format!("{n:>width$}→{line}
"));
}

The right-aligned line number width comes from end, the last line of the window, not from total. Reading lines 1 to 2,000 gives width four; reading lines 1 to 9 gives width one. Alignment shifts between calls. Harmless for a model reading numbers, mildly annoying for a human diffing two outputs side by side.

read_file details: lossy decoding, binary detection

It uses from_utf8_lossy, not strict decoding. If the file contains invalid UTF-8, a GBK-encoded Chinese text, a corrupted log, binary bytes mixed in, lossy decoding replaces those bytes with U+FFFD instead of failing. For an agent that is the right call: a few replacement characters beat refusing to read the whole file over one bad byte.

read_file does no binary detection; grep does.

/// Exposed for reuse by the search module.
pub fn is_binary(bytes: &[u8]) -> bool {
    bytes.iter().take(8192).any(|&b| b == 0)
}

Only grep calls it. Hand read_file a 2 MB PNG, which passes the 4 MB gate, and it reads the whole thing, returns a wall of mojibake, and gets clamped to 20,000 bytes. The model usually works out that it was binary, after wasting the turn. The fix is the same one-line check returning an error like "looks like a binary file": a NUL byte in the first 8,192 is a test with zero false positives on real text and near-total coverage on real binaries.

A flag instead of break, because the closure cannot break out of for_each_file. The guard at the top returns immediately for later files, which is equivalent to stopping early, except the walk itself continues and every remaining file still enters the closure. On a large repository that is wasted motion, at an acceptable cost.

Output is path:line:text, with relative paths and backslashes normalized to forward slashes. One path style across platforms means the model never has to tell two conventions apart. Windows drive letters still create ambiguity, since C: contains a colon.

One performance wart: case-insensitive search lowercases every line, two allocations and two passes each, so a 10,000 line file costs tens of thousands of small allocations. An allocation-free case-insensitive compare would be faster. Not a correctness issue, but grep is one of the most-used tools.

grep has no file-count cap

MAX_FILES = 500 appears only in glob. grep limits nothing but matches.

The worst case: search for a string that almost certainly does not exist, in a tree with 500,000 files. grep reads every file, one fs::read each, and finally answers "no matches", possibly minutes later. No timeout, no file cap, no progress output. glob at least stops collecting after 501 matches, though it too keeps walking. Agents usually search from a project root with a few thousand files, so this is not urgent, but a workspace containing one huge generated directory that the ignore list misses turns grep into an operation that never returns. Two improvements: count visited files in for_each_file and stop early, or make the ignore list configurable.

One genuinely good design in the same function: include goes through path_matches, which tries both the relative path and the file name.

fn path_matches(pattern: &str, rel: &str) -> bool {
    if glob_match(pattern, rel) { return true; }
    let name = rel.rsplit('/').next().unwrap_or(rel);
    glob_match(pattern, name)
}

So include: "*.rs" matches src/main.rs by filename, and include: "src/**/*.ts" matches by relative path. The model never has to decide which form to use.

glob: 500 files and a false message

The segment matcher has three rules: when the pattern is exhausted the path must be too, so *.rs does not match src/main.rs; ** eats zero or more segments, so src/**/*.rs matches src/main.rs; ordinary segments use * and ? within a segment, and * never crosses /. Tests lock all three.

for_each_file uses an explicit stack rather than recursion: no stack overflow on deep trees, and collecting entries before descending avoids holding a read_dir handle while recursing.

Then there is the false message.

if matches.len() >= MAX_FILES {
    out.push_str(&format!("
… capped at {MAX_FILES} files"));
}

The condition is >= 500. A project with exactly 500 matching files, no 501st, still gets "capped at 500 files", and the model concludes there are more and keeps looking another way. The correct test is whether a match was actually dropped because of the cap, which means setting an overflowed flag inside the branch that refuses a match. The difference only shows at the boundary, but a false truncation notice is worse than none: it makes the model abandon a complete result it already has.

list_dir: the only uncapped reader

list_dir applies no internal limit at all. It lists every entry and lets the exit clamp handle it. The consequence is calculable: 5,000 files at about 40 characters a line is 200 KB, clamped to 20,000 bytes leaves roughly 500 lines, and the last 90% of the directory is invisible.

Contrast that with read_file, which refuses and asks for a window. list_dir hands over the first 500 entries and has no pagination parameter, only path, so "show me entries 501 to 1,000" requires finding a deeper subdirectory. For the normal use, "what is in this project", it is fine. For build output or a dataset directory it produces a misleading partial panorama. A cheap fix is an internal cap of 300 with a closing line stating the total.

A smaller issue: sizes are rendered by human_size as "1.5 MB". Friendly for humans, but 1,048,576 becomes "1.0 MB", so a model trying to find the largest files has to parse units and compare. Not wrong, just a choice about who it is optimized for.

run_command: 256 KB twice, plus a timeout

256 KB is per stream, so the theoretical worst case is 512 KB, which the exit clamp then cuts to 20,000 bytes. In practice the 256 KB limit is almost never visible to a user; it exists to stop a chatty command from eating memory.

What users actually see is the timeout, implemented by polling.

let exit = loop {
    match child.try_wait() {
        Ok(Some(status)) => break status.code(),
        Ok(None) => {
            if start.elapsed() >= Duration::from_secs(timeout) {
                let _ = child.kill();
                let _ = child.wait();
                timed_out = true;
                break None;
            }
            std::thread::sleep(Duration::from_millis(25));
        }
        Err(e) => return Err(format!("failed to wait for command: {e}")),
    }
};

Polling at 25 ms trades CPU for the ability to enforce a timeout at all, with about 25 ms of precision, plenty for second-scale limits. wait() right after kill() is mandatory: signal without reap leaves a zombie. On timeout exit is None and the report says exit code: killed, so the model can tell a normal failure from a kill.

if crate::sandbox::needs_approval(ctx.auto_approve, ctx.approval, command) && !confirm(command) {
    return Ok("Command denied by the user. Do not retry it; ask what to do instead.".to_string());
}

Note that this returns Ok, not Err, and the text carries two instructions: do not retry, ask instead. Making a refusal an instruction to the model rather than an error is one of the smarter choices in the design, because "the user refused" and "the command failed" demand opposite reactions. Refusal should stop and ask; failure can be retried with a different command. Return an Err with a generic message and the model will cheerfully retry the exact thing the user just rejected.

Draining both pipes

let out_pipe = child.stdout.take().expect("stdout piped");
let err_pipe = child.stderr.take().expect("stderr piped");
let out_thread = std::thread::spawn(move || read_capped(out_pipe));
let err_thread = std::thread::spawn(move || read_capped(err_pipe));

Why not wait_with_output()? Because it waits for exit before reading anything. Pipe buffers are bounded, 64 KB on Linux typically, so a child writing more than that blocks on the write and never exits, and the wait never returns. That is the classic pipe deadlock.

Two threads, one per stream, and the main thread only waits and watches the clock. A child can now emit megabytes without filling a pipe, because someone is always draining.

// Drain both pipes on separate threads so a chatty child can never deadlock
// by filling the OS pipe buffer while we wait for it to exit.

The pattern is reused in git.rs, since git diff can also emit megabytes. It is not reused in tasks.rs, which is exactly the defect the next section covers.

Background tasks

The foreground timeout caps at 3,600 seconds, but even inside that range, making the model wait through a cargo build is a waste: the whole turn is spent waiting when the model could be reading code, writing docs, and coming back for the result.

if args.get("background").and_then(|v| v.as_bool()).unwrap_or(false) {
    return super::tasks::run_background(args, ctx);
}

The registry lives in Ctx, shared by every tool and guarded by a mutex.

pub struct TaskManager {
    tasks: Mutex<HashMap<String, Task>>,
}

A task id is the process id plus a nanosecond timestamp. Nanoseconds rather than a counter means two tasks started in the same millisecond cannot collide, with no global counter to maintain; the process id makes cross-process logs tell you which agent instance spawned the task.

Three tools cover the lifecycle: task_list for what exists, task_output for increments, task_kill to stop. output() drains increments rather than returning the whole buffer.

pub fn output(&self, task_id: &str) -> Result<String, String> {
    let mut map = self.tasks.lock().unwrap();
    let task = map.get_mut(task_id).ok_or(/* unknown task */)?;
    if let Some(child) = task.child.as_mut() {
        if let Some(mut out) = child.stdout.take() {
            let (kept, total) = read_capped(&mut out);
            task.out_buf.extend_from_slice(&kept);
            task.out_total += total;
            child.stdout = Some(out);
        }
        // …
    }
    // …
}

The take() and put-back exists because read_capped takes the reader by value. Slightly awkward, but it avoids adding a lifetime parameter to Task.

Accumulated output caps at 512 KB, double the foreground limit. That makes sense: a background task is drained over several calls, so the total is naturally larger, and it is retained cumulatively rather than reported per call.

A real defect: stderr is never drained

cmd.current_dir(cwd)
    .stdin(Stdio::null())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped());

Both streams are piped. But output() only takes and reads child.stdout, and Task has a single out_buf field with no error buffer. Once stderr is a pipe, no code ever reads it.

Which means something serious: a background command that writes more than the pipe buffer to stderr, 64 KB typically, blocks forever on that write, never exits, and task_output reports running until the end of time, while the model polls a task that will never finish.

Scenariostderr volume
cargo build with progress and warningsWarnings alone can exceed 64 KB
npm install with deprecations and an audit reportCommonly a few KB to tens of KB
Any CLI with a progress bar, pip or docker includedContinuous redraw, large totals
A test command reporting many failuresUnbounded

The control group is the foreground run_command, which drains both pipes on two threads and therefore has no such problem. git.rs does the same. Only the background path was missed.

Two fixes: merge stderr into stdout, which means editing the command string and is unclean, or add an err_buf to Task and drain stderr in output() the same way.

if let Some(mut err) = child.stderr.take() {
    let (kept, total) = read_capped(&mut err);
    task.err_buf.extend_from_slice(&kept);
    task.err_total += total;
    child.stderr = Some(err);
}

That fixes the hang and makes error output visible, which it currently is not: the model only ever sees stdout. For an agent tool, "the command failed and you cannot see why" is a miserable state.

It is worth calling out because it illustrates a whole class: two similar paths in one project, foreground and background, with different draining strategies, one of them wrong, and no test covering "a background command writes a lot to stderr". Review rarely catches this, because the broken path looks entirely normal. It just never ends.

web_fetch: 2 MB and 20,000 characters

const MAX_RESPONSE_BYTES: usize = 2 * 1024 * 1024;

let max_chars = args
    .get("max_chars")
    .and_then(|v| v.as_u64())
    .unwrap_or(20_000)
    .clamp(500, 200_000) as usize;

Two layers. The response body keeps at most 2 MB and drains the rest. Then clip_chars cuts to max_chars by characters, 20,000 by default. Note the semantic clash with the exit clamp: 20,000 characters of Chinese is 60,000 bytes, which the clamp then cuts to 20,000 bytes. Both cuts do something, and the second is the one that finally binds.

The 200,000 upper bound will never matter, because the exit clamp is 20,000 bytes. An honest range would be 500 to 20,000, or at least consistent with the exit budget.

let mut out = format!("URL: {url}
");
if total > bytes.len() {
    out.push_str(&format!("[response truncated at {MAX_RESPONSE_BYTES} bytes]
"));
}
out.push_str(&clip_chars(&text, max_chars));

Comparing total read against bytes kept is more reliable than trusting Content-Length, which chunked transfer and gzip can make absent or wrong. Deciding on observed facts rather than declarations is the only correct approach in HTTP.

web_search caps result count only, five by default, clamped to 1 through 10. Reasonable: the result shape is fixed, title plus URL plus snippet, so count is the only length driver. A pathologically long snippet can still inflate the output, and the exit clamp catches it.

One last note: capping output is not capping work. html_to_text walks the entire document to strip tags, decode entities and collapse whitespace before clipping, so a 2 MB page is fully parsed. At normal call rates that is irrelevant; put web_fetch in a loop of thousands and the bottleneck is right here.

Skills and project docs eat the same budget

Two things are not tool output but still consume the budget, and both are capped.

Skill bodies. MAX_BODY_CHARS = 20_000. Loading a skill returns the full text, and a very long skill doc would fill the context. Twenty thousand characters matches the web_fetch default, the size of a thorough document that does not hijack the conversation.

Project docs. MAX_PROJECT_DOCS = 20_000, applied to AGENTS.md, the global one plus every one from the repository root down to the workspace. Exceeding it truncates and appends "project guidance truncated".

const MAX_PROJECT_DOCS: usize = 20_000;
const DOC_NAMES: [&str; 1] = ["AGENTS.md"];

Assembly order is global, then root, then down to the workspace, deduplicated by canonicalize so a symlink cannot cause a double read. There is a real risk here: truncation cuts the tail, and the tail is exactly the most workspace-specific guidance. Fifteen thousand characters at the repository root plus eight thousand in a subdirectory is 23,000, and what gets cut is the back half of the subdirectory file, the most specific half. Collecting upward from the workspace and stopping when the budget is full would preserve the right end.

The skill list also costs budget, but one line each, so the effect is linear and small. The real weight is loading a body through the skill tool. Index always resident, body on demand: the same idea as RAG, with a much thinner index.

Errors are results

Every tool failure is expressed as Result<String, String>, with a string error. That decision has three consequences.

The error text is written for the model, not for a log. Each one says what went wrong and what to do next.

ToolError textNext step for the model
read_fileN bytes, over the limit, read it in chunks with offset/limitRe-read with a window
edit_fileold_string not found, read the file and match it exactly, including whitespaceRead the file first
edit_fileold_string occurs 3 times, pass replace_all or more contextAdd the flag or context
grepNo matches for the patternTry another term, or widen the scope
skillUnknown skill, plus the available namesPick from the list
subagentUnknown sub-agentUse a configured name
gitgit status exited with 128, plus git's own stderrRead the underlying error

The skill error lists the available names and the git error embeds git's stderr. Both put the information the model needs into the error and save a round trip through "fail, list, call again".

An error does not abort the turn. execute wraps it into a tool result and the loop continues; run_tool formats it as ERROR: .... If a tool error bubbled up as an exception, one mistyped argument would end the whole task. As a string, the model sees the error and fixes it. That is one of the largest differences between an agent and an ordinary program: errors are first-class input, not exceptions.

A counterintuitive corollary: error text should be capped too, and is not. clamp only touches the Ok branch. A tool returning a 100 KB error, say dumping an entire git diff as a failure message, would pass through untouched. No tool does that today, but "the exit only protects the success path" is an asymmetry worth remembering.

Approval: which tools ask first

Capability is not proportional to danger. read_file cannot destroy code no matter how it is written; one run_command with rm -rf can.

pub fn check_tool(&self, name: &str) -> Result<(), String> {
    if self.permission_mode.blocked_tools().contains(&name) {
        return Err(format!("tool `{name}` is not available in {:?} mode", self.permission_mode));
    }
    if self.disallowed_tools.iter().any(|t| t == name) {
        return Err(format!("tool `{name}` is disallowed by configuration"));
    }
    if !self.allowed_tools.is_empty() && !self.allowed_tools.iter().any(|t| t == name) {
        return Err(format!("tool `{name}` is not in the allowed list"));
    }
    Ok(())
}

The order is deliberate: mode first, because the current situation disallows it; then the deny list, which is the user's explicit instruction; then the allow list, a narrowing rule that only matters if the first two did not already reject.

Blocked tools never appear in the tool list at all, via retain in build_tools, while check_tool errors at call time. The first prevents a wrong pick; the second prevents a bypass, such as a model that learned a tool name from history and tries it anyway.

ToolConfirms by defaultBasis
run_commandPer the approval policyA command cannot be analyzed statically
git_commitPer the approval policyWrites history, but it is reversible
write_file, edit_file, apply_patchNo, outside specific modesFile changes can be rolled back
ModeBlocked toolsTypical use
defaultNoneEveryday work
accept-editsNone, but shell confirmation stays onTrust file edits, not commands
planwrite_file, edit_file, apply_patch, run_command, git_commitRead-only analysis

The contrast between plan and debug is the clearest illustration: plan blocks even run_command, because a planning phase should have no side effects, while debug allows commands to reproduce a problem and forbids touching files, so a broken state does not get worse.

Which directories read-only tools skip

fn is_ignored_dir(name: &str) -> bool {
    matches!(name,
        ".git" | "target" | "node_modules" | "__pycache__"
        | ".venv" | "venv" | "dist" | "build"
        | ".idea" | ".cache" | ".next" | "vendor"
        | ".tox" | ".mypy_cache" | ".ruff_cache" | ".pytest_cache"
    )
}

Fifteen names cover the build output of the main ecosystems: Rust's target, Node's node_modules, dist, build and .next, Python's __pycache__, .venv, .tox and various caches, PHP's vendor, and the IDE's .idea. A medium Node project has a hundred thousand files under node_modules, so without this "just search the name globally" walks a hundred thousand third-party files. Hard-coding means it works out of the box; the cost is that generated directories outside the list, out, bin, obj, .gradle, Pods, can only be handled by editing the code.

grep and glob both go through for_each_file and share the list. list_dir does not, so listing a directory does show node_modules, which is usually what a user wants. The split is right: filter when searching, show everything when listing.

Output order matters

Three tools sort before returning, each for a reason.

list_dir sorts directories and files separately, printing all directories then all files. Unsorted output follows the filesystem, usually inode order on Linux, which looks random and makes it hard to spot the main directories. "Directories first, alphabetical" is a convention both humans and models read easily.

glob sorts too. for_each_file uses a stack, collecting depth-first in reverse, so the natural order is scrambled. Sorting means the same pattern returns the same order twice, which matters for caching and diffing.

grep does not sort. Hits come out in traversal order, line order within a file, but every line carries a path:line prefix, so nothing is lost. Not sorting means truncation drops files that were visited later, and sorting would require collecting everything first.

The three rules reduce to one principle: whenever output is truncated by position, order decides what survives. list_dir does not truncate, so order is only readability. glob's order decides which 500 files survive. grep's decides which 200 hits survive, and that is the one worth improving: sorting by path and line before truncating would make the output far more stable for a little extra memory.

The hidden cost of tools

Tools are not free. Every tool ships its full definition with every request, and 24 tools cost roughly 2,500 to 4,000 tokens depending on description length. Across 100 turns that is hundreds of thousands of input tokens of schema alone.

The larger cost is not money, it is choice difficulty. More tools means more wrong picks. The confusing pairs are predictable.

Confusable pairDifferenceHow it is mitigated
write_file vs edit_fileWhole-file overwrite vs targeted replacementwrite_file says prefer edit_file for small changes
edit_file vs apply_patchOne site vs severalapply_patch says "instead of edit_file"
grep vs globSearch content vs search names"file contents" versus "Find files by"
run_command vs task_outputRun vs collectrun_command explains polling after backgrounding
memory_save vs todo_writeAcross sessions vs within oneBoth descriptions state their persistence scope
web_fetch vs web_searchRead a known URL vs find an unknown oneweb_search points at web_fetch

The third column is the valuable trick: disambiguate in the description instead of making the model guess. For every confusable pair, at least one description names the other. The larger the tool set, the more this should be a hard requirement.

Another hidden cost is overlap: nearly everything apply_patch can do, edit_file can do. Overlap is not a defect, it gives the model options, but it raises the bar on descriptions. Otherwise the model picks one at random, fails, and tries the other.

Eight principles of tool design

One. Every output must have a ceiling, and it must be on by default. Not "this tool might be long, so cap it", but "cap everything, then loosen where it truly cannot be long". Safe by default, not trusted by default.

Two. Caps must be layered, never single. Filter before enumerating, limit while reading, clip after producing, backstop at the exit. With only the exit, memory and latency problems still happen.

Three. Exceeding a cap must be visible. Of the three semantics, silent skip belongs only where a note would create noise, and it should still produce a count. A model that does not know information is incomplete will conclude from what it has, which is the most expensive failure mode.

Four. Error text should say what to do next. Not "file too large" but "read it in chunks with offset/limit". Likewise a refusal should read as an instruction: do not retry, ask instead.

Five. Refuse with Ok plus an instruction; fail with Err plus a reason. The two mean opposite things to a model. Merging them produces a model that retries rejected operations.

Six. Defaults must cover the common case and must not be dangerous. offset: 1, limit: 2,000, timeout: 120, max_chars: 20,000. If the dangerous value is the default, the design is wrong.

Seven. Unify units, or label them explicitly. Mixing bytes and characters in one project is a source-level confusion, because it never errors; it just skews every capacity estimate. Pick one and write it in the field comment.

Eight. Use descriptions to remove ambiguity between tools. For each confusable pair, at least one description names the other. Highest return on effort in the whole set.

One more, outside the eight, matters as much: write symmetric implementations for symmetric paths. Foreground and background commands draining pipes differently caused a guaranteed deadlock. Opening run_command side by side while writing the background path would have found it in five minutes.

The two-stream check is the one that almost always finds a bug: write a script that prints a line to stderr every second, background it for ten seconds, then call task_output. If it reports running forever, you have the deadlock.

Closing

  1. Tool design has three layers. Topology, shape, budget. The first two decide correctness, the third decides whether the context survives.
  2. Caps must be layered and on by default. Filter, limit, clip, backstop. Drop a layer and a matching resource problem appears.
  3. Exceeding a cap must leave a trace. Silent skipping is the most expensive failure, because it lets a model conclude confidently from incomplete data.
  4. Error text is part of the prompt. Saying what to do next beats saying what went wrong.
  5. Symmetric paths need symmetric code. Foreground and background draining differently caused a permanent block.

An agent's tool layer is, in the end, the layer that translates the outside world into text the model can digest. The quality of that translation depends on two things: whether it is accurate, which is schema and description, and whether the volume is controlled, which is budget. Most tutorials cover only the first. Production incidents mostly come from the second.

NanoHermes' tool layer is not perfect: read_file does no binary detection, grep has no file-count cap, background tasks never drain stderr, the clamp's unit label is wrong, and glob can report a false truncation. All of those are identifiable, locatable and individually fixable. They are not "the design missed it", they are "the implementation missed a spot", and that difference matters: the first needs re-architecture, the second needs one more commit.
