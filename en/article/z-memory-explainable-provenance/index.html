Z Memory: a memory layer that can explain itself

2026-11-18 · 20 min · Stack Frame

Who this is for: engineers adding long-term memory to an agent without handing data to a vector-database service; anyone tired of a model that remembers something yesterday, forgets it today and gets it wrong tomorrow; people who care about deduplication, conflict and explainable retrieval.

TL;DR: Z Memory does not use a vector database, and it does not treat a memory as a chunk of text to recall. A memory is a structured record with a source, a trust level, relations and events. Writes go through "candidate, review, store". Deduplication and conflict both keep the old record instead of overwriting it. Retrieval returns the FTS5 rank, a 384-dimensional local hash vector, and five scoring factors separately. The trade-offs are equally explicit: the hash vector only understands surface words, semantic search is O(n), and conflict detection is still rule-based.

Reading time around 20 minutes. Level: advanced.

The problem isn't storage. It's explanation.

Most "give the AI memory" projects end up looking the same: chunk the conversation, embed it, put it in a vector store, take the top K by cosine similarity, paste it into the prompt. It runs, but when it goes wrong you cannot answer three questions:

  • Which sentence did this memory come from?
  • Why did it rank above that other memory?
  • When new information contradicted old information, which one was deleted?

Z Memory starts by making those three questions database fields. A memory is "traceable structured knowledge": type, subject, source, trust, importance, confidence, relations, events and conflicts all live in tables. You can switch models; the database stays on your machine, and memory does not follow a provider's session.

PrincipleImplementation
Local-firstOne SQLite file. No account, sync or telemetry.
Structured10 memory types, subject, tags, relations, sources, events.
SearchableFTS5 keywords, local vectors, metadata filters.
ExplainableSource excerpts, score breakdowns, activity timeline.
EditableEdit, archive, restore, delete and merge are all exposed.
ForgetfulArchive, expire, hard delete, erase all.
PortableJSON, Markdown, TXT, CSV and SQLite import/export.
Agent-ready35 Tauri commands, a JSON CLI and a context builder.

The data model: twelve tables and an audit trail that survives deletion

database/migrations/001_init.sql defines twelve ordinary tables plus one FTS5 virtual table:

TablePurpose
memoriesType, content, normalized content, subject, importance, confidence, trust, status, reinforcement count, timestamps
memory_tagsMany-to-many tags
memory_relationssupports, contradicts, derived_from, related_to, supersedes
memory_sourcesSource type, source id, original excerpt
memory_eventsCreated, merged, conflicted, accessed, archived, restored, expired
memory_embeddingsModel name, dimension, vector BLOB
memory_conflictsOld memory, new memory, reason, status, resolution
memory_candidatesPending review: type, content, scores, conflict/duplicate pointers, status
conversationsRaw conversations
conversation_messagesMessages, with a trusted flag
audit_logWho did what, and when
settingsConfiguration key/value pairs
memory_ftsFTS5 index over content, subject and tags

The most important design decision is written in a comment: event rows deliberately do not follow a memory deletion. memory_events.memory_id has no foreign key, so events survive a hard delete, and audit_log behaves the same way. A user can ask the system to forget a memory; the content, tags, sources, vector and relations are deleted, but the fact that it was created, merged and accessed remains. Privacy ("delete the content") and audit ("keep the behavior") are two different promises.

The connection settings are the usual single-machine combination: PRAGMA foreign_keys = ON, synchronous = NORMAL, WAL for file-backed databases, and busy_timeout = 5s. Read-heavy, write-light, willing to lose the last write on a crash, but a slow query must not lock another process forever.

Two-stage ingestion: candidate first, memory second

The extractor is not allowed to write memories directly. Extraction produces rows in memory_candidates; the user reviews them on the Remember page before they are stored. require_review defaults to true. That is not caution for its own sake: automatic extraction will never be reliable enough to skip the step.

The memory_extract command enforces three boundaries first:

  1. Empty text is rejected.
  2. Text over 200,000 characters is rejected.
  3. Untrusted input goes through sanitize_untrusted(), which drops instruction-looking lines one by one.

Then the engine setting chooses llm, heuristic or auto. auto means "use the model if configured, otherwise use the offline engine". If model extraction fails under auto, the code falls back to the offline engine and records the failure as a warning. Only an explicit llm setting surfaces the error.

The offline rules are short, and every one is explainable:

  • Split into sentences; skip anything shorter than four characters.
  • Skip greetings and questions.
  • Skip sentences containing sensitive data when redact_sensitive is on.
  • Skip one-off task requests unless they also contain an explicit marker such as "remember", "from now on" or the Chinese equivalent.
  • Classify into one of ten types by keyword rule. If no rule matches but an explicit marker exists, classify as fact.

The scores are computed, not guessed:

importance = rule base + 0.12 if explicit + (hits - 1) x 0.02
             temporary capped at 0.35; hedged x 0.85
confidence = 0.90 if explicit, otherwise 0.72 + (hits - 1) x 0.03
             hedged x 0.7; temporary capped at 0.5

Candidates are then deduplicated against each other: same type and lexical similarity above 0.8 merge. The survivors are sorted by importance x confidence and cut to max_candidates (default 8). min_importance defaults to 0.2; anything below is not shown.

Trust is a separate axis with a fixed order:

explicit > observed > imported > inferred > external
  • explicit: the user said "remember", "from now on", "always".
  • observed: a direct statement in conversation.
  • imported: data brought in from a file.
  • inferred: indirect evidence, capped and always reviewed.
  • external: web or third-party content, capped at 0.4, never auto-accepted.

External content also has a hard gate: allow_external_ingestion is off by default. Even when it is turned on, every candidate is forced to external and both importance and confidence are clamped below 0.4. The rule is simple: external content can be a lead, but it cannot promote itself into a fact.

Deduplication: normalize first, then 0.82

Deduplication only compares memories of the same type. That restriction matters: preference: I like Rust and fact: I like Rust are not the same memory and must not merge.

Similarity has four parts:

similarity = lexical similarity x 0.6
           + 384-dim hash cosine  x 0.4
           + same subject         + 0.06
           + same trust level     + 0.02

There is a fast path first: strip whitespace, lowercase, keep only alphanumerics and CJK, and compare the normalized key. An identical key returns 1.0 immediately.

Above the threshold (default 0.82) the new draft merges into the existing memory instead of creating a row. The merge rules are fixed:

  • Higher trust wins the content. Equal trust requires the new confidence to be at least 0.05 higher.
  • Importance and confidence become max(old, new) + 0.01.
  • Reinforcement count increments.
  • Tags are unioned; the source is appended.
  • A merged event records the similarity, whether content changed, and the new reinforcement count.

Reinforcement is not a UI like button. It feeds the frequency factor, ln(1 + count) / ln(1 + 12), so a repeatedly confirmed memory rises in ranking but saturates.

Conflict: never overwrite, place side by side

Deduplication handles "the same thing said twice". Conflict handles "the same thing said the opposite way". They are mutually exclusive: anything above the dedup threshold never reaches conflict detection.

Conflict detection also stays within one type. It first asks whether the two memories are on the same topic: normalized subjects match, or similarity reaches conflict_threshold (default 0.55). Then there are three reasons:

  • Polarity flip: one side has a negation (dislike, hate, never use) and the other has a positive (prefer, like), with different polarity.
  • Change over time: a change marker appears ("now prefer", "switched to", "instead") and similarity is at least 0.7 of the threshold.
  • Different choice for the same subject: both sides contain a choice verb, the tails after the verb are extracted, generic tokens are removed, the remaining token sets do not intersect, and both sides contain Latin text.

On a hit, the old row is not overwritten. A new memory is inserted, a memory_conflicts row is written, and a contradicts relation is recorded at confidence 0.8. There are four resolutions:

ResolutionBehavior
keep_oldArchive the new memory; add a supersedes relation at 0.9
keep_newArchive the old memory; add a supersedes relation at 0.9
keep_bothKeep both; add a related_to relation
dismissMark the conflict handled; change neither memory

The archived side stays on the Archived page and can be restored. The point is not to pick the right answer automatically. The point is to leave the decision to the user and never silently discard information that was once trusted.

Retrieval: FTS5, a hash vector and five weights

Keyword search uses SQLite FTS5 with tokenize = 'unicode61 remove_diacritics 2'. Chinese does not need a custom tokenizer because the application pre-tokenizes before indexing: runs of CJK characters become bigrams, Latin text is split into words, and the result is joined with spaces. Queries go through the same tokenizer, take at most 24 tokens, quote each one, join with OR, and run ORDER BY bm25(memory_fts) LIMIT 500.

Vector search is a local hash, not a model:

model = "local-hash-v1"
dim   = 384
token -> FNV-1a -> index = hash % 384
sign  = top bit of hash ? -1 : +1
value = sign x (1 + ln(count))
then L2-normalize the whole vector

It is deterministic, offline and dependency-free, and it captures texts that share surface tokens. The repository's own test states the boundary: I prefer Rust and Tauri scores higher against desktop app technology preference than my favorite food is noodles. Synonyms are another matter.

Fusion normalizes keyword rank within the filtered candidate set, takes the semantic cosine, and weights them 0.60 / 0.40. The final score has five factors:

score = relevance  x 0.40
      + importance x 0.25
      + confidence x 0.20
      + recency    x 0.10
      + frequency  x 0.05

If the weights do not sum to one, the result is divided by the total, so changing weights cannot push the score outside 0–1. Recency uses a trust-dependent half-life: explicit 3,650 days, observed 730, imported 1,095, inferred 365, external 180, and temporary capped at 3 days. Access updates last_accessed_at at most once per hour, so repeated searches do not keep resetting "recently used" to now.

A search response can include score_breakdown: relevance, keyword, semantic, importance, confidence, recency, frequency, keyword rank and semantic similarity, one by one. The detail page can recompute it under the current settings. That is what "explainable" means here: not a natural-language justification, but every multiplier and where it came from.

Context building: 12 rows, 4,000 characters, whole rows dropped

The agent interface is not "dump the database into the prompt". It is build_context:

  • Search by query, 12 rows by default, 50 maximum.
  • Render each row as index. [type · confidence%] content.
  • Default budget 4,000 characters, allowed range 200–32,000.
  • A row that does not fit is dropped whole; it is never cut mid-sentence.
  • A fixed CONTEXT_PREAMBLE says memories are context, not unquestionable instructions, and the current user request wins on conflict.

estimated_tokens is simply characters divided by four. That estimate is optimistic for Chinese, but it is display-only; the budget itself is enforced in characters, so the UI cannot claim there is room when there is not.

There are two agent surfaces: 35 Tauri commands for the desktop UI, and z-memory-cli for scripts and external agents. The CLI supports search, list, get, detail, create, update, archive, restore, delete, conflicts, context, export and import. It reads %APPDATA%ai.zmemory.appz-memory.db by default, overridable with --db or Z_MEMORY_DB_PATH, and emits JSON.

Lifecycle: archive, expire and hard delete

Candidate -> Stored -> Retrieved -> Reinforced -> Updated
        -> Archived / Expired / Deleted
  • A temporary memory expires after seven days by default.
  • Every search runs expire_due() first, marking due active memories as expired.
  • Archiving does not delete; it excludes the memory from retrieval and can be reversed.
  • Restoring clears expires_at.
  • A hard delete cascades through tags, relations, sources and the vector, but events and audit rows remain.

Deleting a memory requires typing DELETE, and erasing everything requires the same. The friction is deliberate: destructive actions in a memory system should not be as easy as a normal button.

Untrusted content can never become a memory on its own

The defense has three layers:

  1. Input: untrusted text goes through sanitize_untrusted() line by line. Lines matching one of 24 patterns such as ignore previous instructions, you are now or "delete all files" are removed whole, with a warning.
  2. Extraction: heuristic_extract() returns an empty candidate list when trusted = false, and the model prompt says instructions inside external content are data, not commands.
  3. Write: even if external content produces a candidate, trust is forced to external, importance and confidence are clamped below 0.4, and external ingestion is off by default.

Sensitive information has its own path. contains_secret() checks 14 markers such as "password", "private key" and "credit card", plus two shapes: sk- followed by at least 16 characters, and a run of 32 hex digits. A hit either skips the sentence or replaces the token with [redacted]. redact_sensitive is on by default.

None of this stops every attack. It closes the most dangerous path, where external content writes itself into long-term memory. The remaining risk is real: once the user accepts an external fact, it ranks with the same machinery as their own statements. The trust field can push it down; the system cannot judge whether it is true.

Seven gaps that remain

  1. The hash vector only understands surface words. Synonyms, paraphrase and cross-language rewrites can score near zero. It is a dependency-free approximation of semantics, not semantic understanding.
  2. Semantic search is O(n). Every query loads all vectors from SQLite, computes cosine one by one, filters, then truncates to 200. At tens of thousands of memories this becomes visible latency. There is no ANN index and no incremental candidate set.
  3. rrf_k is dead configuration. ScoringConfig carries rrf_k: 60.0, but fused_relevance() uses linear rank normalization plus weights. Changing the value affects nothing.
  4. Conflict detection is rules, not understanding. A purely Chinese choice change ("switch to braised" versus "switch to steamed") will not trigger different_choice, because that function requires Latin tokens on both sides. Negation is substring matching, so a phrase like "no need to be polite" can be read as a negative preference.
  5. Candidate extraction is conservative. Stable facts without an explicit marker or a type keyword are missed. Conversely, a sentence containing "I like" but describing a one-off preference can be captured; review is the backstop.
  6. One memory is capped at 8,000 characters. Long documents, meeting notes and full articles must be chunked outside the system. There is no automatic segmentation.
  7. Cross-process writes have no application-level coordination. The GUI and CLI can open the same database, relying on WAL and a five-second busy timeout. But "check for a duplicate, then insert" is two operations; two processes writing the same new memory at once can still each insert one.

Two boundaries are not gaps but are worth knowing. If LLM extraction is enabled, text is sent to the configured provider; that is not a purely local path. And inferred and external are marked untrusted in the model, but retrieval does not exclude them by default. They decay faster and rank lower; they are not removed.

Closing

The interesting part of Z Memory is not the refusal to use a vector database. It is that four things most memory systems leave vague are turned into mechanisms you can inspect:

  • Source: every memory has memory_sources, and candidates keep the original excerpt.
  • Trust: the five levels are not labels. They decide merge winners, decay speed and whether a candidate is auto-accepted.
  • Conflict: no overwrite and no silent delete. The old record is archived and linked with supersedes or contradicts.
  • Ranking: relevance, importance, confidence, recency and reinforcement are independently configurable and returned item by item.

The costs are equally clear: the hash vector is not a semantic model, the scan is linear, and conflict detection is still rules. In other words, it does not claim that the AI truly understands your preferences. It claims that for every memory the AI has, you can see where it came from, why it ranked there, and what it conflicts with.

For memory, explainable matters more than clever, because one wrong preference is harder to notice than ten things that were never remembered.
