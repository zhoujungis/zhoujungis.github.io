Happy Games: 24 browser games with zero frameworks, one deploy

2026-11-05 · 40 min · Stack Frame

Don't go looking for a game. Just start one. That's the pitch for Happy Games, a browser arcade written in plain HTML, CSS and JavaScript: 24 games, zero frameworks, zero build steps, zero dependencies. The AI ranges from pattern scoring to WebAssembly, multiplayer runs on D1 plus polling, narration streams from a language model, and the whole site deploys to Cloudflare Pages in one command.

Play: happygames.pages.dev · Source: github.com/zhoujungis/happy_games

Why another mini-game collection

The web doesn't lack game portals. It lacks a sample project that can be read end to end and cloned in one click. Happy Games is positioned as three things:

  1. A teaching sample. Every folder runs on its own. There is no "install 300 MB of node_modules, then work through five layers of abstraction" tax.
  2. Real technical depth. Under the zero-framework constraint it still covers AI from heuristics to a WASM engine, realtime multiplayer, streamed narration, accounts and end-to-end tests.
  3. Deployable. The whole site is static files plus Cloudflare Pages Functions and D1. No containers, no servers, one wrangler command.

Read this if you want a starting scaffold for a browser game, a real case of organizing a large frontend without a framework, a minimal full stack on the Cloudflare stack, or simply ten minutes of play.

The hard parts

Four levels of AI, from pattern scoring to WebAssembly

The AI here is never "pick a random move". It spans four technical levels.

One: pattern scoring, in gomoku. Eight directions scan the board shapes, and each shape is scored.

PatternScoreMeaning
Five in a row100000Already won
Open four10000Four with both ends open, a forced win
Blocked four, open three1000Four blocked at one end, or three open at both
Blocked three, open two100Three blocked at one end, or two open
Two10
Single stone1

Difficulty controls search depth. The easy level looks one move ahead and can slip; the hard level looks several ahead and prefers blocking your open three over completing its own blocked four. All of it is pure functions, so the test runner exercises it directly.

Two: alpha-beta pruning, in Chinese chess. The engine is ported from an MIT-licensed open-source project, keeping the core: move generation per piece rule, including horse legs, elephant eyes and palace diagonals; piece-square value tables capturing what a piece is worth on each square, such as a pawn before and after crossing the river; and alpha-beta search with position evaluation, pruning branches that can't beat the best line found so far.

Board logic and the AI engine are fully separated. The server also exposes a model-based move proxy as a fallback, for the extreme positions where the local engine can't produce a move in time.

Three: GNU Go compiled to WebAssembly, for Go. This is the hardest technical path in the project. The open-source GNU Go engine is compiled to WebAssembly at about 8.7 MB and runs inside a web worker, communicating with the main thread over a small message protocol.

main to worker:  { cmd: 'init', size, seed }    start a game with Komi 7.5
main to worker:  { cmd: 'play', i, j }          the player moves
main to worker:  { cmd: 'genmove' }             the engine thinks and moves
worker to main:  { ok, cmd, board, last }       board snapshot, colour-normalized

The worker also does three things that matter. Colour normalization makes the player's colour map to one and the opponent to two after the first move, independent of the engine's internal constants, so rendering stays consistent. A move log records every coordinate, so a crashed game can be replayed. And standard output and error are captured through the module's print hooks, which makes diagnosis possible.

A world-class board engine running in the browser without blocking the main thread is a complete demonstration that a frontend can host heavy AI.

Four: three difficulty tiers, in jungle chess and reversi. Both split AI by search depth into three tiers, and reversi adds undo. Same pure-function approach, fully unit-testable.

Aeroplane chess: realtime multiplayer on D1

The only multiplayer game among the 24, and its architecture has three layers.

create or join  →  advance state (roll, move, start)  →  polling sync
      │                       │                                │
      ▼                       ▼                                ▼
create and join          roll and move              the client polls every 1.5s in
endpoints                and start                  game, every 2s in the lobby;
                                                    the server runs tick() to advance
                                                    AI turns before responding
  • Rooms. One endpoint creates a password-protected room and another joins it. Room state serializes as JSON into a single D1 row holding the code, the password, the state blob and timestamps.
  • State advance. Every move is validated server-side, which stops cheating. Empty seats are driven by server-side AI, so a table can start with one human.
  • Polling. The client periodically fetches state. Before responding, the server runs one tick to advance AI turns, so a player always sees the newest position with everyone else's moves already applied.

D1 is both database and cache here. It's simple enough, and it avoids the operational cost of WebSockets.

Streamed AI narration

Life simulation and the history brawl bring a language model into the game, with the server proxying server-sent events.

Life simulation. After the player allocates birth attributes, the frontend posts them. The server calls OpenRouter and forwards the event stream verbatim to the browser. Six chapters, childhood through a final verdict, generate character by character, so it reads like someone telling a story on the other side of the screen. A rate limit triggers automatic backoff, up to three attempts with a growing interval, and the prompt pins the output shape: 130 to 180 characters per chapter, and a final line that states a life score.

The prompt constraints are explicit.

You are the randomising AI of a Chinese life simulator. Output exactly six headings,
one per line: childhood, youth, adulthood, middle age, later life, verdict.
The first five are 130-180 characters each and must include concrete events in that
stage, their impact, and how they change the next stage. The final section must begin
with a life score from 0 to 100.

History brawl. Two players take turns drafting historical figures for ten posts, such as vanguard or logistics. When drafting finishes, they ask the AI judge. The AI scores ten matchups in the order dynasty fit, then role fit, then actual ability, then lineup synergy, with each round precise to one decimal and every round summing to ten. The voice is a storyteller's, and the answer also streams.

Both are lightweight patterns for combining a game with a language model. The server only authenticates, rate-limits and forwards the stream, and never stores model state. The client consumes standard events, and a failure doesn't block the game loop.

Accounts and the admin console

  • Register, log in, log out. Passwords live in a D1 users table holding the username as primary key, the password and a creation timestamp. Sessions use a random token in a cookie with a 30-day expiry check.
  • Current user. One endpoint reports the login state, which the home page uses to show the username and a logout link. The admin account unlocks a hidden console entry point.
  • Middleware. A shared middleware redirects unauthenticated HTML requests to the login page, while static assets and API routes pass through. Admin paths check the username as well and return 403 otherwise.
  • Admin endpoints. A user list and game statistics.

Fast, without trying

  • Zero dependencies and zero build. Static assets open immediately, with no bundle to download first.
  • Layered caching in the headers file. CSS, JavaScript and module files get five minutes of strong caching plus a day of stale-while-revalidate. WebAssembly gets seven days and is marked immutable, so the Go engine loads once and stays cached. Images get a day, with a week of background refresh.
  • The home page picks three random games as recommendations on every visit and offers a "start something random" button, which is a small cure for decision paralysis.
  • Responsive layout with breakpoints at 850 and 600 pixels, touch and keyboard input, and playability on phone and desktop.
  • A shared runtime manages lifecycle, score and event reporting for every game, and a failure there never blocks the game loop.

Architecture

Frontend: self-contained folders and a data-driven home

index.html          home: section cards, daily picks, start something random
board, puzzle, fun, history   section pages with that section's cards
shared/landing.js   the single source of truth: sections, game config, SVG previews
shared/game-runtime.js  lifecycle, score and the feedback event queue
shared/theme.css, cards.css, game.css

each game is one self-contained folder
<game>/index.html      page shell and the rules dialog
<game>/<game>.js       interaction and rendering, may include a worker
<game>/<game>.css      its own styles
<game>/ai.js           pure AI, no DOM, unit-testable
<game>/engine.js       pure logic: moves, rules, state machine
<game>/logic.js        board rules such as captures and liberties
<game>/levels.js       level data, such as fifteen sokoban levels

Three design rules.

  1. A shared theme. One stylesheet defines the CSS variables for ink, accent red, accent gold, borders, surfaces and soft shadows. A second styles the home and section cards. A third styles the in-game layout and state feedback. Every game reuses one visual language instead of inventing colours.
  2. A data-driven home page. The landing module is the only data source. Its sections array defines four sections of six games, each with an id, name, description, href, accent colour and preview SVG. One function renders the home cards, another renders a section's cards. The three recommendations, the random button and the counts all derive from that config, so adding a game touches one place.
  3. Self-containment. One folder per game holds the page, the styles, the logic and the AI. Adding a game touches no other game, and deleting one is deleting a folder.
// adding a game to the landing module is one more entry
{
  id: 'mygame',
  name: 'My game',
  description: 'One-line summary',
  href: '/mygame/',
  accent: '#2980b9',
  previewSvg: `<svg viewBox="0 0 120 120">…</svg>`,
}

The shared runtime creates a session for each game, records key events, syncs score snapshots and submits a result when the game ends or the page is left.

  • A factory generates a session id, starts the session through an API call, deduplicates score pushes into snapshots, and finishes through another call plus a flush.
  • An event queue batches uploads with a maximum queue of 60, a flush size of 6 and a 1600 ms delay. Events carry idempotent ids, and a network failure requeues instead of blocking the game loop.
  • A DOM observer watches score and status elements, extracting the score and recognizing win or loss keywords, which triggers a finish.
  • Games can also report directly by dispatching custom score and event events.
  • A page-hide handler sends the finish beacon, so a score isn't lost when the tab closes.

The design philosophy: the domain layer must not know about the DOM, canvas, network or database. Pages consume domain snapshots, the runtime owns lifecycle and feedback, and the AI and engine files stay pure so Node can test them. The architecture document fixes the boundary: page, then shared UI and runtime, then game domain, then API client, then Pages Functions, then D1.

Shared helpers live in per-feature shared files, for JSON responses, cookie parsing, identity, loading and saving rooms. Business logic sits in a service module and database access in a repository module, so Functions are transport adapters, services own the workflow, and repositories own the SQL.

Database

A schema file defines seven tables, incremental changes live in a migrations directory, new databases run the whole schema and existing ones apply migrations in order.

users            -- username primary key, password, created_at
sessions         -- token primary key, username, expiry, indexed by username
battle_rooms     -- code primary key, password, state JSON, timestamps
feixingqi_rooms  -- same shape, state holds seats, pieces, turn, dice and log
game_sessions    -- id, game_id, username, anonymous_id, started_at, ended_at,
                 --   status, score, duration_ms, metadata JSON
game_events      -- event_id unique, session_id, game_id, type, score, payload, client time
game_scores      -- session_id primary key, game_id, username, score, outcome, duration

Room state is a single JSON row, which is simple enough for this size. Multiplayer uses client polling plus a server state machine, with D1 acting as both database and cache.

Indexes cover the hot queries: sessions by game and start time, events by session and creation time, and scores by game with descending score.

Quick start

Requires Node.js 18 or newer, because both the wrangler CLI and the test runner need it.

# 1. clone
git clone https://github.com/zhoujungis/happy_games.git
cd happy_games

# 2. install, only wrangler and playwright, no frontend dependencies
npm install

# 3. run locally, serving static assets and Functions together
npm run dev
# open http://localhost:8788

The dev server reads the D1 binding from the wrangler config. Local D1 has to be created or synced first.

# local database, recommended while developing
npx wrangler d1 create happy-games-db   # put the database_id into wrangler.toml
npx wrangler d1 execute happy-games-db --local --file=schema.sql
# or connect to a remote database you already created in the dashboard
npx wrangler d1 execute happy-games-db --remote --file=schema.sql

Tests

npm test          # Node's runner over 25 files and 288 cases
npm run check     # JS syntax plus HTML charset and viewport checks
npm run test:e2e  # Playwright smoke: desktop and mobile home, canvas games, overflow

Testing in Node works because every AI and engine is a DOM-free pure function: gomoku, Chinese chess, Go logic, aeroplane chess and the rest. Importing a module is enough to assert on it.

Deploying to Cloudflare Pages

The site publishes directly, with no build step, because the wrangler config points the output directory at the repository root.

Step 1: create the D1 database

In the Cloudflare dashboard, open Workers and Pages, then D1 SQL Database, and create a database named happy-games-db. Put the returned id into the wrangler config.

# wrangler.toml
name = "happy-games"
compatibility_date = "2025-01-01"
pages_build_output_dir = "."

[[d1_databases]]
binding = "DB"
database_name = "happy-games-db"
database_id = "your-database-id"

Then create the tables, apply any migrations in order, and verify.

npx wrangler d1 execute happy-games-db --remote --file=schema.sql
# if a migrations directory exists, apply each file in order
for f in migrations/*.sql; do npx wrangler d1 execute happy-games-db --remote --file="$f"; done
# verify
npx wrangler d1 execute happy-games-db --remote --command "SELECT name FROM sqlite_master WHERE type='table';"

Step 2: environment variables

In the Pages project settings, under variables and secrets, add the OpenRouter key if you want the life-simulation narration. Without it that one feature returns 503 and nothing else is affected.

The chess move proxy needs its own provider key if you use it. The comment at the top of that function explains the configuration.

Step 3: publish

npm run deploy
# equivalent to npx wrangler pages deploy .
  • The first run creates the Pages project.
  • Later runs publish incrementally, and Cloudflare handles the domain and HTTPS.
  • After that, visit the Pages URL or a bound custom domain.

Caching and routing. Layered caching is already configured in the headers file. The routes file excludes static assets from Functions, so only API routes and HTML reach the worker, which saves invocations.

{
  "version": 1,
  "include": ["/*"],
  "exclude": ["/*.css","/*.js","/*.mjs","/*.wasm","/*.png","/*.svg","/robots.txt","/rss.xml"]
}

Custom domains are configured in the dashboard, and Cloudflare issues the certificate automatically.

Adding a game: two places, and the whole site follows

Thanks to the data-driven design, adding a game takes two steps.

1. Create the folder, following an existing game's structure.

<game>/
├── index.html     # shell: header, board or canvas, rules dialog, shared CSS
├── <game>.css     # game-specific styles
├── <game>.js      # interaction and rendering, may include a worker
└── ai.js          # pure AI, testable with the Node runner

The HTML needs a charset declaration, a viewport declaration, a board container, score and status elements for the runtime's automatic snapshot, and a rules dialog. A module script at the bottom imports the game and creates the runtime.

2. Register it by adding one entry to the matching section's games array in the landing module, with an id that matches the folder, a name, a description, the href, an accent colour and a preview SVG.

Optional 3: a backend endpoint, if the game needs one. The filename becomes the route.

That is all. Home section cards, section pages, daily picks and the random button all pick up the new game without touching another file. That's what a single source of truth buys.

Constraints from the architecture document: keep existing URLs and static deployment behavior stable, migrate a representative game before batch migration, keep the pure-logic tests green, and add browser coverage for lifecycle, score, offline and responsive behavior.

Why zero frameworks

This isn't nostalgia. It's a trade made after weighing the alternatives.

  1. Readability first. Twenty-four games with completely different logic gain little from the abstractions a framework offers, and those abstractions add a "understand the framework before the game" step. Native code lets a newcomer follow one game end to end in ten minutes.
  2. Portability. The AI and engine files depend on nothing. Node imports them directly, and moving to a mini-program, an Electron shell or a server would only mean rewriting the rendering layer.
  3. Performance and offline. No framework means no runtime overhead, no hydration and no bundle. Apart from narration and multiplayer, every game works without a network, and the cache policy makes repeat visits nearly offline.
  4. Teaching value. This is a frontend project that can be read completely. No black-box bundler, no two thousand lines of configuration, just HTML files that run once uploaded. Put the complexity in the game logic and keep the engineering simple.

Zero frameworks doesn't mean zero conventions. The variable system in the theme stylesheet, the single data source in the landing module, the lifecycle contract in the runtime and the layering in the functions directory together form an invisible framework. They are agreed upon rather than depended upon.

Closing

Happy Games tries to prove one thing: that in the age of heavy frontend frameworks, native technology can still deliver a complete, maintainable, deployable full-stack product, as long as the boundaries are drawn clearly, the AI is written as pure functions, multiplayer becomes a state machine, and deployment is handed to a platform that already exists.

Each of the 24 games is its own small world. You can be the strategist on a board, the escapee in a maze, the merchant on a trade route, the courtier under a seven-day decree, or the scholar in an imperial exam. Don't look for a game. Start one.
