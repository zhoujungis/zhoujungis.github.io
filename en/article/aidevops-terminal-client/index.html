The problem: development data lives in six places that never talk

A team generates a lot of development data every day. Requirements sit in Jira. Commits sit in GitHub. Test results sit in CI. Bugs sit in a tracker. Releases sit in a pipeline. All of it exists, and none of it knows about the others.

So every developer does the same manual work. Which modules did this change touch? What broke in those modules before? Do the tests cover them? If we ship this release, where is the risk? The answers are all in the system. Putting them together means five browser tabs, three exported reports, and a memory test.

aidevops links the chain requirement, code, test, bug, release, and answers four questions from it:

  • Where is the risk in this commit, and which signal fired?
  • What should be regression-tested?
  • Where did this production incident probably start?
  • After reading all of it, what does the model suggest?

The terminal client exists because people who live in a terminal should not open a browser to read one risk report.

Architecture: a thin client over a thick server

aidevops is a client. It is a CLI with a full-screen TUI, and it holds no business logic. Every capability is an HTTP call to a Django service backed by PostgreSQL, Redis and pgvector.

That boundary is deliberate, for three reasons.

First, the data is too large for a client. Commit history, test records and bug lists run to hundreds of thousands of rows. The correlation engine, the risk model and the agents all need the whole picture. Putting that on a laptop turns the product into a demo.

Second, credentials stay on the server. Git tokens and model API keys are encrypted with Fernet and stored server-side. The client holds one access token, in its own config directory, mode 0600.

Third, there is only one set of rules. The CLI, the TUI and any future web UI read the same REST API at /api/v1. Logic cannot drift between surfaces, because there is no second copy.

This is why installing the client alone gets you a login failure. That is the architecture, not a bug. To run the backend locally, copy .env.example to .env and run docker compose up -d --build, with Swagger at /api/docs/. Or use make install && make migrate && make run plus make worker and make beat for Celery.

The client is Typer for the CLI, Textual for the TUI, Rich for output, and httpx for HTTP. Pure Python, no compiled extensions, Python 3.11 and up.

Getting data in: two cursors and idempotent ingestion

Without data, everything downstream is an empty state. Ingestion is the least glamorous part of the system and it has three channels.

GitHub sync. Two cursors are maintained separately: one for new commits, one for the initial history backfill. Rate limits are handled with backoff, because hitting them is normal rather than exceptional.

Webhooks. Pushes, CI results and issue changes arrive in real time. Two checks guard the door. An HMAC-SHA256 signature proves the request came from GitHub, and delivery_id idempotency means a redelivered event cannot create a second record.

Scheduled reconciliation. Webhooks get lost when the network hiccups or the service restarts, so a Celery beat job periodically reconciles and guarantees eventual consistency.

Attribution and test correlation run asynchronously afterwards. The trade-off is explicit: ingestion prefers slow over lost or duplicated, because every downstream calculation assumes the data is trustworthy.

Pinning a commit to a module

Correlation starts with a question that sounds trivial: which modules did this commit touch? It is a parsing problem in disguise. src/auth/ clearly belongs to auth, but who owns utils/date.py? Should a change under tests/ count against a business module?

Attribution runs in three levels, in priority order.

  1. Overrides. A maintainer declares a path-to-module mapping. That decision is final.
  2. Source-root inference. Without an override, the layout is read the way the language expects: top-level directories under src/ or lib/.
  3. Fallback. Everything else lands in an explicit bucket instead of floating unassigned.

The important half is the last sentence of the design: every attribution carries a reason you can read. "This file belongs to auth because it matched the override src/auth/**." Attribution is not a guess. Risk scores and regression candidates are built on that traceable layer.

explain: everything behind one commit

aidevops explain <sha> is the command people try first. Give it a SHA and it returns the commit's place in the chain: the requirement it serves, the modules it changed and how central each one is, the tests and bugs historically entangled with those modules, what went wrong there before, which release contains it, and which of these answers has no data behind it.

That last item matters more than it looks. data_gaps separates "nothing was found" from "we have no data". A tool loses trust fastest by dressing ignorance as a conclusion. In a repository that never ingested test results, "no regression candidates" has to mean "unknown", not "safe". explain makes that distinction part of the output.

The risk engine: ten signals, each one inspectable

aidevops risk <sha>, and aidevops module-risk <id> for a module view, return a normalized score. The ten signals are listed with their individual contributions, and the contributions sum to the score.

SignalWhat it measures
change_volumeLines and files changed
historical_bug_densityBug density of the modules involved
test_failure_rateRecent failure rate of the related tests
module_centralityHow central those modules are in the dependency graph
change_frequencyHow often this area changes (hotspot detection)
coverage_gapCoverage on the changed paths
open_high_severity_bugsOpen high-severity bugs on those modules
test_coverage_gapTest coverage for the module
release_proximityDistance to the next release; risk costs more near a cut
data_freshness_penaltyA penalty when the data is too old to trust

Three engineering decisions sit under that table.

Weights are configuration, not code. They live on the server and can be tuned in Django admin without a deploy.

Weights inherit in three levels: defaults, then organization, then project. A team that ships constantly can raise release_proximity. A team with weak test infrastructure can emphasize coverage_gap.

Contributions sum to the score. That is not decoration. It turns "I don't believe this number" into a concrete question: find the largest contributor and inspect its input. A black-box score gives you nowhere to look.

The model layer: five agents, evidence checks, full tracing

The model layer answers a narrower question than it sounds: given this data, what can be automated safely?

Providers are pluggable. Credentials are managed per organization through aidevops providers, provider-add and provider-verify, over an OpenAI-compatible protocol, with presets for DeepSeek, Qwen and Ollama. Keys are encrypted with Fernet and live on the server, like the Git tokens.

Five agents ship with explicit input and output contracts:

AgentWhat it does
Code ImpactAnalyzes the blast radius of a commit
Test GenerationGenerates cases along an eleven-category scenario matrix
Bug InvestigationBuilds an evidence chain around one bug
Root Cause AnalysisWorks backwards from symptoms to plausible causes
Requirement AnalysisExtracts verifiable acceptance points from requirement text

Start one with aidevops analyse -a test-generation --wait. History is in analyses and job. aidevops trace <id> shows every model call and tool call behind one analysis, with timings, so the agent is never a black box.

Findings carry citations. Anything the model says has to resolve back to real data: a commit, a bug, a test. Unresolvable references are dropped rather than shown. aidevops findings, finding <id> and triage <id> <status> track them from open to confirmed or false positive, and that trail becomes team knowledge.

The tool surface is closed on purpose. The model can call thirteen read-only tools, all scoped to the project. No write operation appears in its tool list. It can see the data and cannot change it, which is the precondition for the next section.

Proposals and audit: the model suggests, a person approves

Everything the model produces is a proposal: a batch of tests, an investigation conclusion, a remediation plan. None of it takes effect on its own.

aidevops proposals                 # pending proposals
aidevops approve <id>              # approve; a fixed executor runs it
aidevops reject <id>               # reject; discard

Three rules make that real. Only approve executes, and the executor is code, not a model decision. No approval means no writes; there is no implicit adoption and no "run by default, undo on objection". Everything lands in AuditLog, queryable with aidevops audit.

For QA the trade-off is easy to state. Tests are a line of defense, and you do not put something that acts on its own on a line of defense.

Multi-tenancy follows the same logic. The tenant id comes from the URL and never from the request body. Non-member access returns 404 without leaking existence, insufficient role returns 403, and every query goes through one scoped_queryset entry point, so there is no place to forget the filter.

Install and a five-minute tour

pipx install aidevops        # recommended: isolated venv, command on PATH
# or
pip install aidevops

Login uses the GitHub device flow: type a code in the browser, never paste a password into a terminal. Remote machines and containers use login --no-browser.

aidevops login                       # GitHub device-flow login
aidevops org-add "My Team"           # first run: create an org (you are admin)
aidevops projects                    # list projects (* marks the current one)
aidevops use qa-copilot-platform     # select a project for later commands
aidevops status                      # backend, account and project

Connecting a repository is the real entry point. Skip it and commits, risk and explain all return empty state.

aidevops connections                              # list Git credentials
aidevops connection-add -l my-github -t <PAT>     # private repos need repo read
aidevops connection-verify <connection-id>        # verify before using it
aidevops repo-add -c <connection-id> -f owner/repo  # register the repository
aidevops sync <repository-id> --wait              # pull history; ready on return

A connection is an organization-level credential, managed by admins, and can register several repositories. repo-update adjusts the sync window and attribution depth.

Upgrades run through aidevops upgrade. The client compares itself against PyPI on every run and warns in red when it is behind; the result is cached for 24 hours and AIDEVOPS_NO_UPDATE_CHECK=1 turns it off. One guardrail: upgrade refuses to run inside a pip install -e checkout, because that would silently replace your working tree with the released version. It tells you to git pull instead.

Scripting and CI

--json is a global option and goes before the subcommand:

aidevops --json findings | jq '.[] | select(.severity == "critical")'

Two details exist for pipelines. In --json mode the upgrade notice goes to stderr, so stdout stays clean. AIDEVOPS_JSON=1 is equivalent to the flag. In CI, inject the token with AIDEVOPS_TOKEN and point AIDEVOPS_BASE_URL at a test backend.

A realistic pipeline step: run aidevops --json risk $GITHUB_SHA; if the score crosses a threshold, post the regression candidates as a PR comment.

Tests, types and releases

The client lives in the repository's cli/ directory.

python -m pytest          # 50 client tests, including Textual pilot TUI tests
python -m ruff check .
python -m mypy ai_devops_cli

The TUI is tested with Textual's pilot, so keystroke flows and panel switches are covered without manual clicking. The backend has 569 tests, with four network cases skipped by default, none of which need the internet.

Every multi-tenant write path funnels through scoped_queryset, which lets tests assert case by case that tenant A cannot see tenant B's data.

Releases use tag-triggered trusted publishing: push a tag, GitHub Actions builds, and OIDC short-lived credentials upload to PyPI. No local packaging, no long-lived token.

Where it stands, and what is missing

It is alpha, and the limits are worth stating.

It needs its own backend. The client has no standalone value; trying the full flow means running the server first.

Single organization with multiple projects works. The cross-organization permission model is still settling.

End-to-end testing against a real model is on the roadmap. Agent tests currently use a stub model: the logic paths are covered, the output contract of real models is not.

Attribution wants one override configured per repository. Zero-config accuracy depends on how well source-root inference guesses.

The next priorities are the terminal detail views, then a real-model smoke test, then validating the Celery worker shape in production.

If you are building a QA platform too, or you care about linking development data and about agents kept on a leash, issues are welcome at github.com/zhoujungis/ai_devops. One line to install: pipx install aidevops.
