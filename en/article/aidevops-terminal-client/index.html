aidevops: an AI DevOps copilot that lives in your terminal

2026-10-16 · 17 min · Stack Frame

Who this is for: engineers who want desktop-grade developer tooling without leaving the terminal; people building AI features that must stay on a leash; anyone interested in how four systems of record can be joined into one traceable chain.

TL;DR: aidevops joins requirements, commits, tests, bugs and releases into one chain, then answers four questions from it. The model layer can read everything and write nothing. Every attribution, every risk contribution and every model claim is traceable back to a record you can open.

Reading time around 17 minutes. Level: intermediate.

A few days ago I put aidevops on PyPI. It's the terminal client for an AI DevOps and QA copilot, and pipx install aidevops is the whole installation. The source is on GitHub under MIT, and the project is fully open source.

This post covers what problem it solves, how data moves through it, how the risk score is computed, what the model is allowed to do and why it is kept in a cage, how each command works, and what I chose not to build.

The problem: development data lives in six places that never talk

A team generates a lot of development data every day. Requirements sit in Jira, commits in GitHub, test results in CI, bugs in a defect tracker, and release records in a pipeline. All of it exists. None of it knows about the others.

So every developer does the same manual work, every day. Which modules did this change touch? What broke in those modules before? Do the tests cover them? If we ship this release, where is the risk concentrated? The answers are all in the system, but assembling them means opening five browser tabs, exporting three reports, and trusting your memory for the rest.

aidevops links that chain and answers four questions from it:

  • Where is the risk in this commit, which module, which signal, and why;
  • What should be regression-tested, meaning the historical bugs and the candidate test list;
  • Where did this production incident most likely start, traced back to a requirement and a release;
  • After reading all of it, what does the model suggest?

The terminal client exists because people who live in a terminal should not have to open a browser to read one risk report.

Architecture: a thin client over a thick server

aidevops is a client. It's a CLI with a full-screen TUI, and it holds no business logic. Every capability is an HTTP call to a Django service backed by PostgreSQL, Redis and pgvector.

That boundary is deliberate, for three reasons.

The data is too large for a client. Commit history, test records and bug lists run to hundreds of thousands of rows. The correlation engine, the risk model and the agents all need the complete picture. Putting that on a laptop turns the product into a demo.

Credentials stay on the server. Git tokens and model API keys are encrypted with Fernet and stored server-side. The client holds exactly one access token, in its own config directory, with mode 0600.

There is one set of rules. The CLI, the TUI and any future web UI read the same REST API under /api/v1. Logic can't drift between surfaces, because there is no second copy of it.

This is why installing the client alone gets you a login failure on the first step. That's the architecture, not a bug. To run the backend locally, copy .env.example to .env and run docker compose up -d --build, with Swagger at /api/docs/. Or run make install && make migrate && make run and start Celery with make worker and make beat.

The client stack is Typer for the command line, Textual for the TUI, Rich for output and httpx for HTTP. Pure Python, no compiled extensions, Python 3.11 and up.

Getting data in: two cursors and idempotent ingestion

Without data, everything downstream is an empty state. Ingestion is the least glamorous part of the system, and it has three channels.

GitHub sync. Two cursors are maintained separately: one for new commits, one for the initial history backfill. Rate limits are handled with backoff, because hitting them is normal rather than exceptional.

Webhooks. Pushes, CI results and issue changes arrive in real time. Two checks guard the door. An HMAC-SHA256 signature proves the request actually came from GitHub, and idempotency on the delivery id means a redelivered event can't create a second record.

Scheduled reconciliation. Webhooks get lost when the network hiccups or the service restarts, so a Celery beat job periodically reconciles and guarantees eventual consistency.

Attribution and test correlation run asynchronously after ingestion completes. The trade-off is explicit: ingestion prefers slow over lost or duplicated, because every downstream calculation assumes the data is trustworthy.

Pinning a commit to a module

Correlation starts with a question that sounds trivial: which modules did this commit touch? It's a parsing problem in disguise. src/auth/ clearly belongs to auth, but who owns utils/date.py? Should a change under tests/ count against a business module?

Attribution runs in three levels, in priority order.

  1. Overrides. A maintainer declares a path-to-module mapping, and that decision is final.
  2. Source-root inference. Without an override, the layout is read the way the language expects, taking top-level directories under src/ or lib/.
  3. Fallback. Everything else lands in an explicit bucket rather than floating unassigned.

The important half is the last sentence of the design: every attribution carries a reason you can read. "This file belongs to auth because it matched the override src/auth/**." Attribution isn't a guess. Risk scores and regression candidates are built on that traceable layer.

explain: everything behind one commit

aidevops explain <sha> is the command people try first. Give it a SHA and it returns the commit's place in the chain.

  • The requirement this change serves, or the requirement cluster it belongs to.
  • Module impact: which modules changed, and how central each one is.
  • Regression candidates: the tests and bugs historically entangled with those modules.
  • Historical bugs: what went wrong in the same area before, and in what pattern.
  • The release that contains this commit, and when its window is.
  • Data gaps: which of the above has no data behind it.

That last item matters more than it looks. The gap field separates "nothing was found" from "we have no data". A tool loses trust fastest by dressing ignorance as a conclusion. In a repository that never ingested test results, "no regression candidates" has to mean "unknown", not "safe". Making that distinction part of the output is the product's integrity floor.

The risk engine: ten signals, each one inspectable

aidevops risk <sha>, and aidevops module-risk <id> for a module view, return a normalized score. The ten signals are listed with their individual contributions, and the contributions sum to the score.

SignalWhat it measures
change_volumeLines and files changed
historical_bug_densityBug density of the modules involved
test_failure_rateRecent failure rate of the related tests
module_centralityHow central those modules are in the dependency graph
change_frequencyHow often this area changes, which is hotspot detection
coverage_gapCoverage on the changed paths
open_high_severity_bugsOpen high-severity bugs on those modules
test_coverage_gapTest coverage for the module
release_proximityDistance to the next release, because risk costs more near a cut
data_freshness_penaltyA penalty applied when the data is too old to trust

Three engineering decisions sit under that table.

Weights are configuration, not code. They live on the server and can be tuned in Django admin without a deploy.

Weights inherit in three levels: defaults, then organization, then project. A team that ships constantly can raise the weight on release proximity. A team with weak test infrastructure can emphasize coverage gaps.

Contributions sum to the score. That isn't decoration. It turns "I don't believe this number" into a concrete question: find the largest contributor and inspect its input. A black-box score gives you nowhere to look.

The model layer: five agents, evidence checks, full tracing

The model layer answers a narrower question than it sounds: given all this data, what can be automated safely?

Providers are pluggable. Credentials are managed per organization through the provider commands, over an OpenAI-compatible protocol, with presets for DeepSeek, Qwen and Ollama. Keys are encrypted with Fernet and live on the server, exactly like the Git tokens.

Five agents ship with explicit input and output contracts.

AgentWhat it does
Code ImpactAnalyzes the blast radius of a commit
Test GenerationGenerates cases along an eleven-category scenario matrix
Bug InvestigationBuilds an evidence chain around one bug
Root Cause AnalysisWorks backwards from symptoms to plausible root-cause areas
Requirement AnalysisExtracts verifiable acceptance points from requirement text

Start one with aidevops analyse -a test-generation --wait. History is in analyses and job. The trace command shows every model call and tool call behind one analysis, with timings, so the agent is never a black box.

Findings carry citations. Anything the model says has to resolve back to real data: a commit, a bug, a test. Unresolvable references are dropped rather than shown. Triage moves each finding from open to confirmed or false positive, and that trail becomes team knowledge.

The tool surface is closed on purpose. The model can call thirteen read-only tools, all scoped to the project. No write operation appears in its tool list. It can see the data and can't change it, which is the precondition for the next section.

Proposals and audit: the model suggests, a person approves

Everything the model produces is a proposal: a batch of tests, an investigation conclusion, a remediation plan. None of it takes effect on its own.

aidevops proposals                 # pending proposals
aidevops approve <id>              # approve; a fixed executor runs it
aidevops reject <id>               # reject and discard

Three rules make that real. Only approval executes, and the executor is code rather than a model decision. No approval means no writes, with no implicit adoption and no "run by default, undo on objection". Everything lands in the audit log, queryable from the same client.

For QA the trade-off is easy to state. Tests are a line of defense, and you don't put something that acts on its own on a line of defense.

Multi-tenancy follows the same logic. The tenant id comes from the URL and never from the request body. Non-member access returns 404 without leaking existence, an insufficient role returns 403, and every query goes through one scoped entry point, so there is nowhere to forget the filter.

Install and a five-minute tour

pipx install aidevops        # recommended: isolated venv, command on PATH
# or
pip install aidevops

Login uses the GitHub device flow. You type a code in the browser and never paste a password into a terminal. Remote machines and containers use the no-browser variant.

aidevops login                       # GitHub device-flow login
aidevops org-add "My Team"           # first run: create an org, you become admin
aidevops projects                    # list projects, * marks the current one
aidevops use qa-copilot-platform     # select a project for later commands
aidevops status                      # backend, account and project

Connecting a repository is the real entry point. Skip it and commits, risk and explain all return empty state.

aidevops connections                              # list Git credentials
aidevops connection-add -l my-github -t <PAT>     # private repos need repo read
aidevops connection-verify <connection-id>        # verify before using it
aidevops repo-add -c <connection-id> -f owner/repo  # register the repository
aidevops sync <repository-id> --wait              # pull history; ready when it returns

A connection is an organization-level credential managed by admins, and can register several repositories. A repo update adjusts the sync window and the attribution depth.

Upgrades go through the upgrade command. The client compares itself against PyPI on every run and warns in red when it is behind; the result is cached for 24 hours and an environment variable turns it off. One guardrail is worth calling out: the upgrade command refuses to run inside an editable checkout, because that would silently replace your working tree with the released version. It tells you to pull instead.

Scripting and CI

The JSON flag is global and goes before the subcommand.

aidevops --json findings | jq '.[] | select(.severity == "critical")'

Two details exist for pipelines. In JSON mode the upgrade notice goes to stderr, so stdout stays clean. And setting the environment variable is equivalent to passing the flag. In CI, inject the token through the environment and point the base URL at a test backend for integration checks.

A realistic pipeline step: run the risk command against the commit SHA, and if the score crosses a threshold, post the regression candidates as a pull request comment.

Tests, types and releases

The client lives in the repository's cli/ directory.

python -m pytest          # 50 client tests, including Textual pilot TUI tests
python -m ruff check .
python -m mypy ai_devops_cli

The TUI is tested with Textual's pilot, so keystroke flows and panel switches are covered without manual clicking. The backend has 569 tests, with four network cases skipped by default, and none of them needs the internet, so CI stays fast.

Every multi-tenant write path funnels through one scoped query helper, which lets tests assert case by case that tenant A can't see tenant B's data.

Releases use tag-triggered trusted publishing. Push a tag, GitHub Actions builds, and short-lived OIDC credentials upload to PyPI. No local packaging, no long-lived token.

Where it stands, and what is missing

It is alpha, and the limits are worth stating.

  • It needs its own backend. The client has no standalone value; trying the full flow means running the server first, either through compose or through the local make targets.
  • Single organization with multiple projects works. The cross-organization permission model is still settling.
  • End-to-end testing against a real model is on the roadmap. Agent tests currently use a stub model, so the logic paths are covered and the output contract of real models isn't.
  • Attribution wants one override per repository. Zero-configuration accuracy depends on how well source-root inference guesses.

The next priorities are the terminal detail views, then a real-model smoke test, then validating the Celery worker shape in production.

If you are building a QA platform too, or you care about linking development data and about agents kept on a leash, issues are welcome at github.com/zhoujungis/ai_devops. One line to install: pipx install aidevops.
