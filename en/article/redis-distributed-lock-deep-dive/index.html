Redis distributed locks: the right shape, and where they stop working

2026-11-04 · 22 min · Stack Frame

Who this is for: backend engineers who have been burned by oversold stock, duplicate orders or a cron job that ran twice.

Examples in Redis 7 with Python and Java, but nothing here depends on a particular framework.

Reading time around 22 minutes. Level: intermediate to advanced.

The coupon that sold one too many

def grab_coupon(user_id):
    coupon = Coupon.objects.get(id=1)
    if coupon.stock > 0:
        coupon.stock -= 1
        coupon.save()
        Order.objects.create(user_id=user_id, coupon_id=1)
        return True
    return False

One process, one machine, no problem. Then you scale to four machines and load test two hundred concurrent requests against a hundred coupons. The stock column ends up at minus thirty-seven, the order table has 137 rows, and someone is asking about it in the team channel.

The instinct is to add a lock. An in-process lock cannot reach across four machines, so what you need is a distributed lock: mutual exclusion over one resource among N processes.

Redis is the most common implementation and also the most misused. This post takes five versions apart, what each one fixes, what each one introduces, and why the good ones look the way they do. Then it says plainly which two problems no Redis lock solves.

Four rules any distributed lock must satisfy

PropertyMeaningFailing example
Mutual exclusionAt most one holder at any momentTwo machines decrement stock together
No deadlockA crashed holder eventually releasesA kill signal leaves the lock forever
Fault toleranceMutual exclusion survives network and failover eventsA failover loses the lock and two holders appear
OwnershipOnly the holder can releaseA wakes up late and deletes B's lock

Remember the fourth: eighty percent of the incidents come from it. Deleting someone else's lock is worse than failing to acquire one. Failure is a retry; deleting another holder's lock is corrupted data.

Version one: SETNX, and why it fails in production

def acquire(lock_key):
    return redis.setnx(lock_key, 1) == 1

def release(lock_key):
    redis.delete(lock_key)

Three fatal problems.

No expiry, so it deadlocks. A crash in the middle of the critical section, an out-of-memory kill, a container eviction, and the release never runs. The key stays forever, every later acquire fails, and someone has to delete it at two in the morning.

The obvious patch is two commands, setting the key and then expiring it, which deadlocks the same way if the process dies between them. Acquisition has to be atomic.

Anyone can delete it. A is slow, the lock expires, B acquires, then A wakes up and runs its release, deleting B's lock. C enters, and now three processes are in the critical section.

No reentrancy. A nested call in the same thread fails to acquire and the business logic stops for no visible reason.

Version two: SET with NX and PX, the first usable version

SET lock:coupon:1 <unique_token> NX PX 30000

One command makes acquisition and expiry atomic. NX means only set when absent, PX sets a millisecond expiry, and the token identifies the holder so a release can check ownership.

def acquire(lock_key, ttl_ms=30000):
    token = uuid.uuid4().hex
    ok = r.set(lock_key, token, nx=True, px=ttl_ms)
    return token if ok else None

def release(lock_key, token):
    if r.get(lock_key) == token:
        r.delete(lock_key)
        return True
    return False

That fixes two of the three problems. Acquisition is atomic with an expiry, so no deadlock. Ownership is checked, so a late holder does not blindly delete. Two problems remain.

The check and the delete are not atomic. Between reading the token and deleting, the lock can expire and someone else can acquire it, and the delete removes theirs. The window is small, and under garbage collection pauses it will happen.

The TTL is a guess. Thirty seconds is too short if the work takes thirty-one, and ten minutes is too long if the holder crashes. That tension is what version three resolves.

Version three: Lua unlock plus a watchdog, the production template

Unlocking must be a single Lua script

if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

Redis executes a script as one unit, so the comparison and the delete cannot interleave with anything else. This line is the dividing line between correct and naive implementations: if the unlock is not a script or an equivalent atomic primitive, treat the whole thing as version one.

The watchdog: short TTL plus automatic renewal

The contradiction is that a short TTL evicts slow work, and a long TTL slows recovery after a crash. The watchdog resolves it: acquire with a short TTL, then run a background task that periodically checks the lock is still ours and extends it. When the work finishes or the process dies, renewal stops and the lock expires within one TTL.

class RedisLock:
    def __init__(self, client, key, ttl_ms=30000):
        self.r = client
        self.key = key
        self.ttl_ms = ttl_ms
        self.token = None
        self._stop = threading.Event()

    def acquire(self, timeout_ms=5000):
        deadline = time.time() + timeout_ms / 1000
        while time.time() < deadline:
            token = uuid.uuid4().hex
            if self.r.set(self.key, token, nx=True, px=self.ttl_ms):
                self.token = token
                threading.Thread(target=self._watchdog, daemon=True).start()
                return True
            time.sleep(0.05)
        return False

    def _watchdog(self):
        while not self._stop.wait(self.ttl_ms / 3000):
            lua = ("if redis.call('GET',KEYS[1])==ARGV[1] then "
                   "return redis.call('PEXPIRE',KEYS[1],ARGV[2]) else return 0 end")
            if self.r.eval(lua, 1, self.key, self.token, self.ttl_ms) == 0:
                break   # the lock is gone; stop renewing

    def release(self):
        self._stop.set()
        if self.token:
            release_safe(self.key, self.token)

In production, use a mature implementation rather than thirty lines of your own. A good client library offers the watchdog, a reentrancy counter and pub/sub wake-ups for waiters, all of which are hard to get right by hand.

StrategyMethodFits

Exponential backoff with jitter50, 100, 200 ms, plus randomnessHeavy contention, reduces load on Redis

Version four: Redlock, the most argued algorithm

Version three assumes a single Redis instance, or a primary that is the only writer. The moment failover exists, the lock can be lost: A acquires on the primary, the primary dies before replicating, a replica is promoted without the key, B acquires, and two holders exist.

Redlock's answer is several independent Redis instances, with acquisition succeeding only if a majority grant it within the TTL, and release deleting from each instance.

Why it is so contested

The core objections are two. It depends on system clocks, because validity is decided by elapsed time against a TTL, which assumes clocks roughly agree; a clock jump from an NTP correction or a paused virtual machine breaks that. And it does not solve mutual exclusion under process pauses: a holder that stalls past its TTL after acquiring still writes alongside the next holder, which is the original sin of every TTL-based lock.

The counterargument is that Redlock was never meant to solve process pauses, only to keep mutual exclusion when Redis fails over, and that clock jumps can be managed operationally. Both are right about different layers.

In practice: most teams have not even written the single-instance version correctly, so Redlock is premature. If you use a managed Redis with automatic failover and you need hard mutual exclusion for stock or money, either adopt Redlock or move to a consensus system. For ordinary deduplication, single instance plus version three is enough.

The two things no TTL lock fixes

A pause longer than the TTL

If the holder stalls past its expiry, the lock provides nothing. The fix is a fencing token: every acquisition returns a monotonically increasing number, writes carry it, and the resource layer rejects anything older than what it has already seen.

UPDATE coupon_stock SET stock = stock - 1, fence = 11
WHERE id = 1 AND fence < 11;   -- a stale token cannot write

This is the same idea as sequential nodes in ZooKeeper and Etcd: the lock elects a leader, and the resource layer's version check is what actually prevents concurrent writes. For money and inventory, add this layer.

Locks that are too coarse

Wrapping an entire checkout endpoint in one lock serialises a thousand concurrent requests, and latency goes from fifty milliseconds to two seconds. Three questions: can the key be finer, such as per user and per idempotency key; can the critical section be smaller, moving notifications and logging out of it; and can the lock be avoided entirely?

UPDATE coupon SET stock = stock - 1 WHERE id = 1 AND stock > 0;
-- one affected row means success, zero means sold out, no lock needed

If an atomic operation can solve it, do not use a lock. A lock is the heaviest synchronisation primitive available.

Choosing between Redis, ZooKeeper, Etcd and the database

OptionStrengthAvailabilityPerformanceComplexityFits

The order to think in: can this be done without a lock, with an atomic statement or a unique index? If yes, write SQL. If no, single Redis with version three. If failover has already lost a lock, Redlock or a consensus store. Anything involving money gets a lock plus fencing or a unique constraint.

Checklist and common questions

  • Acquisition is one atomic command, not a set followed by an expire.
  • The token is random per acquisition, and the unlock compares and deletes atomically.
  • The TTL is sized for crash recovery, around thirty seconds, and long work is covered by renewal rather than a bigger TTL.
  • The critical section holds only what must be serialised; IO goes outside.
  • Lock keys carry a business prefix and a version, so a redesign can move to a new namespace.
  • Acquisition has a timeout and backoff rather than spinning.
  • Failover behaviour has been evaluated for anything that cannot tolerate a lost lock.
  • Money and stock have a database-level backstop, a conditional update, a unique constraint or a fence column.
  • Wait time and acquisition failure rate are monitored, not just Redis uptime.
  • Both failure modes, holder crash and work exceeding the TTL, have been tested.

Closing

Three sentences. Acquisition atomic, release atomic. Short TTL with renewal, and keep the lock as narrow as possible. Where losing the lock is unacceptable, the lock only elects a leader, and the resource layer's fencing or unique constraint is what actually keeps the data correct.

Next time someone says "just add a Redis lock", ask the five questions: is the naive version still in the code, is the unlock a script, what is the TTL, what happens on failover, and is there a database backstop. All five answered, and the lock is real.
