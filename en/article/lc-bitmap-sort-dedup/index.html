Sorting and deduplicating a billion integers: one bitmap, 119 MiB instead of 4 GB

2026-09-18 · 13 min · Stack Frame

The problem

A billion unordered integers, limited memory, and the requirement to sort and deduplicate them. If only the count of distinct values is wanted, it is a distinct-counting problem. The follow-up asks how to identify which values repeat and which appear exactly once.

This is where bitmaps shine, and it is asked constantly because it tests a shift in thinking rather than a clever algorithm: when integers are bounded, the value range itself can serve as storage.

Trading range for space

Do the arithmetic first. A billion 32-bit integers held as they are occupy four gigabytes, which most machines cannot spare. A hash set is worse, since each element needs a boxed object, a reference and a node, tens of bytes each, so a billion of them is tens of gigabytes.

But the values are bounded. If they range over a billion possibilities, one bit per possible value is enough to record whether it occurred, and that costs a hundred twenty-five million bytes, about a hundred nineteen mebibytes.

That fits comfortably, and it incidentally solves both other requirements. Deduplication is free because a bit can only be set once, so a repeat finds the bit already on. Ordering is free because scanning bit indices ascending emits sorted output.

The compression ratio here is thirty-two to one, since each possible value is represented in a single bit rather than four bytes. A bitmap is not a sorting algorithm; it is a storage decision that trades the size of the value range against the volume of data, and sorting and deduplication are by-products.

The one-bit version

class BitMap:
    def __init__(self, size: int):
        self.size = size
        self.words = [0] * ((size + 31) // 32)

    def add(self, v: int) -> None:
        self.words[v >> 5] |= 1 << (v & 31)

    def contains(self, v: int) -> bool:
        return (self.words[v >> 5] >> (v & 31)) & 1 == 1

    def sorted_distinct(self) -> list[int]:
        return [v for v in range(self.size) if self.contains(v)]

Three steps: set the bit, test it, and scan in index order. Walking a small example, a repeated value lands on a bit that is already set, so the second occurrence does nothing at all, and deduplication happens without a comparison, a hash, or any extra space.

The two-bit version

One bit only distinguishes presence. To identify which values repeat and which appear once, add a second bit and treat the pair as a state: unset, seen once, seen multiple times, with the fourth state reserved as a safety fallback.

Current stateAnother occurrenceAction
00First sightingBecome 01
01Second sightingBecome 10
10Third and beyondStay
11ReservedFall back to 10
 
def add(self, v: int) -> None:
    cur = self._state(v)
    if cur == 0b00:
        self._set(v, 0b01)
    elif cur == 0b01:
        self._set(v, 0b10)
    elif cur == 0b11:
        self._set(v, 0b10)

Note that the states are not a counter. A counter would overflow on the fourth occurrence, while this only needs to separate once from many, and the many state is a bin that accepts anything.

The cost is double the space, in exchange for three answers from one scan: which values appeared, which repeated, and which appeared exactly once.

The bit operations

word = v >> 5
bit  = v & 31
words[word] |= 1 << bit
(words[word] >> bit) & 1 == 1
words[word] &= ~(1 << bit)

For thirty-seven, the word is one and the bit is five, since thirty-seven is one times thirty-two plus five. The thirty-two bits inside a word are independent, which is what makes a single-bit update safe.

Engineering details worth stating: negative values must be shifted by subtracting the minimum, or the index goes negative; endianness is irrelevant because addressing is by value rather than layout; the word size is a platform detail, and sixty-four-bit words address more coarsely and behave better in cache; and scanning can be accelerated by skipping whole zero words and by counting population for a distinct count, which is thirty-two times fewer operations per word.

When the range explodes

The premise is a bounded, modest range. When it fails, the answer is to reduce and partition. Sixty-four-bit values or identifiers have a range whose bitmap would exceed any storage, so bucket by high bits to disk, build a bitmap per bucket, and merge in order; or partition by hash at the cost of losing the natural ordering; or use a Bloom filter, which answers only membership with false positives and cannot emit results; or fall back to external sorting, which is the general answer and of which the bitmap is the bounded special case.

Across machines, shard by value range, build independent bitmaps, and concatenate in shard order, since deduplication and ordering hold at the shard boundary.

If only the count is needed, sum the population counts over words without emitting any sequence.

The two terms in the time bound are separate: the data volume and the range. At a billion values over the same range they are of the same order, giving roughly two billion basic operations, against thirty billion comparisons for a comparison sort, and the constants for comparison and swapping are far worse than setting a bit.

The deciding ratio is range divided by volume. Comparable magnitudes favour a bitmap with a thirty-two to one saving; a range far larger than the volume is a heavy loss, since a hundred values scattered across the full 32-bit range would cost half a gigabyte; and 64-bit scenarios rule bitmaps out entirely, pushing you to partitioning or external sorting.

Five mistakes, each genuinely fatal

  1. Assigning instead of or-ing when setting a bit, which wipes the whole word. Setting zero then five leaves only five.
  2. Omitting the complement when clearing, which clears every other bit in the word too.
  3. Not offsetting negative values, which produces a negative index.
  4. Choosing a bitmap without computing the range. A bitmap over phone numbers needs eleven gibibytes, more than the original data.
  5. Asking a one-bit bitmap how many times a value appeared, which is unanswerable by construction. The follow-up is not a code change, it is a data structure change.

How to answer it

The short version: the raw array is four gigabytes but the range is bounded, so one bit per possible value costs about a hundred nineteen mebibytes. Setting bits gives deduplication for free and scanning in index order gives sorted output, in linear time over volume plus range and linear space over range, a thirty-two to one saving. Then add the bit operations with their two landmines, the two-bit extension, and the escape hatches for unbounded ranges, noting that a bitmap is a special case with a bounded domain rather than a universal tool.
