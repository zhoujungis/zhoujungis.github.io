LSM-Tree vs B+Tree: How Many Times Does One Write Actually Hit the Disk?

2026-11-13 · 28 min · Stack Frame

Who this is for: people who have written a KV store or are currently picking a storage engine; people who were persuaded by one-line verdicts like "LSMs write fast, B+trees read fast" without ever looking at the ledger; people choosing between SQLite, RocksDB, LevelDB and InnoDB who want to know which layer the cost actually lands on Verdict up front: a B+tree spreads random writes into "random page writes"; an LSM turns random writes into "sequential append + background rewrite". The former's write amplification depends on how many pages each transaction touches, the latter's on how many levels compaction rewrites. Neither comes with a free lunch — only a choice about whether to put the cost on the write path, the read path, or a background thread. 1. Two Counterintuitive Observations

Start with the first set of numbers. 1,000,000 records, keys are 24-byte user:%016d, values are 100 bytes of incompressible random data — roughly 124 MB of logical data in total. Written in random order, committing every 500 records:

Engine Write time Logical throughput Process bytes written Write amplification Database size
SQLite (B+tree, WAL) 201.6 s 0.62 MB/s 12822.9 MB 103.4× 149.9 MB
RocksDB (LSM) 4.0 s 30.7 MB/s 584.7 MB 4.7× 116.4 MB

For the same data, SQLite is about 50× slower and writes 103× the logical bytes to disk; RocksDB writes only 4.7×. But the second set of numbers immediately breaks the impression that "LSMs are faster at everything": change the write order to an ascending sequential append and SQLite needs only 4.7 seconds, with write amplification down to 2.9× — essentially in the same league as RocksDB's 2.8 seconds and 2.0×.

The third observation is subtler still: over 50,000 random reads, SQLite's p50 is 25.2 µs and p99 is 135 µs; RocksDB's p50 is 29.7 µs and p99 is 119 µs. Read latency is nearly identical, even though an LSM theoretically has more levels to probe.

All three observations point at the same conclusion: the performance gap isn't in the word "tree" — it's in where the write path puts the randomness, and whether the log records a whole page or a change. Let's open up the ledger and do the arithmetic.

2. Experiment Setup and Metric Definitions

First, the reproducible conditions, written down plainly. Every number comes from a single Windows 11 (build 26200) machine: Intel Core 5 210H, 8 cores / 12 threads, 15.5 GB of RAM, NTFS; Python 3.13.14, SQLite 3.50.4, RocksDB driven through rocksdict 0.3.29, process I/O sampled with psutil 7.2.2.

The workload comes from a single generator:

import hashlib, random

N = 1_000_000
keys = list(range(N))
random.shuffle(keys)          # or keep 0..N-1 for the sequential control run
keys = [f'user:{i:016d}'.encode() for i in keys]

def value(k):
    return hashlib.shake_128(k).digest(100)   # 100 bytes, incompressible

Writes commit every 500 records. SQLite uses a WITHOUT ROWID table, guaranteeing a single B+tree clustered on the key; the settings are journal_mode=WAL, synchronous=NORMAL, page_size=4096, cache_size=256 MB. RocksDB runs default compression with write_buffer_size=4 MB, max_write_buffer_number=3, target_file_size_base=8 MB, max_background_jobs=4; the memtable was shrunk on purpose so that multi-level compaction actually shows up at 124 MB of data, instead of parking the whole dataset in one giant memtable.

Three metrics, defined precisely:

  • Write amplification (WA): bytes written by the process ÷ logical bytes. Process bytes include the WAL, the data files and compaction output, but not filesystem metadata. It's closer to the real write path than "how much did the database file grow" — but it is still not physical writes at disk-granularity level.
  • Read amplification (RA): bytes read from storage per point lookup, on average. Because there was no administrator privilege to drop the OS page cache, this number is cache-affected; it's valid for same-machine comparison, not for cross-machine comparison.
  • Space amplification (SA): total database file size ÷ logical data size. It answers "how much disk does the same data occupy".

The limitations, up front too: single-threaded client, single machine, Windows, incompressible values, SQLite's WAL recording full page images, RocksDB with block compression enabled. The last two in particular decide this: the 103× below cannot be extrapolated to InnoDB. InnoDB's redo log records in-page changes; it does not write a fresh 16 KB image of every dirty page on every transaction. Its write path is closer to "record which bytes changed" than to SQLite WAL's "record what the whole page now looks like". We'll come back to this separately later in the article.

3. The B+tree Write Path: Pages, Splits and Full-Page WAL

The B+tree write path compresses into one sentence: find the leaf page the key belongs to and modify it; if the page is full, split it; log every change first, then write the data file back at checkpoint.

SQLite's page size is 4096 bytes. After the page header, the cell pointer array and free space, a leaf page holds roughly twenty-odd 124-byte records. The 1,000,000 records end up in about 36,000 leaf pages; including internal nodes, the database file comes to about 150 MB, which matches the measured 149.9 MB.

Under random insertion, 500 keys land on almost 500 distinct leaf pages. When a transaction commits, the WAL has to append one frame for every modified page: a 24-byte frame header plus a full 4096-byte page image. SQLite's WAL format is spelled out clearly in the official documentation — the frame header carries the page number, the database size in pages after commit, a salt and a checksum, and the frame data is one complete page. Recovery scans the WAL sequentially once, validates frame by frame, and stops at the first bad checksum. That design makes WAL writes very direct, and makes the WAL brutally unfriendly to small random transactions.

Here's a rough estimate that's good enough to make the point: each transaction touches about 500 leaf pages, plus new pages from splits, parent node updates and freelist pages — call it 600 pages conservatively, at 4 KB each, so 2.4 MB written per transaction and 4.8 GB across 2000 transactions. The observed figure is 12.8 GB. The extra comes from page splits (a split allocates a page and rewrites the parent), from checkpoint copying WAL content back into the main database (the same pages written a second time), and from the WAL itself being reused over several rounds. The order of magnitude lines up perfectly.

Which also explains why sequential writes are fast: keys increase monotonically, so each write touches only the rightmost leaf page and a few internal pages, and a transaction's dirty page count drops from 500 to single digits. Measured write amplification falls from 103.4× to 2.9×, and elapsed time from 201 s to 4.7 s. A B+tree isn't afraid of writes; it's afraid of "one transaction touching many random pages".

Put that into a formula:

WA_btree ≈ (average number of distinct pages touched per transaction × page size)
           ÷ (logical bytes written per transaction)

Random, 500 records: 500 × 4096 / (500 × 124) ≈ 33; stack splits and duplicate checkpoint writes on top of that and 100× is no surprise. Sequential, 500 records: 2 × 4096 / (500 × 124) ≈ 0.13; now WAL frame headers, commit overhead and checkpoint become the main cost, landing around 3× overall.

Swap in InnoDB and the "page size" in that formula is still 16 KB, but "pages touched per transaction" gets rewritten by the buffer pool and the change buffer: random inserts into secondary indexes can be recorded in the change buffer and merged when the page is read in, and redo records in-page changes rather than a full page image per transaction. So InnoDB's random write amplification is usually far below SQLite WAL's 100×. That's an implementation difference, not a theoretical floor for B+trees.

4. The LSM Write Path: memtable, SST and Compaction

An LSM's write path also compresses into one sentence: every write appends to the WAL, then enters the in-memory memtable; when the memtable fills up it's frozen and flushed sequentially into an L0 SST file; background compaction then merges L0 downward level by level.

Take LevelDB: a handful of key constants define its shape. Four L0 files trigger a compaction; a write backlog of 8 starts slowing writes and 12 stops them outright; each level's capacity is 10× the one above; the SST target size is 2 MB. RocksDB's defaults are larger (64 MB memtable, 64 MB target file, 256 MB base level capacity) but the mechanism is identical. To actually see compaction at 124 MB of data, we dropped the memtable to 4 MB.

An LSM's write amplification decomposes into three parts:

WA_lsm = WA_wal + WA_flush + WA_compaction
  • WAL: each record appended once, roughly 1× the logical bytes (plus frame header overhead).
  • flush: when the memtable fills, it's written out wholesale as an L0 file, roughly 1×.
  • compaction: L0 merges with the next level down and emits new files; that level then merges with the one below it. Every record gets rewritten once per level.

If level capacity grows by a factor of T, the amortized write amplification of each level's compaction is about 1 / (1 - 1/T) — roughly 1.11 at T=10. For data spanning L levels, total compaction write amplification is roughly L × T/(T-1). The more data and the more levels, the more expensive this part gets.

Measured in this run (random writes):

Component RocksDB statistics
WAL 0.12 GB
flush 0.109 GB
compaction writes 0.43–0.50 GB
Total process writes 0.58–0.66 GB
Logical data 0.124 GB
Measured WA 4.7–5.3

With sequential writes, compaction does almost no reading: the newly written keys are already in order and L0 files don't overlap, so merging just moves files down a level. Measured compaction writes drop from 0.43 GB to 0.11 GB and total WA from 4.7 to 2.0. An LSM's advantage on sequential writes comes from having "no random pages"; its advantage on random writes comes from "deferring the randomness to background compaction", not from abolishing it.

5. The Write-Amplification Formula: Which Layer Is Really Paying

Put both engines on the same ledger:

Cost item B+tree (SQLite WAL) LSM (RocksDB)
Logging one full 4 KB page per dirty page one append per record
Data persisted checkpoint writes dirty pages back memtable flushed sequentially to L0
Extra rewriting page splits, duplicate checkpoint writes compaction rewriting level by level
Cost of random writes dirty pages per transaction × page size bandwidth and CPU of background compaction
Cost of sequential writes very small very small
Latency profile write latency directly tied to dirty page count write latency steady, compaction can cause spikes

One easily overlooked point: write amplification isn't just "wearing out the disk". It consumes page cache, filesystem writeback bandwidth and SSD endurance all at once. Of SQLite's 12.8 GB of writes, only 124 MB was new data that actually needed to be kept; the rest was the same set of pages in different versions at different moments. For a read-mostly blog database that's a non-issue; for an ingestion service taking thousands of random writes per second, it's longevity and money.

Conversely, LSM compaction isn't free either. It occupies background threads and disk bandwidth and can compete with foreground reads; L0 files piling up trigger write stalls; the deeper the levels, the more bytes a single compaction has to rewrite. RocksDB exposes max_background_jobs, level_zero_slowdown_writes_trigger, max_bytes_for_level_base and friends — all of which are, at bottom, knobs for balancing write amplification, read amplification, space amplification and tail latency against each other.

5.5 Two Knobs: Commit Batch Size and Value Size

Write amplification isn't a fixed constant; two very ordinary parameters move it significantly — how many records per commit, and how big each value is. Plenty of tuning sessions stare only at engine parameters and skip these two entirely.

Commit batch size first. Fix 100,000 random keys and 100-byte values, and change only the number of records per batch:

Records per batch SQLite WA SQLite throughput RocksDB WA RocksDB throughput
1 95.8× 1.56 MB/s 3.04× 10.75 MB/s
10 94.5× 1.74 MB/s 2.91× 35.38 MB/s
100 86.5× 2.05 MB/s 2.89× 43.04 MB/s
1000 59.0× 2.68 MB/s 2.89× 51.91 MB/s

SQLite's write amplification falls from 95.8× to 59.0×, but with no change in order of magnitude. The reason is the same as before: what drives the cost is "how many distinct pages one transaction touches", not "how many records one transaction contains". Even committing 1000 random keys at once still touches nearly a thousand leaf pages, and each page still costs a full frame. Batching reduces the commit count, WAL frame headers and sync overhead — so throughput improves only modestly.

RocksDB's write amplification barely moves (2.89–3.04×), yet throughput climbs from 10.75 MB/s to 51.91 MB/s. Because the LSM write path is sequential appends to begin with, batching mainly removes the fixed per-write overhead; compaction's workload is set by data volume, not by commit count.

Now value size. Fix 200,000 records at 500 per batch, and change only the value length:

Value size SQLite WA SQLite SA RocksDB WA RocksDB SA
10 B 163.1× 1.22× 1.64× 0.58×
100 B 83.8× 1.21× 3.42× 0.94×
1000 B 27.4× 4.58× 4.55× 1.00×

Small values push SQLite's write amplification to 163×: a 34-byte record still occupies a 4 KB page frame, so the WAL's page-header overhead is a hundred times the record itself. As values grow, fewer records fit per page and each transaction touches fewer pages, so write amplification actually falls; but 1000-byte random inserts shatter the B+tree into finer fragments and space amplification shoots to 4.58× — a 938 MB database file holding only 205 MB of logical data. That's the textbook trade: write amplification down, space amplification up.

RocksDB trends the opposite way: the bigger the value, the more bytes compaction rewrites, so write amplification climbs from 1.64 to 4.55; but SST space utilization stays steady around 1×, with none of SQLite's fragmentation blow-up. The two curves point in different directions, which is exactly why you can't tune against a single metric.

6. The Read Path: Tree Height, Bloom Filters and Read Amplification

A B+tree point lookup is a single descent from root to leaf. With 1,000,000 records at about 30 per page, the tree is roughly 4 levels tall (root, two internal levels, leaf). If the buffer pool holds the upper nodes, a lookup really needs just one leaf page read; worst case is four page reads. Range scans are where it wins outright: leaf pages are linked to one another, so you just read forward.

An LSM point lookup probes the memtable, then the immutable memtable, then several L0 files, and finally does a binary search within each level. Without a Bloom filter, a lookup for a missing key may read a lot of files; with one, most files can be ruled out by a single in-memory check. RocksDB builds a Bloom filter for every SST by default; LevelDB requires an explicit FilterPolicy.

Measured over 50,000 random lookups of keys that exist:

Engine p50 p99 Total disk read Disk read per lookup
SQLite (database after random writes) 25.2 µs 135.0 µs 115.6 MB 2.3 KB
RocksDB (database after random writes) 29.7 µs 119.4 µs 414.2 MB 8.3 KB
SQLite (database after sequential writes) 19.0 µs 106.7 µs 114.9 MB 2.3 KB
RocksDB (database after sequential writes) 15.3 µs 57.6 µs 189.6 MB 3.8 KB

The column most worth staring at here is "disk read per lookup": the B+tree reads about 2.3 KB each time, essentially one page; the LSM after random writes reads 8.3 KB, a bit more than two pages — meaning the Bloom filter eliminated most files but a few still had to be genuinely read. p99 is not notably worse either, because the LSM's levels stay shallow and its block cache hit rate is decent; the real read amplification shows up in the number of bytes read and the CPU spent merging iterators, not in per-lookup latency.

Range scans are a different matter. A B+tree walks forward along the leaf linked list, which is prefetch-friendly; an LSM has to open iterators across several levels and merge them, costing more CPU, though the sequential I/O is still fine. For workloads that "pull a batch of events in a time range", LSMs often do very well, because data is ordered by key and the range is contiguous.

7. Updates and Deletes: In-Place Modification vs Tombstones

Updates are where the gap between the two engines most easily flips. A B+tree usually updates in place: find the record, change the value, mark the page dirty. An LSM doesn't modify in place — it appends a new version, and the old version is discarded only when compaction merges down to a deeper level. Deletes work the same way: the LSM writes a tombstone and keeps it until compaction clears it together with the old value.

After the 1,000,000 random writes, we run another 200,000 random updates (each updating a 100-byte value, committing every 500):

Engine Update time Update throughput Bytes written by updates Update write amplification
SQLite (WAL) 21.04 s 1.18 MB/s 1621.7 MB 65.4×
RocksDB 0.75 s 33.21 MB/s 169.7 MB 6.8×

SQLite's update write amplification is even higher than its insert amplification, because every update touches an existing leaf page and the WAL must write a full new page image; 500 updates can touch 500 pages, which is 2 MB of WAL per transaction. RocksDB writes the new version first and lets compaction merge it; the write path is fast, but compaction will rewrite the files containing the old versions in the background. An LSM doesn't skip the write on update — it defers it and does it in batches.

Implementation differences once more: an InnoDB update writes undo records and modifies the clustered index page, with redo recording in-page changes; random secondary index updates can also go through the change buffer. Its update write amplification is nothing like SQLite WAL's straightforward "dirty pages × 16 KB". Taking this article's SQLite numbers to argue that "all B+tree updates are 30× slower" is a bad extrapolation.

8. Space Amplification: File Size Doesn't Lie

Metric SQLite RocksDB
Logical data 124.0 MB 124.0 MB
Database size 149.9 MB 116.4 MB
Space amplification 1.21× 0.94×

SQLite's 1.21× comes from free space inside pages, half-full pages left behind by splits, and B+tree internal nodes. Random inserts lower page fill factor; the sequentially inserted database is 146.5 MB, slightly smaller but essentially the same. VACUUM can rebuild the database and reclaim fragmentation, at the price of extra space and time.

RocksDB's 116.4 MB is smaller than the logical data, thanks to block compression (even with incompressible random values, keys, block headers and indexes still compress) and SST's compact encoding. LSM space amplification is not constant: during compaction the input and output files coexist, so instantaneous space can approach 2×; in delete-heavy or update-heavy databases, old versions keep occupying space until compaction catches up. RocksDB controls that window with max_background_jobs and compaction priorities, but it can't eliminate it.

One frequently overlooked entry on the ledger: space amplification feeds back into read amplification — the more files there are and the deeper the levels, the more files a point lookup has to probe. Tuning an LSM is fundamentally a triangular trade among the three amplifications; you can't watch only one of them.

9. When to Pick an LSM, When to Pick a B+tree

Turning the conclusions into a table, under the premise of "same hardware, same data, single-node embedded or single-instance":

Workload characteristic Better fit Why
High-frequency random writes, more writes than reads LSM append-only writes plus background compaction, steady foreground latency
Append-only logs, events, time-series data LSM shortest sequential write path, compaction can partition by time
Read-heavy, write-light, mostly point lookups B+tree one tree descent, stable read amplification
Complex range queries, sorting, joins B+tree leaf linked list, ordered scans, mature optimizer
Strong transactions, cross-table consistency B+tree (InnoDB) row locks, MVCC, undo, a complete foreign-key ecosystem
Write throughput first, background jitter acceptable LSM compaction is tunable, write stalls are observable
Limited ops headcount, modest data volume B+tree no compaction tuning, no write stalls
Predictable p99 required Depends on tuning LSM's p99 is shaped by compaction, B+tree's by checkpoint

A few common misconceptions:

  1. "An LSM is always faster at writing than a B+tree." Only true for random writes, batched commits and moderately sized values. On sequential writes the two are close; with small single-record transactions, the WAL's fsync dominates.
  2. "A B+tree always reads faster." Point lookup latency depends on cache and tree height, and with a Bloom filter the LSM gap is tiny; the B+tree is steadier on range scans, but the LSM's sequential I/O isn't bad either.
  3. "Write amplification only affects SSD lifespan." It also affects write throughput, checkpoint spikes and backup windows. 103× write amplification means the same logical writes consume 103× the write bandwidth.
  4. "SQLite's numbers represent InnoDB." SQLite WAL's full-page images are an implementation choice, not an inevitable consequence of B+trees. When choosing, look at the specific engine's log format, buffer pool and change buffer.

9.5 Three Selection Walkthroughs on Real Workloads

Comparing "LSM vs B+tree" in the abstract is easy; once you land on a concrete system it's rarely black and white. Here are three typical workloads walked through the decision, still using the measurements from earlier.

Scenario one: 200,000 monitoring events written per minute, queried by time range over the last hour.

Writes are append-style with mostly monotonic keys and values from tens to hundreds of bytes; queries are time-range scans with the occasional tag filter. This workload is very friendly to an LSM: the sequential write path is shortest, compaction can partition by time, and range scans follow the ordered keys. A B+tree can do it too, but random primary keys or a time index still cause page splits; if each batch of events lands across many index pages, SQLite-style full-page WAL will push write amplification into the tens of times.

Two things to watch if you pick an LSM: first, stagger compaction away from query traffic, otherwise background rewrites will steal I/O; second, expire old data outside the retention window promptly with a TTL, otherwise compaction keeps doing useless work for historical data. With a B+tree, focus on partitioning/sharding and index maintenance, so a single table doesn't grow without bound.

Scenario two: a user-profile KV store, reads far outnumbering writes, with a stable p99 requirement.

The typical operation is GET user:<id>; writes are the occasional profile update, reads dominate, values are a few KB. This workload fits a B+tree better: one tree descent fetches the record and read amplification is stable; updates are in-place, so no pile of old versions accumulates in the background. InnoDB's buffer pool keeps hot pages in memory, and secondary index updates can go through the change buffer.

If you insist on an LSM, you must configure the Bloom filter properly, give the block cache enough memory, and accept that reads pull more bytes. For services extremely sensitive to p99, LSM compaction jitter has to be suppressed with rate limiting and priorities; otherwise a single large compaction can push read latency up.

Scenario three: an order database with strong transactions, multi-table relationships, and complex queries by status and date.

This one is barely a decision: pick a B+tree engine with full transaction support and a mature optimizer, usually InnoDB or PostgreSQL. Not because B+trees are innately faster, but because row locks, MVCC, undo, foreign keys, joins and subqueries represent years of engineering. An LSM can do KV and single-table transactions, but complex queries and cross-row consistency are not its home turf.

What really deserves caution: don't migrate an order database to an LSM just because "write volume went up", while ignoring transaction semantics, secondary indexes and reporting queries. Write bottlenecks have many remedies — batching, partitioning, going asynchronous, adding caches — and changing the storage engine is usually the most expensive option with the hardest rollback.

The common thread across the three: first pin down what reads and writes look like, where the transaction boundaries are, and what the p99 budget is; then talk about engines. Engine selection is the last step, not the first.

10. Source Map: From One put to One fsync

If you only want to remember a few entry points, read along this map:

SQLite (B+tree)

  • btree.c: sqlite3BtreeInsert locates the cursor position and writes the cell; when a page is full, balance_nonroot performs splits and redistribution.
  • pager.c: pager_write marks pages dirty, and sqlite3PagerCommitPhaseOne writes the log during the commit phase; rollback mode writes a journal, WAL mode hands dirty pages to the WAL.
  • wal.c: sqlite3WalFrames/walFrames write each dirty page as "24-byte frame header + the whole page"; the commit frame records the database size in pages in its header.
  • Recovery: one sequential scan of the WAL, frame-by-frame validation, stopping at the first bad checksum; mxFrame takes the last valid commit frame.

LevelDB / RocksDB (LSM)

  • DBImpl::Write: writes the WAL, writes the memtable; MakeRoomForWrite freezes the memtable when it fills and triggers a flush.
  • VersionSet::PickCompaction: selects a compaction based on L0 file count, bytes per level and file overlap.
  • DBImpl::BackgroundCompaction: merges the input files and writes the next level's SSTs; TableBuilder handles blocks and indexes.
  • Bloom filter: LevelDB's FilterPolicy, RocksDB's FullFilterBlockBuilder — they push the "this key isn't in that file" decision into memory.

InnoDB (for contrast; do not extrapolate this article's numbers to it)

  • The clustered index is the table; secondary index leaves store the primary key. Updates write undo, redo records in-page changes, and the change buffer absorbs random secondary index writes.
  • Crash recovery: tablespace discovery → redo apply → roll back uncommitted transactions → change buffer merge → purge. The official documentation states plainly that rolling back an interrupted transaction can take three to four times as long as the transaction itself ran.
  • Half-written pages are protected by the doublewrite buffer: pages are first written sequentially into the doublewrite area and fsynced, then written to the data file; on recovery a complete copy repairs the torn page.

11. Reproducing the Experiment: Scripts, Parameters and Pitfalls

The core script isn't long; the important part is keeping "writing" and "measuring" separate:

import hashlib, os, random, sqlite3, time
import psutil
from rocksdict import Rdict, Options, WriteBatch

N, BATCH = 1_000_000, 500
keys = [f'user:{i:016d}'.encode() for i in range(N)]
random.shuffle(keys)

def value(k):
    return hashlib.shake_128(k).digest(100)

def io_write():
    return psutil.Process().io_counters().write_bytes

# SQLite
con = sqlite3.connect('bench.db')
con.execute('PRAGMA journal_mode=WAL')
con.execute('PRAGMA synchronous=NORMAL')
con.execute('PRAGMA page_size=4096')
con.execute('CREATE TABLE kv(k TEXT PRIMARY KEY, v BLOB) WITHOUT ROWID')
start, t0 = io_write(), time.perf_counter()
for i in range(0, N, BATCH):
    con.executemany('INSERT INTO kv(k,v) VALUES(?,?)',
                    [(k, value(k)) for k in keys[i:i+BATCH]])
    con.commit()
con.execute('PRAGMA wal_checkpoint(TRUNCATE)')
print('sqlite', time.perf_counter()-t0, io_write()-start)

# RocksDB
opt = Options()
opt.set_write_buffer_size(4 * 1024 * 1024)
opt.set_max_write_buffer_number(3)
opt.set_target_file_size_base(8 * 1024 * 1024)
db = Rdict('bench-rocks', options=opt)
start, t0 = io_write(), time.perf_counter()
for i in range(0, N, BATCH):
    wb = WriteBatch()
    for k in keys[i:i+BATCH]:
        wb[k] = value(k)
    db.write(wb)
db.flush()
print('rocks', time.perf_counter()-t0, io_write()-start)

Three pitfalls we hit along the way:

  1. Values must be incompressible. The first experiment built 100-byte values by concatenating sha256(k) repeatedly, and RocksDB's block compression squeezed 124 MB down to 45 MB, distorting both write and space amplification. Only after switching to shake_128(k).digest(100) were the numbers comparable.
  2. Process I/O counters are not physical disk writes. They count the read/write bytes issued by the process, including the WAL, data files and compaction, but not filesystem metadata or the SSD's internal write amplification. They're reliable for same-machine comparison; leave headroom when doing absolute capacity planning.
  3. You must wait for compaction to settle. Reading the counters immediately after RocksDB finishes writing will miss compaction still running in the background. The script polls the compaction lines of rocksdb.stats and only samples the numbers once two consecutive reads are identical.

Also note that SQLite's random-write elapsed time varies widely between runs (140–202 seconds this time). Windows writeback, antivirus scanning and disk cache state all influence the result; write amplification stays stable at around 103×, so read the timings as a trend rather than a precise benchmark.

12. Wrap-up: Asking the Right Question

Back to the question we started with: how many times does a single write actually hit the disk?

  • B+tree + full-page WAL: as many pages as one transaction touches, that's how many pages get written; small random transactions push write amplification into the tens or hundreds.
  • LSM: each record is appended to the WAL once, then flushed to L0, then rewritten level by level during compaction; write amplification depends on the number of levels and the compaction policy.
  • Reads: one descent for a B+tree, with stable read amplification; an LSM uses a Bloom filter to keep most files out of the picture in memory, but it still reads more bytes.
  • Space: a B+tree carries in-page fragmentation, an LSM carries old versions and compaction's temporary files; both need maintenance.

So the question worth asking isn't "which is faster, an LSM or a B+tree", but:

  1. Are my writes random or sequential? How big are my transactions?
  2. Would I rather tolerate foreground write-latency jitter, or background compaction jitter?
  3. Are my reads mostly point lookups or range scans? What's my p99 budget?
  4. Which specific engine am I using? Does its log record whole pages or changes? Does it have a buffer pool, a change buffer, doublewrite?
  5. Can I monitor write, read and space amplification, and tune before they get out of hand?

Answer these five and the selection basically settles itself. As for "which one is more advanced" — that's a question for papers, not for production.
