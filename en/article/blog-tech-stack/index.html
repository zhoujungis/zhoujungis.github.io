How This Blog Is Built: Vue 3 + Django With a Decoupled Frontend

2026-07-07 · 13 min · Stack Frame

Introduction

I had wanted a technical blog of my own for a long time — a place to write down what I learn and to trade notes with people who care about the same things. After a fair amount of tinkering, it is finally live. This post goes through the architecture, how the core features are built, and how the whole thing is deployed, in the hope that it saves a few detours for anyone putting together a personal blog.

Architecture at a Glance

The blog is built as a decoupled frontend and backend architecture, with each side deployed on its own platform:

Why These Choices?

  • Vite over Webpack: near-instant cold start from an ESM dev server, HMR that lands in milliseconds
  • Pinia over Vuex: a smaller API surface, first-class TypeScript, better tree-shaking
  • Vditor: a Markdown editor with three modes — WYSIWYG, instant rendering and split preview — plus built-in code highlighting and math typesetting

The API Layer

A single Axios instance wraps the shared request and response interceptors:
  • Request interceptor: reads the JWT out of localStorage and attaches it to every request header
  • Response interceptor: on a 401 it clears the token and redirects to the login page
const client = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000/api/',
})

// attach the JWT automatically
client.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// handle 401s in one place
client.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      localStorage.removeItem('token')
      window.location.href = '/admin'
    }
    return Promise.reject(error)
  },
)

The Data Model

At the center sits the Article model, with four states — draft, published, archived and scheduled: 
class Article(models.Model):
    class Status(models.TextChoices):
        DRAFT = "draft", "Draft"
        PUBLISHED = "published", "Published"
        ARCHIVED = "archived", "Archived"
        SCHEDULED = "scheduled", "Scheduled"

    title = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    content = models.TextField()              # raw Markdown
    html_content = models.TextField(editable=False)  # rendered HTML
    excerpt = models.TextField(editable=False)       # generated excerpt
    category = models.ForeignKey(Category, ...)
    tags = models.ManyToManyField(Tag, ...)
    status = models.CharField(max_length=16, choices=Status.choices)
    is_top = models.BooleanField(default=False)       # pinned to the top
    views_count = models.PositiveIntegerField(default=0)
    likes_count = models.PositiveIntegerField(default=0)
    cover_image = models.URLField(blank=True)
    scheduled_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
Saving an article triggers all of the following automatically:
  1. Markdown → HTML: handled by Python-Markdown with the code highlighting, table and TOC extensions switched on
  2. Auto excerpt: strips the Markdown syntax and keeps the first 50 words
  3. Scheduled publishing: once the appointed time arrives, the status flips from scheduled to published

RESTful API Design

The API follows REST conventions through DRF's ViewSet + Router: 
GET    /api/articles/               article list (pagination, search, category/tag filters)
GET    /api/articles/{slug}/        article detail (bumps the view counter)
GET    /api/categories/             category list (with article counts)
GET    /api/tags/                   tag list (with article counts)
POST   /api/articles/{slug}/like/   like an article (deduplicated by cookie)
POST   /api/subscribe/              email subscription
POST   /api/token/                  JWT login, returns tokens
POST   /api/token/refresh/          refresh the access token
POST   /api/admin/articles/         create an article (auth required)
PUT    /api/admin/articles/{id}/    update an article (auth required)
DELETE /api/admin/articles/{id}/    delete an article (auth required)
API hardening: - Rate limiting: 30 requests per minute for anonymous users, 100 for authenticated ones, 3 for comments and 5 per hour for subscriptions - JWT auth: access tokens expire after 60 minutes, refresh tokens after one day - CORS: only the frontend origin may call the API

Smart Relations on the Article Detail Endpoint

The detail endpoint does more than return the body — it works out the article's neighborhood in the same pass:
  • Previous and next article: context navigation ordered by publish date
  • Related articles: matched on shared tags, three at most
  • Reading-time estimate: (characters + English words) ÷ 250 gives the minute count

Frontend Deployment

deploy.sh is a script that automates the whole frontend deploy: 
#!/bin/bash
set -e

# 1. Build the Vue app
npm run build

# 2. Copy the build output to the repo root (GitHub Pages serves from there)
cp -r dist/* ../

# 3. Copy the Live2D assets (if any)
if [ -d "../public-live2d" ]; then
  cp -r ../public-live2d/* ../live2dw/
fi

# 4. Commit and push to GitHub
git add -A
git commit -m "deploy: update site $(date +%Y-%m-%d_%H:%M)"
git push origin master
A few deliberate choices: - GitHub Pages serves from the repository root, so the build output has to be copied there - Source lives under frontend/, build output lives at the root, and .gitignore keeps the two apart - A deploy is one git commit + push — small and auditable

Backend Deployment

The backend runs on PythonAnywhere's free plan and is driven from the Web console: 
cd ~/zhoujungis.github.io/backend
git pull origin master           # pull the latest code
source venv/bin/activate         # activate the virtualenv
pip install -r requirements.txt  # install dependencies (if anything changed)
python manage.py migrate         # run migrations (if models changed)
python manage.py collectstatic --noinput  # collect static files
# then hit Reload on the Web tab

The Like Button (Deduplicated by Cookie)

Likes are gated by a cookie rather than an account, so nobody has to sign in to react: 
@api_view(["POST"])
@permission_classes([AllowAny])
@throttle_classes([AnonRateThrottle])
def like_article(request, slug):
    article = get_object_or_404(Article, slug=slug, status=Article.Status.PUBLISHED)
    cookie_key = f"liked_{article.slug}"

    if request.COOKIES.get(cookie_key):
        return Response({"detail": "Already liked"})

    article.likes_count += 1
    article.save(update_fields=["likes_count"])

    resp = Response({"likes_count": article.likes_count})
    resp.set_cookie(cookie_key, "1", max_age=86400 * 365, httponly=True, samesite="Lax")
    return resp
What makes it hold up: - The cookie lives for 365 days, which works out to one like per person per article - httponly=True keeps scripts from tampering with it - API rate limits stop anyone from farming likes

Search

Search rides on DRF's SearchFilter and matches across article titles and bodies: 
class ArticleViewSet(viewsets.ReadOnlyModelViewSet):
    filter_backends = [DjangoFilterBackend, filters.SearchFilter]
    filterset_fields = {
        "category__slug": ["exact"],
        "tags__slug": ["exact"],
    }
    search_fields = ["title", "content"]

Interaction Details

  • Particle background: an animated particle network drawn on Canvas — light enough to stay smooth
  • Reading progress bar: a hairline at the top of the page that tracks how far you have read
  • Dark theme: CSS-variable driven, one click to switch, remembered in LocalStorage
  • Live2D mascot: a draggable character widget

  • Page transitions: fade in and out between routes
