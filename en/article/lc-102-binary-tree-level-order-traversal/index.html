LC 102, level order traversal: snapshot the queue length first

2026-09-23 · 15 min · Stack Frame

The problem

Return the values of a binary tree level by level, left to right within each level.

input:  [3,9,20,null,null,15,7]
output: [[3],[9,20],[15,7]]

Note the nesting. The answer is not a flat list of five values, it is a list of lists.

Barely anyone gets asked this by itself; the question arrives with its family.

VariantProblemRequirement
Zigzag traversalLC 103Odd levels left to right, even levels right to left
Right side viewLC 199Only the rightmost node per level
Bottom-up traversalLC 107Reverse the level order
N-ary traversalLC 429Children list instead of left and right
 
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

A note on the input format: the array is LeetCode's level-order encoding, where the node at index i has children at two i plus one and two i plus two, and gaps are filled with nulls that hold their places. So the nine has no children here, while the twenty has fifteen and seven.

Plain BFS gives the order, not the levels

from collections import deque

def bfs(root):
    if not root:
        return []
    q = deque([root])
    out = []
    while q:
        node = q.popleft()
        out.append(node.val)
        if node.left:
            q.append(node.left)
        if node.right:
            q.append(node.right)
    return out

On the example this produces three, nine, twenty, fifteen, seven, which is the correct visiting order. What it loses is where the boundaries are: from a flat list you cannot tell which values shared a level.

The levels are already in the queue

The key is a property of the queue itself: nodes of the same level are always adjacent in it, and they always leave before any node of the next level.

start        q = [3]
pop 3        q = [9, 20]
pop 9        q = [20]
pop 20       q = [15, 7]
pop 15       q = []
pop 7        q = []

Look at the second line: nine and twenty are adjacent, with nothing from the next level between them, because level one was enqueued as a block while level zero was being drained. First-in-first-out guarantees the grouping for free.

So the layering information already exists. The code above simply consumes one node per iteration and discards the grouping. What is missing is recording, at the moment a level starts, how many nodes belong to it.

The line that does the work

while q:
    size = len(q)
    level = []
    for _ in range(size):
        node = q.popleft()
        level.append(node.val)
        if node.left:
            q.append(node.left)
        if node.right:
            q.append(node.right)
    res.append(level)

The inner loop both drains and refills, so the length changes while it runs. Using the live length as the loop bound pulls nodes of the next level into the same iteration, and the levels merge.

Snapshotted into a variable, that single line gives three things at once: the size of the level, the exact number of iterations, and the hook every variant hangs on.

One sentence to remember: capture the length at the moment you enter the outer loop. Afterwards, whatever happens inside cannot move the boundary.

from collections import deque
from typing import List, Optional

class Solution:
    def levelOrder(self, root: Optional[TreeNode]) -> List[List[int]]:
        if not root:
            return []

        res = []
        q = deque([root])

        while q:
            size = len(q)
            level = []
            for _ in range(size):
                node = q.popleft()
                level.append(node.val)
                if node.left:
                    q.append(node.left)
                if node.right:
                    q.append(node.right)
            res.append(level)

        return res

The three snapshots are one, two, two, which are exactly the widths of the three levels. That is the whole secret; everything else is ordinary BFS.

The enqueue frames leave the snapshot unchanged, because enqueueing does not alter how many nodes belong to the level currently being drained. And the close and enter frames have identical queue contents, differing only in a level counter that increments and a collection that clears.

Variant one: zigzag (LC 103)

Odd levels left to right, even levels right to left, so the example becomes three, then twenty and nine, then fifteen and seven.

The common approach collects normally and reverses afterwards:

res.append(level[::-1] if len(res) % 2 else level)

It passes, and it puts the reversal after the fact, disconnected from the mechanism that actually produces order.

Better is to change which end of the level the value goes into. The dequeue order within a level is always left to right, since enqueueing is always left then right, and that must not change. Only the destination changes:

reversed_layer = (level_index % 2 == 1)

for _ in range(size):
    node = q.popleft()
    if reversed_layer:
        level.insert(0, node.val)
    else:
        level.append(node.val)
    if node.left:
        q.append(node.left)
    if node.right:
        q.append(node.right)

Nine arrives first and becomes nine; twenty arrives later and pushing at the front puts it ahead. One insert does the collecting and the ordering together.

The easiest thing to get wrong here is reversing the enqueue order as well. The children of twenty are still enqueued fifteen then seven even in zigzag mode; reversing that would corrupt the next level. What gets reversed is the output, not the traversal.

class Solution:
    def zigzagLevelOrder(self, root: Optional[TreeNode]) -> List[List[int]]:
        if not root:
            return []

        res = []
        q = deque([root])

        while q:
            size = len(q)
            level = []
            reverse = len(res) % 2 == 1
            for _ in range(size):
                node = q.popleft()
                if reverse:
                    level.insert(0, node.val)
                else:
                    level.append(node.val)
                if node.left:
                    q.append(node.left)
                if node.right:
                    q.append(node.right)
            res.append(level)

        return res

Three differences from the base version: a flag, a conditional insert, and nothing else. The snapshot line is untouched.

One cost worth mentioning: inserting at the front is linear in the level width, so on a very wide tree the constant is worse than collecting and then reversing. In practice the total stays linear because the widths sum to n, but a deque used at both ends, or a reverse at the end, is more predictable, and saying so is a good sign in an interview.

Variant two: right side view (LC 199)

Imagine standing to the right of the tree and returning what you can see from top to bottom, which is the rightmost node of each level. For the example that is three, twenty, seven.

The temptation is to write a separate state machine. But the last node of a level is already the last element of the level list at the moment it closes, so one line on top of the main loop suffices:

while q:
    size = len(q)
    level = []
    for _ in range(size):
        node = q.popleft()
        level.append(node.val)
        if node.left:
            q.append(node.left)
        if node.right:
            q.append(node.right)
    res.append(level)
    right_view.append(level[-1])

class Solution:
    def rightSideView(self, root: Optional[TreeNode]) -> List[int]:
        if not root:
            return []

        right_view = []
        q = deque([root])

        while q:
            size = len(q)
            for i in range(size):
                node = q.popleft()
                if i == size - 1:
                    right_view.append(node.val)
                if node.left:
                    q.append(node.left)
                if node.right:
                    q.append(node.right)

        return right_view

Checking the index against the snapshot is the same thing as taking the last element, without materialising the level list.

But be careful if both variants are asked at once, which does happen. They share the snapshot but are not orthogonal.

ModeSecond levelRightmost
Normal, left to right9, 2020, the last element
Zigzag, right to left20, 9the last element is now nine, which is wrong

If both are required, either compute the right view separately in normal order, or take the first element of the zigzag row. And in an interview, clarify whether the view is defined by the tree geometry or by the output order, because the two diverge exactly here.

Two more variants

Bottom-up (LC 107) reverses the order of the levels and nothing else:

return res[::-1]

Reversing within levels as well would turn it into the zigzag problem.

For an N-ary tree (LC 429) the only change is the source of the children:

for child in node.children:
    q.append(child)

The snapshot line copies over unchanged.

Java

class Solution {
    public List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> res = new ArrayList<>();
        if (root == null) return res;

        Deque<TreeNode> q = new ArrayDeque<>();
        q.offer(root);

        while (!q.isEmpty()) {
            int size = q.size();
            List<Integer> level = new ArrayList<>(size);
            for (int i = 0; i < size; i++) {
                TreeNode node = q.poll();
                level.add(node.val);
                if (node.left != null) q.offer(node.left);
                if (node.right != null) q.offer(node.right);
            }
            res.add(level);
        }
        return res;
    }
}

while (!q.isEmpty()) {
    int size = q.size();
    LinkedList<Integer> level = new LinkedList<>();
    boolean reverse = res.size() % 2 == 1;
    for (int i = 0; i < size; i++) {
        TreeNode node = q.poll();
        if (reverse) level.addFirst(node.val);
        else         level.addLast(node.val);
        if (node.left != null) q.offer(node.left);
        if (node.right != null) q.offer(node.right);
    }
    res.add(level);
}

The size must be extracted into a local, never recomputed in the loop condition. And a deque rejects nulls, though the guarded enqueues here make that moot.

Edges

InputResultNote
emptyemptyReturn an empty list, not a list containing an empty list

Two of those deserve attention. An empty tree must give an empty list; without the guard, the queue is seeded with a null and the first dereference fails. And a left-only and a right-only child produce identical output, which shows the traversal cares about values and levels, not about which side they came from; that intuition breaks the moment you return node objects or compute the right side view.

Complexity

Linear time: every node is enqueued once and dequeued once, and the inner loops together run exactly n times, so they are not an independent nested traversal. This is the same style of argument as the inner skip loop in the duplicate-removal problem, where both loops advanced the same cursor.

Linear space: the queue holds the widest level at its peak, about half the nodes for a complete tree, and the result holds n values. It is not constant.

A good addition: distinguish queue space from result space. The peak queue size is the width of the widest level, which is linear for a complete tree and constant for a degenerate chain, which leads naturally into why breadth-first search is memory hungry on wide trees and depth-first search is stack hungry on deep ones.

Common mistakes

  1. Using the live queue length as the loop bound, which merges levels.
  2. Forgetting the empty guard, which dereferences a null.
  3. Appending before checking for an empty tree, which yields a list containing an empty list.
  4. Reversing the enqueue order in zigzag mode. Enqueue order is always left then right.
  5. Using a list with a pop at index zero, which is linear per removal and quadratic overall.
  6. Applying the last-element trick to a zigzag result. The variants share the snapshot but not the semantics.
  7. Building the tree by hand and treating the nulls in the encoding as nodes, which inflates the width of a level.

How to answer it

Say BFS, then say the key is layering: capture the queue length at the top of the outer loop, because the inner loop refills while it drains and the length keeps changing. Then run the inner loop exactly that many times, collecting values and enqueueing children. When it ends, a level ends. Linear time, linear space.

Then volunteer the two variants. Zigzag adds a flag and switches which end of the row values go to, leaving dequeue order alone. The right view is one line at close time.

For follow-ups: the snapshot is not optional because level zero enqueues level one immediately, so both are in the queue at once; the inner loop does not nest because its iterations sum to n; a DFS with a depth parameter also works but BFS matches the question; a list with pop at the front is quadratic while a deque is constant; and the space is the widest level plus the result, which is why breadth-first search is expensive on wide trees.

What is worth keeping is not the ten lines but the reflex: when output must be grouped by level, use a queue, and capture the length before doing anything else.

q = [3]        snapshot 1
  pop 3, push 9, 20
q = [9, 20]    snapshot 2
  pop 9, 20, push 15, 7
q = [15, 7]    snapshot 2

The snapshot is the boundary line of each level. It is taken at the instant the loop is entered, and after that the queue can do whatever it likes without disturbing the current level.
