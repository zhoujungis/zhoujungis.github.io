Counting the digit one from 1 to n: count positions, not numbers

2026-09-12 · 14 min · Stack Frame

The problem

Count how many times the digit one appears in all numbers from one to n, by finding structure rather than enumerating.

n = 13  ->  6    (1, 10, 11, 12, 13; the eleven contributes two)

The largest 32-bit input would need about twenty-one and a half billion digit operations by brute force. With the right structure the loop runs ten times regardless.

Count positions, not numbers

Brute force looks at every number and every digit. Change the question: instead of asking which numbers contain a one, ask how many ones appear at each position. The totals are the same, but the latter can be computed one position at a time, and each position depends on only three values.

Take the units digit. Among one through n the numbers with a one in that position are one, eleven, twenty-one, and so on, one per decade. So there are as many complete decades as the higher part, and the incomplete tail contributes depending on whether the current digit has already passed one.

The tens position is the same with a period of a hundred and a block of ten consecutive numbers. That period is the weight of the position, and the ledger is identical everywhere: complete cycles times the per-cycle contribution, plus whatever the tail contributes.

In one line: brute force scans numbers in linear time, structure scans positions in logarithmic time, and there are only about ten positions.

Deriving the three values

For a position of weight w, split n into the part above it, the digit itself, and the part below it.

higher = n // (weight * 10)
cur    = (n // weight) % 10
lower  = n % weight
Current digitThe tail givesContribution
0Has not reached one, so nothing extrahigher times weight
1Runs from one up to lowerhigher times weight, plus lower plus one

def count_digit_one(n: int) -> int:
    if n < 0:
        raise ValueError("n must be non-negative")
    total = 0
    weight = 1
    while weight <= n:
        higher = n // (weight * 10)
        cur = (n // weight) % 10
        lower = n % weight
        if cur == 0:
            total += higher * weight
        elif cur == 1:
            total += higher * weight + lower + 1
        else:
            total += (higher + 1) * weight
        weight *= 10
    return total

For thirteen: the units digit has higher one, digit three, and takes the third branch for two; the tens digit has higher zero, digit one, lower three, giving four. Total six, matching the sample.

Variants

For another digit the structure is unchanged, only the comparisons move: below, equal, or above that digit. With the digit being one, the below case is exactly the zero case.

def count_digit(n: int, d: int) -> int:
    total = 0
    weight = 1
    while weight <= n:
        higher = n // (weight * 10)
        cur = (n // weight) % 10
        lower = n % weight
        if cur > d:
            total += (higher + 1) * weight
        elif cur == d:
            total += higher * weight + lower + 1
        else:
            total += higher * weight
        weight *= 10
    return total

Zero is the exception, because leading zeros are not written, so the complete-cycle count must be reduced by one when the current digit is zero.

def count_digit_zero(n: int) -> int:
    total = 0
    weight = 1
    while weight <= n:
        higher = n // (weight * 10)
        cur = (n // weight) % 10
        lower = n % weight
        if cur == 0:
            total += (higher - 1) * weight + lower + 1
        else:
            total += higher * weight
        weight *= 10
    return total

The subtraction removes the cycles that would have started with a leading zero. For a hundred and one, counting zeros gives twelve and counting ones gives twenty-three, so the same n produces answers that differ by nearly a factor of two, and interviewing that difference is a favourite.

A recursive version splits by the leading digit instead of iterating from the units, contributing the remainder plus one when the leading digit is one or the full power otherwise, plus the leading digit count of the complete lower block and a recursive call on the tail. Both agree everywhere; the iterative one is recommended because it uses constant space and no recursion depth.

Java and two overflows

public static long countDigitOne(int n) {
    if (n < 0) {
        throw new IllegalArgumentException("n must be non-negative");
    }
    long total = 0;
    long weight = 1;
    while (weight <= n) {
        long higher = n / (weight * 10);
        int cur = (int) ((n / weight) % 10);
        long lower = n % weight;
        if (cur == 0) {
            total += higher * weight;
        } else if (cur == 1) {
            total += higher * weight + lower + 1;
        } else {
            total += (higher + 1) * weight;
        }
        weight *= 10;
    }
    return total;
}

Two independent overflows. The weight must be a 64-bit value, because near the maximum input the loop reaches a weight of a billion and the next multiplication exceeds a 32-bit integer, wrapping negative and making the loop condition permanently true, which hangs rather than failing.

The answer itself overflows too: at around one thousand six hundred million the count crosses the 32-bit limit, and at the maximum input it is nearly three billion. So the return type must be 64-bit. A useful estimate: each position contributes roughly a tenth of n, so the total is about n times the number of digits divided by ten.

The powers of ten are both a test of correctness and a detector of the wrong loop bound, since the leading digit contributes exactly one and an exclusive bound drops it.

Three bugs the official sample cannot catch

In the sample the current digits are three and one, so the zero branch never executes, and three wrong implementations pass it unchanged.

  1. An exclusive loop bound, which drops the leading position when n is a power of ten and always answers one too few.
  2. Adding the extra full cycle in the zero branch, which answers three instead of two for ten.
  3. Adding nothing in the zero branch, which loses the complete cycles entirely and answers one instead of two for ten.
  4. Forgetting the lower part plus one in the one branch. This one the sample does catch, and it remains the most frequently omitted term, the plus one being the digit itself.
  5. Using a 32-bit weight in Java, which hangs the program rather than returning a wrong answer.

Test with a set where zeros appear inside the number, especially a hundred and one, whose digits are one, zero and one and which therefore exercises both sensitive branches.

How to answer it

State the cost of brute force, then the shift in viewpoint from numbers to positions, then the three values and the three branches, with the weight explained as the period of that position. Add the boundary about powers of ten, the two overflows in a fixed-width language, and the zero-digit variant with its leading-zero correction.
