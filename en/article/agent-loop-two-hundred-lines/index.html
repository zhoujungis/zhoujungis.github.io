Why the first post is about the loop

No field is as rich in nouns as agents.

Planning, reflection, memory, retrieval, tool use, multi-agent collaboration, task decomposition, self-correction. Each one can support its own article, and behind each one sits a stack of papers and frameworks. A newcomer easily concludes that an agent is a complicated system, and that the right move is to pick a framework and fill in configuration.

But pause an agent process at a random moment and look at what it is doing. The answer is usually humiliatingly plain: it is waiting on an HTTP response, or it is running a shell command.

The model is stateless. It doesn't remember what was said last turn and doesn't know which tool it just called. What people call multi-turn conversation is the client resending the entire history every turn. What people call tool calling is the model emitting JSON, the client executing it, and the result going back as the next message. All the magic happens inside that send, receive, execute, send again loop.

NanoHermes does this out in the open. Agent::run in agent/src/agent.rs is 109 lines from pub fn run to the closing brace, comments and blank lines included. Add the functions it calls directly, complete, execute, assistant_message and compact, strip comments and blank lines, and the core is about two hundred lines.

Those two hundred lines contain no async runtime, no state machine generator and no middleware pipeline. There are five decisions, four variables, three gates and one for loop.

The series starts there for a simple reason: context, memory, tools, concurrency, security, multi-agent setups and observability all hang off this loop. Miss the loop and every later post becomes vocabulary recitation.

One sentence: an agent is a model, tools and a loop

Compress the definition as far as it goes:

An agent is a loop. Send messages and a tool list to the model. The model returns text or tool calls. If there are tool calls, execute them, append the results to the message list, and send again. Stop when the model stops calling tools.

Three parts, none optional.

PartJobWithout it
ModelReads messages, decides the next step, emits text or tool callsNo source of decisions, only a script following fixed rules
ToolsActually read files, change code, run commands, fetch pagesThe model can talk but not act, and output stops at the chat box
LoopTurns model output into actions and action results into model inputOne question and answer, no multi-step task

People hear "tool" and think of a plugin marketplace. The minimal definition is narrower: a function with a name, a JSON Schema, and the ability to be called by name. It can be read_file, an HTTP request, or another agent. The model never needs to know how a tool works inside, only what it is called, what the arguments look like and what comes back.

The loop knows as little about reasoning. It does four things: assemble messages, send the request, execute calls, decide whether to continue. Write those four cleanly and an agent exists.

Strip the vocabulary and five elements remain

Set planning, memory and RAG aside for a moment. A minimal working agent needs five things.

ElementIn NanoHermesWhere
Message listVec<Value> in OpenAI messages formatAgent.messages
Tool declarationsNineteen built-ins plus skills, MCP and sub-agentstools::specs(), Agent::build_tools
One model callBlocking HTTP, optional SSE streamingllm::chat
One tool executionPermission check, argument parsing, hooks, dispatchAgent::execute
TerminationNo more tool calls, interrupted, or the iteration capThe three exits of Agent::run

The part people get wrong is not how to send HTTP. It is managing the state of the message list.

The model is stateless but strict about message shape: an assistant message carrying tool_calls must be followed by a tool message for every call, with matching tool_call_id values. One missing, one extra, or a wrong order and the API rejects the request. So the loop is really a state machine whose job is to leave history as a legal message sequence after every turn.

Everything downstream, the interrupt at step boundaries, errors turned into results, concurrent execution with ordered write-back, exists to hold that invariant.

The full timeline of one user turn

Before the code, follow one real turn. The user says: change the install command in the README to pnpm.

That table is worth a second look, because it exposes four design choices.

  • Memory retrieval happens before the user message enters history. The query is this turn's input, not last turn's residue.
  • The interrupt check sits at the top of the loop. It never fires mid-tool. It fires in the gap where the previous turn has fully closed and the next one has not started.
  • Execution and write-back are separate steps. All tools run concurrently first, then results are appended in call order, so what the model sees is always in the order it asked for.
  • Compaction runs after results are appended. It operates on a complete turn, so it can never split an assistant tool call from its result.

The skeleton: a 109-line Agent::run

Strip the UI output, memory distillation and persistence, and the loop looks like this.

pub fn run(&mut self, content: Value) -> Result<String, String> {
    let _guard = InterruptGuard::new();

    let user_text = memory::content_text(&content);
    if let Some(dir) = self.ctx.memory_dir.clone() {
        let block = memory::retrieve_block(&dir, &user_text);
        self.set_memory_block(&block);
    }
    self.messages.push(json!({ "role": "user", "content": content }));

    let mut completed = false;
    let mut interrupted = false;
    let mut had_tools = false;
    let mut final_text = String::new();

    for _ in 0..self.cfg.max_iterations {
        if crate::interrupt::take() {
            interrupted = true;
            break;
        }

        let turn = self.complete()?;
        self.usage.requests += 1;
        self.usage.prompt_tokens += turn.usage.prompt_tokens;
        self.usage.completion_tokens += turn.usage.completion_tokens;

        final_text = turn.content.clone();
        self.messages.push(assistant_message(&turn));

        if turn.tool_calls.is_empty() {
            completed = true;
            break;
        }
        had_tools = true;

        let results = self.run_tool_calls(&turn.tool_calls);
        for (call, result) in turn.tool_calls.iter().zip(results) {
            self.messages.push(json!({
                "role": "tool",
                "tool_call_id": call.id,
                "content": result,
            }));
        }
        self.compact();
    }

    if interrupted {
        self.style.warn("interrupted — the conversation was kept");
    } else if !completed {
        self.style.warn(&format!(
            "reached the {} iteration limit without finishing",
            self.cfg.max_iterations
        ));
    }

    self.persist();
    Ok(final_text)
}

Two merges were made for length here: concurrent execution is folded into run_tool_calls, and UI output is dropped. In the original, concurrency is an inline std::thread::scope, covered further down.

Even so the skeleton is complete. There is no planning phase and no reflection phase. If the model wants to plan, it calls todo_write. If it wants to reflect, it sees the tool results next turn and changes its mind. Planning is not a phase of the loop. It is something the model does inside the loop.

That is the first hurdle in understanding agents: don't hard-code a human workflow into stages. The loop supplies the rhythm of act and observe. What to do is the model's decision.

The four variables in the loop

run declares four mutable variables, each answering a different question.

VariableTypeQuestionWho sets it
completedboolDid the model stop calling tools on its own?turn.tool_calls.is_empty()
interruptedboolDid the user press Ctrl-C?interrupt::take() at the top
had_toolsboolDid this turn actually run any tools?Set on the first pass through the tool branch
final_textStringWhat was the last assistant text?Overwritten after every model response

The first three decide how the turn closes. The fourth decides what run returns.

final_text has an easy-to-miss detail: it is overwritten every turn, not only at the end. So if the loop exits on the iteration cap, what comes back is the text from the last model response, which may be "I'll continue with the next edit" or may be empty. An empty string is a normal return value, not an error.

had_tools serves exactly one side channel: whether it is worth distilling long-term memory afterwards. A turn of pure pleasantries ran no tools and is not worth another model request to summarize. Only turns that did work enter distillation. The variable plays no part in controlling the loop, but it is the gate on the memory feature.

The precedence between interrupted and completed also deserves a note: interrupt wins. If the user presses Ctrl-C after the last tool finishes, the top of the loop sees it, sets interrupted, and takes the interrupt branch even though the model would have finished next turn. That matches intuition. The user said stop.

Step one: retrieve memory, then push the user message

Before the loop starts, run does two things: retrieve long-term memory, and append the user message.

The order matters. The query is memory::content_text(&content), the plain text of this turn's input. A multimodal message is reduced to its text parts, so images never take part in retrieval. Then retrieve_block returns a formatted memory block and set_memory_block writes it into the system message.

fn set_memory_block(&mut self, block: &str) {
    if let Some(system) = self.messages.first_mut() {
        if system.get("role").and_then(|r| r.as_str()) == Some("system") {
            if let Some(text) = system.get("content").and_then(|c| c.as_str()) {
                let updated = memory::set_block(text, block);
                system["content"] = json!(updated);
            }
        }
    }
}

The point of that code is not writing. It is replacing.

The system message contains a marked memory block. Each retrieval replaces it rather than appending. The reason is practical: append and turn two injects once more, turn three again, and the system prompt grows linearly until it eats the context budget. Replacing by marker keeps the block sized by the retrieval result, independent of how long the conversation has run.

An empty block means delete. If nothing relevant is retrieved this turn, set_block clears the old block instead of leaving last turn's residue. That is what "retrieve for the current instruction" means in practice: memory follows the task, not the session.

When memory_dir is None the whole feature is off, and the tool layer stops offering memory_save and memory_search. The declarations are still there; calls return "long-term memory is disabled". This is the subject of the third post. For now the one thing to remember: memory is a hook in front of the loop, not part of the loop.

The system prompt: short by design

run doesn't build the system prompt; prompt::system_prompt does. But its shape drives the cost of every turn, so it belongs here.

The base prompt in NanoHermes is short: identity, tool rules, workspace path.

pub fn system_prompt(cfg: &Config) -> String {
    let mut out = format!(
        r#"You are NanoHermes, a lightweight terminal coding agent working inside the user's workspace.

You help with software engineering tasks: reading and understanding code, editing files,
running commands, searching the codebase, and answering questions about the project.

Operating rules:
- You have tools. Use them to inspect the code instead of guessing about file contents or command output.
- Always read a file before editing it. Never rewrite a file you have not read.
- Prefer targeted edits (edit_file) over whole-file rewrites; keep changes minimal and focused.
- Do not add features, refactors, or "improvements" beyond what the user asked for.
- Prefer non-interactive commands (pass auto-confirm flags) since this terminal has no TTY.
- Briefly explain what you are doing, then act. Do not over-narrate.
- After each tool result, decide the next step. When the task is complete, reply with a
  concise summary and stop calling tools.

Workspace root: {root}
"#,
        root = cfg.workspace.display()
    );
    // Permission mode note, persona and AGENTS.md are appended in order
    ...
}

There is no "you are a senior engineer" and no "first make a plan". That is deliberate, for three reasons.

First, the prompt is resent every turn. The system message leads every request. A 2,000 token base prompt across 20 turns is 40,000 tokens of input, billed again each time. The longer the prompt, the higher the marginal cost of the loop.

Second, a long prompt dilutes the tool rules. Attention over context is not uniform. Burying "read before you edit" behind three thousand words of persona works worse than putting it in the first ten lines. NanoHermes keeps the six most important rules right after the identity block so they stay visible.

Third, project conventions belong to the project. "This repo uses pnpm" and "run cargo fmt before committing" should not be hard-coded into the agent. They belong in AGENTS.md. NanoHermes walks from the filesystem root down to the workspace, concatenates each level's AGENTS.md, and ends with the most specific one last, which creates a natural priority order.

The five sources of the system message form a table.

SourceContentCap or condition
Built-in promptIdentity, six operating rules, workspace pathFixed, about 30 lines
Permission mode noteOne line of constraint per modeOnly when not Default or AcceptEdits
User personaExtra instructions from the system_prompt settingAppended only when non-empty, never replacing base rules
AGENTS.mdGlobal ~/.nanohermes/AGENTS.md plus every ancestor directory20,000 characters in total
NANOHERMES.mdProject context at the workspace rootAppended only when non-empty
Skill listName and one-line description per skillAppended only when skills were discovered

The last two rows are not in prompt.rs. NANOHERMES.md and the skill list are appended by system_content in agent.rs. The split follows a rule: whoever discovers the thing injects it. Project files belong to the workspace, skills belong to the runtime.

One more detail: AGENTS.md files are deduplicated by canonicalize. The same file reached through a symlink or a second path is read once. If the joined text runs long it is truncated at a character boundary and a line reading project guidance truncated is appended. None of that is complicated, and together they guarantee the prompt cannot be blown up by a giant document sitting in the repository.

Step two: assemble the tool list

The model cannot know which tools exist unless each request declares them. A declaration is a JSON Schema, and the model uses it to choose a tool and shape the arguments.

NanoHermes builds the list from four sources.

SourceContentIncluded when
Built-in toolsFile read and write, patch, directories, grep, glob, shell, background tasks, web, todo, git, memoryAlways
skillLoads a skill's full instructions by nameA skill was discovered in the workspace
MCP toolsEverything each MCP server exposesAn MCP server is configured
MCP helpersmcp_list_resources, mcp_read_resource, mcp_list_prompts, mcp_get_promptAn MCP server is configured
Sub-agentssubagent, agent_listSub-agent definitions are configured

Then comes a filter.

fn build_tools(&self) -> Value {
    let mut list = tools::specs().as_array().cloned().unwrap_or_default();
    if !self.ctx.skills.is_empty() {
        list.push(skill_tool_spec());
    }
    if let Some(m) = &self.mcp {
        list.extend(m.all_tools());
        list.extend(mcp_aux_tools());
    }
    list.retain(|t| {
        let name = t.get("function")
            .and_then(|f| f.get("name"))
            .and_then(|n| n.as_str())
            .unwrap_or("");
        self.cfg.check_tool(name).is_ok()
    });
    if !self.cfg.subagents.is_empty() {
        list.push(subagent_tool_spec());
        list.push(agent_list_tool_spec());
    }
    Value::Array(list)
}

check_tool applies three rules, highest priority first.

  1. Permission mode block. Plan mode blocks every write and run_command. Debug mode blocks writes but allows commands.
  2. Deny list. A denied tool can never run.
  3. Allow list. Once an allow list is configured, only the tools on it can run.
ModeBlockedIntended use
DefaultNoneEveryday use, with auto_approve deciding whether shell needs confirmation
AcceptEditsNone, but shell always confirmsFile edits without prompts, commands still gated
Planwrite_file, edit_file, apply_patch, run_command, git_commitRead-only analysis, producing a plan
GoalNone, and never confirmsUnattended runs toward a completion goal
Debugwrite_file, edit_file, apply_patch, git_commitReproduce a problem without changing the scene

There is one asymmetry worth noting: subagent and agent_list are appended after retain, so they never pass through check_tool when the list is built. They do pass through it at execution, so safety is unaffected. The declaration is advertising; execution is the gate. That is the design principle: declare broadly, execute strictly.

Order matters too. All else equal, models favor the tools they see first. NanoHermes puts file read, write, search and shell at the front, and memory, git and background tasks later. That isn't superstition, it is reducing the model's choice cost across a long list.

Step three: one model request

complete is one of the shortest functions in the loop. It fetches the tool list and picks a callback based on the output format.

fn complete(&self) -> Result<AssistantTurn, String> {
    let style = self.style.clone();
    let tools = self.build_tools();
    match self.cfg.output_format {
        OutputFormat::StreamJson => {
            llm::chat(&self.cfg, &self.messages, &tools, |delta| {
                if !delta.is_empty() {
                    println!("{}", json!({ "delta": delta }));
                }
            })
        }
        _ => llm::chat(&self.cfg, &self.messages, &tools, |delta| {
            style.stream(delta)
        }),
    }
}

The output format forks here. Plain text hands each delta to the terminal renderer. stream-json wraps each delta in a JSON object on stdout for pipelines. The HTTP request is identical; only the handling of an arriving delta differs.

The real work is in llm::chat: build the body, handle retries, choose streaming or not, and ultimately return one AssistantTurn.

pub struct AssistantTurn {
    pub content: String,
    pub tool_calls: Vec<ToolCall>,
    pub usage: Usage,
}

That struct is the loop's input. content is what the model said, tool_calls is what it wants to do, usage is what it cost. The loop cares about the first two and books the third.

Every field in the request body answers a question

build_body is short, and every field maps to a real constraint.

FieldValueQuestion it answers

let build_body = |model: &str| {
    let mut body = json!({
        "model": model,
        "messages": messages,
        "temperature": cfg.temperature,
        "max_tokens": cfg.max_tokens,
        "stream": cfg.stream,
    });
    if has_tools {
        body["tools"] = tools.clone();
        body["tool_choice"] = "auto".into();
    }
    if cfg.thinking {
        body["reasoning_effort"] = "high".into();
    }
    if cfg.stream {
        body["stream_options"] = json!({ "include_usage": true });
    }
    body
};

Several choices deserve explanation.

temperature defaults to 0.0. A coding agent is not creative writing. Code edits need to be reproducible. Higher temperature makes the diff from the same context more random and debugging more expensive. NanoHermes sets zero and raises it through configuration when divergence is wanted.

max_tokens defaults to 4096. That is not the model's ceiling, it is the per-response budget. Tool calls are short, and 4096 comfortably holds one explanation plus several calls. A larger value tempts the model into long replies, which slows the loop.

tool_choice only appears when tools exist. Sending "auto" with no tools makes some APIs error out. The has_tools boolean exists to prevent that.

stream_options.include_usage is where streamed usage comes from. An SSE stream does not carry usage at the end unless you ask. NanoHermes needs it to keep books without a non-streaming response.

There is no top_p, seed or presence_penalty. Not because they are useless, but because the payoff for a coding agent is tiny and the compatibility risk is not. OpenAI-compatible layers support these fields unevenly, and every field left out is one fewer "this vendor rejects it" failure.

Retries and fallback: five errors that count

Requests fail. The loop cannot collapse because of one 429, so llm::chat wraps a retry loop.

let mut attempt: u32 = 0;
loop {
    match chat_with_model(cfg, build_body(&cfg.model), &mut on_text) {
        Ok(turn) => return Ok(turn),
        Err(e) => {
            if is_retryable_error(&e) && attempt < cfg.max_retries {
                attempt += 1;
                let delay = backoff_ms(cfg.retry_base_ms, attempt);
                eprintln!("note: retrying in {delay}ms (attempt {attempt}/{})", cfg.max_retries);
                std::thread::sleep(Duration::from_millis(delay));
                continue;
            }
            if let Some(fallback) = &cfg.fallback_model {
                if is_retryable_error(&e) {
                    return chat_with_model(cfg, build_body(fallback), &mut on_text);
                }
            }
            return Err(e);
        }
    }
}

is_retryable_error is honest about how crude it is: the error string contains HTTP 429, HTTP 500, HTTP 502, HTTP 503 or HTTP 504.

ErrorRetryWhy
HTTP 429YesRate limited, waiting may help
HTTP 500YesServer-side fault, possibly transient
HTTP 502, 503, 504YesGateway or upstream temporarily unavailable
HTTP 400, 401, 403NoRequest shape, authentication or permission; retrying changes nothing
JSON parse failureNoThe response shape is wrong and will likely stay wrong
Connection timeoutNoThe error string does not match, so it fails outright

Backoff is base * 2^(attempt-1) capped at 30 seconds. With base = 500ms and max_retries = 2, that is waits of 500 ms and 1000 ms, 1.5 seconds in total. The right order of magnitude for an interactive CLI, where a user is sitting there waiting.

fn backoff_ms(base_ms: u64, attempt: u32) -> u64 {
    base_ms
        .saturating_mul(2u64.saturating_pow(attempt.saturating_sub(1)))
        .min(30_000)
}

Once retries are exhausted, a configured fallback_model gets one try. Not a retry loop, one try. The fallback exists so work continues when the primary is rate limited, not so the process lives forever.

One cost is honest but easy to overlook: a streaming request that fails after emitting text will emit that text again on retry, so the interface can show duplicates. NanoHermes does no incremental deduplication, because almost every retryable error occurs while connecting or on the first frame. Mid-stream drops are rare enough that the deduplication logic is not worth its complexity. Knowing the boundary beats pretending it isn't there.

Streaming: reading SSE line by line

A streamed response is text/event-stream, one data: {...} per line. NanoHermes pulls in no SSE library and reads with BufReader::lines().

fn read_stream(resp: ureq::Response, on_text: &mut impl FnMut(&str))
    -> Result<AssistantTurn, String>
{
    let mut turn = AssistantTurn::default();
    let reader = BufReader::new(resp.into_reader());

    for l in reader.lines() {
        let l = match l {
            Ok(l) => l,
            Err(e) => return Err(format!("stream read error: {e}")),
        };
        let l = l.trim_end_matches(['
', '
']);
        if l.is_empty() || l.starts_with(':') {
            continue;
        }
        let data = match l.strip_prefix("data:") {
            Some(d) => d.trim(),
            None => continue,
        };
        if data == "[DONE]" {
            break;
        }
        let v: Value = match serde_json::from_str(data) {
            Ok(v) => v,
            Err(_) => continue,
        };
        if let Some(err) = v.get("error") {
            return Err(format!("API error: {err}"));
        }
        if v.get("usage").is_some() {
            turn.usage = usage_from_value(&v);
        }
        let Some(delta) = v.get("choices").and_then(|c| c.get(0))
            .and_then(|c| c.get("delta")) else { continue };
        if let Some(text) = delta.get("content").and_then(|c| c.as_str()) {
            if !text.is_empty() {
                turn.content.push_str(text);
                on_text(text);
            }
        }
        accumulate_tool_calls(delta.get("tool_calls"), &mut turn.tool_calls);
    }
    Ok(turn)
}

That handles six kinds of frame.

FrameHandlingWhy
Blank lineSkipSSE separates events with blank lines
Starts with :SkipComment or keep-alive
data: [DONE]End the loopThe stream terminator
data: {...} with errorReturn ErrThe server reported an error inside the stream
data: {...} with usageUpdate usageStreamed usage arrives in its own final frame
data: {...} with deltaAccumulate text and tool callsNormal increment
Unparseable JSONSkipTolerates half frames and vendor extensions

Skipping unparseable frames looks dangerous and is a necessary compromise. Network framing does not guarantee that every read lands on a complete JSON object. lines() already splits by line, but some vendors put non-standard fields inside data:. Skipping a bad frame is cheaper than failing the turn. Real errors surface through the error field or the HTTP status, not only inside a bad frame.

The non-streaming path, read_json, is simpler: parse the body, take choices[0].message, read content, tool_calls and usage. If there is no choices at all, it returns an error containing a truncated response body, so you can see what the compatibility layer actually sent.

Tool calls are assembled, not read

In a non-streamed response, tool_calls is a complete array. In a streamed one it is not.

OpenAI streams tool calls as increments. Each delta carries an index saying which call it belongs to. id and function.name usually appear only in the first frame. function.arguments arrives as string fragments that must be appended in order.

fn accumulate_tool_calls(tcs: Option<&Value>, out: &mut Vec<ToolCall>) {
    let Some(arr) = tcs.and_then(|t| t.as_array()) else { return };
    for tc in arr {
        let idx = tc.get("index").and_then(|i| i.as_u64()).unwrap_or(0) as usize;
        if out.len() <= idx {
            out.resize(idx + 1, ToolCall::default());
        }
        let slot = &mut out[idx];
        if let Some(id) = tc.get("id").and_then(|i| i.as_str()) {
            if !id.is_empty() {
                slot.id = id.to_string();
            }
        }
        if let Some(f) = tc.get("function") {
            if let Some(name) = f.get("name").and_then(|n| n.as_str()) {
                if !name.is_empty() {
                    slot.name = name.to_string();
                }
            }
            if let Some(args) = f.get("arguments").and_then(|a| a.as_str()) {
                slot.arguments.push_str(args);
            }
        }
    }
}

If the model wants to read two files at once, the stream can look like this.

FrameindexContentAccumulated
10id=call_a, name=read_fileSlot 0: name in place, arguments empty
20arguments={"path":"aSlot 0: first half of the argument string
30.rs"}Slot 0: arguments complete
41id=call_b, name=read_fileSlot 1: second call appears
51arguments={"path":"b.rs"}Slot 1: arguments complete

Three things must be right.

arguments must use push_str, never assignment. Writing slot.arguments = args keeps only the last fragment, and the model's JSON is permanently broken. The tool then reports invalid JSON arguments.

id and name only overwrite when non-empty. Later frames usually carry null or an empty string for those fields. Assigning unconditionally wipes the name out of the slot.

Slots must grow by index. The model may send index=1 before index=0, or skip an index entirely. resize(idx + 1, default) guarantees the slot exists so ordered execution never runs off the end.

When assembly finishes, AssistantTurn.tool_calls is an ordered array. The loop executes in that order and writes results back in that order, so the tool_call_id sequence the model sees matches what it asked for. That is the precondition for pairing.

assistant_message: why empty content becomes null

The returned AssistantTurn cannot go straight back into messages. The OpenAI message format expects tool calls on an assistant message in a different shape.

fn assistant_message(turn: &AssistantTurn) -> Value {
    let content = if turn.content.is_empty() {
        Value::Null
    } else {
        Value::String(turn.content.clone())
    };
    if turn.tool_calls.is_empty() {
        return json!({ "role": "assistant", "content": content });
    }
    let calls: Vec<Value> = turn.tool_calls.iter().map(|c| {
        let args = if c.arguments.trim().is_empty() { "{}" } else { &c.arguments };
        json!({
            "id": c.id,
            "type": "function",
            "function": { "name": c.name, "arguments": args }
        })
    }).collect();
    json!({ "role": "assistant", "content": content, "tool_calls": calls })
}

Three details.

Empty content becomes null, not an empty string. Some compatibility layers treat content: "" and content: null differently. When an assistant message carries only tool calls, the standard shape is null. An empty string is read by some vendors as "the model said nothing", and can even trip validation.

Empty arguments become {}. Models sometimes emit arguments: "" for a tool with no parameters. Passing that through leaves an empty string in history, and the next request may be rejected. Normalizing to {} keeps history valid JSON.

tool_calls appears only when non-empty. A text-only response does not need the field. Sending an empty array makes some APIs think the model declared calls but produced nothing, with unpredictable results.

None of this is fastidiousness. It is cross-vendor survival. OpenAI compatibility is not a standard, and every vendor has its own tolerance. An agent's history is resent over and over, so any illegal detail compounds into a 400 on the next turn.

Step four: execute the tools

execute is the function that looks most like a security boundary. It does not dispatch directly. It runs three checks first.

fn execute(&self, call: &llm::ToolCall) -> String {
    if let Err(reason) = self.cfg.check_tool(&call.name) {
        return format!("ERROR: {reason}");
    }

    let args: Value = if call.arguments.trim().is_empty() {
        json!({})
    } else {
        match serde_json::from_str(&call.arguments) {
            Ok(v) => v,
            Err(e) => return format!("ERROR: invalid JSON arguments for `{}`: {e}", call.name),
        }
    };

    for hook in self.cfg.hooks.iter()
        .filter(|h| h.event == HookEvent::PreToolUse && h.matches(&call.name))
    {
        match hooks::run(hook, &call.name, &args, &self.cfg.workspace) {
            Ok(o) if o.ok() => {}
            Ok(o) => return format!(
                "ERROR: `{}` blocked by PreToolUse hook (exit {}):
{}",
                call.name, o.code, o.output
            ),
            Err(e) => return format!("ERROR: PreToolUse hook failed: {e}"),
        }
    }

    let mut result = self.run_tool(&call.name, &args);

    for hook in self.cfg.hooks.iter()
        .filter(|h| h.event == HookEvent::PostToolUse && h.matches(&call.name))
    {
        match hooks::run(hook, &call.name, &args, &self.cfg.workspace) {
            Ok(o) if o.ok() => {}
            Ok(o) => result.push_str(&format!(
                "
[PostToolUse hook exited {}]
{}", o.code, o.output
            )),
            Err(e) => result.push_str(&format!("
[PostToolUse hook failed: {e}]")),
        }
    }
    result
}

Broken open, it is a pipeline.

  1. Permission check: can this tool run under the current mode, allow list and deny list?
  2. Argument parsing: is the JSON the model produced legal? If not, return an error string rather than panicking.
  3. Pre-hook: user scripts can veto this call with a non-zero exit.
  4. Dispatch: hand off to run_tool.
  5. Post-hook: cannot veto, only append warnings.

What stands out is how steps two and three fail: they return strings, not Err, and never panic. A malformed argument does not abort the turn. The model sees "your JSON is invalid" in the next tool message and tries again.

That is a fundamental difference between an agent and an ordinary program: an error is input to the model, not a termination signal to the process. A normal function throws on a bad argument. An agent's tool layer has to translate the exception into a sentence the model can read.

Three gates: permission, arguments, hooks

Looked at separately, the gates have different jobs and different failure semantics.

GateChecksWhat the model seesRecoverable
PermissionMode block, deny list, allow listERROR: tool ... is not available in Plan modeSwitch mode or tool
ArgumentsIs arguments legal JSONERROR: invalid JSON arguments for ...Regenerate the arguments
Pre-hookA user script's exit codeERROR: ... blocked by PreToolUse hookChange the command
Post-hookA user script's warningAppends [PostToolUse hook exited N]Does not affect the result

The permission gate has the strongest semantics. It already filtered the tool list at build time and checks again at execution. Why twice? Because the list is advertising to the model, and the model may call a filtered tool from memory. The check at execution is the real boundary.

The argument gate has the weakest semantics. It guarantees "legal JSON", not "matches the tool's schema". read_file wants a string path; if the model passes a number, req_str inside fs::read_file returns an error, which also becomes a string result. Central schema validation was skipped because each tool knows best how to interpret its own arguments, and centralizing it tends to drift from the implementations.

The hook gate is the only external extension point allowed to veto outright. A non-zero PreToolUse exit means the tool never runs. A non-zero PostToolUse exit happens after the fact, so it can only append a warning. Splitting block from remind avoids the illusion that a post-hook prevented a change it did not prevent.

Tool results are always strings

run_tool does the dispatch and its return type is String, not Result<String, String>.

fn run_tool(&self, name: &str, args: &Value) -> String {
    if name == "subagent" {
        let sname = args.get("name").and_then(|n| n.as_str()).unwrap_or("");
        let task = args.get("task").and_then(|t| t.as_str()).unwrap_or("");
        return match self.run_subagent(sname, task) {
            Ok(s) => s,
            Err(e) => format!("ERROR: {e}"),
        };
    }

    match tools::dispatch(name, args, &self.ctx) {
        Ok(s) => s,
        Err(e) => {
            if e.contains("unknown tool") {
                if let Some(m) = &self.mcp {
                    if let Some(result) = m.call(name, args) {
                        return match result {
                            Ok(s) => s,
                            Err(err) => format!("ERROR: {err}"),
                        };
                    }
                }
            }
            format!("ERROR: {e}")
        }
    }
}

tools::dispatch returns Result<String, String> and every tool implementation does the same. By the time it reaches run_tool, errors are translated into ERROR: ... strings. Successful results are not passed through raw either: the last line of dispatch is r.map(|s| clamp(s, ctx.max_output)) with a default of 20,000, truncated at a character boundary with a note saying how much was omitted. Note that the cap counts bytes, not tokens.

One consequence is direct: the model always learns why a tool failed.

FailureTool layer returnsWhat the model does next
File does not existERROR: path: No such file or directoryTry another path or list the directory
old_string not foundERROR: old_string not found ... read the file and match it exactlyRe-read the file
old_string matches several timesERROR: occurs N times ... pass replace_all=trueAdd context or pass the flag
File above 4 MBERROR: ... read it in chunks with offset/limitRe-read with a window
Command refused by the userCommand denied by the user. Do not retry it; ask what to do instead.Stops and asks
Shell exits non-zeroA normal result including exit code: N and stderrReads the error and fixes it
Unknown toolERROR: unknown tool ...Picks another tool

The denied-command row matters. It does not start with ERROR:. It is an explicit instruction: do not retry, ask instead. That is deliberate. The default reaction to ERROR: is retry or adjust parameters, but the right reaction to a user refusal is to stop. The wording of the error is behavior guidance.

One more layer: when dispatch reports an unknown tool, run_tool looks for a matching tool on an MCP server. That is the unified entry point for built-ins and MCP. Built-ins match first, MCP only on a miss, so an MCP server cannot silently shadow built-in behavior.

Feeding results back: tool_call_id is the anchor

After execution, results go back into messages. It looks like three lines of json! and is the easiest place to break the history invariant.

for (call, result) in turn.tool_calls.iter().zip(results) {
    self.style.tool_call(&call.name, &summarize(&call.name, &call.arguments), &result);
    self.messages.push(json!({
        "role": "tool",
        "tool_call_id": call.id,
        "content": result,
    }));
}

A tool result message has exactly three fields: the role tool, a tool_call_id pointing at a call in the assistant message, and the result string. No name, no timestamp, no structured JSON.

Why so plain? Because the API accepts nothing else. tool_call_id is the only anchor for pairing, the thing that lets the model connect "the third call I requested" with "this result". Get the id wrong, empty or out of order and the model receives a mismatched set, which ranges from nonsense answers to a hard 400.

After a turn with two tool calls, the history looks like this.

#roleKey fieldsNote
1systemcontentSystem prompt plus memory block
2usercontentThe instruction
3assistantcontent: null, tool_calls: [call_a, call_b]The model asks for two tools
4tooltool_call_id: call_aResult of the first
5tooltool_call_id: call_bResult of the second
6assistantcontent: "done, it is pnpm now"The summary after seeing results

That sequence must hold exactly. Note message 3: the order is [call_a, call_b], so messages 4 and 5 must match. NanoHermes uses zip to guarantee it. Even if call_b finishes first, call_a's result still comes first.

Step five: where the loop exits

Three exits, each with its own way of closing out.

ExitTriggerrun returnsHistory stateMessage
Completedturn.tool_calls.is_empty()The last assistant textComplete, ending on assistantNone
Interruptedinterrupt::take() at the topThe last assistant textComplete, ending on a tool resultContext kept, /undo available
Iteration capThe for loop runs outThe last assistant textComplete, ending on a tool resultWarns it did not finish

All three leave legal history. That is the most important invariant in the design.

Why does history end on a tool result rather than an assistant call when the loop is interrupted or capped? Because the checkpoint is at the top. The previous turn's results are all written back, compact has run, and the next request has not been sent. Exiting there leaves history in the complete state of "calls plus all results", which the model can resume from without a broken pairing.

Put the interrupt check in the middle of tool execution and you can end up with an assistant message requesting three tools and only one result written back. The next request is rejected and the user sees no reason why. That trap is subtle enough to appear again in the list of ten.

On normal completion, the last assistant message has no tool calls, only text, and final_text is that text. If the model both talks and calls a tool in the final round, the loop continues; talking is not a finish signal. Only the absence of tool calls ends the loop.

Concurrent tool calls: scoped threads, ordered collection

Models often request several tools in one response: read three files, run tests and lint together. Running them serially makes total latency the sum of every tool, so NanoHermes runs them concurrently whenever there is more than one.

let results: Vec<String> = if turn.tool_calls.len() == 1 {
    vec![self.execute(&turn.tool_calls[0])]
} else {
    let this: &Agent = self;
    std::thread::scope(|s| {
        let handles: Vec<_> = turn.tool_calls.iter()
            .map(|call| s.spawn(move || this.execute(call)))
            .collect();
        handles.into_iter()
            .map(|h| h.join().unwrap_or_else(|_| {
                "ERROR: tool thread panicked".to_string()
            }))
            .collect()
    })
};

This is std::thread::scope, not tokio::spawn and not a pool. One thread per call, joined and reaped.

ApproachLatencyComplexityFits when
SerialThe sum of all toolsLowestStrong dependencies between tools, few calls
One thread per callThe slowest oneLowFew calls, blocking I/O tools
Thread poolBounded by pool sizeMediumHigh-frequency short tasks
Async runtimeThe slowest oneHighMassive concurrency, cancellation

NanoHermes takes the second, consistent with its overall stance: a response usually requests one to five tools, and a pool or an async runtime costs far more complexity than it returns at that scale.

thread::scope lets the compiler guarantee lifetimes. The borrowed &Agent outlives the join, so no Arc and no 'static bound. The price is that Agent must be Sync, which in turn forces shared state in Ctx, such as the task manager, todo list, sub-agent board and concurrency gate, to use interior mutability with synchronization rather than &mut. The type system ends up forcing the shared state to be designed correctly.

Results are collected with zip to preserve order. join is called in handle order, so even if the third tool finishes first, results[0] is still the first call's result. A panicking thread does not kill the process: join returns Err, which becomes an ERROR: tool thread panicked result. The model learns that the tool died instead of watching the process exit.

Concurrency adds a new problem: side effects can interleave. Two write_file calls on the same file depend on who lands first. A git_commit and an edit_file racing make the committed content undefined. NanoHermes applies no tool-level mutex, because models rarely request that combination and real conflicts belong to the tools themselves, such as git's own lock. It is a trade that spends complexity only where it is needed.

Interrupt: Ctrl-C only lands at a step boundary

A terminal agent has to be interruptible. But interrupting cannot mean killing the process, or history stops mid-turn and the next resume is broken.

NanoHermes does this: Ctrl-C does not kill anything, it sets an atomic flag, and the loop reads that flag at step boundaries.

struct InterruptGuard;

impl InterruptGuard {
    fn new() -> Self {
        crate::interrupt::take();
        crate::interrupt::install();
        InterruptGuard
    }
}

impl Drop for InterruptGuard {
    fn drop(&mut self) {
        crate::interrupt::restore_default();
    }
}

The first line of run is let _guard = InterruptGuard::new();. The guard restores the default SIGINT behavior when run ends. Even if the user presses Ctrl-C while a tool runs, the handler only sets the flag; it does not terminate.

The top of the loop is the only place that consumes it.

for _ in 0..self.cfg.max_iterations {
    if crate::interrupt::take() {
        interrupted = true;
        break;
    }
    // ...
}

That position guarantees an interrupt never happens mid-tool. After Ctrl-C, the current tool finishes, its result is written back, compact runs, and only when the next iteration begins does the flag get noticed.

When Ctrl-C landsBehaviourHistory
During the model requestThe request continues, the response is written backComplete
During tool executionThe tool finishes, the result is written backComplete
After results, before the next turnExits immediatelyComplete
During concurrent toolsAll threads join, then exitComplete

The cost is that stopping is not instant. A run_command that takes 120 seconds means the user waits up to 120 seconds after pressing Ctrl-C. That is deliberate: better slow than broken history. If you need an instant kill, use a background task and task_kill rather than interrupting the whole turn.

The guard's comments also mention reference counting, so a nested turn, such as a sub-agent running inside a tool, does not tear down the outer handler. That keeps interrupt semantics consistent when nesting.

After an interrupt, run prints a note saying the conversation was kept, and the user can type a new instruction or /undo. /undo is rewind: walk back from the last user message and delete the whole turn. Interrupt and undo are two mechanisms, one stops, one rewinds.

The iteration cap: what 40 actually counts

max_iterations defaults to 40, and it is often misread as "at most 40 tool calls". It is not.

It counts model round trips. One iteration is one complete(): one HTTP request plus every tool call in that response. Request five tools in one response and that is still one iteration.

ScenarioTypical iterationsNote
Answering a conceptual question1The model replies, no tools
Reading a file and explaining it2 to 3Read, maybe read again, summarize
Fixing a well-scoped bug4 to 8Read, edit, test, edit
Implementing a small feature8 to 20Explore, multi-file edits, verify
Long task or refactor20 to 40Easy to reach the cap
Infinite loop40The model retrying the same failing tool

Forty is a generous ceiling. Its job is not to constrain real work but to catch a stuck model. Without it, a model could retry a permanently failing command forever and burn tokens doing it.

On hitting the cap, the loop prints reached the 40 iteration limit without finishing. Note the wording: not finished, not failed. Reaching the cap is a resource boundary, not an exception.

The cap is also a cost control. At 8,000 input and 500 output tokens per turn, forty iterations is 320,000 input tokens and 20,000 output. On a metered API that is real money. max_iterations is the first cost gate; compaction is the second; tool output caps are the third.

Compaction: 120,000 characters and the last ten

The longer the loop runs, the bigger messages gets. Every turn resends the full history, so growth means more input tokens, more latency, and eventually a request past the model's window.

NanoHermes compacts by replacing old messages with one summary when the budget is exceeded.

fn compact_with(&mut self, force: bool) -> usize {
    let size: usize = self.messages.iter().map(|m| m.to_string().len()).sum();
    if !force && (size <= CONTEXT_CHAR_BUDGET || self.messages.len() <= KEEP_RECENT + 1) {
        return 0;
    }

    let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
    while start < self.messages.len() && self.messages[start]["role"] == "tool" {
        start += 1;
    }
    if start <= 1 {
        return 0;
    }

    let dropped: Vec<Value> = self.messages.drain(1..start).collect();
    let note = match self.summarize_messages(&dropped) {
        Some(summary) => format!("[Earlier conversation summary]
{summary}"),
        None => "[Earlier conversation was omitted to keep the context small]".to_string(),
    };
    self.messages.insert(1, json!({ "role": "system", "content": note }));
    self.style.note(&format!("compacted: {} messages", dropped.len()));
    dropped.len()
}
ParameterValueRole
CONTEXT_CHAR_BUDGET120_000The character budget that triggers compaction, measured on serialized JSON
KEEP_RECENT10Messages always retained
Summary lengthAt most 300 wordsConstrained by the llm::summarize prompt
Insertion pointmessages[1]The summary goes right after the system message
Failure fallbackA one-line placeholderA gap in history never disappears silently

A few details deserve expansion.

The budget counts characters, not tokens. Exact token counts need a tokenizer, and a tokenizer breaks the three-crate rule. Character count is an approximation whose error for mixed English and Chinese is acceptable. 120,000 characters is roughly 30,000 to 60,000 tokens depending on the mix.

It keeps the last ten messages, not the last ten turns. A tool result is a message. A turn with five tool calls occupies seven messages: user, assistant and five results. The point is to guarantee the most recent tool exchange is still in context, so the model does not forget a result the moment it arrives.

The cut point cannot land inside a tool exchange. The while loop pushes it forward until the message is not a tool result. Otherwise you get an assistant call summarized away while its result remains, which is an illegal sequence.

A failed summary leaves a trace. If the summarization request fails, a line reading [Earlier conversation was omitted ...] is inserted rather than nothing. The model needs to know a stretch of history was removed, or it will assume its small context is all there ever was.

Compaction is synchronous. It blocks between writing back results and sending the next request. The summary is itself a model call, so the turn that compacts costs an extra round trip. Unavoidable, and only on the turns that exceed the budget.

/compact forces it through compact_with(true), skipping the budget check, and reports how many messages were summarized so the user can tell whether it did anything.

Session persistence

The last step of run is self.persist(), which writes messages to the session file when --session is configured. The write is a temp file plus a rename, so a crash mid-write cannot leave truncated JSON.

pub fn save_session_file(path: &Path, messages: &[Value]) -> Result<(), String> {
    let body = serde_json::to_string_pretty(messages).map_err(|e| e.to_string())?;
    let tmp = path.with_extension("tmp");
    std::fs::write(&tmp, body).map_err(|e| e.to_string())?;
    std::fs::rename(&tmp, path).map_err(|e| e.to_string())?;
    Ok(())
}

At startup, load_session_file reads the file and refresh_system regenerates the system message from current configuration, replacing the stored one.

OccasionActionPurpose
Startup with a session fileRead JSON, refresh the system messageRestore history under the latest configuration
End of every turnWrite a temp file, rename overCrash safety
Load failureWarn and start freshA bad file must not block startup
resetClear history, keep the system messageNew topic
rewindDelete the last N user turnsUndo recent instructions

Why refresh rather than restore the system message verbatim? Because the system message is configuration, not conversation. The tool list, persona, permission mode and AGENTS.md can all have changed. Restoring the old prompt leaves the session running on expired rules, which shows up as "I changed the config and nothing happened".

Persistence has a boundary too. When self.complete()? fails, run returns early and persist() never runs. Memory then holds a user message that disk does not, so the failed instruction is lost on the next start. That is acceptable, since a failed request produced no useful reply, but it is a reminder that ? inside the loop is an exit that skips the closing steps.

Memory distillation

After the loop ends, if the turn completed normally, memory is enabled and tools were actually used, distill_memories asks the model to extract a few long-term memories from the conversation.

if completed && self.cfg.memory {
    self.distill_memories(&user_text, had_tools);
}

Three gates.

  1. completed must be true. An interrupted or capped turn has no conclusion yet, so nothing is distilled.
  2. cfg.memory must be on. Feature disabled, step skipped.
  3. worth_distilling must pass. Pleasantries, short instructions and turns that used no tools are not worth another model request.

Distillation takes the last 6,000 characters of conversation and asks the model for several (kind, text) pairs, where kind is one of lesson, preference, correction or fact. Each goes through memory::remember, which returns whether it was actually new after deduplication. If at least one was written, the CLI prints how many memories were distilled.

The design keeps memory outside the loop rather than inside it. The loop does not decide what to remember, it only triggers distillation at the right moment. That keeps the loop simple and lets the memory policy evolve on its own.

The token ledger: why it reports deltas

UsageTotals has three fields.

FieldMeaning
requestsHow many model requests this session made
prompt_tokensCumulative input tokens
completion_tokensCumulative output tokens

After each complete(), run adds that turn's usage and calls style.usage(1, prompt, completion). The first argument is 1, meaning one request this time, not the running total.

self.usage.requests += 1;
self.usage.prompt_tokens += turn.usage.prompt_tokens;
self.usage.completion_tokens += turn.usage.completion_tokens;
self.style.usage(1, turn.usage.prompt_tokens, turn.usage.completion_tokens);

Why report deltas instead of totals? Because one Agent instance can serve several isolated sessions. In daemon mode, cloud tasks swap the message vector through replace_messages and reuse the same agent. If the UI received cumulative values it would add unrelated tasks together into a meaningless number. With deltas, the client accumulates per task, and in local mode the deltas sum to exactly the same total.

It is a clean example of an interface shaped by deployment. A single-machine CLI is easier with totals, but a daemon requires deltas. NanoHermes picked the one that is correct for both.

The boundary of two hundred lines

"Two hundred lines" is not a code golf score, it is a boundary that says what belongs to the loop and what does not.

ModuleIn the loop?Why
HTTP, retries, proxyingNollm::chat's job; the loop receives an AssistantTurn

System prompt constructionNoConfiguration and project files; the loop consumes the result

That table explains why the loop can be short: it keeps only the logic that needs to see a complete turn. Anything a single tool can handle is pushed down; anything the transport can encapsulate is pushed up. The loop degrades into a coordinator instead of a god object.

It also gives a test for whether an agent architecture is healthy. If SSE parsing, URL assembly or file-type detection shows up in the main loop, a layer has leaked.

Ten implementation traps

Almost everyone who hand-writes an agent hits at least three of these.

TrapSymptomCorrect approach
Tool results without tool_call_idThe next request 400s, complaining a tool message lacks an idEvery tool message carries the id of its call
Assigning streamed argumentsTools receive broken JSON and report argument errorsAppend with push_str, keyed by index
Interrupting mid-toolThree calls in history, one resultCheck the interrupt only at the top of the loop
No iteration capThe model loops on a failing command and the bill explodesSet max_iterations and say so clearly
Uncapped tool outputOne cat blows the contextTruncate centrally, hard-cap file reads
Panicking on tool errorsOne bad path exits the processTranslate errors into string results
Empty content as an empty stringSome layers reject an assistant message with only tool callsWrite null
Compaction cutting inside a tool exchangeHistory contains an orphaned tool resultPush the cut point to a non-tool message
Appending the memory block every turnThe system prompt grows linearlyReplace the block by marker
Planning as a loop phaseThe model is forced through a fixed workflow even for trivial tasksLeave planning to the model, expressed as tool calls

Three finer ones:

  • Collecting concurrent results in completion order. join order must match tool_calls, not whoever finished first, or results stop lining up with requests.
  • Sending tool_choice with no tools. Some APIs reject it, so wrap it in a has_tools check.
  • Restoring the system message verbatim on resume. Configuration changes quietly stop applying and you spend an afternoon blaming the model.

What these share is that none of them shows up on the first run. A single question and answer looks perfect. The breakage arrives on the third turn, the fifth, the tenth. Most of the difficulty in debugging agents comes from that accumulation.

Closing, and the rest of the series

Back to the opening sentence: an agent is a loop.

The model decides, the tools act, the loop connects them. Planning, memory, reflection and multi-agent setups are behaviors that grow on this loop, not a separate system beside it. Understand the two hundred lines and everything else has somewhere to attach.

This post deliberately covers only how it turns. Half the problem is still open: once it turns, what should history keep and what should it drop?

Context is the scarcest resource an agent has. Tool results, file contents, error messages and past dialogue all compete for one window. Keep too much and the model loses the point while costs climb. Drop too much and it forgets what it is doing. NanoHermes handles it with a 120,000 character budget, the last ten messages and a summary replacement, but the real difficulty is deciding what a summary must preserve.
