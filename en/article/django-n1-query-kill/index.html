From 21 SQL statements to 2: three rounds against N plus one

2026-09-09 · 12 min · Stack Frame

The numbers first

The article list page shows ten posts. The backend runs fourteen queries with eight posts, and twenty-one with a full page of ten. Exactly one of them is necessary.

N plus one is the most common and most invisible performance problem in a Django project. The code looks fine, small datasets are fast, and after launch it degrades linearly with data. It raises nothing, it just makes the homepage slower while you stare at the code and cannot see where.

What the pattern is

class ArticleListSerializer(serializers.ModelSerializer):
    category = CategoryNestedField(read_only=True)
    tags = TagNestedField(many=True, read_only=True)

Each post displays its category name and tag names, and the ORM does this: one query for the ten posts, then one query per post for its category, then one per post for its tags. One plus ten plus ten is twenty-one. The N is ten, the count is twice N plus one, and that is where the name comes from.

VersionQuery count
Looping over category and tags directly14 with eight posts, tags reused
With select and prefetch2

With small data fourteen queries take milliseconds and nobody notices. But the count grows with the number of posts, and pagination, comments, RSS and search each bring their own set. It is not that slowness arrives suddenly; it is that each new post makes it a little slower, until one day it is unbearable.

The key realisation: this is not a slow-query problem, it is a query-count problem. A single statement can be as fast as you like and still the count grows linearly.

First round: counts on the category list

data = [(c.name, c.article_set.filter(status="published").count())
        for c in Category.objects.all()]

Four categories give one query for the list plus four counts, five in total, and the count grows with the number of categories and tags.

def get_queryset(self):
    return Category.objects.annotate(
        article_count=Count(
            "article",
            filter=Q(article__status=Article.Status.PUBLISHED),
        )
    )

The annotation with a filtered count becomes a single statement with a conditional aggregate, so categories and counts come back together, always one query. The same applies to tags.

Note the filter: only published articles count. Drafts, scheduled and archived posts must be excluded, and the counting rule has to match the visibility rule of the listing, or the category page advertises twelve posts and reveals eight. Numbers that do not add up destroy trust faster than anything.

class CategorySerializer(serializers.ModelSerializer):
    article_count = serializers.IntegerField(read_only=True)

The field is declared as a plain read-only integer, so the data comes from the queryset annotation rather than a second query inside the serializer. That separation of duties is the general principle behind everything that follows: how many queries run and how they are shaped is the queryset's business, and the serializer only presents what has already been fetched.

Second round: comments

The comment serializer touches three relations: the reverse relation for replies, and the article twice through the foreign key. Each comment therefore triggers a query for the article and another for its replies, so a page of twenty comments is over forty statements.

return Comment.objects.filter(
    article=article, is_approved=True, parent=None
).select_related("article").prefetch_related("replies__article")

Forward foreign keys use the join variant and come back in the same statement. Reverse relations and many-to-many use the prefetch variant with a couple of extra queries, and note the double underscore in the path: the article of each reply must be prefetched too, or the pattern simply reappears one level down.

The method: do not guess. Open the serializer, list every relation it touches line by line, and prefetch exactly those in the queryset.

There is a second guard worth mentioning. The reply method is recursive, so the caller must prefetch and the recursion needs a depth cap. That protects against a maliciously constructed parent cycle and against runaway payloads. Query count and recursion depth are two different diseases, and nested serialisation needs both defences.

Third round: the RSS feed

The feed is the easiest place to miss the pattern, because it lives outside the DRF views and has no serializer.

.select_related("category")
.prefetch_related("tags")

Every feed item prints its category and tags, so without prefetching, each poll by a reader costs dozens of statements. Nobody reads the feed, but crawlers and readers are the most frequent visitors of all, so skipping it leaves the busiest path in the slowest state.

The lesson: cover every exit, the REST endpoints, the feed, the admin and the cron jobs. Fixing the API and leaving the feed is locking the front door and leaving the back open.

An honest section

The most frequently visited endpoint, the article list itself, had no prefetching at all, while its serializer touches both category and tags. The category and tag pages were fixed and the homepage was missed, the classic blind spot.

queryset = Article.objects.filter(
    status=Article.Status.PUBLISHED
).select_related("category").prefetch_related("tags")

Fourteen queries become two, one for the posts and one for the tags, with the category coming through the join, and the count is independent of N.

Why write this down instead of quietly fixing it: because this is what the problem really is. It is not a bug that disappears once fixed; it is chronic, returning whenever a field or an endpoint is added. A method field that finds related articles by tag hides another few queries, so what is needed is not a fix but a habit of discovery.

A four-step method

StepAction
1List every relation the serializer touches, including queries hidden inside method fields
2Count queries locally, before and after, with a query-counting context or an assertion
3Use the join variant for forward keys and the prefetch variant for reverse and many-to-many, following double underscores to the end
4Cover every exit: API, feed, admin, scheduled jobs

Step two is the one worth insisting on: measure before you optimise. Every number above is measured locally, not estimated. Without a before, you cannot tell an improvement from a placebo.

Closing

The frightening thing about this pattern is not that it is hard to fix, since the fix is often one line, but that it is invisible. Everything works, every test passes, and the site slowly decays as data grows, losing users before anyone knows why.

Three questions to ask yourself next time you write a DRF endpoint: which relations does the serializer touch, what did the query count do before and after, and are there sibling endpoints in the feed, the admin or the cron jobs. And the honest one: after fixing it, look again, because the busiest endpoint is usually the blind spot.
