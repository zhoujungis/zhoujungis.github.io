Z Desktop: putting 44 local tools behind a risk gate

2026-11-18 · 20 min · Stack Frame

Who this is for: engineers building desktop agents, computer-use products, or anything that lets a model touch a real machine; anyone who cares about permission models, approval UX, and command classification; people who would rather put the security boundary in Rust than in a system prompt.

TL;DR: All 44 tools in Z Desktop go through a single entry point, request_tool_execution(). CRITICAL actions are blocked outright, HIGH actions always require a human, and "always allow" only applies to MEDIUM and below. Shell commands are split on ;, &&, || and |, then classified segment by segment, so echo ok && rm -rf cannot borrow the safe-list. The interesting part is what these rules still miss: seven gaps, documented below.

Reading time around 20 minutes. Level: advanced.

The hard part isn't the model

Letting a model read files, list directories and inspect processes is easy. The hard part is the other category: deleting, overwriting, killing processes, shutting down, editing the registry. Those actions share one property, irreversibility, and models have no reliable intuition for what happens after the call returns.

Z Desktop is a Windows desktop workspace built with Tauri 2, Vue 3 and Rust. Its 44 tools cover files, Shell, processes, windows, GUI automation, a browser, screenshots and the clipboard. The product thesis fits in one sentence: the model can plan, but every action that actually touches the machine must pass a decision made in Rust.

That principle turns into three constraints:

  • The planning loop and state machine live in the frontend (src/agent/loop.ts), where streaming UI and state transitions are natural.
  • Permission checks, path sandboxing, tool execution and process cleanup all live in src-tauri. The frontend cannot call a tool directly around invoke.
  • There is exactly one tool schema, supplied by Rust's tool_definitions(). The frontend keeps display metadata only, so the two definitions cannot drift.

The split: loop in the frontend, gate in Rust

A single tool call travels this path:

Agent Loop (Vue)
  -> invoke("tool_execute", { taskId, tool, input, approvalRequestId? })
  -> security::permission::decide()
      |- CRITICAL           -> { status: "blocked" }
      |- needs approval     -> enqueue in pending_approvals
      |                       emit("approval-requested")
      |                       frontend waits for approval-resolved
      |                       allow -> resend with requestId
      |                       deny  -> returned as a failed observation
      |- auto / approved    -> tools::registry::execute()
  -> emit("activity", tool_started / completed / failed / blocked)
  -> return { status, result | error | reason, durationMs }

Rust exposes only 20 Tauri commands, most of them thin forwarders. The decisions that matter sit in three files: security/risk.rs answers "how dangerous is this command", security/permission.rs answers "does this level need a human", and security/sandbox.rs answers "can this path be written".

Five risk levels: turning "can it" into "who decides"

There are five levels: SAFE, LOW, MEDIUM, HIGH and CRITICAL. They do not answer whether a tool may be called. They answer who signs off on this particular call.

LevelDefaultTypical tools
SAFEauto-allowread file, list directory, inspect process, screenshot, read clipboard
LOWconfigurablecopy, rename, start app, write clipboard
MEDIUMneeds approval (configurable)write file, move file, close window, UI click, unknown Shell
HIGHconfirm every timedelete, kill process, git push, install software
CRITICALblockedformat, shutdown, edit HKLM, disable Defender

The defaults are permissive for SAFE and strict for everything else: auto_approve_safe = true, auto_approve_low = false, auto_approve_medium = false, shell_safe_auto_exec = true and max_steps = 30 (clamped to 1–200). Reads do not interrupt the user, writes require confirmation by default, and dangerous actions have no confirmation path at all.

Tool levels are registered in state.rs::tool_risk(). Only filesystem.delete and process.kill are HIGH, and unknown tools fall back to MEDIUM. That fallback is deliberate: unknown does not mean safe.

Shell classification: one command is not one level

shell.exec is the one tool whose level cannot be derived from its name. git status is read-only. git clean -fdx deletes untracked files. Both are Shell, so the level comes from the command text.

classify_command() first splits the command on ;, newlines, &&, || and |, classifies every segment, and takes the maximum. The split exists to close a specific bypass:

echo ok && rm -rf ./build

If you only ask whether the whole string contains a safe keyword, echo lets it through. After splitting, rm -rf ./build is HIGH, so the whole command needs approval. The tests pin this down:

assert_eq!(classify_command("echo ok && rm -rf ./build"), RiskLevel::High);
assert_eq!(classify_command("git status; git clean -fdx"), RiskLevel::High);
assert_eq!(classify_command("dir | Remove-Item -Recurse"), RiskLevel::High);
assert_eq!(classify_command("dir | findstr foo"), RiskLevel::Safe);

The order is: 31 CRITICAL patterns, then 35 HIGH patterns, then a destructive first token, then a read-only check, then MEDIUM. The CRITICAL list includes format, shutdown, diskpart, vssadmin delete, rm -rf / and fork bombs. The HIGH list includes deletion, process killing and package installs, plus git commands that rewrite history: git reset --hard, git clean, git push, git checkout --.

Two details in the read-only check are worth copying:

  • The first token must be a complete word. cdx.exe must not match cd, catalog.exe must not match cat, and lsblk must not match ls. After a prefix match the code checks that the next character is whitespace or a hyphen.
  • Any > redirection disqualifies a segment from being read-only. echo hi > out.txt is MEDIUM; echo hi is SAFE.

This also creates two known false-positive surfaces, covered later: the splitter does not understand quotes or escapes, so echo "a && b" gets split, and lexical matching cannot see powershell -enc <base64>.

The approval queue: approval_required is a return value, not an exception

When approval is needed, the tool does not throw. It returns a structured result:

{ "status": "approval_required", "requestId": "...", "riskLevel": "high", "reason": "Needs user approval" }

request_tool_execution() inserts the request into pending_approvals before emitting approval-requested. The order matters: broadcast first and the user can click Allow before resolve_approval() can find the requestId.

There are three outcomes: deny, allow once, and always allow.

  • Deny removes the request immediately. The frontend hands { status: "failed", error: "User denied the operation" } back to the model as a tool observation. The model can try another route, but it does not get an exception.
  • Allow once keeps the request for replay. The resend must match both the tool name and the full input JSON, and the request is consumed on match. This prevents "approve A, execute B": checking only the tool name is not enough, because the arguments can change between calls.
  • Always allow writes a row to approval_rules, but only takes effect when effective_risk <= MEDIUM. HIGH keeps asking even when a rule matches.

Denial and cancellation both clean the queue. cancel_task() removes only the pending requests that belong to this task and emits approval-resolved: deny for each one, so approval cards do not stay on screen. finish_task() does the same cleanup when a task reaches a terminal state. These look like details, but they are mandatory for a long-running app: an approval table that only grows will leak within a day.

The path sandbox: read and write asymmetry is deliberate

check_path() does one thing: before a mutating operation (write, mkdir, copy, move, rename, delete), it rejects targets inside protected system directories:

C:Windows
C:Program Files
C:Program Files (x86)
C:ProgramDataMicrosoft
/bin  /boot  /etc  /lib  /lib64  /sbin  /usr  /var  /sys  /proc

Three implementation details exist because Windows paths are slippery:

  1. Resolve .. first, then canonicalize. A string prefix check is bypassed by C:Windows..Users.... normalize() handles ParentDir component by component. resolve_real() walks up to the nearest existing ancestor and appends the missing tail, so a symlink in the parent directory is still detected even when the target file does not exist yet.
  2. Strip the \? verbatim prefix. Otherwise \?C:Windows and C:Windows do not compare equal.
  3. Normalize separators before comparison. On Windows, /etc/passwd becomes etcpasswd. Without converting to /, the Unix protected list is dead code on Windows.

The asymmetry is intentional: check_path() allows PathOp::Read and only checks protected directories for PathOp::Mutate. Reading C:WindowsSystem32driversetchosts is allowed. Writing it is not. The boundary is "do not destroy the operating system", not "confine the agent to a project directory" — users should be able to write to their own D:Downloads.

Four brakes in the agent loop

The loop is an explicit state machine: IDLE -> THINKING -> PLANNING -> EXECUTING -> OBSERVING -> VERIFYING, returning to THINKING when the task needs another turn, CANCELLED on user stop, ERROR on an exception. Four brakes are hard-coded in src/agent/loop.ts:

MechanismImplementation
Step capDefault 30, clamped to 1–200. Running out marks the task failed and points the user at settings.
LLM retryTransient failures retry once. The failure reason is appended to the conversation with "continue from the current progress".
Observation capEach tool result is serialized to JSON and cut at 4,000 characters.
Verifier convergenceAfter two consecutive verification failures, the final output is kept with the verifier's note instead of looping.

The verifier itself is worth a look. It asks one question: "Has the task been completed, and is the result credible? Answer yes or no, then explain in one sentence." Parsing only looks at the first word, not a full-text search for yes/no; otherwise no, but it could be yes would pass. If the verifier call itself fails, the final output is accepted (fail-open). Cancellation caused by the user still propagates. This is a deliberate trade-off: it is better to accept one unverified completion than to wedge the task in a "verifier unavailable" loop.

The 44 tools and their limits

More tools is not better. Every category needs an explicit ceiling, or a single call can exhaust memory or the context window.

CategoryCountKey limits
Filesystem10list 2,000 entries, depth 1–8; read 2 MB default, 50 MB hard cap; search 200 default, 2,000 max
Shell1120-second default timeout, 1-hour cap; stdout/stderr each keep the last 100 KB
Process4list 100 default, 1,000 max
Window6enumerate, find, focus, minimize, maximize, close
UI automation7tree depth 4 default, 10 max; 5,000 ms lookup timeout
Browser11CDP against local Chrome/Edge; 10 MB download cap; 20,000-character extract cap
Screenshot3full screen, window, region; multiple monitors and negative coordinates
Clipboard2read text, write text

Several implementation details matter more than the counts:

  • filesystem.write requires content instead of defaulting to an empty string. A missing argument must not silently erase the target file. That is a real failure mode, not a hypothetical.
  • filesystem.read sniffs the first 8 KB for a null byte. Binary content goes out as base64, text goes through lossy UTF-8 decode, and both return a truncated flag so the model knows it is not seeing everything.
  • shell.exec drains output on separate threads and keeps only the last 100 KB. When the process exits, times out or is cancelled, it runs taskkill /PID <pid> /T /F to kill the whole tree, with Child::kill() as a fallback so wait() cannot block forever.
  • The browser uses chromiumoxide to launch Chrome or Edge with a visible window, stores the session in AppState and reuses one page. A second browser.open navigates instead of starting another instance.
  • UIA lookup priority is AutomationId > Name > ControlType > parent-child > UI tree. Clicking tries the Invoke pattern first and falls back to coordinates. Coordinates are the last resort because they break the moment the window moves.

Stop: a cancel flag, an aborted stream, and a process tree

"Stop" is not a button. It is a signal that has to cross three layers:

  1. The frontend's requestStop() sets stopRequested and calls abort() on the active streaming LLM request.
  2. The loop checks the cancel flag at the top of every step, before every tool call, and after an approval wait returns.
  3. Rust's cancel_task() sets the task flag, clears that task's pending approvals, and calls kill_tree() on every PID registered by the task.

Shell timeout and cancellation share one wait_loop: poll try_wait() every 100 ms, kill the tree on timeout or cancel. Then read stdout/stderr from two channels with a 2-second cap. If the read times out, it substitutes placeholder text so cancellation never hangs on a pipe.

Observability is built in rather than added later. Every tool call writes a task_steps row (input cut at 4,000 characters, output at 8,000). Every state change writes to events and emits an activity event. The task timeline is a projection of those two tables.

Browser and UIA: why AutomationId comes first

GUI automation usually degenerates into "take a screenshot and let the model guess coordinates". Z Desktop reverses the order: use control semantics when they exist, coordinates only as a fallback.

  • ui.inspect walks the UI tree and returns each element's Name, AutomationId, ControlType and rectangle.
  • ui.find narrows by automation_id, then name, then control_type.
  • ui.click prefers UIInvokePattern and only takes the element's center point when no Invoke pattern exists.
  • ui.getValue tries the Value pattern, then the Text pattern, then the Name property.

The payoff is stability. AutomationId does not move with the window or change with DPI. Name changes with language. ControlType only identifies a class of control. Coordinates guarantee nothing. The cost is coverage: custom-drawn controls, games and some Electron apps expose no UIA tree at all, so screenshots and coordinates remain necessary.

Seven gaps that still exist

  1. The splitter ignores quotes and escapes. split_segments() only looks at characters, so echo "a && b" becomes two segments. PowerShell backtick escapes and single-quoted strings are not handled either. This creates false positives, not false negatives.
  2. Lexical matching cannot see encoded execution. powershell -EncodedCommand <base64>, alias calls and download-then-run all miss the keyword lists. This is not a matter of a longer list; it is the ceiling of a lexical approach.
  3. Reads have no boundary, only writes do. The sandbox only guards mutating operations. Prompt injection can make the agent read C:Users....sshid_rsa and write it somewhere it is allowed to write. Approval is per tool call; there is no data-flow tracking.
  4. "Always allow" never applies to HIGH. That is intentional, but it means users re-approve the same high-risk operations every day, which nudges them toward loosening global settings instead of confirming each time.
  5. The verifier fails open. If the verifier call fails, the task is treated as complete. The cost is that a model can slip through when verification is unavailable.
  6. Running out of steps ends as failed. Thirty steps is enough to tidy a downloads folder and not enough for a long refactor. Raising the cap only postpones the problem; there is no checkpoint resume.
  7. Windows-only capabilities have no cross-platform equivalent. window.*, ui.* and screenshot.window are stubs that return an explanatory error on other platforms. They compile; they do not work.

One more boundary is not a gap but worth stating: 42 Rust unit tests cover risk classification, permission decisions, the path sandbox, approval lifecycle, Shell output clipping and settings normalization. There is no adversarial command corpus and no end-to-end prompt-injection test. The tests prove the known rules are implemented correctly. They do not prove unknown bypasses do not exist.

Closing

The valuable part of Z Desktop is not the list of 44 tools. It is that "who gets to decide" is executable code:

  • Risk levels are data, not if-statements scattered through the codebase.
  • Shell commands are classified per segment, so a safe keyword cannot be lent to a dangerous command.
  • Approval is a one-time token; replay must match the tool name and the full arguments.
  • The path sandbox guards writes only. Its boundary is "do not break the OS", not "confine the agent to a project".
  • Every layer has an output ceiling, and the cancel signal crosses the frontend, Rust and the process tree.

None of these mechanisms is sufficient alone. Stacked together, they turn "the model might do something wrong" from an uncontrolled incident into an operation that can be approved, replayed and stopped. In a field where model capability is still climbing fast, being able to stop, refuse and trace matters more than what the agent can do.
