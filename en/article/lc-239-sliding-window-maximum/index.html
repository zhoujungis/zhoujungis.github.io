LC 239, sliding window maximum: a monotonic queue keeps only candidates

2026-09-29 · 13 min · Stack Frame

The problem

Given an array and a window size, return the maximum of every window as it slides right, in linear time.

[1,3,-1,-3,5,3,6,7], k = 3  ->  [3,3,5,5,6,7]

Scanning each window is quadratic and becomes truly square when the window is half the array. Linear time requires not repeating comparisons.

Keep only the candidates

Watch what happens when a five arrives behind a three and a minus one. Can either of them ever be the maximum of a future window? No. As long as the five is inside the window, the smaller values cannot win, and the five also leaves later, so they are already gone when it goes. Being beaten on both size and time is domination, and it is permanent.

That is the entire idea: keep only candidates that could still become the maximum, ordered by decreasing value, so the front is always the current maximum. Each new element evicts everything at the back that it dominates, then joins.

The eviction test is inclusive, because an equal older element adds no information and occupies a slot. After eviction the queue is strictly decreasing, which matters later.

Two independent actions

from collections import deque

def maxSlidingWindow(nums, k):
    dq = deque()
    ans = []
    for i, x in enumerate(nums):
        if dq and dq[0] < i - k + 1:
            dq.popleft()
        while dq and nums[dq[-1]] <= x:
            dq.pop()
        dq.append(i)
        if i >= k - 1:
            ans.append(nums[dq[0]])
    return ans

Three points. The queue stores indices, not values, because only an index can answer whether an element has left the window; storing values makes that test impossible, and it is the most common implementation error here. The two actions are independent: the front check uses indices, the space dimension of expiry, while the back loop uses values, the domination dimension, and they pop from opposite ends. And the answer is the front, since the queue is strictly decreasing and every index inside is still in the window.

The front check can be a single conditional because the window advances one step at a time, while the back loop must loop because one newcomer can dominate several elements.

Alternatives

import heapq

def maxSlidingWindow(nums, k):
    h, ans = [], []
    for i, x in enumerate(nums):
        heapq.heappush(h, (-x, i))
        if i >= k - 1:
            while h[0][1] < i - k + 1:
                heapq.heappop(h)
            ans.append(-h[0][0])
    return ans

A max-heap with lazy deletion is slower but quicker to write and harder to get wrong, and it naturally supports broader queries than the maximum. Block decomposition is another linear method: chunk by the window size, precompute prefix maxima from the block start and suffix maxima to the block end, and any window maximum is then the larger of one suffix value and one prefix value. It is genuinely linear with no amortisation, and unintuitive with poor extensibility, so knowing it exists is enough.

For streaming, the monotonic queue is already online, so it needs only a counter. For data larger than memory, chunk and merge, which is the distributed version of the block method, and the point to make is that chunking localises the problem and the merge costs only the number of chunks.

Family rule: when a newcomer kills older elements, reach for a monotonic structure. Take the answer from one end and use a queue, as in sliding windows; want the next greater element per position and use a stack. What gets evicted is permanently out, which is why the amortised cost is constant.

Java

public int[] maxSlidingWindow(int[] nums, int k) {
    int n = nums.length;
    int[] ans = new int[n - k + 1];
    Deque<Integer> dq = new ArrayDeque();
    for (int i = 0; i < n; i++) {
        if (!dq.isEmpty() && dq.peekFirst() < i - k + 1) {
            dq.pollFirst();
        }
        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i]) {
            dq.pollLast();
        }
        dq.offerLast(i);
        if (i >= k - 1) {
            ans[i - k + 1] = nums[dq.peekFirst()];
        }
    }
    return ans;
}

Complexity

Linear time, since each element enters and leaves the queue at most once; the inner loop looks nested and is amortised constant. Space is proportional to the window, since every stored index is inside it and the indices increase.

For contrast: brute force is quadratic, the heap is linearithmic with linear space, and block decomposition is linear with linear space. The monotonic queue wins on all three metrics and costs the effort of understanding domination.

Common mistakes

  1. Storing values instead of indices, which makes the expiry test impossible.
  2. Popping the expired front after reading the answer, so the reported maximum may already have left the window. Order: maintain, push, then read.
  3. Using a strict comparison at the back, which keeps equal values and breaks the strict monotonicity, with degenerate behaviour on equal inputs.
  4. Not rejecting a window larger than the array, which happens to work by accident rather than by design.
  5. Believing the inner loop makes it quadratic instead of explaining the amortised accounting.
  6. Mismatching the heap version's expiry comparison with the window definition, which discards a still-valid top.

How to answer it

State that the queue keeps only the still-possible candidates in decreasing order, then explain domination, which is the correctness argument and worth more than the code. Name the two independent actions and why the queue must hold indices. Volunteer the amortised accounting, then the comparison table with brute force, heap and block decomposition, and finally the streaming and out-of-memory extensions.

Closing

This is the definitive problem for monotonic structures: a single invariant, that domination is permanent, explains both the correctness and the complexity, because what is discarded really is useless and each element dies exactly once. The bracket stack earlier, this queue, and the monotonic stack in the trapping problem are three faces of one idea, differing only in which end the answer comes from.
