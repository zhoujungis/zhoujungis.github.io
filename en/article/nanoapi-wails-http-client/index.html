Why a Postman that is just enough

Postman is powerful, and that power rests on size, accounts, cloud sync, a plugin ecosystem and telemetry. For a developer who wants to enter a URL, pick a method, add a few headers and read the JSON back, most of that is background noise.

NanoAPI compresses the goal into one sentence: a sufficient HTTP debugging client, one executable, double-click to run, data stays local.

"Sufficient" isn't an adjective here. It's a checkable set of constraints. The module file has exactly one direct dependency, the Wails runtime. The frontend has no npm dependencies and no build step, and native ES modules are embedded straight into the binary. The release executable is 11,341,824 bytes, about 10.8 MiB. The NSIS installer for the same version is about 6.3 MB and the MSI about 4.5 MB. An Electron application's installer usually starts in the hundreds of megabytes.

Those numbers don't come from cutting features. They come from choices: rendering belongs to the system WebView2, network and files belong to the Go standard library, and the frontend keeps only the DOM plus a little glue. So there is no Chromium copy, no Node runtime, no third-party HTTP client and no database. There isn't even auto-update or crash reporting.

What "sufficient" leaves out is worth naming, because the omissions are structural rather than temporary. There are no team workspaces, no shared collections, no OAuth 2.0 browser flows that call back to a local port, no mock servers, no monitors running on a schedule, and no generated client code. Those features all assume a server, an account or a background scheduler. Adding any one of them would put a boundary this project deliberately keeps clean, so they stay out. If your daily work depends on them, another tool is the right answer and this one isn't.

What is left is a workflow that covers whole categories of debugging: verify an API contract while reading someone else's documentation, reproduce a failing request from a bug report, paste a cURL command out of a browser's network tab, hit a local development server without fighting CORS, or save a request collection next to the project it belongs to. Those tasks are frequent and short, and a large client charges startup cost for every one of them.

The boundary has to be stated too. NanoAPI supports its own bundle format, version 1, plus a bare settings file. It doesn't import Postman collections, Bruno, OpenAPI or HAR, and the repository contains no parser for any of them. That's scope control rather than an oversight. A format adapter layer turns "a project one person can maintain on weekends" into "a compatibility layer that is never finished". For migration, users go through cURL, the universal channel, or tidy the JSON by hand.

Architecture: edit in the frontend, execute in the backend

This is a two-layer Wails v2 application. main.go owns the window and the embedded assets, and app.go binds the application struct to the frontend. The internal packages split by responsibility into proxy, interp, curl, store, bundle and model. The frontend lives in a dist directory as one HTML file plus a set of ES modules, with no node_modules and no Vite.

At runtime Wails exposes bound methods on a global object. A small bridge module wraps calls in promises so a synchronous throw becomes a rejection and callers can't forget to catch it.

function call(method, ...args) {
  try {
    return Promise.resolve(backend()[method](...args));
  } catch (err) {
    return Promise.reject(err);
  }
}

That boundary decides the division of labour. The frontend owns tabs, the collection tree, the request editor, response rendering, context menus and shortcuts. The backend owns URL merging, variable interpolation, authentication, multipart bodies, TLS, redirects, timeouts, timing capture, response reading, file saving and bundle import and export.

The frontend never calls fetch directly, so there is no "two sets of network rules" problem. Every bound method returns a promise, handled with await or catch. Because all I/O sits in Go, the frontend never deals with CORS, certificates, cookies or filesystem permissions.

That split also explains why response bodies never touch disk. Wails bindings transfer JSON strings, and a large response crossing that boundary once is enough. Persisting another copy only multiplies memory and disk cost. When a response must be kept, the user clicks save body and goes through the system save dialog.

Frontend state lives in tab objects, each owning its own request and response. Response bodies stay in memory and tab state, never in the data file. A restart restores tabs and unsaved edits, but not the last response. That keeps the data file small and stable, and avoids repeatedly serializing potentially large bodies.

Startup checks whether the backend global exists. If the backend isn't ready the app shows an error page rather than a blank window. A failed initial load raises a toast but initialization continues, so one read error can't block the whole application.

The package map is short enough to hold in your head, which matters when you are debugging a request at odd hours.

main.go          window, embedded assets, startup order
app.go           bound methods: request, history, settings, bundle, files
internal/proxy   URL merge, transport, redirect policy, timing, response read
internal/interp  placeholder parsing and three-level resolution
internal/curl    lexer, option table, import mapping, export quoting
internal/store   JSON data file, field repair, atomic write, debounce
internal/bundle  version-1 export and append-merge import
internal/model   request, response, environment, tab types
frontend/dist    index.html plus ES modules: bridge, api, render, state

One consequence of the split is that the frontend can't cheat. There is no second code path where the renderer opens a socket, and no hidden fetch call in a component. If a feature needs the network, it has to go through a bound method, which means it inherits variable resolution, permission-free file access and consistent error shapes. That constraint is why an editor change can't accidentally invent a second set of transport rules three months later.

The full path of one request

The send button lives in the frontend. It guards against re-entry, records the originating tab key, and after the await finds that tab again and writes the result back to the caller. Switching tabs while waiting therefore can't leak a result into the wrong tab.

async function send() {
  if (state.sending) return;
  const tabKey = state.activeTabKey;
  state.sending = true;
  try {
    const res = await bridge.sendRequest(tab.request, state.activeEnvId, {
      timeoutMs: state.settings.timeoutMs,
      followRedirects: state.settings.followRedirects,
      insecureTls: state.settings.insecureTls,
    });
    const target = state.tabs.find((t) => t.key === tabKey);
    if (target) target.result = res;
  } finally {
    state.sending = false;
  }
}

The backend handler is a one-way pipeline. It takes a snapshot of the store, builds the variable table, resolves the request on a copy, builds the body and its content type, assembles transport options, and sends.

Network failures aren't returned as Go errors. They land in a result object with an error kind, so the frontend can distinguish "the request failed" from "the program is broken". Only program state, such as an unavailable store, travels as a Go error.

Request options use pointer booleans to distinguish "the frontend didn't specify, use global settings" from "explicitly off". Timeout, redirect following and TLS skipping all resolve through settings then defaults, so a single request can override settings without rewriting them.

If building the body fails to read a file, that is also not a Go error. It produces a result with a file error kind and records history as usual, so the frontend shows "file read failed" instead of an unhandled exception. The model holds across the chain: once a request has been attempted, failure comes back as a result.

History stores the original request, never the resolved one, so it keeps placeholders rather than resolved secrets. Response bodies, timings and headers aren't persisted, only status code, size, time and an error summary. History caps at 200 entries, dropping from the tail. Success and failure both record, so history contains 200s as well as timeouts and DNS failures.

Each history entry carries the whole request that produced it: method, URL, parameter rows including disabled ones, header rows, body type and body text, auth type and its fields, and the environment id that was selected at the time. That makes "send this again" faithful. It also makes "send it again in a different environment" possible, which is how you compare a staging response with a production one without retyping anything.

Cancellation is part of the same contract. A running request can be aborted from the interface, which cancels the context and ends the read loop. The result then comes back with an aborted kind rather than a network error, so the interface can stay quiet instead of showing a scary message for something the user did on purpose. The same abort path runs when the window closes, so a request in flight doesn't hold the process open.

The HTTP engine: written, not wrapped

There is no third-party HTTP client. The proxy package uses the standard library directly, because it needs full control over TLS verification, redirect policy, timeouts, connection closing and phase timings. High-level wrappers tend to flatten exactly those.

Layer one is URL merging. A bare domain gets its scheme filled in, then the original query string is parsed and the parameter table is merged in. Same-name keys overwrite, the rest keep their order, and query-form API keys append at the end.

One detail is easy to miss: a bare flag parameter with no equals sign has to keep its valueless state and must not become an empty assignment. The implementation records that with an explicit has-value flag, and the same function is shared by sending and by cURL export, so the two can't drift apart.

Concretely, with the original query string holding a page and a flag, and a parameter table adding a size while overriding the page, the final query keeps the flag bare, applies the override, and appends the new key. Spaces become plus signs and non-ASCII text is percent-encoded.

Layer two is request construction. The timeout and the trace hook have to be attached to the context before the request is created.

ctx, cancel := context.WithTimeout(ctx, timeout)
defer cancel()
ctx = httptrace.WithClientTrace(ctx, &httptrace.ClientTrace{ /* DNS, connect, TLS, first byte */ })
req, err := http.NewRequestWithContext(ctx, method, finalURL, bodyReader)

Reverse the order and the request keeps a parent context with no deadline, which makes the timeout a decoration. That trap gets its own entry in the problem list.

Layer three is transport. Every request clones the default transport, sets the skip-verify flag when the user turned off certificate checks, and closes idle connections when done. Redirect handling does two things: with following off it returns the last response so 3xx bodies surface as-is; with following on it allows at most ten hops and records each hop's URL and status.

Layer four is reading the response. A limited reader takes 20 MB plus one byte. Past that, the body is cut and marked truncated, so memory stays bounded and "exactly 20 MB" is distinguishable from "truncated". Content type, UTF-8 validity and NUL bytes decide whether the body is binary; binary becomes base64, text passes through. Cookies live in a shared jar, and clearing swaps in a new jar rather than deleting entries one by one.

One special case in header writing: the host header is assigned to the request's host field rather than the header map, because the map doesn't participate in host selection. Authentication is applied after headers. Basic auth uses the standard helper, bearer writes the authorization header, and API keys go to a header or a query parameter depending on their placement setting.

Protocol, remote address, redirect count and the phase timings in the result aren't decoration. They let a user see whether a request is slow in DNS, TCP, TLS or time to first byte, and where a redirect went. When the network fails, timings already collected are kept and the frontend says so.

Status text is sliced out of the raw status line, the protocol field records HTTP/1.1 or HTTP/2, and headers stay a multi-value map, so the frontend can show repeated headers on separate lines instead of merging them into one.

Two behaviours are inherited from the standard library on purpose, and both surprise people who have only used high-level clients.

Compression is negotiated, not forced. When the client adds the accept-encoding header itself, it also decompresses the body. When a user writes that header by hand, the transport assumes the caller wants the raw bytes and stops decompressing. The interface then shows what looks like garbage, and the honest explanation is "you took over negotiation". The same rule applies to deflate and brotli, which this build has no decoders for. Both facts live in the known limits, because they are a consequence of the design rather than a bug to patch.

Cookies follow the jar, not the tab. Every request shares one cookie jar, which is what makes a login flow work across three requests typed by hand. Clearing cookies replaces the jar instead of walking its entries, so a stale set can never survive a clear. The trade is that two unrelated hosts in the same session share one jar, which is fine for a local tool and wrong for anything approximating a browser profile.

Variable interpolation: one pass, three levels

The syntax is a double-brace placeholder, matched by a regular expression that allows whitespace. Resolution recurses at most three levels, replacing matching keys each round. It exits early when a round changes nothing, and placeholders still unresolved after three rounds stay as written.

That handles a placeholder inside a path and a variable that refers to another variable, without looping forever on a pair that refer to each other.

A worked example, because the three-level rule is easier to see than to describe. Suppose the environment holds host as a staging domain, base as a placeholder pointing at host, and token as a literal string. A URL of {{base}}/users resolves in two rounds: the first replaces base, the second would resolve anything the replacement introduced. A header of Authorization: Bearer {{token}} resolves in one. Both land in the same request, and neither is written back to the environment or to the request editor.

Rounds stop early when a round changes nothing, which is the common case. That detail matters for performance as much as correctness: most requests have shallow placeholders, so the usual path is one match and one replacement pass over a handful of short strings, not three passes over everything.

Precedence is explicit. All global environments merge first, then the selected environment overrides same-name keys. Global variables are the floor and environment variables are the override. Disabled rows and empty keys are skipped.

For example, with a global base URL and a global token, and the current environment overriding the base URL, a placeholder for the base goes to the environment's host while the token still resolves to the global value. When several global environments share a key, the later merged one wins, and that order follows the environment list.

The three-level boundary matters too. A two-step chain resolves. A longer chain leaves placeholders from the fourth level onward in the unresolved list rather than expanding forever. It's a hard anti-cycle cap, not "try a few more times".

Resolution only ever touches a copy. The clone duplicates the slices that may be rewritten, such as parameters, headers, form fields and file fields, while URL, body and auth fields are copied by value. Resolution covers the URL, parameter keys and values, header values, raw and form and file bodies, plus basic username and password, bearer tokens and API key pairs. Enumerated fields such as method and body type aren't interpolated.

Unresolved variables don't fail the request. It's sent as written, and the names come back in the result. The frontend shows them in red with a note that they were sent as-is. That degradation is deliberate, because during debugging you often need to see how the server responds to an unfilled path rather than being blocked client-side.

cURL both ways: lexing, mapping and warnings

Import doesn't shell out. It ships a small lexer handling single and double quotes, backslash continuations, cmd's caret continuation, the PowerShell prefix and the explicit curl.exe name. The lexer emits tokens, which are then parsed against an option table.

The supported set covers day-to-day debugging: request method, header, data, raw data, binary data, JSON, form, user, OAuth bearer, cookie, user agent, referer, GET redirection, and head. Unknown options are never silently dropped; they land in a warnings list shown with the import result.

Method inference follows cURL's habits. An explicit method wins. A head flag yields HEAD. A form or data flag yields POST. A GET flag moves the data into the query string and returns to GET. The JSON flag sets a JSON body and adds an accept header. When an explicit method conflicts with inference, the explicit one wins.

A few mappings deserve detail.

  • Data and binary data read a file behind an at sign, capped at 20 MB and requiring UTF-8. Raw data keeps the literal and reads nothing.
  • Multiple data flags join with ampersands into one body, matching cURL's form behavior.
  • With a form flag the request becomes multipart. Per-file options such as type and filename are stripped with a warning, because NanoAPI's file fields hold only a key and a path.
  • The insecure flag isn't written into the request. It warns that certificate verification lives in settings.
  • The proxy flag warns and is ignored, because there is no proxy configuration screen.
  • Upload-file, config and client certificates also only warn. The tool never pretends to support them.

Export takes a different path but reuses the same URL builder and the same dedupe rules. Output is a Bash-style command with single quotes, and inner single quotes are replaced by the usual escape sequence. Basic auth becomes a user flag, bearer and header-form API keys become header flags, and multipart becomes form-string for text fields plus form flags for files.

Dedupe removes content-length, transfer-encoding, a hand-written multipart content type, and any authorization or API key header that duplicates the auth section.

Since both directions share one option table, it is worth reading the mapping as a table rather than as a list of rules.

Export reuses the same table in reverse, which is the whole reason the two directions can't drift. A change to how a header row is written during import shows up in export the same day, because it is one function and not two.

Multipart text fields use form-string deliberately, so an at sign or a less-than in the value isn't read as a file reference. File fields use a file form, with the path handed to shell quoting. HEAD exports as a head flag rather than an explicit method, because the explicit form can leave clients waiting for a body that never comes. The quoting helper guarantees safety under Bash only, so export targets Bash, WSL or Git Bash. That's an explicit platform assumption.

This isn't a complete cURL. The goal is to bring the common debugging commands in, not to interpret every part of the cURL language, which makes the warning policy important. Anything unrecognized is reported instead of quietly producing a request that looks right and behaves differently. An unclosed quote returns an error rather than guessing intent.

Upload and download

Uploads assemble multipart bodies on the Go side. Text fields are written directly. File fields are stat-checked first, directories are rejected, a single file is capped at 20 MB and the total at 50 MB, and the body uses the file's base name.

All files are read into memory before assembly, which is exactly why the caps have to exist. One enormous file would otherwise take the process down. File paths are interpolated too, so a placeholder directory works, and resolution happens before sending. A missing path returns a file error.

One step before sending is crucial. If the body is multipart, any user-written content type is dropped. The boundary is generated for this request, so a hand-written one can't match, and keeping it only makes the server fail to parse. Import removes a manual content type when a form flag is present and warns; export skips it for the same reason.

Download runs the other way. The filename is chosen in order: the name in the content-disposition header, then the last segment of the final response URL, then the request name. The header supports both the plain form and the RFC 5987 UTF-8 form.

The chosen name is reduced to a base name, characters that are illegal on Windows are replaced, trailing dots and spaces are trimmed, and the result is capped at 120 runes. Both sides clean the name: the frontend for the suggestion, the backend as the final guard. Image preview has an extra 8 MB ceiling; beyond it, or when the body was truncated, the view falls back to base64 rather than stuffing a huge data URL into the DOM.

Binary responses show as base64, and the backend decodes back to raw bytes when saving. Image responses preview directly when untruncated and small. The viewer therefore needs no renderer per format, and binary data never reaches a text highlighter.

The three caps aren't arbitrary round numbers. Twenty megabytes for a single file keeps one attachment from dominating memory while still covering screenshots, PDFs and small datasets. Fifty megabytes for the total bounds a request body that has to be held in memory and then copied into the transport. Twenty megabytes for a response bounds the string that crosses the binding boundary, which is the step that actually hurts when it gets large. Raising any of them is easy. Raising them without measuring the copy cost is how a debugging tool starts swapping.

Filename sanitation is the kind of code that never gets written until it bites. The backend reduces to a base name so a header can't write outside the chosen directory, replaces the characters Windows rejects, trims trailing dots and spaces that Windows silently drops, and caps the length so a long title plus a quota can't produce a path the filesystem refuses. The frontend runs the same cleanup to suggest a name in the save dialog. Duplicated logic usually means two places to fix a bug, and here it is deliberate: the frontend version exists for convenience, the backend version exists for safety, and only the second one is trusted.

Storage: reliability for a single JSON file

The data file sits under the user's application data directory, derived from the standard config path. It holds collections, environments, global variables, settings, history and open tabs. There is no database, no schema version and no migration framework.

If the config directory is unavailable, the application falls back to the system temp directory so it still starts, with no persistence across restarts.

Reads do no whole-file validation, only per-field repair. A timeout of zero or less resets to the default, an empty theme resets to the default, and nil collections, environments, history and tabs become empty slices. One bad field therefore can't cost the user their chosen theme.

The repair pass is deliberately short, and each rule exists because a specific value would break the interface downstream. A negative timeout would make every request fail instantly with an aborted kind that looks like a network fault. An unknown theme name would render the app with no colors at all. Nil slices would turn every list render into a null check spread across the frontend. Repairing four things is cheaper than defending against them at twenty call sites.

If JSON parsing fails, the original file is renamed with a corrupt marker and a timestamp, and the app starts empty. Nothing is deleted, so manual repair or restoring a backup stays possible.

Writes are debounced by 300 ms, so typing doesn't hit the disk. The actual write creates a temporary file in the same directory, writes, syncs, closes, then renames over the target, so a process exiting mid-write leaves no half-written JSON.

Snapshots return slice copies so callers can't mutate underlying data while it is being serialized. That copy looks fussy and is the core of concurrency safety: while a request runs in the background, the frontend may be editing collections or environments, and serialization has to work from a stable copy.

Close performs a final flush, and closing the window also triggers the frontend's tab save. Both paths use the same atomic write, so there is no separate close-time logic. History keeps 200 entries, and bodies and timings never persist. The file usually stays small, and "you can see the previous response after restart" is explicitly not a capability.

Bulk edit and backups

Bulk editing of environment variables is pure frontend logic. Input is dotenv-style key-value text. Parsing skips blank lines and comments, drops an export prefix, supports single and double quotes, and inside double quotes resolves newline, carriage return, tab, escaped quote and escaped backslash.

Duplicate keys take the last line, and invalid lines are counted without blocking the import. Existing variables keep their enabled flag and their description, so one bulk paste can't wipe notes someone wrote carefully.

Formatting is the reverse. Values containing newlines, tabs, leading or trailing spaces, or already quoted, get double quotes and escaping. Frontend tests cover parse-format round-trip consistency, which catches quote and escape edge cases that single-line tests miss.

For example, given an export line, a quoted value with an escaped newline, a comment and a line with no equals sign, parsing yields two variables and one invalid count, and the escaped newline becomes a real line break. A repeated key overrides the earlier one while preserving its flags.

Backups use only the project's own format, version 1, exporting collections and environments but never history, settings or tabs. Import caps at 32 MB and also accepts a bare settings file.

Import isn't overwrite but append-merge. The collection tree generates fresh ids recursively, so nodes can't collide. Environments get fresh ids, with an "imported" suffix on name clashes and a number after that. Global variables exist once only, merging by key with existing values winning, duplicates skipped and a count reported.

To repeat: this import recognises no Postman collection, no Bruno, no OpenAPI and no HAR. No format sniffing, no field mapping. If you hold a Postman export, the path is to export cURL and import that, or convert the JSON by hand.

Problem list one: four network traps

Problem 1: the timeout appeared to do nothing

Symptom. Set a 200 ms timeout against an endpoint that takes two seconds. The client still waits two seconds and reports something other than a timeout.

Cause. The original code created the request first and attached the timeout and trace afterwards. The request keeps the deadline-free context it was built with, and deriving a new context later doesn't affect it. The timer was never on the executed path.

Fix. Reorder: timeout first, trace second, request third. A test now asserts that a 200 ms timeout against a two-second server reports a timeout error kind.

Cost. Every request creates and cancels a context, which makes the code path wordier. And the timeout is a deadline for the whole request, including DNS, connect, TLS, first byte and body read, not a connect timeout. Per-phase limits aren't configurable; the timing panel is how you inspect phases.

Problem 2: a specific redirect error swallowed by a generic one

Symptom. Following redirects into an endless loop shows "network error" rather than "more than ten redirects", and the internal error kind becomes the generic network kind.

Cause. The redirect check noticed the hop limit, wrote a specific error into the result, and returned an error. The HTTP client wrapped that error, and the outer handler then overwrote the result fields with a translated generic error. A specific error lost to a vaguer one.

Fix. In the error branch, check whether the result already carries the specific redirect kind and keep it. A test asserts both the kind and the message survive.

Cost. Error handling now has a branch for one specific kind, coupling the redirect callback to the outer handler. Any future "write the result inside a callback" error type has to remember the same guard.

Problem 3: Windows connection errors didn't match the message table

Symptom. Connecting to a closed port is recognized as connection refused on Linux and falls into the generic network error on Windows. Same condition, different text per platform.

Cause. Classification originally matched Linux strings. On Windows the same condition surfaces as "actively refused" or "no connection could be made", so string matching failed. The underlying error is also wrapped by operation and URL error types, which makes the outermost text unreliable.

Fix. Extract the operation error, then try the syscall errno and compare against the refused, reset and timed-out codes. When no errno is available, fall back to lowercase text matching covering both Windows phrasings.

Cost. String fallbacks are fragile across system languages and Go versions, and can misclassify unrelated errors that happen to contain the phrase. The errno path is primary and strings are insurance.

Problem 4: self-signed certificate errors looked like network failures

Symptom. Hitting a self-signed HTTPS service shows a network error, with no hint that certificate verification can be turned off in settings.

Cause. TLS error types vary across Go versions. Besides an unknown authority error there are certificate verification and hostname errors, usually wrapped in a URL error. Checking one type misses most certificate problems.

Fix. Classify by matching the verification, hostname and unknown-authority types in order, then fall back to certificate and TLS substrings, all mapping to one TLS kind that the interface renders as a certificate error.

Cost. Substring fallbacks can misread a server error that mentions TLS as a certificate problem. And the project has no client certificates, no CA import and no chain inspection, so enterprise mutual TLS means using something else.

Problem list two: four Windows and cURL traps

Problem 5: the shell lexer ate Windows paths

Symptom. Importing a form field that references a Windows path loses the backslashes, and the file isn't found.

Cause. The lexer treated backslashes as escapes by shell rules. Rules meant for backslash, escaped quote and doubled backslash also swallow the backslash before ordinary letters, which destroys Windows paths, and Windows users rarely add extra quotes.

Fix. Escape only spaces, tabs, quotes, backslash, dollar signs and backticks. Keep the backslash for every other character. A test pins the behavior with a Windows path.

Cost. One lexer serves both POSIX shell habits and Windows habits, so the semantics can't be identical. An unquoted path containing spaces still splits into tokens, and an escaped n inside double quotes is still a newline rather than a path fragment.

Problem 6: cmd's caret continuation wasn't recognized

Symptom. Copying a multi-line cURL command out of a cmd window, where lines end with a caret, produces shifted arguments or a parse failure.

Cause. The lexer knew backslash continuations and plain newlines but not the caret. And Windows text can carry CRLF, so a caret followed by CRLF was never treated as one continuation.

Fix. The caret branch handles both line ending forms as continuations, while a standalone caret stays literal. The PowerShell prefix and the explicit executable name are accepted too, which covers commands copied from PowerShell.

Cost. Only continuation is implemented, not cmd's full escaping. Variable expansion, command separation and caret-escaping of other characters aren't simulated, so complex batch commands still warn or parse imperfectly.

Problem 7: cURL options that look alike but aren't

Symptom. Users assume that data and raw data both read a file, then the latter sends a literal at sign path. Or they assume the insecure flag disables certificate checks, and importing leaves settings untouched.

Cause. These differences belong to cURL. Data and binary data read files behind the at sign, while raw data explicitly keeps the literal. The insecure flag is a per-run TLS option in cURL, whereas certificate verification here is a global setting that one command should not silently change.

Fix. Dispatch by option name. Data flags read files, capped and UTF-8 validated. Raw data keeps text. The insecure flag only warns and points at settings. The urlencode flag imports verbatim with a warning that no encoding was applied.

Cost. Option semantics live in a lookup table that has to grow with each new option. Standard input, config files, client certificates and proxies are unsupported. And users may ignore warnings, especially when pasting a large command.

Problem 8: a hand-written multipart boundary conflicted with the server

Symptom. Writing a multipart content type by hand with a boundary, then choosing multipart upload, makes the server fail to parse or receive fields.

Cause. The writer generates the boundary at send time, so a hand-written one differs from the one actually used. Mismatched header and body are rejected by any strict server.

Fix. After building the body and before sending, if the body is multipart, delete the content type from the header copy and use the generated value. Import removes a manual content type when a form flag is present and warns; export skips it as well.

Cost. Users lose the ability to customize the multipart content type, for example to set a charset. That's the intended trade: making a wrong configuration impossible beats preserving a freedom that usually produces errors.

Problem list three: four desktop traps

Problem 9: a per-request transport gives up keep-alive

Symptom. Consecutive requests each re-establish a connection, so load runs and batch debugging take longer than expected. Sharing a transport without closing it, on the other hand, leaves idle connections hanging until timeout.

Cause. The application must switch certificate verification per request, and TLS configuration belongs to the transport, which can't be safely mutated on a shared one. Sharing would also let one request's TLS policy leak into another. Per-request transports mean no connection reuse.

Fix. Clone the default transport per request, set its TLS configuration, and close idle connections when the request finishes. Connection lifetime is bound to the request, nothing hangs, and TLS policies stay separate.

Cost. No keep-alive reuse. Consecutive requests repeat DNS, TCP and TLS. That's acceptable for a debugging tool and poor for high-frequency batch calls. Getting both reuse and per-request TLS would need a transport pool keyed by policy, a clear step up in complexity.

Problem 10: large responses froze the webview

Symptom. A multi-megabyte JSON response makes the response pane unresponsive and the editor laggy. A large request body triggers validation on every keystroke and stutters as well.

Cause. The renderer parsed, formatted and highlighted the entire body, and live validation ran on every input. At scale, string processing and DOM construction dominate the main thread.

Fix. Three thresholds. Response reads cap at 20 MB, truncated with a notice. Bodies over 1 MB skip prettifying and highlighting and show raw text. Request bodies over 512 KB skip live validation, debounced to 200 ms. Truncation propagates to the save dialog, which says so.

Cost. Responses over 20 MB are never fully available, and saving keeps the truncated part. JSON over 1 MB loses folding and color. Request bodies over 512 KB stop reporting syntax errors, which then wait for the server.

Problem 11: an interrupted process left half a JSON file

Symptom. Killing the application mid-write makes the data file unparsable on restart, and collections and environments disappear.

Cause. Overwriting the target in place isn't atomic. Exiting mid-write leaves invalid JSON, and a reader with no recovery strategy shows empty data.

Fix. Write a temporary file, sync it, close it, then rename over the target. On a read failure, rename the original with a corrupt marker and start empty. Fill defaults per field, so one bad field can't sink the whole configuration. Tests assert that every flush leaves valid JSON, that no temporary files remain, and that a corrupt file is backed up and recoverable.

Cost. No schema version means field upgrades rely on filling what is missing and ignoring what is unknown, with no real migration. Corruption recovery is "keep the file, lose the data", which needs manual repair. And a 300 ms debounce can lose the last few hundred milliseconds of edits, which the forced flush on close only partly compensates.

Problem 12: ids, name clashes and global variables after import

Symptom. Importing a backup twice produces duplicate collection nodes where deleting one affects the other, two identically named environments that can't be told apart, and global variables overwritten wholesale.

Cause. Bundle nodes carry their original ids and collide when appended. Environment names have no uniqueness constraint. And global variables are supposed to exist exactly once, so appending them as ordinary environments creates a second copy.

Fix. Collection nodes get fresh recursive ids, and request nodes gain default method, body type and auth type. Environments get fresh ids with an imported suffix and an incrementing number. Global variables stay single, merging by key with existing values winning, duplicates skipped and counted in a warning.

Cost. Import appends rather than deduplicating, so the same backup imported twice still yields two collection sets; only the ids avoid collision. Renamed environments change what the user sees, and "existing value wins" can silently ignore newer values from the backup, leaving only a count in the warning.

Build and release: the cost of one exe

The build command deliberately bypasses the frontend toolchain.

wails build -platform windows/amd64 -s -skipbindings -webview2 browser

The size flag skips the frontend build, the bindings flag skips generating bindings, and the frontend calls through the runtime global instead. Frontend files are embedded, so the artifact is a single executable with no asset directory beside it.

The release script then drives the NSIS template and WiX to produce a portable executable, an NSIS installer and an MSI. The script writes the version into the Wails config before building and restores it afterwards; the portable executable gets its version through a linker flag, while installer metadata comes from the config. The two version sources must stay in sync, or the settings page and the file properties disagree.

The three artifacts serve three distribution stories: the portable build for running anywhere, NSIS for Start Menu and desktop shortcuts plus WebView2 bootstrapping, and the MSI for domain deployment and silent installs.

For version 0.1.0 the portable executable is 11,341,824 bytes, NSIS about 6.3 MB and MSI about 4.5 MB. Three files solve three distribution scenarios, not three feature levels.

The path also surfaced two classic Windows engineering problems. Line endings: running the formatter check on a Windows runner fails on CRLF, so a commit added a gitattributes entry to normalize to LF. MSI shortcuts: WiX enforces component ownership rules for shortcuts, and the first definition failed until a later commit reorganized components and shortcuts.

The costs extend to distribution reality. There is no code signing, so SmartScreen warns about an unknown publisher. The MSI requires WebView2 to be present, while NSIS tries to install it. And the version must be synced between the config and the linker flag. A single executable buys simplicity for users and more manual constraints in the build chain.

Known limits

Compression isn't handled directly. Go's transport only decompresses automatically when it added the accept-encoding header itself. If a user writes that header by hand, the transport won't decompress on their behalf, and NanoAPI has no brotli or deflate decoder, so the pane shows raw compressed bytes. It isn't "gzip unsupported". It's "don't write that header, let the transport negotiate".

Sensitive headers follow the standard redirect policy. Authorization is dropped on a cross-origin hop, and the application neither replays it nor tells the user that it was removed. Same-origin hops are usually fine, but cross-origin debugging produces the classic "it worked, then 401 after the redirect".

Proxies are inherited implicitly. Because transports are cloned from the default one, the environment proxy function still applies, so the usual proxy variables affect requests. There is no proxy screen, and the cURL proxy flag only warns. Anyone with proxy variables set may egress from an unexpected place.

Import formats are closed. Only the project bundle, version 1, and a bare settings file. No Postman, Bruno, OpenAPI or HAR, with no sniffing and no migration wizard.

There is no schema version. Upgrades rely on per-field defaults and ignoring unknown fields, so the file can't express when a field became meaningful, and destructive migration is unsafe.

The capability boundary also includes no client certificates or custom CAs, no custom multipart content type, a hard 20 MB response cap, and history limited to 200 entries without bodies.

Each of those has a workaround, and each workaround has a cost worth knowing in advance.

One more boundary is easy to miss. History stores the original request, so placeholders never become plaintext secrets, but a token typed directly into a URL or a header does land in the data file as plaintext. The tool does no field-level encryption and makes no promise against a local reader.

What those leftovers share is that each needs extra infrastructure: decompression needs an encoding library, auth replay needs a custom redirect policy, proxies need a settings screen, format compatibility needs adapters, and schema versioning needs a migration framework. None of them is a one-line change.

Closing

NanoAPI compresses into three sentences. Rendering belongs to the system WebView2, network and files belong to the Go standard library, and the frontend stays dependency-free native modules. It never tries to replace Postman. It makes the most common debugging path solid: request construction, variables, cURL, upload and download, response inspection and single-file storage.

What decides quality isn't the feature list but the unglamorous failure paths. A timeout has to be attached to the right context. A specific redirect error must not be overwritten by a generic one. Windows connection errors and paths need their own handling. Multipart boundaries must not be user-supplied. Writes must be atomic and corruption must leave evidence. Large responses must be bounded at read, render and validate.

Its leftovers are equally explicit: no brotli or deflate decoding, no auth replay across origins, proxies inherited from the environment, a closed import format, and no schema version. Saying so plainly is worth more than claiming everything is supported. A sufficient tool should tell you where it is sufficient and where it isn't.

None of these conclusions came from reading code and guessing. Timeouts, redirects, paths, storage and import all have unit tests or reproducible mock servers, so breaking any one of them fails the tests first.
