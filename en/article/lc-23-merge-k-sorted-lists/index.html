LC 23, merging k sorted lists: how many nodes belong in the heap

2026-09-22 · 17 min · Stack Frame

The problem

Given an array of sorted lists, merge them into one sorted list.

input:  [[1,4,5],[1,3,4],[2,6]]
output: 1 -> 1 -> 2 -> 3 -> 4 -> 5 -> 6

The constraints matter more than the statement: k can reach ten thousand, but the total number of nodes across all lists does not exceed ten thousand. Those two numbers together already hint at where the naive approach dies.

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

Pricing the work first

This is the k-ary version of the previous problem, whose merge looks like this:

def mergeTwoLists(l1, l2):
    dummy = ListNode(0)
    tail = dummy
    while l1 and l2:
        if l1.val <= l2.val:
            tail.next = l1
            l1 = l1.next
        else:
            tail.next = l2
            l2 = l2.next
        tail = tail.next
    tail.next = l1 if l1 else l2
    return dummy.next

Nothing in those eight lines changes here. The questions are how many times to call it and how to organise the calls.

Sequential merging

def mergeKLists(lists):
    if not lists:
        return None
    result = lists[0]
    for lst in lists[1:]:
        result = mergeTwoLists(result, lst)
    return result

Correct, and slow. The nodes merged early are walked again in every later round.

With k lists each of length n, the i-th round walks about i times n nodes already merged plus the next list, and summing over the rounds gives a total around N times k over two. That is quadratic in k, not linear: each round costs more than the last, and there are k rounds, so the two multiplications compound.

Concretely, with a thousand lists of ten nodes, sequential merging performs 4,543,137 comparisons, while divide and conquer over the same input performs 97,987. A factor of forty-six.

Divide and conquer: reduce the rounds to a logarithm

round 1: k lists    -> k/2 lists
round 2: k/2 lists  -> k/4 lists
...

Pair them up instead of appending one at a time. The count halves each round, so there are logarithmically many rounds, and in each round every node is touched exactly once. Multiply: linearithmic in the total.

For a thousand lists that is about ten rounds instead of nine hundred and ninety-nine.

A min-heap: change the selection instead of the order

The earlier observation still holds with k lists: the global minimum is always among the current heads. So the requirement is a structure that accepts a value and returns the minimum, which is exactly what a heap does.

Each node is pushed once and popped once, so two N heap operations, each logarithmic in the heap size. The heap never holds more than k elements, so it is the logarithm of k, not of N. Total time is N log k, with k extra space.

The three accounts side by side

Asymptotics hide constants, and for small k the constants decide. A counting script implements all three and counts actual comparisons using an instrumented key, rather than timing, because counting is deterministic arithmetic: the same input gives the same number regardless of machine load, whereas timing on this machine has a noise floor of twelve percent reaching fifty-seven across sessions.

That is the quadratic term isolated in one column.

Two counterintuitive facts show up in the same table. At four lists, sequential merging is only fourteen percent slower than divide and conquer, while the heap is sixty-four percent slower: a heap is not a silver bullet, and building, sifting up and sifting down are real comparisons that cost more than pairwise merging when k is small. And divide and conquer beats the heap at every size, despite the same asymptotic class, for a reason covered below.

The heap: the point is not the heap, it is how much goes in it

Since the requirement is to repeatedly take the minimum, one tempting approach is to push all N nodes and pop them one by one. The result is correct and the time is N log N, which means paying for a full sort of data that is already sorted in k places. That throws away the condition the problem gave you.

The correct version keeps only the k heads:

import heapq

def mergeKLists(lists):
    dummy = ListNode(0)
    tail = dummy
    heap = []

    for i, head in enumerate(lists):
        if head:
            heapq.heappush(heap, (head.val, i, head))

    while heap:
        val, i, node = heapq.heappop(heap)
        tail.next = node
        tail = tail.next
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))

    return dummy.next

The heap never exceeds k elements. That is the entire source of the k inside the logarithm, and it is worth stating out loud in an interview, because it is the dividing line between memorising and understanding.

Four details, each a trap. The index in the tuple is not decoration: Python compares tuples element by element, so with equal values it would compare the nodes, and a node class without an ordering raises a type error. A distinct integer short-circuits the comparison at the second element, and it also makes the output deterministic, since equal values then arrive in list order. Second, Python heaps are min-heaps, which is what this needs; a max-heap requires negating the values. Java is the same, despite the naming often confusing people. Third, building the heap incrementally is k log k versus linear with heapify, which is a constant factor here. Fourth, empty lists must be skipped before the value is read.

Two things to notice. The array after building is not in sorted order, only in heap order, which guarantees a parent is no larger than its children; do not read the array as a sorted result. And the last four rounds push nothing, because those lists are exhausted, so the heap shrinks from four to zero, showing that its size is dynamic with k as the bound.

Edge cases fall out rather than being handled: an empty array never enters the build loop, an array with one empty list is skipped, empty lists mixed in are ignored, and a single list degenerates to a linear walk. Equal values are ordered by list index, which is deterministic though not stable, and stability is not required here.

public ListNode mergeKLists(ListNode[] lists) {
    ListNode dummy = new ListNode(0);
    ListNode tail = dummy;
    PriorityQueue<ListNode> heap =
        new PriorityQueue<>((a, b) -> Integer.compare(a.val, b.val));

    for (ListNode head : lists) {
        if (head != null) heap.offer(head);
    }
    while (!heap.isEmpty()) {
        ListNode node = heap.poll();
        tail.next = node;
        tail = tail.next;
        if (node.next != null) heap.offer(node.next);
    }
    return dummy.next;
}

Java puts the nodes in directly and needs no index, because the comparator is explicit, so the comparison never falls through to the node objects. That is the one genuine difference between the two languages here.

Divide and conquer

That is the merge tree of merge sort, upside down. Every level holds all eight nodes, and only the grouping changes: singletons, then pairs, then quads. The number of rounds is the logarithm of k, which is much clearer from the picture than from the formula.

def mergeKLists(lists):
    if not lists:
        return None
    return merge_range(lists, 0, len(lists) - 1)

def merge_range(lists, lo, hi):
    if lo == hi:
        return lists[lo]
    mid = (lo + hi) // 2
    left = merge_range(lists, lo, mid)
    right = merge_range(lists, mid + 1, hi)
    return mergeTwoLists(left, right)

Read it as a contract: merge the slice from lo to hi and return its head. Split the slice, let each half fulfil the contract, then combine with the eight lines from the previous problem. The recursion depth is the logarithm of k, so the stack is small, about fourteen frames even at ten thousand lists, which is actually less space than the heap.

def mergeKLists(lists):
    if not lists:
        return None
    level = lists
    while len(level) > 1:
        nxt = []
        for i in range(0, len(level), 2):
            if i + 1 < len(level):
                nxt.append(mergeTwoLists(level[i], level[i + 1]))
            else:
                nxt.append(level[i])
        level = nxt
    return level[0]

The bottom-up version needs no stack. Its trap is the odd list out: when the count is odd, the last list has no partner and must be carried into the next round unchanged. Writing the append only inside the paired branch silently drops it, and only reproduces when k is odd, which is why it survives casual testing.

One subtlety: an unpaired list is not touched at all, so the per-round cost is bounded by N rather than equal to it. The counting script measures nodes actually visited, not an estimate from N.

Why divide and conquer compares less at the same complexity

At a thousand lists, divide and conquer makes 97,987 comparisons and the heap 116,530. The difference is how many comparisons each node incurs. In the heap, every node is pushed and popped, and each operation walks about log k levels with one comparison per level, so roughly twice the logarithm. In divide and conquer, each node takes part in one merge per round and is compared at most once per round, so roughly the logarithm. The extra factor is the cost of maintaining the heap structure itself.

The heap has an advantage the other does not, visible as node visits: divide and conquer touches each node once per round, so about log k times in total, while the heap touches each node exactly twice. On a linked list, moving a node is a pointer assignment, so this does not affect the complexity. On an array it would be a real copy, and the heap would win outright. Being able to explain that difference is worth more than reciting two identical bounds.

For very small k, use sequential merging: the shortest code, comparable comparisons, and no heap to build. Do not reach for a heap to look sophisticated. For large k and large N, either of the other two works; divide and conquer compares less and uses less space, while the heap is a more natural fit for streaming, such as an external merge sort or k sources that cannot all be held in memory, since it holds only k heads where divide and conquer holds everything.

In an interview, offer one of them and then add that sequential merging is better when k is small. That sentence demonstrates judgement rather than recall.

Common mistakes

  1. The tuple type error from pushing value-node pairs without an index, which fires on the first duplicate value. This is the most common failure in the Python version.
  2. Pushing all N nodes, which is correct and degenerates to a full sort.
  3. Not skipping empty lists when building, which dereferences nothing.
  4. Forgetting to push the next node after a pop, which empties the heap early and truncates the output.
  5. Dropping the odd list in the divide and conquer version, which reproduces only for odd k.
  6. No guard for an empty array, which indexes out of range in the sequential and divide and conquer versions, though the heap version is protected by its loop condition.
  7. Forgetting the empty guard in the recursive version, which recurses into an invalid range.
  8. Assuming the Python heap is a max-heap. It is a min-heap, and so is the Java priority queue by default.

How to answer it

Thirty seconds, heap version: maintain a min-heap of the k current heads, pop the smallest onto the result, push the next node from that same list. The heap never holds more than k elements, each node enters and leaves once at logarithmic cost, giving N log k time and k space. The nodes behind the heads never enter the heap, and that is where the k inside the logarithm comes from.

Expect these follow-ups. Why not N log N: because only the heads are in the heap; putting everything in is a full sort and wastes the given ordering. Which is better: the same class, divide and conquer compares less and uses less space, the heap touches nodes less and suits streaming. Why is sequential quadratic: the i-th round walks everything already merged. What about small k: sequential wins, measured at fourteen percent behind divide and conquer against fifty percent ahead of the heap. Why the index in Python: tuple comparison falls through to the nodes and they are not orderable. And empty lists: skipped at build time, with the empty array handled by the loop condition.

Closing

The lesson is that one unchanged subroutine yields an order of magnitude depending on how it is called. Keep the eight lines and append one list at a time and the cost is quadratic in k; pair them up and it becomes linearithmic; keep only the heads in a heap and it is linearithmic with a streaming capability. The hard part was never the eight lines, it is how you choose to invoke them.

And the second lesson is the measurement table: asymptotics describe what happens as k grows, not who wins at four. A better asymptotic class does not mean the heap is faster on every input, and here it is the slowest of the three at four lists. Asked which one to pick, answer with the size of k.

The previous two articles said that pointer work is boundary maintenance and that a dummy turns special cases into ordinary ones. This one says the complexity depends on how you call the subroutine, which closes the linked-list sequence.
