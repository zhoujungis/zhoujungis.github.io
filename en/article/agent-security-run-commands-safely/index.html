Agent security: letting it run commands without losing control

2026-10-28 · 36 min · Stack Frame

Who this is for: people about to point a coding agent at a real repository on a real machine; people who have been startled by "it deleted my files"; people who want to know which of the four layers, permission mode, approval, hooks and a kernel sandbox, is actually stopping what.

TL;DR: security here is not a switch but five independent gates: the tool list, the permission mode, PreToolUse hooks, command approval and a Landlock sandbox. Each narrows the next, and none depends on another to catch it. Measured against real cases, the weakest link is not the sandbox. It is that the sandbox covers child processes only, never the built-in file tools.

Security is five gates, not a switch

The usual approach is a --safe flag. That always fails, because the problem is not one-dimensional:

  • The model wants to call a tool that should not exist.
  • It calls a legitimate tool with a path outside the workspace.
  • Its command looks read-only but writes files.
  • It genuinely needs to run something dangerous, but not without a human agreeing.
  • The command is legal, and the child process it spawns does something else.

Five situations, five interception points. So the right definition of security is a sequence of gates, one per dimension, none of which relies on another to catch it. NanoHermes has five: the tool list, the permission mode, PreToolUse hooks, command approval and a Landlock sandbox. They span the whole stack from JSON generation to kernel syscalls, which is the point: when one is bypassed, the next still stands.

The five gates and how each one fails

#GateWhereBlocksIf it fails
1Tool list filteringbuild_toolsThe model never sees a banned toolThe model tries anyway and gate 2 stops it
2check_toolFirst line of executeMode bans, deny list, allow listAny tool can run
3PreToolUse hookMiddle of executeA user script's non-zero exitUser policy is inert
4Command approvalrun_command, git_commitNon-read-only commandsDangerous commands run unconfirmed
5Landlockpre_exec in the childWrites outside the sandboxA child can write anywhere

The coverage is nested, not parallel. Gate one is advertising and does no blocking. Gates two and three are per tool call. Gate four is per command. Gate five is per spawned process.

Which produces the single most important conclusion in this post: the built-in file tools, read_file, write_file, edit_file and apply_patch, are governed by gates two and three only. Approval and the kernel sandbox cannot stop the agent from writing to /etc/ with write_file, because no child process is ever spawned.

Permission modes: what each actually blocks

ModeIntentBlocked toolsauto_approvePolicy
defaultNormal workNoneFrom configFrom config

debugReproduce without breakingWrites, patches, commitFrom configFrom config

accept-edits is the counterintuitive one. The name suggests loosening, and the implementation forces auto_approve to false, because in this mode only file edits skip the prompt, and "commands are still asked" has to be guaranteed explicitly. Inheriting auto_approve: true would turn the mode into "ask nothing".

/// AcceptEdits always keeps shell confirmation on; Goal has nobody to
/// ask, so it never blocks; the rest inherit the configured flag.
pub fn auto_approve(self, configured: bool) -> bool {
    match self {
        PermissionMode::AcceptEdits => false,
        PermissionMode::Goal => true,
        PermissionMode::Default | PermissionMode::Plan | PermissionMode::Debug => configured,
    }
}

goal is the only mode that gives up human supervision on purpose. It forces approval on and policy to never, on the stated grounds that there is nobody around to ask. That is honest: better to declare no asking than to pretend and always time out.

plan and debug differ on run_command. Plan blocks it, debug allows it, because plan means reading and thinking while debug means reproducing. Both block file writes, so their danger is orthogonal rather than ordered: debug allows arbitrary code execution, plan does not.

What the default configuration really does

auto_approve: true,
approval_policy: ApprovalPolicy::Untrusted,
sandbox: SandboxMode::Off,
permission_mode: PermissionMode::Default,

auto_approve defaults to true, and needs_approval starts with a short circuit that returns false when it is set. So the default untrusted policy, which would ask about every command, never runs. sandbox: Off means Landlock is never attached.

Run the binary with no flags and the real posture is: every tool available, no command questioned, no filesystem restriction. The help text, meanwhile, says the policy behaves as "untrusted with -y", which reads as if -y makes it untrusted, when -y sets the policy to never and approval to true. The opposite of what it says.

That is not a cosmetic documentation issue. A user reading the help concludes the default is to ask; the default does not ask. A wrong default in security configuration is far more dangerous than a missing feature, because it makes people believe they are protected.

Two fixes, neither complex: default to auto_approve: false with on-request, letting -y loosen it; or keep the behavior and print the posture in a startup banner, every time, not only under a status flag.

The first gate: three layers in check_tool

pub fn check_tool(&self, name: &str) -> Result<(), String> {
    // 1. hard block from the mode
    if self.permission_mode.blocked_tools().contains(&name) {
        return Err(format!(
            "tool `{name}` is not available in {:?} mode",
            self.permission_mode
        ));
    }
    // 2. the deny list always wins
    if self.disallowed_tools.iter().any(|t| t == name) {
        return Err(format!("tool `{name}` is disallowed by configuration"));
    }
    // 3. the allow list only applies when non-empty
    if !self.allowed_tools.is_empty() && !self.allowed_tools.iter().any(|t| t == name) {
        return Err(format!("tool `{name}` is not in the allowed list"));
    }
    Ok(())
}

The mode comes first because it expresses this turn's intent, and intent outranks preference. In plan mode, adding write_file to the allow list does nothing.

The deny list beats the allow list, matching security convention: an explicit prohibition usually exists because something already went wrong.

An empty allow list means everything is allowed, not nothing. That is a semantic trap: to restrict to reading you must list all four reading tools, and forgetting one looks like a broken tool rather than a hole. It fails closed in the sense that the surface shrinks, but it does not fail intuitive.

The return value has two destinations: build_tools uses it to hide tools entirely, and execute uses it to return an error string. Both are needed, because a model may recall a tool name from history or hallucinate one.

Allow and deny lists: order decides meaning

Mode blockDenyAllowResultWhy
HitAnyAnyRejectedThe mode wins
MissHitAnyRejectedDeny beats allow
MissMissEmptyAllowedEmpty means unrestricted
MissMissHitAllowedThe list permits it
MissMissMissRejectedNon-empty means exclusive

A subtler problem: the lists match tool names, not capabilities. Denying run_command does not stop git_commit from running git, and does not stop subagent from starting something that writes files. Banning a name bans an entrance, not a capability.

PreToolUse hooks: a tool chain with a veto

for hook in self
    .cfg
    .hooks
    .iter()
    .filter(|h| h.event == HookEvent::PreToolUse && h.matches(&call.name))
{
    match hooks::run(hook, &call.name, &args, &self.cfg.workspace) {
        Ok(o) if o.ok() => {}
        Ok(o) => {
            return format!(
                "ERROR: `{}` blocked by PreToolUse hook (exit {}):
{}",
                call.name, o.code, o.output
            )
        }
        Err(e) => return format!("ERROR: PreToolUse hook failed: {e}"),
    }
}

Any non-zero exit is a refusal, whether it means "denied" or "the script crashed". That is fail closed, and it is right: a crashing hook is not an opinion.

Hook output goes back to the model verbatim, so a hook can also explain policy, like "do not edit files under src/generated". It is an interceptor and a channel at once.

PostToolUse has no veto, only an appended note, because refusing after the fact would leave history claiming a blocked operation that already happened.

h.matches supports wildcards, so a hook can cover every write_* tool without listing names.

The edges of a hook: 30 seconds, no sandbox, trusted config

A hard 30 second timeout, after which the child is killed and the exit code recorded as -2, which counts as non-zero and therefore as a refusal. A stuck hook cannot hang the agent forever, and cannot be read as approval.

One implementation detail: the timeout branch kills only the direct child. If the hook spawned its own background service, the drain threads wait for pipe EOF, which means they wait for the grandchild. "30 seconds" is not true for that pattern.

Hooks run unsandboxed. hooks::run sets a working directory, two environment variables and three pipes, and never calls sandbox::attach. That is defensible, since hooks come from user configuration, but it means sandbox: read-only does nothing for them. A hook script that clones a repository writes outside the workspace.

The failure path leaks threads. When try_wait errors the function returns immediately, and the two spawned drain threads are neither joined nor dropped, so they keep running to EOF. Rare, since try_wait only fails when the underlying call does, but in a long-lived daemon a leaked thread per failure adds up.

Approval policy: three values and one short circuit

pub fn needs_approval(auto_approve: bool, policy: ApprovalPolicy, command: &str) -> bool {
    if auto_approve {
        return false;
    }
    match policy {
        ApprovalPolicy::Never => false,
        ApprovalPolicy::Untrusted => true,
        ApprovalPolicy::OnRequest => !is_trusted_command(command),
    }
}
PolicyAsksTypical use
neverNeverFull trust or unattended
on-requestOnly non-read-only commandsEveryday work
untrustedEverything, including lsFirst contact with an unfamiliar repository

The auto_approve short circuit overrides every policy, which is how a mode can force trust.

untrusted asking about ls sounds safe and produces approval fatigue. After forty prompts a user presses y without reading, and the one dangerous command rides along. Alert fatigue is the classic failure of security design, and this policy is its textbook case.

on-request is the better default, and its quality rests entirely on how accurate is_trusted_command is.

Six tests inside is_trusted_command

pub fn is_trusted_command(command: &str) -> bool {
    let cmd = command.trim();
    if cmd.is_empty() {
        return false;
    }
    // 1. any control operator, redirection or substitution is untrusted
    if cmd.chars().any(|c| {
        matches!(
            c,
            '|' | '&' | ';' | '<' | '>' | '`' | '$' | '(' | ')'
        )
    }) {
        return false;
    }
    // 2. skip leading KEY=VALUE assignments
    let program = loop {
        match tokens.next() {
            Some(t) if is_env_assignment(t) => continue,
            Some(t) => break t,
            None => return false,
        }
    };
    // 3. judge by basename
    let program = program.rsplit('/').next().unwrap_or(program);
    // 4. git goes through a subcommand list, everything else by binary name
    if program == "git" {
        return git_subcommand_is_read_only(&mut tokens);
    }
    TRUSTED_BINARIES.contains(&program)
}

The first two tests are sound. The operator list covers pipes, background and logical-and, command separators, both redirections, backticks, dollar signs, subshells and newlines. The last one blocks "harmless first line, rm -rf / second line".

Crucially, the check runs on the whole command string before tokenizing, so those characters are caught wherever they appear, including inside quotes. That is far more reliable than inspecting tokens, because quoting and escaping make token boundaries differ from what the shell actually does.

The last four tests each have a problem.

Four holes in the read-only list

TRUSTED_BINARIES holds 62 entries with a promise in the comment: purely read-only, never writing, never spawning other programs. At least four break it.

CommandHow it writesWhy it slipped in
sortsort -o out.txt in.txt-o writes the result to a file
treetree -o out.txtSame option, same effect
xxdxxd -r in.hex out.bin-r reverses hex back into binary and writes it
datedate -s 2026-01-01-s sets the system clock

sort -o and tree -o need no special privilege. And xxd -r can write arbitrary binary content, which means one "read-only" entry provides a complete file write primitive:

xxd -r payload.hex /home/user/.ssh/authorized_keys

No control operators, program name in the list, ordinary file arguments. Trusted, no approval needed. And date -s is subtler: it breaks certificate validation, log ordering and build caches that depend on time.

The fix is not deleting four entries, which would also remove their legitimate uses. It is upgrading from "trust the program" to "trust the invocation".

fn is_read_only_invocation(program: &str, args: &[&str]) -> bool {
    match program {
        "sort" | "tree" => !args.iter().any(|a| a == "-o" || a.starts_with("-o")),
        "xxd" => !args.iter().any(|a| a == "-r"),
        "date" => !args.iter().any(|a| a == "-s" || a.starts_with("--set")),
        _ => TRUSTED_BINARIES.contains(&program),
    }
}

Small change, better semantics: sort is not read-only, but sort without -o is.

Matching by basename: /tmp/ls counts as trusted

Taking the basename is meant to make /bin/ls and ls the same program. It also makes /tmp/evil/ls the trusted ls, regardless of who wrote it or what it contains.

/tmp/x/ls -la

No operators, basename is ls, in the list, trusted, runs without asking, and /tmp/x/ls can be any script at all.

How bad this is depends on the threat model. If the model is benevolent and merely fallible, it never runs /tmp/x/ls. If the repository might contain a hostile file the model could read and follow, this is a complete code execution path: drop an executable named ls in the repository and let the README talk the model into running it.

The weak fix refuses any command containing a path separator, which costs the convenience of /bin/ls but only adds a prompt. The strong fix validates that the path is under a trusted root such as /bin or /usr/bin, which requires handling PATH lookup, symlinks and the fact that Windows has no /bin. For a cross-platform tool the first is realistic, the second suits a strict Linux mode.

Environment prefixes: the LD_PRELOAD line

LD_PRELOAD=/tmp/evil.so ls

The program is ls, in the list, no dangerous arguments, judged read-only and trusted. LD_PRELOAD makes the dynamic loader pull in /tmp/evil.so before ls starts, which is arbitrary code running with your full privileges.

PAGER is the sharpest example: git log is on the trusted subcommand list, so it runs without a prompt, unless the environment points PAGER at a script, in which case git log spawns it. "git log is read-only" depends on the environment being clean, and the environment is exactly what the model can set.

The fix is to allow only known-safe variable prefixes, or to forbid them entirely. Refusing every prefix costs an approval for FOO=bar ./test, which in an agent context is fine.

Why a git subcommand list cannot stop aliases

fn git_subcommand_is_read_only<'a>(tokens: &mut impl Iterator<Item = &'a str>) -> bool {
    const VALUE_FLAGS: &[&str] = &["-C", "-c", "--git-dir", "--work-tree", "--namespace"];
    let mut pending_value = false;
    for token in tokens {
        if pending_value {
            pending_value = false;
            continue;
        }
        if token.starts_with('-') {
            if VALUE_FLAGS.contains(&token) {
                pending_value = true;
            }
            continue;
        }
        return TRUSTED_GIT_SUBCOMMANDS.contains(&token);
    }
    false
}

VALUE_FLAGS exists so that git -C /repo status does not treat /repo as the subcommand. Correct, and tested. Three holes remain.

One: git -c can name any program. git -c core.fsmonitor=/tmp/evil.sh status skips the value and sees status. But core.fsmonitor is executed by git on every status check. Same for core.editor, core.pager, diff.external and filter.*.clean.

Two: --exec-path is not in the list but starts with a dash, so it is skipped, and git --exec-path=/tmp status makes git look for git-status in /tmp.

Three, and the fundamental one: aliases. With alias.status = !rm -rf /tmp/x in ~/.gitconfig, git status expands to that shell command. The checker sees status, trusts it, and something else runs.

The only fix for the third is to look at what git will actually do, by querying git config --get alias.status, or by removing git from the trusted list entirely. The saving from not prompting on read-only git commands is small next to these three holes, especially since git status usually comes with git diff and git log, all hijackable the same way.

The block does not cover backslashes, so m would be judged untrusted because the name does not match. That errs toward prompting, which is fine. Comments and quotes are not blocked, and do not need to be.

So the nine characters are sufficient for their purpose. The real risk is not metacharacters, it is judging program identity. Metacharacters stop one command doing several things. sort -o, /tmp/ls and LD_PRELOAD are one command doing one thing that is not what you think.

Landlock: a kernel sandbox with no crates

Linux 5.13 added Landlock, an unprivileged mechanism for a process to restrict itself. A process installs a ruleset declaring which paths it may access and with which rights, and the restriction cannot be removed and is inherited by children. That is exactly what a sandbox needs.

const SYS_LANDLOCK_CREATE_RULESET: usize = 444;
const SYS_LANDLOCK_ADD_RULE: usize = 445;
const SYS_LANDLOCK_RESTRICT_SELF: usize = 446;

The numbers are identical on x86_64 and aarch64, deliberately, so no per-architecture branching is needed. One prctl is also required, PR_SET_NO_NEW_PRIVS, and it has to come first, because a Landlock ruleset only takes effect without new privileges, otherwise a setuid binary could escape it.

What pre_exec may and may not do

cmd.pre_exec(move || {
    apply(handled, abi, root.as_c_str(), ws.as_deref())
        .map_err(std::io::Error::from_raw_os_error)
});

This closure runs in the forked child before exec, where only one thread exists and every other thread's locks are in an unknown state. So the closure must not allocate memory, must not take any lock, must not call a non-async-signal-safe function, and must not format, print or panic.

The implementation respects that: apply uses two stack-allocated repr(C) structs, issues raw syscalls, and returns an errno instead of building a string. The safety comment says so explicitly. This is the easiest place to get the sandbox wrong: formatting an error message on failure would malloc in a forked child and occasionally deadlock under load, presenting as "the command sometimes hangs".

Both C strings are built before the fork and moved in, so the closure only calls as_c_str(). Moving all preparation ahead of the fork is the correct pattern for pre_exec.

ABI versions and why permission bits are trimmed

fn handled_fs_bits(abi: u32) -> u64 {
    let mut bits = ALL_FS;
    if abi < 2 {
        bits &= !FS_REFER;      // cross-directory rename arrived in ABI 2
    }
    if abi < 3 {
        bits &= !FS_TRUNCATE;   // truncate arrived in ABI 3
    }
    if abi < 5 {
        bits &= !FS_IOCTL_DEV;  // device ioctl arrived in ABI 5
    }
    bits
}

The trimming is mandatory, not an optimization: passing a bit the kernel does not know makes create_ruleset fail with EINVAL and the sandbox never installs, which here means no command runs at all.

Struct size is versioned the same way, and passing a smaller struct than the kernel understands is legal because unknown fields read as zero.

The ABI handling carries a hidden assumption: the constant table must be maintained alongside kernel versions. If ABI 7 adds a dimension that ALL_FS does not mention, the sandbox silently does not cover it, because Landlock restricts exactly the dimensions you declare and allows everything else. A missing bit never fails; it just protects less.

A read-only root and a writable workspace

// 3. read and execute everywhere, write denied by default
add_path_rule(rs_fd, root, READ_EXEC)?;
// 4. in workspace-write mode the workspace gets everything
if let Some(ws) = ws {
    add_path_rule(rs_fd, ws, handled)?;
}

READ_EXEC is execute plus read file plus read directory, with no write bits, while handled declares every write bit, so unmentioned rights are denied. Default deny, explicit grant.

Read-only mode adds no second rule, so the whole filesystem is read and execute only. Workspace-write grants the workspace everything, including creating devices and sockets.

One consequence is easy to miss: READ_EXEC covers all of /, so a sandboxed command can read ~/.ssh/id_rsa, ~/.aws/credentials, .env and other projects' source. The sandbox restricts writing, not reading. Restricting reads would break almost every command, since sh needs its libraries and cargo needs its registry.

But that means exfiltration is a real risk: cat ~/.ssh/id_rsa is a read-only command that runs without asking, and the contents become tool output, then part of the next request to the model provider.

The network is not restricted

let attr = RulesetAttr {
    handled_access_fs: handled,
    handled_access_net: 0,
    scoped: 0,
};

Zero means "I do not handle the network dimension", so networking is unrestricted: any IP and port, uploads via curl, reverse shells, cloud metadata at 169.254.169.254. As a filesystem-write sandbox that is a coherent boundary, but if the goal is running untrusted code it is wide open.

Closing it is cheap on ABI 4 and up: declare the TCP bits and grant no port rules, which denies everything. That breaks every networked command, so it belongs in a third mode rather than in the existing ones, which is a reminder that "sandbox mode" is more than one dimension: filesystem, network, process, IPC, and each dimension doubles the combinations.

Fail closed, and why it will not degrade

let abi = landlock_abi().ok_or_else(|| {
    "this kernel does not expose Landlock (Linux >= 5.13 required);      refusing to run unsandboxed"
        .to_string()
})?;

When the kernel does not support it, the command does not run unsandboxed, it fails. Non-Linux platforms behave the same, and there is a startup warning for the combination.

The reasoning matters: the sandbox's promise is that writes do not leave the workspace. Silent degradation would turn that promise into "usually does not leave the workspace", while the user believes it is absolute. The most dangerous failure of a security mechanism is a silent one, because it changes nothing about the user's behavior and everything about the actual protection.

The cost is that on macOS and Windows, enabling the sandbox makes every command fail. The warning is printed once and does not stop startup, which is reasonable, though a rejected start would be better for goal mode plus sandbox on an unsupported platform, since that combination is unattended plus every command failing.

The sandbox covers child processes only

Built-in file tools spawn nothing, and the sandbox attaches to child processes, so it cannot reach them. The practical meaning of sandbox: workspace-write is that child processes cannot write outside the workspace, not that the agent cannot.

write_file(path="/home/user/.ssh/authorized_keys", content="ssh-rsa AAAA...")

That call passes check_tool, triggers no hook, needs no approval because approval lives in the shell path, and meets no sandbox because there is no child process. All four gates are simply not applicable.

The fix is not another gate. What is missing is that built-in tools have no sandbox at all. One option is a path check inside the file tools; the other, putting built-in tools behind Landlock, is impossible, since the restriction is process-wide and irreversible, and the agent would lose access to its own configuration and prompts. So the path check is the only option, and doing it correctly means handling normalization, symlinks, and which paths are legitimate exceptions.

resolve does no normalization

pub fn resolve(root: &Path, p: &str) -> PathBuf {
    let path = Path::new(p);
    if path.is_absolute() {
        path.to_path_buf()
    } else {
        root.join(path)
    }
}

Neither branch normalizes anything. An absolute path passes through, and a relative one is only joined, so ../../etc/passwd becomes <root>/../../etc/passwd, which the filesystem resolves to /etc/passwd. The exploitation difficulty is the same as writing the absolute path.

read_file(path="../../../../etc/shadow")

is_absolute() is false for that string, so it is joined, and the read follows the parent directories out. Note that canonicalize() alone is not the fix either: it resolves symlinks and requires the path to exist, which a file about to be created does not.

fn resolve_checked(root: &Path, p: &str) -> Result<PathBuf, String> {
    let joined = if Path::new(p).is_absolute() {
        PathBuf::from(p)
    } else {
        root.join(p)
    };
    // 1. lexical normalization: remove . and ..
    let mut out = PathBuf::new();
    for comp in joined.components() {
        match comp {
            Component::ParentDir => { out.pop(); }
            Component::CurDir => {}
            other => out.push(other),
        }
    }
    // 2. prefix check, lexically
    if !out.starts_with(root) {
        return Err(format!("path {} escapes the workspace", out.display()));
    }
    // 3. if it exists, re-check against the canonical path
    if let Ok(real) = out.canonicalize() {
        let root_real = root.canonicalize().unwrap_or_else(|_| root.to_path_buf());
        if !real.starts_with(&root_real) {
            return Err(format!("path {} resolves outside the workspace", real.display()));
        }
    }
    Ok(out)
}

Each step has a job: the first stops .., the second stops absolute paths, the third stops symlinks. The third only works for existing paths, which is exactly where the next hole is.

Symlinks: the kernel and the built-in tools disagree

Landlock judges by the real path resolved when a file is opened. With ln -s /etc/passwd ws/link, a sandboxed echo x >> ws/link is denied, because the kernel resolves to /etc/passwd, which only has read and execute rights. Landlock is reliable here.

Built-in tools have no such protection. write_file calls fs::write, which follows symlinks, so writing to link writes to /etc/passwd.

Which produces an absurd combination: with workspace-write on, run_command cannot write /etc/passwd and write_file can. Security depends on which tool the model picks, and the model only knows which is more convenient.

For a new file, canonicalization fails and the third step is skipped. The fix is to canonicalize the deepest existing ancestor and reattach the rest.

let mut ancestor = out.clone();
let mut tail = Vec::new();
while !ancestor.exists() {
    if let Some(name) = ancestor.file_name() { tail.push(name.to_os_string()); }
    if !ancestor.pop() { break; }
}
let real_ancestor = ancestor.canonicalize()?;
let real_full = real_ancestor.join(tail.iter().rev().collect::<PathBuf>());
if !real_full.starts_with(&root_real) { return Err(...) }

Fifteen lines, and the only correct way to prevent traversal through a symlink for a file that does not exist yet. Without it, the attack is: commit a directory symlink pointing at ~/.ssh, then have the agent write a file that looks like it is inside the repository.

The first three are "the child is protected, the built-in tool is not". The fourth is neither. What this table says is that security depends on which tool the model chooses, and the model does not know that. Fixing it does not mean another gate, it means bringing built-in tools under the same path policy, ideally by making resolve return a Result so the compiler lists every call site that has to decide what out-of-bounds means.

The plan row shows the sandbox doing nothing, because commands are blocked and the sandbox only affects children. Plan's strength comes from blocking the write tools instead.

The goal row shows the most dangerous cell: unattended, unapproved and unsandboxed means the model can do anything to the machine. Nothing prevents that combination, and since sandbox defaults to off, default goal mode is that cell.

Which suggests the two flags should not be independent at all, but a safety level with a fixed bundle of settings, since 15 combinations include several nobody would choose deliberately and a few that are actively dangerous.

Why plan mode is not a read-only sandbox

Plan blocks tools, not paths. It removes the ability to write by removing the tools, which works today and will not cover a tool added tomorrow, such as a query tool that can update rows.

It does not restrict reads either. Plan mode reads everything, and so does a read-only sandbox; the difference is that plan means "I do not change things" while the sandbox means "the process cannot".

And it depends on a hand-written list of five tool names. Add a tool that writes and forget to list it, and plan mode silently grows a write entrance. Any mechanism whose safety depends on remembering to update a list gets worse over time.

The sturdier design tags each tool with capabilities such as fs.write, process.spawn or net.egress, and blocks by tag rather than by name. That is about 100 lines across 24 tools and it turns "safety depends on remembering" into "safety depends on classification".

Goal mode has nobody to ask

Goal mode forces approval on and policy to never, which permanently closes the approval gate. Honest, and it pushes all responsibility onto the other three gates.

GateState in goal mode

So goal's real strength equals whatever hooks are configured plus whether the sandbox is on. With neither, it is zero.

Three things an unattended mode should do: default the sandbox on and refuse or warn when it is off; require at least one PreToolUse hook, since hooks are the only way to express "do not touch these paths" without a human; and add a wall-clock budget, because iteration limits do not bound total commands, total bytes written or elapsed time, and a runaway goal run can produce hundreds of writes in half an hour.

Assume the defaults: approval on, sandbox off, default mode. Only check_tool and hooks are in play.

None of these is a clever chain. Each is one step, one command, no obfuscation. They pass for the same reason: the check judges what the command looks like, not what it will do.

Turn on goal mode and scenarios four through seven no longer need a misjudgment, because the approval gate is gone. That comparison makes the real point: with approval on by default, the gate was already inert.

Add --ask and a workspace-write sandbox and four through seven all get prompted, but one, two and three still pass, because they are built-in file tools with no path restriction at all. Which is the most important conclusion here: the most effective hardening is not tuning the approval policy, it is adding an out-of-bounds check to resolve, because the first three are the common ones and the ones a model can trigger without meaning to.

The first three are real fixes and the rest are policy changes. The first is the most important and the easiest to do badly, because changing the signature produces a wave of compiler errors, each one a decision about what out-of-bounds means: an error for file tools, but an exception for the session store and the memory directory, which suggests two entry points, one checked for workspace paths and one explicit system path that never accepts a model-supplied argument.

The second should follow the same idea as VALUE_FLAGS: trust the invocation, not the program. The current implementation judges while walking the token stream, which is why it accumulated four holes; parsing into an intermediate structure and letting each rule read its own field would not.

The sixth is three lines and it changes the default, which matters more than any single fix, because a default decides the protection received by everyone who never reads the documentation.

How to test a security boundary

Security tests assert that what should not happen did not happen.

// read-only: even writes inside the workspace must be refused
assert_eq!(
    run_sandboxed(
        &format!("touch {}/a", ws.display()),
        SandboxMode::ReadOnly,
        &ws
    ),
    Some(false),
    "read-only sandbox must deny writes"
);
assert!(!ws.join("a").exists());

// workspace-write: writes inside are allowed
assert_eq!(
    run_sandboxed(&format!("touch {}/b", ws.display()),
                 SandboxMode::WorkspaceWrite, &ws),
    Some(true)
);
assert!(ws.join("b").exists());

// workspace-write: writes outside are refused
assert_eq!(
    run_sandboxed(&format!("touch {}/c", outside.display()),
                 SandboxMode::WorkspaceWrite, &ws),
    Some(false)
);
assert!(!outside.join("c").exists());

Three assertions cover both directions of failure: the denials that must happen and the permission that must not be denied. The third is the one that catches a sandbox installed incorrectly, because then b fails and you learn the sandbox blocked everything, rather than discovering it in production when nothing runs.

The approval tests pin the short circuit first: with approval on, even rm -rf / must return false. That combination is exactly what silently changes during a refactor, so it needs a test.

What the tests do not cover is the four holes from this post: sort -o, /tmp/ls, LD_PRELOAD and a git alias. That is the general problem with security tests: known attacks are easy to test, unthought-of attacks are not. Adding more assertions only covers what you already imagined. Testing properties instead covers more: for every trusted command, run its common flag variants in a scratch directory and assert nothing appears; place sentinel files outside the workspace and assert they never change; statically enumerate every spawn site and assert each one passes through approval.

Closing

Security is depth, not strength. Every gate here can be bypassed on its own. Stacked, an attack has to defeat five layers at once to be silent, which is more reliable than one very strong gate that has a single point of failure.

The thinnest layer is usually not the one you expect. The sandbox is the hardest thing here and it has the narrowest coverage. The real hole is that built-in file tools have no path constraint at all, and that is the least alarming-looking place in the system: one filesystem call, no child process, no shell, no approval. Direct IO inside your own process is what security reviews miss.

And defaults are the security level. auto_approve: true plus sandbox: Off disables two of the five gates outright. No single fix is worth as much as changing those two defaults, which is why it needs a deliberate migration decision rather than a quiet edit.

What is worth praising is the honesty: when the kernel does not support Landlock the code refuses instead of degrading; the approval short circuit sits on the first line with no disguise; goal mode says in the comments that there is nobody to ask. Stating the boundaries is much better than claiming safety with a blurry boundary, because only someone who knows where the edge is knows where to reinforce.
