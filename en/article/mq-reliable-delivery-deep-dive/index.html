The case of the vanishing messages

2026-10-30 · 18 min · Stack Frame

Who this is for: engineers who have built async decoupling on a queue and cannot say whether messages are lost or where.

Measured with the Python standard library. The reasoning holds for RabbitMQ, RocketMQ, Kafka and Redis Streams alike.

Reading time around 18 minutes. Level: intermediate to advanced.

The incident

Risk reported that over one month, more than six hundred orders had reached "paid" while the points system never awarded anything. Reconciliation put a queue between the two sides.

The logs were miserable to read: the producer logged a successful send and the consumer had no record at all, so the message had vanished in the middle.

Three factors had combined. The producer sent and assumed success, so a network hiccup lost messages silently. The broker had no persistence and restarted once, clearing the in-memory queue. And the consumer acknowledged on receipt, so a process killed mid-work had already removed the message.

Individually none of those is likely. Multiplied, they cost a few hundred orders a month.

What follows takes the journey apart hop by hop, and then runs a simulator to compare three configurations by loss rate.

Where a message can be lost

producer --1--> broker --2--> storage --3--> consumer
HopHow it losesDefence
Producer to brokerPacket loss, broker crash before handling, fire-and-forget clientsPublish confirmation, retries, a local outbox table
Broker storageNo persistence, crash after buffering, single-disk failurePersistence with synchronous flush, replicas
Broker to consumerAuto-acknowledgement then a crash, unhandled exceptionsManual acknowledgement, redelivery, retry topics, dead letters

Reliability is set by the weakest hop. If any of the three is fire-and-forget, the whole pipeline is, which is why the incident lost a slice at each stage and the slices added up to the reconciliation gap.

And reliability is never free: each layer costs throughput, latency or complexity. So the answer is not to switch everything on but to classify messages by what they are worth.

ClassExamplesConfiguration
DisposableAnalytics, metricsFire and forget
Best effortPush notifications, cache invalidationConfirmation and retries
Never lostOrders, payments, pointsEnd-to-end confirmation, persistence, manual acknowledgement, idempotent consumption

The producer

Two meanings of "sent"

Most message losses start by confusing them. An API call returning means the bytes reached a local buffer. A broker confirmation means the broker received the message and persisted it. Publisher confirms, synchronous sends with an acknowledgement, and Kafka's strongest acknowledgement mode all do the same thing: move the definition of success from the first to the second.

AcknowledgementMeaningLoss window
NoneSent is successAny packet loss, any leader crash
Leader onlyWritten to the leaderA leader crash before replication
All in-sync replicasWritten everywhere requiredNothing, while one replica survives, given a minimum replica count

What retries cannot fix

Confirmation plus retry covers transient faults and cannot cover the atomicity between a local write and a publish. An order endpoint writes the order and then publishes; a crash between the two leaves an order with no event. Reversed, the user receives a confirmation while the order does not exist. Retrying cannot help, because the process that would retry is already dead.

Make the two steps one transaction: write the business row and an outbox row in the same database transaction.

BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (topic, payload, status)
    VALUES ('order.created', '...', 'pending');
COMMIT;

def deliver_outbox():
    rows = db.query(
        "SELECT id, topic, payload FROM outbox "
        "WHERE status='pending' ORDER BY id LIMIT 100"
    )
    for row in rows:
        try:
            broker.publish(row.topic, row.payload)   # with confirmation
            db.execute("UPDATE outbox SET status='sent' WHERE id=%s", row.id)
        except Exception:
            continue  # retried next round

The pattern is the transactional outbox, and its essence is moving the network operation out of the transaction so the transaction only writes locally. A local write is atomic, so once the message is in the database it exists, at worst delivered later.

The cost is a polling delay, which a locking read or change capture can reduce, plus a cleanup policy for the outbox table. Against losing orders, that is almost always worth paying.

The broker

A message in memory is not your message. Two layers, then a third.

Persistence flags. In a broker that requires marking exchanges, queues and messages durable, missing any one of them means a restart loses the message. Brokers that write to disk by default pass this layer for free.

Flush timing. Handing bytes to the operating system's page cache is not writing them to disk, and a power cut loses the cache. The choice is explicit: asynchronous flushing returns immediately and loses whatever is in flight during a power failure, while synchronous flushing acknowledges only after the disk write.

Replication. A failed disk defeats persistence entirely, so replica sets, synchronous replication and leader election all buy immunity to single-machine failure with more machines.

One detail that gets overlooked: confirmation and flushing are separate events with a window between them. A message can be confirmed before it is durable, and the size of that window depends on batching. That is the explanation for "we enabled persistence and still lost a few".

The consumer

Most production incidents live in the third hop, and the culprit is almost always automatic acknowledgement.

Its semantics are that the message is removed from the queue as soon as it is delivered, not when it is processed. A crash halfway through processing therefore loses the work permanently, and a swallowed exception does the same, silently.

def on_message(ch, method, properties, body):
    try:
        handle(body)
        ch.basic_ack(method.delivery_tag)
    except TransientError:
        ch.basic_nack(method.delivery_tag, requeue=False)
    except PermanentError:
        ch.basic_nack(method.delivery_tag, requeue=False)

Two details. A crash before the acknowledgement makes the broker redeliver, so the message survives and may be processed twice. And a negative acknowledgement must not requeue blindly: a malformed message returns to the head, is picked up immediately, is rejected again, and spins a core while blocking the queue. Retry a bounded number of times, then route to a dead letter queue.

Duplicates are acceptable, if consumption is idempotent

At this point a conclusion is unavoidable: not losing and not duplicating cannot both be guaranteed. To avoid loss you must process before acknowledging, and a crash during processing means redelivery. Acknowledging first avoids duplicates and loses on crash.

The engineering answer is at-least-once delivery plus idempotent consumption, which dissolves the duplicate instead of preventing it. The mechanisms are the same as in the idempotency post: unique constraints, state machines and a deduplication table. For a consumer, the deduplication table is usually enough.

CREATE TABLE consumed_messages (
    message_key VARCHAR(64) PRIMARY KEY,   -- business key: order number or event id
    consumed_at DATETIME NOT NULL
);

BEGIN;
INSERT IGNORE INTO consumed_messages (message_key, consumed_at)
    VALUES ('order:20260916:0001', NOW());
-- zero rows affected means already consumed: acknowledge and skip
UPDATE points SET balance = balance + 100 WHERE order_id = ...;
COMMIT;

Two practical points. The key must be a business key, because a broker redelivery usually keeps the message id while a producer resend creates a new one, so only something like order number plus event type identifies meaning. And the table needs a cleanup policy tied to the business tolerance window, deleting records older than reconciliation needs.

Measured: three configurations

A simulator runs a hundred thousand messages through the full path with three injected faults: a tenth of a percent of packets lost on the producer side, one broker restart at fifty thousand messages, and a half percent chance of a consumer crash per message.

Fire and forgetSends and moves onNo persistenceAuto acknowledge
PartialConfirmation and retryPersistentAuto acknowledge
FullConfirmation and retryPersistentManual acknowledge and idempotent

Partial99,512488090

Confirmation on the producer is the best value layer. Adding it to the fire-and-forget configuration saved 127 messages, including every network loss and every message caught by the restart window, for one configuration line.

The last mile is the consumer. The partial configuration had confirmation and persistence and still lost 488, all of them from a crash after automatic acknowledgement. Those are the invisible ones in the opening incident: the log says consumed, and the business never ran.

The full configuration traded eight-five duplicates for zero losses. That is the exact cost of processing before acknowledging: bounded, deterministic, and completely absorbed by the deduplication table. Losing a message is unbounded and unknown in cost, since it might be points and it might be a refund.

In one line: pay a budgetable small cost to eliminate an unbudgetable large risk.

Retries, backoff and dead letters

StrategyWasted attempts in a ten second outage
Fixed interval of 100 ms101
Exponential from 100 ms, doubling, capped at five seconds7

Fourteen times fewer, and the difference grows as the downstream gets more congested: dense retries slow its recovery and extend the outage.

delay = min(base * (2 ** attempt) + random.uniform(0, base), max_delay)

The random term is jitter. Without it, a batch that failed together retries together and re-creates the same spike.

main queue --reject--> retry L1 (5s) --reject--> retry L2 (30s)
                                                    | after three attempts
                                                    v
                                            dead letter queue --> alert and triage

The delayed queues give the downstream room, and the dead letter queue is where exhausted retries go. The point is not the queue but the alarm and the triage process: messages sitting there unread are simply lost somewhere more visible.

Also classify the failure. Timeouts and gateway errors deserve backoff; validation failures and deserialisation errors will fail identically forever and belong in the dead letter queue immediately.

Backlogs and delayed messages

Backlogs mean consumption is slower than production. First try adding consumers, remembering that the count is capped by partitions, so extra instances idle. When scaling is too slow, the standard manoeuvre is to drain the backlog in bulk into a temporary topic with ten times the partitions, consume it with ten times the workers, and delete the temporary pipeline afterwards. The preventive fix is batching: accumulating single updates into batch upserts usually moves throughput by an order of magnitude.

Delayed messages cover automatic cancellation after thirty minutes and coupon expiry reminders.

ApproachPrecisionComplexity
Dead letter queue with a TTLHead-of-line blocking: a long TTL delays everything behind itLow
Broker-level delay levels or scheduled messagesSeconds, or an exact time on newer brokersLow
A time wheel or a delay serviceArbitraryHigh, needs persistence and recovery

The head-of-line trap is the reason not to use TTL-based delays where the delays vary widely: the queue is first in, first out, so a message with a ten minute TTL blocks a message behind it with thirty seconds until the front leaves.

Checklist

On the producer: no fire-and-forget for important messages; bounded retries with alerts; atomicity between the local write and the publish through an outbox; and a business key inside every payload for deduplication and reconciliation.

On the broker: all three of exchange, queue and message durable where the broker requires it; replicas with a minimum in-sync count of two; and an explicit decision about flushing, with the power-failure window known and accepted.

On the consumer: manual acknowledgement after the work succeeds; idempotent handling through a deduplication table or a state machine, keyed on business data; no infinite requeue; and a dead letter queue with monitoring and a triage process.

In operations: alerts on queue depth and consumer lag; a reconciliation job, because the queue is not the most reliable system and reconciliation is the last line; and tiered configuration by message value rather than every topic getting everything.

Questions that come up

Which broker? Small scale with an existing cache, a stream is fine with a length cap and consumer groups. General use, a RabbitMQ-class broker for operational simplicity or a RocketMQ-class one for transactional and delayed messages. High-volume pipelines, Kafka. The differences between products are smaller than the differences between configurations, and a badly configured Kafka loses more dramatically than a well-configured RabbitMQ.

Is a cache reliable as a queue? Not with defaults, where the persistence interval allows a second of loss and failover can lose more. Stronger settings approximate reliability at a large throughput cost. Acceptable for small volumes where occasional loss is tolerable, not for payments.

Broker transactional messages or an outbox table? Transactional messages remove the polling table but bind you to one broker and still require a check-back mechanism. An outbox is broker agnostic, easier to inspect and doubles as an audit log, which is why most teams prefer it unless the broker already solves the problem.

Slow consumption: more consumers or better logic? Find the bottleneck first. CPU-bound work needs batching or faster logic, IO-bound work needs concurrency and a larger prefetch. Batch first when there is any room, then add partitions and consumers, because blind scaling is capped by the partition count and wastes money.

Closing

The six hundred missing orders were fixed without a new component: confirmation and an outbox on the producer, persistence on the broker, manual acknowledgement and a deduplication table on the consumer, and alerts on the dead letter queue. The reconciliation gap went to zero, the duplicates were absorbed, and monthly duplication ended up below nine in ten thousand.

The knowledge here is not complicated. What is complicated is that the default configuration at every hop points away from reliability: automatic acknowledgement, asynchronous flushing, fire and forget. The work is knowing what each default is, which business flows can afford it, and how to replace it for the ones that cannot.
