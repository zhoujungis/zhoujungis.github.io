Agent observability: keeping a ledger for every turn

2026-11-06 · 34 min · Stack Frame

Who this is for: people who have run an agent for a few days and started asking what a task actually cost; people who have been fooled by "restart, and the cost is zero"; people who built multi-agent setups and found sub-agent spending untraceable.

TL;DR: observability is not scattering log lines through the code. It is making every unit of consumption land in one auditable row: who started it, what it did, how much it cost, when. NanoHermes has the parts, usage totals, a usage event and a duration on the board, but no ledger. Usage lives in process memory, three internal model calls are never counted, and sub-agent spending has nowhere to sit in the data structures.

You have logs, so why can you not say what it cost

An agent that can finish tasks acquires three kinds of log quickly: banners for tool calls, error messages, and status notes like "context compacted". All of them prove that something happened. None answers three basic questions.

  • How many model requests did this task make, and how many of those were retries?
  • Of the tokens it burned, how many did sub-agents burn?
  • That forty minute task yesterday afternoon, which session is it billed to?

All three point at the same thing: a log is a stream of events, a ledger is a table. Each line of a stream describes one moment. A stream does not accumulate, does not attribute, and does not survive the process. To keep books you have to decide the table first.

NanoHermes is a typical example. It has the parts and no ledger. Usage totals have three fields, the usage event has one delta semantics, the board records time without money, and the three internal calls that burn most of the tokens, compaction, distillation and sub-agents, do not record a thing. Not an oversight: each part is sufficient on its own, and nobody made them share a data model.

A ledger needs four fields, and accounts go wrong three ways

FieldMeaningToday
whoWho started this consumptionOnly the main agent exists; sub-agents cannot be recorded
whatModel request, tool, compaction, distillationOnly model requests are counted
how muchTokens, requests, elapsed timeTokens yes; time only for sub-agents and background tasks
whenWhich session, which turnNo timestamp, no turn id

Missing fields do not make data ugly, they produce three specific failures.

Missing entries. Spent but not recorded: retried requests, failed requests, the summarization call inside compaction, the distillation call, every call inside a sub-agent.

Misattributed entries. Booked to the wrong account. The daemon runs one agent for several sessions, so usage accumulates per process and gets sliced per request by taking a difference. If a failed turn sits inside that slice, its tokens belong to neither the previous nor the next request.

Fuzzy entries. Recorded, but the definition is unclear. Does requests mean HTTP requests or successful model turns? Does prompt_tokens include cache hits? Do sub-agent tokens count toward the task? Undefined, two people can compute two answers from one number.

Of the three, missing entries are the easiest to fix and fuzzy entries the hardest, because the last one is a definition problem rather than a code problem.

So persistence and observability are two disjoint paths. What survives carries no books, and what carries books does not survive.

UsageTotals: three fields and one interface

/// Cumulative token usage across every model request in the session.
#[derive(Default, Clone, Copy, Debug)]
pub struct UsageTotals {
    pub requests: u64,
    pub prompt_tokens: u64,
    pub completion_tokens: u64,
}

impl UsageTotals {
    pub fn total_tokens(&self) -> u64 {
        self.prompt_tokens + self.completion_tokens
    }
}

Three fields, one derived method, two ways to read: a getter that returns a copy for /cost, JSON output and the daemon difference, and an event emitted once per completed request for the GUI and the streaming daemon.

total_tokens looks harmless and hides a definition question: when the provider counts part of the prompt as a cache hit, the local sum and the provider's total may not agree.

What Copy costs

Deriving Copy is comfortable for single-threaded accounting, and it also decides the shape of the ledger: no shared handle means no second writer.

run() takes &mut self so it can write usage. But run_subagent takes &self, and a shared reference cannot touch self.usage. A sub-agent runs one to forty model requests whose tokens go nowhere.

This is the dividing line between this post and the earlier ones. Every shared structure before now existed for cooperation: todos, the board, the gate. A ledger is shared for attribution. The earlier ones ask who may change something; this one asks whose name goes on the change.

Usage is scraped out of responses

pub fn usage_from_value(v: &Value) -> Usage {
    let u = v.get("usage");
    let get = |k: &str| {
        u.and_then(|u| u.get(k))
            .and_then(|x| x.as_u64())
            .unwrap_or(0)
    };
    Usage {
        prompt_tokens: get("prompt_tokens"),
        completion_tokens: get("completion_tokens"),
    }
}

"Missing means zero" is the most consequential decision in this section. It keeps a missing field from breaking a turn, which matters when talking to a range of OpenAI-compatible endpoints. It also means the ledger cannot tell "genuinely zero tokens" from "the provider did not tell us".

A system that can be reconciled needs three states here: some zero, some n, and unknown. Unknown should be counted separately, so "usage for this task is unknown" becomes a visible fact instead of silently becoming zero.

Only two fields are read, so caching and reasoning are free

Response fieldMeaningCost of dropping it
total_tokensThe provider's own totalNo way to check local addition against it
cached_tokensPrompt tokens served from the prefix cacheCache savings are invisible
reasoning_tokensTokens spent on the chain of thoughtA cost increase after enabling thinking cannot be explained

The third matters because the flag exists: enabling extended thinking raises completion tokens noticeably, and nothing in the ledger says how much of the increase was reasoning. The user sees a bigger number and guesses whether the model got worse, the context got longer, or the reasoning got expensive. Observability exists to turn that guess into a fact.

One fair caveat: cached tokens live in a nested details object that not every compatible endpoint returns. Read it as "record if present, unknown otherwise", never as unwrap_or(0), which dresses unsupported up as a cache miss and misleads more than recording nothing.

Streamed usage depends on one frame

if cfg.stream {
    // Ask for a trailing usage frame so token counts work while streaming.
    body["stream_options"] = json!({ "include_usage": true });
}

And in the reader, a frame carrying usage overwrites the turn's usage rather than adding to it. Correct, since there is one frame, and it assumes exactly one. A provider that reports usage across two frames would lose half of it. The safer form records each usage frame as a span and sums at the ledger layer.

A stream that breaks mid-way loses the whole turn's usage

let l = match l {
    Ok(l) => l,
    Err(e) => return Err(format!("stream read error: {e}")),
};

The turn is a local variable, and returning an error discards it. If the stream read 900 chunks and the provider already counted 30,000 prompt tokens, and the connection dropped before the final frame, that usage vanishes. Not just from the ledger: the fact that a failed request cost money does not appear anywhere either.

It is the classic shape of an error path that carries no data. The return type is a result with a string error, and a string cannot hold an accumulated turn. Either the error variant carries the partial turn, or the turn is passed in mutably so the caller can still see what accumulated.

The same file truncates error detail to 800 bytes, which is right for a terminal and wrong for a ledger: a long provider error survives only as its beginning, and the interesting part of a strange 400 is usually the end.

The accounting line sits after the error return

let turn = match self.complete() {
    Ok(turn) => turn,
    Err(e) => {
        self.persist();
        return Err(e);
    }
};
self.usage.requests += 1;
self.usage.prompt_tokens += turn.usage.prompt_tokens;
self.usage.completion_tokens += turn.usage.completion_tokens;

The error branch comes first, so the four accounting lines never run on failure. The ledger's real definition is therefore successful model requests, not requests that happened.

With one user and a stable network the difference is small. In real use failures are ordinary: timeouts, 429s, 5xx, broken streams, wrong JSON shapes. Most of those are not billed, so "not counted" is defensible for money and indefensible for reliability: you cannot see that a task needed seven retries, or that an endpoint fails thirty percent of the time.

A healthy ledger records failed requests and failed turns separately. A failed request inside a successful turn is a retry; a failed turn is a loss. Both need rows, differing in an outcome field.

Retries and fallback hide N requests behind one success

The retry loop returns the last successful turn, which carries the usage of that final attempt only. The earlier failures, their elapsed time, and the fallback attempt never appear in the return value.

So the main loop always sees one request, and the ledger never learns that three 503s and a degradation happened. The only trace is an eprintln!, which scrolls past in a terminal and goes to the server log in a daemon, with nothing reaching the client.

Fallback is worse, because the ledger has no model dimension. A request served by the primary model or by a much cheaper fallback may differ in price by an order of magnitude, and usage totals hold only token counts. To price anything, each row needs a model field.

There is no model dimension

The model can be switched mid-session, and a sub-agent can override it. One usage total can therefore mix tokens from two or three models behind a single number. It is like adding yuan, dollars and euros and reporting a total: the arithmetic is right and the meaning is wrong.

The fix is either a map from model to usage, or one row per request carrying its model, aggregated later. The first makes queries fast, the second makes audits strong. For a system that must answer "what did this month cost", the second is right, because price tables change and historical rows must carry the model that was actually used.

Three internal calls never enter the books

CallEntry pointTriggerRecorded
Context compactionsummarize_messagesOver 120,000 charactersNo
Memory distillationdistill_memoriesEnd of a turn that passes the gateNo
Sub-agentsrun_subagent_innerThe model calls the sub-agent toolNo

All three call the model directly, take .content, and drop the usage where it stands. It is not forgetting to record, it is having nowhere to put it: none of them holds a mutable agent, and the totals are a value type. Recording would require promoting the ledger to an object passed down the call chain.

The cost of compaction

Compaction joins the dropped messages into an excerpt with no per-message clipping and asks for a summary of at most 300 words. That request's prompt can be tens of thousands of tokens, because it is half a context.

A forty-turn task may compact several times, each a real, large request, and the ledger gains only a note line with no tokens on it.

The subtler part is the invisible payoff. After compaction every subsequent request has a smaller prompt, so compaction spends once and saves repeatedly. Without a ledger you cannot tell whether the investment paid off: 30,000 tokens spent to save 20,000 over the rest of the task is a loss. That judgment depends entirely on the ledger that is missing.

The number /cost prints can be half the truth. Not by a rounding error, by an order of magnitude.

Why sub-agent cost cannot be recorded structurally

let mut result = String::new();
for _ in 0..sub_cfg.max_iterations {
    let turn = llm::chat(&sub_cfg, &messages, &tools, |_| {})?;
    result = turn.content.clone();
    messages.push(assistant_message(&turn));
    if turn.tool_calls.is_empty() {
        break;
    }
    ...
}
Ok(result)

Three things. A sub-agent can run up to forty iterations, cloned from the parent config, so one tool call hides up to forty model requests. The usage on each turn is dropped in place. And structurally, the path returns a string, so the only channel for cost is to write "used N tokens" into the text, which demotes a ledger to a comment.

The right shape returns a structure: text, usage, request count, elapsed time. The parent then records one row attributed to that sub-agent, and the board can answer which sub-agent was most expensive rather than only which was slowest.

The board has time, not money

A job carries id, name, task, status, result, duration and a private start instant. Of the seven, only duration is a quantity, and the result is a 500 unit preview. There is no usage, no request count, no model.

Sub-agent jobs:
- agent-1 [done] reviewer (12.3s) — review auth.rs
  result: looks fine
- agent-2 [running] explorer (…) — map the repo

Adequate for who is doing what, useless for where the money went. The board is an event table with a duration column: event tables restore order, they do not sum.

Duration includes queue time

The start instant is set at registration, registration happens before acquiring a permit, and so the duration includes queueing. A delegation that waited twenty seconds and ran three seconds records twenty-three. Used to judge whether sub-agents are slow, that number is wrong, because it folds rate-gate waiting into sub-agent work.

For a ledger this is more than display. Queue time is evidence of being held back by a quota. If the average wait is fifteen seconds, four slots are not enough, and that is a different problem from the model being slow. They have to be recorded separately to be diagnosed separately.

Tool calls are empty in the ledger

Execution takes no timestamps. What survives into the ledger is a name, a summarized argument list and the result text: no start, no duration, no output size. Yet tools are the least controllable part of an agent. A command may run to its two minute timeout, a fetch may stall on the network, a search may walk hundreds of thousands of files.

Timestamps exist in the code, but only for timeouts, and a timeout decision needs to know whether the deadline passed, not how long something actually took.

FieldPurpose
nameWhich tool
start, endWhen, and for how long
argument bytesHow large the request was
result bytes, truncatedHow large the answer was, and whether it was clipped
exit codeSuccess or failure for commands
tool call idPairs with the message history

The truncated flag is worth having. If a tool's output is clipped ten times in a row, its output granularity is wrong and the tool should change, not the budget.

Two consumers, one drifting meaning

The usage event's comment opens by calling it cumulative and finishes by telling clients to sum what they receive, which is a delta. The sender hard-codes one request per emission, so the implementation is a delta and the first line of the comment is wrong.

With one consumer that drift never hurts. It plants a fuzzy entry: the next consumer reads cumulative, treats the last value as a total, reports a number that is too small, and cannot see why.

In a terminal the handler prints nothing at all, since there is no sink. The stated reason is that /cost exists, which is true and means real-time observability in the terminal is zero: a twenty minute turn gives no usage feedback until it ends.

Daemon accounting by difference

let before = agent.usage();
let result = agent.run(user_content(&prompt, &images));
let after = agent.usage();

Because usage accumulates per process, one request's cost is the difference between two snapshots. Saturating subtraction is a thoughtful touch: a wrapped or reset counter cannot produce an absurd invoice. Under serial service the method is correct, since nothing else writes between the snapshots.

Its precondition is that all growth between the snapshots belongs to this request. That stays true when internal calls start recording, since they do belong to this request. It breaks the day the daemon handles requests concurrently, at which point the difference bills someone else's work to you.

Where failed turns' tokens go

The error branch returns an error and a session id, with no usage field. But usage already grew before the failure, since every successful request in that turn was added. So the growth is not in this response, not in the next one, because the next request's baseline snapshot is taken after it. It exists only in the process total, and nothing can query the process total per session.

Failed turns therefore burn tokens into an unowned account. Two fixes: include usage in error responses, which is minimal and leaves clients handling the combination of usage and error, or record a row per turn so every outcome has a line, which is a rebuild and gives you questions like "how many failures did this session have, and what did they cost".

Streaming gives deltas and no total

The streaming path writes a usage line per update and one done line at the end. The done line carries no accumulated usage, so every client has to sum the deltas itself. That matches what the event comment promises, so it is not wrong, but three clients write the sum three times and two of them get it wrong.

Worse is the error path, which writes an error line and nothing else. A task that fails on the fifth round leaves the client with five usage lines and an error. A client that books on done loses all five; a client that books as it goes records a partial amount with no way to know it is partial.

A sturdier protocol puts total_usage on both terminal lines, so a client reads one field from the last event and treats the intermediate lines as progress. The terminal line is the only anchor for reconciliation, and that belongs in any agent's protocol design.

Session files carry no ledger

Persistence writes the pretty JSON of the message array, with no header, no metadata, no usage. And construction starts usage at zero. So loading yesterday's conversation and asking /cost reports the usage of this process, not of this session. Run the same task across three days with a restart each day and the books are cleared three times.

Invisible when one person uses one process, broken by resume, by daemon multi-session and by a GUI that continues a previous task.

The fix upgrades the session file from an array to an object with a version, messages and usage, and the loader has to accept both forms, treating a bare array as version one with no books. Accept only the new form and every old session fails to load, which looks to the user like history was lost.

/status and /cost are a process dashboard

> /cost
  requests:          18
  prompt tokens:     214,033
  completion tokens: 12,880
  total tokens:      226,913

Not one line of /status is a quantity, and /cost is pure counting: no time, no split by model, no split by source. Together they answer "what state am I in" and "how big are these numbers", not "where did the money go". That is the difference between a dashboard and a ledger.

The only exportable ledger

JSON output at the end of a run is the one structured, pipeable, storable account. It has three limits: one shot rather than per turn, three raw counters with no source, model or time, and it exists only in the JSON and stream-JSON formats, with plain text having nothing.

The direction is right: make the account data rather than printing. The next step does not need new concepts, only turning the scalar usage into rows, while keeping the outer usage object so existing scripts and jq pipelines do not break.

Observability today is eprintln!

About thirty calls across the crate, twenty-eight of them in the main file, in four categories: startup configuration, retry notes, session read and write warnings, and daemon errors. All of them write to stderr with no level, no timestamp, no trace id and no JSON form.

So a failure rate over the last hour means grepping text; associating an error with a request means guessing from ordering; and showing a retry in the GUI is impossible, because stderr never reaches the sink. That last one is a shame, since the style layer already has an event channel that both warnings and notes can use, and the HTTP layer simply does not hold it.

Hooks are observation points that are not observed

pub struct HookOutcome {
    /// Process exit code (-1 if killed by a signal, -2 if we timed it out).
    pub code: i32,
    /// Combined stdout + stderr, trimmed.
    pub output: String,
}

Callers check whether it passed and append the output to a tool result. That is all. So a hook that runs five hundred times a day and times out two hundred of them is invisible; a thirty second hook delay contributes to nothing; and a blocked tool call, which is a real event, enters no metric.

The thirty second cap is itself a signal: one hook can slow a turn by thirty seconds, and with forty iterations that is twenty minutes of pure hook time in the worst case. A design that treats hooks as observation points should record the hook as a span too.

Four of the seven have no structural place to record, two are undefined definitions, and one is an error path that carries no data. The three fix differently: structural problems need a ledger object and change the data flow; definition problems need documentation and tests; error path problems change function signatures. Classifying first beats adding logs, because logs fix none of the last two.

The right model: three tables

Turn table, one row per run: turn id, session, who (main, sub-agent with id, compaction, distillation), start and end, requests issued, retries, usage with prompt, completion, cached and reasoning, and an outcome of ok, interrupted, iteration limit or error.

Span table, one row per external interaction: span id, the turn it belongs to, an optional parent so a sub-agent's spans hang under the tool call that started it, a kind of model, tool or hook, name, model, start and end, optional usage including what accumulated before a failure, and a status that records failures rather than dropping them.

Totals, which is not a table but an aggregation of the first two: by who, by model, by kind.

The relationship is one turn to many spans, isomorphic to trace and span in distributed tracing. Two layers exist because the semantics differ: a turn is one operation the user perceives, a span is one external dependency. Users ask turn questions, operators ask span questions.

Whether the ledger hits disk depends on the question. Surviving a restart means appending next to the session file, at the cost of write amplification and rotation. Cross-session statistics mean SQLite, at the cost of a dependency. NanoHermes chooses memory only, which fits its low-dependency philosophy. The point of this post is not that it needs a database, it is that the in-memory ledger does not even record the rows memory could hold.

Five definitions to settle first

  1. Does requests mean HTTP requests or successful turns? Split it: requests issued, including failures and retries, plus successful separately. Otherwise retries have nowhere to live.
  2. Does prompt usage include cache hits? Split prompt and cached, and let cached be unknown. Do not guess on the provider's behalf.
  3. Do sub-agent tokens count toward the task? Yes, and separately. A parent turn equals its own usage plus its children, and each child has its own row. That gives additivity that always holds.
  4. Do failed retries count? Yes, marked unbilled. Most 429s are not charged, but the client should not assume that.
  5. Does time include queueing? No. Record queue time on its own field.

Four of the five concern tokens and one concerns time, which is not a coincidence: tokens are the billing unit, time is the experience unit, and both are needed without sharing a field.

A sixty-line ledger

use std::sync::Mutex;
use std::time::{Duration, Instant};

#[derive(Clone, Copy, Debug, Default)]
pub struct Usage {
    pub prompt_tokens: u64,
    pub completion_tokens: u64,
    /// None means the provider did not report it, rather than zero.
    pub cached_tokens: Option<u64>,
}

#[derive(Clone, Debug)]
pub enum Who {
    Main,
    SubAgent(String), // agent-7
    Compact,
    Distill,
}

#[derive(Clone, Debug)]
pub struct TurnRecord {
    pub turn_id: u64,
    pub who: Who,
    pub model: String,
    pub requests: u32,
    pub retries: u32,
    pub usage: Usage,
    pub elapsed: Duration,
    pub outcome: String, // ok / interrupted / iteration-limit / error:...
}

/// Append only; every execution path shares one Arc<Ledger>.
#[derive(Default)]
pub struct Ledger {
    inner: Mutex<Vec<TurnRecord>>,
}

impl Ledger {
    pub fn record(&self, rec: TurnRecord) {
        self.inner.lock().unwrap().push(rec);
    }

    pub fn snapshot(&self) -> Vec<TurnRecord> {
        self.inner.lock().unwrap().clone()
    }

    /// Parent equals self plus children; the test asserts this invariant.
    pub fn totals(&self) -> Usage {
        let all = self.inner.lock().unwrap();
        Usage {
            prompt_tokens: all.iter().map(|r| r.usage.prompt_tokens).sum(),
            completion_tokens: all.iter().map(|r| r.usage.completion_tokens).sum(),
            cached_tokens: if all.iter().all(|r| r.usage.cached_tokens.is_some()) {
                Some(all.iter().filter_map(|r| r.usage.cached_tokens).sum())
            } else {
                None
            },
        }
    }
}

Three things matter: cached tokens are optional so unknown is distinct from zero; the identity of a spender is an enum, so a sub-agent's account is not anonymous; and recording is append only, with no update path, so failed rows stay.

Wiring it in takes four changes: one row per completed request in the loop, one each for summarization and distillation, one at the end of a sub-agent, and serialization into the session file. Under forty lines. The work is not the code, it is passing the ledger everywhere a &self method needs it, which means an Arc with a mutex inside, the same pattern the board and the gate already use.

Three invariants to test

One. The sum is consistent. All span usage adds up to the totals. This catches recording without aggregating, and aggregating while missing a category.

Two. Parent equals self plus children. This catches sub-agent cost that is recorded but never attached to the parent.

Three. Failures have rows. Point at a mock endpoint that returns 500, then assert there is a row with an error outcome and a non-zero request count. This is the most valuable of the three, because it forces the failed path to carry its usage out, which is the signature change described earlier. Test first, and the structure has to become correct.

None of these needs a real API. A local mock returning fixed JSON is enough, and the repository already has that infrastructure.

Seven places to harden

One. Move accounting before the error return. Record that a request was issued, then add tokens on success. Three lines, and the most basic missing entry is gone, with requests meaning requests issued and successful counted separately.

Two. Give usage optional cached and reasoning fields. Two optional fields and two more lines in the parser, and cache savings and reasoning costs become queryable.

Three. Collect the usage from summarization, distillation and sub-agents. One line each, once a ledger exists. This is the only fix for the "requests is half the truth" gap.

Four. Return a structure from a delegation rather than a string, and add usage to the board's job, so the board can name the most expensive sub-agent.

Five. Upgrade the session file to an object with metadata, accepting bare arrays as version one on load. This is what stops /cost from being zero after a resume.

Six. Move retries and fallback out of stderr into the event channel, so the terminal and the GUI see the same information and retries can enter the ledger.

Seven. Put total usage on both terminal events. One protocol change, and no streaming client has to sum, and no failure loses partial usage.

The first three plug leaks, four and five build structure, six and seven unify definitions. If only one is possible, do the first. If three are possible, do one, five and seven, which cover a missing entry, a misattribution and a fuzzy definition respectively.

Closing, and what the eight posts describe

Logs and ledgers are different things. A log is a stream that answers what happened; a ledger is a table that answers who spent how much. NanoHermes has the first and not the second, and its three scalars live in process memory and reset on restart.

Missing entries are not carelessness, they are a structural absence of place. Compaction, distillation and sub-agents all call the model directly, none holds a mutable agent, and the totals are a copyable value. Before they can be recorded, the ledger has to be promoted from a field to a shared object. That is the same lesson as the previous post from the other side: shared state needs an owner, and the owner needs somewhere to be written.

And the value of observability is reconciliation, not printing. A system that can answer what this task cost, where it went and why it failed needs no fancy interface, only a row per unit of consumption with who, what, how much and when, and rows that outlive the process.

Writing this series, I kept returning to one criterion: the engineering quality of an agent depends on which things it treats as first-class citizens. The loop is one. The context budget is one. Memory writes and retrieval are one. Output caps are one. Threads and quotas are one. Permission gates are one. Responsibility boundaries are one. And this post argues that the ledger should be one too, not a log bolted on afterwards but a structure that participates in the data flow from day one.

Compressed one more time: a reliable agent is a system that makes explicit trade-offs in eight directions, the loop, context, memory, tools, concurrency, security, multi-agent behaviour and observability. Each direction has a default that will hurt you: no compaction by default, trusting tool output by default, shared state by default, logs instead of a ledger by default. What is valuable about NanoHermes is not that it gets all eight right, but that its trade-offs are legible: two hundred lines of main loop, one JSON memory file, a thirty line gate, a three scalar ledger. Each can be read in half an hour, and then you can say where it breaks.

Which is why almost every post in this series ends with a list of places to harden. Not so readers will patch NanoHermes, but to make one point: the most effective way to understand a system is to find the conditions under which it fails. Being able to list the failure modes is what reading it properly looks like.
