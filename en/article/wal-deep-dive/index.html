Write the log first: how WAL actually works, read at the source

2026-10-28 · 34 min · Stack Frame

Who this is for: backend engineers who want to see what "crash recovery" looks like in source; anyone writing a storage engine, a log, or an embedded database; anyone who has been hit with WAL, fsync, checkpoint and group commit without reading an implementation.

TL;DR: WAL is not a feature. It is four small rules. Append only. Check every record. Stop at the first bad one. Write the ledger before you touch the data. Nothing here is invented: everything comes from SQLite's src/wal.c and the log layer of LevelDB and RocksDB, down to the 32-byte file header, the 24-byte frame header, the 7-byte physical record header, the 32 KB block, two checksum algorithms, salts, the ordering rule, group commit, the three sync levels, four checkpoint modes and four recovery modes.

Reading time around 34 minutes. Level: advanced.

Why a crash lands exactly on the half-written part

Every storage system faces the same crime scene. You are writing bytes into a data file, and halfway through, the power goes.

Without a log, the data file is updated in place. An index page has just been given a new pointer, and the page it points at has not been written; or the first half of a page is the new version and the second half is the old one, which is a torn page. On restart the filesystem hands you something physically legal and logically self-contradictory: checksums that do not match, or worse, a pointer into an offset that never existed.

The whole idea of write-ahead logging fits in one sentence. Before touching the data file, append what you intend to do to another file that only grows; after a crash, replay the log to bring the data file back to a consistent state.

That sounds like a change of order. Turning it into engineering requires answering very specific questions. What does an appended record look like, and how do you know one is complete? If the write dies halfway, how does recovery tell a complete record from garbage? If the log wraps around and reuses space, how do old bytes avoid passing as new ones? Where exactly in the code is the "before" of "before you touch the data"? At what moment is fsync mandatory, and what is lost if it does not happen? The log cannot grow forever, so when and how does its content move back into the data file? And when the tail left by a crash is corrupt, do you refuse to start or salvage what you can?

SQLite and the LevelDB lineage evolved two independent answers. Their formats have nothing in common, and yet, with the source open, four rules match exactly. This post follows those rules: two formats first, then checksums, recovery, salts, commit points, ordering, group commit, sync semantics, checkpoints, recovery modes and reader visibility, and a design checklist at the end.

The contract: four promises

The third rule is the counterintuitive one: stop, do not repair. Recovery never guesses, never scans, never tries to resynchronise past bad bytes. It accepts only the contiguous prefix that passes checks from the start of the file. Everything after the damage, however much it looks like data, is treated as absent. That conservatism is the foundation the rest stands on, and you will see it implemented three separate times.

Two terms first, used throughout. A physical log records which page became what. SQLite's WAL stores whole page images, so recovery copies pages back verbatim. A logical log records which operations happened. The LevelDB WAL stores write batches, so recovery re-executes them.

Format one: SQLite page frames

A SQLite WAL file is a 32-byte header followed by frames, each frame being a 24-byte frame header and one complete database page. The comment block at the top of wal.c pins the header layout down.

**     0: Magic number.  0x377f0682 or 0x377f0683
**     4: File format version.  Currently 3007000
**     8: Database page size.  Example: 1024
**    12: Checkpoint sequence number
**    16: Salt-1, random integer incremented with each checkpoint
**    20: Salt-2, a different random integer changing with each ckpt
**    24: Checksum-1 (first part of checksum for first 24 bytes of header).
**    28: Checksum-2 (second part of checksum for first 24 bytes of header).

The last four bytes of the header are a checksum over the first twenty-four. The header is checked too, so a bad header invalidates the file. The writing code lives in walFrames().

    sqlite3Put4byte(&aWalHdr[0], (WAL_MAGIC | SQLITE_BIGENDIAN));
    sqlite3Put4byte(&aWalHdr[4], WAL_MAX_VERSION);
    sqlite3Put4byte(&aWalHdr[8], szPage);
    sqlite3Put4byte(&aWalHdr[12], pWal->nCkpt);
    if( pWal->nCkpt==0 ) sqlite3_randomness(8, pWal->hdr.aSalt);
    memcpy(&aWalHdr[16], pWal->hdr.aSalt, 8);
    walChecksumBytes(1, aWalHdr, WAL_HDRSIZE-2*4, 0, aCksum);
    sqlite3Put4byte(&aWalHdr[24], aCksum[0]);
    sqlite3Put4byte(&aWalHdr[28], aCksum[1]);

The low bit of the magic is borrowed to carry byte order. Set to zero it means checksums run in native order; set to one it means big endian. One magic bit answers both "is this a WAL" and "how do I read it". Recovery applies the same test and gives every failure the same outcome, abandoning the file.

    magic = sqlite3Get4byte(&aBuf[0]);
    szPage = sqlite3Get4byte(&aBuf[8]);
    if( (magic&0xFFFFFFFE)!=WAL_MAGIC
     || szPage&(szPage-1)
     || szPage>SQLITE_MAX_PAGE_SIZE
     || szPage<512
    ){
      goto finished;
    }
    pWal->hdr.bigEndCksum = (u8)(magic&0x00000001);
    pWal->szPage = szPage;
    pWal->nCkpt = sqlite3Get4byte(&aBuf[12]);
    memcpy(&pWal->hdr.aSalt, &aBuf[16], 8);

    /* Verify that the WAL header checksum is correct */
    walChecksumBytes(pWal->hdr.bigEndCksum==SQLITE_BIGENDIAN,
        aBuf, WAL_HDRSIZE-2*4, 0, pWal->hdr.aFrameCksum
    );
    if( pWal->hdr.aFrameCksum[0]!=sqlite3Get4byte(&aBuf[24])
     || pWal->hdr.aFrameCksum[1]!=sqlite3Get4byte(&aBuf[28])
    ){
      goto finished;
    }

The page size test is the familiar power-of-two bit trick. Page size doubles as the fixed stride between frames, so a non-power-of-two value would break the offset formula that locates any frame.

The frame header is documented the same way.

**     0: Page number.
**     4: For commit records, the size of the database image in pages
**        after the commit. For all other records, zero.
**     8: Salt-1 (copied from the wal-header)
**    12: Salt-2 (copied from the wal-header)
**    16: Checksum-1.
**    20: Checksum-2.

  assert( WAL_FRAME_HDRSIZE==24 );
  sqlite3Put4byte(&aFrame[0], iPage);
  sqlite3Put4byte(&aFrame[4], nTruncate);
  if( pWal->iReCksum==0 ){
    memcpy(&aFrame[8], pWal->hdr.aSalt, 8);

    nativeCksum = (pWal->hdr.bigEndCksum==SQLITE_BIGENDIAN);
    walChecksumBytes(nativeCksum, aFrame, 8, aCksum, aCksum);
    walChecksumBytes(nativeCksum, aData, pWal->szPage, aCksum, aCksum);

    sqlite3Put4byte(&aFrame[16], aCksum[0]);
    sqlite3Put4byte(&aFrame[20], aCksum[1]);
  }else{
    memset(&aFrame[8], 0, 16);
  }

The calling convention is the point. The checksum argument is both input and output: each frame starts from the previous frame's checksum, accumulates the first eight header bytes, then the whole page. Every frame therefore carries the history of everything before it, and altering any frame on the chain breaks every checksum after it.

The write order is equally fixed: header first, body second.

  walEncodeFrame(p->pWal, pPage->pgno, nTruncate, pData, aFrame);
  rc = walWriteToLog(p, aFrame, sizeof(aFrame), iOffset);
  if( rc ) return rc;
  /* Write the page data */
  rc = walWriteToLog(p, pData, p->szPage, iOffset+sizeof(aFrame));

Because the header lands before the body, the most likely crash shape is a complete header over a torn body, and the checksum covers the body, so the tear is found. The design anticipates the accident it will meet.

Format two: LevelDB physical records

LevelDB's log layer knows nothing about pages. It knows records, cut into blocks of 32 KB. db/log_format.h defines the whole format.

enum RecordType {
  // Zero is reserved for preallocated files
  kZeroType = 0,

  kFullType = 1,

  // For fragments
  kFirstType = 2,
  kMiddleType = 3,
  kLastType = 4
};
static const int kMaxRecordType = kLastType;

static const int kBlockSize = 32768;

// Header is checksum (4 bytes), length (2 bytes), type (1 byte).
static const int kHeaderSize = 4 + 2 + 1;

A physical record is a 7-byte header and a payload. Four types exist because one logical record may not fit in the space left in a block, so it is fragmented across blocks: full if it fits, otherwise a first fragment, some middles, and a last. The writer encodes the header here.

  // Format the header
  char buf[kHeaderSize];
  buf[4] = static_cast<char>(length & 0xff);
  buf[5] = static_cast<char>(length >> 8);
  buf[6] = static_cast<char>(t);

  // Compute the crc of the record type and the payload.
  uint32_t crc = crc32c::Extend(type_crc_[t], ptr, length);
  crc = crc32c::Mask(crc);  // Adjust for storage
  EncodeFixed32(buf, crc);

The array of per-type seeds is computed once at startup, and extending from it makes a single CRC cover both the type byte and the data. The mask is the standard CRC32C storage transform that keeps all-zero data from producing a plausible-looking all-zero checksum.

When fewer than seven bytes remain in a block, no header fits, so the tail is zero-filled and a new block starts. That is why recovery must tolerate zeros: they are structurally necessary padding, not damage.

RocksDB keeps the same skeleton and adds a recyclable header that carries a log number, folding it into the CRC.

constexpr unsigned int kBlockSize = 32768;

// Header is checksum (4 bytes), length (2 bytes), type (1 byte)
constexpr int kHeaderSize = 4 + 2 + 1;

// Recyclable header is checksum (4 bytes), length (2 bytes), type (1 byte),
// log number (4 bytes).
constexpr int kRecyclableHeaderSize = 4 + 2 + 1 + 4;

With both skeletons in hand, the first question has an answer. How do you know a record is complete? SQLite: the chained checksum over header and body matches. LevelDB: the CRC in the 7-byte header matches, and the fragments reassemble to a last-type record. Both define completeness as a computable predicate, not a resemblance.

Checksums: two algorithms, one question of coverage

SQLite does not use an off-the-shelf CRC. It uses a pair of 32-bit rolling accumulators whose core loop is five lines.

  }else{
    do {
      s1 += *aData++ + s2;
      s2 += *aData++ + s1;
    }while( aData<aEnd );
  }
  assert( aData==aEnd );

  aOut[0] = s1;
  aOut[1] = s2;

Both accumulators are unsigned 32-bit, so overflow wraps modulo two to the thirty-two for free. The header comment explains the mathematical property: each byte is weighted by a Fibonacci weight, and the weights run in reverse, so earlier bytes carry more weight, and the second accumulator spans one more term than the first.

That property is what makes it useful here. Later frames depend on the initial value supplied by earlier ones, so a change anywhere propagates to the end of the chain and cannot hide. The hot path is unrolled eight bytes at a time, which tells you this code runs on every frame.

LevelDB uses standard CRC32C with a detail that is easy to miss: the length field is not covered. The reader makes the coverage explicit.

    // Check crc
    if (checksum_) {
      uint32_t expected_crc = crc32c::Unmask(DecodeFixed32(header));
      uint32_t actual_crc = crc32c::Value(header + 6, 1 + length);
      if (actual_crc != expected_crc) {
        // Drop the rest of the buffer since "length" itself may have
        // been corrupted and if we trust it, we could find some
        // fragment of a real log record that just happens to look
        // like a valid log record.
        size_t drop_size = buffer_.size();
        buffer_.clear();
        ReportCorruption(drop_size, "checksum mismatch");
        return kBadRecord;
      }
    }

Starting at the type byte and running one plus the length covers type and payload while skipping the two length bytes. If the length flips, the slice is the wrong size and the CRC fails, so damage is still detected. The comment states the real defence: once the length is not trusted, it must never be used to hunt for the next record that happens to look valid. On a mismatch the whole buffer is dropped, because discarding too much beats accepting the wrong thing. That is "stop at the first bad record" expressed at byte level.

A false return breaks the loop, and the outer loop stops too. The replay range is therefore always the prefix from the start of the file up to the last contiguous good frame, and a half-written tail is excluded by construction.

    ...

Ten lines above that loop, the comment answers why nothing looks for the next record after a bad CRC.

  // We intentionally make log::Reader do checksumming even if
  // paranoid_checks==false so that corruptions cause entire commits
  // to be skipped instead of propagating bad information (like overly
  // large sequence numbers).
  log::Reader reader(file, &reporter, true /*checksum*/, 0 /*initial_offset*/);

Checksumming stays on even when paranoid checks are off, because skipping a whole commit is far better than replaying half of one. A partially applied batch would push sequence numbers ahead and corrupt the ordering of everything written afterwards.

Fragment atomicity comes from the reader's state machine, and the end-of-file branch shows the trade-off plainly.

      case kEof:
        if (in_fragmented_record) {
          // This can be caused by the writer dying immediately after
          // writing a physical record but before completing the next; don't
          // treat it as a corruption, just ignore the entire logical record.
          scratch->clear();
        }
        return false;

A crash between two fragments of one logical record is an ordinary accident, not corruption: the half-assembled record is discarded and recovery ends. Fragmentation thus provides atomicity for free, since only a record that reached its last fragment is ever delivered.

Salts: invalidating the previous round

An append-only file eventually reaches the end and has to wrap, either overwriting from the start or restarting after a checkpoint. The danger is that a crash during overwriting leaves a mixture of new frames and old frames, each with a self-consistent chain, and recovery cannot tell which round they belong to.

SQLite gives each round an identity: a salt. The frame header copies the file salt at write time, and recovery compares salts before computing checksums. The timing is in the wal.c comment.

** After each checkpoint, the salt-1 value is incremented and the salt-2
** value is randomized.  This prevents old and new frames in the WAL from
** being considered valid at the same time and being checkpointing together
** following a crash.

static void walRestartHdr(Wal *pWal, u32 salt1){
  volatile WalCkptInfo *pInfo = walCkptInfo(pWal);
  int i;                          /* Loop counter */
  u32 *aSalt = pWal->hdr.aSalt;   /* Big-endian salt values */
  pWal->nCkpt++;
  pWal->hdr.mxFrame = 0;
  sqlite3Put4byte((u8*)&aSalt[0], 1 + sqlite3Get4byte((u8*)&aSalt[0]));
  memcpy(&pWal->hdr.aSalt[1], &salt1, 4);
  walIndexWriteHdr(pWal);
  AtomicStore(&pInfo->nBackfill, 0);
  ...
}

The first salt increments and the second becomes random. Frames left over in the overwritten region still carry the old salt, so the comparison fails immediately. Old frames are not deleted, they are invalidated. The cost is eight bytes copied per frame and one comparison at recovery, and it closes the nastiest scenario in the whole design.

One detail matters: the header restart only happens when the read slot can be taken, meaning no active readers. Changing the salt invalidates every reader's snapshot, so they must be gone first. Correctness and concurrency control are the same lock here.

The commit point: one field decides atomicity

A multi-page transaction spans several frames. If the crash lands in the middle, how does recovery know whether the transaction counts? The answer is the field at offset four: zero on ordinary frames, and the post-commit page count on the commit frame. The comment inside the replay loop is the whole mechanism.

        /* If nTruncate is non-zero, this is a commit record. */
        if( nTruncate ){
          pWal->hdr.mxFrame = iFrame;
          pWal->hdr.nPage = nTruncate;

The visible bound only advances on a commit frame. If the crash came earlier, recovery reads the orphan frames with a zero field but stops the bound at the previous commit, so the uncommitted tail does not exist logically. Atomicity is not implemented by rolling back. It is implemented by not moving the bound.

LevelDB puts its commit point in the 12-byte write batch header: an eight-byte sequence number followed by a four-byte count, then the records. The sequence is the first number in the batch, the count is how many operations follow. Writing sets the sequence against the global counter, replay increments per operation, and a final check that the number of applied operations matches the count catches truncated batches. One batch equals one logical record in the log, so combined with fragment atomicity, a batch either enters the memtable whole or not at all.

Both roads end in the same place: atomicity is bounded by the end of a record in the log. SQLite marks it with a dedicated field and LevelDB encodes it in the record's own consistency.

The ordering rule: log first, memory second

The "before" of "write the log before the data" is two adjacent statements. The LevelDB write path says it in code and comment together.

    // Add to log and apply to memtable.  We can release the lock
    // during this phase since &w is currently responsible for logging
    // and protects against concurrent loggers and concurrent writes
    // into mem_.
    {
      mutex_.Unlock();
      status = log_->AddRecord(WriteBatchInternal::Contents(write_batch));
      bool sync_error = false;
      if (status.ok() && options.sync) {
        status = logfile_->Sync();
        if (!status.ok()) {
          sync_error = true;
        }
      }
      if (status.ok()) {
        status = WriteBatchInternal::InsertInto(write_batch, mem_);
      }
      mutex_.Lock();

Read it in order: append to the log, optionally sync, then insert into the memtable, with every step gated on the previous status. A failed log write never reaches memory, and neither does a failed sync. The reverse order cannot be defended after a single-machine crash, because the in-memory claim of durability evaporates on power loss while the log never landed.

RocksDB keeps the same order with many writers and encodes it in callback semantics, calling the pre-release callback after the WAL write and before the memtable write. The write itself goes through WriteGroupToWAL into log_writer->AddRecord. Two generations, one order, because that order is the definition.

SQLite is the physical route, and the equivalent is frames reaching disk before the frame counter becomes visible. walFrames writes the frames first and only then advances the header's bound, so bytes in the log always precede the header that refers to them and no reader can observe a bound pointing at a frame that is not there.

Group commit: one sync shared by many writes

fsync is where the cost lives. Sync on every commit and the disk becomes a serial device. Group commit lets one writing thread finish the work for everyone queued behind it. LevelDB keeps a queue of writers and wakes the head, which merges the requests behind it into one batch before writing.

  if (status.ok() && updates != nullptr) {  // nullptr batch is for compactions
    WriteBatch* write_batch = BuildBatchGroup(&last_writer);
    WriteBatchInternal::SetSequence(write_batch, last_sequence + 1);
    last_sequence += WriteBatchInternal::Count(write_batch);

The group builder packs suitable requests into a single batch under a byte cap, so small writes are not starved, and sequence assignment keeps them contiguous in the log. Group commit changes the aggregation of IO, not the semantic unit of the log: each request is still its own batch.

RocksDB names the same pattern leader and follower, and the comment states the intent directly: the leader picks up the remaining writers when suitable and finishes them in the same batch. One WriteGroupToWAL covers the group, then the group shares one InsertInto. Whether a sync is needed is decided by OR-ing the group's options, so one request demanding durability makes the whole group durable. That is the fairness price, and the entire reason N syncs collapse into one.

fsync semantics: what the three sync levels really mean

When a sync is mandatory is the most muddled part of WAL. SQLite makes it configurable and leaves a complete derivation in the source.

#define WAL_SYNC_FLAGS(X)   ((X)&0x03)
#define CKPT_SYNC_FLAGS(X)  (((X)>>2)&0x03)

  if( pPager->noSync ){
    pPager->syncFlags = 0;
  }else if( pgFlags & PAGER_FULLFSYNC ){
    pPager->syncFlags = SQLITE_SYNC_FULL;
  }else{
    pPager->syncFlags = SQLITE_SYNC_NORMAL;
  }
  pPager->walSyncFlags = (pPager->syncFlags<<2);
  if( pPager->fullSync ){
    pPager->walSyncFlags |= pPager->syncFlags;
  }

One pragma value is split into two halves, one for the commit path and one for checkpoints. The base level shifts into the high bits that checkpoints read, and the low bits stay zero unless the mode is full. The commit path only looks at the low bits.

  if( isCommit && WAL_SYNC_FLAGS(sync_flags)!=0 ){

NormalNo syncSync
FullSyncSync

Why can the normal mode skip the commit sync? Because in WAL mode a commit only appends to the log and never touches the data file. A crash can lose the log tail, which the format already permits, and the data file is protected by the checkpoint sync. The famous comment in wal.c states the benefit: all barrier operations happen in the checkpoint routine, so if checkpoints run in the background, foreground threads never block on a long fsync.

Synchronisation moves from the commit path to the checkpoint path, foreground threads stop stalling, and the price is that a process crash may lose the last few commits while the database stays consistent. The full mode pays a barrier on every commit and loses only uncommitted work. These levels are not grades of safety; they are answers to where you accept a loss window.

Checkpoints: the log cannot grow forever

#define SQLITE_CHECKPOINT_NOOP    -1  /* Do no work at all */
#define SQLITE_CHECKPOINT_PASSIVE  0  /* Do as much as possible w/o blocking */
#define SQLITE_CHECKPOINT_FULL     1  /* Wait for writers, then checkpoint */
#define SQLITE_CHECKPOINT_RESTART  2  /* Like FULL but wait for readers */
#define SQLITE_CHECKPOINT_TRUNCATE 3  /* Like RESTART but also truncate WAL */

The four are strictly progressive. Passive waits for nobody and copies back what it can. Full takes the write lock and reports busy if it cannot finish. Restart additionally waits for readers so the log can be reused from the start, which works with a salt change. Truncate then cuts the file to zero. The differences are visible in walCheckpoint, where a failure to take the lock downgrades rather than errors out.

      if( eMode!=SQLITE_CHECKPOINT_PASSIVE ){
        rc = walBusyLock(pWal, xBusy2, pBusyArg, WAL_WRITE_LOCK, 1);
        if( rc==SQLITE_OK ){
          pWal->writeLock = 1;
        }else if( rc==SQLITE_BUSY ){
          eMode2 = SQLITE_CHECKPOINT_PASSIVE;
          xBusy2 = 0;
          rc = SQLITE_OK;
        }
      }

A checkpoint is maintenance, and doing half of it beats doing none. Best effort with an honest report is more useful than all-or-nothing.

Combined with the sync table, the division of labour is: in normal mode the log tail can be lost, while the checkpoint syncs whatever it has already copied into the data file, and the log continues from that point. Every change to the data file precedes its own barrier, and that invariant is the whole of "opening after a crash is always consistent".

Recovery modes: which timeline do you want

LevelDB always tolerated a corrupt tail. RocksDB turned the decision into an explicit choice, and the enum comments say why.

enum class WALRecoveryMode : char {
  // Original levelDB recovery
  //
  // We tolerate the last record in any log to be incomplete due to a crash
  // while writing it. Zeroed bytes from preallocation are also tolerated in the
  // trailing data of any log.
  //
  // Use case: Applications for which updates, once applied, must not be rolled
  // back even after a crash-recovery. In this recovery mode, RocksDB guarantees
  // this as long as `WritableFile::Append()` writes are durable. In case the
  // user needs the guarantee in more situations (e.g., when
  // `WritableFile::Append()` writes to page cache, but the user desires this
  // guarantee in face of power-loss crash-recovery), RocksDB offers various
  // mechanisms to additionally invoke `WritableFile::Sync()` in order to
  // strengthen the guarantee.
  //
  // This differs from `kPointInTimeRecovery` in that, in case a corruption is
  // detected during recovery, this mode will refuse to open the DB. Whereas,
  // `kPointInTimeRecovery` will stop recovery just before the corruption since
  // that is a valid point-in-time to which to recover.
  kTolerateCorruptedTailRecords = 0x00,
  // Recover from clean shutdown
  // We don't expect to find any corruption in the WAL
  // Use case : This is ideal for unit tests and rare applications that
  // can require high consistency guarantee
  kAbsoluteConsistency = 0x01,
  // Recover to point-in-time consistency (default)
  // We stop the WAL playback on discovering WAL inconsistency
  // Use case : Ideal for systems that have disk controller cache like
  // hard disk, SSD without super capacitor that store related data
  kPointInTimeRecovery = 0x02,
  // Recovery after a disaster
  // We ignore any corruption in the WAL and try to salvage as much data as
  // possible
  // Use case : Ideal for last ditch effort to recover data or systems that
  // operate with low grade unrelated data
  kSkipAnyCorruptedRecords = 0x03,
};

The four run from refusing to start to salvaging regardless, and the default is point-in-time. The phrase in the comment, that the point before corruption is a valid point in time to recover to, is the philosophy in one line: the log before the damage is a legitimate snapshot, and stopping there is not data loss, it is keeping the promise.

The mechanism is unchanged in every mode. Stop at the first bad record, then choose what to do: refuse to open, stop at the point before the damage, treat the tail as a normal end, or skip the bad record and keep digging. Mechanism and policy are cleanly separated, which is the engineering maturity level that did not exist in the LevelDB era.

Reader visibility: where the snapshot bound comes from

Recovery answers how many frames in the log are legal. Readers also need to know which frame their snapshot sees, and SQLite stores the answer as one number. The frame lookup starts from two bounds: the upper bound snapshotted when the read transaction began, and a lower bound that keeps stale slots out.

  u32 iRead = 0;                  /* If !=0, WAL frame to return data from */
  u32 iLast = pWal->hdr.mxFrame;  /* Last page in WAL for this reader */
  ...
  if( iLast==0 || (pWal->readLock==0 && pWal->bShmUnreliable==0) ){
    *piRead = 0;
    return SQLITE_OK;
  }

      if( iFrame<=iLast
       && iFrame>=pWal->minFrame
       && sLoc.aPgno[(iH-1)&(HASHTABLE_NPAGE-1)]==pgno
      ){
        iRead = iFrame;
      }

For a given page it takes the highest legal frame, so multiple versions of a page resolve to the one the snapshot allows. The upper bound comes from the whole recovery and validation machinery, and the reader never re-validates: it consumes a conclusion someone else proved. Writer, recovery and reader each do one job, and a single number passes between them.

WAL as a general technique

WAL does not belong to databases. It belongs to any append-only system that cannot survive an in-place rewrite accident. Two witnesses.

The LevelDB manifest is the same log format re-employed. Version metadata, which files make up the current set, is written with the same writer and synced, then decoded with the same reader on open. "Metadata must not contradict itself after a crash" and "data must not be lost after a crash" are the same problem, so one log layer serves both files.

SQLite writes page images, LevelDB writes operations, and a text-based engine writes JSON lines. The same rule survives the format change: only a contiguous, verified prefix counts. Three implementations, one contract, which is why the contract comes before the formats.

Items one to five are the format layer, six to eight the semantic layer, nine to twelve the policy layer. The common mistake is deferring the policy items as advanced features. They decide whether an incident costs you a few commits or a database that will not open, so they need an answer in the first version, even if the answer is a hardcoded default.

Closing

Not one line here was written by me, and yet the skeleton of two industrial logs is now on the table: SQLite's 32-byte file header, 24-byte frame header and chained rolling checksum, against LevelDB's 7-byte record header, 32 KB blocks and CRC32C with fragmentation. Different in every byte, identical in four rules. Append only, and change the salt on wraparound. Check every record over an explicit byte range. Stop at the first bad record and accept only a contiguous prefix. Write the ledger before the data, with sync points you can point at.

What is worth chewing on is the temperament they share: they do not guess. Recovery does not guess at what follows the bad bytes. Readers do not guess whether a frame is valid. Checkpoints do not guess whether the lock is available. Every place that could need a guess is replaced by a computable predicate, and a computable predicate is the entire shape of consistency in source code.

Next time someone says a database does not lose data on a crash, you can name the pieces: recovery, frame decoding, the salt restart, the sync flag masks, the append-then-insert order, the point-in-time recovery mode. The promise is not mysterious. It is the sum of those branches.
