A deliberately narrow Windows SSH client

The positioning first. NanoSSH is a Windows SSH client that does five things: a server list, a terminal, SFTP, local port forwarding and key management. No accounts, no cloud sync, no plugin market, no AI assistant and no auto-update. The narrow scope is the product thesis, not an unfinished roadmap.

The stack is Wails v2 plus WebView2. The Go backend splits into three parts.

  • internal/sshcore is a pure SSH core with no UI dependency.
  • internal/shell is the Wails binding facade, owning sessions, files, forwards, keys and the tray.
  • internal/store handles persistence.

The frontend is framework-free TypeScript. The DOM is built by a hand-written helper, state uses a signals library, and the terminal is xterm.js 6. Seven runtime dependencies in total, six of them xterm and its addons.

The artifact is a single executable, 13.23 MB on x64, with no external runtime. The build script sets 14 MB as a hard ceiling and fails the build when the binary goes past it. Five direct Go dependencies, twenty-seven indirect.

Those numbers aren't marketing. They constrain a lot of later decisions: no SQLite, a hand-written tray, no third-party systray library, and as few new modules as possible.

Because the constraints are hard, the problems in this project are concrete. Not "should we support feature X", but "why did this Chinese character turn into a question mark", "why does clicking the tray icon do nothing", "why does vim open misaligned". Each problem below has a symptom, a cause, a fix and a cost.

Architecture: put the risk in the replaceable layer

The most important architectural decision is separating SSH protocol logic from the UI shell completely. sshcore doesn't know that Wails, WebView2 or xterm exist. It exposes connections, sessions, SFTP, forwarding and key parsing. shell translates those capabilities into callable bindings and moves byte streams into event channels. The frontend reaches the backend through two layers, an API module and a transport module.

The benefit is that risk sits in the replaceable layer. Wails is the shell. Replacing it with bare WebView2 or another window container means changing main.go, the bindings in internal/shell and two frontend files. sshcore doesn't move.

The reverse holds too. Protocol tests need no window, because an in-process test SSH server exercises connections, PTYs, SFTP and forwarding directly.

The backend's event outlet is a function type rather than a hard-coded Wails call.

type emitFunc func(ctx context.Context, eventName string, data ...any)

Both the app and each shell session hold that function. Production assigns the real Wails emitter; tests assign a collector. That small indirection is the precondition for testing backpressure, host-key prompts and transfer progress automatically.

Persistence follows the same narrow rule. servers.json is the only database, versioned at 1. Reads run a pure-function migration, saves write a backup first and then go through a temporary file, an fsync and a rename. known_hosts uses standard OpenSSH format, so it can be exchanged with the system file. Private keys are standard OpenSSH keys. Logs live in their own directory. The data root defaults to %APPDATA%\\NanoSSH, overridden by an environment variable for tests and portable mode. There are no hidden binary formats; when something goes wrong, everything opens in a text editor.

The window layer has a few pieces of plumbing that aren't business logic but do shape the experience. The frameless title bar is drawn by the frontend, while Wails keeps resize hot zones and shadow. A single-instance lock focuses the existing window rather than starting a second process. The Mica background reads the Windows build number from the registry and enables translucency only from build 22621 onward, falling back to opaque on older systems, which prevents a transparent window with no background. The frontend asks whether Mica is enabled and decides whether the title bar and sidebar become translucent surfaces.

The frontend has one deliberate seam as well. Views, terminal and components never touch the global Wails object. Every binding call and event subscription goes through the API module. Byte transport lives alone in the transport module, the only frontend file strongly tied to the shell, so replacing Wails later rewrites a bounded area.

Problem 1: the README says binary WebSocket, the code is a base64 event bridge

Symptom. The README mentions binary WebSocket IPC with ack-based backpressure, yet there is no WebSocket server and no binary framing anywhere in the code. Terminal data travels over the Wails event emitter, with event names like term:data:<sessionId>.

Cause. The README described the original design intent, and the implementation settled on Wails' own event bridge. A later section of the same README says a worker decodes base64, which contradicts the first claim.

Wails binding calls are JSON-serialized, and so are event payloads. A Go byte slice arrives in the frontend as a base64 string. The dependency tree does contain a WebSocket library, but as a transitive Wails dependency rather than this IPC implementation.

Fix. Rather than build a WebSocket to match the document, the project accepted the bridge's limits and compensated for them. The frontend decodes base64 in a web worker and transfers the array buffer to the main thread, so decoding never blocks rendering. The decoded bytes go straight to xterm's write call, with no string concatenation on the main thread.

function decodeBase64(input: string): Uint8Array {
  const bin = atob(input);
  const len = bin.length;
  const out = new Uint8Array(len);
  for (let i = 0; i < len; i++) out[i] = bin.charCodeAt(i);
  return out;
}

ctx.onmessage = (e: MessageEvent<string>) => {
  const buf = decodeBase64(e.data);
  ctx.postMessage(buf, [buf.buffer]);
};

Cost. Base64 inflates byte volume by roughly a third, so a 16 KiB terminal chunk becomes a string of about 21.8 KiB. Go also serializes JSON and the webview decodes base64.

What that buys isn't having to maintain a WebSocket service, no connection authentication to design, and no extra port outside Wails. For a local SSH client that is an acceptable trade, but the README was inaccurate. The correct fix was to document "Wails event bridge plus base64 decoding" instead of keeping a faster-sounding noun. Engineering documents should describe the implementation, not the wish.

If the project ever did move back to binary WebSocket, it would lose single-instance behavior, same-origin event dispatch and the no-extra-port property, and it would have to solve local authentication and a new attack surface. That's why the implementation wasn't changed to match the document.

When a worker is unavailable, in some restricted webview environments, the decoder falls back to synchronous base64 decoding on the main thread. Decoding then occupies the render thread and long output stutters more, but nothing is functionally missing. Each terminal session owns a worker, kept across tab switches and terminated only when the session closes, at the cost of a few more worker instances in memory.

Problem 2: multi-byte characters split across chunks

Symptom. An echo containing Chinese, Korean or emoji occasionally shows a replacement character in the middle of the output. It's intermittent, and more likely with longer output or a slower machine.

Cause. The backend originally converted each read to a string and split it into lines before sending. SSH channel read boundaries have nothing to do with character boundaries: a three-byte character can straddle two reads. Converting half a character to a string forces Go to emit a replacement character, and once a UTF-8 decode has happened the pieces can never be rejoined.

Fix. Byte slices end to end. The read buffer is a fixed 32 KiB, every read is copied immediately into a channel of depth eight, and the pump only merges, batches and sends. No line splitting and no decoding anywhere in the backend. Standard output and standard error have separate reader goroutines writing into the same channel, consumed by a single writer. xterm receives raw bytes and does its own decoding and wide-character handling.

Two paths must be distinguished. An interactive shell streams through the pump. A non-interactive command run collects output in a limited buffer capped at 8 MiB, silently dropping the excess without blocking the remote. The second path is for probes and batch work only; large output has to go through the shell or the SFTP streaming interface.

buf := make([]byte, 32<<10)
for {
    n, err := rd.Read(buf)
    if n > 0 {
        cp := make([]byte, n)
        copy(cp, buf[:n])
        select {
        case chunks <- cp:
        case <-sess.done:
            return
        }
    }
    if err != nil {
        return
    }
}

A test covers this specific path. The remote echoes a line containing Chinese, Korean, Japanese and an emoji, and the test asserts the line is byte-identical with no replacement character. Another test pushes a 40,000-byte single line past the 16 KiB chunk cap, forcing several flush and ack rounds and confirming that nothing is dropped. The non-interactive path has an 8 MiB flood command to confirm large output reads continuously.

Cost. The backend gave up line-oriented processing. Keyword filtering, log writing or command auditing on the server side would have to happen in the frontend or in a separate parser. Each chunk is also copied, because the read buffer gets reused by the next read, which is a small memory cost for correct ownership semantics. Ordering between the two streams is still not strictly guaranteed; a PTY merges them, so in practice it looks right.

Problem 3: the ack loop and its three traps

Symptom. With a plain read-and-send approach, running cat on a large local file makes the webview event queue grow without bound. The terminal lags, then the window freezes. Worse, once the frontend is destroyed, the Go reader waits forever for an ack that will never arrive, so the session can neither be read nor closed.

Cause. Wails event emission provides no signal that the frontend has processed anything. xterm's write call is asynchronous; pushing more data before the buffer renders accumulates latency without limit. The SSH channel has a window, but that window covers Go's reader, not the webview renderer. The middle has no feedback loop, so the pressure piles up in process memory.

Fix. Make ack an explicit end-to-end backpressure signal. The backend sends one chunk at a time and waits for the frontend to ack inside xterm's write callback. Three constants govern it: at most 16 KiB per send, at most 8 ms of batching, and at most 30 seconds waiting for an ack. The ack channel has capacity one, and duplicate acks are dropped.

flush := func() {
    if len(pending) == 0 {
        return
    }
    data := pending
    pending = nil
    sess.emit(sess.ctx, "term:data:"+sess.id, data)
    select {
    case <-sess.ackCh:
    case <-sess.done:
    case <-time.After(termAckTimeout):
        wruntime.LogWarning(sess.ctx, "terminal: waiting for ack timed out, resuming reads")
    }
}

The frontend chains write and ack through a promise, so slow rendering can't reorder acks.

this.chain = this.chain
  .then(() => this.handlers.onData(bytes))
  .then(() => (this.disposed ? undefined : backend.ackTermData(this.sessionId)))
  .catch((err) => console.error("[nanossh] terminal write failed:", err));

Three traps sit here.

  1. The frontend can ack before the backend starts waiting, so the ack channel needs capacity one, otherwise the first ack is lost.
  2. Disposal must send one final ack, or the reader hangs until the 30-second timeout.
  3. Duplicate acks must be discarded safely, because only one chunk is in flight at any moment.

One detail inside flush is easy to miss. If the chunk channel is drained while waiting for an ack, the timer may already have fired, so the next loop iteration has to stop the timer and drain it, or a second flush happens immediately.

The 8 ms batch isn't about reducing event count. It's about sending small packets, such as keystroke echoes, promptly. Batching only at 16 KiB makes interaction feel sluggish.

In tests, the collector acks synchronously inside the event callback, which is equivalent to the fastest possible "already rendered". A real browser also goes through worker decoding, a buffer transfer and xterm rendering, so production chunk intervals are longer.

Cost. Throughput is capped by rendering speed, deliberately, because terminals want low latency rather than maximum bandwidth. Acks carry no chunk sequence number, so the implementation guarantees only one chunk in flight; parallelizing would require ids. The 30-second timeout is a safety net rather than a normal path, and it converts "the frontend hung" into "the backend keeps reading", which can mask a real rendering fault, so it has to be visible in logs. Without that timeout, the pump would wait forever after the first send once the collector stopped acking.

Problem 4: PTY width and height order

Symptom. vim opens fine locally but the whole screen misaligns through NanoSSH, and htop columns don't line up. Resizing the window sometimes makes it accidentally correct. The first suspicion was xterm's fit calculation, and the bug turned out to be in the backend.

Cause. Two contradictory naming conventions. RFC 4254 encodes the PTY request and window change with width first and height second, meaning columns then rows. The Go crypto SSH library's request and change calls take height first and width second. Following the RFC field order into the library swaps the two values, so vim receives 80 rows and 24 columns.

Fix. The project's own API is uniformly rows then columns. Shell options, resize, the start-shell request and the frontend resize call all follow that order, with comments spelling out the difference between the RFC and the library. A test pins it: the test server parses the PTY request exactly per the RFC and asserts the rows and columns arrive when expected.

if err := sess.RequestPty(term, rows, cols, opts.Modes); err != nil {
    sess.Close()
    return nil, fmt.Errorf("sshcore: requesting PTY (%dx%d) failed: %w", cols, rows, err)
}

Note that the error text still reads columns by rows, because that is for humans, while the actual argument order is rows then columns. Both perspectives have to coexist, or readers get confused.

There are defaults as well. A rows or columns value of zero or less falls back to 24 by 80, so a frontend that has not laid out yet can't send zeros. Resize rejects invalid sizes and never writes a zero-sized terminal to the remote. The frontend's fit call can throw before layout, so the wrapper swallows it and returns the current terminal size, deferring to the next resize observation.

Cost. The fit call returns rows and columns, and callers must pass them in that order, which the comments repeat more than once. The window-change message is fire-and-forget with no reply, so a successful return only means the bytes were written, not that the remote applied them, which means tests must poll the server's record. Dragging a window produces many resize requests, debounced at 150 ms, at the cost of a slightly delayed remote size.

Problem 5: known_hosts and the hard edges of trust on first use

Symptom. The first connection to an unknown host should show a fingerprint card. A changed host key should block clearly rather than offer an "ignore once" button that people click reflexively. In practice the error types returned by the known-hosts helper get lumped together, mixing unknown hosts with changed fingerprints.

Cause. In the key error returned by the helper, an empty wanted-key list means there is no record for that host, and a non-empty one means a record exists but the presented key doesn't match. The first is trust on first use; the second may signal a man in the middle. There is a third case as well, a distinct revoked error for hosts marked revoked in the file, which must block unconditionally. Mixing the three produces the classic "fingerprint changed, allow once" vulnerability.

Fix. Handle the revoked error first and return immediately. Then check whether the wanted-key list is non-empty. Unknown hosts offer three choices: this time only, trust and save, or cancel. A changed key accepts only an explicit replacement; both accept-once and refusal produce a rejected error. Replacement matches the old entry by address and writes a new public-key line. The write is atomic, with a temporary file, an fsync and a rename, at mode 0600.

The known-hosts helper requires the file to exist, so a first connection has to create the parent directory and an empty file first. Otherwise the first connect fails with a parsing error before the fingerprint card ever appears.

if len(keyErr.Want) > 0 {
    change := &HostKeyChange{Info: info}
    for _, wk := range keyErr.Want {
        change.OldFingerprints = append(change.OldFingerprints,
            ssh.FingerprintSHA256(wk.Key))
    }
    decision, perr := prompt(info, change)
    if perr != nil {
        return perr
    }
    if decision != HostKeyAcceptAndSave {
        return fmt.Errorf("%w (fingerprint changed)", ErrHostKeyRejected)
    }
    return writeKnownHost(knownHostsPath, hostname, key, true)
}

Tests cover three behaviours: prompting and saving on first contact, not prompting the second time, and blocking after the server rotates its key while the callback still receives the old fingerprint. Another test confirms that "this time only" isn't persisted and that both connections prompt again.

Cost. The known-hosts format supports hashed hostnames, and the replacement logic can't reverse a hash. Such lines are skipped and a new line is appended, so the old hashed record stays in the file and later connections may keep reporting a change until the user cleans it by hand. That's a documented boundary, with a comment saying hashed forms are treated as misses and preserved. On Windows, mode 0600 is only an intention; the actual access control comes from ACLs inherited from the application data directory.

Problem 6: the Windows ssh-agent named pipe

Symptom. Windows OpenSSH is installed and ssh-add lists keys, but agent authentication in NanoSSH always fails. With Git Bash installed as well, the agent socket environment variable exists, yet dialling it also fails.

Cause. Windows has no Unix domain sockets. The Windows OpenSSH agent listens on a fixed named pipe. The agent socket environment variable, even when present, may hold a Cygwin or MSYS private format that Go's Unix dial can't reach.

There is a second problem. When the pipe exists but all instances are busy, opening it returns a pipe-busy error, and reporting that directly tells the user the agent is unavailable.

Fix. Hand-written file opening plus wait-for-pipe logic, with no extra dependency. The pipe name is fixed, the deadline is three seconds, and a busy pipe retries every 50 ms. On success the handle is wrapped in an agent client, and the key list is fetched once before authenticating. An empty list produces a clear "run ssh-add first" message instead of the library's "no supported methods remain". The auth methods return a closer, which is closed on handshake failure and otherwise attached to the connection so it closes with it, so a failed handshake can't leak the pipe.

deadline := time.Now().Add(agentDialTimeout)
for {
    h, err := windows.CreateFile(name, windows.GENERIC_READ|windows.GENERIC_WRITE,
        0, nil, windows.OPEN_EXISTING, 0, 0)
    if err == nil {
        return os.NewFile(uintptr(h), agentPipeName), nil
    }
    if err != windows.ERROR_PIPE_BUSY || time.Now().After(deadline) {
        return nil, fmt.Errorf("sshcore: cannot connect to ssh-agent (%s): %w; "+
            "check that the Windows OpenSSH Authentication Agent service is running",
            agentPipeName, err)
    }
    time.Sleep(50 * time.Millisecond)
}

A Windows-only test asserts that the path really reaches the pipe namespace. With no agent running, the error must be file-not-found or pipe-busy, never invalid-name. If Go or the syscall bindings ever change device path handling, that test fails first, rather than a user reporting that agent authentication never works.

Cost. Only the Windows OpenSSH agent is supported. PuTTY's agent isn't, and no third-party protocol is pulled in to support it. Three seconds is a hard cap: better a clear error than a spinner that never resolves. Multiple SSH clients contend for the pipe, so failures inside the retry window are normal, and only past three seconds is it genuinely unavailable. Three seconds is shorter than the 15-second TCP connect timeout because the agent is a local resource that should answer in milliseconds.

Problem 7: the tray icon ignores clicks

Symptom. After closing the window the app minimizes to the tray. The icon is visible, but double-clicking does nothing and the context menu never opens. The log shows no errors and the process is alive.

Cause. Win32 window messages are delivered per thread, so the message window and the message loop must live on the same OS thread. Go goroutines can migrate between OS threads around blocking calls. Create the window on one thread and pump messages on another, and messages never arrive. The symptom looks exactly like "the icon didn't attach", when the message loop is simply not receiving callbacks.

Fix. The tray thread locks itself to its OS thread on entry and unlocks on exit. Both creating the message window and entering the message loop happen on that locked thread. The window is a message-only window, so it takes no screen space, and callbacks, balloons and the context menu are delivered through custom messages.

Creation is a synchronous handshake: the constructor blocks until ready or three seconds elapse, and on failure it returns an error so the caller can shut down normally. It never leaves the state where the window is hidden but the icon was never attached.

func (t *tray) run(done chan<- error) {
    runtime.LockOSThread()
    defer runtime.UnlockOSThread()
    // register the window class, create the message window, Shell_NotifyIcon,
    // then enter the GetMessage loop
}

The tray is created lazily. It takes no notification-area slot while the window is open; the icon appears only when the app actually minimizes. That also means a failed tray creation still lets the user exit, instead of being trapped in a background process with no way out.

The first balloon shows once, guarded by a flag, so it doesn't nag. The context menu returns the chosen command directly instead of routing window messages. Quitting destroys the icon through a custom message and ends the message loop.

Cost. One OS thread is locked for the tray's lifetime and must not block. Callbacks only post messages and flip state, with heavy work pushed back to the business layer. The window procedure defends every branch against panics, menu commands travel over a channel, and the tray thread never touches the database or the network. Only one tray icon is supported, so the window procedure is bound through a package-level variable rather than a window property. The handwritten Win32 code is about two hundred lines, less maintainable than a library, in exchange for zero new dependencies and a smaller binary.

Problem 8: the 14 MB ceiling

Symptom. As features accumulated, the artifact grew past 13.23 MB, leaving under 0.8 MB before the 14 MB limit. At that point any casual "just add a library" decision can fail the build.

Cause. The Wails runtime isn't small, and the SSH implementation from the crypto package, the WebView2 loader and the frontend bundle all live inside. The dependency graph also carries a batch of transitive Wails dependencies, such as an HTTP framework, a WebSocket library, and string and template helpers. Not all of them are reachable, but all of them are in the module graph. Add SQLite or a third-party tray library, and size runs away.

Fix. Turn size from a verbal agreement into a build assertion. The build script fixes the architecture and disables cgo, builds with stripped symbols and debug info, verifies that the executable's machine field matches x64, and then rounds the size and throws when it exceeds the threshold.

$sizeMB = [math]::Round((Get-Item $exe).Length / 1MB, 2)
if ($sizeMB -gt $MaxSizeMB) {
    throw "size exceeded: $sizeMB MB > $MaxSizeMB MB. The goal is 'extremely light'; check dependency growth before raising the limit."
}

The specific choices follow from that. No SQLite, because the server list is dozens of rows and a pure-Go SQLite would add four to six megabytes for nothing; a JSON file with atomic writes and a backup is smaller and easier to repair by hand. No third-party tray library; the notification icon call is written directly. Seven frontend runtime dependencies and no UI framework. Keys, known hosts and the server list all use standard formats, with no bespoke binary containers. The frontend is embedded into the executable, so there is no external asset directory.

The Tauri configuration drives the frontend build, and the build script owns the Go side and the assertions. CI also runs a vulnerability check, because advisories in the crypto package need continuous discovery rather than after-the-fact checks.

Cost. JSON storage rewrites the whole file on save, which is linear in the number of servers and fine for dozens, but there is no SQL for complex queries later. Handwritten Win32 and a hand-rolled DOM helper add maintenance. The size guard itself is brittle: a Go, Wails or frontend dependency bump can move the number, so the threshold needs re-checking after upgrades. The assertion runs after the build, so a failing artifact is kept for analysis while CI fails. And a 32-bit Go toolchain produces 386 by default, so the script must pin the architecture, or you get a binary that runs on the wrong target.

Problem 9: high-DPI flicker and zero-sized terminals

Symptom. Dragging the window between a 100% and a 150% display makes WebView2 repaint repeatedly and flicker. Switching from the terminal view to files and back leaves the xterm cursor misaligned against the old column count, and sometimes the terminal collapses into a thin line.

Cause. Two problems overlap. First, WebView2 receives dense resize events on high DPI or multi-monitor switches, and reflowing on each one flickers. Second, in-session view switching uses display none, so the hidden terminal host measures zero and the resize observer reports a zero-sized box. Calling fit at that moment computes a tiny grid, and switching back leaves it wrong.

Fix. The window layer debounces WebView2 repaints at 120 ms. The frontend debounces resize another 150 ms, skips observations below four pixels in either dimension, and refits plus syncs size inside an animation frame. Returning to the terminal view also goes through an animation frame, so layout finishes first. Switching from the keys page back to servers refits every visible terminal.

const ro = new ResizeObserver(() => {
  for (const [id, handle] of terminals) {
    const host = hosts.get(id);
    if (!host || panes.get(id)?.hidden) continue;
    if (host.clientWidth < 4 || host.clientHeight < 4) continue;
    handle.fit();
    handle.syncSize();
  }
});

WebGL is downgraded at the same layer. The WebGL addon is constructed inside a try block, and initialization failure keeps xterm's DOM renderer; context loss disposes the addon and falls back the same way. Nothing breaks functionally, long output just costs more CPU.

The window declares per-monitor DPI awareness in its manifest, otherwise WebView2 is bitmap-stretched across displays and text blurs. Light and dark follow the system, and Mica enables only on recent builds, with older systems staying opaque so a transparent window never lacks a background.

Cost. The two debounces stack, so the remote PTY receives the final size a moment after dragging ends, which is perceptible but not painful. Skipping tiny sizes avoids the zero-sized case but also means a very small layout change doesn't recompute. The WebGL downgrade is silent, so users only notice that scrolling got slower, a trade made to keep the main flow undisturbed.

Problem 10: SFTP and forwarding share a connection, not a lifetime

Symptom. Initially every file panel opened a new SSH connection and every forwarding rule dialled its own, so opening files added a handshake and another login entry on the server. Worse, closing a session tab left the local listening port occupied, because the forward was never released with the session.

Cause. SFTP and port forwarding are just extra channels on the same SSH connection. SFTP is a subsystem channel and local forwarding is one direct-tcpip channel per forwarded connection. Neither needs a new dial, handshake or authentication. What needs designing is the lifetime: channels belong to the session and have to be torn down with it, along with listeners and rules.

Fix. SFTP is created lazily and cached. The first open starts the subsystem on the existing connection, and later calls reuse the same client; a test asserts that two opens produce one SSH connection and one SFTP channel.

Forwarding keeps a rule table per session. Adding a rule validates the port and host, then listens on loopback. Each incoming local connection opens a direct-tcpip channel through SSH, shuttles both directions through 32 KiB buffers, and counts active connections, total connections and bytes in each direction. Closing the session closes listeners, cuts live connections and pushes a removed state.

func (f *Forward) handle(local net.Conn) {
    remote, err := f.ssh.Dial("tcp", f.remoteAddr)
    if err != nil {
        local.Close()
        return
    }
    // register the pair and splice both directions; either side closing ends both
}

Several smaller details matter. Rename prefers the POSIX rename and falls back to the standard one. A symlink triggers an extra stat only when the entry is a link and not a directory, avoiding a round trip per entry in large directories. Delete removes only empty directories, never recursively, because a wrong path in a recursive delete is irreversible. Forwarding binds loopback only, so exposing a service to the local network is an explicit decision, and a port conflict is an error rather than a half-written rule.

Transfer progress is rate-limited to 120 ms, so every 32 KiB doesn't flood the webview with events. Cancellation travels through a context, the copy loop checks it before each block, and the terminal state is cancelled rather than done. Forwarding statistics share the same interval and only push when a value changes, so idle rules emit nothing.

Cost. All channels share one TCP connection, so terminal, SFTP and forwarding contend for the same bandwidth and connection-level resources; a single large transfer can slow terminal echo. Remote forwarding and dynamic forwarding aren't implemented, only local. A download opens the remote file once to learn its size and reopens it for the transfer, which costs a round trip but avoids holding two handles for a long time. Recursive upload and recursive delete are explicitly unsupported.

Problem 11: passwords, stale passwords and credential self-healing

Symptom. After changing the remote password, every connection attempt fails and there is no way to enter a new one. In the other direction, a password mistyped once in the dialog gets saved, and later attempts keep failing.

Cause. If "the user typed a password" and "save the password" are the same call, a failed authentication still persists it. If a stale saved password is never removed, the frontend sees that a password exists, never prompts, and the user is stuck in a corner where clicking connect always fails. Deleting a server while leaving its credential behind also orphans a password pointing at a host that no longer exists.

Fix. Save only after successful authentication. If authentication fails and no password was supplied this time, delete the saved one so the next attempt prompts. Deleting a server deletes its credential. The password-exists check answers only whether one is stored, never returns the secret itself, and drives whether the frontend connects directly or prompts first. Clearing a password is idempotent, so repeating it isn't an error.

The frontend asks whether a password exists before connecting, and only prompts when it doesn't, so normal use isn't interrupted every time. Key passphrases work the same way: on failure with a stored passphrase, delete it, then prompt again with a retry marker, up to three times.

if srv.Auth == sshcore.AuthPassword && req.Password != "" {
    if serr := a.secrets.Set(store.PasswordTarget(srv.ID), req.Password); serr != nil {
        wruntime.LogWarning(a.ctx, "failed to save server password: "+serr.Error())
    }
}

Credentials live in Windows Credential Manager as generic credentials scoped to the local machine, with targets such as a server password or a key passphrase. There is no bespoke encrypted file, because that is the classic roll-your-own-crypto trap. The credential manager uses the platform data protection API bound to the current user, and it doesn't travel with the data directory.

Cost. Self-healing depends on matching the library's authentication error text, which is a string comparison against a message that could change. Detecting a typed authentication error would be sturdier, but the simpler path was chosen. Credentials bound to the Windows account can't be decrypted on another machine, which is correct behaviour, so copying the server list and keys to a new machine means re-entering passwords.

Passwords are still plaintext in process memory. There is no master password and no memory encryption, which is the usual boundary for a desktop SSH client. Credentials are also not invisible to other programs running as the same user: anything running as that user can enumerate the targets and read them. That's a property of the Windows credential model rather than something NanoSSH can fix on its own. What it does guarantee is that secrets are never in a plaintext JSON file and never travel with the data directory.

Problem 12: three edges of key management

Symptom. Importing a FIDO security key reports that the private key could not be parsed, which looks like file corruption. Generating an RSA key defaults to 2048 bits, which the baseline rejects. Deleting a key that a server still references can quietly change that server's authentication and break the next connection.

Cause. A FIDO key's private handle never leaves the hardware, and Go's SSH library doesn't support it, so the user has to be told the algorithm is unsupported rather than that the file is broken. RSA 2048 is no longer enough, and 4096-bit generation takes seconds, which is too slow for an interactive flow. Deleting a referenced key creates a dangling reference, and silently rewriting server configuration is harder to diagnose than an error.

Fix. Only three algorithms are supported: ed25519, RSA 3072 and ECDSA P256, generated in the native OpenSSH format, with public lines that paste straight into an authorized-keys file and fingerprints that match the standard tool. FIDO detection has to inspect the decoded payload, because OpenSSH private keys store the algorithm name as a plain string inside the binary body; searching the visible text for the FIDO prefix finds nothing.

if block, _ := pem.Decode(pemBytes); block != nil {
    if bytes.Contains(block.Bytes, []byte("sk-ssh-ed25519")) ||
        bytes.Contains(block.Bytes, []byte("sk-ecdsa-sha2")) {
        return nil, ErrKeyFIDOUnsupported
    }
}

Key files are named by a generated identifier rather than by whatever the user typed. That rules out collisions and path traversal, and lets a key be renamed freely. Import parses before writing, so success proves the key is usable and yields the exact public key and fingerprint; failure leaves no half-record with an empty fingerprint.

Three failure paths are distinguished on purpose: a needed passphrase returns a specific error, a hardware key returns its own error, and everything else means the file itself is wrong. Without a name, import uses the source filename without its extension. A passphrase-protected import stores the passphrase, so the first connection doesn't ask again.

Deleting a key scans the server list first and refuses while the key is referenced, naming the servers in the error. The order is record first and file second, so there is never a record pointing at a file that no longer exists.

Cost. FIDO keys and agent forwarding are unsupported, and both say so in the error text rather than failing silently. RSA 3072 generation is slower than 2048 but far better than 4096, which is the middle ground taken. Mode 0600 on Windows is again only an intention; real protection comes from the application data directory's ACL. There is no key rotation and no multi-key binding, because the surface is deliberately narrow.

Closing

The value of NanoSSH isn't how many features it has. It's that a few boundaries that are easy to get wrong are pinned down.

IPC chose the Wails base64 event bridge, accepted the size inflation, and offset it with worker decoding and buffer transfer. Terminal bytes stay byte slices end to end with no line splitting or decoding, using 16 KiB chunks, 8 ms batching and an ack loop to keep latency at the renderer. PTY parameters are uniformly rows then columns, with a test preventing the RFC and library orders from swapping again. Host keys distinguish unknown, changed and revoked, and a changed key allows only explicit replacement. The Windows details land in the named pipe, the locked tray thread, resize debouncing and the 14 MB build assertion.

Every decision has a cost. Throughput is bound to rendering, hashed known-hosts entries can't be replaced automatically, JSON can't be queried, handwritten Win32 costs maintenance, and stale-password healing depends on error text. None of that is hidden; it lives in comments, tests and error messages.

Testing is part of the architecture rather than something added afterwards. An in-process test server provides a real SSH server. An event collector replaces the event outlet and acks immediately on receipt. The credential backend is swapped for an in-memory implementation, so tests never write to the real credential store. Conclusions such as "terminal bytes are never lost", "PTY order is correct", "forwarding reuses one connection" and "closing a session releases the port" can all be verified repeatably without a window. What transfers to similar tools isn't a particular function but the order of work: write the boundaries down first, then choose the implementation.
