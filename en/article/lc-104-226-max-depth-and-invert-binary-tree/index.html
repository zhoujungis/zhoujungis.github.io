LC 104 and 226: max depth and invert, each hiding one nail

2026-09-24 · 17 min · Stack Frame

The two problems

They belong together because they are the two modes of tree recursion, and their edge cases illuminate each other.

LC 104: given a binary tree, return its maximum depth, meaning the number of nodes on the longest path from the root to a leaf.

        3
       / \
      9   20
         /  \
        15   7

input: [3,9,20,null,null,15,7]
output: 3

LC 226: invert the tree and return its root.

      4                        4
     / \                      / \
    2   7        ->            7   2
   / \ / \                  / \ / \
  1  3 6  9                9  6 3  1

class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

The array encoding is the usual level-order one, where nulls hold their places.

Why they belong together

LC 104LC 226
Work done in the callAsk both subtrees for a height, then compute itselfSwap its two children
Can the order changeNo, post-orderYes, either works
WhyIts own height depends on what the subtrees returnEach node acts independently
Return valueA numberNot needed, the structure changes in place

In one sentence: depth propagates information upward, inversion walks downward making local edits. The first order is forced, since without the subtrees there is nothing to compute from. The second is free, and that freedom is exactly where the only trap lives.

LC 104: the one that cannot be dropped

class Solution:
    def maxDepth(self, root: TreeNode) -> int:
        if not root:
            return 0
        return 1 + max(self.maxDepth(root.left), self.maxDepth(root.right))

Three lines, and the interesting part is the literal one.

       3          maxDepth(9)  = 1
      / \         maxDepth(20) = 2
     9   20       max(1, 2)    = 2
        /  \      1 + 2        = 3
       15   7

The inner call gives the height of the subtrees, which is how far down one can go starting from a child. The problem asks from the current node, so the difference is the node itself.

Dropping the one makes everything return zero, which is easy to spot. The subtler family of bug is a return value whose meaning is off by one layer, and the diameter problem is that bug in its evolved form, where the difference between counting edges and counting nodes is one.

Why post-order is required

Because the heights come up from below, and a parent has nothing until it asks.

A top-down version also works:

def maxDepth(self, root):
    self.ans = 0
    def dfs(node, depth):
        if not node: return
        depth += 1
        self.ans = max(self.ans, depth)
        dfs(node.left, depth)
        dfs(node.right, depth)
    dfs(root, 0)
    return self.ans

It passes, and it walks a longer road, and it never materialises a subtree height. That matters later, since the balanced-tree problem needs to compare the two subtree heights at each node.

So whenever a parent's answer depends on its subtrees, post-order is essentially the only choice. Whenever the answer accumulates a parameter on the way down, pre-order is more natural. That distinction separates the two big families better than any template.

A BFS alternative

from collections import deque

class Solution:
    def maxDepth(self, root: TreeNode) -> int:
        if not root:
            return 0
        q = deque([root])
        depth = 0
        while q:
            depth += 1
            for _ in range(len(q)):
                node = q.popleft()
                if node.left:  q.append(node.left)
                if node.right: q.append(node.right)
        return depth

Choose this when the tree is deep enough that recursion overflows. Python's default limit is a thousand frames, and a skewed tree of thirty thousand nodes will fail; the queue version will not.

The trade is space: breadth-first holds the widest level, up to half the nodes, while depth-first holds the height, logarithmic for a balanced tree. Each wins somewhere.

Note the snapshot again, from the level-order problem. Without capturing the length, the inner loop drains and refills in the same pass and the levels merge.

The variants of 104

Minimum depth: the trap

This is the most valuable section in the article. Having solved maximum depth, people substitute min.

# wrong
def minDepth(self, root):
    if not root: return 0
    return 1 + min(self.minDepth(root.left), self.minDepth(root.right))

It passes most cases and fails on any tree with only one child.

    1
   /
  2

The leaf two reports one, the missing child reports zero, and the minimum of one and zero plus one is one. The correct answer is two, because the path runs through both nodes.

The error is that an empty subtree is not a leaf. The question asks for the shortest path to a nearest leaf, and null is the absence of a path, not a path of length zero. Taking it into the minimum fabricates a shorter route.

Maximum depth is immune for a trivial reason: the larger of one and zero is one, so the zero is discarded. The same convention, harmless under max, is fatal under min.

class Solution:
    def minDepth(self, root: TreeNode) -> int:
        if not root:
            return 0
        if not root.left:
            return 1 + self.minDepth(root.right)
        if not root.right:
            return 1 + self.minDepth(root.left)
        return 1 + min(self.minDepth(root.left), self.minDepth(root.right))

If only one of the two is asked in an interview, it is more likely the minimum, because the maximum is hard to get wrong.

Balanced tree: the return value doubles as a status

class Solution:
    def isBalanced(self, root: TreeNode) -> bool:
        def height(node: TreeNode) -> int:
            if not node:
                return 0
            lh = height(node.left)
            if lh == -1:
                return -1
            rh = height(node.right)
            if rh == -1:
                return -1
            if abs(lh - rh) > 1:
                return -1
            return 1 + max(lh, rh)

        return height(root) != -1

The design is worth studying: the return value is nominally a non-negative height, and negative one is borrowed to mean "already violated". One value carries both a number and a state, and returning early prunes the rest of the tree.

This is the same family of trick as a return value with three identities in the lowest common ancestor problem, and one that only reports a single arm in the maximum path sum problem. In tree recursion, the difficulty is almost always in what the return value means.

Diameter

Covered with the path sum problem: the same two-arm skeleton, counting edges instead of summing values, and no clamping needed because a depth cannot be negative.

LC 226: inverting the tree

The famous anecdote first. In June 2015 Max Howell, the author of Homebrew, interviewed at Google for an iOS role and later tweeted that Google told him ninety percent of their engineers use his software but he could not invert a binary tree on a whiteboard.

The tweet went viral. Google engineers asked publicly whether that question had actually been asked, others pointed out that inverting a tree is elementary, and Howell later noted the feedback had included several other weaknesses and the tweet was simplified for effect.

The anecdote is worth including because it captures the awkwardness precisely: five lines, no algorithmic insight, two minutes of work for anyone comfortable with recursion. And yet it does filter, for comfort with recursion is exactly what it measures.

class Solution:
    def invertTree(self, root: TreeNode) -> TreeNode:
        if not root:
            return None
        root.left, root.right = root.right, root.left
        self.invertTree(root.left)
        self.invertTree(root.right)
        return root

The whole problem in one sentence: visit every node and swap its two children once.

The order is genuinely free, except in one place

Pre-order, swapping before recursing, and post-order, recursing before swapping, both work, because the operation on each node depends on nothing from its subtrees and changes no membership.

But this is wrong:

self.invertTree(root.left)
root.left, root.right = root.right, root.left
self.invertTree(root.right)

Walk through what happens. The first call inverts the original left subtree. The swap then moves that inverted subtree to the right. So the third call operates on the already-inverted subtree and inverts it back, while the true right subtree is never touched.

The root cause is that the swap changes what the two name references point at, and the subsequent recursive call reads those same references.

The rule: the swap goes either before both recursive calls or after them, never between.

An elegant equivalent: flip every path

Inversion also equals flipping each node's path from the root, left for right.

node   path    flipped
 2      [L]  ->  [R]
 7      [R]  ->  [L]
 1     [L,L] -> [R,R]
 3     [L,R] -> [R,L]
 6     [R,L] -> [L,R]
 9     [R,R] -> [L,L]

The original animation is built exactly this way: it stores each node's left-or-right role relative to its parent, and computes position by walking up the parent chain and converting the path to a column. A swap is then a single value change, and the node jumps to its mirrored position.

A corollary: inversion is its own inverse, so applying it twice restores the tree, because flipping a path twice returns the original.

Variants of 226

Symmetric tree (LC 101)

A tree is symmetric exactly when it equals its own inversion, so the test is a mirrored recursion walking two subtrees in opposite directions.

class Solution:
    def isSymmetric(self, root: TreeNode) -> bool:
        def mirror(a: TreeNode, b: TreeNode) -> bool:
            if not a and not b:
                return True
            if not a or not b:
                return False
            if a.val != b.val:
                return False
            return mirror(a.left, b.right) and mirror(a.right, b.left)

        return mirror(root, root) if root else True

The cross pairing is the whole point: comparing like with like instead tests whether two trees are identical, which is a different problem.

Flip equivalent trees (LC 951)

class Solution:
    def flipEquiv(self, root1: TreeNode, root2: TreeNode) -> bool:
        if not root1 and not root2:
            return True
        if not root1 or not root2:
            return False
        if root1.val != root2.val:
            return False
        return (self.flipEquiv(root1.left,  root2.left)  and self.flipEquiv(root1.right, root2.right)) or \
               (self.flipEquiv(root1.left,  root2.right) and self.flipEquiv(root1.right, root2.left))

The difference from the symmetric version: there, the cross pairing is mandatory; here, each node may or may not be flipped, so both branches are tried.

Java

class Solution {
    public int maxDepth(TreeNode root) {
        if (root == null) return 0;
        return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
    }
}

class Solution {
    public int minDepth(TreeNode root) {
        if (root == null) return 0;
        if (root.left == null)  return 1 + minDepth(root.right);
        if (root.right == null) return 1 + minDepth(root.left);
        return 1 + Math.min(minDepth(root.left), minDepth(root.right));
    }
}

class Solution {
    public TreeNode invertTree(TreeNode root) {
        if (root == null) return null;
        TreeNode tmp = root.left;
        root.left  = root.right;
        root.right = tmp;
        invertTree(root.left);
        invertTree(root.right);
        return root;
    }
}

Java has no tuple unpacking, so the swap needs a temporary; assigning each field to the other without one, which turns both into the same value, is a very common mistake. And the return type is the node, not void.

Neither problem looks at values, which is what makes them simpler than the path sum problem where negatives complicate pruning.

Common mistakes

  1. Dropping the plus one in depth, which returns zero everywhere.
  2. Substituting min in the minimum depth problem, which is wrong on any single-child tree.
  3. Forgetting to prune in the balanced check, which costs comparisons and readability.
  4. Putting the swap between the two recursive calls, which double-inverts one subtree and skips the other.
  5. Forgetting to return the root in the inversion, which yields null.
  6. Writing the symmetric check without cross pairing, which tests equality instead of symmetry.
  7. Stack overflow on a deeply skewed tree; raise the limit, use BFS for depth, or use an explicit stack for inversion.
  8. Confusing node counts with edge counts, which is precisely the off-by-one that the diameter problem exists to catch.

How to answer it

For depth, lead with the conclusion: post-order recursion returning one plus the larger subtree height, where the one accounts for the current node. If asked about other orders, explain the top-down version and why it loses the subtree height that the balanced problem needs. If asked about overflow, explain BFS and the space trade. Then volunteer the minimum depth trap, since that is the part that scores.

For inversion, lead with the one-sentence description, then spend the time on order: either direction works because each node acts independently, but the swap cannot sit between the recursive calls, because the swap changes what those references point at.

Asked why the order is free, say that the swap is a local mutation independent of subtree state, and every node is visited exactly once, so reordering changes only when the swap happens, not whether. Asked what happens if you invert twice, say it restores the tree, since inversion flips every root path and flipping twice is the identity.

And when both are asked together, close with the general rule: whether a parent's answer depends on its subtrees determines whether the order is forced.

Closing

Both are easy problems treated as introductions, and each hides one nail. The first nail grows out of the minimum depth variant, where the sentence "an empty subtree is not a leaf" is what most people never separate out, since the maximum happens to hide the error. The second grows out of where the swap goes, where exactly one of the plausible arrangements is wrong, and it is wrong quietly.

The most valuable judgement in tree recursion is one question: does the parent's answer depend on what the subtrees return? If it does, post-order. If not, the order is free. Decide that and the skeleton follows in two minutes; only the edges remain.
