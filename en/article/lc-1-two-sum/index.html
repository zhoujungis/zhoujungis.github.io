LC 1, two sum: look before you store

2026-09-24 · 18 min · Stack Frame

The problem

Given an array of integers and a target, return the indices of the two numbers that add up to it. Each input has exactly one answer, and the same element may not be used twice.

nums = [2, 7, 11, 15], target = 9   -> [0, 1]
nums = [3, 2, 4],       target = 6   -> [1, 2]
nums = [3, 3],          target = 6   -> [0, 1]

It is most people's first LeetCode problem, short and obvious on the samples, which is why most people write two loops, pass, and move on. Three things worth learning are hidden in it.

IdeaThe sentence in the statement that carries it
Replacing nested loops with a lookup is the entire point of a hash tableThe answer is indices, not values
The order of two statements cannot be reversedThe same element may not appear twice in the answer
Uniqueness is not decorationEach input has exactly one answer

What the question is really testing

for i in range(n):
    for j in range(i + 1, n):
        if nums[i] + nums[j] == target:
            return [i, j]

Quadratic, which at ten thousand elements is a hundred million operations. The plus one in the inner range is where "the same element cannot be reused" lives: the inner loop only looks forward.

Now turn the question around. Instead of asking whether two indices sum to the target, ask whether the number I need, target minus this value, has already gone past me. That converts a pair enumeration into a membership test, and membership is constant time with a hash table.

i = 0:  x = 2, need 9 - 2 = 7. What is on my left? Nothing. Record 2.
i = 1:  x = 7, need 9 - 7 = 2. On my left? Yes, at index 0. Return [0, 1].

The table maps value to index, not value to count, because the answer is indices: a set can say whether a value exists and cannot say where.

class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}
        for i, x in enumerate(nums):
            need = target - x
            if need in seen:
                return [seen[need], i]
            seen[x] = i
        return []

Six lines, each with a reason. The table starts empty, so at the first index nothing can be found, which matters. The needed value is computed without worrying about which index is smaller, because the table only ever holds earlier elements. The lookup happens first and returns immediately on a hit, and since the stored index is necessarily to the left, the pair comes out ascending. The current element is recorded last.

Frames one and two are deliberately separate, because lookup and storage are separate actions: the table is empty when the lookup runs, and the value is added afterwards. If the order were reversed, frame one would already contain the pair and the lookup would find it, and in this particular input it would find nothing anyway. That is precisely what makes the bug so quiet.

There is no fourth iteration, because index two is never visited: uniqueness means the answer can be returned the moment it is found.

The one real difficulty: order

for i, x in enumerate(nums):
    seen[x] = i                    # wrong: stored first
    need = target - x
    if need in seen:
        return [seen[need], i]

When the target is exactly twice the current value, the number needed is the value itself, and storing first puts it in the table, so the lookup finds the current index and returns the same index twice.

The failure is not a wrong sum, it is an illegal answer, and it triggers on a precise condition: the current value is half the target.

The first official sample is the only one that cannot trigger it, which is exactly why a test run convinces people they are right. The lesson: verify with an input you construct, one where the target is twice a value.

Why looking first satisfies the uniqueness rule for free

In the brute force version, uniqueness comes from starting the inner loop at the next index. In the hash version it falls out of the order of the statements: at the moment of the lookup the table contains only the elements before the current one, so any hit is at an index below the current one and can never be the element itself.

So the order does two jobs at once. It makes the lookup constant time, which is the hash table's contribution. And it makes the uniqueness constraint hold without an explicit check, which is the order's contribution. Reversing the order loses the second, and then the code needs an explicit comparison against the current index, as the two-pass version must do.

The two-pass alternative

class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}
        for i, x in enumerate(nums):
            seen[x] = i
        for i, x in enumerate(nums):
            need = target - x
            if need in seen and seen[need] != i:
                return [i, seen[need]]
        return []

It is correct, at three costs. It scans twice, doubling the constant. It must exclude the current index by hand. And the table keeps the last index for a repeated value, which is harmless for a single answer but loses solutions when every pair is wanted.

The one-pass version is better on all three counts: one scan, the constraint satisfied automatically, and duplicates harmless because the hit happens before anything overwrites the entry.

Variant one: a sorted array, two pointers, no table

class Solution:
    def twoSum(self, numbers: List[int], target: int) -> List[int]:
        left, right = 0, len(numbers) - 1
        while left < right:
            s = numbers[left] + numbers[right]
            if s == target:
                return [left + 1, right + 1]
            if s < target:
                left += 1
            else:
                right -= 1
        return []

Sorting makes the sum monotonic in both pointers: moving the left one right increases it, moving the right one left decreases it. That means each move can be decided from the current sum, with no wasted step, and the space drops from linear to constant.

This table is itself an interview question. The array being sorted is extra information, and extra information buys a cheaper method.

It is the same idea as the sliding window in LC 3: use monotonicity so a pointer only ever moves one way. In LC 3 the left edge never moves back because the characters before it have already been excluded; here the pointers move toward each other because the sum changes monotonically.

One rule generates the chain: each additional fixed value adds a dimension, and the remaining pair is always finished with a linear pass.

def threeSum(nums):
    nums.sort()
    res = []
    for i in range(len(nums) - 2):
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        left, right = i + 1, len(nums) - 1
        while left < right:
            s = nums[i] + nums[left] + nums[right]
            if s == 0:
                res.append([nums[i], nums[left], nums[right]])
                while left < right and nums[left] == nums[left + 1]:
                    left += 1
                while left < right and nums[right] == nums[right - 1]:
                    right -= 1
                left += 1
                right -= 1
            elif s < 0:
                left += 1
            else:
                right -= 1
    return res

Sorting does two jobs there: it makes the two-pointer scan possible, and it puts equal values next to each other so duplicates can be skipped. That is why three sum sorts instead of hashing, and why the choice of technique differs across the family: unsorted with one answer favours a table, sorted allows constant space, and deduplication forces sorting because a hash table cannot see that two index combinations produce the same values.

Java

class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            if (seen.containsKey(need)) {
                return new int[] { seen.get(need), i };
            }
            seen.put(nums[i], i);
        }
        return new int[] {};
    }
}

Three notes. The map must be value to index, not a set, because the answer is indices. Use the contains check rather than comparing the retrieved value against null, which is clearer and avoids a zero value being mistaken for absence. And return an empty array rather than null, so callers do not have to check.

Edge cases and traps

InputOutputNote
[2,7,11,15], 9[0,1]The sample that cannot expose the ordering bug
[3,2,4], 6[1,2]Three is half the target, so it exposes it
[3,3], 6[0,1]Two equal values
[0,0], 0[0,1]Zero is not a false value; do not test truthiness
[-1,-2,-3,-4,-5], -8[2,4]Negatives are ordinary
[0,4,3,0], 0[0,3]Two zeroes at opposite ends
[1,3,4,2], 6[2,3]The answer is at the end
  1. Storing before looking. Triggered exactly when the target is twice a value, and hidden by the first sample.
  2. Using a set instead of a map, which cannot return an index.
  3. Testing the retrieved value for truthiness, which fails when the needed value is zero and stored at index zero.
  4. Returning the pair in the wrong order. The stored index is always smaller, so the ascending order matters even where the judge does not care.
  5. Forgetting uniqueness. It allows an early return; a version that wants every pair must not return early and must store a list of indices per value.
  6. Overflow in languages with fixed-width integers, where the target minus a value can underflow; the constraints here are safe.

How to answer it

Lead with the conclusion and the complexity: one pass with a hash table mapping value to index, compute the complement at each step, return on a hit, store otherwise, linear time and linear space.

Then explain why it is linear: brute force enumerates pairs, and the table turns pair enumeration into a membership test, which is constant time.

Then the important sentence: lookup happens before storage, so the table only ever holds elements to the left, so any hit is at a smaller index and can never be the current element, which means the uniqueness rule holds without an extra check.

Then give the counterexample proactively: reversing the order lets a value that is half the target match itself, and the first official sample happens not to contain such a value, so that sample cannot catch the error.

If asked about a sorted array, describe the two-pointer scan and the constant space. If asked whether three sum can use a table, explain that deduplication is the obstacle and sorting solves both the scan and the duplicates. If asked for all pairs, describe dropping the early return and storing a list of indices.

Closing

Two lessons. Replacing enumeration with lookup is what a hash table is for. And order matters: ask what you are missing before you record yourself.

The second is easy to miss because the first sample hides it: nine is not twice any value in that array, so the bug cannot fire. The wrong version passes, and the code ships.

assert twoSum([3, 3], 6) == [0, 1]      # and not [0, 0]

Passing a counterexample you built yourself is what counts as correct.
