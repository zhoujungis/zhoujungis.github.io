Agent evaluation: a single passing run is a sample, not a result

2026-11-11 · 36 min · Stack Frame

Who this is for: people who treat "the demo worked once" as a conclusion; people whose CI is green and who keep getting hit by the first prompt a user types; people about to add evaluation to an agent and unsure where to start.

TL;DR: one passing run is a sample, not a result. An agent's output is a joint distribution over model, tools and environment, and a single run samples one point. Evaluation needs a denominator, a definition of success, and assertions about the process. NanoHermes has ninety unit tests and five end-to-end cases, and its mock reads each request and throws it away. Make the tool list return an empty array and all five end-to-end cases still pass.

Green CI, broken on the first prompt

Ninety-five Rust tests pass, the badge is bright, and the release notes mention tool call round trips, streaming and non-streaming replies, transient 5xx retries and hard errors. A user installs it, tells it to read a file, which works. Tells it to make a change, which lands in the wrong place. Tells it to try again, and it starts repeating the first request. Three turns later the task is unfinished and the bill has arrived.

The tests are not useless. They answer a different question from the user's. A test asks whether this path can crash. The user asks what the probability is that this thing finishes a job on their inputs. The distance between those two questions is what evaluation fills.

One passing run is a sample

An agent run is one sample from a joint distribution. Temperature, tool returns, file state, network timing, traversal order, any of them changes the path. A single run tells you that one path works, not that this class of task gets done.

A pass rate without a denominator is not a pass rate. Ten of ten and seven of ten are completely different systems, and "I ran it and it passed" flattens both into one conclusion.

Tests that only look at the final answer cannot see how agents typically fail: one extra tool call, a skipped confirmation, the whole history resent, a failed turn missing from the ledger. All of that happens during the run, and the run is in the request bodies.

Tests, evaluation and benchmarks are not the same thing

FormQuestionSamplesDefinitionRepetitionOutput
Unit testIs this function right at the edgesHand-written inputsAssert equalityOnceA green check
Integration testDo these modules connectFixed scriptAssert side effectsOnceA green check
EvaluationWhat is the chance this task class succeedsA batch of real tasksPass rate plus process metricsN timesScores with intervals
BenchmarkWhich version is betterFixed problem setRelative differenceMany timesRanking and deltas
Online observationWhat do real users hitAll trafficDistributions and quantilesContinuousDashboards and alerts

The column that matters most is repetition, and only evaluation and benchmarks have it, because only they care about a distribution rather than about this run. The second most important column is the definition: unit tests inherit it from the compiler, while an evaluation has to decide what counts as success, whether partial counts, whether a timeout counts, whether going over budget counts. Undefined, the score means nothing.

What a single run hides

HiddenMechanismConsequenceOnly repetition catches it
Passes by luckThe model happened to take the right pathThe failure rate appears in productionYes
Fails by luckEnvironment jitter, port conflicts, timingEngineers learn to just re-runYes
Never runs at allConditional skips, tautologies, a mock that is too idealGreen and covering nothingNo, that needs auditing

The third is the most dangerous because it does not even give you occasional failures. It is always green. The second trains a bad habit: see red, re-run, take the majority of three. That is manual retrying, and it erases the signal, since flakiness is information.

Compound success: 0.95 across twenty steps leaves 0.36

Steps0.99 each0.980.950.90
100.9040.8170.5990.349
200.8180.6680.3580.122
300.7400.5450.2150.042
400.6690.4460.1290.015

Taking a single step from 0.90 to 0.95 moves a twenty step task from 12% to 36%, a threefold improvement. Moving 0.95 to 0.98 takes it from 36% to 67%. A few points per step is a multiple at the task level.

It also explains why one success proves almost nothing: on a system with 0.95 per step, a twenty step success happens 36% of the time anyway. What you observed may simply be that 36%.

So the first act of evaluation is not adding samples, it is counting the steps in the task. Step count decides the per-step reliability you need and where to spend repetitions.

A pass rate needs a denominator

pass_rate   = passing runs / total runs
tasks       = 12 real tasks
runs each   = 5
total runs  = 60
criteria    = file contents match + exit code 0 + turns <= 8

What is the numerator, what is the denominator, what is the criterion, how many runs. Any of those missing and the number can be explained to any conclusion.

Three common denials of the denominator. "I ran three cases and they all passed," which has a denominator of three, no statistical meaning and total validity as a smoke test. "Our eval score is 87," where neither part is clear: 87 could be a weighted hundred cases or ten subjective ones. And "it went from 80% to 85% after the change," where if each was ten runs, five points is entirely inside the noise.

What ten clean runs actually prove

Runs, all passing95% lower boundIn words
1072.2%The true rate might be seventy percent
2083.9%Still possibly under ninety
5092.9%Starting to look like "above ninety"
10096.3%Can say "very likely above ninety-five"

Those come from a Wilson interval with z of 1.96, where the all-pass lower bound reduces to 1/(1 + z squared over n). The useful mnemonic: the term in the denominator is the penalty for not having enough samples.

So "ten runs, all passed" concludes that the failure rate is probably under 26%, not that the thing is stable. That distinction matters for a decision, because a 26% failure rate means one user in four hits it.

Zero failures only bound the rate from above

Zero-failure runsUpper boundWhat you may conclude
1026%Only that it does not always fail
309.5%Acceptable for an internal tool
604.9%Acceptable to open to a small group
3001.0%Enough to talk about stability

The rule of three: no failures in n runs gives a 95% upper bound near 3/n. Going the other way, to estimate a 95% rate within five points you need about 73 runs. Both numbers answer a practical question: does your evaluation budget support the sentence you want to write? With ten runs, do not put "95% pass rate" in the weekly report.

pass@1 and pass@k are different numbers

MetricDefinitionDenominatorQuestion
pass@1Success on a single runRunsWhat the first attempt looks like
pass@kAt least one success in k runsTasksWhat k attempts allow
flaky rateTasks that both pass and fail on one versionRepeated tasksWhether the system is stable
completion rateRuns explicitly marked completeRunsWhether it finished the job
mean turnsModel requests per taskRunsEfficiency and cost

For an agent the most useful number is often not pass@1 but the gap between pass@1 and completion rate, because agents have a characteristic failure: they answered without finishing. The run function returns success even at the iteration cap, so from the return value alone you cannot tell "done" from "ran out of turns".

And pass@k is not a product metric. A task that succeeds once in five attempts is still unusable to a user, because users do not run it five times. pass@k answers whether the model has the capability; it does not answer whether the product can ship.

Flakiness can only be found by repetition

Flaky means the same code, the same task, different results across runs. That definition alone rules out finding it in a single run.

for each case, run N = 5 times
  5/5 passing   -> stable pass
  0/5 passing   -> stable fail, a real bug
  1..4/5        -> flaky, the class most worth fixing

The third class is the most valuable data in an evaluation. It is neither broken nor working, it depends on luck, and luck is random locally and load-dependent in production, so it flares up exactly when things are busy.

Execution is the stage people thin out. Storing one final string loses request bodies, tool call sequences, per-call usage, retry counts and timings, and attribution has nothing to work with.

Define success first

Four questions. Is the result right, in file contents, exit codes or key conclusions. Is the process right, no forbidden tool, no skipped confirmation, calls inside budget. Did it finish, normally rather than at the cap or interrupted. And what did it cost in turns, bytes and wall clock.

The third is the easiest to miss, because most APIs return a single result type and "did not finish" produces neither an error nor a distinctive string. It slips quietly inside success.

Four layers of assertion

LayerAssertsExampleCatchesStability
L1, bytesThe request body itselfRequest count, system prefix hash, tool listContext bloat, prefix drift, missing toolsHighest
L2, processThe tool call sequenceRead before write, no extra retriesWrong order, duplicate work, skipped confirmationHigh
L3, resultSide effects and answerFile contents, exit code, key sentenceWrong, missing, off-targetMedium
L4, costResource useTurns, total bytes, elapsedEfficiency regressionHigh

Why four layers rather than just L3? Because L3 failures are hard to attribute. A wrong file could mean the model chose the wrong tool, the tool has a bug, the previous read was wrong, or compaction dropped the key detail. L1 and L2 narrow it to one layer immediately.

A checkup on NanoHermes

The mock uses only the standard library, binds port zero so the kernel assigns one, names scratch directories with pid, nanoseconds and an atomic counter, and splits tool arguments across two SSE frames to exercise incremental assembly. All of that is well done.

And then one line: the full request is read into a byte vector and dropped.

Test inventory: 293 cases

LayerCountWhereAsserts
Rust unit90Module test blocksFunction-level input and output
Rust end-to-end5The e2e test fileFinal answer, files, usage
Frontend198Component testsBehaviour and rendering

The distribution is uneven. The twenty-three tools each have two to eight unit tests, and the module that routes a model-supplied name to an implementation has none. Two more behaviours have no tests: compaction, and message replacement for the daemon. Both sit on the main run path.

293 cases is not a small number. The problem is that almost all of them sit at the function layer, below L3, while agent failures mostly happen at L1 and L2.

How the end-to-end mock is built

Five cases: a tool call round trip, plain text streaming, non-streaming JSON, a transient 500 with retry, and hard error propagation. All share one structure: given a fixed list of responses, assert the final answer.

The assertions are better than average. The tool call case verifies that the SSE fragments assemble into valid arguments, that the tool really wrote to disk, and that usage accumulated across two requests. That is far more than asserting a non-empty string.

And every case stops there. Not one line checks whether the first request actually advertised the write tool.

Four things it gets right

PracticeWhy it mattersCost
Standard library onlyNo dependency can turn the suite red by upgradingHand-written HTTP parsing

Scratch dirs with pid, nanos, counterParallel tests do not overwrite each otherNone
Inject a silent UI sinkTest output contains only assertion failuresNeeds an injectable UI layer

The fourth is the one to copy. Routing all streaming text and banners to an empty sink leaves only failures in the output. Plenty of projects have unreadable test output because the code under test prints hundreds of lines.

One more silent virtue: the mock speaks HTTP, not an SDK, so it validates the protocol layer and still works against a different compatible provider.

Gap one: the request is read and dropped

read_full_request(&mut stream);   // the returned bytes are discarded
let _ = stream.write_all(responses[served].as_bytes());

So none of the five cases can detect a corrupted request body. Make the tool builder always return an empty array, telling the model it has no tools, and what happens?

  • The tools field disappears from the request, so the model could call nothing in production.
  • The mock does not look at requests; it reads its script and answers "call the write tool".
  • Execution routes by name and never checks whether the tool was advertised.
  • So the file is still written, usage still says two requests, and all five cases stay green.

Blank the system prompt, set the token limit to one, remove the usage frame option: the same. The assertions land on the answer and on usage, and usage comes from the mock's response, not from the request.

This is the canonical shape of a single-run test. It did run. It ran a path that passes without the code under test being correct.

Gap two: the test config disables production paths

The test config sets auto-approve to avoid interactive hangs, disables memory to stay out of the real user directory, and disables project docs to avoid reading the repository's own conventions. Each line has a reason, and together they mean the end-to-end suite does not run the production configuration.

In production the first message is the base prompt plus persona plus project guidance plus a memory block. In the tests it is the base prompt alone. So prefix drift caused by rewriting the memory block every turn, a real problem documented at length in the ledger post, cannot be observed here at all.

Not a wrong test, a test of a different system. Evaluation exists to catch exactly this divergence: what you test has to be what you ship.

Gap three: approval and sandbox are short-circuited

Auto-approve skips the entire approval path, and the sandbox is off by default, so commands in the suite run unconstrained. The approval policy has its own unit test, which proves the decision function is correct and proves nothing about whether the decision is wired into execution. That is L3 versus L2, and the missing middle is where agents break: the policy is right and one branch never calls it.

What evaluation should add is not ten more policy assertions but one process assertion: under the untrusted policy, a command request must stop and wait, rather than execute. That needs the mock to see how many requests arrived and whether the second one contains a tool result, which is L1.

Gap four: Ok does not mean done

All three exits, normal completion, interruption and hitting the iteration cap, return success. The only difference is a warning printed to the UI.

So the end-to-end line that expects a turn to complete asserts only that no error was returned, not that the task finished. If the model is still calling tools at the fortieth round, the test takes the last text, possibly half an answer, and goes green.

Gap five: conditional skips posing as passes

#[test]
fn landlock_enforces_workspace_boundaries() {
    if !is_supported() {
        eprintln!("skipping: Landlock unavailable in this environment");
        return;
    }
    // ...
}

Support is always false off Linux, and CI runs on Windows, so this test skips forever, never fails, and never verifies anything. A second one skips when git is missing, which on GitHub's Windows image usually is not, so it mostly runs and would silently become a false pass if the environment changed.

There is a subtler variant: whole tests excluded by a Unix-only compilation attribute. The four hook behaviour tests carry that attribute, and CI only runs Windows, so "the hook sees the tool name", "the exit code propagates" and "writing before reading stdin does not deadlock" have never executed in CI. Not skipped, never compiled.

The fix is not deleting them, it is making skips visible: mark them ignored with a reason, or add a Linux job that runs platform-specific cases. A skip has to be a different colour from green.

Gap six: assertions the name promises and the code skips

One test is named for surfacing a hard API error without hanging, and nothing asserts anything about time. If the code did hang, the job would time out, which is a different signal from this test failing. Honour the name with an elapsed-time assertion.

The other asserts that a transient error recovers, and never asserts that exactly two requests were made. Add a third attempt and the mock, having run out of scripted responses, closes the connection, so the test does fail, but by accident. Prepare three responses for another case and the bug hides.

Names are for the next reader. A name that promises more than the assertions is worse than no name, because it makes people believe coverage exists.

Gap seven: no cases for compaction or batching

Compaction runs at the end of every turn and does something dangerous: it removes messages, inserts one, and changes order. Remove the wrong slice and history is left with tool calls and no results, which the provider rejects outright. It has no test.

The same goes for the batching of parallel tool calls. A model returning twelve calls gets chunks of eight and four, and ordering has to survive. The existing concurrency test calls execution directly with thirty calls and never exercises the chunking.

And the streaming assembler caps tool call indices at 64 to stop a malicious endpoint from forcing a huge allocation. Nothing sends a frame with a huge index to prove it is dropped.

How an always-true assertion gets written

assert!(
    start.elapsed() < Duration::from_secs(2),
    "polling a running task must not block: {out}"
);
assert!(out.contains("no output yet") || !out.is_empty());

The first is meaningful. The second is always true, since the output contains at least a status header, so the alternation can never fail. It was probably meant to check that a freshly started task has no output yet, and writing it as an or-branch swallowed that meaning.

Such assertions do not hide bugs, they inflate the sense of coverage. Two lines look like two checks and only one works. A self-check while writing: make the function always return an empty string; does the assertion go red? If not, it is decoration.

Fix one: turn the mock into a recorder

use std::sync::{Arc, Mutex};

struct MockLlm {
    port: u16,
    seen: Arc<Mutex<Vec<Vec<u8>>>,
    handle: Option<thread::JoinHandle<()>>,
}

Store each raw request under the mutex, and expose a method that splits the head from the body and parses the body as JSON. Split on the first blank line rather than the last, because a body can contain that sequence too.

After that, every assertion rests on the real request instead of on the belief that the request was correct.

Fix two: three golden request assertions

Request count. A two step task uses exactly two requests. This catches turn inflation, and the failure message can dump the bodies.

Tool sequence. The advertised tool names must be identical across turns, and sorted. That second half catches "added a tool and forgot to sort", which silently destroys prefix caching, the cost lever from the ledger post.

Prefix hash. Hash the first message and the tool list, and assert the value is stable across turns. Together these are under forty lines, they live entirely in test code, and they cover the two most expensive regressions: cost drift and capability disappearing.

Fix three: replace the fixed script with a state machine

A fixed queue deals responses in order regardless of what was asked, which makes the test a one-act play and rules out repetition and retries.

fn respond(req: &Value) -> String {
    let messages = req["messages"].as_array().cloned().unwrap_or_default();
    let has_tool_result = messages.iter().any(|m| m["role"] == "tool");
    let user_text = messages.iter().rev()
        .find(|m| m["role"] == "user")
        .and_then(|m| m["content"].as_str())
        .unwrap_or("");

    if user_text.contains("write") && !has_tool_result {
        sse_tool_call("write_file", r#"{"path":"hello.txt","content":"hi"}"#)
    } else if user_text.contains("write") {
        sse_text("done")
    } else {
        sse_text("ok")
    }
}

Now the state is whether a tool result exists and the transition depends on the request. Three benefits: no need to precompute how many responses, faults can be injected at any step, and assertions can target "what the third request looks like" instead of "which scripted response was consumed".

Two rows deserve detail because the behaviour is discoverable in code and invisible in tests. Retryability is decided by matching five HTTP status strings, and a timeout is formatted as a generic request failure with no status, so a timeout never retries even when retries are configured. A unit test then froze that behaviour, asserting that a DNS failure is not retryable. Correct in context, and it quietly makes "no transport error ever retries" part of the contract. A green light becomes a lock.

For a cut stream, the reader only errors when no frames arrived at all. One frame followed by a dropped connection returns success with half the tool arguments, which downstream becomes an invalid argument error and one wasted round.

Fix five: give completion a type

#[derive(Debug, PartialEq, Eq)]
pub enum TurnOutcome {
    Completed(String),
    Interrupted(String),
    IterationLimit(String),
}

Keep the string-returning run as a thin wrapper so existing callers do not change, and let the evaluation assert on the enum: the outcome must be completed. That single assertion is worth more than every result-layer assertion combined, because it separates "answered" from "finished", and on agents those are frequently different.

Fix six: grow the eval set from incidents

Every case then has a story. When it goes red, nobody has to guess what it was testing, because the title names the incident.

Five fields per case

FieldPurposeCost of omission
idStable identifier for cross-version comparisonReports cannot be aligned

The oracle field most often forgotten is the list of files that must not change. Asserting the right edit happened is not enough; an agent's characteristic damage is editing too much. Turn limits and completion belong in the oracle too, which is where cost and correctness meet.

Grading is not boolean

GradeCriterionExampleHandling
passResult and process both fineRight file, turns in budget, completedShip
degradedRight result, cost over budgetCorrect, but eighteen turns or two files touchedRecord and watch the trend
failWrong result or unfinishedWrong file, hit the cap, errorBlock

The middle grade is the point. Pure boolean grading makes "correct but three times the cost" look identical to "correct", so cost regressions are never noticed, and agent cost regressions are gradual: five percent per feature, never a cliff.

How to repeat: counts, seeds, parallelism

ScenarioRuns per casePurposeTrigger
Local smoke1Fast feedbackOn save
PR gate3Catch obvious instabilityEvery commit
Nightly10Estimate the flaky rateDaily
Version comparison30Compare two buildsBefore release

Thirty runs sounds like a lot until you remember the mock is local HTTP: no model spend, only execution time. Only a mock makes thirty repetitions economically possible.

Two parallel concerns: every run needs its own scratch directory, and any configuration read from the environment must be injected explicitly at the harness boundary rather than inherited from the process.

Six ways to isolate flakiness

SourceSymptomIsolation
Port conflictOccasional connection failureBind port zero

Clock and timezoneDate assertions driftingInject a fixed clock
Traversal orderFile listings in different orderSort explicitly before asserting

Network and proxiesTraffic going through a corporate proxyExplicit no-proxy, loopback only

The suite already handles the first two, and the sixth matters because the HTTP layer reads proxy environment variables and bypasses loopback, without which every local mock test would try to go through the proxy.

Retries find problems, they do not hide them

Automatic retry on failure is harmful in evaluation. It turns one failure in five into zero in five, so the flakiness disappears from the report and the problem does not. Flakiness is the most valuable signal there, because it marks the paths that depend on luck, and luck varies with load.

Invert it: let tests run once and let evaluation run N times, and report the difference. A run of five that shows four empty lines and one failure is far more informative than a retry that eventually passed, because it says this case has a twenty percent failure rate and that case covers the tool call round trip.

Retries belong on infrastructure failures, pulling images and installing dependencies. The boundary goes into CI configuration, not into somebody's memory.

Cost is an evaluation metric

MetricDefinitionSourceExample threshold
TurnsModel requests per taskUsage or the mock8 or fewer
Request bytesTotal body bytes per taskMock records180,000 or less

These belong in the same table as the pass rate, or you will ship a version that kept the pass rate and doubled the cost, or one that saved money and edited the wrong file. Cost also degrades earlier: a pass rate is a step function, cost is continuous, so a five percent regression is visible long before a threshold is crossed.

Attribution: five failure classes and two bisections

ClassSignalHandling
ModelSame input varies across runs with no environment differenceChange model, prompt or temperature
PromptWrong tool, wrong format, ignored constraintEdit the prompt, add examples
ToolError text comes from the tool, wrong file stateFix the tool, add unit tests
OrchestrationTurn count explodes, repeated actions, information lost after compactionChange the loop or the compaction policy
EnvironmentFails on one machine or platformFix isolation, add platform cases

Bisect to get there faster. Record the model responses and replay them: still failing means the model is not the cause; passing means it was sampling. Then pin tool returns to fixtures: still failing means orchestration, passing means the tool.

Two bisections narrow five classes to one, which is faster than staring at logs, and it is the second use of recorded requests beyond assertion.

Offline evaluation and online observation

Offline prevents regressions, online discovers new problems. The healthy loop is: online finds a problem, it becomes an offline case, it gets fixed, and the offline gate prevents the return.

Sample structure online, never content

struct TurnTelemetry {
    turn_id: String,
    outcome: TurnOutcomeKind,   // completed / interrupted / iteration_limit
    requests: u32,
    prompt_bytes: u64,
    completion_bytes: u64,
    tool_calls: Vec<ToolStat>,  // name + duration + ok, no arguments
    elapsed_ms: u64,
    error_class: Option<String>,// a class, not the original text
}

No user text, no file contents, no command output. Enough to answer success rate, turn distribution, which tool is slowest and which error class dominates. A case that needs content goes through explicit user reporting or an opt-in debug mode. Structure by default, content by consent.

Regression gates: CI, nightly, human

LayerRunsDuration targetGate rule
CIUnit tests, three end-to-end runs, L1 assertionsUnder ten minutesAny new failure blocks
NightlyTen repetitions, fault matrix, cost baselineUnder an hourFlaky above 2% or cost up 10% alerts
HumanReal model against real repositoriesOn demandVersion comparison report

CI has to be fast and deterministic, so no real model: latency and cost rule it out per commit. Nightly can be heavier because it produces trends rather than blocks. And the human layer checks the definitions: if a person sees an obvious regression while the score is flat, the oracle is wrong.

A directory layout to copy

evals/
  cases/
    edit-wrong-file-001/
      case.json
      fixture/
  harness/
    mock_llm.rs        # state machine mock that records requests
    runner.rs          # repetition, isolation, accounting
    grade.rs           # pass / degraded / fail
  baselines/
    2026-11-01.json    # pass rate, turns, bytes
  report.md

cargo test --workspace
cargo run --bin eval -- --cases evals/cases --repeat 10 --json > report.json
jq '.cases[] | select(.flaky) | .id' report.json

The middle line is the core: a separate binary rather than a test framework plugin, so it works in CI, runs one case alone, and feeds a report. Separate entry points also matter because an evaluation failure need not block compilation while a test failure must, and different semantics should not share an exit code.

Three experiments you can finish in a day

The first decides whether repetition is feasible. The second is the executable version of this post's argument: change one line of production code and see whether the light stays green. The third reveals a boundary you can then either fix or document, as long as you know it exists.

Five common evaluation traps

TrapSymptomConsequenceFix
Mock too idealAlways valid JSON, always instantAll real-world bad data is missedA fault matrix
Overfitted assertionsAsserting exact prose or a full diffOne punctuation change turns it redAssert key fragments and structure
Only single stepsEvery tool passes its unit testThe combination does not workScenario cases
Averages hiding the tailMean two turns, p95 eighteenA few tasks blow the budgetReport quantiles
Distribution mismatchSelf-invented tasksScores rise, users notice nothingGrow cases from incidents

The second is the sneakiest. Asserting exact prose looks strict and writes implementation details into the contract, so every prompt change requires a test change, and eventually the team learns to edit the assertion when it goes red. Assert structure instead: the right file changed, the tool sequence is correct, turns are in budget, the answer contains the key conclusion. Those survive rephrasing and still fail when behaviour changes.

Closing

A single pass is a sample. A twenty step task at 0.95 per step is 36% at the task level, and ten clean runs only prove the failure rate is under 26%.

Evaluation needs a denominator, a definition and process assertions. A pass rate without a denominator is not a pass rate, a score without a definition cannot be compared, and tests without process assertions cannot see how agents actually fail.

NanoHermes writes good tests that stop at the result layer. Ninety unit tests and five end-to-end cases, and the mock reads each request and throws it away. Make the tool list empty and all five stay green. That is not a bug, it is an assertion layer that is not deep enough.

And closing the gap is cheap: record the bodies, add three golden assertions, turn the mock into a state machine, write a fault matrix, add an outcome type. A few days of work. The expensive part is not writing it, it is deciding what success means.
