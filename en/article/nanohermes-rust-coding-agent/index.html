Preface: why write the Nth coding agent

Coding agents are not scarce in 2026. Claude Code, Codex, Trae and Cursor each own a niche, and open-source clones appear weekly. What they share: they are heavy. A Node or Python runtime, hundreds of transitive dependencies, a tokio or asyncio event loop, installers hundreds of MB wide, idle processes hundreds of MB resident.

NanoHermes asks a much smaller engineering question: if all I need is a terminal agent that reads files, edits code, runs commands and speaks MCP, how small can it be?

The answer is a set of trade-offs: a single binary (target around 2 MB), resident memory that scales with context length, three dependency crates, no async runtime, not even libc — and it can run as a resident HTTP service on a 1 GB Debian VPS.

This post does not sell concepts; it takes implementations apart. The density is in a few places: how an agent loop is organized without async, which primitive concurrency uses, how Landlock and SIGINT handling work without libc, how long-term memory does Chinese retrieval without any embedding service, and how every layer of context gets a ceiling. Each of those has details you cannot guess from the outside.

NanoHermes in a minute

One sentence: an OpenAI-compatible terminal coding agent written in Rust, plus a Tauri desktop shell, plus a deployable HTTP daemon. Written once, shipped in three shapes:

ShapeArtefactUse
CLI / REPLagent (crate name; release binary target/release/agent)One-shot tasks, interactive REPL, stdin pipe, --json / --stream-json
DesktopNanoHermes (Tauri v2, gui/ + ui/)Four-column GUI, each task with its own session, permissions, model and persona
HTTP serviceagent --daemonResident service on a VPS, consumed as "cloud tasks" from the desktop

Capabilities, ordered by how quickly you notice them: real tools (read, write, edit, patch, list, grep, glob, shell, fetch web, search web, todos, git, background tasks); planning and memory (todo_write / todo_read keep a plan across turns, long-term memory distils lessons, preferences, corrections and facts into local files and re-injects them by relevance); extensibility (MCP servers over stdio and streamable HTTP, skills at .nanohermes/skills/<name>/SKILL.md, subagents, lifecycle hooks that can veto a tool call); security (three approval tiers plus a Linux Landlock filesystem sandbox); and a desktop shell with a virtualized transcript, incremental Markdown, a docked results panel, a command palette and three themes.

One easily missed fact: the desktop front end is React 19 + TypeScript + Vite, while the Rust side is a 72 KB single file, gui/src/main.rs — no plugins, no glue framework, no state-machine generator. Tauri commands are ordinary functions with an attribute macro.

The three disciplines

One: no async runtime. HTTP uses blocking ureq; concurrent tool calls use std::thread::scope; each MCP server gets a dedicated reader thread. No tokio means no per-task state machines, no thread pools, no runtime memory overhead.

Two: minimalism approaching fanaticism. The agent crate depends on serde_json, ureq (with TLS) and base64. Not even serde's derive macro — everything is serde_json::Value. Not even libc — Landlock and SIGINT handling detour through a hand-written raw syscall module.

Three: every output has a ceiling. Tool results clamp to 20 KB; command output 256 KB per stream; file reads over 4 MB are refused; web responses clip at 2 MB; grep returns 200 matches; glob 500 files; project guidance and skill bodies 20 KB each. Context and process memory are both held by these numbers.

Together they define the project's character: push complexity into the layer that must be written and is worth writing, and cut everything else.

Core 1: the agent loop without an async runtime

Agent::run in agent/src/agent.rs is a bit over a hundred lines and takes one user turn from start to finish:

pub fn run(&mut self, content: Value) -> Result<String, String> {
    // A Ctrl-C during this turn sets a flag instead of killing the process.
    let _guard = InterruptGuard::new();
    // Cross-session memory: retrieve for this instruction, replace the injected block.
    let user_text = memory::content_text(&content);
    if let Some(dir) = self.ctx.memory_dir.clone() {
        let block = memory::retrieve_block(&dir, &user_text);
        self.set_memory_block(&block);
    }
    self.messages.push(json!({ "role": "user", "content": content }));

    for _ in 0..self.cfg.max_iterations {
        // Abort only at a step boundary so the history never keeps an
        // assistant tool-call without its matching tool result.
        if crate::interrupt::take() { interrupted = true; break; }
        let turn = self.complete()?;
        // ... accumulate token usage, push the assistant message
        if turn.tool_calls.is_empty() { completed = true; break; }
        // ... run tools concurrently, backfill tool messages in call order
        self.compact();
    }
    // Only fully completed turns distil memories
    if completed && self.cfg.memory { self.distill_memories(&user_text, had_tools); }
    self.persist();
    Ok(final_text)
}

Four things deserve comment.

Interruption happens at step boundaries, not anywhere. crate::interrupt::take() at the top of the loop is the only break point, and the comment says why: interrupting after a tool call is issued but before its result is written leaves an assistant tool-call with no matching result, which the API rejects on the next request. The cost is up to one step of extra latency.

Long-term memory is re-retrieved and wholesale-replaced each turn. set_memory_block replaces the old block by its markers rather than appending, so a hundred turns still inject one block. This is the classic trap of injected memory.

Token usage reports the delta, not the running total. A daemon serving many sessions would make a cumulative total meaningless to the client; deltas let the client compute a per-task total, and locally deltas sum to the total anyway.

Memory distillation has a hard gate. It only runs when completed is true — not interrupted, not iteration-capped — and failing to distil degrades silently. Half a conversation never becomes a "lesson".

One model round trip is encapsulated in complete(), landing in llm::chat: it builds the request body, attaches tools and tool_choice as needed, sets reasoning_effort: "high" when thinking is enabled, adds stream_options.include_usage so token counts arrive in the stream, then enters the retry loop. Backoff is base * 2^(attempt-1) capped at 30 seconds; retryable means HTTP 429, 500, 502, 503 or 504; after the attempts are exhausted, a configured --fallback-model gets one final call. Defaults: --max-retries 2, --retry-base-ms 500.

Core 2: concurrent tool calls via scoped threads

When a turn returns several tool_calls, they run concurrently — with std::thread::scope, not tokio:

let results: Vec<String> = if turn.tool_calls.len() == 1 {
    vec![self.execute(&turn.tool_calls[0])]
} else {
    // Reborrow as `&Agent` so the scoped threads can share it
    // (`execute` takes `&self`, and `Agent` is `Sync`).
    let this: &Agent = self;
    std::thread::scope(|s| {
        let handles: Vec<_> = turn.tool_calls.iter()
            .map(|call| s.spawn(move || this.execute(call)))
            .collect();
        handles.into_iter()
            .map(|h| h.join().unwrap_or_else(|_| "ERROR: tool thread panicked".to_string()))
            .collect()
    })
};

Four details: a single call takes the direct path and pays no thread cost; results are collected in tool_calls order, so completion order cannot mismatch tool_call_id; Agent must be Sync, achieved by putting each MCP server's Child and reader JoinHandle inside a Mutex<Server>; and a panicking tool thread returns a string that looks like a tool error, so the model simply sees a failed call and continues.

MCP concurrency has a finer grain: calls to the same server serialize on its stdin lock (the protocol is request-response over one connection), while different servers run in parallel.

Core 3: not even libc — a 30-line raw syscall shim

sandbox.rs and interrupt.rs both need syscalls the standard library does not expose: the Landlock family and rt_sigaction. The usual answer is a libc dependency; here it is agent/src/sys.rs:

#[cfg(target_arch = "x86_64")]
pub mod nr {
    pub const CLOSE: usize = 3;
    pub const RT_SIGACTION: usize = 13;
    pub const OPENAT: usize = 257;
    pub const PRCTL: usize = 157;
}

Two architectures get their own tables (x86_64 versus aarch64: openat is 257 versus 56, prctl 157 versus 167), plus a syscall() taking up to six arguments — asm! with the syscall instruction on x86_64, svc 0 on aarch64, with different register assignments.

The module is under 75 lines, gated on #![cfg(all(target_os = "linux", any(target_arch = "x86_64", target_arch = "aarch64")))], and vanishes on other platforms. This is the most expensive consequence of dependency minimalism: portability and some audit surface traded for thirty lines of assembly. It is also reasonable — both features only mean anything on Linux.

Nineteen built-in tools in four groups, up to 28 with conditional ones (the four mcp_* tools appear only with a server configured):

Dispatch is a plain match; every error becomes a string tool result — no panic, no broken loop. The last line is the point:

r.map(|s| clamp(s, ctx.max_output))

Every tool result clamps to max_output (20 KB). That line is where the bounded-output discipline lives: whichever tool, whatever arguments, no single tool result ever exceeds 20 KB in context.

Each tool also has a second ceiling, deliberately chosen:

Core 5: compaction — old conversation becomes a summary

Context management lives in compact_with, set by two constants:

const CONTEXT_CHAR_BUDGET: usize = 120_000;
const KEEP_RECENT: usize = 10;

Past 120,000 characters (or more than keep-count + 1 messages), compaction begins: starting ten messages back, find a safe start point, drain the older span for a model summary, then insert that summary as a system message at index 1. Three details avoid the usual accidents: the start point is pushed forward if it lands on a role == "tool" message, so a summary never orphans a tool result; a failed summary degrades to [Earlier conversation was omitted to keep the context small] rather than erroring or losing data; and /compact forces one regardless of size.

KEEP_RECENT = 10 is empirical: ten messages cover "the file being edited plus the last tool result", and older context decays quickly in value.

Core 6: long-term memory — local BM25 with CJK bigrams

Memory lives in agent/src/memory.rs and persists to ~/.nanohermes/memory.json. The practical question it answers: how do you search Chinese without any embedding service? Two stages: tokenize, then BM25.

tokenize() handles mixed Chinese and English: runs of ASCII alphanumerics become lowercase words, and anything shorter than two characters is dropped as noise; runs of CJK are split into bigrams (windows(2)), with isolated characters kept alone — so 上下文压缩 becomes 上下 / 下文 / 文压 / 压缩; and the CJK ranges cover Han, kana, hangul and compatibility blocks, not just the unified ideographs.

Scoring is standard BM25 with k1 = 1.2 and b = 0.75:

let idf = (1.0 + (n - n_q + 0.5) / (n_q + 0.5)).ln();
score += idf * (f * (k1 + 1.0))
       / (f + k1 * (1.0 - b + b * len / avg_len.max(1.0)));

Two details beyond the textbook: category words participate in matching — each memory has a kind (lesson, preference, correction, fact) whose labels are added to the document bag, so "what did I correct earlier" hits correction entries; and zero-score entries are filtered before ranking so irrelevant memories cannot crowd the top-k.

With a small number of entries it scores linearly, no inverted index — one Vec plus one HashMap. Retrieval is recomputed every turn and injected by the same marker mechanism as the memory block. On the write side, memory_save skips identical text (dedupe), and automatic distillation only runs on completed turns, so small talk and half conversations never pollute the store.

Core 7: an MCP client with two transports

Both transports are implemented. stdio uses LSP-style framing — Content-Length: N\r\n\r\n followed by the JSON body, byte for byte. Streamable HTTP is a synchronous POST with Accept: application/json, text/event-stream; the server's Mcp-Session-Id is remembered and echoed on later requests. Responses may be JSON or SSE (event: message plus data: {...}) and both are parsed.

The handshake is the standard three steps: initialize (protocolVersion: "2024-11-05") → notifications/initialized → tools/list. Declared tools are converted to OpenAI function-calling format and merged into the agent's table, then dispatched by name — an MCP tool is indistinguishable from a built-in one to the model.

Four auxiliary tools expose resources and prompts: mcp_list_resources, mcp_read_resource, mcp_list_prompts, mcp_get_prompt. Configuration is one JSON file where command means stdio and url means HTTP, both inside the same servers object.

Core 8: skills and progressive disclosure

Skills are reusable instruction packs: one directory per skill with a SKILL.md and optional YAML frontmatter declaring name and description. Discovery is workspace-first: <workspace>/.nanohermes/skills/, then ~/.nanohermes/skills/, with workspace entries overriding global ones of the same name.

The key property is that the body never enters context: startup parses only the frontmatter, and the system prompt lists only each skill's name and description. The model calls the skill tool to pull a body (capped at 20 KB) when it needs one. That is progressive disclosure — the library can be large while the base prompt stays small. Missing frontmatter falls back to the directory name and the first body line.

Core 9: the subagent board and the concurrency gate

Subagents come from a JSON file passed with --subagents; each can carry its own prompt, model and allowed_tools allowlist, exposing subagent (delegate) and agent_list (inspect the board).

agent/src/board.rs holds two mechanisms. The board records each delegated task: an incrementing id (agent-N), name, description, status (running, done, failed), duration and a result preview of 500 characters. The preview clipper respects UTF-8 boundaries (while end > 0 && !flat.is_char_boundary(end)) so a multi-byte character is never split into a panic; the full result still returns as the tool result, the board keeps only a summary for readable agent_list output.

The gate is a textbook counting semaphore over Mutex + Condvar: acquire() waits when full, the returned GateGuard decrements and notify_ones on Drop. The cap is MAX_PARALLEL_SUBAGENTS = 4, because the loop spawns one thread per tool call and a turn can emit several delegations at once — without the gate you would fire a dozen concurrent LLM requests.

Core 10: lifecycle hooks that can veto a tool call

Hooks are PreToolUse and PostToolUse shell commands from the config, with a matcher of * or a comma-separated tool list. They run via sh -c in the workspace root, receiving the tool call as JSON on stdin, plus NANOHERMES_TOOL_NAME and NANOHERMES_HOOK_EVENT so scripts need not parse JSON.

Two implementation details worth copying: both pipes get their own draining thread (reading only one deadlocks once the other fills its 64 KB buffer, and chatty hooks are normal), and hooks must be fast or they fail — HOOK_TIMEOUT_SECS = 30, after which the process is killed and -2 returned (-1 means killed by a signal).

The semantics differ by event: a non-zero PreToolUse blocks the call and returns the hook output to the model, while a non-zero PostToolUse can only append a warning to a result that already happened. The asymmetry is deliberate — block before, not after.

Core 11: security — Landlock and three approval tiers

Two independent switches: one governs whether to ask, the other what is possible.

PolicyBehavior
neverNever ask (default; -y as well)
on-requestAsk only for commands that are not recognized read-only
untrustedAsk for everything, read-only included

Read-only detection (is_trusted_command) is stricter than expected. The first gate is metacharacters: any |, &, ;, <, >, backtick, $, parenthesis or newline makes the command untrusted regardless of the program. Past that gate comes allowlist matching: skip leading KEY=VALUE assignments, strip path prefixes, then check TRUSTED_BINARIES (ls, cat, grep, rg, stat, jq, tree and similar). git gets its own git_subcommand_is_read_only() that skips -C, -c, --git-dir, --work-tree and --namespace — options that consume the next token as a value — before checking the subcommand.

Sandboxing uses Linux Landlock to restrict the spawned command's filesystem view:

ModeBehavior
offUnrestricted (default)
read-onlyRead and execute, no writes at all
workspace-writeRead and execute, writes only inside the workspace

The most interesting part is that it refuses to degrade: Landlock is installed in Command::pre_exec, between fork and exec, so the restriction covers every child the command spawns. If the kernel does not expose Landlock (or an outer sandbox blocks it), NanoHermes refuses to run the command rather than quietly running unsandboxed — a security mechanism that always falls back gracefully is no mechanism at all. And all of it still goes through the raw syscall shim, with no external crate.

Core 12: Ctrl-C does not kill, and /undo rewinds

In interactive use Ctrl-C is redefined: it does not kill the process, it flips a flag so the current turn exits cleanly at the next step boundary with the conversation intact.

agent/src/interrupt.rs has one neat piece of timing: the handler is installed only while a turn runs.

static INTERRUPTED: AtomicBool = AtomicBool::new(false);
/// Nesting depth of active turns; the handler is installed at 0 -> 1 and
/// removed at 1 -> 0.
static DEPTH: AtomicUsize = AtomicUsize::new(0);

Reference counting keeps nested turns (a subagent inside a tool call) sharing one handler, and the outermost exit restores SIG_DFL — so Ctrl-C while idle still quits, and only while busy does it mean "stop this turn". One signal, two meanings, decided by install/uninstall timing rather than flag inspection.

One more engineering detail: on x86_64 the kernel refuses to deliver a caught signal unless the caller supplies a restorer that executes rt_sigreturn (syscall 15). That is the only hand-written assembly in the project beyond the syscall instruction itself: a tiny global_asm! stub with mov rax, 15 and syscall.

The desktop has no SIGINT to send, so a request() flips the same flag: the GUI's stop button and the terminal's Ctrl-C take one path, and the loop never needs to know who asked.

Paired with it is /undo [n], which removes the last n complete user turns (that message and everything after) from history and persists. Interrupt preserves, undo erases — both are needed, because "it went sideways, let me correct it" and "it went sideways, pretend it never happened" are different real needs.

The GUI performance notes are four hard-won conclusions: no blocking Tauri commands (synchronous #[tauri::command] runs on the window's main thread and freezes the whole UI; everything touching the filesystem, processes or HTTP is async fn on tauri::async_runtime::spawn_blocking, with only get_settings and stop_task staying synchronous, plus a static mutex serializing settings writes); streaming text stays out of the global store (a dedicated subscription feeds only the bubble being written, committed to the transcript per stage, batched on the nanohermes://delta|tool|note|usage channels at 40 ms); the transcript is virtualized (only visible messages mount, height measurement is skipped while the last bubble grows, and follow-scroll is driven by the stream rather than React); and Markdown is incremental (split on blank lines outside code fences, stable blocks render once, an unterminated fence only updates its code text node, and highlighting runs per block after the turn rather than once over the whole answer).

The GUI's IPC surface is 16 commands plus two stream readers, all inside a 72 KB file.

Daemon mode and VPS deployment

agent --daemon turns the agent into a resident HTTP service with two endpoints: POST / (Bearer auth when a token is set) taking {"prompt": "..."} and returning {"response": "...", "session": "<id>"}, and GET /health returning {"status":"ok","sessions":N} for liveness probes.

Sessions are isolated by a header: X-Session-Id selects a session, different ids never share context, and omitting it uses default. Each session persists to its own JSON file. The desktop connects "cloud tasks" this way, each with its own id, so one daemon serves many desktop tasks without cross-talk. The cost: cloud configuration comes from daemon startup flags (model, persona, temperature, permission mode), and cloud turns cannot be canceled midway.

scripts/deploy-debian.sh does the whole job: install the binary to /opt/nanohermes/nanohermes with a workspace and 700 session directory; generate a token with openssl rand -hex 24 into .daemon_token (reused on re-runs); write a systemd unit running --daemon --daemon-port 8787 -C <workspace> --session <dir>/default.json --sandbox workspace-write with Restart=always; harden with NoNewPrivileges and ProtectSystem=strict plus ReadWritePaths; enable and curl /health, printing the token.

One documented trap: ProtectSystem=strict blocks writes to ~/.nanohermes/memory.json, so long-term memory needs ReadWritePaths=/root/.nanohermes in a drop-in. A 1 GB instance also needs swap first — compilation is the only memory-hungry step. Exposure options: an SSH tunnel (no open port), a Caddy reverse proxy (8443 if 443 is taken, remembering HTTP-01 still needs 80), or a Cloudflare Tunnel. The documentation's warning is worth quoting: never expose 8787 directly — the only credential is the Bearer token and the traffic is plaintext.

Session persistence and multimodal input

A session file is a JSON array of OpenAI-style messages, written atomically: write a .tmp sibling and rename, so a crash mid-write never truncates history. Saves happen after each completed turn and after /clear; a failed read at startup falls back to a fresh conversation with a warning rather than refusing to start.

Multimodal input is available to vision models: -i for one-shot, /image in the REPL, paste or drag on the desktop. Limits: four images per turn, long edge scaled to 1024 px, undecodable images or anything over 12 MB rejected with a reason. Transfer is by data URL, so the model must support vision.

Test matrix

Rust tests are per-module #[cfg(test)] plus a real end-to-end suite, all via cargo test --workspace. agent/tests/e2e_mock_llm.rs starts a standard-library-only local mock OpenAI service and drives the real Agent through tool round trips, streaming and non-streaming replies, a retry after a transient 5xx, and a hard API error; agent/tests/mock_mcp_server.py is a mock stdio server.

Unit coverage reads like a list of places assumed to break: patch application (simple, multi-hunk, insert, missing context), glob matching, MCP resource and prompt listing, MCP tool dispatch, streamable HTTP handshake and calls, MCP concurrency safety, execute() concurrency with built-in and mixed tools, HTML-to-text and search parsing, session task lists, git round trips, token usage parsing and backoff, multimodal assembly, session persistence round trips, AGENTS.md injection, skill discovery, hook execution (exit codes, matcher, stdin payload), the subagent board's ordering and gate, approval decisions and trusted-command detection, Landlock's workspace boundary, SIGINT flag setting and clearing, and long-term memory (CJK bigrams, BM25 ordering, dedupe, distillation gate).

The frontend uses Vitest with jsdom: pure logic (theme resolution and persistence, store migrations, Markdown sanitizing, image attachments, in-session search, diff blocks) plus component tests and an App.e2e.test.tsx that renders the real store and components against a mocked Tauri IPC bridge, verifying transcript virtual scrolling, cross-screen search, diff jump-to-change and input state while running or stopping. One regression test asserts that long-running commands never execute synchronously on the main thread — exactly the performance contract most likely to be broken quietly later.

Known limits and my verdict

  • Sandboxing and SIGINT handling are Linux-only. Both rest on raw syscalls and disappear on Windows and macOS, so the desktop on Windows runs unsandboxed with default Ctrl-C handling.
  • Cloud turns cannot be canceled — the request is held by the daemon and the desktop can only wait; only local tasks stop at step boundaries.
  • The daemon runs as root and the token is the only credential. Anyone with it can read, write and execute in the workspace, which is exactly why the docs insist on not exposing the port.
  • Not having async costs something real. A stuck HTTP request occupies a thread until timeout (120 s default). Fine for CLI and GUI; the assumptions break for a high-concurrency gateway.
  • The Windows installer is unsigned, so the first run trips SmartScreen.

My verdict: what is worth reading here is the discipline, not the feature list. Coding agents converge on similar feature sets; holding four constraints to the end — no async runtime, three crates, no libc, every output bounded — is what produced the raw syscall shim, scoped-thread concurrency, layered clamps and dependency-free Chinese BM25.

What those constraints buy: a single binary targeting about 2 MB, resident memory that tracks context length, doing CLI, desktop app and systemd service on a VPS. When everyone else is adding dependencies, taking them away is also an engineering skill.
