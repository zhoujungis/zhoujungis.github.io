NanoHermes: a coding agent in Rust with no async runtime and three dependencies

2026-10-22 · 38 min · Stack Frame

Coding agents are not scarce in 2026. Claude Code, Codex, Trae and Cursor each own a niche, and open-source clones appear weekly. What they share is weight: a Node or Python runtime, hundreds of transitive dependencies, a tokio or asyncio event loop, installers hundreds of megabytes wide, idle processes hundreds of megabytes resident.

NanoHermes asks a smaller question. If all I need is a terminal agent that reads files, edits code, runs commands and speaks MCP, how small can it be?

The answer is three disciplines. No async runtime. Three dependency crates. And a ceiling on every output.

The result is a single binary targeting about 2 MB, memory that scales with context length rather than with the framework, and the same agent running as a CLI, a desktop app, and a systemd service on a 1 GB VPS.

What it is

An OpenAI-compatible terminal coding agent written in Rust, plus a Tauri desktop shell, plus an HTTP daemon. One codebase, three shapes.

ShapeArtefactUse
CLI and REPLagentOne-shot tasks, interactive REPL, stdin pipe, JSON output
DesktopNanoHermes (Tauri v2)Four-column GUI, each task with its own session, permissions, model and persona
Serviceagent --daemonResident service on a VPS, consumed as cloud tasks

It has real tools, not stubs: read, write, edit, patch, list, grep, glob, shell, fetch web, search web, todos, git and background tasks. It keeps a plan across turns and distils long-term memory into local files. It speaks MCP over two transports, loads skills on demand, delegates to subagents, and runs lifecycle hooks that can veto a tool call. On Linux it also enforces a Landlock filesystem sandbox.

One detail sets the tone. The desktop front end is React and Vite, and the Rust side is a 72 KB single file. No plugins, no glue framework, no state-machine generator. Tauri commands are ordinary functions with an attribute macro.

Three disciplines

No async runtime. HTTP uses a blocking client. Concurrent tool calls use scoped threads. Each MCP server gets a reader thread. No tokio means no per-task state machines, no thread pools, and no runtime memory overhead.

Three crates. The agent depends on serde_json, ureq with TLS, and base64. Not even serde's derive macro. Everything is a JSON value. Not even libc: Landlock and signal handling detour through a hand-written syscall module.

A ceiling on everything. Tool results clamp to 20 KB. Command output caps at 256 KB per stream. Reads over 4 MB are refused. Web responses clip at 2 MB. Grep returns 200 matches, glob 500 files, and prompts and skill bodies 20 KB each.

Together they set the character of the project: push complexity into the layer that must be written and is worth writing, and cut everything else.

Stack and size

The release profile is tuned for size: optimise for size, link-time optimisation, one codegen unit, strip, abort on panic. An empty windowsgui Go binary is 1.2 MB; a Rust binary in this configuration is smaller still.

[dependencies]
serde_json = "1"
ureq = { version = "2", features = ["json", "tls"] }
base64 = "0.22"

That is the complete dependency list of the agent crate. The comment above it in the repository states the goal: no async runtime, one blocking HTTP client instead of a stack of hyper, and JSON without derive macros.

agent/src is about 9,200 lines. The three largest files are the loop, the CLI and the MCP client, which together are more than half the code. The rest is tools.

The loop

One user turn runs through a loop a little over a hundred lines long.

pub fn run(&mut self, content: Value) -> Result<String, String> {
    // A Ctrl-C during this turn sets a flag instead of killing the process.
    let _guard = InterruptGuard::new();
    // Memory is retrieved for this instruction and the injected block is replaced.
    let user_text = memory::content_text(&content);
    if let Some(dir) = self.ctx.memory_dir.clone() {
        let block = memory::retrieve_block(&dir, &user_text);
        self.set_memory_block(&block);
    }
    self.messages.push(json!({ "role": "user", "content": content }));

    for _ in 0..self.cfg.max_iterations {
        // Abort at a step boundary, never mid tool call.
        if crate::interrupt::take() { interrupted = true; break; }
        let turn = self.complete()?;
        if turn.tool_calls.is_empty() { completed = true; break; }
        // Run tools concurrently, then backfill results in call order.
        self.compact();
    }
    if completed && self.cfg.memory { self.distill_memories(&user_text); }
    self.persist();
    Ok(final_text)
}

Four decisions inside that shape are worth calling out.

Interruption happens at step boundaries. Breaking in the middle would leave an assistant tool call with no matching result, and the next request would be rejected by the API. The cost is up to one step of extra latency.

Memory is re-retrieved and replaced, not appended. A hundred turns still inject one block, which avoids the usual failure of injected memory growing without bound.

Token usage reports the delta, not the running total. A daemon serving many sessions would make a total meaningless to the client, and locally deltas sum to the same number.

Distillation has a gate. It only runs on a completed turn, never on an interrupted or iteration-capped one, so half a conversation never becomes a lesson.

One model round trip lives in complete. It builds the request, attaches tools and tool choice as needed, asks for reasoning effort when thinking is on, requests usage in the stream, then retries. Backoff doubles from a 500 ms base with a 30-second cap. Only 429 and 5xx retry. After the attempts are exhausted, a configured fallback model gets one call.

Concurrency without async

When a turn returns several tool calls, they run at once through std::thread::scope.

let results: Vec<String> = if turn.tool_calls.len() == 1 {
    vec![self.execute(&turn.tool_calls[0])]
} else {
    let this: &Agent = self;
    std::thread::scope(|s| {
        let handles: Vec<_> = turn.tool_calls.iter()
            .map(|call| s.spawn(move || this.execute(call)))
            .collect();
        handles.into_iter()
            .map(|h| h.join().unwrap_or_else(|_| "ERROR: tool thread panicked".to_string()))
            .collect()
    })
};

Four details. A single call takes the direct path and pays no thread cost, which matters because most turns call one tool. Results are collected in call order, so completion order cannot mismatch a result to its call id. The agent must be Sync, achieved by putting each MCP server behind a mutex. And a panicking tool thread returns a string that reads like a tool error, so the model sees a failed call and continues.

MCP concurrency has a finer grain. Calls to one server serialise on its stdin lock, because the protocol is request and response over a single connection. Different servers run in parallel.

Thirty lines of assembly instead of libc

Two features need syscalls the standard library does not expose: Landlock and rt_sigaction. The usual answer is the libc crate. Here it is a shim with two syscall tables, one per architecture, and a six-argument dispatch that issues syscall on x86_64 and svc 0 on aarch64.

The module is under 75 lines and compiles away entirely on non-Linux targets. That is the most expensive consequence of dependency minimalism: portability traded for assembly. It is also reasonable, because both features only mean anything on Linux.

Tools and bounded output

Nineteen built-in tools, plus conditional ones for MCP, skills and subagents. Dispatch is a plain match, and every error becomes a string result rather than a panic.

The last line of dispatch is the important one. Every result clamps to 20 KB, whichever tool produced it. That single call site is where the bounded-output discipline is enforced.

Command output is clipped while reading rather than after, so a stray yes cannot eat memory before the cap applies. Patch application matches on content rather than line numbers, so a small drift in the source still applies.

Compaction

History is budgeted by characters. Past 120,000, or past ten messages beyond the keep count, older turns are drained and replaced by a summary inserted near the top of the conversation.

Three details prevent the usual accidents. The cut point never lands inside a tool call, so a summary cannot orphan a tool result. A failed summary degrades to a one-line note instead of losing data. And a command forces compaction on demand.

Keeping ten recent messages is empirical. Ten cover the file being edited and the last tool result, and older context decays quickly in value.

Memory without a vector database

Memory persists to one JSON file. The question it answers: how do you search Chinese with no embedding service? Tokenise, then BM25.

Alphanumeric runs become lowercase words, and runs shorter than two characters are dropped as noise. Runs of CJK characters are split into bigrams, with isolated characters kept whole, so a four-character phrase becomes three overlapping pairs. The query is sliced the same way and every term must match.

Scoring is standard BM25 with the usual parameters. Two details go beyond the textbook: each memory's category label joins the document bag, so a question about corrections hits correction entries; and zero-score entries are filtered before ranking, so irrelevant memories cannot crowd the top results.

Writes are deduplicated on normalized text, and automatic distillation only runs on completed turns. The result is closer to an index than to a brain: no synonyms, no semantic recall, but every entry is visible, editable and deletable, which for a personal assistant matters more than recall.

MCP, skills and subagents

The MCP client implements both transports. Over stdio it uses LSP-style framing with a content-length header and a JSON body. Over streamable HTTP it posts synchronously, keeps the session id the server returns, and parses both JSON and server-sent events.

The handshake is the standard three steps, after which declared tools become OpenAI function definitions. From the model's point of view an MCP tool is indistinguishable from a built-in one.

Skills are directories with a markdown file and optional frontmatter. The system prompt lists only each skill's name and description; the body is read when the model asks for it. The library can be large while the base prompt stays small.

Subagents are declared in a JSON file with their own prompt, model and tool allowlist. A board tracks each delegation with id, status, duration and a preview, and a counting semaphore caps concurrency at four. Without the cap, one turn that emits several delegations would fire a dozen model requests at once.

Hooks

Hooks are shell commands that run before and after tool use, matched by tool name or a wildcard, receiving the call on stdin plus two environment variables.

Two implementation details matter. Both pipes get their own draining thread, because reading only one deadlocks once the other fills its buffer, and chatty hooks are normal. And hooks time out after thirty seconds, because a hook that hangs must not hang the agent.

The semantics are asymmetric on purpose. A non-zero pre-hook blocks the call and returns its output to the model. A non-zero post-hook can only append a warning to something that already happened.

Sandbox and approvals

Two independent switches: whether to ask, and what is possible.

Approval policies are never, on-request and untrusted. On-request asks only for commands that are not recognized read-only, and the read-only test is stricter than it looks. Any pipe, redirect, semicolon, substitution or newline makes a command untrusted regardless of the program, because a shell metacharacter means the command is a program, not a binary. Past that gate, leading environment assignments are skipped, path prefixes are stripped, and the remaining binary is checked against an allowlist.

Sandboxing uses Landlock to restrict the filesystem view of spawned commands: off, read-only, or workspace-write. The most interesting part is that it refuses to degrade. Landlock is installed between fork and exec, so it covers every child, and if the kernel does not expose it the command is refused rather than run unsandboxed. A security mechanism that always falls back gracefully is no mechanism at all.

Ctrl-C and undo

In interactive use, Ctrl-C does not kill the process. It flips a flag, and the current turn exits at the next step boundary with the conversation intact.

The handler is installed only while a turn runs. Reference counting lets nested turns share one handler, and the outermost exit restores the default action, so Ctrl-C while idle still quits. One signal, two meanings, decided by install timing rather than by inspecting a flag.

Paired with it is undo, which removes the last N complete turns from history and persists the result. Interrupt preserves and undo erases, and both are needed, because "let me correct it" and "pretend it never happened" are different intentions.

Desktop and daemon

The desktop shell is four columns: a self-drawn title bar, a collapsible task list, a streaming conversation, and a results panel with a file tree, diffs and read-only previews.

Five permission modes cover the practical range: full agent, accept edits, plan-only, unattended, and debug. Three of them also inject a mode instruction into the prompt, because a model should behave according to how it was launched rather than discover that tools are missing.

Four performance rules came out of real problems. No blocking Tauri commands, because a synchronous command runs on the window thread and freezes the UI. Streaming text stays out of the global store, so a long answer does not re-render the sidebar. The transcript is virtualised. And Markdown is parsed incrementally, splitting on blank lines outside code fences so stable blocks render once.

The daemon exposes two endpoints: post a prompt, and a health check. Sessions are isolated by a header, each persists to its own file, and one daemon can serve many desktop tasks without cross-talk. The cost is that cloud turns cannot be cancelled midway and their configuration comes from startup flags.

The deploy script installs the binary, generates a token, writes a systemd unit with restart-always and basic hardening, then curls the health endpoint. One trap is documented: a strict protected system blocks writes to the memory file, so long-term memory needs an explicit writable path. The warning about exposure is blunt, and correct: never put the port on the internet, because the only credential is a bearer token and the traffic is plaintext.

Tests and limits

Rust tests are per-module unit tests plus a real end-to-end suite driven by a local mock OpenAI server that depends only on the standard library. They cover tool round trips, streaming and non-streaming replies, retry after a transient error, and hard API errors. A mock MCP server covers the other transport.

The unit list reads like a map of where things actually break: patch application, glob matching, MCP dispatch and concurrency, HTML to text, git round trips, backoff arithmetic, multimodal assembly, skill discovery, hook exit codes, the subagent gate, approval decisions, the Landlock boundary, signal flags, and Chinese bigram retrieval.

The limits are stated as plainly. Sandboxing and signal handling are Linux-only, so the Windows desktop runs without either. Cloud turns cannot be cancelled. The daemon runs as root with a token as its only credential. A stuck HTTP request occupies a thread until timeout, which is fine for a CLI and wrong for a high-concurrency gateway. And the installer is unsigned.

Closing

What is worth reading here is the discipline, not the feature list. Coding agents converge on similar features. Holding four constraints to the end, no async runtime, three crates, no libc, and a cap on every output, is what produced the syscall shim, the scoped-thread concurrency, the layered clamps and the dependency-free Chinese search.

What those constraints buy is a single binary targeting about 2 MB, memory that tracks context rather than framework, and one codebase that is a CLI, a desktop app and a systemd service. When everyone else is adding dependencies, taking them away is also an engineering skill.
