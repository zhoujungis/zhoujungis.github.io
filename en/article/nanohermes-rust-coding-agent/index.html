NanoHermes: a coding agent in Rust with no async runtime and three dependencies

2026-10-22 · 38 min · Stack Frame

Coding agents are not scarce in 2026. Claude Code, Codex, Trae and Cursor each own a niche, and open-source clones appear every week. What they share is weight: a Node or Python runtime, hundreds of transitive dependencies, a tokio or asyncio event loop, installers hundreds of megabytes wide, and idle processes that sit on hundreds of megabytes of memory.

NanoHermes asks a much smaller engineering question.

If all I need is a terminal agent that can read files, edit code, run commands and speak MCP, how small can it be?

The answer is a set of trade-offs. One binary, with a design target around 2 MB. Resident memory that depends on context length and nothing else. Three dependency crates. No async runtime. Not even libc. And it still runs as a resident HTTP service on a 1 GB Debian VPS.

This post does not sell concepts. It takes the implementation apart. The technical density is in five places: how an agent loop is organized without async, which primitive concurrency uses, how Landlock and signal handling work without libc, how long-term memory does Chinese retrieval with no embedding service, and how every layer of context gets a ceiling. Each of those has details you cannot guess from outside.

What it is in one minute

An OpenAI-compatible terminal coding agent in Rust, a Tauri desktop shell, and a deployable HTTP daemon. One codebase, three distribution shapes.

ShapeArtefactUse
CLI and REPLagent (release binary at target/release/agent)One-shot tasks, interactive REPL, stdin pipe, --json and --stream-json
DesktopNanoHermes (Tauri v2, gui/ and ui/)Four-column GUI, each task with its own session, permissions, model and persona
HTTP serviceagent --daemonResident service on a VPS, consumed from the desktop as cloud tasks

Capabilities, ordered by how quickly you notice them.

  • Real tools. Read, write and edit files, apply patches, list directories, grep, glob, run shell commands, fetch and search the web, maintain todos, drive git, and manage background tasks.
  • Planning and memory. todo_write and todo_read let the model keep a plan across turns. Long-term memory distils lessons, preferences, corrections and facts into local files, and re-injects them by relevance.
  • Extensibility. MCP servers over stdio and streamable HTTP, skills at .nanohermes/skills/<name>/SKILL.md, subagent delegation, and lifecycle hooks that can veto a tool call.
  • Safety. Three approval tiers and, on Linux, a Landlock filesystem sandbox.
  • A desktop shell. Four columns, a virtualized transcript, incremental Markdown, a docked results panel, a command palette and three themes.

One fact is easy to miss. The desktop front end is React 19 with TypeScript and Vite, and the Rust side is a single 72 KB gui/src/main.rs. No plugins, no glue framework, no state machine generator. Tauri commands are ordinary functions with an attribute macro.

Three disciplines

One: no async runtime. HTTP uses the blocking ureq client. Concurrent tool calls use std::thread::scope. Each MCP server gets a dedicated reader thread. No tokio means no per-task state machines, no thread pools and no runtime memory overhead.

Two: dependency minimalism, close to fanaticism. The agent crate depends on serde_json, ureq with TLS, and base64. Not serde's derive macro, so every value is a serde_json::Value. Not even libc, so Landlock and SIGINT handling detour through a hand-written syscall module.

Three: every output has a ceiling. Tool results clamp to 20 KB. Command output caps at 256 KB per stream. A file read over 4 MB is refused outright. Web response bodies clip at 2 MB. Grep returns at most 200 matches, glob at most 500 files. Project guidance and skill bodies are limited to 20 KB each. Context and process memory are both held down by those numbers.

Together they define the character of the project. Push complexity into the layer that must be written and is worth writing, and cut everything else.

Core 1: the agent loop, without async

Agent::run in agent/src/agent.rs is a bit over a hundred lines and takes one user turn from start to finish.

pub fn run(&mut self, content: Value) -> Result<String, String> {
    // A Ctrl-C during this turn sets a flag instead of killing the process.
    let _guard = InterruptGuard::new();
    // Cross-session memory: retrieve for this instruction, replace the injected block.
    let user_text = memory::content_text(&content);
    if let Some(dir) = self.ctx.memory_dir.clone() {
        let block = memory::retrieve_block(&dir, &user_text);
        self.set_memory_block(&block);
    }
    self.messages.push(json!({ "role": "user", "content": content }));

    for _ in 0..self.cfg.max_iterations {
        // Abort only at a step boundary so the history never keeps an
        // assistant tool-call without its matching tool result.
        if crate::interrupt::take() { interrupted = true; break; }
        let turn = self.complete()?;
        // ... accumulate token usage, push the assistant message
        if turn.tool_calls.is_empty() { completed = true; break; }
        // ... run tools concurrently, backfill tool messages in call order
        self.compact();
    }
    // Only fully completed turns distill memories
    if completed && self.cfg.memory { self.distill_memories(&user_text, had_tools); }
    self.persist();
    Ok(final_text)
}

Four things in that shape deserve their own paragraph.

Interruption happens at step boundaries, not anywhere. The single break point is at the top of the loop. The comment explains why: interrupting after a tool call was issued but before its result was written leaves an assistant tool call with no matching result, and the API rejects the next request. The cost is at most one step of extra latency.

Long-term memory is re-retrieved and replaced each turn. set_memory_block overwrites the old block by its markers instead of appending. A hundred turns still inject exactly one block. This is the classic failure of injected memory, where the prompt quietly grows until it dominates everything else.

Token usage reports the delta, not the running total. A daemon serving many sessions would make a cumulative total useless to the client. Deltas let the client compute a per-task total, and locally they sum to the same number anyway.

Distillation has a hard gate. It runs only when the turn completed normally, not when it was interrupted and not when it hit the iteration cap. A half conversation never becomes a lesson. A failed distillation degrades silently and does not affect the answer.

One model round trip is wrapped in complete, which lands in llm::chat. It builds the request body, attaches tools and tool choice when needed, sets reasoning_effort: "high" when thinking is enabled, adds stream_options.include_usage so token counts arrive inside the stream, and then enters the retry loop.

fn backoff_ms(base_ms: u64, attempt: u32) -> u64 {
    base_ms
        .saturating_mul(2u64.saturating_pow(attempt.saturating_sub(1)))
        .min(30_000)
}

Backoff doubles from the base and caps at 30 seconds. Retryability is decided only by HTTP status: 429, 500, 502, 503 and 504. When the attempts are exhausted and a fallback model is configured, it gets one final call. Defaults are two retries with a 500 ms base.

Core 2: concurrency through scoped threads

When a turn returns several tool calls, NanoHermes runs them concurrently. With no tokio, the primitive is std::thread::scope.

let results: Vec<String> = if turn.tool_calls.len() == 1 {
    vec![self.execute(&turn.tool_calls[0])]
} else {
    // Reborrow as `&Agent` so the scoped threads can share it
    // (`execute` takes `&self`, and `Agent` is `Sync`).
    let this: &Agent = self;
    std::thread::scope(|s| {
        let handles: Vec<_> = turn.tool_calls.iter()
            .map(|call| s.spawn(move || this.execute(call)))
            .collect();
        handles.into_iter()
            .map(|h| h.join().unwrap_or_else(|_| "ERROR: tool thread panicked".to_string()))
            .collect()
    })
};

Four details matter here.

  • A single call takes the direct path. Threads are spawned only when there is more than one call, and most turns call one tool.
  • Results are collected in call order. join runs in the same order as tool_calls, so the completion order cannot mismatch a result with its tool_call_id.
  • Agent must be Sync. That is the precondition for the whole scheme. On the MCP side, each server's child process and reader handle sit inside a Mutex<Server>, which makes the manager and therefore the agent Sync.
  • A panicking thread does not take down the turn. join returns an error, which becomes a string that looks like a tool error. The model sees a failed call and carries on.

MCP concurrency has a finer grain. Calls to the same server serialize on its stdin lock, because the protocol is request and response over a single connection. Different servers run in parallel.

Core 3: not even libc

Both sandbox.rs and interrupt.rs need syscalls that the Rust standard library does not expose: the Landlock family, and rt_sigaction. The usual answer is the libc crate. Here it is agent/src/sys.rs.

#[cfg(target_arch = "x86_64")]
pub mod nr {
    pub const CLOSE: usize = 3;
    pub const RT_SIGACTION: usize = 13;
    pub const OPENAT: usize = 257;
    pub const PRCTL: usize = 157;
}

Each architecture gets its own table, because the numbers differ: openat is 257 on x86_64 and 56 on aarch64, prctl is 157 and 167. On top of that sits a syscall() taking up to six arguments, issuing the syscall instruction on x86_64 and svc 0 on aarch64, with different register assignments on each.

The whole module is under 75 lines and is gated on Linux plus one of those two architectures, so it disappears entirely on other targets.

This is the most expensive consequence of the minimalism discipline: portability and some audit surface traded for thirty lines of assembly. It is also defensible, because both features only mean anything on Linux.

Core 4: nineteen tools and the bounded-output rule

There are nineteen built-in tools in four groups, and up to 28 once conditional ones appear. The four mcp_* tools exist only when an MCP server is configured.

Dispatch is a plain match. Every error becomes a string handed back to the model as a tool result, so nothing panics and nothing breaks the loop. The last line of dispatch is the one that matters.

r.map(|s| clamp(s, ctx.max_output))

Every tool result is clamped to max_output, which is 20 KB. That line is where the bounded-output discipline is enforced: whichever tool runs, whatever arguments the model passes, no single tool result ever exceeds 20 KB of context.

Each tool also has a second ceiling, and the numbers are chosen rather than arbitrary.

One detail is security relevant. Command output is read with a capped reader that clips while reading, not after. Otherwise a stray yes or a runaway build script eats memory before anything gets trimmed.

apply_patch has a trade-off worth stating. Patches match on content, not on line numbers, so a small drift in the source still applies.

Core 5: compaction

Context management lives in compact_with, and two constants set the policy.

const CONTEXT_CHAR_BUDGET: usize = 120_000;
const KEEP_RECENT: usize = 10;

Past 120,000 characters, or past one message more than the keep count, compaction starts. It walks back ten messages, finds a safe starting point, drains the older span for a summary, and inserts that summary as a system message at index one.

Three details prevent the usual accidents.

  • It never cuts inside a tool-call chain. If the starting point lands on a role == "tool" message, it moves forward until it does not. Otherwise the summary would drop an assistant tool call while the tool result stayed behind.
  • A failed summary still loses nothing. The span is replaced by a single line saying earlier conversation was omitted, rather than an error or silent loss.
  • It can be triggered by hand. /compact forces one compaction regardless of size.

Keeping ten recent messages is empirical. Ten cover the file being edited plus the last tool result, and older context decays quickly in value.

Core 6: memory without a vector database

Memory lives in agent/src/memory.rs and persists to ~/.nanohermes/memory.json. The practical question it answers is this: how do you search Chinese with no embedding service at all? The answer is two stages. Tokenize, then score with BM25.

The tokenizer handles mixed Chinese and English text.

  • Runs of ASCII letters and digits become words and are lowercased, and anything shorter than two characters is dropped, which removes noise like single letters.
  • Runs of CJK characters are split into bigrams, using a two-character sliding window, with isolated characters kept whole. A four-character phrase therefore becomes three overlapping pairs.
  • The CJK test covers Han characters, kana, hangul and the compatibility blocks, not just the unified ideographs.

Scoring is standard BM25 with the usual parameters.

let idf = (1.0 + (n - n_q + 0.5) / (n_q + 0.5)).ln();
score += idf * (f * (k1 + 1.0))
       / (f + k1 * (1.0 - b + b * len / avg_len.max(1.0)));

Two details go beyond the textbook. Category words participate in matching. Every memory has a kind, and that kind's labels are added to the document bag, so a question about what was corrected earlier hits correction entries directly. And zero-score entries are filtered before ranking, so an unrelated memory cannot crowd out a relevant one.

Because the number of entries is small, scoring is linear with no inverted index. One vector and one hash map are enough. Retrieval is recomputed every turn and injected by the same marker mechanism as the memory block.

Writing has two gates. memory_save skips text that already exists, and automatic distillation only runs on completed turns. Small talk and half conversations never pollute the store.

The system is closer to an index than to a brain. It does not summarize conversations, and it does not decay the weight of a memory that went unused. What it does guarantee is that every entry can be seen, edited and deleted in the UI, so a user can explain why the model mentioned something. For a personal assistant, that is worth more than recall.

Core 7: the MCP client

Both transports are implemented. Over stdio, frames follow the LSP shape: a content-length header, a blank line, then the JSON body, byte for byte.

let frame = format!("Content-Length: {}\r\n\r\n", body.len());

Over streamable HTTP, requests are synchronous posts with an accept header covering both JSON and server-sent events. The session id the server returns is remembered and echoed on later requests. Responses may be plain JSON or an event stream, and both are parsed.

The handshake is the standard three steps: initialize with the protocol version, send the initialized notification, then list tools. Declared tools are converted into OpenAI function definitions and merged into the agent's table, and from that point they are dispatched by name. An MCP tool is indistinguishable from a built-in one, from the model's point of view.

Four auxiliary tools expose resources and prompts, and they only appear when a server is configured. Configuration is one JSON file where a command means stdio and a URL means HTTP, both inside the same servers object.

Core 8: skills and progressive disclosure

Skills are reusable instruction packs. One directory per skill, with a markdown file and optional frontmatter declaring a name and a description.

Discovery is workspace first: the workspace skills directory, then the user skills directory, with workspace entries overriding global ones of the same name. The implementation deduplicates by name while walking a sorted directory list.

The important property is that the body never enters context at startup.

const MAX_BODY_CHARS: usize = 20_000;

/// A discovered skill. `body` is read lazily so startup only pays for parsing
/// the frontmatter.

Startup parses only the frontmatter. The system prompt lists each skill's name and description. When the model needs a body, it calls the skill tool and the body arrives, capped at 20 KB. That is progressive disclosure: the library can be large while the base prompt stays small.

Missing frontmatter falls back to the directory name and the first line of the body.

Core 9: the subagent board and the gate

Subagents come from a JSON file passed on the command line. Each one can carry its own prompt, model and tool allowlist. Once configured, two tools appear: one to delegate and one to inspect the board.

The board records every delegated task: an incrementing id, the name, the description, the status, the duration and a result preview. The preview is capped.

const RESULT_PREVIEW: usize = 500;

The clipper respects UTF-8 boundaries, stepping back until the cut point is a character boundary, so a multi-byte character is never split into a panic. The full result still returns to the model as the tool result. The board keeps a summary only so the board reads cleanly.

The gate is a textbook counting semaphore built from a mutex and a condition variable. Acquiring waits when the limit is reached, and the returned guard decrements and notifies on drop. The cap is four concurrent delegations.

Why it is needed: the loop spawns one thread per tool call, and a single turn can emit several delegations. Without the gate, one turn could fire a dozen concurrent model requests.

Core 10: hooks that can veto a tool call

Hooks are shell commands of two kinds, before tool use and after tool use, matched by a wildcard or a comma-separated list of tool names.

They run through the shell with the workspace root as the working directory, and the tool call arrives on stdin as JSON.

let payload = json!({ "tool": tool, "event": event, "arguments": args }).to_string();

Two environment variables are exported as well, so a hook does not have to parse stdin just to branch on the event.

Two implementation details are worth copying.

  • Both pipes get their own draining thread. If only one is read, the other fills its 64 KB buffer and the hook deadlocks. Chatty hooks are the normal case, not the exception.
  • Hooks must be fast or they fail. The timeout is 30 seconds, after which the process is killed and a distinct exit code returned. A hook is a quick check and a notification; a stuck hook must not stall the agent forever.

The semantics are deliberately asymmetric. A non-zero exit from a pre-hook blocks the tool call and returns the hook's output to the model. A non-zero exit from a post-hook can only append a warning to a result that already happened. If you want to stop something, stop it before.

Core 11: Landlock and three approval tiers

Two independent switches govern this: whether to ask, and what is permitted.

The approval policy decides when confirmation is required.

PolicyBehaviour
neverNever ask, for any command. This is the default, and what the yes flag selects.
on-requestAsk only for commands that are not recognized as read-only.
untrustedAsk for everything, read-only commands included.

Read-only detection is stricter than it looks. The first gate is metacharacters.

if cmd.chars().any(|c| matches!(c, '|' | '&' | ';' | '<' | '>' | '`' | '$' | '(' | ')' | '\n')) {
    return false;
}

Any pipe, ampersand, semicolon, redirect, backtick, dollar sign, parenthesis or newline makes the command untrusted, whatever the program at the front of it is. In other words, a shell metacharacter means the thing is a program rather than a binary.

Past that gate comes allowlist matching. Leading environment assignments are skipped, path prefixes are stripped, and the remaining binary is checked against a list of read-only programs. Git gets its own check, because its global options consume the following token as a value, so those are skipped before the subcommand is judged.

The sandbox mode uses Landlock to restrict what a spawned command can see.

ModeBehaviour
offNo restriction. Default.
read-onlyRead and execute, no writes at all.
workspace-writeRead and execute, writes only inside the workspace.

The most interesting part of the implementation is that it refuses to degrade. Landlock is installed between fork and exec, so the restriction covers every child the command spawns. If the kernel does not expose Landlock, or an outer sandbox blocks it, NanoHermes refuses to run the command rather than quietly running it unsandboxed. The comment makes the argument: a security mechanism that always falls back gracefully is not a mechanism.

All of this still goes through the hand-written syscall shim, with no external crate.

Core 12: Ctrl-C that does not kill, and undo

In interactive use, Ctrl-C is redefined. It does not kill the process. It flips a flag, and the current turn exits cleanly at the next step boundary with the conversation intact.

The implementation depends on a piece of timing.

static INTERRUPTED: AtomicBool = AtomicBool::new(false);
/// Nesting depth of active turns; the handler is installed at 0 -> 1 and
/// removed at 1 -> 0.
static DEPTH: AtomicUsize = AtomicUsize::new(0);

Reference counting keeps nested turns sharing one handler, and the outermost exit restores the default action. Ctrl-C while idle still quits. Only while busy does it mean "stop this turn". One signal, two meanings, decided by when the handler is installed rather than by inspecting a flag.

One more engineering detail. On x86_64, the kernel refuses to deliver a caught signal unless the caller supplies a restorer that executes rt_sigreturn. That is the only hand-written assembly in the project beyond the syscall instruction itself: a few lines, hidden from the symbol table, that issue syscall 15.

core::arch::global_asm!(
    ".globl nanohermes_sigrestorer",
    ".hidden nanohermes_sigrestorer",
    "nanohermes_sigrestorer:",
    "mov rax, 15",
    "syscall",
);

The desktop has no signal to send, so a request function flips the same flag directly. The GUI stop button and the terminal Ctrl-C take one path, and the loop never learns who asked.

Paired with it is /undo [n], which deletes the last n complete user turns, including everything that followed each one, and persists the result. Interrupt preserves, undo erases, and both are needed, because "it went sideways and I want to correct it" and "it went sideways and I want to pretend it did not happen" are different intentions.

The desktop shell

gui/ wraps the same agent as a desktop application in four columns.

There are five permission modes, and their differences are larger than their names suggest.

ModeLabelBehaviour
defaultAgentAll tools available, edits and commands without asking
accept-editsAcceptFile edits auto-approved, commands still gated

Plan, goal and debug inject a mode instruction into the system prompt as well. The reason is in the source comment: the model should behave according to how it was launched, rather than discover that tools are missing and keep retrying them.

Desktop performance notes come from four hard-won conclusions.

  • No blocking Tauri commands. A synchronous command runs on the window's main thread, so any disk or network work freezes the whole UI for that turn. Everything touching the filesystem, processes or HTTP is async and handed to the blocking pool. Only two memory-only commands stay synchronous. Settings writes are also serialized behind a static mutex so two flushes cannot land out of order.
  • Streaming text stays out of the global store. Deltas go through a dedicated subscription that only the bubble being written listens to, and each stage, such as a tool call or the end of a turn, commits once to the transcript. A long answer therefore does not re-render the sidebar, the results panel and the title bar. Events batch on dedicated channels at 40 ms intervals.
  • The transcript is virtualized. Only messages in or near the viewport mount, height measurement is skipped while the last bubble is still growing, and follow-scroll is driven by the stream rather than by React.
  • Markdown is incremental. During streaming the text is split into blocks on blank lines outside code fences. Stable blocks render once and stay, an unterminated fence only updates its own code text node, and syntax highlighting runs per block after the turn instead of over the whole answer.

The IPC surface is sixteen commands plus two stream readers, all inside a 72 KB file.

Daemon mode and VPS deployment

agent --daemon turns the agent into a resident HTTP service with two endpoints.

EndpointMethodAuthBehaviour
/POSTBearer when a token is configuredTakes a prompt, returns the response and a session id
/healthGETNoneReturns status and session count, for liveness probes

Sessions are isolated by a request header. Supplying a session id selects that session, different ids never share context, and omitting it uses the default. Each session persists to its own JSON file.

The desktop connects cloud tasks this way, each with its own session id, so one daemon serves many desktop tasks without cross-talk. The cost is that cloud configuration is fixed at daemon startup, meaning model, persona, temperature and permission mode all come from flags, and that a cloud turn cannot be cancelled midway because the request is held by the daemon.

The deployment script does the whole job.

StepWhat happens
InstallBinary to /opt/nanohermes/nanohermes, workspace to /opt/nanohermes/workspace, session directory permission 700
TokenGenerated with openssl rand -hex 24 into /opt/nanohermes/.daemon_token, reused on re-runs
ServiceA systemd unit running the daemon with the workspace, a session file and workspace-write sandboxing, with restart-always
HardeningNo new privileges, strict system protection, plus explicit writable paths
StartEnable and start, then curl the health endpoint and print the token

One trap is documented. Strict system protection blocks writes to the memory file, so long-term memory needs an explicit writable path in a drop-in. A 1 GB instance also needs swap added first, because compilation is the only memory-hungry step.

Exposure has three documented options: an SSH tunnel with no open port, a Caddy reverse proxy on 443 or 8443 while remembering that certificate validation still needs port 80, or a Cloudflare Tunnel. The warning is worth quoting unchanged: never expose the daemon port directly, because the only credential is the bearer token and the traffic is plaintext.

Sessions and multimodal input

A session file is a JSON array of OpenAI-style messages, written atomically: a temporary sibling file is written and then renamed over the target. A crash mid-write therefore cannot truncate history. Saves happen after each completed turn and after clearing; a failed read at startup falls back to a fresh conversation with a warning rather than refusing to start.

Multimodal input is available for vision models: a flag for one-shot use, a command in the REPL, and paste, drag or picker on the desktop. Limits are four images per turn, a long edge scaled to 1024 pixels, and rejection with a reason for undecodable or oversized files. Transfer is by data URL, so the model must support vision.

Tests

Rust tests are per-module unit tests plus a genuine end-to-end suite, all run by one workspace command. The end-to-end suite starts a local mock OpenAI server that depends only on the standard library and needs no network, and drives the real agent through tool round trips, streaming and non-streaming replies, a retry after one transient 5xx, and a hard API error. A mock MCP server written in Python covers the other transport.

The unit list says a lot about which parts are assumed to break: patch application including multi-hunk and missing context, glob matching, MCP resource and prompt listing, MCP tool dispatch, streamable HTTP handshake and calls, MCP concurrency under mixed load, concurrent tool execution including a mix of built-in and MCP tools, HTML to text and search result parsing, session task lists, git round trips, token usage parsing and backoff arithmetic, multimodal content assembly, session persistence round trips, project guidance injection including the off switch, skill discovery including frontmatter fallback and workspace override, hook execution covering exit codes and matching and stdin payloads, subagent board ordering and the concurrency gate, approval decisions and trusted command detection, the Landlock workspace boundary, signal flag set and clear, and long-term memory covering Chinese bigrams, BM25 ordering, deduplication and the distillation gate.

The frontend uses Vitest with jsdom. Pure logic tests cover theme resolution and persistence, store migrations, Markdown sanitization, image attachments, in-session search and diff blocks. Component tests cover the settings page, the command palette, the results panel and the shortcuts panel. One end-to-end test renders the real store and components against a mocked Tauri IPC bridge and verifies virtual scrolling over a long transcript, search across screens, jump-to-change in a diff, and the input state while a task is running or stopping.

One regression test exists solely to assert that long-running commands never execute synchronously on the main thread, because that is the performance contract most likely to be broken quietly by a later change.

Known limits

  • Sandboxing and SIGINT handling are Linux-only. Both rest on raw syscalls and disappear on Windows and macOS, so the Windows desktop runs without a sandbox and with default signal handling.
  • Cloud turns cannot be cancelled. The request is held by the daemon and the desktop can only wait. Only local tasks stop at step boundaries.
  • The daemon runs as root, and the token is the only credential. Anyone holding it can read, write and execute inside the workspace, which is exactly why the documentation insists on not exposing the port.
  • No async has real costs. A stuck HTTP request occupies a thread until its timeout, 120 seconds by default. That is fine for a CLI and a desktop app, and wrong for a high-concurrency gateway.
  • The Windows installer is unsigned, so the first run trips SmartScreen.

Verdict

What is worth reading in NanoHermes is not the feature list but the discipline. Coding agents converge on similar feature sets. Holding four constraints all the way through is what produced these implementations: no async runtime, three crates, no libc, and a ceiling on every output.

Those constraints buy a single binary with a design target around 2 MB, memory that tracks context length rather than framework overhead, and one codebase that is simultaneously a CLI, a desktop application and a systemd service on a small VPS.

When everyone else is adding dependencies, taking them away is also an engineering skill.
