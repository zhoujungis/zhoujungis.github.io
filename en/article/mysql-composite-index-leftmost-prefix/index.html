Why an index on (a, b) cannot answer a query on b

2026-11-04 · 14 min · Stack Frame

Who this is for: people who built an index on two columns and watched a query on the second one do a full scan; people confused by the length column in a query plan; people wondering what order composite index columns should be in.

TL;DR: an index on (a, b) is not two trees, it is one tree sorted by a and then by b. To use b, you must first narrow the scan with a. That is the leftmost prefix rule, and it comes from the B+ tree's physical order, not from an optimiser limitation.

Reading time around 14 minutes. Level: advanced.

A slow query with an index that should have worked

SELECT id, uid, kind, ts
FROM events
WHERE kind = 2 AND ts >= '2026-01-01';

The table has an index on (uid, kind, ts), and the plan says a full table scan with no index chosen. The first instinct is that the index is not being used or the statistics are stale.

The real reason is simpler: the query does not mention uid, which is the first sort key of that index. Without it the scan cannot be narrowed to a contiguous range, so the optimiser falls back to a full scan.

What a composite index looks like on disk

CREATE TABLE events (
    id      BIGINT PRIMARY KEY AUTO_INCREMENT,
    uid     BIGINT NOT NULL,
    kind    TINYINT NOT NULL,
    ts      DATETIME NOT NULL,
    payload JSON,
    KEY idx_uid_kind_ts (uid, kind, ts)
) ENGINE=InnoDB;

A leaf entry is not three separate keys. It concatenates the three values in declaration order into one composite key, and sorts by that key lexicographically: compare uid, then kind, then ts.

(uid=1, kind=1, ts=10:00) -> (uid=1, kind=1, ts=10:05)
-> (uid=1, kind=2, ts=09:00) -> (uid=1, kind=2, ts=09:30)
-> (uid=2, kind=1, ts=08:00) -> (uid=2, kind=3, ts=11:00)

Look at the third entry: kind 2 with an earlier timestamp comes after kind 1 with a later one. Sorting looks at kind first, so all kind 2 entries follow all kind 1 entries regardless of time.

That picture is the entire source of the rule. Given uid, the matching records are contiguous and can be found by binary search. Given only kind, the records are scattered across every uid block. Given uid and ts while skipping kind, ts is only ordered within each kind block, so it cannot be located either.

The strict definition

The rule is not "you must use the first column", it is: starting from the first index column, match a consecutive run of columns; once you skip one, no later column can be used for seeking.

Two distinct actions are worth separating. Seeking narrows the scan start to a leaf range using the tree's branch decisions. Filtering tests conditions on records already read. The leftmost prefix constrains seeking, not filtering. A skipped column can still filter, it just cannot save you page reads.

a = 1aSeeks the contiguous a block
a = 1 AND b = 2a, bSeeks the (1,2) block

a = 1 AND b > 2 AND c = 3a, bAfter a range, c is unordered within the scan

Six shapes, checked one by one

All equality. All three columns seek, the index length is the full key, and the access type is usually a reference or a constant lookup if the combination is unique.

Prefix equality. Two columns seek the (uid, kind) block, and the key length stops after kind.

First column only. Seeks the uid block; kind and ts cannot be used for seeking.

Skipping the middle column. Only uid seeks. The third column may appear as an index condition, meaning it was pushed down to the index layer to reduce table lookups, but the whole uid block still has to be scanned. Many people misread that note as "the third column used the index", when it only filtered.

Range conditions. Equality on the first column plus a range on the second seeks the start of the range and scans to the end of the block. Adding equality on the third column cannot seek, because once the second column is a range the output is no longer ordered by the third.

IN and OR. An IN list is expanded into several equality ranges and still uses both columns. An OR on the same column merges into a range. An OR across different columns cannot be satisfied by one composite index, and the optimiser may choose an index merge, which in practice is usually less stable than a purpose-built composite index.

Why a range breaks the chain

It is the same sorting argument. For an index on (a, b, c), b is ordered across the whole scan range only after a is pinned to a single value, and c is ordered only after b is too.

Once b becomes a range, the scan produces several values of b, and c is not globally ordered across them. The tree cannot binary search on c and has to compare row by row.

Which produces the column-ordering rule: equality columns first, range columns last.

If equality on the last column is also common, consider swapping the order. Whichever query shape is more frequent gets the more precise index, and trying to serve both perfectly with one index usually degrades both.

Reading the key length as evidence

The key length in a plan is how many bytes of the index were actually used. Combined with column types, it reveals how many columns were involved.

For an index of BIGINT, TINYINT and DATETIME, all non-null: one column is 8, two are 9, three are 14. A key length smaller than expected usually means the extra columns are not in the WHERE clause, the order violates the prefix rule, or a range appears in the middle.

One trap: the key length counts index key bytes and excludes the primary key suffix. Do not use it to infer the total size of a secondary index entry.

Ordering, grouping and distinct

An index is already sorted, so sorting, grouping and deduplication can sometimes avoid extra work.

For ordering, the same rule applies: the ORDER BY columns must continue the index prefix, and the preceding columns must be equality conditions. If the plan says it is sorting files, the index did not help.

Direction matters too. Ascending on both columns can use a forward scan, descending on both can use a backward scan, and mixed directions need a descending index, available from MySQL 8.0.

For grouping, if the column order matches the index, the optimiser can use a loose or tight index scan instead of building a temporary table. The same holds for distinct, which is grouping in disguise.

Pushdown, covering and the prefix rule

MechanismProblem it solvesStill needs the table?
Leftmost prefixWhether the index can seek at allDepends on covering
Index condition pushdownFilters at the index layer, fewer table lookupsYes
Covering indexEvery needed column is in the indexNo

Note that covering does not require the leftmost prefix. Even a query whose WHERE clause cannot seek may still report a covering scan, because the optimiser chose to scan the whole, smaller index. That is a scan, not a seek, and the performance is a different story.

Choosing column order in four steps

  1. Put equality columns first: the ones nearly every query carries and that have high selectivity, such as tenant, user or status.
  2. Then add ordering columns: a stable ORDER BY belongs after the equality columns and before any range.
  3. Put range columns last: timestamps, thresholds, prefix matches.
  4. Finally consider covering columns: append the few columns a frequent SELECT needs, to earn a covering scan.

Selectivity is not the first priority. However selective a column is, it is useless if it cannot be part of the seek. Satisfy the query shape first, then prefer higher selectivity among equals.

The cardinality shown by the index listing is the optimiser's estimate, not an exact count. After a bulk import, refresh statistics before trusting it.

Prefix and functional indexes

A prefix index builds only the first characters of a long string column. It can still seek for equality and prefix matching, but it cannot cover, because the full value is not in the index, and ordering by the full value may not use the index, since prefix order is not value order. Choose the length by comparing prefix selectivity against full selectivity.

Functional indexes, available from 8.0.13, let a query filter on an expression without wrapping the column in a function in the WHERE clause. The expression must match the query text exactly, or the index is not used.

Skip scan, the 8.0 exception

MySQL 8.0.13 added skip scan for the case where a composite index's first column does not appear in the condition. The idea: if the first column has few distinct values, treat each one as a virtual prefix and seek the second column under each.

Its limits matter. The first column must have low cardinality, or the number of virtual prefixes explodes. The first column must not already carry an equality or range condition. The switch must be on, which it is by default. And it only makes an unusable index barely usable; a purpose-built index on the second column is usually better. Know it exists, do not treat it as a safety net.

One composite index or several single-column ones

OptionStrengthCost
Two single-column indexesEach query is preciseMore indexes, more write amplification, possible index merge
One composite indexBest for the combined query, still serves the first columnThe second column alone cannot use it

The decision depends on the distribution of query shapes, not on a preference for fewer indexes. If the two forms are equally frequent, two single-column indexes may be right; if the combined form dominates, one composite index is cheaper.

Index merge appears in plans as an intersection, a union, or a sorted union. It is frequently mis-chosen, and while you can disable it for comparison, doing so globally in production is not a good long-term plan.

Indexes are not free

Every secondary index is its own tree, maintained on every write: inserts add an entry to each, updates delete and re-insert when indexed columns change, deletes mark entries, and page splits, buffer pool pressure and log volume are all multiplied. The right approach is not one index per query, it is: find the genuinely slow statements, check whether they lack seeking, covering or ordering, index only the frequent and well-understood ones, and periodically look for indexes that have never been read.

From a slow query to an index, in five steps

Confirm the current plan shows no index and a full scan. Classify the shape: equality on one column, range on another, and a missing leading column. Design the candidate with equality first and the range last. Verify that the plan now reports a range access with the expected key length and a plausible row estimate. Then, if the query is frequent and the column list is small, append the extra columns to make it covering, accepting a bigger index and slower writes in exchange for faster reads.

Five misconceptions

An index on (a, b) serves a query on b. It does not. Build (b, a) or a single-column index on b.

The most selective column should always lead. Selectivity decides how many rows survive, but if the prefix rule is violated the index cannot seek at all.

Functions on an indexed column still use the index. Wrapping the column in a function defeats an ordinary index; rewrite as a range or build a functional index.

Implicit conversion only affects performance, not correctness. Comparing a string column against a number converts the column and drops the index, and some boundary values can match unexpectedly. Align types explicitly.

An index condition in the plan means every index column was used. It only means some conditions were pushed down; the prefix may still be broken.

Summary

  • A composite index is one tree sorted by column order, and the prefix rule follows from that order.
  • Columns after a range cannot seek, only filter.
  • Column order goes equality, then ordering, then range, then covering.
  • The key length is direct evidence of how many columns were used, remembering variable-length overhead and nullable flags.
  • Verify with plans and instrumentation rather than intuition.
