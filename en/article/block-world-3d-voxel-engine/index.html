Block World 3D: a voxel engine with no game engine

2026-11-19 · 34 min · Stack Frame

Who this is for: people who want a voxel world with Three.js but do not want a full game engine; frontend engineers interested in procedural generation, chunk streaming and instanced rendering; indie developers fighting frame time, memory and save formats.

TL;DR: Block World 3D uses Three.js for rendering only. Terrain, chunks, lighting, physics, redstone, mob AI and saves are all written from scratch. It moves terrain sampling into a Worker with a 28 by 28 grid, stores blocks in a string-keyed Map across 251 layers, packs sky light and torch light into one byte, batches draws with InstancedMesh by block type and state, and runs block updates through a priority queue with a 4,096-event budget. Measured on this machine, one chunk's terrain prep costs about 5 ms, terrain sampling runs at 160,000 to 250,000 points per second, and A* finds a path in 0.05 ms. The costs are a string key at roughly 80 bytes, redstone that is still incomplete, and a cloud save schema two versions behind the client.

Reading time around 36 minutes. Level: advanced.

The boundary: what is engine, what is gameplay

"Build Minecraft with Three.js" sounds like a joke. Three.js does three things: scene graph, materials, and drawing triangles. It does not know what a block is, what "standing on the ground" means, or how a redstone signal attenuates.

Block World 3D draws the boundary clearly:

LayerOwnerCode
RenderingThree.js: camera, materials, InstancedMesh, fog, shadowssrc/rendering/
World dataCustom: block Map, chunks, block states, water levelssrc/world/block-store.js
TerrainCustom: noise, biomes, caves, ore veinssrc/world/terrain.js
GenerationCustom: trees, villages, 17 structure types, lootsrc/world/generation.js
PhysicsCustom: AABB collision, gravity, swimming, ladderssrc/physics/player-physics.js
SimulationCustom: fluids, fire, crops, random ticks, redstonesrc/systems/
SavesCustom: schema v6, Electron SQLite, D1 cloud syncsrc/persistence/, cloudflare/worker.mjs

The repository, excluding Three.js and build output, is 103 text files and about 22,900 lines. The entry point alone, game.js, is 87 KB. This is not a Three.js demo. It is a small engine split across more than twenty modules.

Start with the scale. Counting the real data modules gives:

blocks                 528
expanded block names   263
items                  835
crafting recipes       332
stonecutter recipes     80
hostile types           40
animal types            20
villager professions    13
surface biomes          34

The README badges still say "479 blocks" and "325 recipes". The code says 528 and 332. That drift is a useful reminder: content grows faster than documentation, and the data table is the source of truth, not the marketing image.

The world: string keys, 251 layers, 81 chunks

The world data structure is deliberately plain:

world = new Map();          // key: "x,y,z" -> value: "stone"
blockStates = new Map();    // same key -> { facing, half, powered, ... }
worldLevels = new Map();    // same key -> 0..8, for water and lava

keyOf(x, y, z) is a template string. It is not compact, but it has two advantages: you can read it while debugging, and it serializes directly as a JSON key without another encoding layer.

The vertical range is MIN_Y = -50 to MAX_Y = 200, 251 layers. Horizontally the world is split into 16 by 16 chunks, with a load radius of 4 and an unload radius of 5:

  • Load radius 4 means 81 chunks.
  • Unload radius 5 means a chunk is only released after five chunks of distance, which prevents reload thrash at the boundary.
  • View distance is 112 blocks, with fog closing the far edge.

The number of blocks in a chunk depends on terrain height. Sea level is 2. Surface usually sits between -10 and 40, so a column holds roughly 60 to 100 non-air blocks. With 16 by 16 columns that is 15,000 to 25,000 keys. Load all 81 chunks and the Map holds close to 1.9 million entries.

I measured the key cost on its own: 300,000 entries of "x,y,z" -> "stone", with --expose-gc and the Map still alive, retained 23.0 MB, or 80 bytes per entry. At 1.86 million entries that is roughly 149 MB for the block Map alone. It is not exact, because V8 string interning and Map growth both matter, but the magnitude is enough to make the point: string keys buy readability with memory.

Why not a Uint16Array or a chunk bitmap? Because the world is not fixed size. Infinite terrain means chunks are created and released on demand, and player edits have to be persisted separately. A Map stores sparse data with O(1) lookups and deletes, and it is the cheapest thing to implement. When the world grows another order of magnitude, it will be worth moving to one typed array per chunk plus a palette.

A chunk object itself is tiny:

const chunk = { x: chunkX, z: chunkZ, keys: new Set(), meshes: [] };

keys holds every non-air block key in that chunk. It serves two purposes: rebuilding light and meshes iterates only this chunk instead of the whole world, and unloading can delete the blocks from the global Map by walking keys.

The unload path in ensureChunks() is:

for (const key of chunk.keys) {
  world.delete(key);
  worldLevels.delete(key);
  blockStates.delete(key);
  fallingBlockKeys.delete(key);
  copperBlockKeys.delete(key);
}
for (const mesh of chunk.meshes) removeChunkMesh(mesh);
chunks.delete(chunkKey);

There is room for improvement here. It clears five index sets but leaves waterSet, lavaSet, fireKeys, cropKeys, leafKeys and torchKeys alone. The simulation loop checks whether a chunk is still loaded and skips stale keys, and the key is removed lazily when the chunk loads again. Nothing computes wrong, but long exploration leaves entries from unloaded chunks in those sets. For a sandbox that lets you walk forever, that is a long-term memory item worth watching.

Block state is a second Map. Stair facing, slab half, door upper and lower halves, repeater delay, comparator mode, water level and crop stage all live there. setBlock() maintains more than a dozen index sets:

fallingBlockKeys   sand, gravel, concrete powder
copperBlockKeys    copper that can oxidize
farmlandKeys       farmland
fireKeys           fire
leafKeys           leaves
saplingKeys        saplings
growableKeys       crops that can be bonemealed
waterSet / lavaSet fluids
cropKeys           crops
torchKeys          light sources

These sets are not decoration. They let random ticks avoid scanning the world. Each frame iterates only the active sets, so the cost is proportional to the number of active blocks, not the number of blocks in the world.

Terrain: seven noise layers and 34 biomes

Terrain generation is built on seven noise salts:

const NOISE_SALT = {
  continents: 0x1a2b3c4d,
  erosion:    0x2b3c4d5e,
  ridges:     0x3c4d5e6f,
  temperature:0x4d5e6f70,
  vegetation: 0x5e6f7081,
  river:      0x6f708192,
  detail:     0x708192a3,
  variant:    0x8192a3b4,
};

Each salt drives a fractalNoise2D with two to five octaves of value noise. latticeNoise2D mixes the coordinates and seed as integers, then scrambles the result with mix32. That is more stable than a Math.sin hash and avoids floating-point differences across calls.

heightAt(x, z) does not simply add noise. It works in layers:

base     = continentalness -> base elevation (-14 to 30)
macro    = low-frequency detail * (5 + low erosion * 8)
detail   = high-frequency detail * 2.6
mountain = low erosion * land mask * ridge mask^1.38 * (92 + peak * 142)
natural  = base + macro + detail + mountain

Then it handles oceans, rivers and ravines:

  • Below a continentalness threshold, the sea floor is pushed down by SEA_LEVEL - 5 - oceanStrength * 8.
  • Rivers use warped coordinates and two noise channels, carving the channel down to near sea level.
  • Ridges use 1 - abs(ridge) * 2.15, multiplied by an erosion mask. Mountains only rise when low erosion, high land and high ridges all agree.

Biomes are not cut by height. They use climate targets and weighted distance:

distance = dTemperature^2 * 1.45
         + dVegetation^2 * 1.25
         + dContinentalness^2 * 0.45
         + dErosion^2 * 0.58
         + dRidges^2 * 0.72

Twelve targets, including plains, forest, jungle, birch, swamp, mountains, snow, desert, taiga, savanna, badlands and meadow, compete for the nearest match. A variant noise then derives sub-biomes: plains can become sunflower plains, forest can become dark forest or flower forest, jungle can become bamboo or sparse jungle. The result is 34 surface biomes.

Caves are a separate system, not a biome:

  • caveFieldAt sums four trigonometric fields; a value above 1.12 becomes a cave.
  • isTunnel creates horizontal tunnels per 20-block segment, seeded per world.
  • isRavine uses warped noise to find narrow, deep canyons whose width varies with height.
  • aquiferAt creates water below the sea floor and lava deeper down.
  • isLavaLake uses a 34 by 12 grid to place lava lakes.

Ore veins are not per-block random. Each ore has its own spacing, verticalSpacing, radius and chance. The generator first candidates centers in a 3 by 3 by 3 neighborhood, then tests whether the current point falls inside an ellipsoid. That clusters veins instead of scattering ore like pepper.

Chunks: 28 by 28 worker sampling

The main thread's worst enemy is computing terrain while the player walks. chunk.worker.js moves terrain sampling into a Worker:

const MARGIN = 6;
const width = chunkSize + MARGIN * 2;   // 16 + 12 = 28
const originX = chunkX * chunkSize - MARGIN;
const originZ = chunkZ * chunkSize - MARGIN;

for (let localZ = 0; localZ < width; localZ += 1) {
  for (let localX = 0; localX < width; localX += 1) {
    const x = originX + localX;
    const z = originZ + localZ;
    heights[index] = heightAt(x, z);
    biomes[index] = BIOME_IDS.get(biomeAt(x, z)) ?? 0;
    slopes[index] = Math.min(255, terrainSlopeAt(x, z));
  }
}
self.postMessage({ id, ok: true, heights, biomes, slopes },
  [heights.buffer, biomes.buffer, slopes.buffer]);

Several details decide the performance:

  • Six-block margin: canopies, structures and slopes need two to six blocks outside the chunk, so the worker samples 28 by 28 instead of 16 by 16. The main thread then does not need cross-chunk queries.
  • Typed arrays: heights use Int16Array; biomes and slopes use Uint8Array. Compact memory, fast transfer.
  • Transferables: the three buffers transfer ownership instead of being structured-cloned.
  • One layer at a time: the worker returns heights, biomes and slopes, not blocks. Block filling stays on the main thread because it reads the global world, blockStates and saved edits.

Measured on 81 chunks at radius 4, 63,504 sample points cost 385 to 479 ms of CPU time, or 4.8 to 5.9 ms per chunk. Radius 1 costs 4.0 to 5.8 ms per chunk, radius 2 costs 4.2 to 5.2 ms. Notice that this is not "bigger is cheaper". terrainRouterAt caches 16,384 samples. Radius 4's 63,504 points clear that cache repeatedly, so the per-chunk cost rises slightly. Cache hit rate explains the difference better than JIT warm-up.

This is why the Worker matters: not raw speed, but not blocking the frame. A 5 ms budget on the main thread would visibly eat a 60 FPS frame. In a Worker, the main thread only has to fill blocks and build meshes.

Generation: how 17 structures stay pinned to a seed

generateChunk(chunkX, chunkZ) runs in a fixed order:

1. Take the prepared samples (or fall back to heightAt/biomeAt/terrainSlopeAt)
2. Fill terrain column by column: bedrock, caves, surface/filler, stone/ore
3. Fill water below sea level
4. Fill deep lava and aquifers
5. Decorate caves (lush, dripstone, deep dark)
6. Plant trees (roots may sit two blocks outside the chunk)
7. Surface vegetation (flowers, grass, cactus, sugar cane, pumpkin, mushrooms)
8. Villages
9. The other 16 structure types
10. Apply saved player edits

Structures are not placed at random. Their positions are computed from the seed. Each structure has bounds and a region grid, so a chunk first checks whether it intersects the bounding box. Villages are the clearest example:

const gridX = Math.floor(chunk.x / 32);
const gridZ = Math.floor(chunk.z / 32);
const centerX = (gridX * 32 + 16) * 16 + 8;
const centerZ = (gridZ * 32 + 16) * 16 + 8;
if (Math.abs(centerX) + Math.abs(centerZ) < 128) return;   // keep spawn clear
if (hash(gridX * 127, gridZ * 911) >= .065) return;        // 6.5% of cells

One village per 32-chunk grid at most. Each has three to six houses, one villager for each of 13 professions, an iron golem, a farm plot and a loot chest. Beds are real points of interest, with two beds per house leaving capacity for children instead of treating the house itself as population capacity.

House generation has a practical detail:

// A structure foundation must flatten natural caves and bumps,
// or the same seed produces a house with a missing corner.
if (getBlock(x, y, z)) put(x, y, z, null);
put(x, y, z, "planks");

Clear the foundation, then lay the floor. If a cave happens to be underneath, the house still has all four corners. Structure generation is most fragile when the seed is fixed but the terrain boundary conditions are not. Flattening the foundation is what makes snapshot regression possible.

The list runs to 17: mineshafts, nether fortresses, end cities, ocean monuments, woodland mansions, ancient cities, trial chambers, desert temples, jungle temples, igloos, pillager outposts, ruined portals, shipwrecks, abandoned mineshafts and end ships. All of them share one pattern: position comes from the seed, layout from local randomness, loot from STRUCTURE_LOOT.

Structure positions also get a cache:

const cacheKey = seed + ':' + type;
if (structureCenterCache.has(cacheKey)) return { ...structureCenterCache.get(cacheKey) };

Each world and structure type is located once, then shared by every chunk. That matters. If every chunk recomputed "where is the nearest village", structure lookup would go from milliseconds to seconds.

Cross-chunk structures are the other problem. A house bounding box can span four chunks, and each chunk has to decide which part it builds. structureIntersects(type, minX, maxX, minZ, maxZ) handles the bounding-box test, and coordinates are clipped inside the chunk. Whichever chunk loads first, the assembled house is the same.

This is exactly why world-generation-v1.json exists. Structure generation has no runtime state, only seed and coordinates. If the snapshot is unchanged, no village moved by accident.

On seed 1337, all 17 structure types locate successfully, in 1.9 to 3.7 ms per pass. Location is not the bottleneck. Filling blocks and building meshes is.

Lighting: one byte for sky light and torch light

Each chunk owns a Uint8Array(16 * 16 * 251) light array, 64,256 bytes. One byte is split in half:

high 4 bits: sky light 0-15
low 4 bits:  torch light 0-15

setLight() writes with bit operations:

chunk.light[index] = (sky !== null ? (sky << 4) : (cell & 0xF0))
                   | (torch !== null ? torch : (cell & 0x0F));

Sky light scans top-down:

  • From MAX_Y downward, an opaque block drops the level to zero.
  • Water attenuates by 2 per block, other transparent blocks by 1.
  • Air keeps the current level.

This simplified model does not spread sky light horizontally, so cave mouths are less subtle than the original game. It is cheap: a chunk is a fixed 64,256 operations.

Torch light is a BFS. Each source starts at 14, spreads in six directions, stops at opaque blocks, and does not enqueue a cell that is already brighter:

const existing = lightAt(nx, ny, nz) & 0x0F;
if (existing >= current.l - 1) continue;
setLight(nx, ny, nz, null, current.l - 1);
queue.push({ x: nx, y: ny, z: nz, l: current.l - 1 });

At render time, each instance color comes from the light array:

brightness = max(1, min(15, round(sky * min(1, daylight + 0.2))), torch)
base       = brightness * 3
color      = LIGHT_RAMP[base..base+2]
variation  = 0.94 + hash(x * 3 + y, z * 5) * 0.1
ao         = 1 - min(0.24, blockedNeighbors * 0.045)
final      = color * variation * ao

LIGHT_RAMP is a precomputed 16-step color table, so no pow call runs per frame. At night a readability floor is applied:

const readableFloor = 0.36 + daylight * 0.16;

This is not physically correct lighting. It is a product decision: at night the silhouette still has to be readable. Fully correct nights in voxel games are usually too dark, and players turn up gamma. Better to raise the floor in the renderer.

Rendering: buried-block culling and InstancedMesh

The expensive part of rendering is not triangles. It is draw calls. A chunk has tens of thousands of blocks. One Mesh per block would kill the browser before the GPU sees anything.

The code buckets by block type and state signature:

const bucketKey = type + '|' + stateSignature(type, state);

Each bucket becomes an InstancedMesh. All blocks of the same type and state share geometry and material and only pass instance matrices. Draw calls per chunk equal the number of distinct type and state combinations, usually a handful to a few dozen.

Before bucketing, buried blocks are culled:

const buried = occludesBlockFace(type, x, y, z, x+1, y, z) &&
               occludesBlockFace(type, x, y, z, x-1, y, z) &&
               occludesBlockFace(type, x, y, z, x, y+1, z) &&
               occludesBlockFace(type, x, y, z, x, y-1, z) &&
               occludesBlockFace(type, x, y, z, x, y, z+1) &&
               occludesBlockFace(type, x, y, z, x, y, z-1);
if (!buried) { /* add to bucket */ }

An underground block with all six faces hidden is not rendered. This cuts 60 to 80 percent of instances underground, especially around deep caves.

Several performance switches matter:

  • mesh.instanceMatrix.setUsage(THREE.StaticDrawUsage), because block positions rarely change, so the driver does less synchronization.
  • Shadows only for blocks within one chunk of the player, and never for water, leaves or plants.
  • Shadow receiving only within two chunks.
  • Water is separate: water body, water surface and foam are three InstancedMeshes with renderOrder 1, 2 and 3.
  • Torches use a scaled matrix instead of a separate model.
  • Crops change height by growth stage instead of swapping geometry.

Water has one more detail. A surface mesh is only created where the block above is not water, and foam only where a solid neighbor touches the water. Without that, every water cell would stack a transparent face and transparent sorting would get much worse.

Geometry and materials are reused by type. getBlockGeometry(type, state) caches one geometry for combinations such as "stairs facing north, top half, not waterlogged", and materials[type] reuses one material per block type. The README says 250 of the 528 blocks use procedural textures, and the repository also ships common-blocks.png as a base atlas. Procedural textures avoid one image per variant, but the first generation costs CPU, so caching is mandatory.

This also explains why the state signature participates in bucketing. Two stairs differ in instance matrix but can share geometry. Top and bottom slabs need different geometry offsets. Folding state into bucketKey balances draw-call reduction against geometry reuse.

Physics and feel: 1.6 tall, 0.10 radius, 6 block reach

All player parameters live in constants.js:

PLAYER_HEIGHT = 1.6;
PLAYER_RADIUS = 0.10;
EYE_HEIGHT = 1.43;
REACH = 6;
CAMERA_FOV = 56;
THIRD_PERSON_DISTANCE = 3.8;
MOUSE_LOOK_SENSITIVITY = 0.0015;
TOUCH_LOOK_SENSITIVITY = 0.0055;

A radius of 0.10 is much narrower than the original game's roughly 0.3. That is a deliberate feel trade-off: a narrow radius makes it easier to squeeze through a one-block gap and reduces "it looks passable but I am stuck". The cost is a higher chance of clipping when hugging a wall, so collision cannot test only the center point. It has to test the four corners of the AABB.

Movement is four steps: input, desired velocity, collision resolution, grounded check. Water, ladders, cobwebs and ice each change acceleration and friction. The third-person camera follows at a speed of 14 with damping, so turning does not snap the camera.

REACH = 6 sets block interaction distance. Mining, placing, opening doors, lighting fires, feeding animals and trading all validate against it, which blocks "operate through walls".

Block updates: a 4,096-event priority queue

A voxel world has many things that need to happen later: water flows, fire burns, crops grow, repeaters delay, pistons push, observers pulse. Iterating the whole world every frame is not an option, so there is one event queue.

An event looks like:

{ x, y, z, type, due, priority, sequence, dedupeKey, payload }

Ordering is due time, then priority, then insertion order:

function compareEvents(a, b) {
  return a.due - b.due || b.priority - a.priority || a.sequence - b.sequence;
}

dedupeKey merges duplicate events for the same cell. Pouring water repeatedly does not need a hundred fluid updates; one is enough. A later event that is no earlier than an existing one is dropped.

tick(dt, { budget }) processes at most 4,096 events per frame:

  • Due events in loaded chunks enter the heap.
  • Events outside the loaded range count as inactive, kept but not processed.
  • It returns processed, processedByType, inactive, remaining and saturated.
  • saturated = true means the budget was hit and the next frame continues.

The value of this design is observability. If a redstone circuit jams, the log shows remaining not falling and saturated stuck at true. The diagnosis is "events are produced faster than consumed", not "the game froze for no reason".

Delays are not arbitrary. setBlock() schedules the next tick by type:

TypeDelayPurpose
Crop6.5 sGrowth stage
Water0.4 sFlow
Lava1.2 sFlow, slower
Fire0.5 sSpread and extinguish
Sapling, growable, farmland2 sEcology update

These delays, along with randomTickSpeed = 3 and simulationDistance = 4, are stored in the save. Change a setting and the save remembers it. Open the world on another machine and the rhythm is the same. For a single-player game this is much simpler than server authority, though it also means editing a local file can change random tick speed. A single-player game does not need anti-cheat.

Redstone: signal, delay and pistons

Redstone is the easiest system to lose control of, because it is graph computation with feedback and clocks.

Block World 3D recomputes dirty regions every frame. It is not an event-driven circuit solver:

  • Dust carries strength 0 to 15 and decrements by 1 per BFS step.
  • A repeater delays (configured + 1) * 0.1 seconds, where configured is 1 to 4, so 0.2 to 0.5 seconds.
  • A comparator supports compare and subtract.
  • A torch is an inverter: input on, output off.
  • An observer watches block state changes and emits a pulse.
  • A piston collects the blocks to push, then moves them together, up to 12 blocks in collectPistonMove.
  • A target block outputs 15 when hit by an arrow or projectile.

Signal propagation uses propagateDust(seeds). Every current source, including levers, buttons, torches, pressure plates and comparator outputs, becomes a seed. BFS spreads the signal and updates any cell that becomes stronger. Each frame recomputes only dirty regions, not the whole graph.

The hard part is not signal. It is ordering. Two repeaters pointing at each other: which updates first? The blockUpdateQueue uses due time and sequence to make same-frame events deterministic. Across frames, the configured delay decides. That makes circuits reproducible and lets clock circuits oscillate reliably.

It is still incomplete. There is no full TNT, pressure plate, tripwire or dropper system. Hoppers only point down. Pistons do not move entities. The gaps section covers this.

Mobs: A* with 900 nodes and 60 creature types

Creatures split into two data-driven groups: 40 hostile types and 20 animals.

const HOSTILE_TYPES = { zombie: {...}, skeleton: {...}, creeper: {...}, ... };
const ANIMAL_TYPES  = { cow: {...}, sheep: {...}, wolf: {...}, ... };

Spawn rules check five conditions: dimension, biome, light, height and weather. mobSpawnRules.js turns them into query functions, and canMobSpawn() runs on random ticks.

Pathfinding is a restrained A*:

function manhattan(a, b) {
  return Math.abs(a.x - b.x) + Math.abs(a.z - b.z) + Math.abs(a.y - b.y) * 1.25;
}
  • Four cardinal directions, no diagonals.
  • Each step allows one block up or up to two blocks down.
  • Up costs 0.6; each block down costs 0.18.
  • maxNodes = 900, maxDistance = 32, configurable goalTolerance.
  • It returns the closest node, not necessarily an exact arrival, so a mob that cannot reach the target stops nearby instead of giving up immediately.

On a flat synthetic world, 5,000 paths of about 20 blocks averaged 23.5 path nodes, 0.05 to 0.06 ms per path, or 16,000 to 20,000 paths per second. Real terrain expands more nodes, but the order of magnitude says per-frame pathfinding for a handful of mobs is affordable.

Villagers are a different system: 13 professions, five trade levels, demand and restocking, point-of-interest workstations, schedules, breeding, bell shelters, raids and iron golems. It behaves more like an economy than an AI.

There are two bosses: the ender dragon, with circling, perching, diving, breath and crystal healing phases, and the wither, summoned from soul sand and wither skeleton skulls, with ranged and armored phases and the wither effect. The wither's full phase loop is still incomplete, as noted later.

Saves: v6, 15 seconds, D1 sharding

Saving has three layers.

The first is the world snapshot:

{
  schemaVersion: 6,
  world: { id, name, seed, gameTime, difficulty, randomTickSpeed, simulationDistance },
  player: { position, yaw, pitch, health, hunger, inventory, stats, advancements, deathHistory, ... },
  dimensions: {
    overworld: { chunks: [...], entities: [...], redstone: {...} },
    nether: {...},
    end: {...}
  }
}

The second is chunk edits. The save does not store the whole world, only blocks the player changed:

{ x, y, z, type, state?, level? }

Chunk generation runs from the seed first, then applies the edits. This is what makes an infinite world storable. Otherwise a world you have walked across is hundreds of megabytes.

The third is runtime entities. Hostile mobs, animals, villagers, golems, dropped items, experience orbs and minecarts all serialize per dimension and rebuild on load.

Version migration is explicit. SAVE_SCHEMA_VERSION = 6, MIN_SUPPORTED_SAVE_SCHEMA_VERSION = 1, and migrations run step by step:

if (sourceVersion === 1) { /* lift dimensions, add offhand */ }
if (sourceVersion <= 2) { /* add effects, unlocked recipes, beacon effect */ }
if (sourceVersion <= 3) { /* add world.difficulty */ }
if (sourceVersion <= 4) { /* add random tick speed, simulation distance, spawn dimension, scheduled ticks */ }
if (sourceVersion <= 5) { /* add stats, advancements, death history */ }
snapshot.schemaVersion = SAVE_SCHEMA_VERSION;

Unknown versions throw:

if (sourceVersion > SAVE_SCHEMA_VERSION) {
  throw new RangeError('Save schema ' + sourceVersion + ' is newer than supported schema ' + SAVE_SCHEMA_VERSION);
}

Rejecting a future version matters more than supporting it. An old client reading a new save should refuse, not guess fields.

Local saves use Electron plus node:sqlite, isolated per world. Autosave runs every 15 seconds, and also on exit, dimension switch and world reset. Cloud saves use Cloudflare Pages Functions plus D1:

worlds              world metadata + snapshot_json
users               account + PBKDF2 hash + salt + owner_id
world_dimensions    state JSON per dimension
world_chunks        edits JSON per chunk
world_entities      entity state per entity

The cloud does not store one giant JSON. Dimensions, chunks and entities are separate rows, so a save can batch 75 statements at a time and a load can fetch only the current dimension's chunks. The player core snapshot has a 500 KB cap. Over the cap, the save fails loudly instead of truncating silently.

The relationship between local and cloud is "same snapshot, two stores", not "live sync". desktop.worlds.save() writes to the current device, SQLite or cloud D1, every 15 seconds. The cloud updates rows by owner_id + world_id, with no version vector and no conflict merge. If two devices play the same world, the later save wins. For a single-player game that is acceptable, but it is not collaborative editing. The world menu offers JSON export, copy, rename and delete. Backup is delegated to the user, not hidden behind a version history.

Autosave also leaves a window: kill the process and you lose up to 15 seconds. Switching dimensions, leaving the world and resetting it trigger extra saves, so normal play does not lose progress. Task Manager does. That is the same trade most single-player games make: a fixed interval for low overhead, instead of writing on every block change.

Measurements: about 5 ms per chunk

To avoid tuning by feel, I ran the real modules from the repository. The environment was Windows with Node 24.18.0. The script imports terrain.js, generation.js, ecology.js, catalog.js, entities.js, pathfinding.js and save-schema.js directly. No implementation was changed.

The method needs a note first. Wall-clock time on Windows can double with background load, so the script measures process CPU time with process.cpuUsage(). The scheduler tick is about 15 ms, so anything smaller is repeated dozens to thousands of times and divided. Even then, the same script varies by 20 to 50 percent across runs. The numbers below are ranges, not promises to two decimal places.

Terrain sampling:

StepSamplesCPU timeThroughput

Step 16 is fast because 4,225 samples fit entirely inside the 16,384-entry router cache. Step 4 has 66,049 points, clears the cache repeatedly, and the per-point cost rises. Each point includes heightAt + biomeAt. Add the five internal height samples inside terrainSlopeAt and the real per-point cost is higher. That is why "200,000 terrain samples per second" cannot be converted directly into "200,000 blocks per second". Chunk generation also handles caves, ore, trees and structures.

Each chunk has 784 sample points, 28 by 28, and each point does a height, biome and slope query. Radius 4 takes 0.39 to 0.48 seconds for 81 chunks. Per-chunk cost rises slightly with radius for the same cache reason: 63,504 samples exceed the 16,384 limit and force repeated full clears.

That 80 bytes per entry deserves emphasis. At 81 chunks and roughly 23,000 entries per chunk, the total is about 1.86 million entries, or 149 MB by this ratio. Add light arrays at 64 KB per chunk, about 5.2 MB for 81 chunks, plus meshes, entities, materials and Three.js objects, and a loaded world sits in the hundreds of megabytes. The heapGrowthMb = 20 budget only limits growth after eight moves. It is not total memory.

These numbers do not include Three.js rendering, the browser event loop, GPU uploads or actual save I/O. A* runs on a flat synthetic world; real terrain expands more nodes. Structure lookup measures "compute the position", not "build the house". They are useful for answering "which layer is the bottleneck", not for promising a frame rate. The conclusion is clear: terrain prep is milliseconds. Block filling and mesh building are the parts that need more work. And at 149 MB for the block Map, the real ceiling may be memory, not CPU.

38 test suites and a performance budget

The repository contains 38 test-* files covering:

  • Terrain and generation: test-terrain, test-generation-snapshots, test-ecology, test-structures.
  • Block rules: test-blocks, test-block-rules, test-building-families, test-building-visual.
  • Survival: test-progression, test-player-experience, test-difficulty, test-furnace, test-container-transfer.
  • Redstone: test-redstone, test-redstone-devices, test-redstone-e2e.
  • Mobs: test-mobs, test-mob-behavior, test-mob-spawn-rules, test-pathfinding, test-mob-navigation.
  • Exploration and completion: test-exploration-e2e, test-completion-e2e.
  • Saves: test-persistence, test-save-migrations, test-sqlite, test-cloud-api.
  • Performance and desktop: test-performance, test-electron.

Two design choices are worth copying.

First, generation snapshots. tools/snapshots/world-generation-v1.json stores terrain output for a fixed seed. After a generator change, compare against the snapshot to see immediately whether a biome boundary moved. Procedural generation is exactly the kind of system where "it looks about right" hides regressions. Snapshot regression is the only reliable defense.

Second, budgets written as JSON:

{
  "budgets": {
    "worldReadyMs": 15000,
    "chunkMoveP95Ms": 4000,
    "frameMedianMs": 34,
    "frameP95Ms": 100,
    "heapGrowthMb": 20,
    "maxLoadedChunks": 25
  }
}

frameMedianMs = 34 corresponds to roughly 30 FPS median frame time. frameP95Ms = 100 allows occasional hitches. chunkMoveP95Ms = 4000 is a worst-case bound: moving one chunk must not exceed four seconds at P95. That sounds generous, but it constrains the worst case, not the average feel. Putting budgets in the repository gives CI something to compare against. Otherwise "performance work" stays a slogan.

Six things still incomplete

One: redstone is simplified. There is no full TNT, pressure plate, tripwire or dropper system. Hoppers only point down. Pistons ignore entities. Comparator container signals cover only some containers. You can build circuits, but not the large machines of the original game.

Two: enchanting and brewing are cut down. Only 14 enchantments exist, with simplified conflict and probability rules. Brewing has four basic chains, without splash, lingering or upgraded potions. The loom, cauldron, grindstone and fletching table are villager workstations with appearance but incomplete function.

Three: the wither has no complete phase loop. It can be summoned and has ranged, armored and wither phases, but it lacks the original's full "armor plus minion summons at half health" rhythm.

Four: no creative, spectator, hardcore or commands. Only the survival loop exists. For players who want to "just build something", that is a hard gap.

Five: string keys cost memory. At 80 bytes per entry, 81 chunks approach 150 MB. Switching to one typed array per chunk plus a palette would cut it significantly, but it would complicate sparse worlds and edit persistence. This is a deliberate trade, not a bug.

Six: the cloud save schema lags the client by two versions. The client has SAVE_SCHEMA_VERSION = 6; the cloud has SCHEMA_VERSION = 4. On write it labels the snapshot as v4, and on read it runs the v4 to v6 migration. Because migrations only add fields and never delete them, it works. But "cloud save format" and "local save format" are not the same thing, and that gets more awkward over time. The cloud PBKDF2 also uses only 10,000 iterations, not the 120,000 used by the main site.

Two more boundaries are not defects but must be known. The browser build only shows the entry screen; full gameplay requires the Electron desktop app. The README badges, 479 blocks and 325 recipes, are behind the code at 528 and 332.

Closing

The interesting part of Block World 3D is not that it resembles Minecraft. It is that it turns five hard voxel problems into inspectable code:

  • World: a string-keyed Map plus sparse edits, trading memory for debuggability and simple saves.
  • Terrain: seven noise layers, climate targets, caves, rivers and ore veins. The 34 biomes are not hard-coded shapes.
  • Chunks: 28 by 28 Worker sampling at about 5 ms per chunk, with the main thread only filling and batching.
  • Lighting: one byte for sky and torch light, a 16-step color ramp, ambient occlusion and a night readability floor.
  • Rendering: buried-block culling plus InstancedMesh, taking draw calls from tens of thousands to dozens.
  • Simulation: a 4,096-event priority queue shared by redstone, fluids, crops and random ticks.
  • Saves: edits only, v1 to v6 migrations, future versions rejected, D1 rows split by dimension, chunk and entity.

The gaps are equally clear: incomplete redstone, missing game modes, heavy memory, and a drifting cloud schema. These are not "later" TODOs. They are the current boundaries of the implementation.

If you want to build a voxel world with Three.js, the first things to copy are not the renderer. Copy these three: put terrain in a Worker, save only block edits, and write performance budgets into a file. The first two decide whether it runs. The third decides whether you still know, six months later, that it got slower.

The hard part of a voxel world has never been drawing a block. It is making a million blocks appear, disappear, brighten and flow at the right moment, and still be in the same place the next time you open the world.
