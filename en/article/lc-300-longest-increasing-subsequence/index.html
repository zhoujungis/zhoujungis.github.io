LC 300, longest increasing subsequence: anchor the state, then change the anchor

2026-09-30 · 14 min · Stack Frame

The problem

Return the length of the longest strictly increasing subsequence.

[10,9,2,5,3,7,101,18]  ->  4    ([2,3,7,101] or [2,3,7,18])

Subsequences may skip elements as long as order is preserved, so whether to take an element depends on what was taken before. That is a combinatorial problem and not greedy, since the locally longest chain does not always extend to the globally longest.

Anchor the state

The breakthrough is one move: anchor the state on the ending index. Define the length of the longest increasing subsequence ending at each position. With that anchor, the question becomes which predecessor to attach to, because an increasing subsequence ending here, with its last element removed, is an increasing subsequence ending at some earlier position. The subproblem has exactly the same shape, only smaller.

Two misconceptions to clear. Defining the state as the best within the first i elements fails, because that best may not end at i, so extending it with the next element is undefined; the anchor must be the ending position. And it is safe to look only at the endpoint, because increasing-ness acts only between adjacent elements, so deciding whether an attachment is legal requires comparing the new value with the last one and nothing else.

This is the same move as in the maximum subarray problem, whose state is also anchored on the ending index. It is the most useful anchor for subsequence and subarray problems.

The recurrence

def lengthOfLIS(nums):
    n = len(nums)
    if n == 0:
        return 0
    dp = [1] * n
    for i in range(n):
        for j in range(i):
            if nums[j] < nums[i] and dp[j] + 1 > dp[i]:
                dp[i] = dp[j] + 1
    return max(dp)

Three points. The initial value is one, because each element alone is a subsequence of length one, and zero would make a descending array return zero. The inner loop looks back at everything rather than stopping at the first legal predecessor, since a longer chain may hide further back. And the answer is the maximum over the row rather than the last entry, because the longest chain need not end at the final element, which is the biggest trap in the problem and one the official sample does not expose.

When one hundred one arrives, all six previous elements are legal and the value climbs to four. Two rows share the same predecessor and the same length, which shows why this is faster than enumerating subsequences: each anchored optimum is computed once and then looked up by every later index that can attach to it.

The advanced version

The quadratic class comes from the anchor itself: there are n possible endings, and finding who can attach to a new value requires scanning back. To use binary search, change the bookkeeping to be indexed by length instead.

tails[len] = the smallest possible tail among all increasing
             subsequences of length len + 1

That array is strictly increasing, by a short contradiction: if a larger length had a smaller or equal tail, truncating that subsequence to the shorter length would produce a tail below the recorded minimum. Being strictly increasing, it supports a binary search for the first position with a value at least as large as the new element.

If that position is inside the array, replace the entry: the tail for that length becomes smaller, which is strictly better for future attachments and does not change the length. If the position is past the end, the new element is larger than every recorded tail, so append it and the answer grows, which is the only operation that can increase the answer.

from bisect import bisect_left

def lengthOfLIS(nums):
    tails = []
    for x in nums:
        pos = bisect_left(tails, x)
        if pos == len(tails):
            tails.append(x)
        else:
            tails[pos] = x
    return len(tails)

The hand-written binary search is a dozen lines and is often required, since it also proves the candidate understands lower bound semantics: the high bound starts at the array length because appending must be representable, and the midpoint rounds down so that the loop cannot fail to shrink.

An important clarification: the array is not the subsequence. After the sample it holds the four values of a different chain than the true answer, because a later replacement overwrote content. Only its length is reliable.

To reconstruct an actual subsequence, go back to the quadratic version and record parents.

Java

public int lengthOfLIS(int[] nums) {
    int n = nums.length;
    int[] dp = new int[n];
    int best = 0;
    for (int i = 0; i < n; i++) {
        dp[i] = 1;
        for (int j = 0; j < i; j++) {
            if (nums[j] < nums[i] && dp[j] + 1 > dp[i]) {
                dp[i] = dp[j] + 1;
            }
        }
        best = Math.max(best, dp[i]);
    }
    return best;
}

public int lengthOfLISFast(int[] nums) {
    int[] tails = new int[nums.length];
    int size = 0;
    for (int x : nums) {
        int lo = 0, hi = size;
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (tails[mid] < x) lo = mid + 1;
            else hi = mid;
        }
        tails[lo] = x;
        if (lo == size) size++;
    }
    return size;
}

Using the library binary search is a poor substitute, since on a hit it returns an arbitrary matching index rather than the leftmost, and the negative return value then needs conversion. The hand-written loop is shorter and more predictable.

Complexity

The quadratic version is time quadratic and space linear, the latter doubled if parents are kept for reconstruction. The tails version is linearithmic and linear, since each element costs one binary search over at most n entries.

Each compression gives up information: brute force over all subsequences is exponential, the anchored DP turns enumeration into lookup, and the tails version turns the backward scan into a search while losing the identity of the chain. Offer the quadratic version with a proper explanation of the definition first, then upgrade; the order matters.

Common mistakes

  1. Returning the last entry, which the official sample does not expose. Self-test on a case where the longest chain is not at the end.
  2. Using the strict-increasing binary search for a non-decreasing problem, or the reverse. On equal elements the wrong choice either overcounts or undercounts.
  3. Defining the state as the best in the prefix, which makes the recurrence unwritable.
  4. Initialising to zero, which returns zero for a descending array, or forgetting the empty guard before taking the maximum.
  5. Treating the tails array as the answer subsequence, whose contents are overwritten.
  6. Getting the hand-written binary search boundaries wrong, which loops forever or misses the append case.

How to answer it

Give the quadratic version with the anchor explained, then point out the sample blind spot, since that sentence separates memorisation from work. Then the upgrade, phrased as changing the anchor: record by length the smallest tail per length, use strict monotonicity to binary search, and return the length. Then the clarification that the array is not the subsequence, and finally the variants: non-decreasing needs the right-hand search, counting distinct longest subsequences needs a counter array, sorting by one dimension reduces the two-dimensional version to this one, and the longest common subsequence is a relative.

Closing

State definition decides everything here. The first question tests whether you dare anchor the state on the ending index, at which point the recurrence grows by itself. The second tests whether you dare abandon that anchor for one indexed by length, at which point binary search becomes available. Two breakthroughs, in opposite directions: first pin the state down, then loosen it. The earlier maximum subarray problem used the first; this one collects both.
