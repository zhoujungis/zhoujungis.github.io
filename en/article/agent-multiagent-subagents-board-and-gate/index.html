Multi-agent: sub-agents, the task board and the gate

2026-11-04 · 36 min · Stack Frame

Who this is for: people whose single agent works and who now want it to work in parallel; people who have been burned by four sub-agents editing the same file; people who want to know who should own the task board and the rate gate.

TL;DR: the hard part of multi-agent is never parallelism, it is responsibility. The task board, the gate and the tool context are shared; prompts, message histories and model choice are per agent. NanoHermes cuts those two groups cleanly, and leaves three holes: nesting prevention filters the tool list but not execution, the gate checks neither interrupts nor reentrancy, and the board never clears across sessions.

Multi-agent is not the main loop copied four times

The intuition is: one loop works, so run four. That is easy to code, four threads each with a message history, calling tools, then collecting results. It runs into three problems immediately.

  • Four sub-agents each call edit_file on the same file. Whose change counts?
  • Each wants to print progress, and the output interleaves into garbage.
  • If each sub-agent can spawn another, what stops exponential growth?

None of those is a parallelism problem. They are distribution problems: which things should be shared and which must stay individual. The file conflict shares a filesystem. The garbled output shares stdout. The explosion shares the ability to delegate without sharing a quota.

NanoHermes splits multi-agent into three pieces: the sub-agent definition, which is a configuration contract; the task board, which is shared observability state; and the gate, which is a resource quota. The first two together are under two hundred lines and the third is thirty. This post walks individual, then shared, then quota, and then takes apart the three places where the cut was not clean.

Sharing itself is right. Independent todo lists would show the user five unrelated plans, and independent task tables would turn task_kill into a lottery. The price of sharing is that a sub-agent can damage state, not just files.

A simple test for whether a multi-agent design is healthy: can a sub-agent corrupt the parent's state? If yes, that state should split into read-only shared and writable individual, or at minimum carry an owner marker.

What a sub-agent is

pub struct SubAgentDef {
    pub name: String,
    pub prompt: String,
    /// If non-empty, only these tools are available to the sub-agent.
    pub allowed_tools: Vec<String>,
    /// Optional model override for this sub-agent.
    pub model: Option<String>,
}

Restrained: a sub-agent gets no independent iteration cap, permission mode, approval policy or sandbox setting. All inherited. The benefit is simple configuration; the cost is that the abstraction is much weaker than it looks. A sub-agent is the same Agent with a different prompt, a different tool list and possibly a different model. It is not a new role under independent constraints.

allowed_tools deserves precision. The comment says only those tools are available, and the implementation applies it to the tool list shown to the model, not to the execution-time permission check.

model deserves the same precision. It changes the model name sent to the API and nothing else: not max_tokens, not temperature, not the timeout. So "run sub-agents on a cheap model to save money" holds, and "use a small model to cap a sub-agent's output length" does not, since that would need max_tokens, which is not exposed.

Configuration as contract

{
  "subagents": {
    "reviewer": {
      "prompt": "You review Rust code for correctness and security. Read the diff, then list concrete defects with file:line.",
      "allowed_tools": ["read_file", "list_dir", "grep", "glob", "git_diff"],
      "model": "gpt-4o"
    },
    "verifier": {
      "prompt": "You run the test suite and report failures. Never modify source files.",
      "allowed_tools": ["run_command", "read_file"]
    }
  }
}

prompt is required, and a missing one fails the whole load.

allowed_tools omitted means everything is granted. The empty vector is interpreted at the trimming step as "no restriction", so a definition with only a prompt arrives with the parent's full capability. Same direction as the empty allow list in the security post: safe in the fail-closed sense, surprising in every other sense.

A load failure only warns. A stray comma in the JSON means "no sub-agents" rather than "startup failed". Since build_tools then hides the subagent tool when the list is empty, the model never sees it and the user concludes the agent does not delegate, while the real cause appears once in a stderr line nobody reads.

Lookup by name, and no discoverability

let def = self
    .cfg
    .subagents
    .iter()
    .find(|s| s.name == name)
    .ok_or_else(|| format!("unknown sub-agent `{name}`"))?;

The failure path is useful: the error lands on the board as failed with the message as a preview, so the model can discover its own mistake.

But there is a blind spot: no discoverability input. In the tool schema, name is a plain string with no enum and no examples, and the system prompt never lists sub-agent names, since prompt.rs only assembles mode notes, persona and AGENTS.md. The names are invisible to the model.

In practice the user has to hard-code the roster in their persona, or the model guesses, and a wrong guess costs a full round trip before it learns.

How the sub-agent tool list is trimmed

// 1. start from the parent's full list, already filtered by mode and lists
let all_tools = self.build_tools();
// 2. if the definition declares a whitelist, filter by name
let tool_list: Vec<Value> = if !def.allowed_tools.is_empty() {
    all_tools.as_array().cloned().unwrap_or_default()
        .into_iter()
        .filter(|t| {
            let tname = /* ... name ... */;
            def.allowed_tools.iter().any(|a| a == tname)
        })
        .collect()
} else {
    all_tools.as_array().cloned().unwrap_or_default()
};
// 3. remove `subagent` itself, to prevent unbounded nesting
let tool_list: Vec<Value> = tool_list.into_iter()
    .filter(|t| /* name */ != Some("subagent"))
    .collect();

Step one is the important one: a sub-agent's tool list is a subset of the parent's. The five gates from the security post still apply, so a sub-agent under plan mode cannot write either. That is much safer than giving sub-agents independent permissions, because it guarantees a sub-agent cannot be more capable than its parent.

Step two is exact string matching with no wildcards. "read_*" matches nothing. That contrasts with the hook matcher, which does support wildcards, in the same configuration system.

Step three removes subagent by name, which works for its stated goal and only for that goal.

One easily missed point: agent_list is not removed. A sub-agent can read every job on the board, including the parent's and its siblings' result previews. Good for shared context, bad for isolation: a review sub-agent limited to read_file can still read another sub-agent's 500 character result summary, so allowed_tools has an unadvertised side door.

Nesting prevention blocks advertising, not execution

The comment on that filter is explicit about preventing unbounded nesting, and it does prevent the common path: a sub-agent cannot see the tool, so it does not call it.

if let Err(reason) = self.cfg.check_tool(&call.name) { return format!("ERROR: {reason}"); }

check_tool looks at the mode list, the deny list and a non-empty allow list. subagent appears in none of them, so nothing rejects it at execution time. Rejection only ever happened at "the model cannot see it".

So one tool call naming subagent opens the path, because the dispatch branch is a plain string comparison.

Where would such a call come from? A hallucinated name is possible, since the parent's context taught the model the name. A restored session that contains earlier subagent calls is more plausible: replace_messages can load a history where the model has used the tool before. Explicit instructions to call unlisted tools do not work, models do not follow them.

So the accurate statement is that nesting prevention is a filter on advertising, not a gate at execution. Making it a gate means adding a rule in check_tool for sub-agent contexts, or adding a depth counter to Ctx and asserting it at the entry. The second is stronger, since it also bounds depth rather than forbidding it outright.

Why sub-agents are serial inside

for _ in 0..sub_cfg.max_iterations {
    let turn = llm::chat(&sub_cfg, &messages, &tools, |_| {})?;
    result = turn.content.clone();
    messages.push(assistant_message(&turn));
    if turn.tool_calls.is_empty() { break; }
    // Execute sub-agent tool calls sequentially (sub-agents are bounded).
    for call in &turn.tool_calls {
        let out = self.execute(call);
        messages.push(json!({ "role": "tool", "tool_call_id": call.id, "content": out }));
    }
}

The stated reason is that the count is already bounded at four, and adding inner parallelism would raise the real concurrency to four times N, which distorts what the gate means.

But it conflicts with something from the concurrency post: the parent parallelizes tool calls with a scope, the sub-agent is serial, so the same execute runs under two different orchestration strategies. The same-file lost-update defect disappears inside a sub-agent, since serial code cannot conflict with itself, and remains between four parallel sub-agents that each run serially and finally write the same file.

Serial only removes conflicts within one layer, never across layers. What is needed is a file lock, or a scheduling rule that forbids two sub-agents writing one file.

A subtler difference: the sub-agent loop never calls compact(). The parent compacts after every turn; a sub-agent can run all 40 iterations without compacting. Forty rounds times up to 20,000 characters of tool result is close to 800,000 characters in a local vector whose budget is meant to be 120,000. The sub-agent has no budget of its own and does not borrow the parent's.

Execution-time permission checks use self.cfg, not sub_cfg. If the parent has an allow list of read_file and grep, every sub-agent call is judged against it, including tools the definition explicitly granted. Inversely, if the parent's list is empty, which is the default, def.allowed_tools takes no part in execution checks at all.

So the definition's list is advertising, and the parent's list is what binds. The combined effect is an intersection that only tightens when the parent is tightened. To make a sub-agent read-only in practice, you rely on it not seeing write tools. To guarantee it cannot write, you have to tighten check_tool itself.

No memory injection, no memory distillation

let mut messages: Vec<Value> = vec![
    json!({ "role": "system", "content": def.prompt }),
    json!({ "role": "user", "content": task }),
];

Two hand-built messages. The parent re-retrieves memory every turn and replaces the injected block; a sub-agent never does. Its whole world is its prompt, the task description and its own tool results. It does not know the user's preferences or the repository's conventions.

Two consequences. The task description must be self-contained, because "do it the way we discussed" means nothing to an agent with no "discussed". And the task string itself has no length check, since clamp applies to tool output, not inputs. A 10,000 character task goes into the first request verbatim.

And sub-agent work never becomes memory. Distillation runs only at the end of the parent's run(). That is right, because four sub-agents would otherwise write four near-duplicate records that the 12-byte dedupe threshold cannot merge. The cost is that if a sub-agent is the only one that saw a key conclusion, it exists only in the text it returned, and the parent may lose details while paraphrasing.

Shared Ctx: three neglected side effects

Everything in Ctx is shared, because sub-agents execute through self.execute and there is one self.ctx. Three side effects follow.

Todos are overwritten. todo_write replaces the whole list, so a sub-agent writing its own three-step plan erases the parent's five-step plan. The 50 item cap does not help, since it governs replacement, not appending. Letting sub-agents plan is unsafe without an owner field and per-owner filtering.

Background tasks can be killed. The task manager is one field in Ctx, so a sub-agent's task_kill can stop a service the parent started, and task_list shows it jobs it never spawned. The security post noted that a tool name is not a capability boundary; here is the multi-agent version: "who started this task" is not recorded, so no layer can enforce it.

The memory directory is shared. A sub-agent can write into the parent's memory store, and if its prompt says to save important facts, it will, with nothing recording which sub-agent wrote it. Facts are retrievable across sessions, so one wrong fact from a sub-agent pollutes every later conversation.

All three have the same fix: give shared state an owner, then filter by the current role at the tool layer. Small change, but it requires admitting that sharing has a price.

The board is append-only

pub struct Board {
    jobs: Mutex<Vec<Job>>,
    seq: Mutex<u64>,
}

A job carries id, name, task, status, result, duration and a private start instant. Three design points.

The start instant is private and the duration is public. External readers know how long something ran and not when. That avoids clock confusion and also means the board cannot answer "did these two overlap": there is ordering and duration, but no intervals.

Three statuses only: running, done, failed. No cancelled, no queued, no timed out. The absence of queued is a real problem, since a job waiting for a permit is displayed as running.

Append only. No remove, no clear, no capacity. The vector grows and the sequence grows.

finish looks up by id and returns silently when not found, which is safe only because ids come from start and cannot appear from nowhere. Add board cleanup later and that silence becomes "jobs stuck at running forever". Append-only and silent-finish are a pair that must stay true together.

Task ids are agent-N

pub fn start(&self, name: &str, task: &str) -> String {
    let mut seq = self.seq.lock().unwrap();
    *seq += 1;
    let id = format!("agent-{seq}");
    self.jobs.lock().unwrap().push(Job { id: id.clone(), /* ... */ });
    id
}

Sequence then jobs, always in that order, so no deadlock. One lock could cover both, but splitting means list() does not wait behind numbering, which pays off when reads dominate.

The ids are readable: agent-1, agent-2. Better than UUIDs for humans, worse in one way: unique only within one board instance.

Which matters in daemon mode, where one agent serves every session. replace_messages swaps only the message vector; the board, todos and tasks stay. So session A creates agent-1 through agent-3, session B's first sub-agent becomes agent-4, and B's agent_list shows six jobs including A's.

Yet the tool description says it lists delegations started in this session. That sentence is false in daemon mode. An observability tool whose semantics differ between two run modes, described as if only one exists. The fix is a session field on jobs, filtered at render time, or clearing the board on session switch. The first preserves cross-session audit, which suits a board treated as observability rather than as a log.

Result preview at 500, on the board but not in the model

const RESULT_PREVIEW: usize = 500;

fn preview(text: &str) -> String {
    let flat = text.replace('
', " ");
    if flat.len() <= RESULT_PREVIEW { return flat; }
    let mut end = RESULT_PREVIEW;
    while end > 0 && !flat.is_char_boundary(end) { end -= 1; }
    format!("{}…", &flat[..end])
}

All three details are right: compare by bytes but retreat to a character boundary, flatten newlines so each preview is one line, only add the ellipsis when truncated.

Note the asymmetry: the board holds a 500 unit excerpt while the model holds the full result. That is correct, the model needs the whole thing, but it means the board is not an audit log. To see what a sub-agent actually said you go back to session history, and history gets compacted. A completed sub-agent's full output may survive only as one sentence of summary while the board keeps the first 500 units.

And those units are bytes, since len() and is_char_boundary both count bytes, so 500 bytes is about 166 Chinese characters. The constant name does not say which, the same ambiguity as the clamp comment in the tool post.

What duration actually measures

job.duration = Some(job.started.elapsed());

The start instant is set in start, and start happens before acquire. So duration is queue time plus execution time. A user reading agent-7 [done] reviewer (12.3s) assumes the review took 12.3 seconds, when 8 of them may have been spent waiting for a permit.

Record two timestamps, queued and started, or register after acquiring. The second has a cost: queued work becomes invisible until it starts, so the board shows nothing and then four jobs appear at once. The complete fix keeps registration where it is and splits the status into queued and running, which means the gate has to notify the board once a permit is granted.

The gate: four details

pub struct Gate {
    active: Mutex<usize>,
    cv: Condvar,
    max: usize,
}

impl Gate {
    pub fn new(max: usize) -> Self {
        Gate { active: Mutex::new(0), cv: Condvar::new(), max: max.max(1) }
    }

    pub fn acquire(&self) -> GateGuard<'_> {
        let mut active = self.active.lock().unwrap();
        while *active >= self.max {
            active = self.cv.wait(active).unwrap();
        }
        *active += 1;
        GateGuard { gate: self }
    }
}

max.max(1) prevents a zero quota from blocking forever. Correct, and only correct under the assumption that the quota comes from configuration. If it ever arrives from an environment variable or a server, clamping silently converts a configuration error into a looser policy than intended. Returning a Result and rejecting zero would be more honest.

while rather than if is the standard requirement, since the predicate may be false again on wake.

notify_one frees one slot and wakes one waiter. Waking all produces a thundering herd where all but one go back to sleep.

Counting in Drop means an early return releases the permit. The same RAII pattern as the interrupt guard, which suggests the author was thinking about it.

One implicit assumption: notify_one plus saturating_sub assumes there is no second release path. A double release will not be noticed, it just quietly admits one fewer sub-agent, and nothing asserts that the counter matches reality.

The existing test asserts the peak never exceeds the limit and that the counter returns to zero. The second assertion is the valuable one, and it deserves to be an available() method so callers can check for leaks too.

Queued jobs report as running

fn run_subagent(&self, name: &str, task: &str) -> Result<String, String> {
    let id = self.ctx.board.start(name, task);   // status = Running
    let _permit = self.ctx.gate.acquire();       // may block here a long time
    // ...
}

The fifth job appears as running while it waits, and renders as agent-5 [running] verifier (...) - run the tests. The user experience is five jobs running when four are. Over a four-way gate with two-minute jobs, the lie lasts minutes.

How much it matters depends on who reads the board. For a human it is cosmetic. For the model, which has the tool, it changes decisions: it may stop delegating because it believes there is no capacity, or delegate again because it sees activity.

The gate ignores interrupts

while *active >= self.max {
    active = self.cv.wait(active).unwrap();
}

No exit condition other than a free slot.

The interrupt flag has no effect here. The parent checks at step boundaries, but the main thread is blocked inside execute into run_subagent into acquire, where the flag is invisible. It takes effect only after some sub-agent finishes and the loop comes around. A sub-agent can run 40 rounds of a 120 second timeout, which is 80 minutes in the worst case.

And the wait is not cancellable, since a condition variable wait does not report interrupts. What is needed is a timed wait with a poll, checking the flag every 200 ms. At four slots the extra wakeups cost nothing.

This is the same class of bug as sub-agents not checking interrupts, in a second location: an interrupt has to be checked at every place that can block for a long time, and checking in one place is the same as not checking.

The gate is not reentrant

This is the only finding in the post that causes a permanent hang. Its precondition is that nesting prevention is only advertising: if the model emits a subagent call, nesting happens, and nesting re-enters run_subagent.

The outer sub-agent already holds a permit and holds it for the entire inner loop, because the guard lives to the end of the function. With four slots taken by four outer sub-agents, each calling a nested sub-agent, four inner threads wait for a permit that only the outer threads could release, and the outer threads are waiting for the inner ones. The cycle closes.

The condition variable has no timeout, so this is not a pause, it is until the process dies. And Ctrl-C sets a flag that nobody in that wait ever reads.

Two fixes, and they should both land: add a depth counter and refuse at the entry point, which also makes future two-level nesting an explicit number rather than a rewrite; and make the gate reentrant, either passing a permit through on the same execution chain or not acquiring again when nested. The current implementation is the only combination that deadlocks: nesting is neither forbidden nor reentrant.

Rate limiting bounds concurrency, not request rate

The gate bounds how many sub-agents run at once. It does not bound requests per second, total requests, or rounds per sub-agent. Four slots at 40 rounds each is 160 model requests per turn, plus the parent's own 40, all fired within a few minutes against an API that meters tokens or requests per minute.

That is a semantic mismatch: local concurrency control cannot solve remote rate limiting. No matter how good the gate is, a 429 still means backing off.

What is needed is a budget: not "how many at once" but "how many in total". It matters more here because a sub-agent's round count is unpredictable; it runs until the model stops calling tools.

A pragmatic version puts a shared counter in Ctx that both parent and sub-agents draw from, and after it is exhausted a sub-agent returns "budget exhausted" instead of continuing. That turns "what can one turn cost" from four times forty times the per-call price into a configurable number.

Retry storms without jitter

fn backoff_ms(base_ms: u64, attempt: u32) -> u64 {
    base_ms
        .saturating_mul(2u64.saturating_pow(attempt.saturating_sub(1)))
        .min(30_000)
}

Pure exponential, defaults of two retries and a 500 ms base, so waits of 500 then 1,000 ms. Retryability is decided by string matching on the error message containing "HTTP 429", not by parsing a status code. Change the error format and retries silently stop happening, the same interface-shaped-like-a-message problem noted for the clamp unit.

Back to multi-agent: four backoff curves with no randomization. If the API returns 429 to all four at the same moment, they retry in lockstep, all at 500 ms, then all at 1,000. It is the textbook thundering herd at a smaller scale.

The standard three fixes: add jitter, honor the Retry-After header, and back off at the shared layer so that one sub-agent being throttled pauses its siblings. The third matters most here, because only a shared layer knows that four sub-agents are using one key.

Worth noting the retry sleep is blocking. Four sub-agents sleeping does not affect other threads, but the parent's own retry blocks the turn for up to 30 seconds.

Fallback is silent

After retries are exhausted, a configured fallback model gets one attempt, for both 429 and 5xx. Errors that retries cannot fix, such as a 401, go straight back, which is right because switching models does not fix authentication.

The visibility is the problem. One stderr note is the only signal, and in JSON or daemon mode it is buried. Worse, a sub-agent's fallback is invisible to the parent: two model calls may have degraded, and the parent receives only the final text with no idea which model produced it.

That matters for cost accounting. Usage totals record requests, prompt tokens and completion tokens, with no model dimension, so a turn where four sub-agents all fell back is recorded as a count without attribution.

Why four

const MAX_PARALLEL_SUBAGENTS: usize = 4;

Hard-coded and not configurable. The justification is plausible: code work rarely needs more than four concurrent subtasks, four concurrent model requests are safe on most plans, and four parallel commands do not saturate a laptop.

Three costs. It is also the concurrency limit for the parent's parallel tool calls, so eight subagent calls mean four running and four parked, each parked thread occupying a tool thread. Tool threads are unbounded, so nothing breaks, but four threads idle for nothing.

Not configurable means not adjustable to the machine or the plan. Four is wasteful on 64 cores and constantly throttled on a two-concurrency plan.

And it is independent of how many sub-agents one turn may spawn. Nothing in the schema limits that, so the model can dispatch twenty, all of which register as running, four executing and sixteen queued.

The deeper problem is placement: the constant lives in agent.rs as a module constant, which reads like a behaviour parameter of the main loop, when it is really a resource quota belonging to Ctx or the config layer. Move it and configurability and testability follow.

Will the model actually use agent_list

The tool takes no arguments and returns one line per job plus an indented result line. The workflow it was meant to serve runs into a fact: subagent is synchronous and blocking. The parent calls it and waits. So a model cannot "dispatch four and then check progress". Four calls in one turn do overlap, but only because the parent's scope runs the tool calls in parallel.

Which leaves agent_list as retrospective: what did I dispatch, why did something fail, what came back. Its value would be much higher in an asynchronous design. Here it is an observability backstop.

Sub-agent work is invisible in the terminal

The parent prints every tool call through the style layer, including the summarized arguments and result. The sub-agent loop calls execute directly and never calls the style method.

So every tool a sub-agent runs is silent: the user sees a delegation, waits two minutes, and gets a paragraph. The read_file, the run_command and its output all happened off screen. In daemon mode it is worse, because the UI sink streams the parent's calls but sub-agent calls never reach it.

Printing with a role prefix is the obvious fix and produces interleaved nonsense without attribution, so what is actually needed is a style layer that can say who is speaking. The same gap the concurrency post hit when two approvals shared one stdin.

Hooks cannot tell parent from child

Sub-agent tool calls go through execute, so PreToolUse hooks apply, which is good news: the user-defined veto survives into multi-agent work.

But the environment passed to a hook names the tool and the event, never the caller. A hook cannot apply different rules to a sub-agent, and cannot count how many files a given sub-agent changed. Adding NANOHERMES_AGENT and an agent id would enable exactly the granularity multi-agent work needs, and as a bonus the hook's output, which returns to the model, could say who triggered the refusal.

What permission modes mean here

ModeCan the parent delegateWhat a sub-agent may do
defaultYesThe same as the parent
accept-editsYesEdits unasked, commands still asked
planYesDispatch allowed, writes and commands blocked
goalYesEverything, with nobody to ask
debugYesCommands yes, writes no

Plan mode allows delegation, since subagent is not in its blocked list, and the sub-agent inherits plan mode so it cannot write either. No security problem, but four round trips to learn "I cannot do this". Delegation should probably be removed from the tool list in plan mode, since pure analysis does not need it.

Goal mode plus sub-agents is the most dangerous combination: four parallel agents, each able to run commands, with nobody asked. The risk surface multiplies rather than adds, and the configuration documentation should say so.

There is a subtler point: a permission mode expresses the intent of the turn, and a sub-agent is a role inside that turn. Inheriting it verbatim assumes the intent applies to every role. Usually true, with debug as the counterexample: the parent in debug mode cannot edit files, and a fix-it sub-agent may need to.

One item is deliberately absent: def.allowed_tools not participating in execution checks. It never produces an error, it just makes the isolation stricter in the user's imagination than in reality. That belongs in a security review, not in a failure list.

How to test multi-agent behaviour

Four tests worth writing directly.

The gate's limit holds. N threads for M slots, record the peak, assert it never exceeds M, then assert the counter is back to zero. The second assertion is the one that proves nothing leaked.

The board's transitions are complete. Running to done and running to failed are covered; what is missing is finishing the same id twice, which should be idempotent, and finishing an unknown id, which should be silent.

Nesting is refused. Trivial to write, and its value is not coverage but turning an implicit design, "prevention lives in the tool list", into an explicit contract. Write the test and the depth field gets added.

An interrupt breaks the wait. One thread holds a permit, another sets the flag and calls acquire, and the assertion is that it returns nothing within 200 ms. This test currently fails, which is exactly its value.

One harder question is how to verify the absence of deadlock. The classic answer is stress: far more threads than slots, thousands of acquire and release cycles, and a lock-order bug will hang at some point. Since a hang means the test never finishes, it needs a watchdog, and note that stress covers lock ordering and leaks but not the nested deadlock, because that one requires the model to cooperate. Which is why the nesting test has to be a unit test.

Seven places to harden

One. A depth counter on Ctx, asserted at the sub-agent entry. Three lines, and it removes the only fatal failure mode, while turning "support two levels later" into a number rather than a rewrite.

Two. Make acquire interruptible and timed. Poll every 200 ms and check the flag. It fixes both the Ctrl-C hang and the unrecoverable deadlock, because an interrupt can break a deadlock even after it happens.

Three. Add a queued state and split duration into queue time and run time. Two files change and the observability becomes accurate.

Four. Add max_iterations to the sub-agent definition. Inheriting 40 is a dangerous default; a "run the tests and report" agent should not have 40 rounds. Default it low, around ten.

Five. Move the parallel limit into configuration, with a CLI flag and a JSON field. The real value is giving the concept of quota a correct home in the code.

Six. Give shared state an owner. Todos, tasks and memories each gain an owner field, filtered at the tool layer. The largest change in the list and the only one that root-fixes corruption of parent state.

Seven. Enforce def.allowed_tools at execution, by intersecting the parent's allow list with the sub-agent's inside the sub-agent execution path.

The first three are small and clearly worth doing today. Four and five are configuration layer, six and seven are permission layer, and both need the semantics settled first, starting with what identifies an owner.

Closing

The abstraction is weaker than it looks. Four fields, and a sub-agent is the same Agent with a different prompt, a different tool list and possibly a different model. Things you assume are isolated are not: the todo list, the background tasks, the memory directory and hook visibility are all shared.

Sharing is not the defect; unowned sharing is. The board, the gate and Ctx all should be shared, or the user sees five unrelated plans and task_kill becomes a lottery. The problem is that shared objects carry no "whose is this" field, so any role can change any state.

And the three unclean cuts share one shape: advertising filters passed off as execution gates. Nesting prevention by tool list, sub-agent tool restrictions by tool list, available sub-agent names by system prompt. All three make things invisible rather than making calls invalid. That distinction is harmless with one agent, since an invisible tool is never called, and it compounds into deadlocks, overreach and information leaks once there are several.

What deserves credit is the gate's internals: RAII release, the re-check loop, single notification, and a test asserting all permits are returned. The author clearly knows the traps of a hand-written semaphore. The problem is not the implementation, it is the semantic boundary: the gate answers "how many at once", when multi-agent work needs "whose budget, whose quota, whose visibility".
