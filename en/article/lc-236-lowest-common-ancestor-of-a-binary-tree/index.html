LC 236, lowest common ancestor: the return value is a messenger, not the answer

2026-10-13 · 18 min · Stack Frame

The problem

Given a binary tree and two of its nodes, return their lowest common ancestor: an ancestor of both whose depth is maximal. A node counts as its own ancestor.

tree: [3,5,1,6,2,0,8,null,null,7,4]
p = 5, q = 1  ->  3
p = 5, q = 4  ->  5

This is the graduation exam for tree recursion. It is short, and short in a dangerous way, because three things become visible at once: whether you write post-order, whether you understand that a return value can carry more than one meaning, and whether you can pass information upward without any global state.

class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

Where the difficulty is

The obvious approach is to find the path from the root to each node and compare the two paths from the front, returning the last common node.

def lowestCommonAncestor(self, root, p, q):
    path_p, path_q = [], []

    def dfs(node, target, path):
        if not node:
            return False
        path.append(node)
        if node is target:
            return True
        if dfs(node.left, target, path) or dfs(node.right, target, path):
            return True
        path.pop()
        return False

    dfs(root, p, path_p)
    dfs(root, q, path_q)
    i = 0
    while i < len(path_p) and i < len(path_q) and path_p[i] is path_q[i]:
        i += 1
    return path_p[i - 1]

It is correct and linear, and it walks the tree twice and keeps two arrays. The obvious follow-up is whether both can be avoided, and the answer is eight lines.

Instead of asking for paths, ask each node a simpler question: looking down from here, can you find p and q? There are only three possible answers.

SituationAnswer
Neither is in this subtreenull
Exactly one is in this subtreeReturn the one found
Both are in this subtreeThis node is the answer

The third case has a precise test: a non-null result from each side means p and q lie on different sides of this node, making it the fork, hence the lowest common ancestor.

The second case is the heart of it. When only one is found, the return value is not the answer, it is a marker that says "one is over here, whoever has the other should meet me". Confusing the marker with the answer is what makes this problem feel tangled.

Handling a node being its own ancestor

The definition explicitly allows it, and the temptation is to special-case it. No case is needed, because of one line:

if not root or root is p or root is q:
    return root

Recursion stops the moment it reaches p or q, without descending into that node's subtrees. That single behaviour covers both situations. If q is inside p's subtree, the call at p returns p and it propagates upward, and no ancestor above it can ever see a non-null result from the other side, because q was cut off below. So p travels all the way up and becomes the answer. If q is not inside p's subtree, then p is merely a marker that keeps rising until some node sees two non-null children.

So there is no branch for "p is an ancestor of q". The single return handles it, which is the most elegant part of the design.

Three frames matter. The hit frame enters six and returns immediately without descending. The deciding frame at five sees six from the left and four from the right, the only place in the whole run where both sides are non-null, and returns itself. And the deciding frame at the root sees only five on the left with nothing on the right, so it is not the fork, merely an ancestor passing the answer upward. That is what "lowest" means here: not containing both, but separating them.

Worth pausing on three things. The hit frame does not descend, which matters as soon as p has a subtree of its own. The deciding frame at five is the only fork in the whole tree. And the root, though it is also an ancestor of both, sees only one non-null side and therefore passes the answer along untouched.

Also note the frame where the entire right subtree finishes having found nothing. The recursion does not exit early; it walks the whole tree, which is where the linear bound comes from. There is no pruning, because until you finish a side you cannot know whether a target is hiding there.

The code

class Solution:
    def lowestCommonAncestor(self, root: TreeNode, p: TreeNode, q: TreeNode) -> TreeNode:
        if not root or root is p or root is q:
            return root

        left = self.lowestCommonAncestor(root.left, p, q)
        right = self.lowestCommonAncestor(root.right, p, q)

        if left and right:
            return root
        return left or right

The first line merges three conditions, each returning the node itself: null means nothing found here, and identity with either target means a hit, return immediately without descending.

Identity comparison is essential. Values are not unique in a tree, so comparing values would mistake a different node with the same value for a target.

The two recursive calls happen before any decision, which is what makes this post-order: the node must wait for information from below before it can act.

The fork branch is the only place that produces an answer. Both sides non-null means one target on each side, so this node is the lowest common ancestor, and because the recursion is bottom-up the first such node to see that condition is the deepest one. Ancestors above it will only ever see a single non-null side, so they cannot overwrite the answer.

The final line covers both remaining cases through short-circuiting: exactly one non-null returns it, reporting honestly that both targets are on that side, and both null returns null.

if left and right:
    return root
elif left:
    return left
else:
    return right

This expansion is equivalent. The short form is idiomatic but relies on the assumption that the only values are nodes and null, which holds because tree nodes are always truthy in Python. Say the assumption out loud if you use the short form.

Time is linear, with each node visited once, and note the absence of pruning: even if the fork is found on the left, the right must still be walked. Space is the recursion depth, logarithmic for a balanced tree and linear in the degenerate case.

Compared with the path approach, both are linear, but this one walks once and allocates nothing beyond the stack.

Variant one: LCA in a binary search tree

Ordering changes everything. Compare the two target values against the current node and there are three cases: both smaller, so both live left; both larger, so both live right; or they straddle, in which case this node is the fork.

The criterion is the same as above, but the implementation is completely different. The general tree provides no information, so you must search everything and let results bubble up. The BST lets you decide at the current node, so a single top-down walk suffices.

class Solution:
    def lowestCommonAncestor(self, root: TreeNode, p: TreeNode, q: TreeNode) -> TreeNode:
        while root:
            if p.val < root.val and q.val < root.val:
                root = root.left
            elif p.val > root.val and q.val > root.val:
                root = root.right
            else:
                return root
        return None

No recursion, no stack, no backtracking: constant space iteratively, logarithmic time.

Note that the else branch also covers the case where one target equals the current node, which is the BST reflection of "a node is its own ancestor", handled without a special case.

def lowestCommonAncestor(self, root, p, q):
    if p.val < root.val and q.val < root.val:
        return self.lowestCommonAncestor(root.left, p, q)
    if p.val > root.val and q.val > root.val:
        return self.lowestCommonAncestor(root.right, p, q)
    return root

The recursive form is closer to the general solution, and note it still recurses only once per level.

Reusing the general code on a BST produces correct answers and wastes the ordering, turning logarithmic into linear. That is exactly what the interviewer is checking for.

One sentence: on a general tree you can only search, on a BST you can decide.

Variant two: LCA with parent pointers

Add a parent reference to each node and the problem becomes the intersection of two lists: the chain from p to the root and the chain from q to the root, whose first shared node is the answer. That is exactly the intersection problem from earlier in this series, including its cursor-swapping trick.

class Solution:
    def lowestCommonAncestor(self, p: 'Node', q: 'Node') -> 'Node':
        a, b = p, q
        while a is not b:
            a = a.parent if a.parent else q
            b = b.parent if b.parent else p
        return a

def lowestCommonAncestor(self, p, q):
    seen = set()
    while p:
        seen.add(p)
        p = p.parent
    while q not in seen:
        q = q.parent
    return q

The set version is more direct, the pointer version uses no extra memory.

The key comparison is why the parent version reaches constant space at all: the pointer makes going upward an explicit operation. Without it, going upward can only happen through return values, which is precisely why the general solution needs the bubbling mechanism.

Two more variants

With many targets, replace the identity check with set membership and keep everything else:

class Solution:
    def lowestCommonAncestor(self, root, nodes):
        target = set(nodes)

        def dfs(node):
            if not node:
                return None
            if node in target:
                return node
            left = dfs(node.left)
            right = dfs(node.right)
            if left and right:
                return node
            return left or right

        return dfs(root)

One line changed, which shows the mechanism was never about there being two targets.

For the deepest leaves, the return value becomes a pair of depth and answer:

class Solution:
    def lcaDeepestLeaves(self, root):
        def dfs(node):
            if not node:
                return (0, None)
            dl, nl = dfs(node.left)
            dr, nr = dfs(node.right)
            if dl > dr:
                return (dl + 1, nl)
            if dr > dl:
                return (dr + 1, nr)
            return (dl + 1, node)

        return dfs(root)[1]

Same fork test, with equal depths instead of non-null results.

ProblemThe fork test

LC 1123Both subtree depths equal
LC 1676Both subtrees contain targets

One skeleton, three tests: post-order, report subtree conclusions upward, and declare yourself the answer under some condition.

Java

class Solution {
    public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
        if (root == null || root == p || root == q) return root;

        TreeNode left  = lowestCommonAncestor(root.left,  p, q);
        TreeNode right = lowestCommonAncestor(root.right, p, q);

        if (left != null && right != null) return root;
        return left != null ? left : right;
    }
}

class Solution {
    public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
        while (root != null) {
            if (p.val < root.val && q.val < root.val) {
                root = root.left;
            } else if (p.val > root.val && q.val > root.val) {
                root = root.right;
            } else {
                return root;
            }
        }
        return null;
    }
}

In Java the identity comparison is the default for references, and it must be used rather than a value comparison. The null return carries a single meaning here because the inputs are guaranteed non-null, which is worth keeping in mind if the guarantee is lifted.

Common mistakes

  1. Treating the marker as the answer. A returned p only says "p is here"; the answer is only produced by the fork branch.
  2. Comparing values instead of identity, which fails on trees with duplicates.
  3. Returning the right subtree as soon as the left is empty, which skips the fork test that needs both results.
  4. Using the general solution on a BST, which is correct and abandons the ordering.
  5. Tracking the first found target in a global variable, which then requires extra work to track that target's ancestry.
  6. Forgetting that a null return in Java means both "nothing found" and "empty node", which is safe only while the inputs are guaranteed non-null.

How to answer it

Thirty seconds: post-order DFS where each node reports what it found, with three meanings. Null means nothing, returning p or q means a marker, returning itself means a fork. If both sides are non-null, the targets straddle this node and it is the answer. Two base cases, empty and hit, and the hit return covers the self-ancestor definition for free. Linear time, stack-depth space.

Then volunteer the variants: the BST version decides instead of searching, in a single top-down walk with constant space iteratively, and the parent-pointer version is the intersection of two lists with the cursor-swapping trick.

For follow-ups: the self-ancestor case is automatically handled because the hit return prevents descending; identity comparison is necessary because values repeat; there is no useful pruning because the other side must be finished before the fork test can run; post-order is required because the decision depends on subtree results; and space is the tree height, logarithmic for balanced trees.

What to keep is not the eight lines but two reflexes: when a question about the relationship between nodes must be decided bottom-up, reach for post-order; and when information from a subtree must reach its parent, treat the return value as a carrier that can mean more than its literal type.

dfs(node)
  empty or hit -> return immediately
  left  = dfs(node.left)
  right = dfs(node.right)
  both non-null ? return self : report honestly

The return value is a messenger, not the answer. Only when both messengers come back does the node receiving them become the answer.
