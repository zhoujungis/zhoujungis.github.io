From three seconds to a first paint in milliseconds

2026-11-12 · 13 min · Stack Frame

Three seconds of blank screen, and no single file to blame

Shortly after the English edition went live, someone reported that it took over three seconds to open.

The first guess was a slow CDN, so I measured the build output: 22.9 KB of HTML, 30.5 KB of CSS (6.0 KB gzip), a 79.9 KB entry script (30.2 KB gzip). Nothing looked wrong. Not one file was unusually large.

The problem was that these files form a sequence that has to execute in order.

HTML -> 30 KB CSS -> 79.9 KB entry -> 63.5 KB Vue runtime -> 45.6 KB client
     -> route chunk -> Vue clears #app and re-renders -> the page appears

Six requests and 220 KB of raw bytes, 78.3 KB gzipped, where each step waits for the one before. First paint is not the download time of the largest file. It is the sum of the chain.

Counting the chain

A hundred-line script reads the build output directly instead of estimating. Run against the SPA shell:

files 5 | raw 220.1 KB | gzip 78.3 KB
   /assets/index-DQvGHmaK.js                    79.9 KB | gzip 30.2 KB
   /assets/_plugin-vue_export-helper-tRUQJj3d.js 63.5 KB | gzip 24.6 KB
   /assets/rolldown-runtime-QTnfLwEv.js          0.7 KB | gzip  0.4 KB
   /assets/client-DDSzq_-U.js                   45.6 KB | gzip 17.1 KB
   /assets/index.DnfPoa2_.css                   30.5 KB | gzip  6.0 KB

Five files, six requests counting the HTML. And that is only the first paint: the route chunk is fetched by import() after the entry script runs.

For parse and compile, the script builds a vm.SourceTextModule without instantiating it, seven runs, median:

entry bundle 79.9 KB -> 3.4 ms
inline shell  0.8 KB -> 0.01 ms

Three milliseconds is not much, and that is the point: it is only compilation. Download, execution, DOM construction, style calculation and third-party tags are all on top. On a real device the first paint is three phases added together.

PhaseWhat decides itEffect of the change
Download220 KB at the available bandwidth, six round trips12.9 KB gzip, two requests
Parse and compileJavaScript bytes3.4 ms to 0.01 ms
Execute and renderVue mount, route match, API callentire phase gone

At one megabit per second, transfer alone is 78.3 KB times eight divided by 1024, about 0.61 s, before six serial round trips, the Vue mount, an analytics-style ad script and a backend preconnect that nothing used. Three seconds is not surprising; one second would be.

The conclusion: the problem was never a file that was too big. The problem was that this page had no business being rendered by a single-page app.

Which pages may be static

Every page on the English edition has one property: its content is fully determined at build time.

  • The article list comes from a registry read during the build.
  • An article page is HTML generated at build time, with no comment box and no editor.
  • Topic pages and pagination are derived from the same data.

There is no runtime state. The three things that genuinely need JavaScript are tiny: toggling the theme from localStorage, opening the mobile menu, and following links that could have been static in the first place.

The Chinese edition cannot be treated this way. It has search, comments, an admin area, Live2D and dynamic routing. The criterion is not whether you want speed. It is whether the page contains anything that can only be known at runtime.

The replacement: a twenty-three line shell

== /en/ static shell ==
html raw 22.9 KB | gzip 6.9 KB
external scripts 0 | external css 1
inline js bytes 792 | lines 23
css /assets/index.DfnPoa2_.css 30.5 KB | gzip 6.0 KB

Zero external scripts. The whole page is HTML, one stylesheet, and 792 bytes of inline JavaScript. That script restores the theme and binds the menu button, and it shares the same localStorage key as the Vue toggle, otherwise switching between editions would flip the theme.

<script>
  (function () {
    var t = localStorage.getItem('theme')
    if (t === 'dark' || (!t && matchMedia('(prefers-color-scheme: dark)').matches)) {
      document.documentElement.dataset.theme = 'dark'
    }
  })()
  document.addEventListener('click', function (e) {
    var btn = e.target.closest('[data-menu-toggle]')
    if (btn) {
      var nav = document.querySelector('[data-nav]')
      var open = nav.classList.toggle('is-open')
      btn.setAttribute('aria-expanded', open ? 'true' : 'false')
    }
  })
</script>

Three rules keep it honest. The theme script runs synchronously in the head and touches only the root element, because waiting for DOMContentLoaded shows a white flash first. No module system is used, since type="module" adds another scheduling step. And nothing is mounted: the moment a framework mounts, it clears the container and rebuilds what was already painted.

What else went away

RemovedWhat it cost
modulepreload hintsCompeted for bandwidth on chunks the first paint never used
Auto adsA third-party script plus its own subresources, on its own schedule
A backend preconnectAn early handshake for a request the English pages never make

The last one is the clearest: preconnect is a promise that something is about to be needed. Keeping it means asking the browser to negotiate a connection for a request that never happens.

Pagination has to move into the build

Once the pages are static, every list must exist on disk. The English list holds twelve posts per page across seven pages:

/en/articles/
/en/articles/page/2/ … /en/articles/page/7/

Three rules are hard-coded in the build script. Each page carries a self-referential canonical, because pointing page two at page one keeps it out of the index forever. Pages after the first put the number in the title, so seven pages do not share one title. And every page URL goes into the sitemap, since a crawler can otherwise only find them by following links.

This is the easiest thing to miss: under an SPA, pagination is state. After static generation, pagination is pages.

The cost: comments no longer mount

Static generation is not free. The article pages used to mount a Vue comment component, and with no mount there is no comment box.

Rather than loading a second lightweight comment widget, I put one line at the end of each article pointing to the Chinese edition.

The reasoning is simple arithmetic. Comments are a low-frequency interaction and the first paint is the high-frequency path. Slowing every reader down by 220 KB to serve one percent of them is a bad trade.

If comments ever do come back, the right shape is on demand: render a static button, and only import the comment bundle when it is clicked. That keeps it outside the first paint and unchanged from the numbers here.

Checklist

  • No external script src in the first-paint HTML unless genuinely required.
  • The theme script runs synchronously in the head and shares its storage key with the framework side.
  • Navigation links are real URLs generated at build time, not router paths.
  • Each paginated page has its own canonical and a numbered title.
  • Every paginated URL is in the sitemap.
  • Unneeded preconnect, modulepreload and third-party tags are deleted.
  • The page renders completely with JavaScript disabled, verified with curl or a no-JS browser.
  • Theme switching is checked against the framework edition for flashes.

Questions that come up

Can the English site still be searched? It has no search today. Adding one means shipping a small client-side index, which is far cheaper than restoring the SPA.

Why not staticise the Chinese site too? It has an editor, comments, an admin area and dynamic routes. Staticising it means rewriting the product. Content pages can be static; application pages cannot.

Does inline JavaScript break a content security policy? It would. The site has no strict policy today; if one arrives, this script needs a nonce or a hash.

Why not defer or async? The theme has to be decided before style calculation. Deferring shows a white frame.

Does the Chinese edition benefit? Indirectly. The English pages no longer download the Vue runtime, and both editions share the same stylesheet, so switching between them hits a warm cache.

Closing

The turning point was not learning to write static HTML. It was accepting an unintuitive fact: a slow first paint is not fixed by shrinking a file.

Those 220 KB were spread across five files, none of them large, yet together they formed a chain that had to run end to end, and the length of the chain was the length of the blank screen. The only way to make the first paint depend on HTML and CSS alone is to delete the chain, not to shorten it.
