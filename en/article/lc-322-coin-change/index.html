LC 322, coin change: iterate amounts ascending, or the answer becomes minus one

2026-09-30 · 13 min · Stack Frame

The problem

Given coin denominations and a target amount, return the fewest coins summing to the amount, or minus one if impossible. Each denomination is available unlimited times.

[1,2,5], amount 11  ->  3    (5 + 5 + 1)
[2],     amount 3   ->  -1

This is the canonical unbounded knapsack minimisation. The recurrence is one line; the two thresholds are the choice of infinity and the direction of the inner loop over amounts. The second is the main character here: the same code returns three when amounts ascend and minus one when they descend.

Definition and recurrence

Enumerating how many of each coin explodes, so ask instead how many coins are needed for each amount. The state is the minimum count for an amount, zero needs none, and everything else starts at infinity.

dp[x] = min over coins c ( dp[x - c] + 1 )      for x >= c

Read it as trying coin c as the last one added: the optimum for the remainder is already known, and appending this coin gives a candidate. Amounts ascend so that every dependency is already computed.

def coinChange(coins, amount):
    dp = [0] + [float('inf')] * amount
    for x in range(1, amount + 1):
        for c in coins:
            if x >= c:
                dp[x] = min(dp[x], dp[x - c] + 1)
    return dp[amount] if dp[amount] != float('inf') else -1

Two details decide everything. Infinity rather than zero, because zero would declare every amount reachable with one coin and the minimum would collapse. And ascending amounts inside the loop, which is the switch for unlimited reuse.

Why ascending is the fingerprint of unbounded knapsack

Rewrite with coins outside and amounts inside, and only one variable remains: the direction of the inner loop.

Ascending, when the loop reaches amount a, the entry for a minus c has already been updated in this same pass, and may itself be built from coin c. So the recurrence naturally allows adding another copy of the same coin. That is where reuse happens: the eleven is built from ten, ten from five, giving five plus five plus one.

Descending, that entry has not yet been touched in this pass, so the value read is the one left by the previous pass, which is equivalent to each coin being usable once. With coins of one, two and five the total face value is only eight, so eleven is unreachable and the answer is minus one.

One sentence: ascending reads the current pass, descending reads the previous pass.

So this problem must ascend, while problems where each item is used at most once must descend. That is a difference in meaning, not in style.

The family

  • Perfect squares. Coins replaced by square numbers, structurally identical with one line changed.
  • Coin change two, counting combinations. Addition instead of minimisation, and the loops must be coins outside and amounts ascending, which removes duplicate orderings.
  • Combination sum four, counting permutations. The same addition with the loops transposed, which is the only difference between the two.
  • Word break. The boolean version of the same recurrence.
  • Partition equal subset sum. Each item once, so the inner loop descends, which is the right panel of the second animation.

The axes: capacity is the amount, items are the coins, unlimited means ascending, single-use means descending, optimisation means minimum or maximum, and counting means addition.

Java

public int coinChange(int[] coins, int amount) {
    int INF = amount + 1;
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, INF);
    dp[0] = 0;
    for (int x = 1; x <= amount; x++) {
        for (int c : coins) {
            if (x >= c && dp[x - c] + 1 < dp[x]) {
                dp[x] = dp[x - c] + 1;
            }
        }
    }
    return dp[amount] == INF ? -1 : dp[amount];
}

The sentinel is the amount plus one rather than the maximum integer, because incrementing that maximum overflows to a negative and the minimum then picks it. Adding a predecessor array recovers the actual coins by walking backwards from the target. A breadth-first search over amounts is equivalent and convenient when a combination must be printed.

Edges

  • A target of zero answers zero without entering any loop.
  • Unreachable targets leave infinity in place and return minus one.
  • Coins larger than the target are skipped, and filtering them up front is cleaner.
  • A single denomination matching the target answers one, and twice the target answers two, relying precisely on the ascending order.
  • If a one exists, everything is reachable, which is why so many test cases feel safe.
  • Duplicate denominations change nothing.
  • Choose the sentinel per language so that incrementing it cannot overflow.

Collapsing the two-dimensional table to one row relies exactly on the ascending inner loop, since each entry depends only on smaller indices of the same row. Descending is what happens when that collapse is done in the wrong direction.

Common mistakes

  1. Initialising with zero instead of infinity, which collapses every answer.
  2. Iterating amounts descending, which still runs and may still pass samples while quietly turning the problem into the single-use variant.
  3. Greedily taking the largest coin first, which fails without divisibility: for six from one, three and four, greedy needs three coins and the optimum is two.
  4. Omitting the zero-target short circuit in code that assumes at least one coin.
  5. Returning infinity or a large number instead of minus one.
  6. Recording only the count when the combination is needed, which requires a predecessor array.
  7. Using the maximum integer as infinity in a fixed-width language.
  8. Mixing the loop-order rules between the minimisation and counting variants.
  9. Forgetting to filter coins larger than the target.

How to answer it

Define the state, the base, the recurrence and the sentinel, with an explanation of why zero will not do. Then the direction, which is where candidates separate: ascending reads this pass and permits reuse, descending reads the last pass and forbids it. Then the graph viewpoint, amounts as vertices and coins as unit edges, so the answer is a shortest path and a breadth-first search solves it, which is convenient for printing a combination. Then the follow-ups: counting combinations or permutations by loop order, and single-use items by descending.

Closing

The difficulty compresses into one initialisation and one direction. Infinity decides whether impossibility can be expressed at all, and the direction decides whether a coin may be reused. Say both clearly and the rest of the family is the same machine with new parameters.
