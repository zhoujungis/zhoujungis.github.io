Agent concurrency without an async runtime

2026-10-26 · 34 min · Stack Frame

Who this is for: people who added parallelism to an agent and got deadlocks or mismatched results; people unwilling to drag an async runtime into a CLI; people who want to know how many things can actually run at once inside one turn.

TL;DR: NanoHermes has exactly two concurrency primitives, scoped threads and a counting gate built on a mutex and a condition variable. No async runtime, no cancellation token, no queue. What holds it together is one join barrier per turn, which confines concurrency to a bounded box.

Parallelism is not mainly about speed

A coding agent spends most of its time on two things: waiting for the model, and waiting for a command. Model calls are serial, because you need this turn's assistant message before you know which tools to call. That leaves exactly one window for parallelism: several tool calls returned in a single model response.

The window is small and it sets the floor on the experience. If the model asks for four read_file calls and one grep, serial execution makes one exploration take five times as long. If one run_command hangs on a service that never answers, a serial implementation drags the other four results down with it. Parallelism makes the batch cost the slowest call rather than the sum, and stops one slow tool from holding back everyone else's result.

Once parallelism exists, the question stops being "is it fast" and becomes "is it right": is the order preserved, is shared state trampled, where does Ctrl-C land, does one dead thread kill the turn. NanoHermes answers plainly. No async runtime, threads from thread::scope, one join barrier to close the batch, one counting gate to bound sub-agents. This post walks each place where that plain design had to be thought through.

Four levels of concurrency

LevelImplementationConcurrencyWho waits

The four numbers are different on purpose, so "how much concurrency does NanoHermes support" has no single answer. The accurate answer is: one daemon serves one session at a time; inside a turn it runs all the tool calls the model asked for; among those, at most four sub-agents run simultaneously.

The first level is the one that goes wrong, because it is the only level with no ceiling. It gets its own section.

A world without async: threads are the primitive

No tokio, no async-std, no futures. There is not a single async runtime in the dependency tree. That looks unfashionable in 2026 and is the right call for this project.

The costs are real too. Without a cancellation token, interrupts can only be checked at step boundaries, so a running tool cannot be stopped. Without select!, "did output or the timeout arrive first" needs 25 ms polling. Without structured concurrency, a panicking thread is only caught by the return value of join.

Why not async: four reasons and three costs

One. Nearly every tool is a blocking call. read_file is std::fs, run_command is spawn plus pipe reads, git is a subprocess, web_fetch is synchronous HTTP. In async, each either gets wrapped in spawn_blocking, which is still a thread, or gets replaced with an async library, which grows the dependency tree by an order of magnitude. For a single binary that aims to fit in a few megabytes, that trade is bad.

Two. The concurrency window is naturally bounded. A response contains a handful of tool calls, usually one to eight, and every turn ends by joining them all to assemble messages. Thread count therefore never accumulates over time, so the problem a thread pool solves, lifetimes longer than tasks, does not exist here.

Three. The barrier simplifies state management. Because each turn has a join barrier, self.messages is read-only for the whole parallel section. The main thread writes history only after every join returns. That means conversation history needs no lock at all. With async and select!, a tool future could interleave with a history write, and you would need a lock or a more elaborate ownership design.

Four. The compiler checks it. For Agent to be shared by scoped threads it must be Sync, and any field without a mutex fails to compile. You find the data race at build time, not in production. Async's equivalent check is Send, but since an await point can appear anywhere, the compiler cannot help with holding a lock guard across an await.

CostManifestationMitigation
No cancellation mid-taskOnce a tool starts, you wait for itCommand timeouts, 120 s default, 3,600 s ceiling
Thread stack overhead2 MiB of virtual stack per threadBounded call counts, so real RSS stays far below the peak
Blocked threads waste OS threadsA sub-agent waiting for a permit holds a threadFour sub-agents, queue length bounded by call count

That second row deserves unpacking: 2 MiB is virtual address space, not physical memory. Linux allocates thread stacks lazily, committing only the pages actually used. So "20 tool threads equals 40 MB" is wrong arithmetic; the real RSS increase is usually hundreds of kilobytes. What actually costs is the per-thread buffer, such as the 16 KiB read buffer inside read_capped.

The structure of one turn: a join barrier

let results: Vec<String> = if turn.tool_calls.len() == 1 {
    vec![self.execute(&turn.tool_calls[0])]
} else {
    // Reborrow as &Agent so scoped threads can share it (execute takes &self, Agent is Sync).
    let this: &Agent = self;
    std::thread::scope(|s| {
        let handles: Vec<_> = turn
            .tool_calls
            .iter()
            .map(|call| s.spawn(move || this.execute(call)))
            .collect();
        handles
            .into_iter()
            .map(|h| {
                h.join()
                    .unwrap_or_else(|_| "ERROR: tool thread panicked".to_string())
            })
            .collect()
    })
};

Four decisions.

One call takes the fast path. With a single tool call there is no thread at all; it runs on the current thread. That is the common case, and it saves the spawn and join cost plus the cognitive cost of the Sync requirement.

let this: &Agent = self is not redundant. The scope closure captures &mut self, since self is &mut Agent, and spawn needs move. Reborrowing explicitly as &Agent tells the compiler a shared reference is moved, not a mutable one, so Agent only needs Sync. Omit the line and the compiler complains about moving out of self.

handles.into_iter().map(join) preserves order. The result vector lines up with tool_calls by index, regardless of which thread finished first. Everything in the next section depends on this.

unwrap_or_else turns a panic into a string. join returns Err when the thread panicked, and instead of unwrapping, the code produces an error result.

The whole thing is a fork-join rebuilt every turn: start N threads, wait for all N, take N strings, append them. No pool, no queue, no long-lived worker. That throwaway model pays a spawn cost of tens of microseconds and buys an enormous simplification in state management.

Only sub-agents have a concurrency cap. Tool threads and the daemon do not. The first relies on the empirical claim that models ask for a few calls, the second is an explicit single-thread design. Neither has a hard guard.

Four is a resource number, not a performance one. Each sub-agent sends a full model request, so four in flight means four contexts at once. With a 120,000 character budget that is a 480,000 character memory peak, plus four JSON serializations. Beyond that it starts competing with the main conversation for memory and bandwidth.

Forty iterations times four equals 160. In theory a sub-agent runs up to 40 rounds, each with several tool calls, and four run at once. That is not a target, it is an upper bound, and it matters because it prices a single runaway: at most 160 model requests.

What thread::scope buys

Plain thread::spawn requires a 'static closure, so nothing on the stack can be borrowed. Sharing &Agent would mean wrapping it in an Arc and cloning that per call. scope introduces a lexical scope whose threads may borrow stack variables, and which joins everything when it ends.

No Arc overhead, and no temptation. Wrapping the agent in an Arc is not expensive by itself, but it invites Arc<Mutex<Agent>>, which serializes the entire agent. scope forces a shared immutable &Agent, so mutable shared state can only live behind the locks inside Ctx, which is exactly the right granularity.

The scope always joins. Even if a ? returns early, the scope waits for its threads on exit. That guarantees no thread is still writing state while the main thread moves on.

A panic does not leak a thread. The scope still joins a panicked thread, receiving Err, so nothing is left unreaped.

What scope does not give you is a thread count limit. The code maps over every call, so 20 calls means 20 threads. That is the unbounded first level, handled later.

Why the agent must be Sync

Sharing Agent across threads is not a design choice, it is the compiler's requirement: &Agent moves into a closure that must be Send, which means Agent: Sync.

Among its fields, only Ctx carries shared mutable state.

pub struct Ctx {
    pub root: PathBuf,
    pub auto_approve: bool,
    pub approval: crate::config::ApprovalPolicy,
    pub sandbox: crate::config::SandboxMode,
    pub max_output: usize,
    pub tasks: TaskManager,       // Mutex<HashMap<String, Task>>
    pub todos: TodoList,          // Mutex<Vec<Todo>>
    pub skills: Vec<Skill>,       // read-only
    pub board: Board,             // Mutex<Vec<Job>> + Mutex<u64>
    pub gate: Gate,               // Mutex<usize> + Condvar
    pub memory_dir: Option<PathBuf>,
}

The first four fields are immutable, the next three hold locks, and skills are read-only. memory_dir is only a path; actual memory reads and writes go through the filesystem, so two threads writing the memory file can lose an update. That comes up again under "not every tool should run in parallel".

The remaining agent fields are either touched only outside the parallel section, or carry their own locks: the MCP manager holds an Arc<Mutex>, and the UI sink is an Arc<dyn Fn + Send + Sync>.

That field layout is what makes concurrency safe: the only things mutable inside the parallel section are the five locked parts of Ctx. Anything that writes messages has to return to the main thread, which is sitting in the join barrier. It is structure bought instead of correctness checks.

Five locks in Ctx

LockProtectsTypical operationContention
TaskManager.tasksHashMap<String, Task>Start, read output, killMedium, per background call

The last two have the highest contention but the shortest critical sections: Board::seq is an increment plus a format, Gate.active is a compare and an increment. What can actually be held for a long time is TaskManager.tasks, because it reads pipes while holding the lock.

pub struct Board {
    jobs: Mutex<Vec<Job>>,
    seq: Mutex<u64>,
}

One lock would force start() to hold it while formatting an id and copying a possibly long task string. Two locks keep both critical sections tiny, and since start() always locks seq then jobs, there is no reverse path and no deadlock.

The price is that numbering and registration are not atomic together: concurrent starts can register agent-3 before agent-2, so the board's order is not monotonic in id. Harmless, since ids identify rather than sort.

Lock granularity: why the board uses two mutexes

There are three granularities in Ctx.

Coarse: one lock for a whole collection. The todo list and task manager work this way, because the todo semantics are replace-everything.

Medium: one lock per logical entity. The board separates numbering from the job list: numbering is frequent and instant, the list is occasional and longer.

Fine: one lock per entry. Not used here. If each task carried its own lock, task_output on one task would not block task_kill on another, which is exactly the task manager's biggest problem.

The test for correct granularity is not "is the lock fine enough" but "is there a path that performs blocking IO while holding it". The board's critical sections are all memory operations, so any granularity works. The task manager's output() calls read() under the lock, and no amount of refining the granularity fixes that; the structure has to change.

A condition variable and a gate in twenty lines

pub struct Gate {
    active: Mutex<usize>,
    cv: Condvar,
    max: usize,
}

impl Gate {
    pub fn new(max: usize) -> Self {
        Gate {
            active: Mutex::new(0),
            cv: Condvar::new(),
            max: max.max(1),
        }
    }

    pub fn acquire(&self) -> GateGuard<'_> {
        let mut active = self.active.lock().unwrap();
        while *active >= self.max {
            active = self.cv.wait(active).unwrap();
        }
        *active += 1;
        GateGuard { gate: self }
    }
}

Three details.

while, not if. A condition variable can wake spuriously and the predicate may not hold. Re-checking in a loop is the standard form; tutorials that use if usually get away with it on Linux, by luck.

max.max(1). Configured as zero it becomes one, because otherwise acquire() never gets a permit and the turn deadlocks. One extra agent beats a hang.

The guard returns the permit in Drop.

impl Drop for GateGuard<'_> {
    fn drop(&mut self) {
        let mut active = self.gate.active.lock().unwrap();
        *active = active.saturating_sub(1);
        self.gate.cv.notify_one();
    }
}

Drop covers all four paths: normal return, early ?, panic unwinding, and every match arm. That is RAII's real value in concurrency; nobody hand-writes a release on each return.

notify_one rather than notify_all, since each release frees exactly one slot. Waking everyone causes a thundering herd where all waiters contend and all but one go back to sleep.

The gate is in the wrong place

fn run_subagent(&self, name: &str, task: &str) -> Result<String, String> {
    let id = self.ctx.board.start(name, task);   // register first
    let _permit = self.ctx.gate.acquire();       // then queue
    let result = self.run_subagent_inner(name, task);
    match &result {
        Ok(text) => self.ctx.board.finish_ok(&id, text),
        Err(err) => self.ctx.board.finish_err(&id, err),
    }
    result
}

Two consequences.

The board lies about status. start registers the job as running. If four sub-agents already hold permits, the fifth blocks in acquire() having executed nothing, while the board shows it as running. agent_list then shows a row of running jobs, half of which are queued.

Duration includes queue time. The start timestamp is taken in start(), so a sub-agent that waited 30 seconds and ran for 2 reports 32.0 s. Every performance judgment based on the board is skewed.

The fix is a queued state and a state parameter on registration: register as queued, acquire, then mark running, and set the start timestamp at that point. Under 20 lines, and the board turns from approximately right into something you can use to see where things are stuck.

Why did it end up this way? Because the natural order is register then work, since you need an id to settle afterwards, and the gate arrived later as one line inserted right after registration. Nobody re-read the state machine. It is the most common mistake in concurrency retrofits: inserting a blocking point into an existing flow without re-checking what the code upstream of it has already done.

Sub-agents: the first real user of parallelism

Parallel tool calls are a batch of independent jobs. Sub-agents are one task handed to several specialists, and unlike tools they issue their own model requests and tool calls.

PhaseCodeShared state
Registerboard.start(name, task)Board jobs and sequence
Queuegate.acquire()Gate counter
Build configClone, override the model, disable streamingNone
Build toolsbuild_tools() filtered by allowed_tools, minus subagentNone
Build messagesOne system prompt plus one task messageNone
LoopModel call, tools, append, at most 40 roundsThe five locks
Settlefinish_ok or finish_errBoard jobs

The key point is that a sub-agent does not inherit the parent's conversation. It receives two things: its own system prompt from configuration, and one task description. That is the precondition for real parallelism. If it inherited the dialogue, four sub-agents would each copy a 120,000 character history and memory and token cost would explode.

The cost is information asymmetry: a sub-agent does not know what the parent already tried or which approaches failed. So the tool description says it suits review, testing, research, and any task that benefits from a focused specialist. It suits self-contained subtasks, not "continue from where the last step stopped".

The board records each sub-agent's task text and a 500 character result preview, and agent_list gives the parent a progress table. The design intent is to let the model decide whether to keep waiting: two done and one running for 40 seconds means it can process the finished results first. Scheduling authority goes back to the model instead of being hard-coded as "wait for everything".

Why sub-agents are serial inside

// Sub-agent tool calls run in order (the sub-agent is already bounded).
for call in &turn.tool_calls {
    let out = self.execute(call);
    messages.push(json!({
        "role": "tool",
        "tool_call_id": call.id,
        "content": out,
    }));
}

Three reasons, all valid.

Nested parallelism multiplies threads. Four sub-agents each spawning five tool threads is 24 threads. Since the subagent tool is filtered out of sub-agent tool lists, further nesting cannot happen, but serial execution is still a deliberate downgrade at the nested level.

Sub-agents rarely call several tools at once. A specialist prompt narrows the task, so a round usually has one or two calls. Parallelism would buy little.

The real reason: the sub-agent is already parallel. Four running at once, each serial inside, gives a concurrency of four, which is where the benefit already is. Going deeper has diminishing returns and linear thread growth.

The cost: five 20-second commands inside one sub-agent means 100 seconds, and the slowest sub-agent sets the turn's duration. Serial-inside moves the worst case from "the slowest single tool" to "the sum of the slowest sub-agent's tools".

There is also a wording problem in that comment. "Bounded" here means concurrency is capped, but it reads as "a sub-agent's tool calls are limited", which they are not. A better comment would say the gate already bounds concurrency and adding inner parallelism would multiply threads.

Four places a sub-agent exceeds its bounds

A sub-agent shares &self, and four things it looks like it inherits, it does not.

Interrupts. The parent checks the interrupt flag at the top of each round; the sub-agent loop has no check at all. After Ctrl-C, a sub-agent keeps going for up to 40 model requests, and the parent only sees the flag once execute returns. The fix is one line at the top of the sub-agent loop, but a plain take() would consume the flag so the parent never sees it. Use a read-only peek, or re-request the interrupt before breaking.

The iteration cap. A sub-agent uses the cloned parent config, so it inherits all 40 rounds. There is no separate limit. Forty is baked in and cannot be tuned, when a focused subtask should default to something much smaller, perhaps ten, via a field on the sub-agent definition.

The model override applies to the model call only. Tool execution runs through the parent's context, so a sub-agent configured with a cheap small model still receives up to 20,000 bytes of tool output that the small model may not be able to read.

And the worst one: allowed_tools is advertising, not a gate. It filters the list handed to the model. The actual pre-execution check uses the parent's allow and deny lists, with no reference to the sub-agent's whitelist. So if the model emits a tool name that was never advertised, and the parent config allows it, the tool really runs.

Will a model emit an unadvertised name? Normally not, but it can: it appeared in history, another sub-agent used it, or it hallucinated. This is a boundary that depends on the model's self-discipline, and a whitelist exists precisely so that nothing depends on self-discipline.

The fix is to push the whitelist into the execution path, either as an optional parameter on execute or by giving sub-agents a scoped view of Ctx. The second is cleaner and takes hours rather than minutes.

Tool threads have no cap

let handles: Vec<_> = turn
    .tool_calls
    .iter()
    .map(|call| s.spawn(move || this.execute(call)))
    .collect();

Whatever the model returns becomes threads, and that count is shaped by the number of tools and the context length. A batch task phrased as "read thirty files" can plausibly produce thirty calls.

RiskManifestation
Thread explosionTwenty threads each holding a read buffer and file contents
File descriptor exhaustionTwenty concurrent opens is fine; two hundred may not be
Unbounded total outputTwenty results of 20,000 bytes is 400,000 characters in one append

The third is the dangerous one, because its interaction with the context budget is unintuitive. clamp caps each tool's output, not the batch total. Twenty results can push messages past the 120,000 character budget and trigger compaction, which costs another model request for the summary.

The fix is not a thread cap of eight, it is a budget for the batch: keep a running total, clamp each result against what remains, and stop at 40,000 characters. A thread cap is still worth adding for resource reasons, but one number cannot solve both problems.

Result order is not optional

handles.into_iter().map(join) follows tool_calls order, so alignment is by construction.

for (call, result) in turn.tool_calls.iter().zip(results) {
    self.style.tool_call(&call.name, &summarize(&call.name, &call.arguments), &result);
    self.messages.push(json!({
        "role": "tool",
        "tool_call_id": call.id,
        "content": result,
    }));
}

zip assumes equal length and matching order. Collect results through a channel instead, first finished first delivered, and the order becomes completion order. The consequence is not mild confusion, it is a protocol error: each tool message's tool_call_id must match an id in the preceding assistant message, so misordering hands the model one tool's output labelled as another's.

A subtler version: join correctly, but filter out empty results. The vectors no longer match, zip silently truncates, and the last tool call has no tool message. The next request returns 400 saying tool_calls must be followed by tool messages, several hundred lines away from the cause.

RuleWhyIf broken

The third rule is why unwrap_or_else(|_| "ERROR: tool thread panicked") exists. A panic still has to produce a string, so the pairing survives.

What happens when a thread panics

join returns Err on panic, and the code turns it into an error string, so one tool's panic does not fail the turn. Other results are appended, the model sees the error, and decides whether to retry.

That is right, with one precondition: the lock must not be poisoned. A Mutex panicking while held poisons the lock, and every subsequent lock().unwrap() panics. Since the codebase uses unwrap everywhere, a panic while holding the board's job lock would take agent_list down permanently, turning one tool failure into a dead subsystem.

The good news is that these critical sections are short and pure memory operations, so a panic is very unlikely. The real risk is the task manager, which does IO under the lock: one panic during a pipe read poisons the whole table.

Two fixes: replace unwrap() with unwrap_or_else(|e| e.into_inner()) to ignore poisoning, or switch to parking_lot::Mutex, which does not poison. For a system that already degrades tool panics into strings, ignoring poisoning is more consistent: inconsistent data is a smaller risk than a permanently dead feature.

Not every tool should run in parallel

CombinationProblemResult
Two edit_file on one fileEach reads the whole file, edits, writes backThe later write erases the earlier edit
write_file and read_file on one fileThe read may see stale contentThe model decides on old content
Two todo_writeThe semantics are replace-everythingThe later list erases the earlier one
Two run_command needing approvalOne stdin between themPrompts interleave, answers mismatch
git_commit and edit_fileThe committed content is undefinedA half-finished state is committed

The first is the easiest to hit. edit_file is read, replace, write, so two concurrent calls necessarily lose an update, and a model can easily ask for two edits to different lines of the same file in one round, believing they are independent.

Nothing protects against it: no file lock, no mtime check. So it is not a theoretical risk. If the model does it, it is wrong.

Three levels of fix. Cheapest: say so in the description, asking for multiple edits to one file to be combined into a single call. Zero cost, depends on the model, removes most cases. Middle: serialize per file in the dispatch layer with a map from path to mutex, about 30 lines, which eliminates lost updates entirely. Thorough: tag each call with a resource and parallelize only across different resources, which is truly correct but requires annotating all 24 tools.

todo_write has an extra wrinkle under parallelism: whichever concurrent write lands last wins, while the model sees both calls report success. "Both succeeded, one took effect" is the hardest class of concurrency bug to diagnose.

Approval under concurrency: there is one stdin

pub fn confirm(command: &str) -> bool {
    eprint!("Run this command? [y/N] {command}
> ");
    let _ = io::stderr().flush();
    let mut line = String::new();
    if io::stdin().read_line(&mut line).is_err() {
        return false;
    }
    matches!(line.trim().to_ascii_lowercase().as_str(), "y" | "yes")
}

Two run_command calls needing approval in one round means both threads enter confirm(). The prompts interleave, so the user cannot tell which command is which. Two threads read the same stdin, so a single "y" may be consumed by either, and the other keeps waiting. And in a non-interactive environment, where stdin is not a TTY, both reads return EOF and both commands are denied.

This is not hypothetical: the approve policy returns true for dangerous commands, and models ask for "run the tests" and "run the build" together all the time.

The proper fix moves approval back to the main thread: parallel workers return a pending-approval marker, the main thread asks serially after joining, then runs the approved ones. That means splitting execute into a parallelizable part and an approval part, which is substantial.

The cheap version wraps confirm() in a global mutex. Prompts stop interleaving, and "the turn blocks while waiting for input" remains, but as a queue instead of a collision. For an interactive CLI that is enough, because human input is serial anyway.

Background tasks: another kind of concurrency

Everything so far is "do it together, then collect". Background tasks are "return now, collect later", which removes test runs, builds and dev servers from the critical path.

But the module has two real defects, both concurrency related, and neither theoretical.

Defect one: stderr is never drained

spawn pipes stderr, but output() drains only stdout. Nothing ever reads the other pipe.

When the child writes 64 KiB to stderr, the kernel pipe buffer fills and the write blocks. Nobody reads, so it never unblocks. The task never finishes, task_output reports running forever, stdout is quiet so it returns "no output yet", and the model keeps polling a task that will never complete.

Which commands hit this? Anything writing more than 64 KiB to stderr: compiler warnings from cargo build, progress bars from npm install, failure stacks from a verbose test run. Those are exactly the commands background mode exists for.

The fix is a thread that drains stderr into its own buffer, appending to a shared buffer. It is precisely what the foreground path already does: one problem, two implementations, one right and one wrong. The background path was presumably built minimally first and never revisited.

Defect two: reading to EOF while holding the lock

pub fn output(&self, task_id: &str) -> Result<String, String> {
    let mut map = self.tasks.lock().unwrap();          // hold the lock
    let task = map.get_mut(task_id).ok_or_else(…)?;
    if let Some(child) = task.child.as_mut() {
        if let Some(mut out) = child.stdout.take() {
            let (kept, total) = read_capped(&mut out); // blocking read under the lock
            // …
        }
    }
    // …
}

read_capped loops until EOF or error. For a task that is running and currently silent, stdout is open with no data, so read() blocks. It returns neither zero nor an error; it just waits.

So task_output on a quiet task hangs, and while it hangs the task map stays locked. task_list blocks, task_kill blocks, a new background command blocks, another task_output blocks. One poll freezes the whole subsystem: the classic error of blocking IO inside a critical section.

This is also why the foreground path is fine: it reads pipes in separate threads and only polls try_wait() every 25 ms. The same read_capped is correct in a thread and wrong under a lock.

The fix moves reads into a thread and leaves only a buffer snapshot in the lock, so the critical section is a memory copy.

Pipe backpressure, the thing mistaken for a deadlock

ShapeSymptomRoot cause
Reading stdout but not stderrThe command hangs, stdout silentstderr filled 64 KiB
Reading pipes under a lockEvery task operation hangsA blocked read holds the lock
Waiting before readingThe command never endsOutput filled the buffer, the child cannot exit

The third is the classic: wait for the exit code first, read the pipe after. A command producing more than 64 KiB writes into a full buffer, blocks, never exits, so the wait never returns and the read line is never reached. Genuine deadlock.

There is exactly one correct order: start the readers, then wait for exit. The foreground path does it, the background path gets both parts wrong. That inconsistency inside one module is why backpressure deserves a full section: it is basic competence for this kind of code, not trivia.

And read_capped keeps reading after the buffer fills, discarding. It cannot break at the cap, or the child blocks again. That is why it returns both kept and total: the total is what tells the model how much it did not see.

Interrupt: exactly one preemption point

The interrupt is checked in one place only, at the top of each iteration, and "step boundary" means after a full model round trip plus all the tool execution it triggered.

Moment of Ctrl-CDelay before it takes effect
Model streamingUntil this request ends
A tool runningUntil all tools join
A sub-agent runningUntil it finishes, up to 40 rounds
A command runningUntil it returns or times out, 120 s by default

The justification is in the comment: interrupting mid-tool leaves history with three calls and one result, and the next request returns 400. Better to be unresponsive than to break the invariant.

The cost is that the worst case can be minutes. Two things limit it incidentally: command timeouts and the sub-agent iteration cap. Neither was designed for interrupts.

A better design is a two-stage interrupt: first Ctrl-C sets the flag and prints "finishing the current step, press again to force quit", the second exits immediately. It preserves the invariant and gives the user an escape hatch, for the price of one more atomic counter.

static INTERRUPTED: AtomicBool = AtomicBool::new(false);
static DEPTH: AtomicUsize = AtomicUsize::new(0);

#[cfg(all(target_os = "linux", any(target_arch = "x86_64", target_arch = "aarch64")))]
extern "C" fn on_sigint(_sig: i32) {
    INTERRUPTED.store(true, Ordering::SeqCst);
}

A signal handler may only do async-signal-safe things, and an atomic store qualifies. The depth counter handles nesting so an inner install cannot tear down the outer handler when it exits; install on zero to one, restore on one to zero. A RAII guard created on the first line of run handles both the early-return and panic paths, and a guard against underflow protects the restore.

Where Ctrl-C actually lands

LayerInterrupt effectiveWhy
Main loopYes, at boundariesThe flag is read at the top of each round
Tool threadsNoexecute has no checkpoint
Sub-agentsNo, indirectlyNo check inside, and joining cannot be interrupted
Child processesPartlyOnly a timeout kills them; Ctrl-C does not propagate

On Linux, SIGINT goes to the whole process group from the terminal driver, so the child receives it and exits on its own; the parent's polling loop sees the exit and returns normally. "The command was interrupted" is really "the child answered SIGINT".

On Windows there is no sigaction, so installing the handler returns false and Ctrl-C takes the default action: the process dies, agent included. Ctrl-C is not "stop this turn", it is "quit the program". That is a platform difference, not a bug, but the documentation has to say so or users will assume the conversation survived.

GUIs have no terminal to send SIGINT, so there is an in-process path: a request function sets the same flag, and the stop button calls it. Same semantics, finish the current step then stop.

The daemon: concurrency zero

for stream in listener.incoming() {
    let mut stream = match stream {
        Ok(s) => s,
        Err(e) => { eprintln!("accept error: {e}"); continue; }
    };
    let peer = stream.peer_addr().ok();
    match handle_daemon_request(&mut agent, &mut store, &mut stream) {
        Ok(()) => {}
        Err(e) => { /* log */ }
    }
}

The incoming iterator blocks, and each request is handled synchronously on the same thread. So process-level concurrency is one; the second request waits in the backlog. The agent is taken as a mutable reference, which forbids concurrent handling at the type level. The session store is a plain hash map with no mutex, because it needs none.

For a single-user desktop scenario that is fine. For several clients sharing one daemon it is a bottleneck, since two sessions cannot run at once.

It still works because the real parallelism is inside the agent: one request may spawn four sub-agents and eight tool threads. Concurrency of one at the process level does not mean one thing runs at a time.

Session isolation uses an X-Session-Id header, mapping each id to its own message vector and session file. Different ids cannot see each other, and because handling is serial, that isolation is temporal rather than concurrent, which is why no locks are needed.

Supporting real concurrency minimally means one thread per connection plus Arc<Mutex<Agent>>, but then one slow session blocks every other session's model call. The correct fix is one agent instance per session, which is a refactor.

Why a single-threaded daemon still works

It is not a performance bottleneck. The bottleneck is model latency, seconds to tens of seconds per call, not CPU. Serializing two requests costs "the second waits", and running them in parallel would have the second waiting on the same HTTP response anyway.

It simplifies state. The message vector, the UI sink and the session path all stay in "used by one request from start to finish" form, so none needs a lock or a copy.

It keeps streaming simple. The stream sink holds an Arc<Mutex<TcpStream>> so tool threads can write NDJSON lines to one connection. Share that agent between two requests and the sink points at the wrong client. That is another hidden dividend of the single-thread model.

So the real boundary is: one user, one task, serial is acceptable. Outside it, refactor; inside it, the design is right.

The first three cause visible failures in real use; the last four need specific conditions. Defect seven has the best return on effort at five lines, while one and two are small in code but change data structures, affecting output, list and kill.

There is also one not in the table: mutex poisoning. Every lock().unwrap() fails in a cascade after a panic while held. It is rare but permanently disabling rather than transient, and the fix is ignoring poisoning or switching to a non-poisoning mutex.

How to verify that concurrency is actually correct

"Ran it once and nothing crashed" proves nothing. NanoHermes keeps a dedicated test module that drives the real parallel path, with and without MCP, so data races surface there rather than in production.

Shared state in built-in tools: ten groups of three tools, thirty threads at once, which checks that nothing mutable in Ctx is unprotected.

MCP mixed with built-ins: eight concurrent MCP echoes, three MCP helpers and two built-ins. This exercises the MCP request and response pairing: eight requests each expecting their own answer, where any id mismatch makes one echo receive another's result and fails the assertion immediately.

The gate itself: six threads for two permits, asserting the peak never exceeds two and the counter returns to zero. The second assertion matters most, because a forgotten release fails here instead of showing up as "gets slower over time" in production.

LimitationConsequenceSupplement
Races found by luckEverything may pass while a race remainsMore threads, more repetitions
No memory ordering checksSubtle ordering bugs stay hiddenThreadSanitizer or Miri
No panic simulationPoisoning paths untestedDedicated panic injection tests

A stricter tool is Loom, which exhaustively explores thread interleavings and finds races in seconds, at the cost of swapping in Loom's mutex and condition variable behind a cfg flag. For this project the intrusion outweighs the benefit, but it is worth knowing it exists.

Practical advice: keep concurrency tests in their own module, run once with a single test thread and once with the default parallel test harness. Passing both tells you more than passing one.

Six principles of concurrency design

One. Draw the parallel region before discussing concurrency. NanoHermes has exactly one, the execution of a tool batch, bounded by one scope. Everything outside it is safe by construction. With a fuzzy boundary, every piece of state needs a lock and complexity doubles.

Two. Use the join barrier to eliminate locks. The main thread waits at the barrier, so history is read-only for the whole parallel section. Trade a little latency for a whole class of synchronization problems disappearing.

Three. Any IO while holding a lock is wrong. Both task-manager defects violate this. Critical sections hold memory operations only; IO goes on a thread or becomes non-blocking plus polling.

Four. Bounded concurrency needs RAII to return permits. Drop covers every return path including panics. Hand-written release always misses one, and the missed one is the exceptional path, which is also the least tested.

Five. Fewer interrupt points means clearer semantics. Checking in one place buys history that is always consistent, at the cost of worst-case delay that timeouts and a two-stage interrupt can soften. An interruptible-anywhere implementation will almost certainly leave half a turn in history.

Six. Caps and bounds are separate designs. Sub-agents are capped at four, tool threads are not; a single output is capped at 20,000 bytes, a batch total is not. Where there is a cap, it prevents exhaustion; where there is none, the assumption is that the count stays small, and a prompt change will eventually break it.

Closing

The interesting part is not how to start threads, which is a dozen lines. It is where the boundaries are: what can be mutated inside the parallel region, which operations are bounded, which are not, which semantics break under parallelism, and which delays are designed in.

NanoHermes is not perfect. Two of its seven defects genuinely hang the feature. But the skeleton is right: one clear parallel region, one join barrier, one RAII-counted gate, one interrupt point. Those four things are under sixty lines and they carry the entire concurrency model.

Avoiding an async runtime is not a religious position, it is a cost calculation. For this project the total cost of threads and a barrier, tens of microseconds to spawn, 2 MiB of virtual stack, no mid-task cancellation, is far below the cost of the async ecosystem, the dependency tree, the state held across await points and the complexity of Send checks. Change the scenario to one that must hold thousands of long-lived connections and the arithmetic flips.

The next post is security: letting it run commands without losing control. Concurrency answers "how many things at once", security answers "what may those things do", and the two meet on exactly one line of code, the approval check, which is where defect seven lives.
