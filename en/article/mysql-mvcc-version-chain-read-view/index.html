MySQL MVCC: version chains and how a read view decides visibility

2026-11-04 · 14 min · Stack Frame

Who this is for: people who can recite "read committed sees the latest, repeatable read sees a snapshot" but cannot say where the snapshot lives; people whose disk filled up because a long transaction held purge back; people wondering why a locking read returns a different value from a plain select.

TL;DR: InnoDB's MVCC does not store multiple copies of a row. There is one current record, the old values live in the undo log, and a pointer in the record header chains them together. A read takes a read view, walks the chain backwards, and stops at the first version visible to it. The only difference between read committed and repeatable read is how often that view is created.

Reading time around 14 minutes. Level: advanced.

The same row, two different values

CREATE TABLE account (
    id      BIGINT PRIMARY KEY,
    balance INT NOT NULL
) ENGINE=InnoDB;

INSERT INTO account VALUES (1, 100);

Two sessions open transactions at repeatable read. Session A reads a balance of 100. Session B updates it to 200 and commits. Session A reads again and still sees 100.

A read after B's commit, showing the old value. People explain it as "A read a snapshot", but what the snapshot is, where it lives and when it is taken is usually left vague. The answer has three parts: hidden columns, the undo log, and the read view.

Hidden columns: the skeleton of the version chain

Hidden columnBytesPurpose
transaction id6The transaction that last modified this row
roll pointer7The previous version of this record in the undo log
row id6A generated id when there is no primary key

The transaction id says who changed it, the roll pointer says where the previous version is. Together they are the entire metadata of the version chain. Note that the transaction id records only the last modifier; history is not in the clustered index, it is in the undo log.

The undo log: where old versions actually live

Every update or delete writes an undo record holding the value before the change and a pointer to the previous undo record. There are two kinds: insert undo, produced by inserts, used only for rollback and discardable soon after commit; and update undo, produced by updates and deletes, used both for rollback and for MVCC reads, so it must survive until no transaction needs it.

An update undo record holds roughly the old primary key, the old values of the changed columns, a pointer to the previous undo record, and header information such as the transaction id and undo type. All historical versions of one key therefore form a singly linked list: the newest in the clustered index, the oldest at the tail of the undo log.

How the chain is strung together

trx 10: balance = 100   (the original insert)
trx 20: balance = 150
trx 30: balance = 200

The cluster index holds balance 200 with transaction 30 and a pointer to undo 30, whose old value is 150 with a pointer to undo 20, whose old value is 100 with a pointer to the insert undo. Reading walks that chain: if transaction 30 is not visible, step back to 20, then to 10, until a visible version appears or the chain ends, which means the row did not exist when the view was taken. The chain is not on the data pages; it hops between data pages and undo pages.

The four fields of a read view

FieldMeaning
active idsTransactions still running when the view was created
minimum active idThe smallest id in that list
next transaction idThe next id the system had not yet assigned
creator idThe transaction that created this view

The active list is what decides whether a row was touched by something uncommitted. The two boundaries say that anything below the minimum has certainly finished, and anything at or above the next id started after the view existed.

The full visibility rule

  1. If the record's transaction id equals the creator id, it is visible. Your own change is always yours to see.
  2. If it is below the minimum active id, it is visible, because that transaction finished before any of the active ones.
  3. If it is at or above the next id, it is not visible, because it started after the view.
  4. If it is in the active list, it is not visible, because it was still running when the view was created.
  5. Otherwise, visible.

The intuition: committed before the view was taken, visible; uncommitted when the view was taken, invisible; started after the view, invisible. When the current version is not visible, follow the roll pointer to the previous version and repeat.

The only difference between the two levels

LevelWhen the view is createdEffect
Read committedAt the start of every snapshot read statementEach statement sees the latest committed data
Repeatable readAt the first snapshot read in the transactionThe whole transaction reuses one view

A frequent misconception: the repeatable read view is not created at BEGIN, it is created at the first real read. Write first and read later, and the view is taken at that read. To fix it at transaction start, use START TRANSACTION WITH CONSISTENT SNAPSHOT, which matters at repeatable read; at read committed the view is still per statement.

Snapshot reads and current reads

MVCC applies only to snapshot reads, meaning ordinary selects. A current read reads the newest version and locks it: SELECT ... FOR UPDATE, SELECT ... FOR SHARE, and the write statements themselves. A current read bypasses the read view entirely, and if the newest record is locked elsewhere it waits, governed by the lock wait timeout.

Which explains a common observation: in one transaction, a plain select shows the old value while a locking read shows the new one. That is not inconsistency, it is two different read semantics.

What happens on an update

  1. Locate the newest record for the key with a current read and take an exclusive lock.
  2. Write the old value into a new update undo record.
  3. Modify the clustered index record: new value, new transaction id, roll pointer to the new undo.
  4. Maintain any secondary indexes over changed columns.
  5. After commit, the undo record is not removed; purge decides later whether any older view still needs it.

Step five is the root of the long transaction problem. A transaction that runs for ten minutes prevents cleanup of every undo record produced after it started.

Delete marks and purge

A delete usually marks the record rather than removing it. The record and its version chain remain, invisible to new views. Physical removal is the purge thread's job: it scans the undo log for useless update undo, and if the corresponding record is delete-marked and no older view needs it, removes the record from the page. Removing records can trigger page merges, and emptied pages can return to the freelist.

So a table that does not shrink after deletion is normal. The delete only marked, and space only becomes reclaimable after purge catches up, while in-page fragmentation and unmerged pages need a rebuild to tidy.

Why long transactions are dangerous

  • Undo cannot be cleaned, so the history list grows and the undo tablespace swells.
  • Purge falls behind, and once the purge lag threshold is reached new transactions are delayed and write throughput drops.
  • Version chains get longer, so every read walks more nodes and burns CPU.
  • Replication lags, because a large transaction generates a burst of binlog that the replica has to replay.
SELECT trx_id, trx_state, trx_started, trx_isolation_level
FROM information_schema.INNODB_TRX
ORDER BY trx_started;

The older the start time, the more suspicious. Then check the history list length in the transactions section of the engine status output. A value that keeps climbing usually means a long transaction or purge that cannot keep up.

Observing the chain and the history list

SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.events_transactions_current;

The lock tables show what a current read has locked, and the transaction events show state and isolation level. Page-level detail needs a tool that decodes index pages, which shows the hidden transaction id, the roll pointer and the deleted-byte counter. Do not run that against production; a replica or a test copy is safer.

Five common misconceptions

MVCC stores several copies per row. It does not. One current record, old versions in the undo log.

The repeatable read view is created at BEGIN. It is created at the first snapshot read, unless you ask for a consistent snapshot explicitly.

Repeatable read eliminates phantoms entirely. A snapshot read does not see newly inserted rows, but a current read does, and gap locks are what block the inserts. Mixing the two kinds of read still produces surprising results.

A locking read is also a snapshot read. It is a current read: newest version, plus locks.

Undo is released at commit. It waits for purge to confirm no older view needs it, and long transactions stretch that interval.
