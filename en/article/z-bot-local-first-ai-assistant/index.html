Z Bot: building a local-first personal AI assistant

2026-11-05 · 55 min · Stack Frame

Who this is for: people who want an AI assistant on their own machine without handing chat history and file paths to a cloud; people building desktop agents in Electron and fighting permissions, paths and packaging; people who want to see where a local-first product has to compromise.

TL;DR: the core of Z Bot isn't "plug in a model". It's putting the model inside a box the main process controls. The database, keys, tool execution and system capabilities all stay in the main process, and the renderer gets only a whitelisted API. Every action with a side effect asks for permission first. Memory starts with SQLite FTS5 rather than a vector store. Reminders, context and retries all have hard caps.

Reading time around 55 minutes. Level: advanced.

Why build a local-first personal assistant

Cloud chat products are already strong, but "personal assistant" and "general question answering" are different products. General Q&A doesn't need to know your project directories, last week's todos or your writing voice. A personal assistant does, and that information naturally should not leave the machine.

Z Bot starts from a plain idea. Keep personal context, long-term memory, tasks and reminders in a local SQLite database. Let the model handle reasoning and generation. Execute file reads, web fetches and reminder creation on the machine, with the user's authorization each time.

That positioning brings three hard constraints.

Data has to be explainable, backup-able and deletable. There must be no state where memory lives in some cloud table that the user can neither see nor remove.

The model has to be swappable. OpenAI, OpenAI-compatible endpoints, Anthropic, Google and Ollama all work. The product can't lock anyone to one vendor.

The assistant has to be resident. It has to keep standing by after the window closes, send system notifications and read local files. That makes it a desktop application rather than a web page.

Z Bot isn't a coding agent. Its loop is understand, remember, reason, help, act, learn, and the focus is personal context and daily tasks rather than editing a repository. The README says plainly that complex software work belongs to a specialized agent such as NanoHermes, while Z Bot understands the request, dispatches work, receives results and reminds the user. That boundary matters. The moment it sees itself as a general coding agent, the tool set, the permission model and the context budget all run out of control.

Local-first has costs too. There is no multi-device sync and no server push. A new machine means reconfiguring models and authorized directories. Reminders are reliable only while the process is alive, with no catch-up after a full exit. And local OCR is capped by whatever engine Windows ships. Those costs recur throughout this post, so it is worth stating the product boundary before the technical choices.

Architecture: the main process and six packages

The stack is Electron 45, React 19 and TypeScript 6. The database is Node's built-in SQLite module, with FTS5 for search. The repository is a pnpm workspace with six packages: shared, database, model, memory, tools and bot-core. The desktop application sits in apps/desktop. Tests are 32 unit tests plus 2 end-to-end tests, covering path guards, memory deduplication, reminder recurrence, provider normalization, the runtime and project-stall reminders.

The layering is direct.

  • shared holds types, Zod schemas, IPC channel constants and default settings.
  • database wraps the SQLite module, migrations and individual stores.
  • model collapses five provider kinds into one streaming event shape.
  • memory owns writing, deduplication, retrieval and prompt formatting.
  • tools is the registry, the path guard, the web safety policy and the concrete tools.
  • bot-core is the runtime, the context manager, the permission manager, intent routing and the agent loop.

The Electron main process in apps/desktop assembles those packages and exclusively owns the database, secrets, tool execution and system capabilities.

One conversation flows like this. The renderer calls chat.send through preload. The IPC layer validates the payload with Zod. The runtime's startChat immediately writes the user message and an empty assistant message, creates a request id and an abort controller, then runs asynchronously. Execution first judges intent. A direct answer takes one model call; a multi-step task enters the agent loop. Model events are normalized into one chat event shape and pushed back over chat.event. Tool calls pass through the permission manager first, results are appended to the message array, and the assistant message is persisted at the end.

Two database decisions deserve their own paragraphs.

Why the built-in SQLite module. It avoids native compilation, so the installer never faces node-gyp or ABI mismatches. The cost is a synchronous API, which puts every query on the main process's single event loop.

Z Bot manages that in five ways: short transactions, serialized migrations, WAL mode, synchronous=NORMAL and a 5-second busy timeout on open. Before exit it runs a WAL checkpoint. Before a version upgrade it copies the whole database as a backup. It didn't move the database to a worker, so a long query can still stall the window and IPC.

Problem 1: a synchronous database on the main process

Symptom. During migrations, bulk queries or checkpoints, window events and IPC responses can be blocked by the same thread. The interface looks briefly unresponsive.

Cause. The database API is synchronous, and Z Bot deliberately gives the main process exclusive ownership without a worker or a separate database process.

Fix. WAL raises read and write concurrency, synchronous=NORMAL lowers the fsync cost per commit, the busy timeout is set on open, migrations serialize inside an immediate transaction, a checkpoint runs before exit, and upgrades are guarded by the schema version with a full backup taken first.

Cost. The root problem of a synchronous API doesn't disappear, it is confined to short transactions. A full export, an index rebuild or log searching over a large model history would still need a worker thread. This version chooses simplicity over throughput.

Process boundary: what the renderer can and can't do

The first rule of Electron security isn't to hand Node to a page. Z Bot's window uses context isolation, no Node integration and a sandbox. The renderer has no require, no process and no filesystem.

What the page can load is narrowed by CSP as well: only self and a custom media scheme, not arbitrary HTTPS. All web permission requests are denied by default, so camera, microphone, geolocation and notifications never open just because a page asked once.

Attachments are capped before saving: 25 MB each, at most 6 per message. That keeps one conversation from blowing up local storage and later requests. Attachment images are read through a custom protocol of the form zbot-media://attachment/<id>. The main process accepts only the attachment host, treats the path as an attachment id, looks it up in the database and the attachment directory, returns 404 when missing, and adds a restrictive CSP to the response.

The renderer therefore can't reach an arbitrary local path. It can only reach an image that is already recorded in the attachment table. That's far safer than exposing file URLs, but it also means attachments must pass through the main process first and can't be dropped into an image tag from anywhere.

Preload is the only bridge. It exposes one API object through the context bridge, with roughly 40 methods grouped under app, chat, conversations, memory, settings, providers, web search, projects, roots, tasks, todos, reminders, home, permissions, clipboard, screenshot and events. Raw IPC is never handed over, so the page can't compose channel names or listen to arbitrary events.

Event subscriptions are closed off in the same way. The chat event, navigation, screenshot and theme subscriptions all return an unsubscribe function, wrapping the listener internally before removing it. That looks cosmetic and actually fixes listener leaks after React unmounts: callers can unsubscribe in an effect cleanup without remembering which function reference they passed.

This boundary isn't "configure once and stay safe". Add one generic invoke method to preload and the whitelist is decoration. Expose a shell open call directly to the renderer and the path guard is bypassed. Z Bot keeps every IPC channel in one registration file behind a uniform wrapper with per-channel schemas, but a few channels slipped through, and they are covered below.

IPC contract: whitelist, Zod and redaction

IPC registration goes through one wrapper that takes a channel, a handler and an optional schema. Each call validates the raw payload with Zod. The strict schema mode rejects extra fields, so the renderer can't smuggle unexpected properties in. A validation failure turns the issue list into a readable message. A handler throw passes through a redaction function before the message goes back to the renderer. Logs record one failure line per channel, without raw keys, tokens or cookies.

ipcMain.handle(channel, async (_event, raw: unknown) => {
  try {
    const input = schema ? schema.parse(raw) : raw;
    return await handler(input);
  } catch (error) {
    logger.warn({ channel, error: redactErrorMessage(error) }, 'ipc request failed');
    throw new Error(redactErrorMessage(error));
  }
});

The value here is safe by default. Adding a channel forces an explicit decision about a schema, and a channel without one stays visible in review.

There is also an obvious gap. The third argument is optional, so two channels genuinely have no schema: the open-path channel and the search-key channel. The first only checks that the target string sits inside the data directory, and the second uses the incoming value as a string directly. Neither is the most dangerous channel, but together they show that a uniform wrapper isn't uniform validation.

Problem 2: inconsistent IPC surface and validation

Symptom. The open-path and search-key channels have no schema. Clipboard read and screenshot capture execute over IPC without a permission prompt, while tools with the same names go through the permission manager. More subtly, the renderer never calls those two channels, so they are high-privilege surfaces that exist unused.

Cause. IPC is the UI's fast path and tools are the model's controlled path. The two evolved separately, and the permission model only covers the second. Optional schema arguments make omissions easy.

Fix. The open-path channel compares paths relatively instead of by naive string containment. Secret-writing channels accept only strings and go through the encrypted secret service. Logging and error messages are redacted uniformly. Clipboard and screenshot tools go through full permission confirmation, with the risk written into the prompt.

Cost. Unused high-privilege IPC stays on the attack surface. The right move is deleting channels nobody needs, or giving them a schema and a confirmation. The repository keeps them because the UI may need them later, so this is an explicit to-do rather than a solved problem.

Problem 3: secrets on disk and redaction in logs

Symptom. Model API keys and web search keys are sensitive. Written in plaintext or leaked into logs, even a local application exposes them.

Cause. A desktop app has to persist keys, but the OS keychain facility is unavailable in some Windows environments. Logs, error messages and IPC payloads can all carry configuration objects.

Fix. The secret service throws when encryption is unavailable instead of saving plaintext. The database stores the encrypted value. Outbound DTOs strip the encrypted field entirely and tell the UI only that a key is configured. The logger redacts key, password, cookie and encrypted-key fields including nested variants, and error messages get a regex pass as well.

Cost. The OS keystore is tied to the system credential service, so keys can't be decrypted after a machine change or a broken profile, and the user has to re-enter them. Redaction is a double line of defense, field names plus regex, and it still can't guarantee that a key concatenated into an arbitrary string is caught. For a local application that is an acceptable compromise, not absolute safety.

Permissions: declare first, confirm every time

Registering a tool doesn't make it runnable. Every tool calls its permission declaration before executing, producing a spec with title, description, risk level, scope and operation list. The permission manager checks persisted rules first: an allow hit passes, a deny hit rejects. Only a miss creates a permission request, pushes it to the UI over a chat event, and awaits the user's decision.

tool.run()
  -> getPermission() -> ToolPermissionSpec
  -> PermissionManager.authorize(spec)
       -> rule allow / deny
       -> miss: chat.permission -> wait for the UI
       -> AbortSignal cancel -> cancelForChat

Users have four choices: deny, allow once, allow for the scope, or cancel the task. Allow-once is deliberately not persisted, so the same action asks again next time. Allow-for-scope persists on the pair of tool name and scope, where the scope is usually an authorized directory or an operation type. Deny doesn't run the tool and returns a tool result saying the operation wasn't executed, so the model learns the path is blocked and the conversation doesn't collapse. Cancellation rejects every pending promise through the abort signal, so a permission dialog never hangs forever.

The key idea is that a denial isn't an exception. Many agent implementations throw when a tool is refused, which leaves the model blind to the reason and retrying the same action next turn. Z Bot makes denial an ordinary tool result: the model can take another route or explain why it didn't act.

The cost is that the model may ask for the same permission repeatedly. There is no soft "don't ask again in this conversation", only persisted deny rules.

Scope granularity is a separate question. Allow-for-scope binds a tool and a scope, not specific arguments. Once write access to a directory is allowed, later writes there never prompt. That matches the goal of reducing interruptions, but high-risk tools then depend on scopes designed narrowly enough. Z Bot models write, delete and batch move separately, sends deletes to the Recycle Bin and previews batch operations first, which is using tool design to compensate for permission granularity.

Tasks and permissions also interact. If the agent stalls while waiting for permission, the task state becomes waiting for permission. On application exit, the runtime marks running and pending tasks as paused, so a restart never automatically replays an interrupted task that may already have had side effects. That trades automatic resume for never quietly deleting or moving files again.

Path safety: an authorized directory isn't a string prefix

The first gate for every file tool resolves an authorized path. It rejects relative paths, drive roots, device paths and UNC shares, caps the length at 4096 bytes, and refuses embedded NUL bytes. Then it canonicalizes the target and checks containment against every authorized root's real path. Writes additionally require that root to permit writing, and the existence and kind checks verify whether the target is a file or a directory.

Containment must not use a string prefix. A directory named Documents and a sibling named Documents-evil differ by a suffix, and a prefix check misjudges them. Z Bot computes a relative path, rejects parent traversal and absolute escapes, and lowercases both sides on Windows before comparing. That detail is easy to miss in cross-platform code, and missing it is a directory traversal bug.

Problem 4: Windows 8.3 short paths broke the test assertions

Symptom. A test creates a temporary directory and compares it against a canonicalized path. The two differ, and the test fails on Windows. Two commits fixed tests for exactly this.

Cause. Windows generates 8.3 short names for long paths, so the temporary directory and its real path can come back in different forms. The test compared strings while production code canonicalized, so the test concluded the product was wrong when the assertion wasn't normalized.

Fix. Tests normalize their expectations the same way. Production code resolves path components level by level, reattaches missing segments to the real parent, and lowercases before comparing.

Cost. Path canonicalization is best effort, not cryptographic equivalence. Short names, casing and junctions can make two strings look different or identical. Tests have to follow platform behavior rather than assume POSIX semantics.

Problem 5: symlink escapes and targets that don't exist yet

Symptom. Canonicalizing only the target makes a not-yet-created write path fail with a missing-file error. If the target is a junction or a symlink pointing outside the authorized directory, canonicalization lands outside the root. The two failures are opposite: one false positive, one false negative.

Cause. Write targets often don't exist and can't be required to resolve, and a symlink can carry a path outside the authorized range after resolution, so checks are needed before and after.

Fix. A helper walks upward from the target to the nearest existing parent, at most 64 levels, collecting missing segments, resolves that parent, then reattaches the segments in order. Roots are canonicalized too. The kind check rejects symbolic links after a link status call. A Windows system-directory blacklist rejects the system root, Program Files and similar locations.

for (let index = 0; index < 64; index += 1) {
  try {
    const canonical = await realpath(current);
    return resolve(canonical, ...missing.reverse());
  } catch (error) {
    const code = (error as NodeJS.ErrnoException).code;
    if (code !== 'ENOENT' && code !== 'ENOTDIR') throw error;
    missing.push(basename(current));
    current = dirname(current);
  }
}

Cost. A time-of-check to time-of-use window remains. An attacker can swap a parent directory for a link between the check and the write. The 64-level cap rejects very deep paths, and the system blacklist depends on environment variables that may be missing. The guard stops ordinary mistakes and naive attacks, not a kernel-level sandbox.

The agent loop: when to answer, when to act

The first step of starting a chat isn't calling the model. It's persisting. The runtime confirms or creates the conversation, writes the user message, updates the title, and writes an empty assistant message. Then it creates the request id and abort controller, emits a started event, and runs asynchronously.

That ordering guarantees the user message and a failure placeholder exist even if the model call fails, so the interface never shows a message that was sent but is missing from history.

Two shortcuts sit at the entrance. The first is an explicit memory pattern: sentences that begin with "remember" go straight to memory writing without a model call. The second is intent routing: short sentences, greetings and questions take the direct path, while todos, reminders, files, web requests and long sentences take the agent path. Routing isn't a semantic classifier but an ordered set of regular expressions, which is cheap, testable, needs no extra model call, and is occasionally wrong.

Direct mode calls the model once, which suits "explain this concept" or "write one line of copy". Agent mode loops: the model emits text and tool calls, results are appended to the message array, the model is called again, and the loop ends when there are no more tool calls or a cap is reached.

The loop allows at most 20 steps, 30 tool calls and a 5-minute total timeout. Usage and retry counts accumulate on the task record. If a tool result fails its own verification, the step is marked failed rather than pretending success.

Problem 6: the boundary of regular-expression routing

Symptom. Routing depends only on keywords and sentence length. A chatty sentence containing the word "file" can enter the agent, while a long sentence with no keyword that genuinely needs several steps can be misrouted.

Cause. There is no trained classifier and no model call to judge intent first. Regular expressions plus an 80-character threshold were chosen to save a call and reduce latency.

Fix. High-frequency intents became separate patterns, matched in a fixed order: memory, todo, reminder, web, system, file, recall, image, greeting, question, short sentence. Explicit memory and shortcuts short-circuit before routing. Long or unclassifiable requests default to the agent, spending one extra tool loop rather than treating a multi-step task as chat.

Cost. Pattern maintenance grows with every intent, and mixed Chinese and English or colloquial phrasing slips through. The 80-character threshold is empirical, not semantic. A small local classifier could replace this layer later; that has not been done.

Context budget: how 72,000 characters get spent

Z Bot doesn't stuff the whole history into the prompt. The context manager loads the project, the authorized roots and the relevant memories, assembles the system prompt, and then fills history against a character budget.

The total budget is 72,000 characters. History holds at most 20 messages, newest first, and any single message is truncated to 8,000 characters. The current user input is cut at 20,000. OCR text is capped at 24,000 characters and wrapped in a tag that tells the model plainly it is untrusted data rather than instructions.

Memory retrieval uses the first 500 characters of the current question as the query and takes 8 full-text hits. If fewer than four arrive, it tops up with the four most recent by project and time, deduplicates, and caps at eight. Ordering is by BM25 ascending, then importance descending, then update time descending. The strategy is conservative: give a few recent memories rather than let the model answer with none.

History loading is short code with a clear boundary.

let remaining = Math.max(0, maxChars - system.length);
const selectedHistory: LlmMessage[] = [];
for (let index = history.length - 1; index >= 0; index -= 1) {
  const message = history[index]!;
  if (message.content.length > remaining) break;
  selectedHistory.unshift(message);
  remaining -= message.content.length;
}

Problem 7: one oversized message ends the loop

Symptom. When a single historical message is longer than the remaining budget, the loop breaks and no older messages load at all. One long old reply truncates the entire history instead of being skipped.

Cause. The implementation chose to load continuously from newest backwards, which keeps the context as one contiguous run with no holes. The cheapest way to handle a message that doesn't fit is to stop.

Fix. Each message is truncated to 8,000 characters first, which lowers the chance of hitting the case at all. The system prompt and memories are kept inside the budget. The current user message is truncated separately and never competes with history.

Cost. This is a known rough edge. Skipping the oversized message and continuing with older ones would be more reasonable, and budgeting in tokens rather than characters would be more accurate. Neither is done, because contiguous history helps the model and the 8,000-character cut already excludes most cases.

Character budgets carry another error. Chinese, English and code have different token densities, so 72,000 characters isn't 72,000 tokens. Characters were chosen because they can be estimated cheaply without a tokenizer, at the risk of occasionally exceeding the model window. Provider errors surface in the interface as model error codes, so the user sees the failure rather than a silently dropped message.

The model layer: streaming, retries and the fallback boundary

The provider layer wraps OpenAI, OpenAI-compatible endpoints, Anthropic, Google and Ollama. The first four use official or compatible SDKs. Ollama goes through the OpenAI-compatible interface, at the usual local address by default.

The AI SDK's streaming call performs the request, and Z Bot normalizes its output into its own events: text delta, tool call, finish, usage, error and aborted. The agent above never needs to know which provider is in use or how each one streams.

The retry policy is at most three attempts per provider, with backoff of 500 ms, 1000 ms and 2000 ms. The SDK's own retry is set to zero, so a second layer doesn't retry underneath. Only retryable errors retry; configuration failures such as a missing key or a missing base URL fail immediately. The fallback model is used only after every primary attempt fails, and never once text has already been emitted.

const retryable = normalized instanceof ModelRequestError ? normalized.retryable : true;
if (!retryable || attemptNumber >= maxAttempts || textEmittedRef.value) {
  break;
}
retries += 1;
await delay(500 * 2 ** (retries - 1), signal);

Problem 8: retries duplicated text in the interface

Symptom. Streaming has already produced a few words, the request fails midway, the retry answers from the beginning, and the interface shows partial text followed by a complete answer.

Cause. Retry logic cared only about "the request failed" and not about whether visible deltas had already been emitted. The SDK could also retry internally and amplify it.

Fix. A flag records whether this attempt emitted any text delta. Once true, the current provider may not retry and fallback is forbidden. The provider sets its own retry count to zero, concentrating retries in one layer.

Cost. Emitted partial text isn't retracted, so a user may see half a sentence followed by an error. And if the model fails after a tool call, retry is also forbidden and the task simply fails. This buys "no duplicates" over "always succeed", which is the right trade for chat.

The 5-minute overall timeout is a second gate covering the whole conversation rather than one request. When it fires, the abort controller cancels the running stream, permission waits and tool execution, and the run is marked cancelled rather than treated as a successful partial answer.

Memory: no vector store, full-text search first

Memory has five kinds: user, project, event, task and global. Rows live in a strict memories table holding content, kind, project id, importance, confidence, expiry and archive time. Tags live in a separate table with cascading deletes. Retrieval uses an FTS5 virtual table, contentless-linked to the memories table, kept in sync by three triggers for insert, update and delete.

Chinese retrieval is the most underrated problem in this area. The default FTS5 tokenizer targets space-separated languages, so a whole Chinese sentence tends to become a single token and a query matches only an exact phrase. Z Bot switches to the trigram tokenizer, indexing three-character windows so phrases can be matched partially. Queries shorter than three characters can't use FTS, so they degrade to a substring scan.

CREATE VIRTUAL TABLE memories_fts USING fts5(
  content,
  content='memories',
  content_rowid='rowid',
  tokenize='trigram'
);

Problem 9: the default FTS5 tokenizer doesn't split Chinese

Symptom. English keywords match and whole Chinese sentences don't. After switching the tokenizer to trigram, two-character queries stop matching entirely.

Cause. The default tokenizer expects spaces, and Chinese has none. The trigram tokenizer needs at least three characters to build a window.

Fix. The table is created with the trigram tokenizer. Queries of three or more characters use a full-text match with the query quoted and inner quotes escaped. Shorter queries use a case-folded substring scan. A test covers the degraded path specifically with a two-character word.

Cost. A trigram index is larger than the default and costs more on write. Two-character queries become full scans and get slower as memory grows. There are no synonyms, no pinyin and no semantic recall, so "go live" and "release" stay unconnected. Version 0.1 accepts those limits and defers a vector store.

Memory has exactly two write paths. The entry pattern recognizes an explicit "remember" instruction and writes directly, or the model calls the remember tool during a conversation. The second is gated by an auto-extract switch; with it off, the model can't write on its own. There is no post-conversation extraction pass, deliberately, because that needs extra model calls plus handling for duplicates and hallucination. Version 0.1 first makes "the user explicitly said remember" reliable.

Deduplication is exact equality after normalization: same kind, same project, and equal case-folded trimmed content. A hit takes the larger of importance and confidence and merges tags. There is no semantic dedupe and no decay scoring. Expiry only archives rows, with no time-decayed ranking. Retrieval orders by BM25, then importance, then update time, which is simple, explainable and fast enough.

This system is closer to an index than to a brain. It doesn't summarize conversations, and a memory that went unused never loses weight. Its strength is that every item can be seen, edited and deleted in the interface, so a user can explain why the model mentioned something. For a personal assistant, explainability matters more than recall.

Reminder scheduling: the ceiling of the timer

The scheduler is light. Each enabled reminder gets one timer, and a refresh call clears every timer and re-plans when the app starts or a reminder changes. A fired reminder writes an event, sends a Windows notification according to settings, and computes the next trigger. One-off reminders are disabled, and recurring ones advance to the next future moment.

The problem is the timer ceiling. Node's timer delay overflows above 2^31 minus 1 milliseconds, which is about 24.8 days, and an overflowing delay fires immediately. Z Bot clamps to just under that value, sleeps one segment, then re-reads the reminder and re-plans, forming a chain.

const MAX_TIMEOUT = 2_147_000_000;
const delay = reminder.triggerAt - Date.now();
if (delay > MAX_TIMEOUT) {
  const timer = setTimeout(() => {
    this.timers.delete(reminder.id);
    this.schedule(this.reminders.get(reminder.id) ?? reminder);
  }, MAX_TIMEOUT);
  timer.unref?.();
  this.timers.set(reminder.id, timer);
  return;
}

Problem 10: long reminders overflowed the timer

Symptom. A reminder set a month out fires immediately after startup.

Cause. The timer delay is a signed 32-bit value. Past the maximum it wraps to a negative number or zero, and the timer runs at once.

Fix. Sleep one segment and re-read the reminder in the callback. Treat a negative delay as zero so an already-overdue reminder fires once. Disable one-off reminders after firing, and advance recurring ones instead of replaying missed occurrences.

Cost. Chained re-planning requires the process to stay alive. A full exit loses the timers and missed reminders never fire, which the README states plainly. It doesn't use Windows Task Scheduler, and it doesn't scan at startup for reminders that should have fired in the last 24 hours, because catch-up policy is a product decision, whether to fire once or fire every missed occurrence, and version 0.1 declines to choose.

There is one more boundary. At startup a negative delay fires immediately. For a one-off reminder that surfaces an overdue item. For a recurring one it fires the current occurrence and advances, without replaying every missed day. The semantics are right, but a user expecting a full catch-up will feel one is missing.

Proactive checks and task recovery

The proactive service handles project-stall reminders. It checks ten seconds after start and then every six hours. A running flag prevents re-entry, so a second check can't stack on the first.

Each pass reads 400 events and finds the latest inactivity notification per project. If that notification is newer than the project's latest activity, the project is skipped. Otherwise the threshold decides. The default threshold is seven days, and a directory modification time counts as activity only when the directory is inside an authorized root.

The deduplication solves "notify the same stalled project on every pass". It compares the last notification time with the latest activity time: activity after a notification restarts the clock, and silence since then stops repeats. The cost is that the event table has to retain enough history. Four hundred rows is an empirical cap, and a busy event stream can squeeze out old records and cause a duplicate notification.

Task recovery is the other half. On exit, the runtime marks running and pending tasks as paused, and nothing resumes automatically. Agent tasks can have side effects: writing files, moving files, deleting to the Recycle Bin, sending notifications. Replaying them after a restart could delete or move twice, which is far worse than a task sitting paused.

Problem 11: side effects replayed after a restart

Symptom. The app closes halfway through a task, and resuming from the stored state on restart can execute a tool call a second time.

Cause. Task state and tool-call records persist, but "which step ran" and "whether the side effect happened" have no transactional link, so the model can replay a tool.

Fix. On startup the runtime marks interrupted tasks as paused, and tasks waiting on permission become waiting-for-permission. Nothing resumes automatically; the user confirms and re-issues. Tools add idempotency of their own: writes carry content hashes, moves and deletes preview first, and deletes go to the Recycle Bin.

Cost. Users lose automatic resume, and a long interrupted task must be described again. Paused tasks have no one-click resume. That's safety over completeness.

Tray residency, minimize-on-close, single instance and launch at login are the foundation of that residency. A single-instance lock makes a second launch exit and focus the existing window. Closing the window minimizes to the tray, and only an explicit quit ends the process. That gives reminders and proactive checks somewhere to run, and it makes it easy for a user to think the app already exited.

Windows integration: notifications, OCR and the tray

Windows notifications are mandatory for a desktop assistant, and they are the classic case of correct code that produces no visible result.

Z Bot sets the app user model id at startup, which is the prerequisite for Windows notifications. Before sending, it checks whether notifications are supported and returns false instead of throwing. A click can navigate, so a reminder opens the home page and a stalled project opens memory.

Problem 12: Windows notifications never appeared

Symptom. A reminder fires, the log shows it fired, and no desktop notification appears.

Cause. Windows needs the correct app user model id or it can't attribute the notification. Focus assist, disabled notification permissions, or a tray process that isn't running also suppress it silently.

Fix. Set the model id in the main process, check support before showing, and document the diagnostic steps: system notification settings, focus assist, and whether the app is running in the tray.

Cost. Support checks report platform capability, not whether the user muted notifications. There is no in-app banner fallback, so a reminder can be missed. That's a blank spot in this version.

OCR better illustrates how plans change. The repository ends up using the OCR engine built into Windows, called through a PowerShell child process with no profile, no interaction, a bypassed execution policy and a hidden window. The call has a 30-second timeout and a 1 MB output buffer. Results are written to a temporary file, read back, clipped to 20,000 characters, and a failure returns null so the vision model can take over.

Problem 13: OCR moved from Tesseract to the system engine

Symptom. The project started with Tesseract, and the build configuration still carries a plugin that copies the Tesseract data package, while runtime code no longer references it.

Cause. Tesseract needs extra language data and native dependencies, with unfavourable size, startup time and Chinese accuracy. Windows 10 and 11 ship an OCR engine with language packs already installed, and calling it is lighter.

Fix. Move to a PowerShell child process driving the system OCR API, packaging the script as a resource. Return null on failure so the vision model handles it. Hide the window and cap the timeout and the output size so the main process can't hang.

Cost. The child process has startup overhead, and 30 seconds may be too short for very large images. It depends on Windows language packs, so Chinese recognition can fail on a system without them. The leftover Tesseract build configuration is technical debt: harmless at runtime, misleading to the next reader.

The tray and the shortcuts are the last piece. The tray menu offers show, quick ask and quit. One shortcut opens quick ask, another captures the primary screen into the chat. Single instance and launch at login keep those entry points stable, which also means the lifetime is longer than a normal window application. Quit order therefore matters: stop the scheduler, stop the proactive service, close the database, and checkpoint the WAL, in that sequence.

Tests and packaging

The 32 unit tests cover what is easy to get wrong and hard to notice afterwards: short paths and symlinks in the path guard, exact memory deduplication, reminder recurrence rules, provider event normalization, runtime permission denial, and project-stall deduplication. Two end-to-end tests cover starting a real window and a basic conversation. The suite is small, but each case maps to a real hole, which is worth more than a coverage number.

Packaging is another category of trap. Automated releases ship only the portable build and the MSI, because the NSIS uninstaller gets locked by antivirus during the build. Unsigned Windows installers trigger SmartScreen, which asks the user for one extra click. Playwright and jsdom sit in runtime dependencies and inflate the installer, and the repository has no measured size, so this post states the cost without inventing a number.

Problem 14: NSIS locked and runtime dependencies bloated

Symptom. The NSIS installer never reaches release artifacts, only the portable build and the MSI. The installer is also larger than expected.

Cause. The NSIS uninstaller is held or locked by antivirus during the build. Playwright and jsdom, which belong in tests or tooling, were written into runtime dependencies, so the packager bundles them.

Fix. The release script builds portable and MSI directly, bypassing NSIS. ASAR packaging is enabled. The signing gap is documented rather than pretended away. Dependency cleanup, meaning moving test-only packages to development dependencies or excluding them in the bundler, is deferred.

Cost. Without NSIS there is no classic setup wizard or Start Menu uninstall entry, only the portable build or the MSI. Unsigned builds warn in SmartScreen. And no size measurement exists to judge the benefit. All three remain open.

Closing

Z Bot compresses into four sentences.

  1. Keep dangerous capability in the main process. The database, keys, tools and system calls never enter the renderer, and preload exposes only whitelisted methods.
  2. Make permissions a flow rather than a switch. Tools declare a spec, matching rules pass, misses wait for the user, and denial becomes a tool result rather than an exception.
  3. Write the budgets down. Seventy-two thousand context characters, 20 history messages, 8 memories, 20 agent steps, 30 tool calls, 5 minutes, and a 24.8-day timer ceiling. Numbers can be audited; intentions can't.
  4. Make memory an explainable index. Full-text search with trigrams, exact deduplication, archival on expiry, and no vector store.

Its value isn't the feature count but that every feature has a traceable boundary: which step runs in the main process, which needs authorization, which can fail, and what the user sees when it does. Its rough edges are equally explicit. An oversized history message ends the loop, some IPC lacks validation, OCR build configuration is stale, NSIS and signing are unresolved, and reminders don't catch up after a full exit. Writing those down beats pretending they don't exist.

If you are building a desktop agent, copy these three first: main-process exclusivity with a whitelisted preload, the declare-check-wait permission flow, and canonicalization in the path guard. Context budgets, memory retrieval and scheduling can be tuned to your own product.
