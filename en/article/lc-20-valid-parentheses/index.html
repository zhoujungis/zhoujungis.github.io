Valid Parentheses: the stack is forced by the structure

2026-09-29 · 14 min · Stack Frame

The problem

Given a string s containing only '(', ')', '{', '}', '[' and ']', decide whether it is valid.

Valid means every opening bracket is closed by the same type, in the correct order, so nesting never crosses. Every closing bracket has a matching opener.

Input:  s = "{[()]}"   Output: true
Input:  s = "()[]{}"   Output: true
Input:  s = "(]"       Output: false   (wrong type)
Input:  s = "([)]"     Output: false   (crossed nesting)
Input:  s = "(()"      Output: false   (unclosed)

It is a fixture in Chinese interview loops and the classic introduction to the stack.

1. The core insight: the structure forces the stack

The interesting part is that you never have to think "I should use a stack". The bracket structure hands you one.

Why is "(]" invalid while "{[()]}" is fine? Because every closing bracket matches the nearest unclosed opener of its type. Which is to say:

The innermost unclosed opener has to close first. Last opened, first closed. That's LIFO.

"Remember the openers you haven't closed yet, and when a closer arrives look at the most recent one" is a stack, in plain English.

So the solution reads like prose. On an opener, push it and record what you're waiting for. On a closer, ask the top of the stack whether it's the one you're waiting for. When the scan ends, the stack must be empty.

def isValid(s: str) -> bool:
    pairs = {'(': ')', '[': ']', '{': '}'}
    stack = []
    for ch in s:
        if ch in pairs:                 # opener: push
            stack.append(ch)
        else:                           # closer: ask the top
            if not stack:               # failure two: nothing to close
                return False
            if pairs[stack.pop()] != ch:  # failure one: wrong type
                return False
    return not stack                    # failure three: leftovers

Nine lines, but three independent validity checks live in them. Miss one and a whole class of input goes wrong. That's the real test here, and section 2 breaks it down.

There is one implementation choice worth mentioning. The stack can hold the openers and look up the mapping on pop, or it can hold the expected closers directly: push pairs[ch] on an opener, then a closer only has to compare against pop(). The second version saves a lookup at pop time, and saying so in an interview is a small plus.

2. Three failure modes, three checks

"Valid" is not one condition. It is the conjunction of three negations, and each one has its own check. Miss one and you misjudge one family of input.

FailureExampleSymptomWhere the check lives
Wrong type"(]", "([)]"The closer and the stack top are not a pairpairs[stack.pop()] != ch
Nothing to closethe second ) in "())", or a lone "]"The stack is empty when a closer arrivesif not stack
Left unclosed"(()", "(((("The scan ends with the stack non-emptyreturn not stack

The first is "paired with the wrong partner", the second is "one too many", the third is "never finished". They are independent. A given input trips exactly one of them, and input is only valid when none of them fires.

Two positive-looking cases that catch people out:

  • "(]": when ) arrives the top is (. The count is right, one opener and one closer, but the type is wrong. Some people think "every opener got a closer" is enough. It isn't.
  • "([)]": right count, right types, wrong nesting order. [ closes ] while ( is still open. The stack catches exactly this: when ) arrives the top is [, not (.

3. The frames, step by step

Walking "{[()]}" takes six steps: three pushes, three matched pops, and the stack ends empty. Read the stack from bottom to top and keep an eye on the top, because that's the only cell the algorithm ever looks at.

  • push frame: an opener enters the stack and records what it is waiting for.
  • match frame: the current closer matches the top, and the top pops. The pair is settled.
  • mismatch frame: the top and the current character disagree. The stack top was waiting for "]" and got ")".
  • unmatched frame: the stack is empty and a closer has nowhere to go.
  • done frame: valid means the whole string is consumed and the stack is empty. Leftovers mean the remaining openers are marked as failures.

The main example uses eight frames: three pushes, three matched pops, and the stack happens to empty out.

5. The priority variant, and sibling problems

5.1 Adding a priority constraint

One common interview twist assigns priorities: ( is 1, [ is 2, { is 3. Beyond correct pairing, an inner bracket may not have lower priority than the one containing it. Priority can only rise as you go inward, never fall.

InputPlain rulesWith priorityWhy
([{}])truetrue1, then 2, then 3, rising
{(})truefalse( at 1 sits inside { at 3, priority inverts
[({})]truefalse{ at 3 sits inside ( at 1
{[()]}truetruerising throughout

The direction can be reversed: some versions require the outer bracket to be strictly higher, which just flips the comparison. The mechanism does not change. Carry one more field in the stack frame and compare against the top before pushing.

def isValidWithPriority(s: str) -> bool:
    pairs = {'(': ')', '[': ']', '{': '}'}
    prio = {'(': 1, '[': 2, '{': 3}
    stack = []                       # holds (char, priority)
    for ch in s:
        if ch in pairs:
            if stack and prio[ch] < stack[-1][1]:   # inner must not be lower
                return False
            stack.append((ch, prio[ch]))
        else:
            if not stack or pairs[stack[-1][0]] != ch:
                return False
            stack.pop()
    return not stack

This is where the stack approach earns its keep: any extra constraint becomes one more field in the frame. That is what the interviewer is usually probing when they keep twisting a familiar problem.

The family rule: when the most recently handled thing must be handled first, reach for a stack. Pairing problems store what I am waiting for, counting problems store only the balance, and index problems store the position too.

6. Java

public boolean isValid(String s) {
    Map<Character, Character> pairs = Map.of('(', ')', '[', ']', '{', '}');
    Deque<Character> stack = new ArrayDeque<>();
    for (char ch : s.toCharArray()) {
        if (pairs.containsKey(ch)) {
            stack.push(ch);
        } else {
            if (stack.isEmpty() || pairs.get(stack.pop()) != ch) {
                return false;      // failure two and failure one, merged
            }
        }
    }
    return stack.isEmpty();        // failure three
}

Java convention prefers ArrayDeque over Stack, which extends Vector, carries locks and mixes in index access. Note also that the merged condition relies on short-circuit evaluation: stack.isEmpty() runs first, so pop() never touches an empty stack.

8. Complexity

  • Time O(n): each character is pushed and popped at most once.
  • Space O(n): the worst case is all openers, "((((", with a stack depth of n.

9. Common traps

9.1 Checking pairing but forgetting the final emptiness check

In "(()" every closer finds its opener, but openers are left over. The stack has to be checked after the loop. This is the failure mode people miss most often, because its check lives outside the loop.

9.2 Popping before checking for an empty stack

For the second ) in "())" or a lone "]", pop() on an empty stack raises IndexError in Python and an exception in Java. Plenty of people write pairs[stack.pop()] first and add the empty check afterwards. The empty check has to come before the pop.

9.3 Replacing the stack with two counters

Do count( and count) matching make a string valid? "(]" defeats it immediately: ( and ] are not the same type and counters do not know types. Even with one counter per type, "([)]" slips through, because every count is correct. Counters can check the balance. They cannot check the order, and order is the whole point.

9.4 Assuming crossed nesting is fine

"([)]" has the right counts and the right set of types, so intuition says true. What saves you is the top-of-stack comparison: when ) arrives the innermost bracket is [, not (. Keep this case as a self-test.

9.5 Mishandling the empty string

"" should return true: there is nothing to pair. The loop does not run, the stack is empty, and return not stack gives the right answer. Adding if not s: return False at the top, on the assumption that empty means invalid, breaks it.

9.6 Using java.util.Stack

It runs, but Stack extends Vector: synchronized, with an index interface it should not expose. Modern Java uses Deque or ArrayDeque. Small engineering point, easy to earn.

10. How to answer in an interview

  1. State the insight in one sentence. The innermost unclosed bracket has to close first, which is last-in-first-out, which is a stack. The structure chose the data structure for you.
  2. List the three failure modes before writing code. Wrong type, nothing to close, left unclosed. Three checks, none optional, and the last one sits outside the loop.
  3. Offer "([)]" yourself. Correct counts, correct types, crossed nesting. It proves you understand that the top-of-stack comparison is checking order.
  4. Complexity. O(n) time, O(n) space, worst case all openers.
  5. Extend. The expected-closer variant, the priority variant that adds a field to the frame, the counter version (LC 921) and the index version (LC 32). It shows you know where this problem sits in the family.

Closing

Valid parentheses is the cleanest way to explain a stack, because it needs no tricks. One observation carries the whole solution: nested brackets are inherently last-in-first-out. Nine lines hold three checks for three failure modes, and none of them is optional. Every variant in the family, whether counting, index-based or priority-constrained, is a change to what the frame stores. Next time something has to handle the most recent unhandled item first, start here.
