NanoBrowser, part 2: tabs, the headless agent, and fourteen pits

2026-10-16 · 24 min · Stack Frame

This is part two. Part one covered the shell topology, the in-process CDP core, the hand-written WebSocket server and the docked DevTools panel. This half covers the tab engine, the frontend, the headless agent, the MCP server, traffic capture, the five security layers, the size accounting, persistence, and the fourteen pitfalls that cost real time.

Core 6: the tab engine

tabs.rs is the largest business file, and it holds a number of small algorithms that deserve to be read on their own.

Address bar parsing: three branches

One function turns whatever the user typed into a navigation target.

  1. Empty input goes to the new tab page.
  2. An internal page under the nano:// scheme is used as written.
  3. Something that looks like a URL gets https:// prepended if it needs one.
  4. Everything else is searched with the configured engine.

The third branch is where the judgement lives, and it has precise rules.

  • An explicit http:// or https:// prefix must also survive URL parsing.
  • A string containing spaces, or an empty string, is not a URL. That's a strong signal the user wants to search.
  • Otherwise the candidate gets https:// and must then satisfy one of: the host is localhost, the host parses as an IP address, or the host has at least two dot-separated segments.
  • And the first character must be an ASCII letter or digit.

Together they draw the least-wrong line between "example.com should be treated as an address" and "how to code should be treated as a query".

Downloads: race-safe naming

Same-name files don't overwrite. They become report (1).pdf, report (2).pdf and so on. That sounds simple until two downloads start at once: both can decide the path is free, and both write the same file.

The project removes the race with an atomic reservation. It claims the path by creating the file exclusively, and only the winner proceeds, so ownership is decided by the filesystem rather than by a check in memory. WebView2 fills in the content afterwards. The naming helper tries up to a thousand candidates, and the reservation is that exclusive create.

In one line: let the filesystem's atomicity arbitrate the name, not an in-memory check.

Favicons: keep the port

The favicon guess has one detail that is easy to drop.

scheme://host:port/favicon.ico

The port must be included. A site running on a non-default port would otherwise point at a different origin's icon. Guessing wrong there isn't just ugly, it is semantically wrong.

Zoom: a fixed fifteen-step ladder

0.25, 0.33, 0.5, 0.67, 0.75, 0.8, 0.9, 1.0, 1.1, 1.25, 1.5, 1.75, 2.0, 2.5, 3.0

The index is clamped against the array length before use, so an out-of-range value written into an old profile can't panic. In a build that aborts on panic that matters: one out-of-bounds read is the whole process. A test pins the behaviour, with index 999 still yielding 3.0.

Shortcuts: split across two worlds

Shortcuts are handled in two places, depending on whether focus is inside the page or inside the shell. A keystroke in a page is reported by the injected script and handled in Rust. A keystroke in the shell is handled directly by shell.js.

Core 7: the zero-framework frontend

The frontend lives in ui/ and is hand-written HTML, CSS and JavaScript, with no bundler, no framework and no npm.

Three things improve.

  • No build step, so editing one line of HTML and reloading is the whole cycle.
  • UI asset size is close to zero, against a typical Electron plus React baseline.
  • The interface to Rust is trivial: with the global API enabled, the page calls those 40 commands directly through it.

Two things get worse. There is no component reuse and no type checking, and state plus DOM are managed by hand. That's why shell.js spends so much effort on interactions that are manual but deterministic.

Tab dragging: FLIP plus one deterministic click suppression

This is the most delicate piece of the frontend.

  • Pointer move, up and cancel drive it. The dragged tab follows the cursor while its siblings slide aside with FLIP transitions, so the strip always previews where the drop will land.
  • On release, a command tells Rust to reorder for real.
  • One detail decides whether it feels broken. The browser still fires a click after a drag, so without care you drag a tab and accidentally select it. The project sets a suppression flag and clears it on the next pointer down, rather than waiting a tick. It's deterministic and doesn't depend on task-queue timing.

Other frontend notes

  • Suggestions. The function calls Rust, which matches against history and bookmarks, returns at most eight entries and deduplicates them. The frontend builds the DOM and handles both clicks and keyboard selection before navigating.
  • Themes. One function resolves the setting plus the system dark flag into a final value, and then sets a data attribute on the document element. All design tokens hang off the root selector and its dark variant, so switching themes never touches a component class name.
  • Window control icons. The icons are injected by JavaScript, and the SVG's CSS class must come with the markup. Without it, glyphs sized by class name, most visibly the fullscreen restore icon, render at their default enormous size. The README lists this as a pitfall.

Core 8: nanoagent, an invisible browser

nanoagent is the same browser engine in a window that is never shown, driven by AI tools.

  • The window is created hidden, without a taskbar entry and without decorations. It uses its own WebView2 user-data directory under data/automation, fully isolated from the GUI profile, so automated logins and personal cookies never mix.
  • Control goes through the in-process CDP bridge, which means no debugging port.
  • One-shot commands start a fresh browser every time. MCP mode keeps one warm page across many tool calls.

One-shot CLI

nanoagent --mcp                              MCP over stdio, long session
nanoagent <command> [args...]                run one action and exit

navigate <url>                               open a URL, print url and title
read <url> [selector] [--html]               print page text, or HTML
shot <url> <out.png>                         save a PNG screenshot
cookies <url>                                list the profile's cookies for that page
traffic <url> [limit]                        print recorded requests, redacted
eval <url> <js>                              run JavaScript, print the value
click <url> <selector>                       click with a trusted mouse event
fill <url> <selector> <value>                type into an input
wait <url> <selector> [timeout_ms]           wait for an element

Three implementation details, all of them pits

First, trusted input. A click dispatches mouse events in sequence, and filling inserts text through the input domain. The combined effect is that the page sees real user input rather than a scripted assignment to a DOM property. That matters against pages which detect automation through the trusted-input flag.

Second, screenshots go around the missing API. WebView2 doesn't implement Page.captureScreenshot. A hidden window, however, still composites, so the agent subscribes to the screencast stream and caches frames. The README leaves a fallback on record: if hidden windows ever stop compositing, move the window off-screen instead of hiding it.

Third, readiness and thread discipline. The worker polls a readiness check up to 600 times at 50 ms intervals, because a webview must have a running event loop before it answers CDP. And while waiting for a reply it must never block the UI thread, which would deadlock. The reply lands in shared state and the worker waits on a condition variable. Those two rules are exactly what the cdp.rs design buys in the agent scenario.

Core 9: the MCP server and its nine tools

In --mcp mode the agent speaks JSON-RPC 2.0 over stdin and stdout, implements tools/list and tools/call, and reports its name as nanobrowser-agent.

ToolWhat it does
browser_navigateOpens a URL, returns url and title
browser_readPage text or HTML, with an optional selector
browser_clickSynthesizes a trusted mouse event
browser_fillInserts text into a selector
browser_wait_forPolls until a selector exists
browser_screenshotReturns PNG bytes
browser_cookiesThe automation profile's cookies
browser_trafficRecorded requests, redacted
browser_evalRuns JavaScript and returns its value

The loop is simple and typical: read stdin line by line, parse method, params and id, dispatch initialize, list or call, and write the reply to stdout. It's pure stdio, with no network and no port, which makes it a natural child process for a local agent to manage.

Set against the capabilities, the design intent is clear. Navigate, read, click, fill, wait, screenshot and eval are hands and eyes. Cookies are the session. Traffic is observability. Together they are the minimal complete set for letting an agent operate a web page.

Core 10: traffic capture and capture-time redaction

traffic.rs subscribes to network events and records requests. Its security rule is one sentence: redact at capture time, not at output time.

The distinction matters. With "store first, redact later", the plaintext secret has already been sitting in a log buffer, and any dump can carry it away. Redacting at capture means the secret never entered the buffer.

The rules are specific.

  • Eighteen sensitive key substrings, matched case-insensitively: password, passwd, pwd, pass, token, secret, apikey, api_key, api-key, auth, cookie, session, csrf, credit, card, cvv, ssn and otp. A hit is replaced with three asterisks, in both JSON bodies and header maps.
  • Authorization and cookie headers, and form bodies, are covered by the same rules.
  • Bodies are truncated, with a separate cap for individual values. The buffer holds at most 500 entries.
  • The log lives in memory only and is never written to disk.
  • Redaction can't be turned off.

There is one more trap, about redirects. A redirect reuses the same CDP request id, so keying records by the raw id lets a later record overwrite the original request and lose its body. Entries are therefore keyed by a unique key derived from the redirect chain.

The five security layers

Layer one: event origin, checked by token

Each tab webview's init script embeds an opaque random token minted in Rust, twenty-four hex digits. Two properties follow.

  • A page can't forge events for another tab, because it doesn't know that tab's token.
  • Rust resolves the sender through the token and never trusts a tab id the page reports about itself.

In other words, tab identity is minted on the Rust side and injected into the page, rather than something the page gets to declare. That's "pages are untrusted" made concrete.

Layer two: favicons are hostile data

A favicon is reported by a page and displayed by the trusted shell, so it is treated as hostile input.

  • It is HTML-escaped before insertion.
  • It is given an error handler that swaps in a built-in globe icon when it fails to load.

The conclusion: a page can never inject a URL of its choosing into the shell.

Layer three: per-webview capability scopes

Tauri capabilities are scoped by webview label.

CapabilityApplies toGrants
shellThe shell webviewDefaults plus window control and queries
tab-localtab-* webviews running internal pagesDefaults plus the ability to emit events, which is full application IPC
tab-remotetab-* webviews on external URLsOnly the ability to emit events, so a remote page can report UI events and never call a command

That last cell is the most important one in the whole security model. Internal pages are trusted with the full IPC surface. External pages can only emit. Even if the injected script is fooled by a page, all it can do is emit a UI event.

There is a counter-intuitive trap here, and the README names it. tab-remote must cover all ports: both schemes with any port, plus the path form. A site running on a non-default port that no capability declaration matches will lose every injected feature at once. Shortcuts, hover state, find highlighting and favicon reporting all fail together. A configuration problem whose symptoms look like broken code is the hardest kind to diagnose.

Layer four: no debugging socket

Neither binary passes the debugging-port flag, and all CDP goes through the in-process call. The GUI's DevTools WebSocket does listen on loopback, but it binds a random port and accepts only the session id minted for this panel. Nothing outside the process can attach.

Layer five: profile isolation

The automation browser uses its own WebView2 data directory, separate from the GUI's. Cookies and login state never cross that boundary in either direction.

Where 4.52 MB comes from

Add up the earlier decisions.

  1. No rendering engine. Reusing the system WebView2 removes the largest block.
  2. A release profile tilted entirely towards size: optimize for size, link-time optimization, one codegen unit, strip, abort on panic.
  3. No WebSocket library. A hand-written SHA-1 and frame codec removes a whole dependency tree.
  4. No framework and no bundler in the frontend. UI assets are close to zero.
  5. Rust and Tauri. Tauri never bundles a webview, which is an order of magnitude smaller than the route that puts Chromium inside the binary.

That gives 4.52 MB for the GUI and 4.24 MB for the agent, sharing one library crate, so the protocol bridge exists once.

Startup follows the same logic. The launcher prefers the release binary and only falls back to debug. For a shell, cold start is essentially creating a window and loading local HTML. There is no engine to initialize.

  "history":   [ { "url": "...", "title": "...", "time": 0 } ],   // capped at 500
  "downloads": [ { "url": "...", "name": "...", "path": "...", "time": 0,
                   "status": "done" } ],                          // capped at 100
  "session":   { "tabs": ["..."], "active": 0 },
  "window":    { "x": 0, "y": 0, "w": 1280, "h": 800, "maximized": false }
}

Three practices are worth copying.

  • Atomic save. The JSON is written to a temporary file and then renamed over the profile. A crash mid-write can't corrupt it, because the rename is atomic within a directory.
  • Cap-tolerant loading. History and downloads are truncated on read, so a file someone edited by hand can't exhaust memory.
  • Debounced window geometry. A pending flag plus a debounce keeps dragging the window from writing to disk on every frame.

Fourteen pitfalls that cost real time

The README devotes a section to these counter-intuitive constraints, because they are the most valuable part of the project. Every one of them came out of a real debugging session.

Layout and z-order

  1. Every tab is an independent window, so a later-created page covers the shell and clips menus and suggestions. The fix is to expand the shell over the window and raise it while a menu is open, restore it on close, and re-assert z-order after any tab create, activate or close.
  2. A child webview can't see pointer movement outside its own bounds, so panel resizing has to route the pointer through a full-window capture layer in the shell.
  3. Window control icons are injected by JavaScript, and the SVG's CSS classes must travel with them, or class-sized glyphs such as the fullscreen restore icon render at default enormous size.

Concurrency and downloads

  1. Closing tabs by index concurrently deletes the wrong neighbours, so the tab has to be looked up again inside the lock.
  2. Concurrent downloads of the same URL overwrite each other when matched by URL alone, so the path is reserved with an atomic exclusive create instead.

CDP

  1. Waiting for a CDP reply on the UI thread deadlocks, especially with a hidden window. The callback writes shared state and a worker thread waits.
  2. A redirect reusing the same request id overwrites the original record and loses its body, so records are keyed by an id derived from the redirect chain.
  3. The debugging port is a dead end, because only the shell webview becomes a CDP target.
  4. Schema.getDomains lists domains and returns no event names, so a static event table plus lazy per-domain subscription is required.
  5. Disabling native DevTools doesn't affect CallDevToolsProtocolMethod, which is why the native popup can be killed while keeping full CDP.

Docked DevTools

  1. The devtools:// page is privileged: neither the WebView2 host object nor Tauri IPC exists, so a popup request that the app denies is the only signalling channel.
  2. A second query key after ?ws= fails the entire load, so extra data must go in the fragment. And while debugging it, the reported URL can't be trusted, because the error page still reports what you asked for. The reliable signals are whether the bridge received a client and how many domains it registered.
  3. The grip sits on the edge facing the page, and the cursor follows the dock axis. The drag maths is a subtraction from the window edge on that axis.

Capabilities

  1. A site on a non-default port that no declaration matches loses every injected feature at once: shortcuts, hover state, find highlighting and favicon reporting.

Three of the fourteen are worth memorising outright: the DevTools URL rejects a second query key, disabling native DevTools doesn't disable in-process CDP, and sibling webviews can't see outside themselves. They are the most counter-intuitive, and the most likely to reappear in another project.

Known limits

The README lists these plainly, and they are worth passing on.

  • History and the new tab page still guess favicons from the host, while only bookmarks store the icon a page actually reported. Unifying them onto the bookmark logic is a known follow-up.
  • The docked panel supports the bottom and the right only. There is no left side, and no detaching into a separate window.
  • Windows only, because the whole stack rests on WebView2 COM interop.
  • The repository ships no release pipeline beyond the installer target declared in the Tauri configuration.
  • There is no LICENSE file yet, which the README itself flags as something to add before distribution.

Verdict

Three things are worth taking away from this codebase, and none of them is really about how to write a browser.

First, building no engine is a capability, not laziness. Most projects default to implementing whatever they need. NanoBrowser asks the opposite question first: what does the system already have? Windows already has Chromium, so build only the shell. That buys 4.5 MB and near-zero engine maintenance, at the cost of Windows-only, and that cost is acceptable to its audience. Recognising which costs are acceptable matters far more than any comparison table.

Second, the hard part isn't features but the host's boundaries. Almost all of the complexity here comes from four invariants: child webviews are siblings, CDP callbacks run on the UI thread with no request ids, the devtools:// page has no conventional IPC, and its URL rejects a second query key. Those non-negotiable constraints shape the architecture, and they explain the whole list of pitfalls.

Third, a side-effect channel can be a signal channel. When both legitimate channels are cut, find an effect the host is guaranteed to intercept and hang the parameters on it. It isn't elegant. It's correct, reliable, and needs no cooperation from the host.

Back to the three decisions: no engine, no debugging port, hand-written hard dependencies. Together they say one thing. Push reuse to its limit, and shrink the self-written surface to the part that must be written and is worth writing. A 4.5 MB browser isn't the result of trimming. It's the result of choosing not to rebuild something at every fork in the road.
