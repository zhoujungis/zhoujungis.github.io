Core 6: the tab engine

tabs.rs is the largest business file, and it is full of small algorithms worth looking at individually.

Omnibox parsing (parse_input) has three branches: empty input goes to nano://newtab; an internal page (nano://...) is used as-is; something that looks like a URL gets https:// prepended when needed; anything else is searched with the configured engine. looks_like_url is precise: an explicit http:// or https:// prefix must also survive Url::parse; strings containing spaces or empty strings are rejected (a strong "the user wants to search" signal); otherwise the candidate gets https:// and must then have a host equal to localhost, or parse as an IP, or contain at least two dot-separated segments, and must start with an ASCII letter or digit. Together they draw the least-wrong line between "example.com is a URL" and "how to code is a search".

Downloads: race-safe naming. Same-name files become report (1).pdf, report (2).pdf. Sounds easy, except two downloads starting together can both conclude "this path is free" and write the same file. The fix is an atomic reservation: claim the path with an exclusive create_new, and only the winner owns it; WebView2 fills in the content afterwards. unique_path tries up to 1000 candidates. In one line: use the filesystem's atomicity to arbitrate naming, not an in-memory check.

Favicons must include the port: scheme://host:port/favicon.ico. Dropping the port on a site running on a non-default port points at a different origin's icon — not just ugly, but semantically wrong.

Zoom is a fixed 15-step ladder (0.25 … 3.0) read with zoom_idx.min(len - 1), so an out-of-range index in an old profile cannot panic. In a panic = "abort" build that matters: one out-of-bounds is the whole process. A test pins it (index 999 still yields 3.0).

Shortcuts are handled in two places depending on whether focus is in the page or the shell: page keystrokes are reported by the injected script and handled in tabs.rs::handle_shortcut; shell keystrokes are handled directly in shell.js. The map covers tab creation and closing, Ctrl+Shift+T reopen, tab cycling and number selection, omnibox focus, find, bookmark, history, downloads, bookmark manager, back/forward, zoom in/out/reset, F5 reload, F11 fullscreen and F12/Ctrl+Shift+I for the docked panel.

One act of restraint is worth noting: editing keys (Ctrl+C/V/X/A), Ctrl+R, Ctrl+P and Ctrl+Shift+1..9 are deliberately left to the engine. The worst thing a browser shell can do is cleverly swallow keys a page needs. Under the same rule, F5 is not intercepted either.

Core 7: the zero-framework front end

ui/ is hand-written HTML/CSS/JS with no bundler, no framework, no npm. What that buys: no build step (edit a line of HTML and reload); a UI asset size near zero; and an extremely simple interface to Rust — withGlobalTauri on, so the page calls those 40 commands through the global Tauri API. What it costs: no component reuse, no type checking, manual state and DOM management — hence the effort spent on "manual but deterministic" interactions.

Tab dragging: FLIP plus one deterministic click suppression. Driven by pointermove/pointerup/pointercancel, the dragged tab follows the cursor while siblings slide aside with FLIP transitions, so the strip always previews where the drop will land; on release invoke("move_tab", ...) makes Rust reorder for real. The subtle part: the browser still fires a click after a drag, so without care you "drag a tab and accidentally select it". The project sets a suppressClick flag and resets it on the next pointer-down — not on a timer, not after a tick. It is deterministic and does not depend on task-queue timing.

Other front-end notes: suggestions call omnibox_suggest (Rust matches history and bookmarks, at most eight, deduplicated); themes resolve "setting + system dark flag" into a final value and merely set document.documentElement.dataset.theme — all design tokens hang off :root and [data-theme="dark"], so switching themes never touches a class name; and window control icons are injected by JS, and the SVG's CSS class must come with them — without the class, glyphs sized by class name (most visibly the fullscreen restore icon) render at default giant size.

Core 8: nanoagent, an invisible browser

nanoagent is the same browser engine in a window that is never shown, driven by AI tools. The window is created with visible(false), skip_taskbar(true) and decorations(false), and uses its own WebView2 user-data directory (data\automation) fully isolated from the GUI profile — automated logins and human cookies never mix. Control goes through the in-process CDP bridge: no debugging port. One-shot commands start a fresh browser each time; MCP mode keeps one warm page across many tool calls.

nanoagent --mcp                              MCP over stdio (long session)
nanoagent <command> [args...]                run one action and exit

navigate <url>                               open a URL, print {url,title}
read <url> [selector] [--html]               print page text (or HTML)
shot <url> <out.png>                         save a PNG screenshot
cookies <url>                                list cookies in the profile for that page
traffic <url> [limit]                        print recorded requests (redacted)
eval <url> <js>                              run JS, print the value
click <url> <selector>                       click with a trusted mouse event
fill <url> <selector> <value>                type into an input
wait <url> <selector> [timeout_ms]           wait for an element

Three implementation details, all of them pits. First, trusted input: click uses Input.dispatchMouseEvent (moving, pressed, released) and fill uses Input.insertText, so the page sees real user input rather than a scripted DOM assignment — which is what defeats pages that detect automation via isTrusted.

Second, screenshots go through screencast: WebView2 does not implement Page.captureScreenshot, but a hidden window still composites, so the agent subscribes to Page.startScreencast and caches frames. The README keeps a fallback on record: if hidden windows ever stop compositing, the official workaround is to move the window off-screen rather than set visible(false).

Third, readiness and thread discipline: the worker polls is_ready() up to 600 times at 50 ms, because a webview must have a running event loop before it answers CDP. And while waiting for a CDP reply it must never block the UI thread — the reply lands in shared state and the worker waits on a condition variable. That is exactly the payoff of the cdp.rs design in agent scenarios.

Core 9: the MCP server and its nine tools

--mcp speaks JSON-RPC 2.0 over stdin/stdout, implements tools/list and tools/call, and reports serverInfo.name as "nanobrowser-agent". The nine tools: browser_navigate, browser_read, browser_click (synthesized trusted mouse event), browser_fill (Input.insertText), browser_wait_for (poll until a selector exists), browser_screenshot (PNG bytes), browser_cookies (the automation profile's cookies), browser_traffic (recorded requests, redacted) and browser_eval (run JS, return its value).

The loop is simple and typical: read stdin line by line, parse method/params/id, dispatch initialize / tools/list / tools/call, write the reply to stdout. Pure stdio — no network, no port — which makes it a natural child of a local agent process. Against the earlier capabilities, the intent is clear: navigate, read, click, fill, wait, screenshot and eval are hands and eyes; cookies are the session; traffic is observability — a minimal complete set for "let an agent operate a web page".

Core 10: traffic capture and capture-time redaction

traffic.rs subscribes to Network.* events and records requests. Its core security principle: redact at capture time, not at output time. The difference matters — with "store then redact", the plaintext secret has already been sitting in a log buffer where any dump can take it; capture-time redaction means the secret never entered the buffer.

The rules: eighteen sensitive key substrings (case-insensitive) — password, passwd, pwd, pass, token, secret, apikey, api_key, api-key, auth, cookie, session, csrf, credit, card, cvv, ssn, otp — replaced with three asterisks in both JSON bodies and header maps; Authorization/Cookie headers and form bodies covered by the same rules; bodies truncated (MAX_BODY = 4096, MAX_VALUE = 512) with MAX_ENTRIES = 500; the log kept in memory only, never written to disk; and redaction cannot be turned off.

One more pit: a redirect reuses the same CDP requestId, so keying by the raw id lets a later record overwrite the original request and lose its body. Entries are therefore keyed by a unique key derived from the redirect chain.

The five security layers

Layer one: origin validation for page events. Each tab's init script embeds an opaque random token minted in Rust (new_token(), 24 hex digits). A page therefore cannot forge events for another tab, since it does not know that tab's token, and Rust looks the sender up with tab_id_by_token rather than trusting a self-reported id. Tab identity is minted on the Rust side and injected into the page — "pages are untrusted" made concrete.

Layer two: favicons as hostile data. A favicon is reported by a page and displayed by the trusted shell, so it is treated as hostile input: HTML-escaped before insertion, plus an <img onerror> falling back to a built-in globe icon. A page can therefore never inject a URL of its choosing into the shell.

Layer three: per-webview capability scopes. Tauri capabilities are scoped by webview label: shell gets core:default plus window control; tab-local (internal pages) gets core:default plus core:event:allow-emit, i.e. the full app IPC; tab-remote (external URLs) gets only core:event:allow-emit — a remote page can report UI events and never call a command. That cell is the crux: internal pages are trusted with IPC, external pages can only emit.

There is a counter-intuitive trap here, explicitly called out: tab-remote must cover all ports (https://*:*, http://*:* and https://*/*). A site on a non-default port that no capability matches loses every injected feature at once — shortcuts, hover state, find highlighting and favicon reporting all fail together. "A configuration problem that looks like broken code" is the hardest kind to diagnose.

Layer four: no debugging socket. Neither binary passes --remote-debugging-port; all CDP goes through in-process CallDevToolsProtocolMethod. The GUI's DevTools WebSocket binds a random loopback port and accepts only the session id minted for this panel, so nothing outside the process can attach.

Layer five: profile isolation. The automation browser uses its own WebView2 data directory, separate from the GUI's; cookies and login state never cross that boundary in either direction.

Size and startup accounting

Adding up the earlier decisions: no rendering engine (reuse the system WebView2) removes the largest block; the release profile is entirely size-oriented; no WebSocket library (hand-written SHA-1 and framing) removes a dependency tree; the front end has no framework or bundler, so UI assets are near zero; and Rust + Tauri never bundles WebView, which is an order of magnitude smaller than embedding Chromium.

Hence 4.52 MB for the GUI and 4.24 MB for the agent, sharing one library crate — the protocol bridge exists once. Startup follows the same logic: start.bat prefers the release binary and only falls back to debug, and for a shell, cold start is essentially "create a window and load local HTML" with no engine initialization to wait for.

Persistence: atomic writes, caps and drive policy

Every path derives from the executable's location, with environment overrides for tests: data root <project>\data (NANO_DATA_DIR), profile data\profile.json, WebView2 user-data data\webview, default downloads <project>\Downloads, automation profile data\automation (NANOBROWSER_AGENT_DIR), agent data root (NANOBROWSER_DATA_DIR). That is where "everything lives on the D: drive" comes from: runtime data, caches, downloads and WebView2 user-data all stay inside the project directory and never write to the system drive.

profile.json holds settings (search engine, theme, homepage, bookmarks bar, startup mode, downloads dir, dock side), bookmarks, history (capped at 500), downloads (capped at 100), the session and window geometry. Three practices worth copying: atomic save — write .profile.tmp then rename over profile.json, so a crash mid-write cannot corrupt the profile; cap-tolerant reads — truncate history and downloads on load, so a hand-edited oversized file cannot exhaust memory; and debounced window geometry so dragging the window does not write to disk every frame.

Fourteen paid-for pitfalls

The README lists these counter-intuitive constraints in their own section, because they are the most valuable part of the project — each one cost a real debugging session.

Layout and z-order: every tab is an independent HWND, so a later-created page webview covers the shell and clips menus and suggestions (fix: expand and raise the shell while open, restore on close, and re-assert z-order after any tab change); a child webview cannot see pointer movement outside its own bounds, so panel resizing must route the pointer through a full-window capture layer in the shell; and window control icons injected by JS must carry their SVG CSS classes, or class-sized glyphs render at default giant size.

Concurrency and downloads: closing tabs by index concurrently deletes the wrong neighbours (re-look the tab up inside the lock); and concurrent downloads of the same URL overwrite each other if matched by URL alone (reserve the path with an atomic create_new).

CDP: waiting for a CDP reply on the UI thread deadlocks, especially with a hidden window (callback writes shared state, worker thread waits); a redirect reusing requestId overwrites the original record and loses its body (key by a redirect-chain-derived id); --remote-debugging-port is a dead end since only the shell becomes a target; Schema.getDomains lists domains without event names, so a static event table plus lazy per-domain subscription is required; and AreDevToolsEnabled = false does not affect CallDevToolsProtocolMethod, which is what makes docking possible at all.

Docked DevTools: devtools:// is a privileged page where neither window.chrome.webview nor Tauri IPC exists, leaving window.open plus Deny as the only signalling channel; a second query key after ?ws= fails the whole load, so extra data must go in the fragment — and while debugging that, webview.url() lies (the error page reports the requested URL), leaving "did the bridge get a client" and "how many domains registered" as the reliable signals; and the grip sits on the edge facing the page, with drag maths of panel_h = window_h - clientY or panel_w = window_w - clientX.

Capabilities: a non-default-port site matched by no capability declaration loses every injected feature at once.

Three of the fourteen are worth memorizing outright: the devtools:// URL rejects a second query key, disabling native DevTools does not disable in-process CDP, and sibling webviews cannot see outside themselves. They are the most counter-intuitive and the most likely to recur in another project.

Known limits

  • History and the new-tab "top sites" still guess favicons as scheme://host/favicon.ico; only bookmarks store the icon the page actually reported. Unifying them is a known follow-up.
  • The docked panel supports bottom and right only — no left side, no undocking into a separate window.
  • Windows only: the whole stack rests on WebView2 COM interop.
  • The repository ships no release pipeline beyond the nsis target declared in tauri.conf.json.
  • There is no LICENSE file — per the README's own note, one should be added before distribution.

My verdict

Three takeaways, none of them really about "how to write a browser".

First, "build no engine" is a capability, not laziness. Most projects default to "implement whatever I need". NanoBrowser asks what the system already has. Windows already has Chromium, so build only the shell. That buys 4.5 MB and almost zero engine maintenance, at the cost of Windows-only — a cost its target users can accept. Recognizing which costs are acceptable matters far more than any comparison table.

Second, the hard part is not features but the host environment's boundaries. Almost all the complexity here is four invariants: child webviews are sibling HWNDs; CDP callbacks run on the UI thread with no request ids; devtools:// has no conventional IPC; and its URL rejects a second query key. Those non-negotiable constraints shape the architecture and explain the long list of pitfalls.

Third, "use a side-effect channel as a signal channel" is worth learning. The panel-to-native window.open('https://nano-dt.invalid/...') plus Deny path is a clean way out when both legitimate channels are cut: find a side effect that is guaranteed to be intercepted and hang the parameters on it. Not elegant, but correct, reliable, and requiring no cooperation from the host.

Back to the three decisions — no engine, no debugging port, hand-written hard dependencies. Together they say one thing: push reuse to the limit and shrink the self-written surface to the layer that must be written and is worth writing. A 4.5 MB browser is not the result of trimming; it is the result of choosing "do not rebuild this" at every fork.
