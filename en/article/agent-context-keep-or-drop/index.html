Agent context: what to keep, what to drop

2026-10-22 · 28 min · Stack Frame

Who this is for: people who have a working agent loop and are now being tortured by a history that keeps growing; people who want to know what compact should actually preserve; people about to add memory, retrieval or sub-agents and who want the budget worked out first.

TL;DR: context is not the chat log. It is the working set the next step still needs. The only test for keeping something is whether the next message will use it. NanoHermes turns that into arithmetic with four layers of caps: a 4 MB file read is refused, a single tool result is cut at 20,000 bytes, project docs stop at 20,000 characters, and the session compacts at 120,000 characters. Compaction keeps the last ten messages and replaces everything older with a summary under 300 words.

Context is not a chat log

The first post in this series treated the message list as one thing: whatever the model answers, append it, and as long as the history stays legal the loop keeps turning.

History isn't free, though. The model has no memory, so every request resends the whole history. The context window is a container refilled on every turn, not a chat log stored somewhere.

So the hard part was never fitting things in. It is deciding what to bring.

That produces a constraint no ordinary program has: the cost of context is not storage, it is input paid again on every turn. Leave a 20,000 character tool result in history and you have not spent one disk write, you have made every following request 20,000 characters heavier. Ten turns later you have resent two hundred thousand characters.

Keeping too much makes the model lose the thread while latency and the bill both rise. Dropping too much makes it forget the goal, forget which file it edited, forget that a path was already ruled out, and start circling.

The answer compresses to one line:

What stays is the working set for the next step, not the record of what already happened.

The test is just as short: will the next message use it? If yes, keep it. If no, drop it. If you are unsure, compress it to a sentence.

What one request actually carries

The messages array of a single request is usually made of seven things.

ContentTypical sourceSize profileHow often it changes
System promptprompt::system_promptFixed, about 30 linesAt startup or on a config change
Project conventionsAGENTS.md, assembled level by levelAt most 20,000 charactersWhen the file changes
Project contextNANOHERMES.mdNo separate capWhen the file changes
Skill listskills::listingOne line per skillAt startup
Memory blockmemory::render_blockAt most 2,400 charactersRe-retrieved every turn
Conversation messagesuser, assistant, toolGrows with turnsEvery turn
Compaction summarysummarize_messagesAt most 300 wordsWhen the budget is exceeded

The first three and the skill list all live in the system message and are rebuilt only at startup or when configuration changes. The memory block also lives in the system message, but it is replaced by marker every turn. Conversation messages are the part that grows, and the summary exists to stop that growth.

The intuition most people have is that conversation messages dominate. Often they don't. A read_file that returns 2,000 lines gets clamped to 20,000 bytes, and five of those is 100,000 bytes, which is nearly the entire session budget. What eats the window is usually tool output, not model prose.

ContentEstimated sizeShare of a 120k budget
System prompt plus project conventions2,000 to 22,000 characters2% to 18%
Memory block2,400 characters or less2% or less
An ordinary tool result200 to 2,000 characters0.2% to 1.7%
A clamped tool result20,000 bytesabout 17%
The last ten messages5,000 to 40,000 characters4% to 33%
The compaction summary1,500 to 2,500 characters1% to 2%

Which explains a familiar symptom: context blows up because a few tool calls returned too much, not because the conversation was long. One uncapped cat, one whole-repo grep, one web_fetch that returns a full page of HTML, and the budget is gone.

Four budgets, from a single file to the whole session

NanoHermes does not have one context manager. It has caps at four levels, each aimed at a different failure.

LevelCapWhereBehaviour when exceeded

Search scan1 MB per file, 200 hits, 240 characters per linesearch.rsOversized files skipped, stops at the hit cap

Background task512 KBtasks::CAPTURE_BYTESKeeps the first 512 KB, notes the omission

Why four layers instead of one compaction pass at the session level?

Compaction comes too late. If you only react at 120,000 characters, the model has already paid for the giant results across several turns. A cap at the tool layer applies the moment the result exists, so the cost stops there.

Compaction is expensive. It is itself a model request. If it had to read a 4 MB file and summarize it, the summarizer could blow its own window. The tool layer refuses first so the compaction layer only ever handles material worth summarizing.

Compaction loses information. A 20,000-byte tool result cut in place still shows the model its first 20,000 bytes. The same result summarized into a paragraph loses the detail entirely. Anything solvable at the tool layer should not be pushed down to compaction.

The relationship fits in one line: closer to where the bytes are produced, cut hard; closer to the session, summarize. Hard cuts are cheap and preserve existence but lose detail. Summaries are expensive and preserve meaning but introduce model error. Neither substitutes for the other.

Why one tool result can eat half the window

Suppose the model calls read_file on a 2,000 line file averaging 80 characters a line. That is about 160,000 characters.

fs::read_file does not hand 160,000 characters to the model. It takes the first 2,000 lines per limit, then hands off to dispatch, whose last step is clamp(s, ctx.max_output) at 20,000 bytes by default. So the model sees the first 20,000 bytes plus one line reading … output truncated (N chars omitted).

Those 20,000 bytes then get JSON-serialized once more. Newlines become , quotes become ", and the whole thing is wrapped in {"role":"tool","tool_call_id":"…","content":"…"}. Say it grows 3%, which makes 20,600 characters.

Against a 120,000 character budget, that single result is 17%. Five of them is 85%. Add the system prompt, project docs and the model's own explanation, and the budget is gone.

ScenarioRaw sizeLanded sizeShare of 120k
Read a 200 line file16,000 characters16,000 characters13%
Read a 2,000 line file160,000 characters20,000 bytes17%
Whole-repo grep, 200 hits48,000 characters20,000 bytes17%
git diff on a large changepossibly 500,000 characters20,000 bytes17%
web_fetch on an articleup to 2 MB20,000 characters by default17%

That last row is worth noticing. web_fetch has its own max_chars floor at 20,000, the same number as the tool clamp. Not a coincidence: it is one budget, enforced twice.

It also explains a design choice. Every built-in tool's result passes through dispatch's clamp, rather than each tool deciding whether to truncate. A single tool can forget, or underestimate its own output. Enforcing at the exit is what guarantees no tool can flood the context in one shot.

The stable prefix

The system message sits at messages[0] and leads every request. Its content affects two things: how the model behaves, and whether the inference service gets a prefix cache hit.

NanoHermes builds it in system_content: the built-in prompt, the NANOHERMES.md project context, and the skill list. It is rebuilt on three occasions.

OccasionActionWhy
New sessiondefault_messages builds itStarting from nothing
Resuming a sessionrefresh_system replaces itConfiguration may have changed
resetRebuiltNew topic, same rules

Resuming deserves attention. When a session file is loaded, NanoHermes does not reuse the system message stored in it. It regenerates one from the current configuration. The system message is configuration, not conversation. Permission mode, persona and AGENTS.md can all have changed, and restoring verbatim would leave the session running on expired rules.

It isn't fully read-only either. The memory block is replaced every turn by set_memory_block, and that block sits at the end of the system message. So the front half is stable and the back half changes every turn.

For an inference service, prefix caching usually matches on a token prefix. The stable front half hits; everything after the memory block is recomputed. That is an acceptable trade, because putting the volatile part at the end at least preserves the long stable prefix.

Reverse it and the caching collapses. Put the memory block in the middle of the prompt, or prepend a timestamp to the system message every turn, and the cache misses entirely. Context design is not only what goes in, it is where it goes and how often it changes.

The system prompt: short, and layered

The first post covered the five sources of the system prompt. Here they are again, by size.

SourceContentCapFrequency of change
Built-in promptIdentity, six rules, workspace pathAbout 30 linesAt startup
Permission mode noteOne line of constraint per modeOne lineOn mode switch
User personaThe system_prompt settingNo separate capAt startup
AGENTS.mdGlobal plus ancestors, level by level20,000 charactersWhen the file changes
NANOHERMES.mdProject context at the workspace rootNo separate capWhen the file changes
Skill listName and one-line description per skillOne line eachAt startup

Two asymmetries are worth naming.

AGENTS.md has a 20,000 character cap; NANOHERMES.md does not. prompt::project_docs truncates after joining and appends … project guidance truncated. system_content reads NANOHERMES.md whole, with no separate cap. The session budget eventually catches it, but by then it has already ridden along in every request. That is a real boundary: keep the project context file short, and do not treat it as a documentation repository.

The skill list carries names and descriptions only; bodies load on demand. skills::listing emits one line per skill, and the actual instructions are read when the model calls the skill tool, with a 20,000 character cap of its own. Knowing what exists is cheap. Reading all of it is not.

fn system_content(cfg: &Config, skills: &[crate::skills::Skill]) -> String {
    let mut system = prompt::system_prompt(cfg);
    let project_ctx = cfg.workspace.join("NANOHERMES.md");
    if let Ok(text) = std::fs::read_to_string(&project_ctx) {
        if !text.trim().is_empty() {
            system.push_str("

=== Project context (NANOHERMES.md) ===
");
            system.push_str(text.trim());
            system.push('
');
        }
    }
    if !skills.is_empty() {
        system.push('
');
        system.push_str(&crate::skills::listing(skills));
    }
    system
}

The system prompt is resent every turn. A 2,000 token prompt across 20 turns is 40,000 tokens of input. Every sentence has to justify itself as worth paying per turn. Identity and tool rules earn it. Project conventions earn it. A three thousand word company introduction does not.

AGENTS.md: order of assembly and the 20,000 character cut

AGENTS.md is not just the file at the workspace root. NanoHermes collects it from the global config directory, then down from the filesystem root to the workspace.

fn project_docs(workspace: &Path) -> Option<String> {
    let mut candidates: Vec<PathBuf> = Vec::new();
    if let Some(home) = std::env::var_os("HOME") {
        candidates.push(PathBuf::from(home).join(".nanohermes").join("AGENTS.md"));
    }
    let mut chain: Vec<&Path> = workspace.ancestors().collect();
    chain.reverse();
    for dir in chain {
        for name in DOC_NAMES {
            candidates.push(dir.join(name));
        }
    }
    // canonicalize to deduplicate, read the files, join into parts
    let mut joined = parts.join("

");
    if joined.len() > MAX_PROJECT_DOCS {
        let mut end = MAX_PROJECT_DOCS;
        while end > 0 && !joined.is_char_boundary(end) {
            end -= 1;
        }
        joined.truncate(end);
        joined.push_str("
… project guidance truncated");
    }
    Some(joined)
}

The order carries two meanings.

LevelRead orderEffect
Global~/.nanohermes/AGENTS.md firstPreferences shared by every project
Outer directoriesFilesystem root down to the workspaceBroader scope comes earlier
Inner directoriesThe workspace, most specificMore specific comes later, which means higher priority

"More specific later" is not ceremony. When a model reads a long document, later content is usually treated as the current instruction. Putting the workspace's own rules last means they override the general rules above them. The priority is expressed through order rather than hard-coded.

Deduplication handles another case: a file reachable by a symlink or a second path is read once. When canonicalization fails, the code falls back to the original path, preferring a duplicate over a miss.

The 20,000 character cut happens after assembly, so it removes the end of the joined text, which is the most specific project rule. That is a deliberate trade: global preferences and outer conventions are protected first, and if the workspace rules are too long their tail is what gets sacrificed. The better fix is a shorter workspace AGENTS.md, not reliance on the cut.

Memory injection on a 2,400 character budget

The memory block is the only part of the system message that changes every turn. Its budget is small and hard.

ParameterValuePurpose
INJECT_TOP_K4Inject at most four memories
INJECT_CHAR_BUDGET2,400Total characters for the injected block
MAX_TEXT400Length cap per memory
MarkersBLOCK_START and BLOCK_ENDLocate and replace the old block wholesale
 
pub fn render_block(entries: &[&Entry]) -> String {
    if entries.is_empty() {
        return String::new();
    }
    let mut out = String::from(BLOCK_START);
    out.push_str("
Relevant memories retrieved from earlier sessions (extracted automatically, for reference only; the user's current instruction takes precedence):
");
    let mut used = 0usize;
    for e in entries {
        let line = format!("
- [{}] {}", e.kind.label(), e.text);
        if used + line.chars().count() > INJECT_CHAR_BUDGET {
            break;
        }
        used += line.chars().count();
        out.push_str(&line);
    }
    out.push('
');
    out.push_str(BLOCK_END);
    out
}

The important word is break, not continue. When the budget runs short it stops rather than skipping an entry to try a shorter one later. Retrieval already ordered results by relevance, so anything further down matters less. Skipping a highly relevant memory to squeeze in a weak one is a bad trade.

set_block does the replacement: find the old markers, delete the whole segment, append the new block at the end of the system message, and if the new block is empty, delete without appending. Appending instead of replacing is the trap from the first post. Append every turn and the system prompt grows linearly until it owns the entire budget.

The injected text says the user's current instruction takes precedence. That is not politeness. Retrieval ranks by relevance, and relevant is not the same as correct. A stale preference can outrank the current instruction on relevance alone. Writing the precedence into the injected text gives the model a rule to arbitrate with when the two conflict.

Every tool needs a ceiling

A tool that cannot limit its output is a context bomb. It arrives as a cat on a large file, a whole-repo search, a web fetch, or a build command that dumps a log.

NanoHermes puts a gate wherever large output can appear.

Tool or layerCapBehaviour when exceeded
read_file4 MB file, 2,000 lines by defaultRefuses oversized files and suggests chunking
grep1 MB per file, 200 hits, 240 characters per lineSkips oversized files, stops at the hit cap
glob500 filesTruncated, marked as capped
run_command256 KB for stdout and stderr eachKeeps reading, discards, notes the truncation
Background tasks512 KBFirst 512 KB kept, omitted bytes noted
web_fetch2 MB response, 20,000 characters of body by defaultResponse truncated, body cut at max_chars
web_searchResult count and snippet length boundedReturns the first few
All built-in tools20,000 bytesdispatch applies clamp uniformly

These numbers map to different failures, which is why they differ.

4 MB is the read-or-not boundary. Past that size, reading is pointless: the model is never going to see the whole thing through a 20,000-byte cut, so it is better to say "this file is too large, read it in chunks with offset and limit". Refusal, not truncation.

1 MB is the search-or-not boundary. grep walks the whole workspace. A file above 1 MB is skipped so archives, build output and logs are not scanned as source. The skip is silent, but the result shows nothing matched there, and the model can confirm with glob or read_file.

200 hits is the enough-is-enough boundary. Search is for locating, not enumerating. Two hundred hits is plenty to find the target file, and more than the model will read. It stops and says so, so the model doesn't conclude those were all the matches.

256 KB is how loud a command may shout. A build command can emit megabytes. read_capped keeps the first 256 KB and discards the rest while still reading, because stopping would block the pipe and hang the child process. Classic case of "discard but never stop reading".

20,000 bytes is how much of the window one result may take. It does not care which tool produced it. Every built-in result passes through. It is the last line of defense against a tool that forgot its own cap.

Three truncation semantics: refuse, cut, summarize

Truncation is not one action but three different semantics. Mix them up and the model receives contradictory signals.

SemanticExampleWhat the model seesStrengthWeakness
Refuseread_file above 4 MB… is N bytes (> 4194304); read it in chunksExplicit, costs no contextThe model must ask again
Hard cut with a notedispatch's clampFirst 20,000 bytes plus N chars omittedCheap, keeps the beginningThe tail is lost
Counter with a notegrep at 200 hits200 hits plus stopped after 200 matchesPredictable outputLater hits may be missed
Response cut with a noteweb_fetch above 2 MBText plus response truncated at …Body still extractableThe page may be incomplete
SummarizecompactA 300 word summaryPreserves meaning in little spaceOne more request, some loss

All three share one requirement: leave a trace. Silent truncation is the worst option. A model that cannot see the cut treats an incomplete result as complete and decides on missing information. A grep that quietly returns the first 200 matches can convince a model that those are the only matches in the repository, and it edits the wrong file.

Every truncation path in NanoHermes carries a note:

  • clamp: … output truncated (N chars omitted)
  • grep: … stopped after 200 matches
  • glob: … capped at 500 files
  • read_file: … N more lines (total M)
  • shell: … stdout truncated (N bytes not shown)
  • Background tasks: … output truncated (N bytes not shown)
  • web_fetch: [response truncated at 2097152 bytes]

The notes cost space, and they are the best few dozen characters in the context. Without them, the model acts on a false assumption of completeness.

How clamp works

clamp is a dozen lines that handle three easy-to-miss details.

fn clamp(s: String, max: usize) -> String {
    if s.len() <= max {
        return s;
    }
    let mut end = max;
    while end > 0 && !s.is_char_boundary(end) {
        end -= 1;
    }
    format!(
        "{}
… output truncated ({} chars omitted)",
        &s[..end],
        s.len() - end
    )
}

The cap counts bytes. s.len() returns bytes, not characters. For pure ASCII output such as logs, code and command results, those are the same thing. For Chinese output, a character is three bytes, so 20,000 bytes holds roughly 6,600 characters.

The cut must land on a UTF-8 boundary. Slice directly at a byte offset that falls inside a three-byte character and Rust panics. The while loop walks back at most two bytes to guarantee a legal slice.

The note counts bytes but says chars. A small inconsistency: s.len() - end is a byte count and the message calls it characters. Harmless for ASCII, an overestimate for Chinese. It does not affect safety, but it makes the model slightly conservative about how much is left. Better to know that than to pretend it isn't there.

InputCapOutputActually kept
30,000 bytes of ASCII20,000First 20,000 bytes plus the note20,000 characters
30,000 bytes of Chinese, 10,000 characters20,000First 20,000 bytes plus the noteAbout 6,666 characters
Boundary inside a multi-byte character20,000Backs off to 19,998 bytesLegal UTF-8

Which is why the unit should be documented as bytes. Ctx.max_output is a bare usize with no unit, and clamp uses len(), so bytes is what it means.

When compaction fires

Compaction is compact, called after each turn's tool results go back into history.

fn compact_with(&mut self, force: bool) -> usize {
    let size: usize = self.messages.iter().map(|m| m.to_string().len()).sum();
    if !force && (size <= CONTEXT_CHAR_BUDGET || self.messages.len() <= KEEP_RECENT + 1) {
        return 0;
    }

    let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
    while start < self.messages.len() && self.messages[start]["role"] == "tool" {
        start += 1;
    }
    if start <= 1 {
        return 0;
    }

    let dropped: Vec<Value> = self.messages.drain(1..start).collect();
    let note = match self.summarize_messages(&dropped) {
        Some(summary) => format!("[Earlier conversation summary]
{summary}"),
        None => "[Earlier conversation was omitted to keep the context small]".to_string(),
    };
    self.messages.insert(1, json!({ "role": "system", "content": note }));
    dropped.len()
}

Four gates decide whether it runs.

GateConditionWhen not met
Budgetsize > 120_000No compaction
Message countmessages.len() > 11No compaction, not enough old material
Forcedforce == true from /compactThe first two gates are ignored
Cut pointstart > 1 and not on a tool messageNo compaction

size is computed as messages.iter().map(|m| m.to_string().len()).sum(). It measures the serialized JSON length, not the length of the content.

The /compact command calls compact_now(), which calls compact_with(true) and skips the budget gate, so an interactive user can tidy up before the budget explodes.

That distinction matters. A tool message's JSON carries role, tool_call_id and content, plus quotes, colons and escapes. Every newline becomes two characters, every double quote becomes an escape. So size is always slightly larger than the sum of content lengths. For newline-dense material such as code and logs, the gap runs 5% to 10%.

ContentRaw charactersSerializedGrowth
1,000 lines of log50,000about 52,0004%
2,000 lines of code80,000about 84,0005%
JSON full of quotes20,000about 24,00020%

So 120,000 is a JSON character count, not a token count and not a content character count. Treat it as a conservative approximation, not the exact window size.

Why characters and not tokens

Precise context management should count tokens. Each model has its own tokenizer, and the same text costs different amounts on different models. Counting tokens is the only way to hit the window exactly.

NanoHermes counts characters for three reasons.

A tokenizer is a heavy dependency. One vocabulary per model, tens to hundreds of megabytes. Bundling one means binding to a model family or maintaining a copy per model. NanoHermes has three crates and did not want a fourth and fifth just to estimate.

Character counts are a good conservative approximation. English and code run about three to four characters per token; Chinese runs one to two. So 120,000 characters lands somewhere between 30,000 and 60,000 tokens. As long as the budget sits below the real window, the error points the safe way.

Character counts are explainable. "Context: 120,000 characters" is something a user can reason about. "Context: 37,842 tokens" tells them nothing about how much room is left. For an interactive CLI, explainability beats precision.

Text typeCharacters per token (rough)120k characters is about
English prose430,000 tokens
Source code3 to 3.534,000 to 40,000 tokens
Chinese1 to 1.580,000 to 120,000 tokens
Mixed English, Chinese and code2 to 340,000 to 60,000 tokens

The Chinese row is the blind spot. A context that is entirely Chinese can push 120,000 characters close to 120,000 tokens, past the window of many models. NanoHermes mostly handles code and English technical text, so the Chinese share is usually low. If your workload is long Chinese documents, lower the budget or switch to token estimation.

Keep the last ten messages, not the last ten turns

Compaction keeps the last ten messages. The difference from ten turns is large, because the message count per turn depends on how many tools the model called.

What happens in one turnMessages
User asks, model answers in text2 (user and assistant)
User asks, model calls one tool, then summarizes4 (user, assistant, tool, assistant)
User asks, model calls five tools, then summarizes7 (user, assistant, five tools, assistant)
User asks, three tool rounds of two calls each1 + 3 × (1 + 2) + 1 = 11

Keeping "the last ten turns" would preserve 110 messages in the last case, which no budget survives. Keeping the last ten messages caps the retained count no matter how many tools a turn used.

let mut start = self.messages.len().saturating_sub(KEEP_RECENT);
while start < self.messages.len() && self.messages[start]["role"] == "tool" {
    start += 1;
}

saturating_sub handles a history shorter than ten, yielding zero, and the later start <= 1 check returns without touching the system message.

Ten is chosen to guarantee the most recent tool exchange survives. One turn with five tool calls is seven messages; add a user and an assistant and that is nine. Ten covers a complete round trip, so the model knows what just happened.

The cut point must not land on a tool message

The first version of the cut was "start ten from the end and drop everything before". That has a fatal case: if the tenth-from-last message happens to be a tool message, dropping the assistant call before it while keeping the result leaves a tool result with no call behind it.

The next request is rejected outright:

messages with role 'tool' must be a response to a preceding message with 'tool_calls'

The subtler version is a compatibility layer that doesn't reject it. The model then sees a result with no matching call and starts improvising.

NanoHermes pushes the cut point forward until it is no longer a tool message. After that, the dropped region holds complete assistant calls and all their results, and the kept region starts at a non-tool message, so the history stays legal.

Cut pointDroppedKept historyLegal
On a user messageThat user message and everything beforeuser, assistant, tool…Yes
On an assistant messageThat assistant message and everything beforeassistant, tool…Yes
On a tool message, unadjustedThe call, but not the resultAn orphaned tool resultNo
On a tool message, adjustedThe whole round of calls and resultsThe next non-tool messageYes

One more boundary: start <= 1 returns immediately. messages[0] is the system message and messages[1] is the summary or the first exchange. A cut point at 1 or earlier means there is nothing old enough to drop, so compaction gives up rather than discarding the system message.

This rule is a direct extension of the first post's invariant that history must stay legal. Compaction is not deleting an arbitrary slice. It has to preserve the pairing between calls and results.

The summary is one more model request

Compaction does not just delete old messages. It asks the model to summarize what was dropped, and that paragraph goes back in as a system message.

fn summarize_messages(&self, messages: &[Value]) -> Option<String> {
    if messages.is_empty() {
        return None;
    }
    let mut excerpt = String::new();
    for m in messages {
        let role = m.get("role").and_then(|r| r.as_str()).unwrap_or("?");
        let content = match m.get("content") {
            Some(Value::String(s)) => s.clone(),
            Some(Value::Array(arr)) => arr
                .iter()
                .filter_map(|p| p.get("text").and_then(|t| t.as_str()))
                .collect::<Vec<_>>()
                .join(" "),
            _ => String::new(),
        };
        let content = content.trim();
        if content.is_empty() {
            continue;
        }
        excerpt.push_str(&format!("{role}: {}
", content));
    }
    if excerpt.trim().is_empty() {
        return None;
    }
    match llm::summarize(&self.cfg, &excerpt) {
        Ok(s) if !s.is_empty() => Some(s),
        _ => None,
    }
}

The first job is flattening each message into role: content text. Multimodal messages contribute only their text parts; image URLs never enter the summary. Empty messages are skipped.

Then it calls llm::summarize, which turns streaming off, passes no tools, and reuses the main temperature (0 by default). A summary is an ordinary, non-streaming, tool-less model request.

What the summarizer sees, and what it does not

This is the most overlooked part of the design.

summarize_messages reads only each message's content. It does not read function.name or function.arguments from tool_calls.

Message typeEnters the summaryDoes not
userThe text, with multimodal reduced to textImage data
assistant, plain textThe contentNothing
assistant, tool callUsually empty, so the whole message is skippedThe name, arguments and id in tool_calls
toolThe full result textThe tool_call_id and the call it answers

So the summarizer sees a sequence like this:

user: change the install command in the README to pnpm
assistant: let me look at the README first.
tool: 1|# Project
2|
3|## Install
4|npm install
…
assistant: done, it says pnpm now.

It can see that the README was read and what those lines said. It cannot see that the call was read_file with path=README.md. If the tool result itself doesn't name the file, the summary loses the critical fact of which file was changed.

That is a real limitation, and the reason the summary prompt asks for file paths changed. Since structured fields never arrive, the paths have to come from the tool output and the model's prose. read_file output here doesn't carry the filename, so the summarizer infers it from context. edit_file results do carry a path, which usually fills the gap.

Two ways to improve it:

  1. Keep tool names and arguments in the summary input. Render the assistant message's tool_calls as assistant: [read_file] {"path":"README.md"} instead of skipping the message.
  2. Give tool results their own identity. Have each tool say what it did and where, such as read_file README.md.

Both lengthen the summary input and both sharply reduce the "after compaction nobody remembers which file changed" problem.

Degradation when the summary fails

Summarization is one more request, so it can fail: rate limit, timeout, empty response. When it does, compact_with still compacts. It inserts a note instead of a summary:

[Earlier conversation was omitted to keep the context small]

The result is smaller and less useful. The model knows something was removed, which is the important part: it can re-read a file or re-run a search instead of assuming the gap never existed. Silent loss is far worse than an acknowledged gap.

After insertion, the sequence reads: system message, the summary note, then the last ten messages. Legal, bounded, and honest about its own missing pieces.

What to keep, what to drop

Five kinds of information have to survive compaction.

  1. The goal. What the user actually asked for, including constraints and corrections. A summary that loses "don't touch the tests" causes damage later.
  2. Decisions already made. Chosen approach, rejected alternatives, and why. Otherwise the model re-litigates settled questions.
  3. Files touched. Paths created, edited or deleted. Without them the next edit lands in the wrong place.
  4. Dead ends. What was tried and did not work. This is the cheapest information in the world: one line prevents an hour of repetition.
  5. Current state. What is done, what is pending, what is blocked.

Four kinds of content can go without much loss.

  1. Verbose tool output already consumed. The 20,000 lines of a log that produced one conclusion. Keep the conclusion, drop the log.
  2. Successful command chatter. Build logs that passed, install output, test listings that all went green.
  3. Superseded plans. The first draft of an approach that was replaced.
  4. Social scaffolding. "Sure", "let me take a look", "now I'll check the second file".

The asymmetry is deliberate: keeping the wrong thing costs tokens every turn, dropping the right thing costs a repeated action.

Context, memory and session are three different things

The boundary matters because people try to solve context growth by adding memory. Memory is not a bigger context. It is a small, relevance-filtered injection for facts that outlive a conversation. Anything specific to the current task belongs in history, not in memory.

What compaction costs

  • Latency. One extra request on the turn it fires, which is exactly the turn that was already slow because the context was large.
  • Loss. Anything the summary omits is gone from the model's view, even though the full log is still on disk.
  • Drift. Summaries are written by a model. Repeated compaction compounds small distortions, and after several rounds the model's idea of the goal can differ from the user's.

Mitigations are structural: compact late rather than often, keep the goal in the system prompt where it cannot be summarized away, and keep the raw session file so the user can rewind.

Seven ways context goes quietly wrong

  1. A tool without a cap. One uncapped output and the budget is spent before compaction can help.
  2. Appending instead of replacing the memory block. The system prompt grows every turn until it owns everything.
  3. Cutting inside a tool exchange. Orphaned results, and either a hard API rejection or a confused model.
  4. Silent truncation. The model assumes an incomplete result is complete and edits the wrong file.
  5. Volatile content at the front of the system prompt. A timestamp in the opening line kills prefix caching for the whole request.
  6. Treating the last ten turns as the last ten messages. A tool-heavy turn makes the retained set five times bigger than intended.
  7. Summarizing without tool names. The summary cannot say which file was read or changed, and the model re-does work.

How to check that compaction didn't break anything

  • Assert the sequence is legal after every compaction. Every tool message must follow an assistant message with a matching tool_call_id, and the count must match.
  • Assert the system message survives. messages[0] must still be the system message after the cut.
  • Assert the retained count. After compaction, the message count should be at most KEEP_RECENT + 2, the extra two being the system message and the summary.
  • Assert idempotence. Compacting twice in a row without new messages should be a no-op the second time.
  • Check the summary is bounded. A summary longer than the budget is a bug, not a feature.
  • Replay a known session. Keep one recorded session as a fixture and assert that compaction leaves a legal sequence and a summary containing the goal.

These tests are cheap and they cover exactly the failure modes above. A context bug is nearly always a legality bug that shows up as "the model got weird", so the tests belong at the sequence level, not at the prompt level.

Closing

Context engineering compresses into four sentences.

  1. Context is the working set, not the record. Keep what the next message will use, drop the rest, and summarize when unsure.
  2. Cap close to the source. Four megabytes is a refusal, twenty thousand bytes is a cut, and both happen before the session budget matters.
  3. Leave a trace on every cut. The few dozen characters saying "200 matches, stopped" are the highest-value text in the context.
  4. Compaction must preserve legality. The cut point cannot land on a tool message, and the summary has to carry the goal, the decisions, the paths and the dead ends.
