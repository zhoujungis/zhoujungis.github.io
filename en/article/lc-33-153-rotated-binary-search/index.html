LC 33 and 153, rotated sorted arrays: one cliff, two opposite comparisons

2026-09-16 · 14 min · Stack Frame

The problems

153: find the minimum in a rotated sorted array. 33: search for a target in one, in logarithmic time.

Both share one picture: two ascending runs separated by a cliff, with the minimum standing at the start of the right-hand run. Binary search over it must answer one question per step: which side of the cliff is the midpoint on?

Curiously, the two problems compare against opposite ends, and each has a reason, which is the content of this piece.

153: compare with the right end

def findMin(nums):
    l, r = 0, len(nums) - 1
    while l < r:
        mid = (l + r) // 2
        if nums[mid] > nums[r]:
            l = mid + 1
        else:
            r = mid
    return nums[l]

If the midpoint is larger than the current right end, the cliff lies to its right, since otherwise the run would ascend to the right end and not exceed it. So the minimum is further right and the midpoint is eliminated.

If the midpoint is smaller, it is on the right-hand run, or the cliff is at the midpoint itself, so the minimum lies at or left of it, and the midpoint cannot be discarded, which is why the right bound becomes the midpoint rather than one past it.

The loop runs while the bounds differ, stopping when a single element remains.

Why not compare with the left end: if the midpoint exceeds the left end, it may be on the first run, or the array may not be rotated at all, and one comparison cannot distinguish them, so the direction is undetermined. Comparing with the right end has no such ambiguity, since equality only occurs when the interval has shrunk to one or two elements, which does not affect the decision.

The second frame shows why the bound must not step past the midpoint: writing the right bound as midpoint minus one would discard the very candidate that turns out to be the minimum, and the algorithm breaks.

33: compare with the left end, to find the sorted half

The midpoint splits the interval, and the cliff lies entirely in one half, so the other half is fully sorted. Whether the left half is sorted is decided in one step by asking whether the left end is at most the midpoint, with the equality included because a single-element interval must count as sorted.

def search(nums, target):
    l, r = 0, len(nums) - 1
    while l <= r:
        mid = (l + r) // 2
        if nums[mid] == target:
            return mid
        if nums[l] <= nums[mid]:
            if nums[l] <= target < nums[mid]:
                r = mid - 1
            else:
                l = mid + 1
        else:
            if nums[mid] < target <= nums[r]:
                l = mid + 1
            else:
                r = mid - 1
    return -1

So why does one problem use the left end and the other the right? Because the quantities differ. The minimum problem needs to know which side of the cliff the midpoint occupies, which the right end answers unambiguously. The search problem needs to know which half is sorted, which the left end answers in one comparison.

One cliff, two problems, opposite comparisons, because the questions differ.

The two range tests are half-open and closed for different reasons. The left half is open at the upper end since equality with the midpoint already returned. The right half is closed at the upper end because the right endpoint itself may be the target. Getting either wrong loses a solution when the target is exactly an endpoint, which is why both endpoints belong in the self-test.

Entering the unsorted half sounds risky and is proven safe by the range test: if the target were in the sorted half it would have to fall inside that half's range, so failure to fall inside leaves only the other half.

Two classic traps

The minimum problem needs the right bound to become the midpoint, paired with a loop condition that stops when the bounds meet. Substituting midpoint minus one with an inclusive condition is a different and wrong algorithm that skips the minimum.

The search problem needs the equality in the sortedness test. With a strict comparison, a single-element interval is judged unsorted and the logic goes the wrong way.

A frequent follow-up: does an unrotated array break the test? No. Every step finds the left half sorted and the range check works normally, so rotation only moves which half is sorted. The same holds for the minimum problem, which reduces to walking to the first element.

Complexity

Logarithmic time, since each step halves the interval, and constant space. A linear scan is unnecessary because the two-run structure carries enough information, which is why both statements ask for the logarithmic bound. Note the caveat: this depends on distinct elements.

With duplicates

Duplicates break exactly one case in each problem, and both are repaired by retreating one step.

  • Search with duplicates: when the left end equals the midpoint, which half is sorted cannot be determined. The only safe move is to advance the left bound, discarding an element that is certainly not the target, since equality there would already have returned. The worst case, all elements equal, degrades to linear, while the average stays logarithmic.
  • Minimum with duplicates: when the midpoint equals the right end, the cliff direction is undetermined, so retreat the right bound. Even if that element is the minimum, it equals the midpoint, so discarding it cannot discard the answer's value. Also linear in the worst case.

Those two retreats are the only deterministic actions left once duplicates exist, and explaining when and why the bound degrades is worth more than writing the distinct version.

Java

public int findMin(int[] nums) {
    int l = 0, r = nums.length - 1;
    while (l < r) {
        int mid = (l + r) >>> 1;
        if (nums[mid] > nums[r]) l = mid + 1;
        else r = mid;
    }
    return nums[l];
}

public int search(int[] nums, int target) {
    int l = 0, r = nums.length - 1;
    while (l <= r) {
        int mid = (l + r) >>> 1;
        if (nums[mid] == target) return mid;
        if (nums[l] <= nums[mid]) {
            if (nums[l] <= target && target < nums[mid]) r = mid - 1;
            else l = mid + 1;
        } else {
            if (nums[mid] < target && target <= nums[r]) l = mid + 1;
            else r = mid - 1;
        }
    }
    return -1;
}

How to answer it

Draw the picture first, since every test follows from it. Then the minimum problem: compare with the right end, keep the midpoint, loop while the bounds differ. Then the search problem: compare with the left end including equality, then a range test with one open and one closed boundary. Then the contrast, which is the discriminator: the two problems compare against opposite ends because they ask different questions. Self-test on the two endpoint targets.

Closing

Rotated-array binary search is ordinary binary search plus one extra question per step, and the answer grows out of the choice of comparison target.
