LC 234, palindrome linked list: reverse the back half and compare

2026-09-22 · 13 min · Stack Frame

The problem

Decide whether a singly linked list reads the same forwards and backwards.

1 -> 2 -> 2 -> 1   true
1 -> 2             false

Follow-up: linear time and constant space. This is a common warm-up in interviews, and the follow-up is usually the actual ask.

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

What palindromic means on a list

def is_palindrome(arr):
    i, j = 0, len(arr) - 1
    while i < j:
        if arr[i] != arr[j]:
            return False
        i += 1
        j -= 1
    return True

This works because indexing is constant time. A list has no indices, and walking the second pointer back from the end costs a full traversal, which makes the naive version quadratic.

So the "from the end" motion has to be converted into something a list is good at.

1 -> 2 -> 2 -> 1
front: 1 -> 2
back:       2 -> 1
back reversed: 1 -> 2

Reversed, the back half reads exactly like the front half. That is the whole insight: a list is a palindrome exactly when the front half and the reversed back half match node by node.

A counterexample, one, two, three: the front is one, and the reversed back is three then two, so the first comparison already fails.

Reversing in place needs no extra memory, which is how the constant space requirement is met. Finding the middle with two pointers is also constant, so the whole algorithm uses six pointers and no auxiliary structure.

One note: this does modify the list's structure, and the problem does not forbid it. Unlike the reorder problem, which explicitly demands moving nodes, this one only cares about the boolean.

Where the middle lands, and why it differs from the reorder problem

slow = fast = head
while fast and fast.next:
    slow = slow.next
    fast = fast.next.next

Both pointers start at the head here, unlike the reorder problem, and that changes where slow stops. For four nodes it stops on the third, leaving the front as the first two and the back as the last two. For five nodes it stops on the middle one, so the middle belongs to the back half, with the front holding two and the back holding three.

Giving the middle to the back is harmless here because it ends up compared with itself, which always succeeds. It is also convenient: after reversing, it lands at the end of the back half automatically.

Reverse, and notice there is no cut

prev, curr = None, slow
while curr:
    nxt = curr.next
    curr.next = prev
    prev = curr
    curr = nxt

Word for word the reversal from LC 206, starting at the middle instead of the head. And here is the interesting part: the cut is not needed.

In the reorder problem the cut is essential, because merging two live halves winds the pointers into a cycle. Here nothing is merged, only read, so the situation is different in a useful way. The last node of the front still points at the middle, while reversing sets the middle's link to none, since it becomes the first node of the reversed segment. So walking from the head stops at the middle naturally, and the front traversal has exactly the length we want.

after reversing, four nodes:
front: 0 -> 1 -> 2 -> None
back:  3 -> 2 -> None

The leftover link is not a bug here; it is borrowed.

Compare pairs

p1, p2 = head, prev
while p2:
    if p1.val != p2.val:
        return False
    p1, p2 = p1.next, p2.next
return True

The condition must be on the back pointer. For an even length the front chain has one more node than the reversed back, because the front is walked until it reaches the middle while the back stops there. Using the front pointer instead would dereference an empty pointer once the back one runs out. The back is always the shorter chain, so it is the correct bound; for odd lengths they are equal and the last pair is the middle against itself.

The animation

The original post breaks the example into nine steps. In the middle-finding phase fast crosses two nodes per step and exits while slow lands at the start of the back half. In the reversing phase the back half drops a row, its arrows turn around one by one, and the whole segment reads left to right like the row above it. In the comparison phase the two rows line up, one pointer walking each, with a marker between each pair.

Seen that way, the core insight is literal: the two rows are identical.

Code

class Solution:
    def isPalindrome(self, head: Optional[ListNode]) -> bool:
        if head is None or head.next is None:
            return True

        slow = fast = head
        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next

        prev, curr = None, slow
        while curr:
            nxt = curr.next
            curr.next = prev
            prev = curr
            curr = nxt

        p1, p2 = head, prev
        while p2:
            if p1.val != p2.val:
                return False
            p1, p2 = p1.next, p2.next
        return True

class Solution {
    public boolean isPalindrome(ListNode head) {
        if (head == null || head.next == null) return true;

        ListNode slow = head, fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }

        ListNode prev = null, curr = slow;
        while (curr != null) {
            ListNode nxt = curr.next;
            curr.next = prev;
            prev = curr;
            curr = nxt;
        }

        ListNode p1 = head, p2 = prev;
        while (p2 != null) {
            if (p1.val != p2.val) return false;
            p1 = p1.next;
            p2 = p2.next;
        }
        return true;
    }
}

The early return is defensive: a single node would also compare correctly, since the middle compares with itself, but stating it saves a pointless reversal and makes the intent explicit.

For one, two, three the failure is immediate: after reversing, the back starts with three, and the first comparison is one against three, so it returns false after a single pair. That is why the check returns as soon as a mismatch appears rather than collecting everything first.

Worth remembering: an empty list is a palindrome, and so is a single node. Odd lengths compare the middle with itself once, which is free. The number of comparisons is the ceiling of half the length, though only the floor of it is informative.

Complexity

Linear time: the middle-finding loop runs about half the length, reversing touches the other half, and comparison walks half again, which totals under one and a half passes over the nodes. Constant space: six pointers, no array, no stack, no recursion.

The array version would also be linear in time and linear in space, and compressing that space is precisely what the follow-up is testing.

Common mistakes

  1. Putting the front pointer in the comparison loop condition, which dereferences an empty pointer for even lengths.
  2. Confusing the middle convention with the reorder problem. The two are opposite, and each start position pairs with a matching way of taking the back half; mixing them loses or adds one comparison.
  3. Adding the cut. It is unnecessary here and not wrong, but it costs one comparison and makes restoring the list harder.
  4. Comparing recursively, which is elegant and uses linear stack space, failing the follow-up.
  5. Forgetting the empty and single-node guards, particularly in variants that manipulate the second link inside the loop.
  6. Being unable to answer whether the list can be restored. It can, in one line: reverse the back half again, because nothing was ever cut, so re-reversing reattaches it.

How to answer it

State the idea in thirty seconds rather than starting to type: a palindrome means the front half equals the reversed back half, and since a list cannot walk backwards, reverse the back and compare with two pointers. Then find the middle with two pointers, reverse, compare. Linear time, constant space.

Then volunteer the three subtleties, which is what separates understanding from memorisation: both pointers start at the head so slow lands at the start of the back half with the middle included, no cut is needed because reversing clears the middle's link so the front walk stops there by itself, and the comparison loop is bounded by the back pointer because the front chain is longer for even lengths.

For the follow-ups: no extra space is already the case, six pointers; restoring is one more reversal of the back half; the odd middle compares with itself and needs no special case; and the recursive front-and-back-pointer trick uses linear stack space, so it does not qualify.

This and the reorder problem share a skeleton; the difference is the third step. One rewires the topology, so it must cut to avoid a cycle. The other only reads values, so the cut is optional and skipping it is actually simpler.

So when a list problem asks you to go backwards, ask first whether reversing the back half turns it into a forwards problem. If it does, half the work is done.
