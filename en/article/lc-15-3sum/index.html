LC 15, three sum: the difficulty is the two dedup checks, not the pointers

2026-09-24 · 20 min · Stack Frame

The problem

Given an integer array, return all unique triples that sum to zero.

[-1, 0, 1, 2, -1, -4]  ->  [[-1, -1, 2], [-1, 0, 1]]
[0, 1, 1]              ->  []
[0, 0, 0]              ->  [[0, 0, 0]]

One more number than the two-sum problem, one more order of magnitude in complexity, and two more levels of difficulty in deduplication. The typical first attempt reaches for a hash table, passes the samples, and then submits an answer full of duplicates.

The correct route is a single path, and it counterintuitively stops using hashing entirely after sorting.

What is being tested

for i in range(n):
    for j in range(i + 1, n):
        for k in range(j + 1, n):
            if nums[i] + nums[j] + nums[k] == 0:
                res.append([nums[i], nums[j], nums[k]])

Cubic, and worse than slow: it cannot deduplicate at all. On the official example it returns three groups where only two are distinct, because it emits permutations of the same triple.

Two constraints that are easy to conflate. The indices must differ, which means no element is reused. And the answer must not repeat a triple, which means an ordering of the same three values counts once. The brute force enforces the first through the loop bounds and ignores the second entirely.

Fixing one value reduces it to two sum

Rewrite the equation so the other two terms are on one side: for each index i, find two values in the remainder that sum to the negation of nums at i.

Carrying the hash-table solution over works, and shows why it is a bad fit.

def threeSumHash(nums):
    n = len(nums)
    seen_triples = set()
    for i in range(n):
        target = -nums[i]
        seen = {}
        for j in range(i + 1, n):
            if target - nums[j] in seen:
                triple = tuple(sorted([nums[i], nums[j], target - nums[j]]))
                seen_triples.add(triple)
            seen[nums[j]] = j
    return [list(t) for t in seen_triples]

Two problems. A hash table cannot answer whether a triple has already been recorded, only whether a value has been seen, so a set of tuples becomes mandatory, and building and hashing quadratic numbers of tuples costs real time. And that tuple must be sorted to make different orderings collide, which means sorting is unavoidable anyway, so why not sort the array once at the start.

The correct route

1. sort ascending
2. for each i, fix the smallest member of the triple
3. squeeze with l = i + 1 and r = n - 1

The inner test has three cases: too small, move the left pointer right to a larger value; too large, move the right pointer left to a smaller value; equal to zero, record the triple.

Why the squeeze cannot skip a solution, which should not be taken as obvious. With i fixed, the target for the pair is fixed. When the right pointer sits at the far end, the pair sum is the largest reachable with the current left pointer, because the right end holds the largest remaining value. If even that maximum falls short of the target, no pairing with that left pointer can work, so the left pointer may safely advance and never needs to return.

Symmetrically, when the left pointer is at its leftmost, the pair sum is the smallest reachable with the current right pointer; if it exceeds the target, the right pointer may retreat.

The same argument proves that both pointers move monotonically, so they total at most n steps, making the inner loop strictly linear rather than quadratic.

The real benefit of sorting

Sorting is not there to make lookups faster; there are no lookups. It is there to put equal values next to each other.

What needs deduplicatingUnsortedSorted
Repeated starting valuesRemember which minimums were already usedCompare with the previous element
Repeated partner pairsNormalise and insert triples into a setCompare with the neighbouring index
Ordering within a tripleSort each answerAscending by construction

The whole deduplication collapses into two constant-time comparisons.

The code

def threeSum(nums):
    nums.sort()
    res = []
    n = len(nums)

    for i in range(n - 2):
        if nums[i] > 0:
            break
        if i > 0 and nums[i] == nums[i - 1]:
            continue

        l, r = i + 1, n - 1
        while l < r:
            total = nums[i] + nums[l] + nums[r]
            if total < 0:
                l += 1
            elif total > 0:
                r -= 1
            else:
                res.append([nums[i], nums[l], nums[r]])
                while l < r and nums[l] == nums[l + 1]:
                    l += 1
                while l < r and nums[r] == nums[r - 1]:
                    r -= 1
                l += 1
                r -= 1

    return res

Twenty lines, of which three exist to handle repetition: the positive break, the outer skip, and the inner skip. A third of the code is about duplicates.

Worth isolating. The first round squeezes four times and finds nothing, because the largest remaining pair sums to three while four is needed, which is a candidate for pruning. The second round hits twice, and both dedup frames report nothing to skip; they still run, they are fixed steps of the algorithm. The eleventh frame is the only real deduplication, and without it both triples would be found again from the same starting value. And the last round runs unnecessarily, since the smallest possible sum is positive, which is the other pruning opportunity.

Deduplication: two places, different shapes

The outer skip, before the work

if i > 0 and nums[i] == nums[i - 1]:
    continue

The starting value for this round equals the previous round's starting value. Since the array is ascending, the fixed value is the smallest member of any triple this round could produce, and the available partners are the same suffix of the array. Anything findable here was findable last round, so the entire round is skippable without entering the inner loop.

The guard on i is not merely an out-of-range check. In Python, indexing at minus one is legal and wraps to the last element, so without it the first iteration compares the first element with the last, producing a decision that is effectively random and far harder to debug than a crash.

The inner skip, after a hit

res.append([nums[i], nums[l], nums[r]])
while l < r and nums[l] == nums[l + 1]:
    l += 1
while l < r and nums[r] == nums[r - 1]:
    r -= 1
l += 1
r -= 1

Having recorded a triple, any neighbour holding the same value produces an identical triple. This must be after the fact, because before a hit there is no pair to skip. That is why the shape is a loop rather than a branch.

The extra step after each loop matters: the loops stop on the last copy of the left value and the first copy of the right value, which are the values just used, so both pointers must move once more to leave the pair behind.

The bounds check inside the loops does two jobs, preventing an out-of-range read and preventing a pointer from overrunning the other, which would skip pairings that should be considered.

What happens if either is missing

Both produce duplicate answers, under different conditions, which is why testing with the official samples catches neither.

[-1, -1, 0, 1]
  with the outer skip:   one triple, -1, 0, 1
  without it:            the same triple recorded twice

[-2, 0, 0, 2, 2]
  with the inner skip:   one triple, -2, 0, 2
  without it:            the same triple recorded twice

What those two inputs have in common is that a duplicate sits exactly where a pointer will pass. In the official example, after sorting, the two copies of minus one are adjacent but one lands as the anchor and the other as a left pointer, so neither skip condition actually fires.

So passing the official sample proves nothing about deduplication. Those two arrays belong in the self-test set.

The sort is not the bottleneck, which is why sorting up front is free, and is the confidence behind the earlier argument. Strictly, constant space excludes the sort itself: Timsort needs linear auxiliary space and Java primitive sorting needs logarithmic stack. Saying that out loud is a good note.

Note that the hash version and this one share an asymptotic class. The pointers win on constants, space, and clarity of the deduplication, not on order of magnitude. Saying that precisely is better than claiming the pointers are faster.

Two prunings

if nums[i] > 0:
    break

If the smallest member is already positive, the other two are larger and the sum cannot reach zero. It is a break rather than a continue because ascending order implies every later anchor is also positive. The official sample never triggers it, but an all-positive array terminates the whole outer loop immediately.

minimum = nums[i] + nums[i + 1] + nums[i + 2]
if minimum > 0:
    break

maximum = nums[i] + nums[-1] + nums[-2]
if maximum < 0:
    continue

These compute the reachable range for the round before entering the inner loop. The third round of the trace is exactly what the second line catches: with zero as the anchor, the largest possible sum is positive and the smallest is positive too, so no zero is reachable.

Both are optional. Get the main logic and both deduplications right first; a pruning that breaks a boundary is a net loss.

Variant: closest sum, and four sum

def threeSumClosest(nums, target):
    nums.sort()
    best = nums[0] + nums[1] + nums[2]
    n = len(nums)

    for i in range(n - 2):
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        l, r = i + 1, n - 1
        while l < r:
            total = nums[i] + nums[l] + nums[r]
            if abs(total - target) < abs(best - target):
                best = total
            if total < target:
                l += 1
            elif total > target:
                r -= 1
            else:
                return target

    return best

Three differences. The inner deduplication disappears, because the answer is a single sum and duplicate triples produce the same value. An early return is safe, since a difference of zero cannot be beaten. And the initial best must be a real sum rather than zero, since a difference from zero could look better than the true answer.

def fourSum(nums, target):
    nums.sort()
    res = []
    n = len(nums)

    for a in range(n - 3):
        if a > 0 and nums[a] == nums[a - 1]:
            continue
        for b in range(a + 1, n - 2):
            if b > a + 1 and nums[b] == nums[b - 1]:
                continue
            l, r = b + 1, n - 1
            while l < r:
                total = nums[a] + nums[b] + nums[l] + nums[r]
                if total < target:
                    l += 1
                elif total > target:
                    r -= 1
                else:
                    res.append([nums[a], nums[b], nums[l], nums[r]])
                    while l < r and nums[l] == nums[l + 1]:
                        l += 1
                    while l < r and nums[r] == nums[r - 1]:
                        r -= 1
                    l += 1
                    r -= 1

    return res

Cubic, with the same deduplication pattern: one extra comparison per added loop, and the innermost skip unchanged.

Note that the second level compares against the start of its own range rather than against zero, because deduplication happens within a fixed outer anchor. The boundary condition of a dedup check depends on where that loop begins, and cannot be copied blindly.

def threeSumSmaller(nums, target):
    nums.sort()
    count = 0
    n = len(nums)

    for i in range(n - 2):
        l, r = i + 1, n - 1
        while l < r:
            if nums[i] + nums[l] + nums[r] < target:
                count += r - l
                l += 1
            else:
                r -= 1

    return count

When the sum is below the target, every index between the left pointer and the right also works with the current left value, because the array is ascending. So an entire stretch counts at once instead of being enumerated.

That is the real power of ordering: not just that pointers can move, but that whole ranges can be counted in one statement. The single-step jump of the sliding window problem and this batch count are the same idea, using monotonicity to replace a linear enumeration with a constant-time conclusion.

Java

class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> res = new ArrayList<>();

        for (int i = 0; i < nums.length - 2; i++) {
            if (nums[i] > 0) break;
            if (i > 0 && nums[i] == nums[i - 1]) continue;

            int l = i + 1, r = nums.length - 1;
            while (l < r) {
                int total = nums[i] + nums[l] + nums[r];
                if (total < 0) {
                    l++;
                } else if (total > 0) {
                    r--;
                } else {
                    res.add(Arrays.asList(nums[i], nums[l], nums[r]));
                    while (l < r && nums[l] == nums[l + 1]) l++;
                    while (l < r && nums[r] == nums[r - 1]) r--;
                    l++;
                    r--;
                }
            }
        }
        return res;
    }
}

Passing three primitive integers to the list factory autoboxes them, which is what you want. Passing the whole array instead yields a single-element list containing the array, which is a classic trap. And primitive sorting differs from object sorting in both algorithm and auxiliary space, which matters when someone asks whether the space is truly constant.

Edges and mistakes

InputOutputNote
shorter than threeemptyGuarded by the loop bounds
three values, no zeroempty
three zerosone triple
four zerosone tripleThe outer skip does the work
all positiveemptyPruned immediately
exactly minus one, zero, oneone triple
  1. Omitting the index guard on the outer skip. Python wraps a negative index to the end of the array, so the first round is skipped or not at random rather than crashing.
  2. Omitting the pointer ordering check inside the inner skip loops, which reads out of range and can also overrun.
  3. Forgetting the step inward after the inner skips, which leaves the pointers on the values just used and loops forever.
  4. Sorting with a default comparator in JavaScript, which converts to strings and breaks monotonicity: minus four sorts after minus one. The code does not crash, it silently returns wrong answers.
  5. Doing it with a hash table and a set, which works and costs quadratic tuple construction. Sorting first makes deduplication two comparisons.
  6. Confusing distinct indices with distinct triples. The first is guaranteed by the loop bounds and is not the part to write; the second is what needs the two checks. A result like three zeros is legitimate as long as three distinct indices exist.

How to answer it

Start with the brute force and its two defects: cubic, and unable to deduplicate. Then explain why hashing is not the answer: a table cannot say whether a triple has been recorded, and normalising orderings requires sorting anyway. Then give the pointer correctness argument, which is where preparation shows: at the extreme right the pair sum is maximal for the current left pointer, so a shortfall eliminates that left pointer entirely, and the symmetric argument applies to the right; both pointers move monotonically, so the inner scan is linear.

Then volunteer the two deduplication sites and why their shapes differ, one before the work as a skip and one after a hit as a loop. Then the boundaries: the index guard on the outer and the ordering check on the inner. Then the prunings, and finally the variants, including the batch count that monotonicity makes possible.

Closing

The skeleton takes ten minutes to memorise; the deduplication does not, because the two sites differ in shape, timing and boundary trap, and the official sample triggers neither.

The value of sorting is not faster lookup but adjacency, and once equal values are adjacent, deduplication degenerates into comparing with the previous value. Two constant-time comparisons carry most of the difficulty of this problem.

That view extends further: sliding window, two pointers and binary search all replace enumeration with conclusions drawn from order. Ordering produces no answers by itself; it produces space that can be skipped.

assert threeSum([0, 0, 0, 0]) == [[0, 0, 0]]
assert threeSum([-2, 0, 0, 2, 2]) == [[-2, 0, 2]]
assert threeSum([-1, -1, 0, 1]) == [[-1, 0, 1]]
assert threeSum([1, 2, 3]) == []

Those four lines are worth more than ten runs of the official sample.
