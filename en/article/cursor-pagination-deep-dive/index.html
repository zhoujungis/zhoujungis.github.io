Why a deep offset gets slower, and what cursor pagination fixes

2026-11-04 · 16 min · Stack Frame

Who this is for: backend engineers whose list endpoints get slower the deeper they are paged, and whose slow query logs fill with large offsets.

Examples are in Django and standard SQL, and the same reasoning applies in any stack.

Reading time around 16 minutes. Level: intermediate.

One statement from the slow query log

SELECT id, title, created_at
FROM article
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 500000;

This is the blog's article list endpoint. Everything was fine just past a million rows, and then, as the table grew and users paged into the twenty-thousandth page, which crawlers and a few endless-scroll clients like to do, the statement went from three milliseconds to over two seconds. Database CPU oscillated and every request sharing the same connection pool slowed down with it.

The first instinct is to add an index. There is one: the whole point of the index is to serve that ordering. Adding an index and still being slow means the problem is not the index, it is what the offset does.

What an offset really costs

Most people imagine the database jumping straight to row 500,001. That is not what happens, because there is no general ability to fetch row N directly. The engine reads rows one to 500,020 in index order, throws the first 500,000 away, and returns the remaining twenty.

So the work is offset plus limit. The deeper the page, the more rows are read and discarded, and the time grows linearly. That is the origin of the O(offset) complexity.

Comparing two plans on a million-row table, changing only the offset, shows the difference: a near-zero startup cost at offset zero, and a startup cost that already includes scanning half a million rows at offset 500,000. If the selected columns are not in the index, each of those rows also needs a fetch, which is worse.

One common workaround, the deferred join, first selects primary keys from a covering index and then joins back to the table. That genuinely cuts the fetches from 500,020 to twenty and is often ten times faster. But it does not change the linear nature: the subquery still walks 500,000 index entries. It buys time; it does not solve the problem.

The problem is not only that one query is slow. Deep paging traffic concentrates in a few clients, crawlers, export scripts and infinite scroll, and they issue a series of ever deeper requests that push the genuinely hot pages out of the buffer pool. Every query in the system slows down, which is why deep pagination so often appears in alerts alongside a CPU spike.

The core idea: replace the page number with the last row

Offset pagination asks the database to skip N rows. Cursor pagination, also called keyset pagination, changes the question: instead of how many to skip, tell it what the last row of the previous page was, and continue from there.

SELECT id, title, created_at
FROM article
WHERE (created_at, id) < ('2026-09-01 12:00:00+08', 86400)
ORDER BY created_at DESC, id DESC
LIMIT 20;

That row comparison means lexicographic comparison: either the timestamp is smaller, or it is equal and the id is smaller.

The execution path is completely different. The index is stored in that order, so locating the pair is one seek, after which twenty rows are read in sequence. No matter how deep the page, the rows scanned equal the limit. The complexity is constant with respect to page depth.

The simplest version

SELECT id, title FROM article
WHERE id < 86400
ORDER BY id DESC
LIMIT 20;

def get_page(last_id, size=20):
    qs = Article.objects.order_by("-id")
    if last_id is not None:
        qs = qs.filter(id__lt=last_id)
    return list(qs[:size])

Fine as a starting point, with two production problems. It only supports ordering by id, whereas the product wants ordering by publish time with a stable tie-break. And the cursor is bare, so clients can guess and construct values, which exposes internal keys and invites scripted enumeration.

Five details for production

The sort key must be unique and stable

Ordering by timestamp alone has a fatal detail: timestamps repeat, either because several rows share a second or because the column has only second precision. If the cursor carries only the timestamp, a page boundary that falls in the middle of a repeated value either loses rows or repeats them.

So add a tie-breaker and make the sort key the pair of timestamp and id. The id makes the total order unique and the timestamp satisfies the product requirement. Index in that order, and note that some engines handle the row comparison well while others are better off with the equivalent expanded or-form.

WHERE created_at < '2026-09-01 12:00:00'
   OR (created_at = '2026-09-01 12:00:00' AND id < 86400)

It is an or, not an and, and the comparison direction is easy to invert. Those two mistakes are the most common bugs in cursor pagination.

The cursor should be opaque and signed

Clients should not pass raw key values. They should pass an opaque string the server issued, which they return unchanged. The server encodes the payload, appends a short HMAC over it, and base64url encodes the pair; decoding verifies the signature and rejects anything malformed with a validation error rather than a server error.

The signature does two things: it stops clients from tampering with a cursor to walk data they should not see, and it stops nonsense values from producing a scan. A whitelist on the sort key is the second half of that defence.

Null values in the sort key

If the sort key can be null, for example drafts without a publish time, the default ordering behaviour differs between engines, and some put nulls first on a descending sort while others put them last. Migrating between databases breaks immediately. Declare it explicitly, or better, make the column non-null with a default so the cursor never meets a null. A nullable sort key plus cursor pagination produces intermittent lost rows that are very hard to reproduce.

Snapshot semantics while paging

Offset pagination has a subtle flaw: someone publishes a new article while you are on page three, every row shifts, and content you already saw on page two appears again. Cursor pagination is immune, because the cursor anchors to a position rather than a count, so inserts do not move the starting point.

It is not a panacea either. Inserts behave correctly. A delete is also fine, since the condition compares against a value rather than requiring the row to exist. But an update to the sort key can move a row to an earlier position and make it appear twice, so ordering by a field that changes, such as an update time, needs the semantics thought through. Prefer immutable fields.

Totals and the next-page probe

Offset pagination hands out a total page count for free, and clients get used to it. With cursors, three things change. An exact count is another deep scan on many engines. An estimate from table statistics is nearly free and can be shown as approximately a million. And whether a next page exists is discovered by fetching one extra row: request size plus one, return size, and if the extra row came back there is more.

The product implication is that infinite scroll and load-more use cursors, while jump-to-page plus exact totals, typical in admin tools, keep offsets. Both can coexist.

A pagination class you can copy

A keyset paginator supports a composite sort key, both directions, an HMAC-signed opaque cursor, and a one-row lookahead. The essentials:

class KeysetPagination(BasePagination):
    """Cursor pagination over (created_at, id) descending.
    Requires an index on that pair, and both columns non-null."""

    page_size = 20
    cursor_query_param = "cursor"

    def paginate_queryset(self, queryset, request, view=None):
        page_size = self.get_page_size(request)
        cur = decode_cursor(request.query_params.get(self.cursor_query_param, ""))
        direction = cur.get("d", "next")

        if "t" in cur:
            ts, pid = cur["t"], cur["i"]
            if direction == "next":
                queryset = queryset.filter(
                    Q(created_at__lt=ts) | Q(created_at=ts, id__lt=pid)
                ).order_by("-created_at", "-id")
            else:
                queryset = queryset.filter(
                    Q(created_at__gt=ts) | Q(created_at=ts, id__gt=pid)
                ).order_by("created_at", "id")
        else:
            queryset = queryset.order_by("-created_at", "-id")

        rows = list(queryset[: page_size + 1])   # one extra to detect a next page
        self.has_next = len(rows) > page_size
        rows = rows[:page_size]
        if direction == "prev":
            rows.reverse()
        self._rows = rows
        return rows

The response carries a signed next cursor when more rows exist, a previous cursor pointing at the first row, and the results. The client sends the cursor back verbatim and never parses it.

The cursor's cost is a flat line, independent of depth, which is its whole advantage. The deferred join is cheap first aid, one statement to change, clearly worthwhile up to a few thousand pages. And for crawlers, cursor pagination turns a cost that grew quadratically into a linear one, which in this case took search engine crawling from a database problem to almost nothing.

When not to use cursors

  • Users need to jump pages and see exact totals, as in admin and reporting screens. Data volume there is usually manageable, and offsets plus a decent index are enough.
  • The result set is small: return it whole and paginate in the client.
  • Ordering depends on a computed score that cannot be indexed. Either materialise the score into a column and index it, or accept the query and cache the result.
  • The endpoint is stable and pages are shallow, where changing the client contract costs more than it saves.

A pragmatic migration: leave old endpoints alone, build new ones with cursors, and convert the deepest traffic first. Deep paging concentrates in one or two endpoints, so converting those removes most of the slow queries.

Checklist before shipping

  • Is the sort key unique and stable, with a tie-breaker.
  • Does the index match the ordering direction.
  • Are both key columns non-null, or is the null ordering declared explicitly.
  • Is the cursor signed and encoded, with invalid cursors returning a client error.
  • Is the next page detected by fetching one extra row rather than a separate existence query.
  • Are totals replaced with estimates, and has the product accepted that pages cannot be jumped to.
  • On engines where row comparisons index poorly, is the condition expanded.
  • Does the client documentation say the cursor is opaque and that a reset goes back to the first page.
  • Has the slow query log been checked to confirm the deep offset statements are gone.

Closing

Deep pagination in one sentence: an offset makes the database pay for skipping, a cursor makes it pay for seeking. Skipping grows with depth, seeking on a tree is constant.

The change itself is not much work: one composite key, one signed cursor, one lookahead. The real effort is persuading the product and the client that pages cannot be jumped to, and thinking through the snapshot semantics of the sort field. Get those two settled and the rest is mechanical.
