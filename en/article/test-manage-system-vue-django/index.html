Building a Test Management System from Scratch: A Vue 3 + Django Full-Stack Walkthrough

Introduction

In software development, testing is where quality is won or lost. Yet plenty of teams still manage test cases in Excel spreadsheets and sync defect status through a WeChat group — slow, and prone to gaps and mistakes. The Test Management System I want to walk through today is a full-stack platform built specifically for QA teams. It uses Vue 3 for the front end and Django for the back end, and it covers the entire lifecycle: test case management, test plans, execution tracking, defect management, and team collaboration.
Repository: github.com/zhoujungis/test_manage_system

3. Four roles, each with its own job

The system defines four roles, and each one sees a different slice of the product: 
┌───────────────────────────────────────────────────────────┐
│  Role permission pyramid                                  │
│                                                           │
│       ┌──────────┐                                        │
│       │  Admin   │  system + users + permission setup     │
│       │ (Admin)  │  "I hold every key"                    │
│       └────┬─────┘                                        │
│            │                                              │
│       ┌────▼─────┐                                        │
│       │Developer │  case library CRUD + projects + runs   │
│       │(Developer│  "I maintain the case library"         │
│       └────┬─────┘                                        │
│            │                                              │
│       ┌────▼─────┐                                        │
│       │  Tester  │  join projects + read cases + run      │
│       │ (Tester) │  "I execute the tests"                 │
│       └────┬─────┘                                        │
│            │                                              │
│       ┌────▼─────┐                                        │
│       │  Viewer  │  read only, no writes                  │
│       │ (Viewer) │  "I am just looking"                   │
│       └──────────┘                                        │
│                                                           │
└───────────────────────────────────────────────────────────┘
Every permission is fine-grained. Same "view the case library" capability — can you read it but not change it? Then you are a Tester. Can you also create, update, and delete? Then you are a Developer. Each capability is an independent switch that can be combined freely.

Security measures

  • 📧 Sign-up is restricted to @glazero.com email addresses
  • 🔑 Passwords are stored hashed, and login requires a verification code
  • ⏱️ Access tokens are valid for 1 hour; refresh tokens renew automatically for 8 hours
  • 🚦 The login and code-sending endpoints are rate limited

4. A closer look at the ten functional modules

4.1 Authentication — badge in before you go anywhere

The registration flow is deliberately strict: 
User enters email (@glazero.com)
        │
        ▼
  Validate email format + check domain allowlist
        │
        ▼
  Send verification code to email
        │
        ▼
  Enter the code + set a password
        │
        ▼
  Registered → assign default role
        │
        ▼
  Log in → fetch JWT token → enter the system
The user model pairs Django's built-in auth.User with a UserProfile extension: 
# accounts/models.py — the actual shape of the code
from django.contrib.auth.models import User

class UserProfile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE,
                                related_name='profile')
    role = models.CharField(max_length=20, default='tester',
        choices=[('admin','Admin'),('tester','Tester'),
                 ('developer','Developer'),('viewer','Viewer')])
    phone = models.CharField(max_length=20, blank=True)
    can_access_projects = models.BooleanField(default=True)
    can_access_testcase_library = models.BooleanField(default=True)
    can_manage_testcase_library = models.BooleanField(default=True)
    can_access_my_projects = models.BooleanField(default=True)
Default permissions are derived from the role at registration time — the ROLE_DEFAULT_PERMISSIONS dict defines which feature switches each of the four roles (admin, tester, developer, viewer) gets out of the box.

4.2 Project management — creating the workspace

Every test project carries its full context: 
Project
├── Basics: name, description, product line (camera / doorbell)
├── Status: active / archived
├── Members
│   ├── Leader (owner)
│   ├── Tester
│   └── Developer
├── Module tree
│   ├── 📁 Video features
│   │   ├── 📄 Live preview
│   │   └── 📄 Video playback
│   └── 📁 Audio features
│       └── 📄 Two-way talk
└── Task management
    ├── Test rounds
    ├── Priority
    └── Due date
The neat part here is the module tree — a self-referencing parent foreign key in Django gives you unlimited nesting: 
class Module(models.Model):
    project = models.ForeignKey(Project, on_delete=models.CASCADE)
    name = models.CharField(max_length=100)
    parent = models.ForeignKey('self', null=True, blank=True,
                               on_delete=models.CASCADE)
    # parent is None → root module
    # parent points at another Module → child module

Bulk import is where it really earns its keep — a single Django command pulls every case out of an Excel file: 
python manage.py import_camera_cases camera_cases.xlsx
It detects the column headers, groups worksheets into modules by sheet name, and numbers the steps for you.

How does a case turn into a test task? Follow the flow:

Project → Task → Member

    │  Execute
    ▼
┌──────────────────────────────────┐
│  Status:                         │

Every execution result supports attachments (up to 15MB) — screenshots, logs, and so on. Leaders can approve in bulk instead of clicking through one by one.

4.7 Defect tracking — the life of a bug

Found a problem while executing tests? File a defect right there: 
Defect lifecycle

│   Open   │───▶│In Progress  │───▶│ Resolved │───▶│  Closed  │
│    New   │    │  Being fixed│    │   Fixed  │    │  Closed  │

Each defect record contains: - Title & description — what is broken - Severity — from S0 (worst / blocking) to S4 (minor / suggestion) - Related project — which project the problem belongs to - Related test result — which test run surfaced it - Assignee — who is fixing it

4.9 Statistics — data aggregation at the API layer

Beyond the launcher page, the dashboard app exposes a stats API (GET /api/dashboard/stats/) that other pages and external tools can call:
  • total_projects, total_testcases, total_testplans, total_testruns — the four top-level counters
  • results — result distribution (passed/failed/blocked/skipped/pending) plus the pass rate
  • defects — defect counts (total/open/resolved)
  • priority_distribution — case priority distribution (how many sit at each of P0-P4)
  • type_distribution — case type distribution (functional/API/UI/performance)
  • recent_runs — the five most recent runs
A project_id parameter scopes everything to a single project. The endpoint uses Django ORM's aggregate together with conditional Count to compute every statistic in a single query, which keeps it fast.

4.10 Admin console — keeping hold of the whole picture

Features reserved for the Admin role:
  • User management — create, delete, and list users
  • Permission configuration — fine-tune each person's role and permission switches
  • Non-admin users cannot change their own permissions (a deliberate security decision)

# one command turns Excel into test cases

How do the database tables relate?

User ──1:1──▶ UserProfile (role, permissions)
  │
  │  (many-to-many, through ProjectMember)
  ▼
Project ──1:N──▶ Module (self-referencing tree)
  │   │
  │   └──1:N──▶ ProjectTask
  │                │
  │                └──1:N──▶ TestCaseAssignment
  │                             │
  │                             └──1:N──▶ AssignmentAttachment
  │
  └──1:N──▶ TestPlan ──1:N──▶ TestPlanCase
                │                 │
                │                 └──(references TestCase)
                │
                └──1:N──▶ TestRun ──1:N──▶ TestResult
                                              │
                                              └──1:N──▶ Defect

TestCase ──1:N──▶ TestCaseStep
The key design decisions: - One-to-many relations run through the whole schema, which keeps the structure easy to follow - A self-referencing Module delivers an arbitrarily deep tree - Defect ↔ TestResult is an optional link, so every bug traces back to the test that found it - select_related / prefetch_related keep query counts under control

API design: RESTful

The two halves talk over a RESTful API and authenticate with JWT: 
Client request                          Django backend
    │                                   │
    │  POST /api/auth/login/            │
    │  {"email":"...","password":"..."}  │
    │ ─────────────────────────────────▶│
    │                                   │ verify password
    │  {"access":"...","refresh":"..."}  │ return tokens
    │ ◀─────────────────────────────────│
    │                                   │
    │  GET /api/testcases/?product_line=camera&page=1
    │  Authorization: Bearer <token>    │
    │ ─────────────────────────────────▶│
    │                                   │ permission check
    │  {"count":326,"results":[...]}    │ query data
    │ ◀─────────────────────────────────│
A consistent response envelope:

{
  "count": 326,
  "next": "http://...api/testcases/?page=2",
  "previous": null,
  "results": [
    {
      "id": 1,

      "priority": "P1",
      "status": "enabled",
      "steps": [...]
    }
  ]
}

7. Getting started

Requirements

  • Python 3.13+
  • Node.js 18+
  • PostgreSQL (production) / SQLite (development)

Three steps to boot

Step 1: start the back end 
git clone https://github.com/zhoujungis/test_manage_system.git
cd test_manage_system/backend

# configure environment variables
cp .env.example .env
# edit .env: database connection, SECRET_KEY, email settings

pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser   # create an admin user
python manage.py runserver 0.0.0.0:8000
Step 2: start the front end 
cd test_manage_system/frontend
npm install
npm run dev
# open http://localhost:5173 in your browser
Step 3: start using it
  1. Log in with the admin account
  2. Create a project → add members → build the module tree
  3. Write test cases, or import them from Excel
  4. Create a test plan → run the tests → file defects

9. Wrap-up

This test management system is a textbook example of how a full-stack web application should be put together:
  1. Front end — Vue 3 + Element Plus for the interface, Pinia for state, Vue Router for navigation
  2. Back end — Django + DRF for the RESTful API and JWTs for stateless authentication
  3. Data layer — PostgreSQL for production reliability, with the Django ORM keeping database work simple
  4. Permission system — designed at fine granularity, from role all the way down to individual feature switches, balancing safety against flexibility
The code is clearly organized and thoroughly commented, which makes it a great reference project for learning full-stack Vue 3 + Django development. Whether you are a front-end developer curious about the back end or a back-end developer who wants to learn the front end, there is something practical in here for you.
