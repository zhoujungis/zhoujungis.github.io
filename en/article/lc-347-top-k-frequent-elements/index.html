LC 347, top k frequent elements: frequency is a bucket index

2026-09-28 · 13 min · Stack Frame

The problem

Return the k most frequent values, in better than linearithmic time.

[1,1,1,2,2,3], k = 2  ->  [1,2]

The previous article handled top-k on the value axis with quickselect. This one changes the axis: the key becomes the frequency, and that change brings a structural gift quickselect never had.

Counting first is linear and needs no cleverness. The remaining question is selecting the top k by frequency, which is again a top-k problem. Sorting the pairs would be linearithmic, which the problem forbids, leaving two candidates: a size-k min-heap at k log n, or bucket sort, which is linear and is the intended answer.

Note the semantics, because it mirrors the kth-largest problem exactly: here the result is k distinct values, each appearing once, not k positions.

Frequency as an index

After counting, a frequency is at least one and at most n, the case where every element is the same. So the key being sorted always lies in a small known integer range, which is precisely the precondition for counting sort.

Build n plus one buckets, drop each value into the bucket indexed by its frequency, and collect by scanning from the highest index down until k values are gathered. No comparisons at all.

FramePhaseAction
0initCount, bucket, collect
1-3countOne appears three times, two twice, three once
4bucketOne into bucket three
5bucketTwo into bucket two
6bucketThree into bucket one
7-9collectBuckets six, five and four are empty, skipped
10collectBucket three yields one
11collectBucket two yields two, reaching k
12doneThe answer

The empty buckets are not waste; they are the scan made literal. Frequencies six, five and four have no values, which shows the index and the frequency correspond exactly.

from collections import Counter

def topKFrequent(nums, k):
    freq = Counter(nums)
    buckets = [[] for _ in range(len(nums) + 1)]
    for v, f in freq.items():
        buckets[f].append(v)
    ans = []
    for f in range(len(nums), 0, -1):
        for v in buckets[f]:
            ans.append(v)
            if len(ans) == k:
                return ans
    return ans

All three steps are linear, so the total is linear, one notch below the required bound. The costs are linear bucket space and the precondition that the key is an integer with a known range.

The heap version

import heapq

def topKFrequent(nums, k):
    freq = {}
    for x in nums:
        freq[x] = freq.get(x, 0) + 1
    heap = []
    for v, f in freq.items():
        heapq.heappush(heap, (f, v))
        if len(heap) > k:
            heapq.heappop(heap)
    return [v for f, v in heap]

Maintain a size-k min-heap of pairs, so the root is the weakest of the current candidates and a newcomer must beat it to enter. Same idea as the kth-largest problem, with the comparator moved from values to counts.

SpaceLinear in n, the bucketsLinear in k

Large kUnaffectedDegrades toward a full sort

Buckets win on asymptotics and constants; the heap wins on generality and memory, and it is the only choice when the key has no range guarantee.

The linear total has three linear parts: counting, bucketing each distinct value, and scanning at most n plus one buckets. What is saved relative to the heap is exactly the logarithm that having a bounded key range buys.

The large-scale variant

Asked to find the most frequent items in a huge dataset, the extra difficulty is that even the deduplicated table may not fit in memory. A billion log lines may contain hundreds of millions of distinct URLs, which at fifty bytes each is several gigabytes, so the counting map itself cannot be built.

The standard answer is hash partitioning into shards, local counting, then a merge. Partition by a hash of each element so that identical elements always land in the same shard, which is what makes the approach correct. Count each shard independently and keep its local top k, then merge those candidates globally.

This is the divide-and-conquer frame of external sorting with the sort replaced by a selection. Compare it with the billion-number problem, which needs no partitioning because numbers are comparable and only k candidates must fit in memory. The dividing line in large-scale questions is always what must fit in memory: k candidates means a heap works, an entire distinct set means partitioning is unavoidable.

Java

class Solution {
    public int[] topKFrequent(int[] nums, int k) {
        Map<Integer, Integer> freq = new HashMap<>();
        for (int x : nums) freq.merge(x, 1, Integer::sum);

        List<List<Integer>> buckets = new ArrayList<>();
        for (int i = 0; i <= nums.length; i++) buckets.add(new ArrayList<>());
        for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
            buckets.get(e.getValue()).add(e.getKey());
        }

        int[] ans = new int[k];
        int idx = 0;
        for (int f = nums.length; f >= 1 && idx < k; f--) {
            for (int v : buckets.get(f)) {
                ans[idx++] = v;
                if (idx == k) break;
            }
        }
        return ans;
    }
}

The heap version uses a priority queue ordered by frequency ascending, offering each pair and evicting when the size exceeds k.

Edges and traps

  1. Forgetting ties. Values with equal frequency share a bucket and are collected in insertion order; the problem guarantees a unique answer so it does not bite here, but a variant that breaks ties lexicographically needs a sort inside the bucket.
  2. Reversing the comparator in the heap version, which turns it into a max-heap that evicts the most frequent element.
  3. Allocating buckets by the maximum observed frequency rather than by n. The bound is n, so there are n plus one buckets, and index zero is always empty.
  4. Sorting the distinct list after counting, which is still linearithmic in the worst case and misses the bound, which is exactly why buckets or a heap are expected.

Variants

One decision rule: a small integer key range means bucket sort; an arbitrary key with only the top k wanted means a heap; a static full ordering means quickselect.

How to answer it

Give the frame first: count in linear time, then select the top k by frequency, which is a top-k problem. Then the intended answer with the structural precondition stated explicitly, that a frequency is always between one and n. Then the heap as the general fallback, which needs no range and works on streams. Then the large-scale variant with partitioning, and the dividing line about what must fit in memory. Close with the one-liner: when the key being sorted is a small integer range, the sort is free.
