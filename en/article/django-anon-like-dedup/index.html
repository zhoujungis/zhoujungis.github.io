Why I let anonymous visitors like: five layers of anti-abuse

2026-09-09 · 13 min · Stack Frame

The setup

The like endpoint on this blog is anonymous: a POST to the article like route, no login. The previous article argued that rendering untrusted input is safe here; this one argues that accepting writes from the internet is equally deliberate.

If a like is just a counter increment, four questions arise immediately. Can someone spam it without logging in, can two simultaneous clicks lose one, does clearing the browser reset the limit, and can a forged header bypass it?

The point is that this is not solved by adding a check. It is a system problem of identity, concurrency correctness and layered throttling, and each layer solves exactly one failure.

Layer one: why not cookies

The intuitive answer is a cookie: mark the browser after a like and refuse a second one. But the frontend and backend here are deployed separately on different origins, so any cookie needs a same-site and secure configuration, credentials on the client, and a CORS allowlist to all agree at once. Any browser quirk, whether tracking prevention, an in-app webview or private mode, drops the cookie, and the dedup silently stops working.

Worse, a cookie is stored by the user. Clearing browser state resets the identity. Using a credential the user controls as the basis for preventing that same user from cheating is a trust inversion.

So the decision recorded in the code is that dedup state lives on the server.

Layer two: a server-side dedup table

class ArticleLike(models.Model):
    article = models.ForeignKey(
        Article, on_delete=models.CASCADE, related_name="like_records",
        verbose_name="article",
    )
    ip = models.CharField(max_length=64, verbose_name="client ip")
    ua = models.CharField(max_length=255, verbose_name="user agent")
    created_at = models.DateTimeField(auto_now_add=True, verbose_name="liked at")

since = timezone.now() - timezone.timedelta(hours=24)
already = ArticleLike.objects.filter(
    article=article, ip=ip, ua=ua, created_at__gte=since
).exists()
if already:
    article.refresh_from_db(fields=["likes_count"])
    return Response({"likes_count": article.likes_count, "liked": True},
                    status=status.HTTP_200_OK)

Three design points. The window slides rather than being permanent, so a client may like again after a day; a permanent uniqueness constraint would grow the table without bound and would punish users on dynamic addresses. The repeated like returns success with the current count, because a duplicate request is a known state rather than an error, which keeps the client simple. And the fingerprint combines address and user agent, since an address alone merges an entire office behind one NAT and a user agent alone merges the whole internet behind one browser.

This does not stop a determined operation with a proxy pool and randomised agents, but the threat model for a personal blog is a bored person rather than a commercial farm, and the investment should match the threat.

The real bug: reading the forwarded header wrongly

The backend sits behind a proxy, so the client address arrives in the forwarded header as a comma-separated list: the claimed client first, then each proxy in order. The leftmost entry is whatever the client chose to write, and only the rightmost was appended by the trusted proxy.

The old code read the leftmost, which meant an attacker could supply a random address per request and never match the dedup table. The door was locked and the key was hanging on it.

xff = request.META.get("HTTP_X_FORWARDED_FOR", "")
if xff:
    ip = xff.split(",")[-1].strip()
else:
    ip = request.META.get("REMOTE_ADDR", "")

The lesson generalises: anything a client can control, whether a header, a cookie or a body field, cannot be a trust anchor. Trust comes only from infrastructure you operate.

Layer three: atomic counting

article.likes_count += 1
article.save()

That is read, modify, write. Two simultaneous clicks read the same old value, each add one, and each write back, so two likes produce one increment. Low frequency makes it unlikely but not impossible, and a popular post is exactly where the collision happens.

with transaction.atomic():
    ArticleLike.objects.create(article=article, ip=ip, ua=ua)
    Article.objects.filter(pk=article.pk).update(likes_count=F("likes_count") + 1)

The expression pushes the increment into the database, where writes are serialised, so no increment can be lost. The transaction makes recording the dedup row and bumping the counter succeed or fail together.

View counts have the same problem and the same fix.

Layer four: throttling

'DEFAULT_THROTTLE_RATES': {
    'anon': '30/minute',
    'user': '100/minute',
    'comment': '3/minute',
    'subscribe': '5/hour',
    'upload': '100/hour',
},

The dedup table stops the same fingerprint repeating, but the attacker can rotate addresses and agents, so a rate layer caps total requests regardless of identity.

Note that the rates are graded by risk. Liking allows thirty a minute, comment creation three, subscriptions five an hour. The closer an action is to amplified writes or external cost, the tighter the quota, because each kind of abuse has a real price: polluted data, polluted content, burnt SMTP quota, blacklisting.

Dedup and throttling are complementary: dedup governs accuracy and throttling governs speed. Fingerprints can be forged, but forging costs money and time, and capping the rate per minute makes the economics fail.

Layer five: bounded storage

Every like adds a row. Left alone for years, the table grows to hundreds of thousands of rows and each check scans more.

Since the window is a day, anything older than forty-eight hours is useless. A scheduled command prunes in batches: select a batch of primary keys older than the cutoff, then delete by key. Deleting hundreds of thousands of rows at once locks the table for a long time, especially on SQLite, and batching spreads the cost. Selecting keys first also avoids relying on a delete-with-limit feature that not every database supports.

indexes = [
    models.Index(
        fields=["article", "ip", "ua", "created_at"],
        name="articlelike_dedup_idx",
    ),
],

The index columns follow the query's order, so the lookup is a range scan on the index rather than a full table scan. Schema, index and cleanup policy are three faces of one decision: do not create a table you are unwilling to prune.

The whole chain

LayerMechanismAttack it stops
1Anonymous throttle, thirty per minuteRotating fingerprints, script floods
2Address plus agent, twenty-four hour windowBrowser resets, ordinary repeats
3Rightmost forwarded entryHeader forgery bypassing dedup
4Atomic increment in a transactionLost updates, half-written state
5Cleanup plus composite indexTable growth slowing queries

The method matches the previous article's defence: trust nothing from the client, give each layer one job, and assume the layer above has already fallen.

When to reach for Redis

ApproachHowSuitable for
Current: database dedupExistence check plus composite indexThousands of daily users, single SQLite box, no operations burden
Redis dedupConditional set with expiry, nil returned on a repeatHigh-frequency likes, atomic test and expiry in one call
Redis countersAtomic increment, periodic flushTraffic the database cannot absorb
HyperLogLogApproximate distinct countOnly the rough number of likers is needed

But do not optimise ahead of need. Redis means another component, another failure mode and a consistency problem between cache and database. At this scale, a small indexed table with scheduled cleanup is accurate, stable and sufficient. Architecture follows the threat model and the load, not the fashion.

Closing

Opening a write to anonymous users is not courage; it is each layer knowing what it defends. Dedup state on the server, because the trust boundary matters. The rightmost forwarded entry, because trust comes only from your own infrastructure. Atomic increments, because concurrency cannot rely on luck. Graded throttling, because every abuse must have a cost. Cleanup and aligned indexes, because schema design is feature design.

Three questions for any endpoint that accepts anonymous writes: whose hands does the identity rest in, is the data still correct under concurrency and replay, and will tables and quotas blow up in the worst case.
