Memory is an index, not a warehouse

People remember something not because it was stored, but because the right situation brought it back. Agents work the same way. Writing every sentence the user ever said into a database does not make an agent understand them better. What matters is whether, at the start of the next task, it can pull three genuinely relevant items out of a few hundred and put them into this request.

That sounds like a job for semantic search. Last time the user said "the release script should dry-run first", this time they ask "how do I publish a post". The two sentences share no words, so vector similarity connects them and BM25 does not. Plenty of projects therefore reach for a vector store on reflex. But a vector store solves only half of recall, and none of the other half: what to write, how long, when to drop, how much to inject. It also turns a single binary that works offline and is easy to test into a system that needs a model service, an index file and a rebuild pipeline.

NanoHermes takes the other road: no vector store, local BM25, and bigram splitting for Chinese and Japanese as an approximation of semantic matching. The whole memory module, agent/src/memory.rs, is under 500 lines, and with three call sites in agent.rs it covers "remember preferences and lessons across sessions". This post follows the data flow: how a memory is written, deduplicated, evicted, retrieved and injected, and where the approach breaks.

Four numbers to remember

ConstantValueGovernsSymptom when missing
MAX_ENTRIES500Total entriesThe file grows without bound, retrieval slows, old noise buries new conclusions
MAX_TEXT400Characters per entryOne memory eats half the injection budget and the summary turns into a diary
INJECT_TOP_K4Entries injected per turnToo much injected, old memories crowd the system prompt
INJECT_CHAR_BUDGET2,400Characters injected per turnMemory itself blows up the context window

Three more sit behind those: the distillation excerpt is capped at 6,000 characters, a single message is clipped to 1,200 characters, and the containment threshold for dedupe is 12 bytes. They govern how much is read, how long a write may be, and when two memories count as the same one.

These limits interlock rather than being four independent round numbers. Four entries at 400 characters is 1,600, and with a prefix like - [lesson] plus the header line it lands inside 2,400. So under normal conditions INJECT_TOP_K binds first and the character budget is a backstop. The budget only fires when log lines get long or labels multiply.

Total size is computable too: 500 times 400 is 200,000 characters worst case, roughly 600 KB of UTF-8 Chinese, usually 300 to 400 KB for mixed text. For a local agent that whole file can be read into memory and scanned linearly, which is why no index is needed.

Context, session and memory are three different things

ContextSessionMemory
Lives inThe messages array of this requestThe JSON file named by --session~/.nanohermes/memory.json
LifetimeOne request, one turnResumable across processesAcross sessions and projects
Managed bycompact_withpersist, load_session_filememory.rs
Clearing it costsContinuity in this conversationHistory, though memory survivesEvery session loses its long-term preferences

The three evolve independently. Compaction touches only messages and never memory.json. reset rebuilds the message array and leaves the memory store untouched. Turning memory off has no effect on session resume.

That boundary matters because a lot of people conflate memory with history and build the thing that stuffs all history into context and summarizes when it overflows. That is not long-term memory, that is a longer context. The test for memory is simple: open a new session, start a new task, and it is still there and retrievable.

One more layer: by default the memory directory is global, under ~/.nanohermes, not per project. So "run the tests before deploying", learned in project A, shows up in project B's system prompt. For general preferences that is a feature. For project-specific path conventions it is noise. Isolation requires pointing memory_dir somewhere else; the code does not partition by workspace on its own.

Four practical reasons not to use a vector store

Vector retrieval is not bad. The part of the problem it solves simply does not rank in the top three here.

Vector storeLocal BM25
DependenciesAn embedding model, hundreds of MB locally or an API callThe Rust standard library and one JSON file
OperationsIndex files, rebuilds, version migrationsRead the file, scan it
PrivacyMemory text goes to an embedding serviceEverything stays on the machine
ExplainabilityA similarity scoreWhich terms matched and what each contributed
Update costRecompute vectors on writeA write takes effect immediately
Synonym recallStrong: "release" reaches "deploy"Weak: no shared term, zero score
Cold startModel loadMilliseconds
TestabilityDepends on model output, unstablePure functions, stable assertions

The four practical constraints:

  1. The project targets a small binary, low memory and no async runtime. An embedding model pushes binary size and memory up by an order of magnitude, which is a direct conflict with the design goal.
  2. Memory is on by default and the user may be entirely offline. A network embedding step makes "works offline" a slogan.
  3. Memories contain file paths, internal interface names and fragments of code. Sending those to a third-party embedding API is an extra privacy surface.
  4. There are only a few hundred entries. Linear BM25 over a few hundred texts costs nothing per turn, and a vector index at this scale is textbook over-engineering.

The cost deserves stating. BM25 is a bag of words and does not understand paraphrase. If the user said "ship it" last week and asks about "deploy" today, and the memory only says "ship it", retrieval misses. The fix is not a vector store, it is writing the memory with both phrasings, or writing it more concretely, such as "ship it, meaning deploy to GitHub Pages", so future queries are more likely to land. That is a writing problem, not a retriever problem.

The four actions in one conversation

write (end of turn)
  user_text --> worth_distilling? --> excerpt_from(6000)
            --> llm::distill --> parse_distill
            --> normalize --> dedupe --> trim(500) --> memory.json

write (during a turn, model-initiated)
  memory_save(kind, text) --> remember --> same chain

read (start of the next turn)
  user_text --> tokenize --> BM25(search) --> top 4
            --> render_block(2400 max) --> set_block(system)

Four actions, four entry points: distill_memories for automatic writes, save_tool for model-initiated ones, retrieve_block to read, set_block to inject. They share one memory.json, with no cache and no daemon.

The ordering is worth noticing. Reads happen before the user message is queued, at the top of Agent::run. Writes happen after the turn completes. A memory distilled at the end of this turn therefore does not affect this turn, only the next one or the next session. The delay is deliberate: distillation costs an extra model call, and putting it mid-turn would add that latency to the user's wait.

Storage: one JSON file, four fields

The default location is ~/.nanohermes/memory.json, derived by default_dir() from HOME or USERPROFILE, and overridable through memory_dir. Loading is deliberately forgiving:

pub fn load(dir: &Path) -> Vec<Entry> {
    let Ok(data) = std::fs::read_to_string(store_path(dir)) else {
        return Vec::new();
    };
    let Ok(v) = serde_json::from_str::<Value>(&data) else {
        return Vec::new();
    };
    // ...
}

A missing file, a permission error, corrupted JSON: all return an empty list. The upside is that memory never blocks a conversation. The downside is that "empty list" and "genuinely no memories" are indistinguishable, which the failure semantics section comes back to.

One more detail: save uses std::fs::write, creating the directory and overwriting the whole file, with no temp file and no atomic rename. Kill the process mid-write and half a JSON file remains. The next load returns empty, and the next save overwrites the fragment with fresh content. So the consequence of corruption is not "cannot read", it is "silently resets to zero".

Four kinds, so eviction has something to sort on

Kind has four values. Each has a meaning and takes part in two things: the label shown on injection, and the rank used when something has to be dropped.

KindMeaningExampleLabelEviction rank
PreferenceA stable user preferenceAnswer in Chinese, no emoji, keep the UI plainpreference0, dropped last
CorrectionA rejected approach plus the right oneDon't open a dialog, dock it on the right sidecorrection1
LessonA pitfall hit, or an approach that proved outgit push inside WSL loses the credential managerlesson2
FactA durable project or environment factVite and React on the front end, Django on the backfact3, dropped first

A higher rank means dropped sooner. The reasoning is direct: preferences and corrections represent stable user intent and are the most expensive to get wrong twice, while facts and specific lessons expire and can usually be rediscovered from the code.

Kind::parse accepts aliases so the model and external scripts can write loosely.

InputParsed as
lesson, lesson-learned, experience, lesson_learnedLesson
preference, prefPreference
correction, feedbackCorrection
fact, projectFact
Anything elseNone: the tool errors, distillation falls back to Fact

That last row is a deliberate asymmetry. A model-initiated write with a bad kind fails; a distillation with a bad kind degrades to a fact. Distillation output is not under your control, and losing an entire memory because the model misspelled an enum value would be a bad trade.

Write path one: the model calls memory_save

The tool declaration is plain: let the model record what is worth carrying across tasks, with a kind and one self-contained sentence.

pub fn save_tool(args: &Value, dir: &Path) -> Result<String, String> {
    let kind = args
        .get("kind")
        .and_then(|k| k.as_str())
        .and_then(Kind::parse)
        .ok_or("kind must be one of lesson / preference / correction / fact")?;
    let text = args
        .get("text")
        .and_then(|t| t.as_str())
        .ok_or("missing text")?;
    let added = remember(dir, kind, text, "tool")?;
    let n = load(dir).len();
    Ok(if added {
        format!("Saved ({kind:?}). {n} memories stored.")
    } else {
        format!("Duplicate of an existing memory, nothing added. {n} memories stored.")
    })
}

The reply carries the total so the model knows how large the store is. A duplicate explicitly says nothing was added, which stops the model from assuming success and retrying. source is fixed to tool, so afterwards you can tell a model-initiated memory from a distilled one.

When should the model write? The prompt lists four cases: user preferences, corrections to its own behavior, lessons that cost something to learn, and durable project facts. What not to write matters as much: one-off file states, temporary decisions in the current task, and anything readable straight from the code. Those only dilute retrieval.

The tool layer has a switch. memory_dir in Ctx is an Option<PathBuf>.

"memory_save" => match &ctx.memory_dir {
    Some(dir) => crate::memory::save_tool(args, dir),
    None => Err("long-term memory is disabled (settings)".to_string()),
},

When memory is off the tool still appears in the list and the call returns an error. That asymmetry gets its own section later.

Write path two: distillation at the end of a turn

Model-initiated writes depend on the model remembering to write, and coverage is uneven. So there is a fallback: at the end of every completed turn, ask the model to distill the conversation.

if completed && self.cfg.memory {
    self.distill_memories(&user_text, had_tools);
}

completed is the important part. A turn interrupted by Ctrl-C, or one that hit the iteration cap, is not distilled. Interrupted turns usually stop mid-tool with no conclusion yet, and what comes out is mostly process noise.

fn distill_memories(&mut self, user_text: &str, had_tools: bool) {
    let dir = match self.ctx.memory_dir.clone() {
        Some(d) => d,
        None => return,
    };
    if !memory::worth_distilling(user_text, had_tools) {
        return;
    }
    let excerpt = memory::excerpt_from(&self.messages, 6000);
    let items = match memory::distill(&self.cfg, &excerpt) {
        Ok(items) => items,
        Err(_) => return,
    };
    let mut saved = 0usize;
    for (kind, text) in items {
        if memory::remember(&dir, kind, &text, "auto").unwrap_or(false) {
            saved += 1;
        }
    }
    if saved > 0 {
        self.style
            .note(&format!("distilled {saved} long-term memories from this conversation"));
    }
}

All three failure points are silent: no directory, failed gate, failed model call. Memory is a bonus, and it must not turn a successful conversation into an error. On success a single line tells the user something was remembered, rather than leaving it entirely invisible.

The distillation gate

Distillation costs one extra model request per turn. If the user said "continue" or "ok", that request is pure waste, so there is a cheap pre-check.

pub fn worth_distilling(user_text: &str, had_tools: bool) -> bool {
    if had_tools {
        return true;
    }
    const MARKERS: [&str; 8] = ["no", "wrong", "don't", "should", "instead", "again", "next time", "not quite"];
    let text = user_text.trim().to_lowercase();
    if MARKERS.iter().any(|m| text.contains(m)) {
        return true;
    }
    text.chars().count() >= 24
}
ConditionResultWhy
Tools ran this turnAlways distillA tool round trip usually means reusable operational knowledge
Contains a correction markerAlways distillCorrections and preferences are exactly what should persist, even in four words
User message is 24 characters or moreDistillLonger messages usually carry a goal, a constraint or context
Everything else, such as short pleasantriesSkip"continue" and "ok" carry nothing that survives a session

The gate is crude in one way: markers use contains with no word boundaries, so "no" fires inside "notion" and "should" fires inside "shoulder". The cost of getting this exactly right is a tokenizer, which is more than the benefit, so false positives are accepted. An extra distillation is one extra model call; a missed correction is real loss.

Letting every tool turn through has the same shape. A turn that only read a file may produce nothing worth keeping, and it still gets distilled. That is why the distillation prompt includes a rule saying return an empty array when nothing is durable. The judgment goes back to the model.

The distillation prompt: four hard rules

Distillation uses its own prompt, fully isolated from the main conversation.

const DISTILL_SYSTEM: &str = "You extract durable long-term memories for a coding assistant from a finished conversation turn.
Return ONLY a JSON array (no prose, no markdown fences). Each item is
{"kind": "lesson|preference|correction|fact", "text": "..."} where:
- lesson:     an experience or lesson learned (a pitfall to avoid, or an approach that worked);
- preference: a stable user preference (style, workflow, deliverable format);
- correction: something the user rejected and the right way they gave instead;
- fact:       a durable project/environment convention.
Rules: each text is ONE self-contained sentence in the conversation's language, at most 200 characters;
it must hold up in future unrelated sessions (no task-local details like dates or one-off file states);
dedupe near-identical items; if nothing is durable, return [].";
RulePurposeCost of breaking it
One self-contained sentenceReadable outside the original conversationA memory like "change that one" is never retrieved and never useful
At most 200 charactersBounds the injection budgetOne memory fills the entire 2,400 character budget
Must hold in future unrelated sessionsFilters one-off state"The current branch is fix-123" is garbage next week
Merge near-duplicatesBounds the totalThe same preference written ten times squeezes out everything else

There is an inconsistency here. The prompt says 200 characters, and MAX_TEXT in the code is 400. When the model obeys, nothing goes wrong. When it writes long, remember silently truncates at 400 and can cut a sentence in half. The looser cap leaves room for model-initiated memory_save calls, but for distillation the space between 200 and 400 is really a risk zone.

The prompt also allows an empty array, which is the most overlooked sentence in the design. Having nothing to record is more correct than manufacturing an entry. A memory store that only ever says "the user asked me to change code" has zero retrieval value.

How the excerpt is assembled

Distillation does not send the whole conversation. It builds an excerpt first.

pub fn excerpt_from(messages: &[Value], max_chars: usize) -> String {
    let mut out = String::new();
    for m in messages {
        let role = m.get("role").and_then(|r| r.as_str()).unwrap_or("");
        let body = match role {
            "system" => continue,
            "tool" => format!("[tool result] {}", content_text(m.get("content").unwrap_or(&Value::Null))),
            "assistant" => {
                if m.get("tool_calls").is_some() && m.get("content").and_then(|c| c.as_str()).unwrap_or("").trim().is_empty() {
                    continue;
                }
                content_text(m.get("content").unwrap_or(&Value::Null))
            }
            _ => content_text(m.get("content").unwrap_or(&Value::Null)),
        };
        let body = body.trim();
        if body.is_empty() {
            continue;
        }
        let body: String = body.chars().take(1200).collect();
        out.push_str(&format!("[{role}] {body}
"));
        if out.chars().count() >= max_chars {
            break;
        }
    }
    out
}
Message typeHandlingWhy
systemSkipped entirelyThe system prompt is configuration, not conversation
toolPrefixed with [tool result], body clipped to 1,200 charactersTool output is often tens of kilobytes and would crowd out the actual conclusion
assistant with only tool callsSkipped entirelyFunction names and arguments help distillation very little
assistant with textKept, clipped to 1,200Conclusions, plans and explanations live here
userKept, clipped to 1,200Goals, constraints and corrections live here
Multimodal arraysOnly the text partsImages do not help text distillation and base64 would blow the length

Note that clipping happens per message, not on the total: each message contributes at most 1,200 characters and the loop stops appending once it reaches 6,000. One distillation therefore sees at most five full-length messages, or more short ones.

Tool results are kept rather than dropped, which is the opposite of what compaction does. Compaction drops tool results first because they are long. Distillation keeps them because they are the evidence for which command worked and what error came back. Same history, two consumers, two different trades.

The blind spot: only the first 6,000 characters

excerpt_from walks messages from index 0 forward, so the excerpt is the beginning of the conversation, not the end.

For a short turn that is fine. For a long one, where the user asked it to read ten files, run five commands and finish with a conclusion, the budget is spent on the first five or six messages. The conclusion, the final correction and the agreed approach all sit past 6,000 characters. The distilled memories then skew toward "what was said when the task began" rather than "what was established when it ended".

Worse, the blind spot is invisible. The model has no idea it saw only the first half, and it distills confidently from it. The store gains one memory about an early idea and loses one about the final decision.

FixApproachCost
Take the tailIterate backwards, or compute the total and collect from the endLoses the task goal, may distill conclusions without context
Half head, half tailFirst 3,000 characters plus last 3,000, with a gap markerA dozen extra lines, keeps both goal and conclusion

If history has already been compacted things get a little better: messages[1] is a summary covering the dropped middle, and an excerpt starting at index 1 will include it early. That is luck, not a fix.

Parsing: four fallbacks for a disobedient model

Distillation asks for a bare JSON array. Models add fences, add a preamble, or wrap the array in an object. The parser has four layers of tolerance.

Dedupe: normalize, then compare, but 12 means bytes

Models repeat themselves. The same "answer in Chinese" can be distilled ten times across ten turns, and without dedupe the 500 entry ceiling fills with one sentence. remember normalizes first, then compares for equality or containment.

fn normalize(text: &str) -> String {
    text.to_lowercase()
        .chars()
        .filter(|c| !c.is_whitespace() && !"，。！？；：、,.!?;:()（）""'‘’【】…-·*#>~".contains(*c))
        .collect()
}

let key = normalize(&text);
for e in entries.iter_mut() {
    let old = normalize(&e.text);
    if old == key || (key.len() >= 12 && old.contains(&key)) || (old.len() >= 12 && key.contains(&old)) {
        e.ts = now();
        e.source = source.to_string();
        save(dir, &entries)?;
        return Ok(false);
    }
}
NewExistingResult
Identical textIdentical textNothing added, timestamp refreshed
Same text plus punctuationSame textNothing added
"run cargo test first""run cargo test first to avoid regressions"The short one is contained and at least 12 bytes, nothing added
"use Chinese""always answer in Chinese"The new text is under the threshold, so it is added and may duplicate
Same text, different kindSame textNothing added, kind unchanged

The number people misread is 12. String::len() returns UTF-8 bytes, not characters. For Chinese, 12 bytes is four characters. For English it is twelve characters. So "use Chinese", three characters and nine bytes, never triggers containment, while a four-character Chinese phrase does. The threshold effectively favors English and long sentences, and short Chinese preferences pile up.

When dedupe hits, only ts and source change. kind and text stay. That has a side effect: write a fact, later write the same sentence as a preference, and it remains a fact with the same eviction rank. Changing the kind requires deleting the old entry, and there is no tool for deleting a single memory.

Limits and eviction

Before writing, text is clipped to 400 characters, appended, then trimmed.

let text: String = text.chars().take(MAX_TEXT).collect();
// ...
entries.push(Entry { kind, text, source: source.to_string(), ts: now() });
trim(&mut entries);
save(dir, &entries)?;

fn trim(entries: &mut Vec<Entry>) {
    while entries.len() > MAX_ENTRIES {
        let victim = entries
            .iter()
            .enumerate()
            .max_by_key(|(_, e)| (e.kind.eviction_rank(), e.ts))
            .map(|(i, _)| i)
            .unwrap_or(0);
        entries.remove(victim);
    }
}
  1. Sort by eviction rank: Fact 3, Lesson 2, Correction 1, Preference 0.
  2. Break ties by the largest ts.
  3. Remove that entry until the count is back to 500.

The intent is in the comment: drop lessons and facts first, touch preferences and corrections last, because stable user intent is worth more than a one-off fact.

But max_by_key with the largest ts picks the newest entry, which is the opposite of that intent.

A real defect: the comment says oldest, the code drops newest

The comment above trim says eviction drops the oldest lessons and facts. The code, on a tie in rank, picks the entry with the largest ts, which is the most recent one. So when the store is full and the evictable category has several entries, the one deleted is the one just written.

The observable effect is counterintuitive. The user corrects something, and a fresh Lesson is distilled; if the store already holds 500 entries mostly in Fact and Lesson, that new memory can be evicted moments after being written. Preferences and corrections survive only because their rank is lower.

The fix is to reverse the time comparison.

let victim = entries
    .iter()
    .enumerate()
    .max_by_key(|(_, e)| (e.kind.eviction_rank(), std::cmp::Reverse(e.ts)))
    .map(|(i, _)| i)
    .unwrap_or(0);

Reverse turns "largest" into "smallest" on the time axis, so the sort is by rank first and age second. The alternative is two steps: filter to the highest rank, then take min_by_key(|e| e.ts).

Why did nobody notice? Because the test only asserts that preferences survive.

#[test]
fn trims_oldest_lessons_before_touching_preferences() {
    let mut entries = vec![entry(Kind::Preference, "prefers concise replies")];
    for i in 0..MAX_ENTRIES {
        entries.push(entry(Kind::Lesson, &format!("lesson {i}: a detail that only mattered once")));
    }
    trim(&mut entries);
    assert_eq!(entries.len(), MAX_ENTRIES);
    assert!(entries.iter().any(|e| e.kind == Kind::Preference));
}

The test name says oldest; the assertion only checks that the preference is still there. A classic blind spot: the name describes the intent, the assertion verifies half of it. One extra line asserting the last lesson is still present would have caught it immediately.

This is not about point-scoring. It illustrates a real pattern: when comments, test names and implementation disagree, a low-frequency, hard-to-observe module like memory is where the debt accumulates. Nobody gets an error when eviction is wrong. They just think "why did it forget that again".

Retrieval: why BM25 and not cosine similarity

BM25 is the classic scoring function in information retrieval: term frequency times inverse document frequency times length normalization. It produces no vectors and only asks whether terms overlap, how often, and how rare they are.

PropertyWhat it means for memory retrieval
Bag of wordsQuery and memory must share terms, and the result is explainable
IDF weighting"the" and "is" barely count, rare terms weigh more
Length normalizationA long memory does not win just by having more words
No trainingA new memory takes effect immediately, no index rebuild
DeterministicThe same store and query give identical scores, which makes tests easy

The weakness is just as clear: no shared term means zero, so paraphrase, cross-language and pronoun references all fail. search therefore filters zero scores outright, preferring an empty result to a list of irrelevant ones.

Two behaviors are implicit. First, there is no time decay: a preference from three years ago scores the same as one written yesterday given equal term counts. ts is used for dedupe refresh and eviction order, never for ranking. Second, there is no category weight: Preference does not score higher for being more important. The category only enters the index as a label term.

At a few hundred entries both are acceptable. Most of the store is recent, so decay buys little, and category weights would add a tuning burden.

Tokenization: words in English, bigrams in Chinese

BM25 assumes terms. English has spaces and Chinese does not, so tokenize uses two rules.

let flush_word = |buf: &mut String, out: &mut Vec<String>| {
    if buf.chars().count() >= 2 {
        out.push(buf.to_lowercase());
    }
    buf.clear();
};
let flush_cjk = |cjk: &mut String, out: &mut Vec<String>| {
    let chars: Vec<char> = cjk.chars().collect();
    if chars.len() == 1 {
        out.push(chars[0].to_string());
    } else {
        for w in chars.windows(2) {
            out.push(w.iter().collect());
        }
    }
    cjk.clear();
};

  1. Runs of ASCII alphanumerics become lowercase words; anything under two characters is dropped.
  2. Runs of CJK characters become overlapping bigrams: n characters produce n-1 tokens, and a single character stays as itself.
  3. Spaces, punctuation, underscores and symbols are separators that flush both buffers.

The benefit of bigram splitting is that it needs no dictionary. Any Chinese string can be split, including rare words, proper nouns and Chinese comments inside code. The cost is cross-word pseudo-tokens and very weak single-character queries.

Bigram false positives

Take the phrase "front end uses Vite". The CJK run splits into two overlapping pairs, and the second pair is not a word at all, yet it enters both the index and any query. The consequences fall into four kinds.

PhenomenonExampleImpact
Cross-word pseudo-tokenA meaningless pair spanning two wordsA query for that pair would falsely match, but nobody searches for it
Single-character noiseA lone character kept as a unigramAny memory containing it scores
Synonym mismatchMemory says "ship", query says "deploy"Zero score, no retrieval
Word order ignored"A calls B" and "B calls A" tokenize identicallyDirection is lost, possibly the wrong lesson is recalled

The last two actually hurt. Pseudo-tokens are mostly harmless because no one searches for them.

The mitigation lives on the writing side, not in the retriever.

  1. Write key synonyms into the memory: "before shipping (deploying), run a dry-run".
  2. Prefer concrete nouns and paths over pronouns: "the deploy script", not "that script".
  3. One memory, one statement, so a long sentence with several subjects does not create order ambiguity.

Which explains a design choice that looks odd at first: MAX_TEXT is 400 characters but the prompt asks for 200. Short sentences are easier to retrieve and less likely to crowd the budget.

Category labels go into the index too

When document frequencies are built, the category label and the English kind name are added to the body tokens.

let docs: Vec<Vec<String>> = entries
    .iter()
    .map(|e| {
        let mut t = tokenize(&e.text);
        // Label terms participate in matching, so a query like "preference"
        // hits the right bucket directly.
        t.extend(tokenize(e.kind.label()));
        t.push(e.kind.as_str().to_string());
        t
    })
    .collect();

Now three kinds of query work.

QueryWhat matches
A term from the bodyMemories containing that term
The label wordEvery entry of that kind, via the label term
preferenceEvery Preference entry, via the English kind name

That is a free type filter. Neither the user nor the model has to remember a slug; the category word itself pulls up a bucket.

The side effect is that label terms inflate the length and term counts of their category. Since document frequency is computed over documents that include labels, the frequency of the label word equals the number of entries in that category, so its IDF drops. That is reasonable: a category word should be more common and worth less than a specific noun.

The BM25 formula

let idf = (1.0 + (n - n_q + 0.5) / (n_q + 0.5)).ln();

  1. IDF. The rarer a term, the more a hit on it distinguishes. "deploy" is worth more than "the".
  2. Saturation. Going from 1 to 10 occurrences raises the score quickly, from 10 to 100 barely at all, so no memory wins by repeating its own keywords.
  3. Normalization. With b at 0.75, length carries most of the penalty, so a long document needs a higher term frequency to score the same.

The complexity is entries times query terms. Five hundred entries is a few thousand hash lookups once per turn, which needs no inverted index at all. That is the engineering reason "no vector store" holds up: the scale is small enough to brute-force.

Top-K and the character budget

Injection has two limits, count and characters. retrieve_block takes the top four and hands them to render_block.

Four maximum-length memories still come to 1,640 characters, leaving 760 of headroom. The budget rarely fires first; top_k = 4 is the binding constraint. The budget matters when labels get longer, categories are renamed, or extra explanatory lines are added to render_block.

Order matters here too. Hits are sorted by descending score, so if the budget runs out, what gets dropped is the lowest-scoring entry rather than an arbitrary one. The most relevant memories are always injected first.

Injection: a marker pair and wholesale replacement

pub const BLOCK_START: &str = "=== Long-term memory (retrieved from past sessions) ===";
pub const BLOCK_END: &str = "=== End long-term memory ===";

=== Long-term memory (retrieved from past sessions) ===
Relevant memories retrieved from earlier sessions (extracted automatically, for reference only; the user's current instruction takes precedence):

- [preference] Answer in Chinese, code comments too
- [correction] The deploy script dry-runs by default; confirm before it runs
- [lesson] git push inside WSL loses the credential manager; use PowerShell
- [fact] Vite and React on the front end, Django on the back

=== End long-term memory ===

pub fn set_block(system: &str, block: &str) -> String {
    let mut base = system.to_string();
    if let Some(start) = base.find(BLOCK_START) {
        let end = base[start..]
            .find(BLOCK_END)
            .map(|i| start + i + BLOCK_END.len())
            .unwrap_or(base.len());
        base.replace_range(start..end, "");
    }
    let base = base.trim_end().to_string();
    if block.is_empty() {
        base
    } else if base.is_empty() {
        block.to_string()
    } else {
        format!("{base}

{block}")
    }
}

Two things matter.

  1. Replace, never append. The old block is removed first, so the block does not grow linearly with turns.
  2. An empty new block deletes the old one. That part is easy to miss: if this turn's query hits nothing, the previous injection is cleared rather than left in the system prompt.

The second is intentional. Memory should follow the current task, not hold a permanent slot. The side effect is that if the user says only "continue", nothing is retrieved and the block disappears.

The block sits at the end of the system prompt, the tail of the stable prefix. As the context post explains, prefix caching matches from the front, so putting the volatile part last means the change only affects the tail and the long stable prefix still hits. It is an important cooperation between two modules that no comment records.

Re-retrieval on every turn

At the top of Agent::run, the plain text of the current user message becomes the query.

let user_text = memory::content_text(&content);
if let Some(dir) = self.ctx.memory_dir.clone() {
    let block = memory::retrieve_block(&dir, &user_text);
    self.set_memory_block(&block);
}
self.messages
    .push(json!({ "role": "user", "content": content }));

Retrieval happens before the message is queued, so the query contains neither this message nor any earlier dialogue. The query is that one sentence.

The benefit is intent alignment. Ask about the deploy script and you get deployment memories. Ask about front-end styles next and the front-end preferences appear.

The cost is short-command amnesia.

User messageLikely outcome
A sentence about the deploy scriptDeployment memories retrieved
A sentence about front-end stylesFront-end preferences retrieved
"continue"Very likely zero hits, block cleared
"ok, go with that"Very likely zero hits

So there is an experience gap: describe the task carefully and the agent remembers your preferences, say "continue" and it forgets them. That is not a bug, it is a direct consequence of querying with the current message.

FixApproachCost
Concatenate recent user messages into the queryQuery over the last few turnsRelevance gets diluted, old topics contaminate new ones
Keep the previous block on short messagesUnder eight characters, do not replaceExtra state, and stale memories can linger

NanoHermes takes the simplest version: retrieve independently every turn, clear on zero hits. For a habit of stating the requirement once, that trade holds.

How memory coexists with compaction

Compaction keeps the last ten messages and replaces the rest with a summary at messages[1]. The memory block lives inside the system message at messages[0]. The two never touch.

ActionTouchesAffects the memory block
compact_withmessages[1..start]No, index 0 is always kept
set_memory_blockmessages[0].contentReplaces the block itself
refresh_systemRebuilds messages[0]Drops the old block, re-retrieves next turn
resetRebuilds all of messagesDrops the block, memory.json unchanged
persistWrites the session fileWrites whatever block is current

Two details. The compaction summary sits at index 1 while the memory block sits inside index 0's body, so they cannot overwrite each other, because set_block only cares about the text between the two markers. And on session resume, refresh_system rebuilds the system prompt from current configuration, discarding the old block and re-retrieving at the first turn, so a restored session never carries memories from a different environment.

Put differently: memory is external material fetched again every turn, compaction is internal tidying of this turn's history. One lives in the system message, the other in the middle of the array, and their lifetimes have nothing in common.

Failure semantics

FailureHandlingVisible to the user
memory.json missingEmpty listNo, it looks like having no memories
memory.json corruptedEmpty listNo, every old memory disappears silently
Disk write failsThe tool returns an error, distillation ignores itModel-initiated writes yes, distillation no
Distillation call failsReturn without writingNo
Distillation output is not JSONParsed as emptyNo
No hits on injectionDelete the old blockNo

The governing principle, that memory never blocks the main flow, is right. But "corrupted means empty" leaves a hazard.

  1. load sees broken JSON and returns an empty list.
  2. The next distillation succeeds and appends one entry to that empty list.
  3. save overwrites the whole file, replacing the corrupted content.
  4. The user has lost every old memory and was never told.

A safer version renames the file to memory.json.broken before returning empty, or writes through a temp file plus rename so a partial file never exists. Neither changes the normal path; both turn "silent reset" into "keep the evidence".

Model-initiated write failures are visible: save_tool returns the error from remember and the model sees it, so it can retry or tell the user. Distillation swallows errors with unwrap_or(false), because it runs after the turn with no chance to interact.

Concurrent writes without a lock

The storage layer has no file lock. Every write is read everything, modify in memory, write everything.

let mut entries = load(dir);
// ... dedupe or append ...
save(dir, &entries)?;

Single-threaded, that is fine. But Agent::run executes the tool calls of one turn concurrently, each on its own thread.

let this: &Agent = self;
std::thread::scope(|s| {
    let handles: Vec<_> = turn
        .tool_calls
        .iter()
        .map(|call| s.spawn(move || this.execute(call)))
        .collect();
    // ...
});

If the model calls memory_save twice in one turn, both threads load the same old list, each appends one entry, and they save in some order. The later write overwrites the earlier one and only one memory survives.

The same problem appears in daemon mode: several sessions share one memory_dir, each distills at the end of its turn, and overlapping writes lose updates.

ScenarioConcurrent writesResult
One tool call in a turnNoSafe
Several memory_save calls in a turnYesLater write wins, one entry lost
Several sessions finishing at onceYesSame
Model write overlapping distillationYesSame

A complete fix needs a cross-process file lock, which is not cheap. A lighter one is an append-only log: each write appends one JSON line and reads merge and dedupe in order, avoiding whole-file overwrites. NanoHermes keeps the simplest whole-file scheme, which is acceptable under the assumption that models rarely write memories in parallel, an assumption the code does not enforce.

Sub-agents and multiple sessions

A sub-agent runs its own loop with a system prompt taken from def.prompt, bypassing Agent::run.

let mut messages: Vec<Value> = vec![
    json!({ "role": "system", "content": def.prompt }),
    json!({ "role": "user", "content": task }),
];

So a sub-agent never retrieves memories and never distills at the end. Its tool calls still go through the parent's self.execute and share the same Ctx, which means memory_save and memory_search work and write to the same store.

CapabilityMain agentSub-agent
Retrieve and inject every turnYesNo, the system prompt is fixed
Distill at the end of a turnYesNo, it runs its own loop
Call memory_save and memory_searchYesYes, through the shared Ctx
Write the same memory.jsonYesYes

The upside is that a sub-agent can look things up and record them without having the memory block stuffed into its limited context. The downside is that a sub-agent does not know the user's long-term preferences unless the parent puts them in the task description.

Daemon mode isolates differently: each session id gets its own message array, swapped through replace_messages. The memory store is shared across sessions, which matches the intuition that long-term memory belongs to the user rather than the conversation, but it also means a temporary lesson written in one session shows up in another session's retrieval.

The third row is an asymmetry: tool declarations are not filtered by memory_dir, only by permission mode. The model can see an available tool, call it, and get an error. Filtering the two tools out when memory is off would be more consistent and would save the model a wasted call.

That asymmetry also explains why turning memory off deletes nothing. memory.json is untouched and old memories come back the moment it is re-enabled. The switch controls read and write behavior, not the lifetime of the data.

The gaps are just as clear.

  1. No test of eviction order, which is exactly why the defect above went unnoticed.
  2. No test of concurrent writes.
  3. No test of the corrupted-file path.
  4. No test of the excerpt blind spot on long conversations.

None of these is hard to write. Nobody thought they would break. For a low-frequency, silent, cross-session module, those are the four tests most worth having.

One testability benefit is worth stating: because retrieval is a pure function, a test can build three memories, query one term and assert the first hit. A vector store would make the same assertion depend on model version and floating-point error, with far worse stability and readability. That is an invisible dividend of skipping the vector store.

Closing: an index, not a warehouse

  1. Memory earns its keep through retrieval, not storage. Five hundred entries none of which are ever used are worse than twenty that all hit.
  2. Write quality sets the ceiling. Kind, length, self-containment and cross-session validity matter more than any ranking algorithm.
  3. The limits have to exist. Entry count, entry length, injection count and injection characters interlock; drop one and something runs away in some scenario.
  4. The simple version has explicit edges. BM25 misses synonyms, whole-file writes lose concurrent updates, corruption resets to empty. Knowing where the edges are beats pretending there are none.

NanoHermes' memory module is a few hundred lines and it does cover remembering preferences and lessons across sessions. It is not perfect: the excerpt takes the head, eviction order is inverted, concurrency loses updates, corruption resets. But those defects are concrete, locatable and individually fixable. The complexity a vector store brings, by contrast, is diffuse: model version, index rebuilds, privacy boundaries, offline availability, each needing permanent maintenance.

For a personal project or a small team, running the loop with one JSON file and BM25 first, and reaching for vector retrieval only once the store is genuinely thousands of entries and synonyms genuinely bind, is usually the cheaper order.
