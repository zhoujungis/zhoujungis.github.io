The index is there, so why is the sort unindexed? A slow query investigation

2026-09-14 · 30 min · Stack Frame

Follows the earlier post that took a list endpoint from twenty-one queries down to two. The count problem was solved, and the cost problem was still waiting.

Django with SQLite, matching this site's stack. The reasoning holds for MySQL 8 and PostgreSQL, and the differences are called out.

Reading time around 30 minutes. Level: intermediate to advanced.

After the N+1 fix, the bill arrived

SetupPlanFirst page, ten rows, median
No index at allSCAN plus a temp B-tree395.92 ms
The index in productionSEARCH plus a temp B-tree476.50 ms
One more column addedSEARCH plus a temp B-tree for the last term690.80 ms
Directions alignedSEARCH0.18 ms

Three findings, each counterintuitive. The index made it slower than no index at all, 476 against 396, so for this statement the index was effectively absent. Adding the missing column made it worse, because a partial index is more damaging than none: it convinces the optimiser it can help. And writing the direction correctly made it roughly 2,600 times faster.

The gap is not about having an index. It is about whether the physical order of the index matches the order the query asks for. On a blog with nine posts, you would never see any of it, which is what makes slow queries so quiet.

Two separate bills: how many queries, and how expensive each one is

DimensionSymptomUsual culpritFix
Query countThe count grows with the dataN+1Related-object loading, prefetching, annotation
Per-query costThe count is stable but each one slows downFull scans, sorting, temporary tablesIndexes, rewritten SQL, a different paging strategy

Two queries per request, each scanning nine hundred thousand rows, is almost a second. The count optimisation can be perfect and the site still feels slow.

So investigate in this order: the count first, because removing an outrageous N+1 is the biggest single win; then the plan for each statement, which sets the ceiling; then the internals of each statement, whether an index can be used and whether sorting or a temporary table appears.

Reading a plan

KeywordMeaningCostDanger
SCAN tableFull table scanAll rowsHigh
SEARCH table USING INDEX (col=?)Index seek to specific rowsMatching rowsLow
SEARCH using COVERING INDEXEvery needed column is in the index, no row fetchMatching rows, cheaperLower
SCAN using COVERING INDEXWalks the whole index rather than the tableAll rows, but narrowerMedium
USE TEMP B-TREE FOR ORDER BYAn extra sort is requiredn log nHigh
USE TEMP B-TREE FOR LAST TERM OF ORDER BYOnly part of the ordering was satisfiedPart of n log nMedium-high
USE TEMP B-TREE FOR GROUP BYGrouping needs a temporary tablen log nMedium-high

A search seeks, a scan walks, and a temp B-tree means the index did not cover the ordering. A scan is not automatically a disaster on a small table or when few columns are needed, but on a hot path it is a time bomb. The temp B-tree is the engine telling you the index was used for half its job.

Getting the plan out of Django

# tools/explain.py -- print the plan for any queryset
import os
import django

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "blog_api.settings")
django.setup()

from django.db import connection


def explain(qs, verbose=True):
    """Return the plan for a queryset, using EXPLAIN QUERY PLAN on SQLite."""
    sql, params = qs.query.sql_with_params()
    if verbose:
        print(sql)
    with connection.cursor() as cur:
        # MySQL 8: "EXPLAIN", or "EXPLAIN ANALYZE" from 8.0.18
        # PostgreSQL: "EXPLAIN (ANALYZE, BUFFERS)"
        cur.execute("EXPLAIN QUERY PLAN " + sql, params)
        return [row[-1] for row in cur.fetchall()]


if __name__ == "__main__":
    from articles.models import Article

    qs = Article.objects.filter(status=Article.Status.PUBLISHED)
    for line in explain(qs):
        print("   ", line)

Capturing how long each statement took

Count and duration together are the full picture. With only the count, the common incident of two statements each taking half a second is invisible.

The real model, and its real plan

class Article(models.Model):
    class Status(models.TextChoices):
        DRAFT = "draft", "Draft"
        PUBLISHED = "published", "Published"
        ARCHIVED = "archived", "Archived"
        SCHEDULED = "scheduled", "Scheduled"

    title = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    # ... other fields omitted ...
    status = models.CharField(max_length=16, choices=Status.choices, default=Status.DRAFT)
    is_top = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-is_top", "-created_at"]        # order: pinned first, then newest
        indexes = [
            models.Index(                            # index: status and created_at
                fields=["status", "-created_at"],
                name="articles_status_created_idx",
            ),
            models.Index(fields=["scheduled_at"], name="articles_scheduled_idx"),
        ]

Put those two lines side by side. The ordering needs two columns and the index holds one of them; the missing one is the pinned flag.

SEARCH articles_article USING INDEX articles_status_created_idx (status=?)
USE TEMP B-TREE FOR ORDER BY

Remove the pinned column from the ordering and the same query against the same table gives a single line, with no temp B-tree. Same index, same data, one fewer sort term, and the extra sort disappears.

With nine rows both versions take a fraction of a millisecond, so nothing is visible. Whether an index is valid has nothing to do with data volume; the pain of an invalid one is entirely about data volume.

Every measurement takes the median of seven runs, and every index change drops the others so each group stands alone. The statement under test is the list page.

WHERE status = 'published'
ORDER BY is_top DESC, created_at DESC

S3status, is_top desc, created_at descSEARCH0.18 ms2,200x

Without an index, a scan reads a million rows and the sort orders a million rows. The production index is the painful one: it was genuinely used, cutting a million rows to nine hundred thousand, and the sort still ran, and it came out twenty percent slower than the scan. Two reasons. Walking the index means nine hundred thousand index entries plus nine hundred thousand row fetches to get the unindexed columns, while the scan reads the table sequentially, and sequential reads are cheaper than random ones. And the ten percent filter it saved is not worth the detour.

Adding the pinned column in ascending order is the most counterintuitive case. The index holds it ascending while the query asks for descending, so the engine can only walk the index backwards, which flips the timestamp term into ascending as well and breaks the second ordering term. The optimiser settles for sorting the last term again, and since 99.9995 percent of the pinned column is zero, that last group is essentially all nine hundred thousand rows. It paid the index cost and still sorted everything.

A partial index is worse than none, because it convinces the optimiser it can help, so the optimiser takes a longer road and saves nothing.

With the direction aligned, the physical order of the index matches the requested order term by term. The engine seeks to the first published row and reads ten entries down the index, and the limit finally means something: 476.50 to 0.18, about 2,600 times.

Why the wrong direction equals no index

Most people think of an index as faster lookup. That is half of its value; the other half is order.

Picture the aligned composite index as a phone book ordered by status, then pinned descending, then timestamp descending. The query asks for exactly that order, so the engine opens to the first published page and reads ten rows.

Now the production index: ordered by status and then timestamp, with the pinned flag absent altogether. The query asks for pinned first, so the engine has to pull all nine hundred thousand published rows, look up the flag for each, and sort them itself. That is the temp B-tree.

Three rules follow. Equality columns come first and sort columns after, because a condition on the first column is what lets the seek happen at all. The index columns must cover the ordering columns in order, starting from the first term, since a missing or misplaced term forces a sort. And each column's direction must match, which is the rule people forget and the one that produces results slower than no index.

DatabaseDescending index supportSignal that sorting was not indexed
SQLiteSupported since 3.3.0USE TEMP B-TREE FOR ORDER BY
MySQLOnly really from 8.0; 5.7 silently ignored the keyword and built ascending indexesUsing filesort
PostgreSQLSupported, but only whole-index reverse scans, so mixed directions need a matching indexSort, or incremental sort

On MySQL 5.7, a Django index with descending fields generates DDL containing the keyword, and 5.7 builds an ascending index regardless, with nothing to see in the table definition. Upgrading to 8.0 changes the behaviour, which is where a surprising number of "it got slow after the upgrade" incidents begin.

The fix

class Article(models.Model):
    # ... fields unchanged ...

    class Meta:
        ordering = ["-is_top", "-created_at"]
        indexes = [
            # Aligned with the ordering: the equality column first,
            # then pinned descending, then timestamp descending
            models.Index(
                fields=["status", "-is_top", "-created_at"],
                name="articles_status_top_created_idx",
            ),
            models.Index(fields=["scheduled_at"], name="articles_scheduled_idx"),
        ]

CREATE INDEX "articles_status_top_created_idx"
ON "articles_article" ("status", "is_top" DESC, "created_at" DESC);

[before]
    SEARCH articles_article USING INDEX articles_status_created_idx (status=?)
    USE TEMP B-TREE FOR ORDER BY

[after]
    SEARCH articles_article USING INDEX articles_status_top_created_idx (status=?)

The disappearance of the temp B-tree is the only hard evidence that the fix is right. Do not trust a feeling, and do not trust timings, because at nine rows timings never differ.

Three details to watch. The column order cannot be rearranged: the equality column has to be leftmost. The old index may still be useful for orderings that omit the pinned flag, so check whether any query sorts by timestamp alone before dropping it, since otherwise it is pure write amplification. And adding an index to a large table can block writes for tens of seconds, so use an online DDL path: MySQL with a no-lock algorithm, PostgreSQL with a concurrent build, and accept that SQLite locks briefly.

HSelect a narrow set, still fetching rowsSEARCH using index0.23 msFetch is fine under a limit
ISkip the leftmost columnSCAN using covering index216.15 msPrefix violated
JEquality plus range on the second columnSEARCH on both0.28 ms770x better than I

Function wrapping is the most expensive mistake. The index stores the raw column value, so once you wrap it in a function the engine cannot use the ordered values and must compute the function for every row. In Django, three wrappers hide in plain sight: date part lookups, which should be expressed as a range; case folding, which belongs in a collation or a normalised column; and string comparisons against numeric columns. The date one is the sneakiest, since it reads as harmless and generates a cast that kills the index.

A prefix LIKE failing is the surprising one. A prefix pattern can use an index in principle, but SQLite's default LIKE is case-insensitive for ASCII while the index uses a binary collation, so the semantics do not match and the optimiser gives up. Turning on case-sensitive LIKE or adding a no-case collation fixes it, and the better advice is to prefer equality where possible. MySQL differs: a prefix pattern can use an index under its default collation, while patterns with a leading wildcard never can.

A leading wildcard cannot be helped. No starting point means no seek, which means a full scan. Case D is only twenty-five milliseconds rather than nine hundred because the plan used a covering index: it walked a narrow index instead of the table. That is the practical value of coverage, where the same scan class costs ten to forty times less.

OR is not doomed. SQLite has handled OR by running each branch through the index and merging since 3.9, and case F shows the index was used, with only the sort left over. MySQL does the same through index merge, whose cost is routinely underestimated, and a single branch without an index collapses the whole query into a scan. Rewrite to IN or UNION ALL when you can.

The leftmost prefix is worth a factor of 770. Cases I and J differ only in whether the leftmost column appears. Without it there is no starting point in the index. The precise rule: the index can be used continuously from its leftmost column, and once a column is missing, everything to its right is unavailable for positioning. A range condition also cuts off the columns after it, so order index columns as equality, then range, then sort.

The second slow query: an offset of 900,000

SELECT id, title FROM articles_article
WHERE status = 'published'
ORDER BY is_top DESC, created_at DESC
LIMIT 10 OFFSET 900000;    -- the engine must count and skip 900,000 rows

No index fixes this. The offset is linear work by definition. The answer is to paginate from a position rather than a page number.

-- first page
SELECT id, title, is_top, created_at FROM articles_article
WHERE status = 'published'
ORDER BY is_top DESC, created_at DESC
LIMIT 10;

-- next page, carrying the last row as a cursor
SELECT id, title, is_top, created_at FROM articles_article
WHERE status = 'published'
  AND (is_top, created_at) < (?, ?)      -- row comparison, SQLite 3.15+ and PostgreSQL
ORDER BY is_top DESC, created_at DESC
LIMIT 10;

The index seeks to the cursor and reads ten entries, so every page costs the same. MySQL 8 needs the expanded OR form, since a row comparison does not use an index there. Django REST Framework ships cursor pagination, and the only decision is which field to use.

An honest conflict: pinned posts and cursors

Cursor pagination takes a single ordering field, and that field has to be unique and stable because its value is the cursor. The list orders by pinned and then timestamp, which fails twice: the ordering is composite, and the pinned flag is edited. When a post is pinned or unpinned, an existing cursor no longer means what it did, and the reader may see duplicates or miss rows.

# pinned posts are few; fetch them whole, no pagination
top_articles = Article.objects.filter(
    status=Article.Status.PUBLISHED, is_top=True
).order_by("-created_at")

# the main list paginates on the immutable timestamp
class ArticleCursorPagination(CursorPagination):
    page_size = 10
    ordering = "-created_at"

Merging the two sets inside one paginator would put the cursor across two datasets and break at the boundary, so render them as two regions. The front end wants that anyway, since pinned posts look different.

The cost of cursors is losing "jump to page N". If the product needs a page indicator, accept offsets and reduce the count cost instead. That is a product decision, not a technical one.

COUNT is also a slow query

SELECT count(*) FROM articles_article WHERE status='published'
→ SEARCH articles_article USING COVERING INDEX idx_status_created (status=?)
→ 88.05 ms

Eighty-eight milliseconds to render a line saying there are 128 posts. The plan is the best available, walking a narrow index rather than the table, and it is still linear: ninety thousand index entries have to be counted.

OptionMethodFits

This site combines the first two: the list shows no exact total, and category counts come from a single annotated query.

One detail worth knowing: counting a column is no faster than counting rows, and the only real optimisation is to make sure a narrow index exists that includes the filter column. The genuine shortcut is not counting at all.

More indexes is not better

OperationOne indexFive indexes
InsertRow plus one treeRow plus five trees
Update the statusRow plus one treeRow plus five trees
DeleteRow plus one treeRow plus five trees

On a read-heavy blog, five indexes are harmless. On a table taking a thousand writes a second, every redundant index costs real throughput and buffer pool space.

Selectivity is distinct values over rows, and low selectivity makes an index near useless on its own: a unique slug has selectivity near one, a status column with four values has almost none, and a boolean has effectively zero. In this article's index, the first two columns are barely selective, and nearly all the value comes from the last one. Their job is not filtering but aligning the physical order with the ordering, which is the theme of the whole post.

So two questions decide whether an index earns its place: how many rows does its leftmost column eliminate, and which ordering does its column order align with. An index that answers neither is pure write amplification.

The storage cost is real too: a 63 MB table grew to 128 MB with three indexes, and indexes larger than the data itself are ordinary in production.

-- PostgreSQL: find indexes nobody reads
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

MySQL has no view quite this direct. The reliable manual method is to list every ordering and filter in the codebase, match each against the existing indexes, and treat the unclaimed ones as deletion candidates.

Five steps for any slow query

StepActionTools
MeasureFind the slowest endpoint and statement, do not guessDebug toolbar, a profiler, an APM, the slow log with a digest tool
Split the billDecide whether it is count or costThe query capture context gives both
Read the planLook for scans and temp B-treesExplain, with analysis where available
Change the index or the SQLAlign the ordering first, then remove function wrapping, leading wildcards and prefix violationsModel metadata plus a migration, or a rewritten queryset
Verify with numbersRun the plan and the timing before and after, and require the temp B-tree to be gone or the scan to become a searchThe same tools, plus a query-count assertion against regressions

The last step deserves a rule of its own, because the enemy of performance work is "it feels faster". At nine rows, 0.18 and 476 milliseconds both round to nothing, and at small sizes a scan can genuinely beat a search on sequential reads, so tuning by feel can move you backwards.

Any performance change has to answer two questions: what was the number before, and what is it now. If it cannot, it is not an optimisation, it is a code change.

And indexes get undone. Someone adds a third sort term, the index no longer covers the ordering, and the temp B-tree is back. Pin the requirement in a test.

# articles/tests/test_query_plan.py
from django.db import connection
from django.test import TestCase
from articles.models import Article


class QueryPlanTests(TestCase):
    """The list query must not scan the table or sort."""

    def test_list_query_uses_index_without_sort(self):
        qs = Article.objects.filter(status=Article.Status.PUBLISHED)
        sql, params = qs.query.sql_with_params()
        with connection.cursor() as cur:
            cur.execute("EXPLAIN QUERY PLAN " + sql, params)
            plan = " | ".join(row[-1] for row in cur.fetchall())

        self.assertNotIn("TEMP B-TREE", plan, f"sort not indexed: {plan}")
        self.assertNotIn("SCAN articles_article", plan, f"full scan: {plan}")

Turning a plan into an assertion is the practice most worth copying here. It moves performance from something discovered after deploy to something blocked at commit.

Checklist

  • The plan before the change was captured, along with the numbers: time and rows scanned.
  • Index columns are ordered equality, then range, then sort.
  • Every ordering column and direction is matched by the index, including descending terms.
  • No index column is wrapped in a function, including date lookups and case folding.
  • No pattern begins with a wildcard.
  • No query skips the leftmost index column.
  • When a limit accompanies an ordering, the ordering itself uses the index, otherwise the limit only saves transfer.
  • Deep paging uses a cursor, or the linear cost of an offset is accepted deliberately.
  • Counts are cached or estimated rather than recomputed per page.
  • Large tables got their index through an online DDL path.
  • After the change, the plan shows no temp B-tree and no scan.
  • A plan assertion test exists to prevent a regression.
  • The old index was checked for remaining users and dropped if it had none.

Closing

All of this reduces to one sentence. An index has two halves: faster lookup, and order. Most people only use the first half.

The production index used the first half, filtering a million rows down to nine hundred thousand, and looked like it was working. It ignored the second half, so the engine sorted nine hundred thousand rows by hand. The plan said so the whole time; nobody had looked.

Three things to take away. Match every ordering column and direction in the index, because one missing term or one wrong direction is worse than no index. At small data volume an invalid index is invisible, so build data and read plans instead of trusting how it feels. And turn the plan into a test assertion, because performance is not a one-time task but a chronic condition that returns with every new field, ordering and endpoint.
