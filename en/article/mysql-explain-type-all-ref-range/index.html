Reading a MySQL query plan: what each column actually tells you

2026-11-04 · 14 min · Stack Frame

Who this is for: people who run a plan every day but only read the access type; people burned by a row estimate that was off by ten times; people wondering which of the length, filter and extra columns to believe.

TL;DR: the access type says how a table is visited, not whether the query is fast. A full scan is not automatically bad on a small table, and an index lookup is not automatically fast if it fetches hundreds of thousands of rows. What matters is whether an index was chosen, how large the scanned counts multiply out, and whether the plan shows an extra sort or temporary table.

Reading time around 14 minutes. Level: advanced.

A plan is not a performance score

People treat the access type as a grade: constant lookup is a hundred, index lookup is eighty, full scan is zero. That produces two kinds of mistake. Seeing a full scan, someone rushes to add an index, when scanning a small table was already faster. Seeing an index lookup, someone relaxes, when the plan expects 800,000 rows and the fetches rinse out the buffer pool.

A plan answers what the optimiser intends to do, not how long it will take. Every field is an estimate or a structural description. Real timing comes from execution analysis, the slow query log and instrumentation.

Constant lookups: the best rung

An equality condition on a primary key or unique index lets the optimiser decide at compile time that only one row can match, so the type is a constant lookup. If the table itself has a single row, the type becomes the system case.

The precondition is unique and non-null. A primary key is both. A unique index that permits nulls is not: several nulls do not violate uniqueness, so the optimiser cannot promise one row and may fall back to a reference.

One detail: if the value does not exist, the plan says there is no matching row in a constant table and reports zero rows. That is not an error, it is the optimiser knowing in advance.

Unique join matches

This access type appears in joins, where the driven table is matched through a unique index so each driving row corresponds to exactly one row. If the join column is not unique, it degrades to a plain reference.

The difference from a constant lookup is the source of the comparison value: a compile-time constant against the current row of another table. So it means one unique lookup per driving row.

Plain references, the most common good state

An equality condition on an ordinary secondary index may match several rows, and the type is a reference. That is the ordinary good outcome, with one caution: it only says the index could seek. How many rows that means is in the row estimate.

A variant covers the case of equality or null, which forces the optimiser to scan both the matching range and the null range. One extra range is usually harmless, unless there are many nulls, in which case the estimate rises noticeably.

Range scans on an index

SELECT * FROM users WHERE tenant_id = 7 AND status > 1;
SELECT * FROM users WHERE created_at BETWEEN '2026-01-01' AND '2026-02-01';
SELECT * FROM users WHERE email LIKE 'abc%';

Narrow ranges are better. If the range covers most of the table, the optimiser may choose a full scan instead. The index length usually stops at the range column, since anything after it cannot seek and only filters.

Two shapes of a full scan

An index scan walks the whole index rather than the table. With a covering note it reads only the index and never fetches rows, which is common for a covering index plus an ordering requirement. It is still slow if the index is large.

A full table scan is the other shape. A column that is not the leading part of any usable index forces it. On a table of a few hundred rows that is completely normal; on a million rows it is the thing to fix.

Both can be fast and both can be slow. The criterion is how many pages are read, not which name looks more advanced.

Merging several indexes

When a condition matches several indexes and no single composite index covers it, the optimiser may merge results. The plan shows an intersection for a conjunction, a union for a disjunction, or a sorted union when the union needs ordering.

In practice this is unstable: several index scans plus a set operation cost both CPU and memory, and it usually loses to one well-designed composite index. Disabling it for comparison is fine; leaving it disabled in production is not a good long-term plan.

Subquery access types

These appear when an IN subquery is executed per value. A unique index inside the subquery gives one type, an ordinary index another, and a subquery with no usable index degrades to a full scan or gets materialised.

Version matters: 8.0 applies semi-join transformations, materialisation and derived merging that 5.7 did not, so plans differ. Do not transplant experience from an older version without checking.

For an index on a BIGINT and a TINYINT, both non-null, one column gives 8 and two give 9. If both are nullable the total becomes 10, one null flag each.

A smaller than expected length usually means one of three things: the extra columns are absent from the condition, the order violates the prefix rule, or a range appears in the middle.

One trap: the length counts index key bytes and excludes the primary key that InnoDB appends to secondary indexes automatically. Do not use it to estimate the size of a secondary index record.

Row estimates and filter ratios

The row estimate is how many rows this access is expected to scan, and the filter ratio is what share of those should pass the remaining conditions. Multiplying them gives the rows that go on to the next stage. Chain that across a join and you see the order of magnitude of the whole statement.

The estimates depend on statistics, which go wrong in familiar ways: a bulk import before statistics are refreshed, frequent inserts and deletes leaving statistics stale, too many equality conditions pushing past the dive limit so the optimiser switches to sampling, and skewed distributions that the histogram does not cover. Histograms on skewed columns improve this noticeably.

A filesort note does not prove a disk sort. Small results sort in memory quickly. The problem is CPU and memory when the row count is large. Likewise a temporary table does not necessarily hit disk: since 8.0.16 internal temporary tables default to an in-memory engine and spill only past a threshold, so check the disk-temporary counter to know which happened.

What the JSON format adds

The tabular plan compresses information. The JSON format exposes finer cost and condition detail: the access type, candidate and chosen indexes, the key parts actually used, the key length, the comparison values, rows examined per scan and rows produced per join, the filter ratio, the conditions attached or pushed down, the columns the query needs, and a cost breakdown.

The used key parts field is the one to remember. On an index over three columns with conditions on the first and third, it plainly shows that only the first was used, which beats inferring it from a byte count.

The reported query cost is in arbitrary cost units, not milliseconds. It compares two plans against each other; it does not predict wall clock.

Reconciling estimates with reality

Execution analysis, available from 8.0.18, actually runs the statement and reports per operator the real time, the real row count, how many times the operator ran, and the optimiser's estimate. The usual use is reconciliation: an estimate of three rows against an actual 1,200 means the statistics or the cost model is wrong, so refresh statistics first and consider a histogram second.

Two cautions. It really executes the query, which is safe for a select and needs care for writes. And it reports one execution, so cache state and concurrency affect the numbers; one sample is not a conclusion.

Five common misreadings

Implicit type conversion. A string compared against a numeric column converts the constant, which usually keeps the index; a number compared against a string column converts the column, which loses it. Align types explicitly.

Stale statistics. After a bulk load or heavy churn the estimates can be badly off, so refresh and then re-read the plan.

The optimiser abandoned the index. When the matching fraction is high, fetching rows costs more than scanning, and a full scan is the correct arithmetic. Force the index once to check: faster means the statistics or model need attention, slower means accept the choice.

An index exists but was not chosen. Look for a broken prefix, a function wrapped around a column, an implicit conversion, a fetch cost estimate that came out too high, or a competing index merge or skip scan.

A limit clause as a universal optimisation. With an index it is fast; without one, the sort has to order the whole result before taking ten rows. A limit reduces transfer, not sorting.

An order of investigation

  1. How big is the table: rows and data size.
  2. Access type and chosen index: any full scan, any missing index.
  3. The product of rows and filter ratio: does the magnitude match business expectations.
  4. Plan notes: sorting, temporary tables, join buffers.
  5. Used key parts, from the JSON format, to see how many index columns were really used.
  6. Reconcile with execution analysis.
  7. Then change something, and re-run the same sequence to compare.

The optimiser trace explains why a plan was chosen, listing the cost estimate for every candidate index. It is worth using for one question, and too verbose for daily reading.

Summary

  • Access type is how, row count is how much, plan notes are what else happens. Read all three.
  • Constant lookups, unique join matches, references and ranges are usable; index scans and full scans depend on table size.
  • The index length is direct evidence of columns used, and the JSON format states it more plainly.
  • Row and filter estimates are estimates; reconcile them with execution analysis when it matters.
  • Plan before adding an index, plan after, and compare. Do not work from a feeling.
