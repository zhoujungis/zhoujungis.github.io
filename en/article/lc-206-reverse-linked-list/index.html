LC 206, reverse a linked list: save the link before you cut it

2026-09-21 · 16 min · Stack Frame

The problem

Given the head of a singly linked list, reverse it and return the new head.

input:  1 -> 2 -> 3 -> 4 -> 5
output: 5 -> 4 -> 3 -> 2 -> 1

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

It is labelled easy and asked constantly, usually as the first linked-list question in an interview. It is asked repeatedly not because the answer is hard but because it separates people who understand pointers from people who memorised code. The memorised version falls apart the moment the interviewer asks for the first n nodes, a range, or k at a time; the understood version sees those as the same operation with different boundaries.

Translating "reverse" into pointer operations

In an array, reversing is two indices walking toward each other and swapping. Positions are contiguous, so the fifth element is findable.

A linked list is not like that. Nodes can be anywhere in memory, each knows only its successor, nothing knows its predecessor, and nothing knows its position. All you hold is the head, and everything is reached by pulling on that thread.

1 -> 2 -> 3 -> 4 -> 5 -> None
None <- 1 <- 2 <- 3 <- 4 <- 5

So reversing means one thing: change every node's next from pointing at its successor to pointing at its predecessor. Five nodes, five pointer changes, and the difficulty is entirely in the timing.

Picture a row of people holding hands blindfolded, each knowing only whose hand is in their right. Now everyone must turn around. The moment you let go to reach behind you, you no longer know who was on your right, because that was your entire memory.

So there is only one correct order. Remember who is on the right, turn by taking the hand on the left, then step forward together. Skip the first and the chain snaps.

The animation, as a walkthrough

The original post has a sixteen-step animation. Here is what it shows. Three markers move along the list: prev one node behind curr, and next holding the node that would otherwise be lost. After each node is processed, the arrow between it and its former successor flips. And the end marker moves: it starts after the last node, and finishes before the first one, because the original head becomes the tail.

Watching it, the useful observation is that there is never an instant where the chain is broken. The temporary pointer exists precisely so that the road ahead is marked before the road behind is cut.

Running it on paper, five boxes numbered one to five, following the three steps strictly, teaches more than reading the code ten times.

The boundary between prev and curr separates what is done from what is not, and each iteration moves it one node right until curr falls off the end.

def reverseList(head):
    prev = None
    curr = head

    while curr:
        nxt = curr.next
        curr.next = prev
        prev = curr
        curr = nxt

    return prev

Why prev starts as none and not as the head: after reversing, the original head becomes the tail, and a tail points at nothing. Starting at nothing means the first pointer change sets 1.next to none automatically.

The temporary save is the heart of it, because the next line overwrites the link to the rest of the list. The pointer change is the actual work. Then the two moves: prev moves only after the pointer change, or it would hold the wrong value, and curr advances using the saved value rather than the field just overwritten.

And return prev, not curr. When the loop ends curr is none while prev rests on the original last node, which is the new head. Returning the wrong one is the most common slip.

None of those need a special case, which is the comfort of the iterative version: recursion needs explicit guards for empty and single-node lists, iteration covers them naturally.

class Solution {
    public ListNode reverseList(ListNode head) {
        ListNode prev = null;
        ListNode curr = head;
        while (curr != null) {
            ListNode nxt = curr.next;
            curr.next = prev;
            prev = curr;
            curr = nxt;
        }
        return prev;
    }
}

In Java the temporary must be declared inside the loop, and the four statements cannot be compressed the way Python allows, because the order genuinely matters.

Recursive

Iteration walks forward from the head. Recursion can think backwards: assume the call on the rest of the list has already reversed everything after the current node and returned the new head, and all that remains is to attach the current node to the end of that reversed segment.

The subtlety is that the recursive call returns the new head, which is the original tail, while head.next has become the tail of the reversed segment. So the tail must point back at the current node, and the current node must then point at nothing.

Two things are easy to misread. The new head is the same node at every level, carried upward unchanged, while the real work happens in the two pointer assignments. And recursion reaches the bottom first and rewires on the way back, so the order of pointer changes is the reverse of iteration: iteration changes the first link first, recursion changes it last.

def reverseList(head):
    if not head or not head.next:
        return head

    new_head = reverseList(head.next)
    head.next.next = head
    head.next = None
    return new_head

Both halves of the guard matter. The first handles an empty list, without which the next line dereferences nothing. The second stops at a single node, which is already its own answer. Writing only the second crashes on an empty input; writing only the first recurses one level too far on a single node.

class Solution {
    public ListNode reverseList(ListNode head) {
        if (head == null || head.next == null) return head;
        ListNode newHead = reverseList(head.next);
        head.next.next = head;
        head.next = null;
        return newHead;
    }
}

The recursion is shorter and reads better, and an interviewer will usually ask about space. The answer is linear, not because of an array but because of the call stack: n nodes means n frames. In practice, Python's default recursion limit fails on a list of a few tens of thousands, and the JVM's stack overflows at a few thousand to ten thousand levels, so long lists need the iterative form.

The standard answer: recursion uses linear space, iteration uses constant space, and unless asked otherwise, write the iterative one.

Follow-up: k at a time (LC 25)

With [1,2,3,4,5] and k of two, the answer is [2,1,4,3,5], with the leftover single node untouched. So the whole thing decomposes into three actions: count k nodes ahead and bail out if the run is short; reverse those k using exactly the LC 206 loop; then reconnect the previous group's tail to this group's new head, and this group's tail to the next group.

Reconnection is where it goes wrong, because reversing swaps head and tail.

The first group also means the original head is no longer the list head, so a dummy node in front gives a stable anchor, and the answer is the dummy's next. That is a general linked-list trick: if the head can change, add a dummy, because it makes changing the head and changing the middle the same case.

def reverseKGroup(head, k):
    dummy = ListNode(0, head)
    group_prev = dummy

    while True:
        kth = group_prev
        for _ in range(k):
            kth = kth.next
            if kth is None:
                return dummy.next

        group_next = kth.next

        prev, curr = group_next, group_prev.next
        while curr is not group_next:
            nxt = curr.next
            curr.next = prev
            prev = curr
            curr = nxt

        group_tail = group_prev.next
        group_prev.next = kth
        group_prev = group_tail

Starting prev at the next group's head is the neat detail: after reversing, the group's original head, now its tail, already points at the next group, so half the reconnection is free.

def reverseKGroup(head, k):
    node = head
    for _ in range(k):
        if node is None:
            return head
        node = node.next

    prev, curr = None, head
    for _ in range(k):
        nxt = curr.next
        curr.next = prev
        prev = curr
        curr = nxt

    head.next = reverseKGroup(curr, k)

    return prev

The recursive form is easier to remember and makes the grouping obvious: check the count, reverse k, then let the group's tail point at whatever the rest becomes.

class Solution {
    public ListNode reverseKGroup(ListNode head, int k) {
        ListNode dummy = new ListNode(0, head);
        ListNode groupPrev = dummy;

        while (true) {
            ListNode kth = groupPrev;
            for (int i = 0; i < k; i++) {
                kth = kth.next;
                if (kth == null) return dummy.next;
            }
            ListNode groupNext = kth.next;

            ListNode prev = groupNext;
            ListNode curr = groupPrev.next;
            while (curr != groupNext) {
                ListNode nxt = curr.next;
                curr.next = prev;
                prev = curr;
                curr = nxt;
            }

            ListNode groupTail = groupPrev.next;
            groupPrev.next = kth;
            groupPrev = groupTail;
        }
    }
}

The short tail must be handled inside the counting loop: the moment a null appears, return, rather than finishing the count and checking afterwards, which either crashes or reverses a partial group.

Linear time is easy to see: each node is visited once and each link is changed once. The space difference is the interview point.

Common mistakes

  1. Forgetting to save the successor, so advancing reads the link just overwritten and the rest of the list is lost.
  2. Returning the loop variable instead of the previous pointer, which hands back an empty list.
  3. Omitting the final pointer clear in the recursive version, which creates a cycle: the two nodes point at each other and printing loops forever.
  4. Writing only half the recursive guard, which either crashes on an empty list or recurses once too far on a single node.
  5. Checking the k-count after the loop rather than inside it, which crashes on a short tail.
  6. Reconnecting the wrong end in the k-group version. After reversing, the original group head is the group tail and the kth node is the group head.

How to answer it

Do not start typing. Confirm the contract, state the three-pointer idea with the order of operations, mention that empty and single-node lists need no special case, then give the complexity. Then offer the follow-up yourself: the k-group version is this loop repeated, plus a dummy node to manage the joins.

That last step is the one that scores, because it shows you can restate the same operation under a different boundary, which is what the follow-ups are testing.

Closing

The boundaries change; the three steps do not. Next time a variant appears, ask two questions before writing anything: which segment is being reversed, and what has to be attached on either side of it afterwards.
