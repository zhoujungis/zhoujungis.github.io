Why I dare to render user Markdown: one XSS defence, four layers

2026-10-27 · 15 min · Stack Frame

The backend is Django and DRF, the front end is Vue. Articles are stored as Markdown and the read endpoint returns rendered HTML for the browser to display. Which means user Markdown becomes HTML that I serve.

If you have only written admin panels, or think of Markdown rendering as reading a column and joining strings, the sentence deserves restating: rendering user input is executing user code.

Why rendering is dangerous

### Hello, world

<h3>Hello, world</h3>

Harmless, until the same text comes from anywhere untrusted, a comment, a submitted note, or an article an administrator pasted from elsewhere. Then rendering hands your execution privileges to the input, because Markdown can express these:

<img src=x onerror="alert(document.cookie)">
[click](javascript:alert(1))
<a href="data:text/html,<script>alert(1)</script>">click</a>
<svg><a xlink:href="javascript:alert(1)"><text>click</text></a></svg>

An image error handler fires when loading fails, a javascript protocol fires on click, a data URL can carry executable markup in some browsers, and an SVG can hide a script behind a link. That is a fraction of the surface, which includes iframes, style blocks, objects, video posters, math, and forged forms.

XSS is not a filtering problem, it is a trust boundary problem. A blocklist chases attackers forever. The inversion is to allow only the small set you know is safe.

Layer one: controlled rendering

class Article(models.Model):
    content = models.TextField(verbose_name="Content (Markdown)")
    html_content = models.TextField(blank=True, editable=False)

    def save(self, *args, **kwargs):
        md = markdown.Markdown(
            extensions=["fenced_code", "codehilite", "tables", "extra", "toc"]
        )
        raw_html = md.convert(self.content)
        ...

Three details. The extensions are listed explicitly rather than everything being enabled, so the renderer produces only known structures and an attacker cannot borrow a tag the renderer never emits. The output is still dirty, because the library converts syntax and does not care about safety, preserving javascript links and inline HTML verbatim. And the derived column is not editable, so it can only come from the save method rather than being written directly.

So rendering is not a defence. It is the input to the whitelist.

Layer two: the whitelist

self.html_content = bleach.clean(
    raw_html,
    tags=bleach.sanitizer.ALLOWED_TAGS
    | {
        "h1", "h2", "h3", "h4", "h5", "h6",
        "img", "pre", "code", "span", "div",
        "table", "thead", "tbody", "tr", "th", "td",
        "hr", "br", "sup", "sub",
        "figure", "figcaption",
    },
    attributes={
        **bleach.sanitizer.ALLOWED_ATTRIBUTES,
        "img": list(set(["src", "alt", "title", "loading", "decoding"])
                     | set(bleach.sanitizer.ALLOWED_ATTRIBUTES.get("img", []))),
        "a": list(set(["href", "title", "rel", "target"])
                  | set(bleach.sanitizer.ALLOWED_ATTRIBUTES.get("a", []))),
        "code": list(set(["class"])
                     | set(bleach.sanitizer.ALLOWED_ATTRIBUTES.get("code", []))),
    },
    protocols=["http", "https", "mailto"],
    strip=True,
)

One call applies three whitelists.

Tags. The library's defaults cover the basics, extended here with the elements the renderer emits. Anything absent, including script, iframe, object, embed, style, svg, math, form and input, is removed entirely, content and all, rather than being left as text.

Attributes. Allowing a tag does not allow its attributes: an image may carry only source, alt, title and loading hints, a link only href, title, rel and target, and code only a class for highlighting. Every event handler is absent, so an image with an error handler comes out as a plain image.

There is a trap here. Assigning a fresh attribute dictionary for a tag overwrites the library defaults and silently kills things like table spans, which is why each entry unions the defaults with the additions instead of replacing them. Treat the default list as a base package and yours as an increment.

Protocols. Even a permitted link still has its scheme checked, so a javascript URL loses its href and the link text survives without a target.

Real hole one: the data protocol

The first version added data to the protocol list, on the theory that inline images might be useful.

<a href="data:text/html,<script>alert(document.cookie)</script>">click</a>

The sanitiser saw a permitted protocol, a permitted tag and a permitted attribute, and passed all three. Clicking it, however, makes some browsers render the payload as a document and run the script, and the attacker only needs one click.

That is the soft spot of any whitelist: every permission you add for convenience is another way around. And one opening is enough for arbitrary script.

# C-S2: protocols drop 'data' globally — it was letting
#   <a href="data:text/html,<script>...</script>"> through, which Safari /
#   WebViews still execute. Inline base64 images aren't used here
#   (covers are URLField elsewhere), so the loss is acceptable.

The engineering trade is explicit: dropping data loses the ability to inline base64 images, and since covers already come from ordinary URLs, the capability was never used. An unused capability is pure risk with no benefit, and the smaller the surface the better.

Layer three: hardening outbound links

Script execution is not the only surface. A link opened in a new tab can reach back through the opener reference and navigate the original page to a phishing site, which older browsers allow by default.

self.html_content = re.sub(
    r'<a ([^>]*?)href="(https?://[^"]+)"',
    r'<a \1href="\2" rel="noopener noreferrer" target="_blank"',
    self.html_content,
)

Every external link gains a noopener relation so the new page cannot touch the opener, a noreferrer relation so the referrer is not leaked, and a new tab so the reader keeps the current page. Internal links are untouched, since they do not need a new window.

Real hole two: HTML leaking through the excerpt

The second hole was in the summary used by the article cards. The old code stripped Markdown syntax from the raw source with a regular expression, which assumes Markdown is regular and forgets that it permits inline HTML.

An article containing an SVG with an onload handler kept that markup as text through the stripping, and the card rendered it, executing the script in the listing page. The same approach also mangled autolinks, leaving angle brackets and the URL as visible text or, worse, as a tag.

def make_excerpt(html_content, fallback_text="", word_limit=50):
    text = html_content or ""
    text = re.sub(r"<pre\b[^>]*>.*?</pre>", " ", text, flags=re.DOTALL)
    text = re.sub(r"<(style|script)\b[^>]*>.*?</\1>", " ", text, flags=re.DOTALL)
    text = re.sub(r"<[^>]+>", " ", text)
    text = unescape(text)
    text = re.sub(r"\s+", " ", text).strip()

The insight is the source: the summary is no longer derived from untrusted Markdown but from the already-sanitised HTML. Everything dangerous was removed upstream, so even an imperfect regular expression here can only leak harmless text, never executable markup.

That is defence in depth in practice: the same data is cleaned at several stages, and every stage assumes the previous one failed.

The chain

user Markdown
  -> controlled rendering, fixed extensions, no extra tags
  -> three whitelists: tags, attributes, protocols
  -> outbound link hardening
  -> excerpt extracted from the sanitised HTML
  -> stored, served, rendered
LayerMechanismStops
OneExplicit Markdown extensionsReduces the HTML structures that can exist at all
TwoThree whitelistsScript tags, event handlers, javascript and data URLs, SVG
ThreeNoopener and noreferrerReverse tabnabbing, referrer leaks
FourExcerpt from sanitised HTMLSecond-order XSS in the listing, Markdown syntax leaks

Why one layer is not enough: a renderer does not do security, a sanitiser cannot stop the browser's own opener mechanism, and a regular expression always has an edge case, as the autolink showed.

The premise is not "I am safe" but "I will have a hole". Each layer assumes the previous one is breached and narrows the surface further.

The principles do not change. Always whitelist and never blocklist. Cover tags, attributes and protocols, because filtering tags alone misses error handlers and scheme abuse. Keep rendering and sanitising separate and chain them in a pipeline. Clean again when deriving a summary, since one more pass costs nothing. Treat unused capabilities as risk and delete them. And write the comments, because the reasoning and the discarded options are the most valuable artefact you leave behind.

Closing

Daring to render is not courage, it is the confidence that comes from having designed every layer. That save method was not written in a day, and two real holes paid for it.

Three questions worth asking before rendering anything from a user: do I trust this input, what is the worst case if I am wrong, and does everything I allow actually need to be allowed. Answer those and you are close.
