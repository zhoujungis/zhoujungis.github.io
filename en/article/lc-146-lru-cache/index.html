LRU Cache: a hand-written hash map and doubly linked list

2026-10-12 · 18 min · Stack Frame

The problem

Source: Tencent asks it 123 times, ByteDance 72. Among hand-written design questions, this is the cache problem that shows up most.

Design and implement a data structure that satisfies the least recently used cache constraint.

  • LRUCache(int capacity): initialize with a positive capacity.
  • int get(int key): return the value if the key exists, otherwise -1.
  • void put(int key, int value): update the value if the key exists, insert it if not, and evict the least recently used entry when the cache is full.
  • Both get and put must run in O(1).

You have to hand-write the doubly linked list and the hash map. LinkedHashMap and OrderedDict are off limits. Two follow-ups usually come next:

One: how would you make it thread-safe?

Two: how does it differ from LFU, LC 460?

The canonical test case, which is also the default script for the walkthrough below:

LRUCache(2)
put(1,1); put(2,2)        list: [1] then [2,1]
get(1)                    returns 1,  list becomes [1,2]
put(3,3)                  evicts 2,  list: [3,1]
get(2)                    -1
put(4,4)                  evicts 1,  list: [4,3]
get(1) -1; get(3) 3; get(4) 4

1. The core insight: two legs for O(1)

Start with why both structures are necessary.

  • A hash map alone: get is O(1), but nothing records who is least recently used. Every eviction would scan all keys, O(n), and the order of use cannot be maintained at all.
  • A linked list alone: order is trivial, but get(key) has to find the node first, and searching a list is O(n).
  • Both together: the map gives key to node lookup in one step, and the doubly linked list keeps usage order. Each does the job the other cannot.
front (head side) = most recently used (MRU)
back  (tail side) = least recently used (LRU)   evictions always come from here

Two "why" questions come up almost every time.

Why doubly linked and not singly linked? A get hit has to detach the node from the middle of the list and move it to the front. A singly linked list needs the predecessor to detach a node, and finding the predecessor means scanning from the head, O(n). With a doubly linked list the node carries prev, so detaching is O(1).

Why sentinels? With a dummy head and tail, every node's prev and next are non-null, so insertion and removal never need a null check. That is half the if statements gone, and the boundary cases, capacity one and single-node lists, stop being special.

2. Hand-written structure: three fixed operations

The whole implementation is three pointer operations. Memorize their order and you stop getting them wrong.

  • addToFront(node): attach the node right behind the head sentinel.
  • unlink(node): remove the node, letting its neighbors point at each other.
  • moveToFront(node): unlink then addToFront.

Python, with no OrderedDict:

class Node:
    __slots__ = ("key", "value", "prev", "next")

    def __init__(self, key=0, value=0):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.cache = {}                    # key -> Node
        self.head = Node()                 # sentinel: head.next is the first real node
        self.tail = Node()                 # sentinel: tail.prev is the last real node
        self.head.next = self.tail
        self.tail.prev = self.head

    def _add_to_front(self, node):
        node.prev = self.head
        node.next = self.head.next
        self.head.next.prev = node
        self.head.next = node

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _move_to_front(self, node):
        self._unlink(node)
        self._add_to_front(node)

    def get(self, key: int) -> int:
        node = self.cache.get(key)
        if node is None:
            return -1
        self._move_to_front(node)          # a hit is a use
        return node.value

    def put(self, key: int, value: int) -> None:
        node = self.cache.get(key)
        if node is not None:
            node.value = value
            self._move_to_front(node)      # rewriting counts as a use
            return
        if len(self.cache) == self.cap:    # full: evict from the tail
            victim = self.tail.prev
            self._unlink(victim)
            del self.cache[victim.key]     # delete from both, or you get a ghost
        node = Node(key, value)
        self.cache[key] = node
        self._add_to_front(node)

put has exactly three cases: the key exists, so update and move to front; the cache is not full, so insert at the front; the cache is full, so evict the tail from both structures and then insert. Reeling those three off in an interview is worth far more than "it's an LRU, you know".

3. Reading the two walkthroughs

Walkthrough one, the LRU itself. The top row is the linked list. H and T are sentinels, the front is the most recently used and the tail is the eviction candidate. Each node shows key:value and a node number. The middle row is the hash map, whose entries look like key to #n. Watch them change together: an insert adds to both, an eviction removes from both. On an eviction frame the tail shows a dashed ghost node, which is the entry that was just detached.

Walkthrough two, the LFU contrast. The same operation script is fed to an LFU cache, where nodes are ordered by ascending frequency, so the leftmost node is the next eviction. Each node carries a frequency badge, and both get and a put hit increment it. Two frames tell the whole story: at put(3,3) the LRU evicts (2,2) while the LFU evicts (1,1).

4. The full walkthrough

Running the default script through the LRU, with the list written head to tail:

Both eviction moments are worth memorizing. put(3,3) evicts (2,2) even though 2 was inserted later than 1, because the get(1) in between used 1 and left 2 untouched. put(4,4) evicts (1,1): 1 had been popular, but once 3 arrived it was the tail. LRU looks at whether something was used recently, not at how often it was used.

The LFU contrast, same script, one divergence:

Same operations, same capacity, different key evicted. That is the entire difference between LRU and LFU compressed into one trace.

5. Follow-up two: how LFU differs

LRU (146)LFU (460)
Dimension rememberedTime: was it used recentlyFrequency: how often was it used
What a get hit doesMove the node to the front, changing orderIncrement frequency, changing eviction priority
Who gets evictedThe tail, the least recently usedThe lowest frequency, and among equals the least recently used
StructureHash map plus one doubly linked listHash map plus frequency buckets plus a minFreq pointer
Difficulty of O(1)Low, three operationsHigh, bucket churn and minFreq maintenance
Typical weaknessA single scan can flush the hot set, which is cache pollutionHistorical hot keys stick around; new keys get killed instantly

LFU reaches O(1) through frequency buckets: each frequency value owns a doubly linked list ordered by recency, and a minFreq pointer tracks the smallest bucket. A hit moves the node from bucket f to bucket f+1. An eviction takes the tail of the minFreq bucket. The hard part of LC 460 was never the linked list, it is the buckets and the pointer.

Production caches take a fourth route. Caffeine uses W-TinyLFU, an admission window combined with a frequency sketch, which resists scan pollution without maintaining exact buckets. Mentioning that in an interview changes the level of the conversation.

6. Follow-up one: making it thread-safe

Start by killing an assumption: get is not a read-only operation. It calls moveToFront, which mutates the list. "Use a read-write lock because reads dominate" is therefore a non-starter, since every read may write.

  • One global lock is the simple, correct answer: synchronized in Java, threading.Lock in Python. Correct, trivial, and fully serialized. Say this first, then talk about optimization.
  • Striped locks are the engineering answer: hash the key into N shards, each with its own LRU and its own lock. Concurrency rises, but capacity stops being exact, since each shard evicts independently and the total can drift.
  • Approximate algorithms are the production answer: CLOCK or W-TinyLFU reduce each access to a constant number of bit operations instead of precise list maintenance, trading eviction accuracy for scalability.

An interview sentence that works: the simplest correct version serializes everything behind one lock, and the bottleneck is that get also writes to the list. In production you step back to striping or approximation, trading eviction precision for concurrency.

7. Java, also hand-written

class LRUCache {
    private static final class Node {
        int key, value;
        Node prev, next;
        Node(int k, int v) { key = k; value = v; }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);   // sentinel
    private final Node tail = new Node(0, 0);   // sentinel

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        moveToFront(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToFront(node);
            return;
        }
        if (map.size() == capacity) {
            Node victim = tail.prev;            // tail is least recently used
            remove(victim);
            map.remove(victim.key);             // delete from both
        }
        Node fresh = new Node(key, value);
        map.put(key, fresh);
        addToFront(fresh);
    }

    private void addToFront(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void moveToFront(Node node) {
        remove(node);
        addToFront(node);
    }
}

One Java detail: the sentinels are never in the map and can never be overwritten by a put. After remove you must call map.remove, or the evicted key stays in the hash map and the next get finds a node that is no longer on the list.

If a written test ever allows the standard library, new LinkedHashMap<>(cap, 0.75f, true) with removeEldestEntry overridden, or OrderedDict with move_to_end, solves it in one line. This question exists precisely because it forbids that.

8. The family: 460, 432, 707, 2296, interview 16.25

LC 146 is the origin point for the design, linked list and hash map family.

  • LC 460, LFU cache: the contrast in section 5. Frequency buckets plus minFreq, the natural next step.
  • LC 432, all O(1) data structure: increment, decrement, get max and get min in O(1), using the same value-to-list bucket idea.
  • LC 707, design a linked list: no cache at all, just raw doubly linked list operations.
  • LC 2296, design a text editor: a doubly linked list with a cursor, the other classic use.
  • Interview 16.25: the same problem under the interview numbering, with comparable frequency.
  • LC 588 and 1166: path-to-node hashing combined with trees and lists, same underlying idea.

9. Edge cases and traps

  • A put on an existing key must move it to the front and update the value. Forgetting that an overwrite counts as a use is the most common bug in this problem.
  • A get miss must not disturb anything: return -1 and leave the structure alone.
  • Eviction is a double delete: detach from the list and delete the map entry. List only gives a ghost node; map only leaks the node.
  • Writing the same value still counts as a use. put(1, 5) when 1:5 is present still moves the node to the front.
  • Capacity one needs no special case with sentinels, which is exactly what they buy you.
  • Pointer order matters. Four lines in addToFront, two in remove. Get them backwards and a single-node list points at itself.
  • Do not use the library. The prompt forbids LinkedHashMap and OrderedDict. It compiles, and the interviewer counts it as not answering the question.
  • __slots__ in Python is a nice touch, worth mentioning and worth nothing if you skip it.

10. Complexity

OperationTimeWhy
getO(1) amortizedHash lookup, then a constant number of pointer writes
putO(1) amortizedLookup, at most one eviction, one insert at the front
SpaceO(capacity)Map and list each hold at most capacity nodes

No traversal, no scan. That is all "O(1) LRU" means. Against LFU: with buckets and minFreq maintained correctly it is also O(1), but with considerably more structure to keep alive.

11. How to answer in an interview

First, structure selection. Two legs: the hash map gives O(1) lookup from key to node, the doubly linked list gives O(1) reordering and eviction. Then why doubly linked, because detaching a middle node needs the predecessor, and why sentinels, because they remove every null check. Most candidates are vague here, and clarity on this part is half the interview.

Second, the hand-written part. Three operations, addToFront, unlink, moveToFront. Three cases in put. The double delete on eviction.

Third, the follow-ups. Thread safety, led by the observation that get writes to the list, with the global lock, striped and approximate answers in that order. LFU, which is the time dimension against the frequency dimension, with the same script evicting different keys, and O(1) from buckets plus minFreq.

One sentence to close on: the whole question is hash map finds, doubly linked list queues, and when you write it by hand, watch the sentinels, the double delete, and the fact that a put hit still moves the node to the front.

Closing

LC 146 contains no algorithm and no math. It tests how well you command a combination of two basic structures: the map gives O(1) access, the list gives O(1) order. Get this one right and LFU's frequency buckets, 432's buckets of buckets, and the striped and approximate thread-safe variants are all the same map with more detail on it. Write it once by hand; reading it ten times will not do the same thing.
