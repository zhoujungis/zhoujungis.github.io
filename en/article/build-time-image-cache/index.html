A four minute build, three and a half of it re-encoding 94 images

2026-11-12 · 10 min · Stack Frame

The build is slow, and you do not know where

The build is unremarkable on paper.

{
  "scripts": {
    "build": "vite build && node scripts/prerender.mjs",
    "postbuild": "node scripts/compress-images.mjs"
  }
}

Vite bundles the frontend, the prerender script writes one static page per article, and the postbuild step encodes 94 cover images into WebP and AVIF.

It felt like three minutes, and it felt like three minutes every time, even when the only change was a line of CSS with no image touched.

The instinct is to blame the bundler or the prerender step. Then you time the three phases separately.

vite build     : 1.75 s
prerender      : ~16 s   (146 pages, API + file writes)
image postbuild: 181.9 s (94 encoded, 0 cached)
TOTAL          : 191.3 s

Ninety-five percent of the build re-encodes files that never changed.

Time the phases before optimising

A forty-line wrapper runs the build once and extracts three numbers from the output.

const t0 = Date.now()
const res = spawnSync('npm', ['run', 'build'], { cwd: FRONTEND, shell: true, encoding: 'utf8' })
const total = (Date.now() - t0) / 1000

const vite = out.match(/built in ([\d.]+)s/)
const compress = out.match(/Done: (\d+) images, (\d+) encoded, (\d+) cached, ([\d.]+)s/)
PhaseTimeShare

1.94 seconds per image is reasonable, since AVIF is genuinely expensive to encode. What is unreasonable is paying it for an unchanged file.

Why the first cache attempt did nothing

The obvious fix is to record what has been encoded and skip it. My first attempt stored the manifest at frontend/dist/.image-cache.json and skipped when the source size and modification time matched and both outputs existed.

Run on its own, the script behaved perfectly: 94 images, 0 encoded, 94 cached, 0.1 seconds. Inside the build it always reported 94 encoded.

The reason is Vite's default behaviour: emptyOutDir wipes dist/ at the start of every build, taking the manifest and the cached outputs with it.

The cache was in the wrong place. An output directory means exactly that, and anything with a lifetime longer than one build has to live elsewhere.

frontend/
  .cache/images/            ← survives builds, git ignored
    manifest.json
    lc-1-cover.webp
    lc-1-cover.avif
  dist/photos/              ← rewritten every build

Hit the cache, copy the file

const hit = await cachedOutputs(src, manifest[src], srcStat)
if (hit) {
  await copy(hit.webp, distWebp)
  await copy(hit.avif, distAvif)
} else {
  await sharp(src).webp({ quality: 80 }).toFile(cacheWebp)
  await sharp(src).avif({ quality: 60 }).toFile(cacheAvif)
  await copy(cacheWebp, distWebp)
  await copy(cacheAvif, distAvif)
}

Three conditions decide a hit, and all three are needed. The source size must match, which catches the common case of a different image saved under the same name. The modification time must match, which catches a re-export that happens to have the same size. And both cached outputs must exist and be non-empty, which catches a half-cleared cache directory.

The manifest also carries the encoder options:

{ "options": "webp80-avif60-max2400", "entries": { ... } }

Changing quality or the maximum dimension invalidates the whole manifest, which prevents a subtle failure where new settings silently apply only to images encoded after the change.

A realistic case: change one cover, rebuild, and only that image is encoded. The image phase takes about two seconds while the other 93 are copied from cache.

Cold builds still take three minutes, which is unavoidable since something has to be encoded the first time. But daily builds going from three minutes to twenty seconds decides whether you are willing to rebuild the site to fix a typo.

What could still be faster

Parallel encoding is the biggest win left. The loop is serial: 94 images at 1.94 seconds each. Four workers would put it near fifty seconds. Sharp wraps libvips and is safe to call concurrently, so batching with Promise.all is enough.

Producing AVIF only where it is used matters too. AVIF encoding costs several times what WebP does, and images that only appear in the feed or an archive page do not need both formats.

Incremental prerendering is the last one. The prerender script already caches article details, but it still rewrites all 146 pages. Rewriting only pages whose article changed would take the sixteen seconds down to a few, though it is smaller than the image win.

Order matters: remove duplicated work first, then parallelise. The cache eliminates ninety-five percent of the duplication, which is what makes parallelism worth doing at all.

Checklist

  • Build caches live outside the output directory, or emptyOutDir deletes them.
  • The cache key includes source size and modification time.
  • The cache key includes encoder settings, and changing them invalidates everything.
  • A hit is only accepted when the cached outputs exist and are non-empty.
  • A force flag exists for when the encoder, the fonts or your trust in the cache changes.
  • The cache directory is git ignored and is not inside dist.
  • CI caches that directory, otherwise CI is always cold.
  • The cold path still works, since the first build on a fresh machine has no cache.

Questions that come up

Why not commit the encoded files? You could, and 94 images in two formats would add several hundred megabytes of binary to the repository, then need another commit whenever quality changes. The cache is a local and CI concern; the repository keeps sources.

Are modification times stable in CI? No. A fresh clone stamps every file with checkout time, so CI is cold by definition. Cache the directory in CI rather than relying on timestamps.

Could the cache serve a stale image? Only if size and modification time both match while the content differs, which is vanishingly rare. The force flag exists for that day.

Why is compression a postbuild step? A prebuild step would write into a directory that the bundler then wipes.

Why is AVIF so much slower? It uses a costlier intra-frame codec, and in exchange produces files thirty to fifty percent smaller than WebP at comparable quality.

Closing

No application code changed. A step that ran every build but had nothing to do became incremental.

The number worth keeping is the split: of 191.3 seconds, 181.9 were spent re-encoding the same 94 images. When a build feels slow, time the phases before replacing the toolchain. The problem is rarely that the build is slow; it is that you keep rebuilding the same thing.
