Logged out after an hour? Dual-token auth with Django and Vue

2026-10-30 · 26 min · Stack Frame

Stack: Django 6 with SimpleJWT, Vue 3 with Pinia and Axios. The code is the actual blog: settings, urls, the auth store, the Axios client and the router guard.

Reading time around 26 minutes. What you get: a dual-token template that refreshes on its own, refreshes once under concurrency, logs out cleanly and resists password guessing.

The most annoying bug is "I just logged in"

When the admin area first shipped, it had a mysterious failure. Login in the morning and the dashboard works. Write an article at noon, hit save, and the page bounces to login with the draft nearly lost. The network tab shows a wall of 401s from the admin endpoints.

The cause in one sentence: the access token expires after an hour and the front end never renews it, so the user must log in again by hand.

After the fix, the first request after expiry refreshes and retries without the user noticing, five concurrent 401s produce exactly one refresh, and only an expired refresh token sends anyone back to login. That is the full dual-token chain.

The whole picture

login page
  -> POST /api/token/ {username, password}
  -> {access (1h), refresh (1d)} stored locally

save an article
  -> POST /api/admin/articles/ with Bearer access -> 201

an hour later, save again
  -> 401 (access expired)
  -> interceptor: POST /api/token/refresh/ {refresh} -> new access
  -> retry the original request -> 201, user sees nothing

refresh expired too (a day away from the admin)
  -> refresh also 401 -> clear tokens -> go to login
TokenLifetimePurposeIf leaked
AccessSixty minutesSent with every request, short livedUsable for at most an hour
RefreshOne dayOnly exchanges for an access tokenCan mint access tokens for a day, so protect it and make it revocable

The idea is a short-lived everyday key and a long-lived key that is used rarely. A single seven-day token is a seven-day master key once leaked; this halves the blast radius into an hour.

How a JWT works, in five minutes

header.payload.signature

The header names the algorithm and type. The payload holds the claims, base64-encoded and readable, so never put a password there; the defaults include the token type, expiry, issued-at, a unique id and the user id. The signature is an HMAC over header and payload with the server key, so tampering fails verification.

{
  "token_type": "access",
  "exp": 1725828000,
  "iat": 1725824400,
  "jti": "a3f1c9...",
  "user_id": 1
}

The expiry is read by the client for a local guess, the unique id is what a blocklist keys on, and the user id is who you are.

A JWT is stateless: no session on the server, only a signature check, which suits multiple workers that share nothing. The price is that a token cannot be invalidated after issue without a blocklist.

Why a JWT here rather than sessions or OAuth

ApproachMultiple workersCross-originRevocationFits
Server sessions with cookiesNeeds shared session storageThird-party cookies are increasingly blockedDelete the session, easiestSame-origin, tightly controlled admin
Dual JWTStateless, any worker verifiesA header, no cookies, no problemHard by default, needs a blocklist or a versionSeparate front end, mobile, serverless
OAuth with a providerSame as JWTSame as JWTThe provider handles itThird-party login, no passwords to manage

A static site on one domain calling an API on another makes cookie-based sessions a permanent source of friction, and the header approach pairs once and works everywhere. Add statelessness across workers and reuse in a mobile app and the choice makes itself.

Why an hour and a day: too short an access token means constant renewal while writing, which fails on weak networks; too long and it becomes a single token in disguise. A day of refresh matches a daily visit, and anonymous readers never need one at all. For a personal blog, thirty to sixty minutes and one to seven days is a reasonable range; a heavily used admin can use fifteen minutes and eight hours.

Two endpoints issue every token in the system: one takes credentials and returns a pair, the other takes a refresh and returns an access, plus a new refresh once rotation is enabled.

The distinction between 401 and 403 drives the interceptor: 401 means the server does not know who you are, which is worth a refresh; 403 means it knows and refuses, which a refresh cannot fix.

Five curl commands for the whole lifecycle

# log in and receive both tokens
curl -s -X POST https://example.com/api/token/ \
  -H "Content-Type: application/json" \

# call an admin endpoint with the access token
curl -s https://example.com/api/admin/stats/ \

# without one: 401
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/api/admin/stats/

# exchange the refresh for a new access
curl -s -X POST https://example.com/api/token/refresh/ \
  -H "Content-Type: application/json" -d "{\"refresh\":\"$R\"}"

# tamper with one character of the payload: 401, signature mismatch

The gap nobody notices: the login endpoint has no rate limit

Auditing this blog turned up a real hole. Five throttle scopes were configured, and the two token endpoints used the default views with no throttle class at all, which means unlimited password attempts against a username that is easy to guess.

class LoginThrottle(AnonRateThrottle):
    scope = "login"  # '5/minute'

class RefreshThrottle(AnonRateThrottle):
    scope = "refresh"  # '30/minute'

urlpatterns = [
    path("api/token/", TokenObtainPairView.as_view(throttle_classes=[LoginThrottle])),
    path("api/token/refresh/", TokenRefreshView.as_view(throttle_classes=[RefreshThrottle])),
]

Five a minute is generous for a person and useless for a dictionary attack, while thirty a minute on refresh tolerates several tabs renewing at once. Something stronger such as an account lockout library is available, but for a small blog the limiter is the right first step.

On the client, answer both 401 and 429 with the same message, so a guesser learns nothing about which usernames exist, and disable the button for a few seconds after a failure.

Where to store the tokens

StorageXSS can read itCSRF affects itSurvives reloadFits
localStorageYesNo, the header is manualYesA single-admin SPA
HttpOnly cookieNoYes, needs SameSite and CSRF tokensYesHigher-security products
Memory onlyNothing to stealNoNo, a reload logs outMaximum security, poor experience

This blog uses local storage with a local expiry check, on three mitigations. Article HTML is sanitised through a whitelist and a content policy, so injection is cut off first. The only privileged account is the author, with no bulk user data to exfiltrate. And an access token is useless after an hour.

With real user data or payments, use HttpOnly cookies with a strict same-site policy and CSRF protection instead. Security is a trade, not a talisman.

On naming: avoid generic keys that collide with other libraries, and store the expiry as a millisecond timestamp so it is visible in developer tools.

class CookieJWTAuthentication(JWTAuthentication):
    def authenticate(self, request):
        token = request.COOKIES.get("access")
        if not token:
            return None
        validated = self.get_validated_token(token)
        return self.get_user(validated), validated

The price is that CSRF returns, because cookies travel automatically, so the same-site flags, the CSRF middleware and a header from the client all become mandatory. Choose by threat model rather than by fashion.

Login, and the local expiry guess

function parseJwtPayload(token) {
  try {
    const base64 = token.split('.')[1].replace(/-/g, '+').replace(/_/g, '/')
    return JSON.parse(atob(base64))
  } catch { return null }
}

function getStoredToken() {
  const token = localStorage.getItem('token')
  const expiry = localStorage.getItem('token_expiry')
  if (token && expiry && Date.now() >= parseInt(expiry, 10)) {
    localStorage.removeItem('token')
    localStorage.removeItem('token_expiry')
    localStorage.removeItem('user')
    return null
  }
  return token || null
}

Two details. Parsing the stored user is wrapped in a try, because a hand-edited or stale value once white-screened the whole app. And the local expiry check means an expired token is treated as no token, saving a round trip that would only return 401.

Remember me, custom claims, and revoking everything

Remember-me is a checkbox that requests a longer refresh lifetime from a second login endpoint, with the client passing the choice through. Sessions solved this with a cookie age; tokens solve it with a different lifetime at issue.

class MyTokenSerializer(TokenObtainPairSerializer):
    @classmethod
    def get_token(cls, user):
        token = super().get_token(user)
        token["username"] = user.username
        token["is_staff"] = user.is_staff
        token["tv"] = getattr(user, "token_version", 0)
        return token

Claims like these save a call to fetch the current user, but remember the payload is readable, so only non-sensitive display fields belong there.

For revocation, add a version column to the user, put it in the token, and compare on every request: a mismatch returns 401. Bumping the version on a password change invalidates every access and refresh token at once, which is far cheaper than blocklisting them one by one. A blocklist revokes a single token, a version revokes all of them, and the two complement each other.

Automatic renewal: the sixty lines that matter

client.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

Without single-flight, saving a long article with five concurrent requests produces five 401s and five refresh calls, and the last four may fail once rotation is enabled because the refresh they hold has already been consumed. One shared promise fixes it.

let refreshInFlight = null

async function refreshAccessToken() {
  if (refreshInFlight) return refreshInFlight

  const refresh = localStorage.getItem('refresh_token')
  if (!refresh) throw new Error('No refresh token')

  refreshInFlight = axios
    .post(`${client.defaults.baseURL}token/refresh/`,
      { refresh },
      { timeout: 15000, _skipRefresh: true })
    .then((res) => {
      const { access, refresh: newRefresh } = res.data || {}
      if (!access) throw new Error('No access token in refresh response')
      localStorage.setItem('token', access)
      if (newRefresh) localStorage.setItem('refresh_token', newRefresh)
      const payload = JSON.parse(atob(access.split('.')[1].replace(/-/g, '+').replace(/_/g, '/')))
      if (payload?.exp) localStorage.setItem('token_expiry', String(payload.exp * 1000))
      return access
    })
    .finally(() => {
      setTimeout(() => { refreshInFlight = null }, 0)
    })

  return refreshInFlight
}

client.interceptors.response.use(
  (response) => response,
  async (error) => {
    const status = error.response?.status
    const original = error.config || {}
    if (status !== 401) return Promise.reject(error)

    const url = original.url || ''
    if (url.includes('/token/')) return Promise.reject(error)
    if (original._skipRefresh) return Promise.reject(error)
    if (original._retry) {
      clearAuth()
      if (window.location.pathname.startsWith('/admin')) window.location.href = '/admin'
      return Promise.reject(error)
    }

    const wasAuthenticated = !!original.headers?.Authorization
    if (wasAuthenticated && localStorage.getItem('refresh_token')) {
      original._retry = true
      try {
        const newToken = await refreshAccessToken()
        original.headers.Authorization = `Bearer ${newToken}`
        return client(original)
      } catch (refreshErr) {
        clearAuth()
        if ((original.url || '').includes('/admin/')) window.location.href = '/admin'
        return Promise.reject(refreshErr)
      }
    }
    return Promise.reject(error)
  },
)

Four guards, all of them necessary. The refresh call itself is never refreshed, or a failure recurses. A retried request is not retried again, or a dead refresh loops forever. An anonymous 401 leaves the session alone, because a public endpoint failing once must not log the admin out. And a 401 from the token endpoints is a wrong password, not an expired session.

The router guard

router.beforeEach(async (to, from, next) => {
  if (!to.meta.requiresAuth) return next()
  const authStore = useAuthStore()
  authStore.checkAuth()
  if (authStore.isAuthenticated) return next()

  try {
    await refreshAccessToken()
    authStore.checkAuth()
    if (authStore.isAuthenticated) return next()
  } catch { /* fall through */ }
  next({ name: 'AdminLogin' })
})

Without this, opening the dashboard directly after the access token expires bounces the user before any API call happens. The guard tries a refresh first. And it reuses the same function the client uses: two implementations once diverged and produced a bug.

Logout, and the holes around it

Clearing local storage only clears this browser. The refresh token stays valid for its remaining lifetime, so anyone holding a copy can still mint access tokens, and the stateless server has no idea you logged out. Acceptable for a single-author blog, not for anything with users.

Two things are possible without touching the backend: shorten the refresh lifetime, and be honest that logging out clears this device only. Claiming "signed out of all devices" without a blocklist is a lie.

The real fix is rotation plus a blocklist.

SIMPLE_JWT = {
    'ACCESS_TOKEN_LIFETIME': timedelta(minutes=60),
    'REFRESH_TOKEN_LIFETIME': timedelta(days=1),
    'ROTATE_REFRESH_TOKENS': True,
    'BLACKLIST_AFTER_ROTATION': True,
    'AUTH_HEADER_TYPES': ('Bearer',),
}

With rotation, each refresh returns a new pair and the used one is blacklisted, so replaying it fails. The client was already written to store a new refresh when one arrives, so enabling this needs no front-end change.

@api_view(["POST"])
@permission_classes([IsAuthenticated])
def logout(request):
    refresh = request.data.get("refresh")
    if not refresh:
        return Response({"detail": "refresh required"}, status=400)
    try:
        RefreshToken(refresh).blacklist()
    except Exception:
        pass
    return Response({"detail": "logged out"})

The client calls that endpoint first and clears storage regardless of the result. Only after this is "log out" honest.

Debugging, and eight traps

Set the access lifetime to a minute locally and the chain becomes visible in the network tab: a 401, a refresh, and the retried request succeeding a few hundred milliseconds later, which is the whole evidence for single-flight plus retry.

  1. The authorization header never arrives. Cross-origin configuration did not allow the header; check that the allowed headers include it.
  2. The scheme is wrong. The client must send the exact scheme the backend expects.
  3. An access token sent to the refresh endpoint. It wants a refresh; the keys differ.
  4. Refresh reuse after rotation. The old token is dead, so concurrent refreshes without single-flight mostly fail.
  5. Clock drift. The expiry is signed by the server and compared with the client's clock, so a few minutes of drift makes the two disagree. The local check is an optimisation; the 401 is the truth.
  6. Secure cookies over local HTTP. Once cookies are in play, a secure flag breaks local development; expect it and configure around it.
  7. Malformed JSON in storage. Parsing a corrupted value throws during store initialisation and white-screens the app.
  8. An anonymous 401 treated as a session expiry. A transient failure on a public endpoint must not clear the session, which is why the interceptor checks both that the request was authenticated and that it targeted admin routes.

Checklist

Backend.

  • Access of thirty to sixty minutes and refresh of one to seven days, with a non-default secret in production.
  • Both token endpoints reachable and the header scheme identical on both sides.
  • Login limited to a handful per minute and refresh to a looser but still bounded rate.
  • Reads open, writes restricted, and the 401 versus 403 distinction preserved.
  • Only the JSON renderer in production, to avoid leaking detail in error responses.
  • HTTPS with HSTS, and exact allowed origins rather than a wildcard.
  • Optionally rotation with a blocklist and a logout endpoint.
  • Optionally a token version for revoking everything at once.
  • Failed logins logged, with an alert on a burst of throttled attempts.

Frontend.

  • Store access, refresh and the expiry timestamp at login.
  • Attach the bearer header, or enable credentials instead in cookie mode.
  • Refresh on 401 with single-flight, a single retry, and the recursion guard.
  • Never refresh a token endpoint failure, and never clear a session on an anonymous 401.
  • Try a refresh in the route guard before redirecting.
  • Clear all four keys on logout, after calling the logout endpoint when a blocklist exists.
  • Survive malformed stored JSON without white-screening.
  • Synchronise logout across tabs with a storage listener.
  • Keep editor drafts locally with a restore prompt.
  • Cool the login button down and use a neutral error message.
  • Clear storage by hand after using a shared machine.

Questions that come up

Does an expiring access token lose a long draft? No. The interceptor refreshes and replays the request, so the save succeeds a few hundred milliseconds later, and the local draft is a second safety net.

A week away with a one-day refresh? Log in again. Raise the lifetime, or offer a remember-me tier, if that is too often.

Is local storage really worse than a cookie? For anything with user data or payments, use cookies. For a single-author blog behind sanitisation with short tokens, local storage is an acceptable trade.

Why do tabs disagree? They do not, once a storage listener propagates logout.

Does changing a password invalidate old tokens? Not by default. Either blocklist them or bump a token version.

JWT or sessions? Separated origins and cross-domain calls favour tokens, a same-origin admin favours sessions for easy revocation, and third-party login adds OAuth on top.

Is putting a username in the token safe? The payload is readable, so only display fields belong there; anything sensitive is looked up server-side.

What if a refresh token is stolen? Rotation makes a used token dead, a short lifetime limits the window, and a version bump ends every session at once.

Does the login form need a captcha? A five-per-minute limit makes scripted guessing useless; add a challenge only if someone targets you.

What about clock drift? The local expiry check is only an optimisation; the server's 401 is authoritative.

Where do mobile apps store tokens? The platform keychain rather than plain application storage, with the same renewal logic.

Can a refresh still be used after logout? Without a blocklist, yes, for its remaining lifetime. That is what the logout endpoint is for.

How does the client tell 401 from 403? Refresh on the first, show a permission message on the second.

Why does it work in a REST client but fail in the browser? A REST client skips cross-origin checks; verify the allowed origins and that the authorization header is permitted.

How should the secret be managed? An environment variable, never committed, because losing it means every token must be reissued.

On the front end, three cases are worth pinning: five concurrent 401s produce one refresh, a 401 from the token endpoint does not trigger a refresh, and an anonymous 401 clears nothing.

Closing

Three sentences. The access token does the work and lives briefly; the refresh token waits and lives long; expiry renews itself. The hard parts are never the two lifetimes but the concurrency of renewal, the edge cases around anonymous failures, the honesty of logout, and the rate limit on the door.

Get those four right and the session stops randomly dropping and starts lasting quietly.
