MicroMD: a 3 MB single-file Markdown reader

2026-11-05 · 35 min · Stack Frame

Who this is for: Go and frontend developers building single-file Windows desktop apps; anyone weighing a WebView2 shell or planning to hand-write a Markdown parser; engineers who care about binary size, startup time, save semantics and the security boundary.

TL;DR: MicroMD fits a 3.17 MiB exe, a dependency-free HTML interface and a hand-written Markdown parser into one process. The small size isn't the interesting part. Four trade-offs are: leaning on the system WebView2, hosting the UI on file://, connecting native and JavaScript with exactly three bindings, and a two-pass parser that protects both escaping and placeholders. Seven problems remain open, each with its cost spelled out below.

Reading time around 30 minutes. Level: advanced.

Why build another Markdown reader

A 3 MB single-file Markdown reader sounds like compressing something that was never big. Markdown isn't the hard part. A parser for headings, lists and tables can be short. The hard part is the Windows desktop shell: windows, DPI, icons, the WebView2 runtime, file permissions, and the distribution problem behind "double-click and it works".

MicroMD answers by externalizing as much cost as possible. No bundled rendering engine, just the system WebView2. No UI framework, just one HTML file. No Markdown library, just a hand-written parser of a couple hundred lines of JavaScript. The native layer stays down to window creation, three bindings and argument parsing. The result is one exe, unzip and run, writing only to its own app-data directory, installing no service and needing no network.

Boundaries first, though. It isn't cross-platform. Heavy Win32 usage and the WebView2 dependency pin it to Windows 10 and 11. It isn't a complete editor either: no syntax highlighting, no sidebar outline, no file watching, no recent-file list. Those aren't roadmap items. They are the current state.

Get the size right too. The stripped release build is 3,323,392 bytes, meaning 3.17 MiB or about 3.32 MB decimal. Unstripped, it is 4,943,872 bytes, so -s -w saves 32.8%. "3 MB" in the title describes an order of magnitude, not an exact 3.00 MB.

This post follows the implementation order: the shell and the disk writes, then the three bindings and the parser, then the seven exposed problems one at a time.

One exe and its native shell

What is actually inside? No Chromium is bundled, so "3 MB" means 3 MB of shell plus an engine that is already on the system. It doesn't mean a 3 MB browser. The shell has five layers.

LayerImplementationVerified fact
Native shellGo plus github.com/jchv/go-webview2Three direct Go modules, all three mislabeled // indirect in go.mod
InterfaceA single web/index.html29,520 bytes, zero JavaScript libraries
Rendering engineMicrosoft Edge WebView2, installed by the systemNot shipped with the exe
Icon and version resourceA .syso file produced by go-winresThe .syso is gitignored. Skip generating it locally and the app has no icon
Packaging//go:embedmain.go:18 compiles the HTML into the binary

The native entry point is short. main.go initializes DPI, computes the app-data directory, writes the embedded HTML to disk, parses command-line arguments, then creates a window and calls Run(). The window comes from webview2.NewWithOptions with only a few parameters: title MicroMD, size from windowSize(), IconId: 1, Center: true, and DataPath pointing at %LOCALAPPDATA%\\MicroMD\\webview. Debug: false turns off the default context menu and DevTools, which makes this a release configuration rather than a development one. Window style comes from go-webview2's defaults. The comment says WS_OVERLAPPEDWINDOW, so there is no custom title bar and no native menu bar. Appearance is entirely the system's.

That choice saves work and hard-codes limits. Without a custom title bar there is no drag region of your own, and no window shadow to adapt. Without a menu bar, every action has to live in HTML buttons and keyboard shortcuts. Pointing DataPath at the app directory keeps the WebView2 cache, cookies and localStorage inside %LOCALAPPDATA%\\MicroMD\\webview, so it never pollutes another browser profile and uninstalling is deleting a directory. The cost is that this directory grows with use and nothing cleans it up.

One easily missed detail: when NewWithOptions returns nil, main calls openExternal(page) to open the same page in the default browser, then returns. That path is the fallback for a missing WebView2 runtime and gets its own section later. Note that not every initialization failure returns nil. Some error paths inside go-webview2 call log.Fatal directly, so the fallback covers window creation failure, not all startup failures.

Why the interface is written to disk first

//go:embed web/index.html compiles the 29,520-byte interface into the binary. The code then doesn't call NavigateToString. It writes the file out and navigates with file://. Startup order:

  1. appDataDir() reads LOCALAPPDATA and builds %LOCALAPPDATA%\\MicroMD. On failure it falls back to os.UserCacheDir(), then to the relative path MicroMD.
  2. Append app\\index.html and call os.MkdirAll(appDir, 0o755).
  3. Read the existing file and compare it with indexHTML. Only on a read failure or a difference does it call os.WriteFile(page, indexHTML, 0o644).
  4. Call view.Navigate(fileURL(page)), where fileURL uses net/url for drive letters, slashes and escaping.

Why not navigate from a string? The benefits are observable. The page gets a stable file:// origin, which is what lets localStorage persist per origin. <input type="file">, the File System Access API and relative resource resolution all behave like they do on an ordinary page. And there is no custom scheme to register and no local HTTP server.

That last point matters most. A local port brings port conflicts, firewall prompts and the "is this thing online?" question, while one of the project's selling points is that rendering is entirely local.

The write policy is "rewrite only when the bytes differ", not every launch. The good part: upgrades update the UI, and a normal launch costs one 29,520-byte read. The bad part: if a user hand-edits %LOCALAPPDATA%\\MicroMD\\app\\index.html, the next launch overwrites it. There is no "use an external UI" switch, deliberately.

Two silent failure points sit on this path. A MkdirAll failure returns immediately, and so does a WriteFile failure. Neither shows a dialog, so the user sees "double-click does nothing". Under normal permissions this almost never happens. With an antivirus lock, a full disk or an unwritable LOCALAPPDATA, there is nothing to diagnose from. That's the direct cost of one file and no installer: no setup program checks directory permissions for you.

Three bindings and the meaning of "save"

Native and JavaScript share exactly three bindings, all plainly named.

BindingNative behaviorReturn
micromdLoadIf a file path came on the command line, read it and json.Marshal it into {name, content}Empty string when there is no file
micromdSaveIf docPath is non-empty, os.WriteFile it backok on success, the error no file without a path
micromdOpenExternalAccept only http://, https:// and mailto: prefixes, then call ShellExecuteWok when accepted, empty otherwise

micromdLoad is economical. It returns no path, only a filename and content. The frontend sets app.native = true when it receives JSON, so Ctrl+S calls micromdSave. micromdSave takes no path argument and honors only the docPath parsed at startup. When the frontend calls it with no native file, the native side rejects it with no file, which is one layer of defense.

The real semantic fork is in the frontend. native is true in exactly one case: a file path on the command line, or a .md dropped on the exe icon, which Windows also presents as an argument. Every other way of opening a document goes through setDocument(file, handle), whose first act is app.native = false. Saving therefore has three paths.

  • A native file. micromdSave writes back to the original path and shows "saved to filename".
  • The file picker. If showOpenFilePicker exists, keep the FileSystemHandle and write through createWritable(). The toast says "saved to handle.name".
  • A file dropped into the window or loaded through the <input type="file"> fallback. There is neither a native path nor a writable handle, so saving degrades to a Blob download and says "exported filename".

The downgrade is explicit in saveFile().

if (app.native && typeof window.micromdSave === 'function') {
  await window.micromdSave(content);
  return;
}
if (app.handle && app.handle.createWritable) {
  const writable = await app.handle.createWritable();
  await writable.write(content);
  await writable.close();
  return;
}
const link = document.createElement('a');
link.href = URL.createObjectURL(new Blob([content], { type: 'text/markdown;charset=utf-8' }));
link.download = app.name || 'untitled.md';
link.click();

One detail deserves credit. setDocument resets native every time a new file is opened. Open A.md from the command line and the native docPath points at A. Then open B.md through the picker. Without the reset, Ctrl+S could write B's content into A. The code ties "can this document be written natively" to "which document this is", which avoids the most dangerous class of mis-write.

The cost is three meanings for one shortcut. The same Ctrl+S means "overwrite the original", "overwrite the picker file" or "download a copy", depending on how the document was opened. The README documents the rules. The UI distinguishes only "saved" from "exported" in a toast, and never warns at open time that this file won't be written back. That's not an implementation error but a gap between the safety model and user expectation, covered below.

A hand-written parser: two passes and a block state machine

The parser sits between /* md:start */ and /* md:end */ in web/index.html, roughly lines 166 to 412. No marked, no markdown-it. It implements inline() and blocks() itself. The interesting part is inline()'s two-pass design, because it solves two seemingly contradictory problems at once: Markdown syntax must still be recognized, and the source must never inject HTML.

The first pass isn't parsing but hiding. Code spans, autolinks and backslash escapes are replaced with placeholders of the form \\u0001 plus a number plus \\u0001, and the matching HTML goes into a stash array.

const stash = [];
const put = (html) => '\\u0001' + (stash.push(html) - 1) + '\\u0001';
t = t.replace(/(`+)([\\s\\S]*?)\\1/g, (m, ticks, code) =>
  put('<code>' + esc(code.replace(/^ ([\\s\\S]*?) $/, '$1')) + '</code>'));
t = t.replace(/<((?:https?:\\/\\/|mailto:)[^\\s<>]+)>/g, (m, url) =>
  put('<a href="' + esc(url) + '">' + esc(url) + '</a>'));
t = t.replace(/\\\\([`*_{}\\[\\]()#+\\-.!>~|])/g, (m, ch) => put(esc(ch)));
t = esc(t);

The second pass escapes everything. &, <, > and " become entities. The third pass recognizes images, links, bare URLs and emphasis on the escaped text, then restores the placeholders.

The order is the point. Escape first and backticks inside code spans plus brackets inside links get mangled by entities, which breaks syntax recognition. Recognize first and the <a> and <img> you emitted get escaped as if they were user input. Placeholders move "HTML that must survive" out of the text temporarily, so esc only touches real user text, and put it back afterwards.

blocks() is a line-by-line state machine. It normalizes newlines and expands tabs to four spaces, then loops with priority dispatch: fenced code, horizontal rule, heading, blockquote, table, list, and finally a paragraph. Each block type has its own boundary rules.

  • Fenced code records the number of backticks or tildes. Only a closing line with the same character and at least the same length ends it. The body gets escaped wholesale, and the language becomes class="language-xxx".
  • Headings match ^ {0,3}(#{1,6}). The id strips tags and punctuation, then turns whitespace into hyphens. Repeated headings produce repeated ids.
  • Blockquotes strip the > prefix from consecutive lines and recurse into blocks(), so lists and code fences work inside quotes.
  • Tables split the header row, read the separator row for alignment, and split body rows on \\| with a negative lookbehind, so escaped pipes aren't column boundaries.
  • Lists record the first item's indent and ordered or unordered type, absorb deeper-indented lines into the current item, and recurse blocks() per item, which is what makes nesting work. Task items match ^\\[([ xX])\\][ \\t]+ and render a disabled checkbox.

Paragraphs join consecutive non-blank lines with <br> rather than CommonMark's soft-break-to-space. That's a deliberate choice, not a bug. In a local reader, an author's line break usually means they want a visible break. It also means the output isn't strictly CommonMark, so the same Markdown copied elsewhere may have different paragraph shapes.

There is no syntax highlighting. class="language-xxx" is left for future or external styles, and no color rules exist. There is no sidebar outline either. Heading ids are generated, but nothing scans them into navigation. The block machine is line-oriented with no AST, so complex nesting, cross-line emphasis and extreme list and table combinations are covered by rules rather than automated tests. The repository contains no *_test.go, so parser quality rests on manual samples.

Security boundary: escape before parsing

The parse order is the first boundary. A <script>, an <iframe> or an onerror= in the source passes through esc and appears as text instead of entering the DOM. The second boundary is safeUrl(): before building an image or a link, it checks for javascript:, vbscript: or data:text/html prefixes, and on a hit it renders the original text escaped.

The third is click interception. Ordinary links and bare URLs in the preview carry target="_blank" and rel="noreferrer noopener". A capture-phase handler allows only http(s) and mailto, calls preventDefault(), then hands off to micromdOpenExternal. The native side applies the prefix allowlist again before ShellExecuteW. Debug: false removes DevTools and the context menu, which narrows the ways to poke at the page from inside the app.

These layers block ordinary script injection, with two caveats worth stating. First, remote images aren't disabled. An https:// image in the Markdown will still be fetched. "Rendering is local, no network" means the app itself needs no network, not that remote resources inside a document never load. Second, safeUrl blocks only three dangerous schemes. Other schemes and relative paths pass through, and relative links under file:// resolve against the current page's base, which is exactly the image-path problem below. Note also that ordinary links and bare URLs get target and rel, while the angle-bracket autolink branch doesn't. It's still intercepted on click, and the real boundary remains the native allowlist.

Problem one: missing WebView2 and the browser fallback

Symptom. On a Windows machine without the WebView2 runtime, double-clicking the exe opens no app window. Instead the default browser opens showing what still looks like MicroMD, except "save" becomes a download and native write-back is gone. micromd.bat offers another route: try Edge, then Chrome, then the system default browser with --app on web/index.html.

Cause. The whole rendering layer depends on the system-installed WebView2 Runtime. Most Windows 10 and 11 installs have it. LTSC, slimmed images and some managed enterprise fleets may not. When window creation inside webview2.NewWithOptions fails, it returns nil and leaves main with openExternal(page) as the only fallback. In that mode typeof window.micromdLoad isn't a function, micromdSave doesn't exist, and saving degrades. The batch file also depends on web/index.html in the source tree, while the release ships only an exe, so it helps people who cloned the repository and not end users.

Fix. The native layer detects nil and opens the already-written page through ShellExecuteW. The README documents "no runtime, open it in a browser". The batch file tries Edge, Chrome, then the default browser to reuse whatever Chromium exists. The frontend needs no branch for these modes, because it already treats native bindings as optional.

Cost and leftovers. The two modes have different capabilities, and the UI gives almost no indication which one you are in. Browser mode has no native window, no icon, no direct write-back, and draft localStorage depends on the browser's file:// policy. The code never says "please install WebView2" and offers no install link. The fallback covers only window creation failure. Some initialization errors call log.Fatal inside the library, so the process exits silently. The essence of the problem: externalizing the engine buys size, and the price is a runtime you don't control.

Problem two: relative image paths resolve against the wrong base

Symptom. A document containing ![shot](images/shot.png) renders fine elsewhere and shows a broken image in MicroMD. The URL resolves to %LOCALAPPDATA%\\MicroMD\\app\\images\\shot.png instead of images\\shot.png next to the Markdown file.

Cause. The page is navigated from the app directory over file://, so the browser's relative base is the directory holding app/index.html. The parser puts src into <img> verbatim. No <base href="..."> is injected and no rewrite against the document path happens. The native binding returns only a filename and content, never a directory, so the frontend could not rewrite even if it wanted to. In command-line mode the native side knows docPath. It simply never passes it to the page.

Fix. Not fixed in the current version. Workarounds exist: absolute paths such as file:///C:/docs/images/shot.png, or images embedded as data:. Both pass safeUrl and load in WebView2. But absolute paths destroy portability and data: balloons the file, so neither is general.

Cost and leftovers. This is the direct side effect of writing the UI to disk. Fixing it means returning a directory from micromdLoad and rewriting relative src into absolute file:// URLs after render, or injecting a <base> computed from the document directory. The first has to handle URL encoding, drive letters, .. and mixed slashes. The second affects every relative URL on the page, links included.

Worse, dropping a file into the window and the file picker never expose a full path for security reasons, only a File object. The same document therefore behaves differently depending on how it was opened. That's why this stays a known limit rather than a fixed item.

Problem three: full re-render and large-file throttling

Symptom. Typing into a long document keeps the cursor moving while the preview stutters. The longer the document, the more obvious the lag. Scrolling sometimes desynchronizes preview and editor.

Cause. render() has one line of core logic: preview.innerHTML = MD.render(editor.value). Every keystroke re-parses the entire document and replaces the whole preview tree's HTML string. No incremental parsing, no DOM diff, no worker. scheduleRender() only merges several keystrokes inside one frame via requestAnimationFrame. It merges call counts, not work. Parsing and layout still run on the main thread at full-document scale.

Fix. There is a threshold, BIG_DOC = 200000. Above 200k characters, scheduleRender() drops requestAnimationFrame for a 150 ms setTimeout, roughly six or seven renders per second. Below it, everything renders every frame. That's a very cheap degradation: no worker, no incrementality, just a coarser cadence.

Cost and leftovers. The threshold is character-based and doesn't map cleanly to parse cost. A 199k-character document still renders every frame. At 201k it suddenly slows, so the experience is discontinuous across the boundary. The 150 ms is fixed and doesn't adapt to document size or machine speed. On longer documents a single parse can exceed 150 ms, so throttling reduces frequency but not the length of each stall.

Replacing innerHTML also loses the preview selection, reloads images and changes scroll height abruptly. Scroll sync computes scrollTop proportionally and goes wrong when heights jump. A real fix needs incremental parsing, virtualized lists or at least a worker, and all of those raise code size and state-management cost, against the project's size goal.

Problem four: draft quota and an unused MAX_DRAFT

Symptom. The README claims "very long drafts aren't written to local storage", but MAX_DRAFT = 1000000 is declared and referenced nowhere. Actual behavior: every keystroke tries to write localStorage, failures are swallowed by try/catch, the UI says nothing, and the draft may already be gone when the window closes.

Cause. saveDraft() runs 400 ms after typing stops and calls store.set('draft', editor.value) and store.set('name', app.name). store.set is try { localStorage.setItem(...) } catch (e) {}, so quota errors, private-mode restrictions and serialization failures never surface. MAX_DRAFT was probably meant for a "skip when over the limit" branch that never got wired up.

localStorage quota is typically a few MB per origin depending on the browser and its file:// policy. Writing the whole document as one string over and over means setItem throws past the quota, and the draft freezes at the last successful version.

Fix. No real oversize protection exists, only "exceptions aren't fatal". Straightforward options: check editor.value.length > MAX_DRAFT in saveDraft(), skip and toast once; move drafts to IndexedDB; or, in native mode, write a draft file into the app directory. All three are more honest than an empty catch.

Cost and leftovers. Users are promised automatic draft saving and get best-effort saving. The 400 ms debounce resets on every keystroke, so a write happens only after a pause. Type for ten minutes and lose power, and everything since the last successful write is at risk. When a native file has unsaved changes, the draft is the only recovery path, which makes "opened from the command line, edited, never saved" the most dangerous scenario. That README sentence should be read as a current defect, not a shipped limit.

Problem five: size, icon and startup time

Symptom. The release exe is 3,323,392 bytes and 4,943,872 unstripped. An empty windowsgui Go program is 1,214,976 bytes. The embedded WebView2Loader.dll is about 134 KB. Window handle appearance measured 203 ms, 112 ms and 106 ms on this machine. And an exe built locally with plain go build has no custom icon.

Cause. Size has four parts: the Go runtime and link baseline, the code from go-webview2 and golang.org/x/sys, the 134 KB WebView2Loader, and the 29,520-byte HTML. -H windowsgui removes the console window and -s -w removes the symbol table and debug info. Together they take 4.94 MB down to 3.17 MiB, a 32.8% saving.

Icons aren't something Go code can carry directly. IconId: 1 only looks the icon up by resource id at window creation. The actual icon and version info are written by go-winres into rsrc_windows_amd64.syso, and that file is gitignored. CI installs go-winres and generates resources before building. Skip that locally and IconId: 1 finds nothing, so the window is missing its icon.

Fix. The build command is fixed at -trimpath -buildvcs=false -ldflags "-H windowsgui -s -w". The release workflow installs and generates go-winres output before building and fails if rsrc_windows_amd64.syso is missing. windowSize() clamps a 1280 by 860 request to 92% and 88% of the screen so small displays aren't overrun. DPI tries SetProcessDpiAwarenessContext(-4) first and falls back to SetProcessDpiAwareness(2). The icon itself is generated by tools/icon/main.go with a signed distance field and 4x supersampling, emitting sizes from 16 to 256 pixels with no external design file.

Cost and leftovers. -s -w strips symbols from the release binary, which makes crash diagnosis harder. Local builds gain a toolchain step: forget the .syso and you get "runs, but no icon", with no compile-time error.

The startup numbers measure "window handle appeared", not first frame and not finished rendering. After the window appears, WebView2 still creates its environment, navigates to file://, runs the boot script and reads the draft or native document. Calling 106 ms "startup complete" is inaccurate. It says the native window is created quickly.

Size is the same story. 3.17 MiB is what you get from not shipping an engine, not from compressing Chromium to 3 MB.

Problem six: save semantics versus user expectations

Symptom. Drop notes.md into the window, edit a few lines, press Ctrl+S. The toast says "exported notes.md" and the original is untouched. Drop it again and you still see the old content. Drop the same file onto the exe icon instead and Ctrl+S writes back to the original. The UI makes the difference hard to see.

Cause. The browser security model doesn't let a page write to an arbitrary path from a File object, and native is true only when a startup argument exists. Dropping into the window yields a File API File with no writable handle. The picker yields a FileSystemHandle through showOpenFilePicker, but setDocument still sets native = false and saving goes through the handle, not a native path. The code chose "safe by default": without an explicit native path it never guesses which file to overwrite, preferring to export a copy.

Fix. The three-level degradation covers three capabilities: native path, writable handle, Blob download. setDocument resets native to prevent cross-file writes, micromdSave rejects path-less calls natively, and toasts distinguish "saved to" from "exported". The implementation isn't wrong. It turns "can we write back" into a capability probe instead of a memory test for the user.

Cost and leftovers. The probe result isn't surfaced in advance. Nothing tells you on drop that this document will be saved by export, and you find out at Ctrl+S. There is no native "save as" dialog either. Once in the download branch, WebView2's download policy decides the location, usually the Downloads folder, with a duplicate for identical names.

The picker branch depends on the File System Access API, whose availability and permission prompts inside WebView2 vary by runtime. When it is unavailable, the app silently falls back to <input type="file"> with no handle at all. No extra branch closes this gap. The UI would have to show the save mode at open time, or expose a native "save as".

Problem seven: no file watching, no recent files

Symptom. Edit notes.md in another editor and MicroMD still shows the old content. Press Ctrl+S in native mode and the old content overwrites the external change with no conflict prompt. Close and reopen and there is no recent list, so you drag the file in again or retype the command.

Cause. The native layer reads the file once at startup through micromdLoad and then does nothing. No ReadDirectoryChangesW, no fsnotify, no mtime polling. Frontend state is app.name, app.saved, app.handle and app.native. localStorage holds only draft, name, theme, view and split, with no path history. There is no single-instance lock and no IPC either, so a second instance can't tell the first that the file changed.

Fix. No auto-reload and no conflict detection in this version. Workarounds are closing and reopening, re-dropping, or reopening through the picker. None of them warn that the on-disk version moved. The minimal addition would be native polling of docPath's mtime, notifying the page through a binding or Eval, and showing a bar offering "reload / keep current". The fuller version uses ReadDirectoryChangesW and handles rename, delete and atomic replace.

Cost and leftovers. Without watching, the boundary between reader and author disappears. As a pure reader that would be acceptable. But the app also edits and writes back, so stale content overwriting newer content is a real data risk. No recent files pushes the cost of opening onto the file system, which sits oddly with "double-click and it works".

Watching also introduces decisions. Auto-reload loses unsaved edits, a prompt interrupts reading, and saving needs an overwrite-versus-copy policy. Adding it carelessly would be more dangerous than not having it.

Known limits and design trade-offs

Pulling the scattered limits into one table, so you can judge whether this fits your use.

LimitCurrent stateImpact
Relative image pathsBase is the app directory; no <base>, no src rewriteImages beside the document don't display
Draft ceilingMAX_DRAFT declared but unused; quota errors swallowedVery long drafts may vanish silently
Large documentsFull innerHTML replacement; 150 ms throttle past 200k charactersTyping lags, scroll sync can drift
File changesNo watching, no polling, no conflict promptExternal edits can be overwritten
Recent filesNo path history; localStorage stores no pathEvery open requires reselecting
Syntax highlightingOnly a language-xxx class, no colorizerCode blocks are plain text
Outline sidebarHeading ids exist, no navigation generatedLong documents require scrolling
Parser testsNo *_test.go in the repositoryEdge-case syntax verified by hand
Local build iconDepends on go-winres output, which is gitignoredSkip generation and there is no icon
Startup failure messageMkdirAll and WriteFile failures return silentlyDouble-click does nothing in extreme environments

Most of these aren't oversights but "not done within the size and complexity budget". They group into four trade-offs.

  • Externalize the engine for size. No bundled Chromium, accepting a WebView2 dependency and two capability modes.
  • One file for engineering simplicity. UI, parser and styles in one HTML file, accepting no module split, no build step and no frontend tests.
  • Full render for short code. One innerHTML line works, accepting a performance ceiling on long documents.
  • Safe by default. No native path means no write-back, accepting three outcomes from one shortcut.

If work continues, data safety should outrank experience polish. Wire up the draft ceiling and handle external-change conflicts first, then consider incremental rendering and image bases. Highlighting and an outline are reading comfort and don't risk data loss, so they come later. That ordering is also why this post spends more words on the seven problems than on the features. Features can be added. Lost data can't.

Closing

MicroMD compresses into three sentences.

  1. Size isn't one optimization but a budget split. The 3.17 MiB exe is roughly a 1.21 MB empty windowsgui baseline, three Go modules, a 134 KB WebView2Loader, 29,520 bytes of HTML and link output. The Chromium that was omitted is supplied by the system WebView2.
  2. Shell complexity concentrates in Windows details. Writing to disk for file://, three bindings, save semantics, DPI fallback, icon resources and the runtime-missing fallback are each small, and each can break "double-click and it works".
  3. The hand-written parser's key is order, not syntax coverage. Hide code spans, autolinks and escapes in placeholders, escape everything, then restore. The two-pass design solves "syntax must be recognized" and "source must not inject" at once.

It isn't a finished product either. Relative images, draft quota, full re-render, file changes, recent files, highlighting, outline and parser tests are all missing or half-done. They are documented as current state because the value of a 3 MB single-file app isn't how small it is. It's what it cost to get there, and whether those costs are stated honestly.
