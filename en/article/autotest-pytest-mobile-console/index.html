AutoTest: turning pytest into a remotely driven mobile-automation console

2026-11-23 · 32 min · Stack Frame

Who this is for: engineers who have written pytest suites but never turned them into a service; people building internal tools, test platforms or device farms; anyone using Appium for Android automation and getting tired of adb, sessions and report formats.

TL;DR: AutoTest chains three roles into one remote pipeline. A developer laptop only picks scripts. A test server streams pytest stdout over Server-Sent Events. Every script gets its own pytest process. The whole batch sends exactly one summary email. The hard part is not making Appium click. It is four boundaries: interpreter discovery, single-batch mutual exclusion, sub-report merging, and report IDs plus mail de-duplication. This article walks through ten HTTP routes, four SSE events and three config tables, and then points at three latent bugs, five undeclared imports and one Stop button with no backend.

Reading time around 32 minutes. Level: advanced.

This is not a folder of pytest scripts

Most teams end up with the same kind of "automation" after a year: a tests/ directory with dozens of test_*.py files, one person running them on their own laptop, and a screenshot of the log pasted into a chat group. It finds bugs, but it is not a system, because nobody answers four questions:

  • Can someone launch a run without installing Python or plugging in a phone?
  • What happens when a second person clicks Run while the first batch is halfway through?
  • When ten scripts finish, where do I look, and which script does a failed log line belong to?
  • If three people click Run, how many emails land in the inbox?

AutoTest is an internal test platform that grew out of those four questions. Its size is modest: seven Vue components, a 25 KB server.js with ten routes, three test_*.py scripts in the test directory, and three PostgreSQL config tables. The complexity is not in the line count. It is in the boundaries: where the Python process comes from, how an SSE stream ends, how reports merge, how one email is sent instead of ten, and how configuration evolves without migrations.

Here is the thesis up front:

role            where it runs           responsibility

script author   anywhere                write tests/debug or tests/release

developer box   Vite :5173              scan local scripts, queue, show logs

test server     Node :3000              spawn pytest, write reports, mail, config

Of those three, the test server is the hard one. It has to turn one HTTP request into a controlled child process, then reassemble that child's output, files and exit code into something both humans and machines can read. Appium is only one part of that child process.

Two machines, one proxy: the topology

AutoTest splits the system into a developer box and a test server. The developer box needs no Python, no Appium, no Android SDK, and no phone. It runs a Vite frontend. The execution environment lives on the test server, addressed by AUTOTEST_REMOTE_SERVER:

+-------------------------+         +------------------------------+

|  developer box (:5173)  |  proxy  |  test server (Node :3000)    |

|  - scans local tests/   | ------> |  - runs pytest (SSE output)  |

|  - Testbed / config UI  |         |  - reads and writes reports/ |

|                         |         |  - PostgreSQL config         |

|                         |         |  - Pretest checks            |

+-------------------------+         +------------------------------+

The Vite proxy table is the load-bearing part. It keeps the script list local, and forwards execution, reports, config and environment checks to the remote host:

const REMOTE_SERVER =

  env.AUTOTEST_REMOTE_SERVER || process.env.AUTOTEST_REMOTE_SERVER || 'http://127.0.0.1:3000'



server: {

  proxy: {

    '/api/log': { target: REMOTE_SERVER, changeOrigin: true,

      rewrite: (p) => p.replace(/^\/api\/log/, '/log') },

    '/api/reports': { target: REMOTE_SERVER, changeOrigin: true },

    '/api/report': { target: REMOTE_SERVER, changeOrigin: true },

    '/run-tests-stream': { target: REMOTE_SERVER, changeOrigin: true },

    '/stop-tests': { target: REMOTE_SERVER, changeOrigin: true },

    '/api/pretest': { target: REMOTE_SERVER, changeOrigin: true },

    '/api/config': { target: REMOTE_SERVER, changeOrigin: true },

  },

  host: true,

  port: 5173,

}

Why split at all? Two reasons. The developer box is where scripts change all day, and requiring every author to install Appium, the Android SDK and a matching Python is an adoption tax. The test server is where the phone and the SDK live, and it is usually a fixed Windows machine with USB devices attached. Separating them also means a frontend deploy cannot break a running device session, and a driver crash cannot take down the UI. The cost is a second network hop and a proxy configuration that has to stay in sync with backend routes. For a team of five the trade is worth it; for a solo developer on one laptop, running both processes locally is also supported, because the default remote server is simply 127.0.0.1:3000.

One detail is easy to miss: /api/log needs its own rewrite and must sit before the broader rules. The backend route is /log; the frontend prefixes everything with /api for consistency. If a single /api rule caught it, the request would arrive as /api/log and 404. In Vite, proxy order is not decoration. It is routing.

The other detail is host: true. It makes Vite listen on the LAN, so a colleague can open http://192.168.x.x:5173 without installing a second set of Node dependencies. The price is that there is no authentication by default. That is section 27.

Deployment is worth one paragraph because it explains several defaults. The test server is typically a Windows machine on the office LAN, reached by IP rather than by hostname, because there is no DNS entry for a workstation. That is why the remote server is configured as a full URL, and why CORS is open: the page is served from a Vite origin and calls a different host. It is also why the backend binds 0.0.0.0, since binding loopback would make the LAN setup impossible. Every one of these choices is reasonable in isolation and dangerous in combination, which is the recurring theme of this article.

What the developer box actually does

The script list is not fetched from the remote host. A Vite middleware scans it locally:

function localScriptsPlugin() {

  return {

    name: 'local-scripts',

    configureServer(server) {

      server.middlewares.use('/api/scripts', (req, res, next) => {

        if (req.method !== 'GET') return next()

        const url = new URL(req.url || '/', 'http://localhost')

        const mode = url.searchParams.get('mode') === 'test' ? 'release' : 'debug'

        const dirPath = path.resolve(__dirname, '..', 'tests', mode)

        const files = fs.readdirSync(dirPath)

          .filter(f => f.startsWith('test_') && f.endsWith('.py'))

          .map(f => ({ name: f, path: path.join(dirPath, f) }))

        sendJson(res, 200, files)

      })

    }

  }

}

This has one clear benefit: a script author adds a new test_xxx.py, refreshes the console, and sees it, with no deployment to the test server. The same endpoint also exists inside server.js, with nearly identical logic but a different root. Keeping two implementations in sync is a human job; a shared module would be better. For a small internal tool, the duplication is survivable.

The Testbed interaction is deliberately narrow. The left panel lists scripts and supports search; typing a keyword and pressing Enter appends every match to the run queue. The right panel is a draggable table; its order is the execution order, because server.js iterates the scripts parameter in order. Debug and Test map to tests/debug and tests/release. The top bar has exactly six actions: run, stop, Pretest, results, live report, and three config pages.

Run ultimately does one thing: it builds an EventSource URL.

const params = new URLSearchParams()

params.set('mode', mode.value)

params.set('scripts', selectedScripts.value.map(s => s.name).join(','))

evtSource = new EventSource(`/run-tests-stream?${params.toString()}`)



evtSource.addEventListener('stdout', e => appendStreamLine(e.data))

evtSource.addEventListener('stderr', e => appendStreamLine(e.data))

evtSource.addEventListener('report', e => { /* remember reportId */ })

evtSource.addEventListener('close', e => { /* finish */ })

The queue sends file names, not paths and not objects. That is a small but important decision. Objects stringify to [object Object] in a URL. Absolute paths would hand the server an arbitrary file read. Accepting only names that match test_*.py is a protocol-level allowlist.

The queue deserves a note because it is the only place where human intent becomes execution order. Dragging a smoke test above a long stress loop is a meaningful action: if the smoke test fails, the stress loop still runs, because the server does not short-circuit on failure. That is deliberate for data collection, but it surprises people who expect fail-fast. A future version could expose a "stop on first failure" switch; today the ordering is the only control. The search-to-queue shortcut has the same property: it appends every match, so a broad keyword can queue twenty scripts by accident. A confirmation with the match count would be a small but worthwhile improvement.

The test server: turning HTTP into processes

server.js is a single-file Express service with very few dependencies: express, cors, pg, tcp-port-used, and Node's built-in child_process, fs and readline. It implements ten routes:

MethodPathPurpose
GET/api/scripts?mode=debug|testRemote script list, mirroring the local middleware
GET/run-tests-streamSSE test execution
GET/api/reportsReport list with running/finished status
GET/api/report/:reportIdOne merged report
GET/log?reportId=&nodeid=One test case and its log
GET/POST/api/config?table=Read/write the three config tables
GET/api/pretestDatabase, Appium, Python checks
POST/api/pretest/installInstall missing pip packages
GET/test-results-jsonLegacy overview file (historical)

There is no /stop-tests in that table, although the frontend posts to it. Section 26 is about that gap.

Functionally the service does three things. It delegates config reads and writes to PostgreSQL and keeps no business state itself. It turns one run into N child processes and turns their stdout/stderr into SSE events. It merges each child's pytest JSON report into a batch report, and triggers one email at the end.

There is no queue, no task table and no worker. Batch state lives in one boolean and one directory on disk. That is what makes it simple, and also what makes it fragile.

Four SSE events and one batch timeline

/run-tests-stream is the only long-lived connection in the system. It writes SSE headers, then does five things in order. First it allocates an ID and a directory. Then it writes an empty report shell so the live page can open immediately:

res.setHeader('Content-Type', 'text/event-stream')

res.setHeader('Cache-Control', 'no-cache')

res.setHeader('Connection', 'keep-alive')



reportId = generateDailyId()

reportDir = path.join(REPORTS_BASE, reportId)

fs.mkdirSync(reportDir, { recursive: true })



fs.writeFileSync(reportFile, JSON.stringify({

  tests: [], collectors: [], summary: {},

  status: 'running', created: now, updatedAt: now,

  duration: 0, exitcode: 0, root: __dirname, environment: {},

}, null, 2))



res.write(`event: report\ndata: ${JSON.stringify({ reportId, status: 'running' })}\n\n`)

After that, every script starts independently. The loop is a forEach, not an await chain, so scripts run concurrently. There are only four event types:

EventPayloadConsumer
report{ reportId, status }Frontend stores the ID and can open the live report
stdout{ script, line, type }Console appends the line
stderr{ script, line, type }Console appends the line; busy/init errors also use this
close{ script, code, reportId, label } or { code, message }One script finished, or the whole batch failed to start

The batch does not send one final close. Each script sends its own. Only when the remaining counter reaches zero does the server finish the report, send mail and release the lock:

scriptsRemaining -= 1

if (scriptsRemaining === 0) {

  markReportFinished(reportFile, batchMailExit)

  spawnFinishMail(batchMailExit)

  runTestsStreamBusy = false

}

The frontend's onerror handling deserves a note. EventSource can fire onerror on a normal stream close, so the handler checks running first. Without that check, every successful run ends with a red "connection lost" message. Small detail, but it is the difference between a tool that feels finished and one that feels broken.

SSE rather than WebSocket or polling is a deliberate fit. The traffic is one-directional: server to browser. There is no message from the client after the run starts, except the separate stop request. SSE reconnects automatically, carries a simple text framing, and travels through the same proxy as normal HTTP. Polling would require a job ID and a cursor, plus a store for partial output; WebSocket would add a second protocol and a connection lifecycle for no benefit. The limitation is that SSE is one stream per run, so a second tab cannot attach to the same run. The live report page solves that by reading the JSON file instead of the stream, which is why it can be opened after the fact, or from a link in an email.

Why every script gets its own pytest process

The natural shortcut is to pass all selected scripts to one pytest invocation: pytest -v a.py b.py c.py --json-report. AutoTest does not do that. Every script gets a process:

const proc = spawnPythonModule(

  'pytest',

  ['-v', scriptPath, '--json-report', `--json-report-file=${subReportFile}`],

  { env: spawnEnvWithPython(deferMailEnv), cwd: AUTOTEST_ROOT,

    stdio: ['ignore', 'pipe', 'pipe'] }

)

There are three reasons. The first is crash isolation. Appium tests regularly drive a session into an unusable state; one script killing the driver must not fail every later script. A separate process means a segfault, a sys.exit or an interpreter crash only takes down its own script.

The second is fixture isolation. app_driver is module-scoped, so one pytest process reuses it. Ten scripts in one process would inherit the first script's Appium session, or need explicit teardown between files. A process per script forces a fresh initialisation, so state cannot leak.

The third is natural report sharding. Each script writes its own <script>.json. A failure loses one shard, not the batch. The server merges by nodeid afterwards.

The cost is explicit: every script re-imports, restarts the Appium session, and pays startup N times. For short scripts, startup can exceed test time. AutoTest chooses diagnosability over total wall time, which is a reasonable trade for an internal platform.

There is also a hidden cost. Because each script is a separate process, pytest_sessionfinish runs N times, and by default it sends mail. That leads directly to the batch-mail problem.

The startup cost is not theoretical. On a Windows machine with Appium 1.x, creating a session can take five to fifteen seconds depending on the device and the app. If a script itself only checks one screen, the session dominates. A team with many tiny scripts should either group them into one file with multiple test functions, or add a batch mode that passes several files to one pytest process and accepts the shared-session trade. AutoTest chooses the opposite default because its scripts are long stress loops, where session startup is noise. The right default depends on the shape of the suite, not on ideology.

Single-batch exclusion: one boolean against four races

One unremarkable variable in server.js does a lot of work:

/** Prevent two /run-tests-stream batches from overlapping

 *  (races on .daily_counter, report dirs, and mail config reads). */

let runTestsStreamBusy = false

It blocks four distinct races, not one. Two batches arriving together can read-modify-write .daily_counter.json and allocate the same report ID, so the second overwrites the first directory. They can create and merge report files in the same directory at the same time. One batch can be reading test_config for mail while an admin changes the recipient. And two batches can each try to start Appium on port 4723, with the second killing the first.

The implementation fails fast instead of queueing:

if (runTestsStreamBusy) {

  res.write(`event: stderr\ndata: ${JSON.stringify({

    line: 'A batch is already running; wait for it to finish.', type: 'busy'

  })}\n\n`)

  res.write(`event: close\ndata: ${JSON.stringify({ code: -2, message: 'busy' })}\n\n`)

  return res.end()

}

runTestsStreamBusy = true

That choice is defensible for humans. "A batch is already running" is more useful than silently queueing a second run whose start time nobody knows. But the lock is in-process. If server.js runs under pm2 with two instances, or behind a multi-worker proxy, the lock does not exist. The correct upgrade is a file lock or a PostgreSQL advisory lock. For a single-instance LAN tool the boolean is enough; for anything horizontally scaled it is not.

Finding Python: five fallbacks from file to PATH

This is the least elegant and most useful part of the project. A Node process's PATH often differs from the user's shell. The fact that python works in a terminal does not mean a child process of node server.js can find it. AutoTest tries five levels:

1. configs/python_path.txt        first non-comment line

2. AUTOTEST_PYTHON                environment variable

3. where python / python3         PATH

4. py -3                          Windows launcher

5. scan LOCALAPPDATA / Program Files Python installs

The order matters less than the fact that every candidate is actually executed:

function verifyPythonExe(exe) {

  if (!exe || !fs.existsSync(exe)) return false

  const r = spawnSync(exe, ['-c', 'import sys; print(sys.executable)'], {

    encoding: 'utf8', env: PYTHON_ENV_FOR_AUTOTEST, timeout: 20000,

    windowsHide: true,

  })

  return r.status === 0

}

fs.existsSync proves a file exists, not that it runs. A broken venv, an interpreter behind a licence check, or an exe locked by antivirus will only fail at the real spawn. Running -c "import sys" early moves the failure from "while running tests" to "while starting the server".

After finding the interpreter, the surrounding PATH has to be repaired too. The child needs pip and, later, appium:

function spawnEnvWithPython(baseEnv) {

  const env = { ...baseEnv }

  const { cmd } = resolvePythonLaunch()

  if (cmd.toLowerCase().endsWith('.exe')) {

    const dir = path.dirname(cmd)

    const scripts = path.join(dir, 'Scripts')

    env.PATH = `${dir}${path.delimiter}${env.PATH || ''}`

    if (fs.existsSync(scripts)) {

      env.PATH = `${scripts}${path.delimiter}${env.PATH}`

    }

  }

  return env

}

Why is this necessary? python.exe, pip.exe and appium.cmd usually live in different directories, and a child shell command needs to resolve the global npm directory. AutoTest prepends both the interpreter directory and Scripts, then uses python -m pip rather than bare pip to avoid PATH ambiguity entirely.

One more global matters:

const PYTHON_ENV_FOR_AUTOTEST = withAndroidSdkEnv({

  ...process.env,

  PYTHONUNBUFFERED: '1',

  PYTHONIOENCODING: 'utf-8',

  PYTHONPATH: [AUTOTEST_ROOT, process.env.PYTHONPATH || ''].join(path.delimiter),

})

PYTHONUNBUFFERED=1 is the precondition for streaming. Without it, pytest's stdout sits in a buffer until a few kilobytes accumulate, and the user sees a long pause followed by a wall of text. PYTHONPATH is what lets python -m core.finish_report_mail import a package from the project root.

Virtual environments add one more trap. A common setup is a project venv for pytest and a global npm install for Appium. If configs/python_path.txt points at the venv, python -m pip installs into the venv, which is correct, but appium is still resolved from the global npm directory. If someone points at the system Python instead, packages install somewhere else and the next run cannot import them. The Pretest install endpoint makes this worse because it uses the same resolved interpreter but gives no feedback about which environment it modified. Printing sys.executable and sys.prefix in the Pretest result would remove most of the confusion.

Report directories and IDs: looks daily, is global

The ID format is YYYYMMDD-NNNNNN, for example 20260520-000084. It looks like "reset to 1 every day". It is not:

const COUNTER_FILE = path.join(REPORTS_BASE, '.daily_counter.json')



function generateDailyId() {

  const now = new Date()

  const ymd = `${now.getFullYear()}${String(now.getMonth() + 1).padStart(2, '0')}${String(now.getDate()).padStart(2, '0')}`



  let counter = 0

  if (fs.existsSync(COUNTER_FILE)) {

    counter = JSON.parse(fs.readFileSync(COUNTER_FILE, 'utf-8')).counter || 0

  }

  counter += 1

  fs.writeFileSync(COUNTER_FILE, JSON.stringify({ counter }, null, 2), 'utf-8')



  return `${ymd}-${String(counter).padStart(6, '0')}`

}

Both the variable and the file say daily, but the counter never resets at midnight. The date part is the day of the run. The sequence part is the total number of runs on this deployment. Tomorrow's first report will not be ...-000001; it will continue from wherever the counter left off. Delete the counter file and it starts at 1 again, possibly colliding with existing directories.

This does not fail tests, but it makes the ID ambiguous. Worse, the mailer depends on the counter to find the report directory:

def _find_report_id_for_counter(counter: int) -> str | None:

    suffix = f"-{counter:06d}"

    names = [

        p.name for p in _REPORTS_ROOT.iterdir()

        if p.is_dir() and _REPORT_DIR_RE.match(p.name) and p.name.endswith(suffix)

    ]

    return max(names) if names else None

If the counter and the directories drift, the "this report" link in the email points at the wrong place or at nothing. The fix is to pass the report ID to the mail process instead of letting it guess. Or store the counter as { date, counter } and reset on date change. The stronger fix is a ULID: monotonic, time-sortable, and no lock required.

Merging sub-reports: nodeid is the primary key

Each script writes a pytest JSON report. When the script exits, the server merges it into the batch report:

function mergeSubReportToTotal(totalFile, subFile) {

  const total = JSON.parse(fs.readFileSync(totalFile, 'utf-8'))

  const sub = JSON.parse(fs.readFileSync(subFile, 'utf-8'))



  sub.tests.forEach(test => {

    const exists = total.tests.find(t => t.nodeid === test.nodeid)

    if (exists) {

      exists.call = exists.call || { log: [] }

      exists.call.log = exists.call.log.concat(test.call?.log || [])

      exists.outcome = test.outcome

      exists.setup = test.setup

      exists.teardown = test.teardown

    } else {

      total.tests.push(test)

    }

  })



  total.collectors = total.collectors.concat(sub.collectors || [])

  total.summary = sub.summary || total.summary

  total.exitcode = sub.exitcode || total.exitcode

  total.updatedAt = Date.now() / 1000

  fs.writeFileSync(totalFile, JSON.stringify(total, null, 2), 'utf-8')

}

Using nodeid is correct. A pytest nodeid looks like tests/debug/test_binding.py::test_device_bind_loop. It includes the path, class and method, so it is unique across scripts. If the same script is queued twice, the second run's logs merge into the same entry instead of creating duplicates.

But the last three lines have two problems. total.summary = sub.summary overwrites instead of aggregating. After the merge, the header counts reflect only the last script, not the batch. The UI hides this because TestTable recounts from json.tests; any other consumer of summary, including mail, scripts and a future API, reads the wrong number. And total.exitcode = sub.exitcode || total.exitcode only updates when the sub exit code is truthy. Zero is falsy, so "the last script succeeded" never writes a successful batch exit code. The batch result is actually tracked separately in batchMailExit.

The fix is straightforward: recompute summary from total.tests after merging, and compute exitcode explicitly as "any failure means 1". The bug is a classic one: the merge was written as last-writer-wins, not as an aggregation.

A report has more consumers than the UI. Mail links to it, scripts may parse it, and a future dashboard will aggregate it. That is why a silently wrong summary is worse than a missing field: the UI looks right while every downstream number is wrong. A useful discipline is to define the report schema once, with a version field, and to make every producer and consumer import the same type. The current JSON is pytest's schema plus a few added fields, which is pragmatic but means a pytest upgrade can change the contract. Pinning pytest and validating the merged file against a schema in CI would catch that early.

Attaching logs: stdout pasted onto every test

pytest's JSON report already contains call.log, but in verbose mode the progress output and Python logging lines do not always land in every test's log. AutoTest patches it by hand:

function appendLogToSubReport(subReportFile, line) {

  line = line.trim()

  if (!line) return



  let subReport = { tests: [] }

  if (fs.existsSync(subReportFile)) {

    subReport = JSON.parse(fs.readFileSync(subReportFile, 'utf-8'))

  }

  if (!Array.isArray(subReport.tests)) subReport.tests = []



  if (subReport.tests.length === 0) return



  subReport.tests.forEach((test) => {

    test.call = test.call || { log: [] }

    test.call.log = test.call.log || []

    test.call.log.push({

      name: test.nodeid.split('::')[0] || 'unknown',

      msg: line, args: null, levelname: 'INFO', levelno: 20,

    })

  })



  fs.writeFileSync(subReportFile, JSON.stringify(subReport, null, 2), 'utf-8')

}

Three consequences follow, in ascending order of severity. First, collection-phase logs are lost. Before running a test, pytest imports modules, resolves fixtures and executes conftest.py. Import errors, fixture failures and syntax errors are exactly what you most need to see, and at that moment subReport.tests is still empty, so the function returns immediately. The report looks blank while the console clearly shows a traceback.

Second, a multi-test script duplicates every line N times. Each stdout line is pushed into every test in that file. Five tests means the same line appears five times. Per-test display tolerates it; exporting the report for statistics multiplies it.

Third, every line rewrites the whole JSON file. For each stdout line the function reads, parses, pushes, stringifies and writes the entire report. A 5,000-line run does 5,000 full-file rewrites, and it gets slower as the report grows. That is O(lines x report size) I/O.

The correct split is two streams. Process-level logs go to reports/<id>/run.log, appended line by line and tailed over SSE. They belong to no single test, but they are complete and cheap. Test-level logs come from pytest hooks such as pytest_runtest_logreport, where report.capstdout can be attached to the matching nodeid. Collection errors get their own bucket from pytest_collectreport. AutoTest's current approach is a "good enough to read" compromise. It stops being good enough the moment someone uses reports for quality trends.

Log volume is the other hidden cost. A stress loop that runs for hours can produce hundreds of megabytes of stdout, and the current design stores a copy in every test entry as well as in the JSON report. Disk fills quietly, and the largest file is also the slowest to rewrite. A production version needs retention: keep the full run log for N days, keep per-test logs for failures only, and compress finished batches. None of that exists today, which is acceptable for a tool whose reports are read within a day, and dangerous for one that is expected to keep a year of history.

Summary mail: from N messages to one

conftest.py has a default behaviour that looks innocent:

def pytest_sessionfinish(session, exitstatus):

    if os.environ.get("AUTOTEST_DEFER_SESSION_MAIL") == "1":

        return

    from core.finish_report_mail import send_finish_mail

    send_finish_mail(exitstatus)

Running one script locally is natural: pytest ends, one mail goes out. Through Testbed, each script is a process, so ten scripts would send ten mails. The fix is one environment variable:

const deferMailEnv = {

  ...PYTHON_ENV_FOR_AUTOTEST,

  AUTOTEST_DEFER_SESSION_MAIL: '1',

}



function spawnFinishMail(batchExitForMailBody) {

  const mailProc = spawnPythonModule(

    'core.finish_report_mail', [String(batchExitForMailBody)],

    { cwd: AUTOTEST_ROOT, env: PYTHON_ENV_FOR_AUTOTEST,

      stdio: ['ignore', 'pipe', 'pipe'] }

  )

}

Two benefits follow. Mail logic exists in exactly one place, shared by local and batch runs, so Node never needs its own SMTP implementation. And mail failure cannot affect test results: the mail process exit code is recorded separately (0 sent, 2 skipped or failed), while the batch exit is tracked in batchMailExit.

The failure modes are equally explicit. If server.js crashes before the last script settles, spawnFinishMail never runs and the batch mail is lost. If the last pytest child hangs, for example inside driver.quit(), scriptsRemaining never reaches zero, so the batch neither finishes nor mails. If the counter and the report directories drift, the link is wrong. The robust version treats "batch finished" as a recoverable state: write batch.json with the report ID and exit code, let the mailer retry, or model mail as a task row rather than a one-shot spawn.

Deliverability is another boundary. Sending through an enterprise SMTP relay with a hard-coded sender works until the relay changes its policy, the account password rotates, or the company moves to another provider. Because the sender must match the login, there is no way to send on behalf of a team address. A better design uses a dedicated service account, reads credentials from the environment, and records the SMTP response code so a failure is visible instead of silent. The current code prints the result and exits with status 2, which is a start, but the server does not surface that code anywhere except its own console.

Mail encoding: subject, NUL, and surrogate pairs

The body is HTML with tester name, project name, report path and links. Those fields come from config and can contain anything. finish_report_mail.py applies three layers of defence:

def _sanitize_subject(subject: str) -> str:

    s = (subject or "").replace("\r", " ").replace("\n", " ").replace("\t", " ")

    s = "".join(ch for ch in s if ord(ch) >= 32 or ch in "\t")

    s = " ".join(s.split()).strip()

    if len(s) > 200:

        s = s[:197] + "..."

    return s or "[automation] notification"



def _sanitize_html_body(html_body: str) -> str:

    s = (html_body or "").replace("\x00", "")

    return "".join(ch for ch in s if not (0xD800 <= ord(ch) <= 0xDFFF))

Why these characters? Mail headers are strict. A \r\n in a subject can be interpreted as header injection by some gateways; at best the message is rejected, at worst an extra Bcc is forged. NUL and UTF-16 surrogate pairs (0xD800 to 0xDFFF) can throw during MIME encoding, especially on Windows when strings arrive from files or the clipboard. A too-long subject is truncated or rejected; RFC limits are much lower than 998 bytes, so 200 characters is conservative.

The body uses EmailMessage with plain first and HTML second:

msg = EmailMessage()

msg["From"] = _sender_email

msg["To"] = to_email

msg["Subject"] = subject

msg.set_content(plain, charset="utf-8", subtype="plain")

msg.add_alternative(content_html, charset="utf-8", subtype="html")

From must equal the SMTP login account. Alibaba enterprise mail rejects a display-name form with a 440. The recipient must end in @glazero.com, enforced in code. Both constraints tie the module to one provider; switching providers means editing code.

Two practical problems remain. The SMTP host, sender and password are hard-coded at the top of the file, so anyone with the repository can send mail. They belong in environment variables or a secret manager, with only .env.example in git. And TEST_REPORT_BASE_URL defaults to http://localhost:5173. If production never sets it, the "this report" link opens the recipient's own localhost. That is the classic development default leaking into production.

Config without files: three tables, DELETE plus INSERT

Config lives in PostgreSQL, not JSON or YAML:

CREATE TABLE IF NOT EXISTS device_config (

    product TEXT, product_sn TEXT, product_name TEXT,

    serial_port TEXT, serial_baud_rate TEXT, device_view TEXT,

    ssid TEXT, password TEXT

);



CREATE TABLE IF NOT EXISTS test_config (

    test_name TEXT, user_name TEXT, email TEXT,

    retry_count INTEGER, timeout INTEGER

);



CREATE TABLE IF NOT EXISTS phone_config (

    android_remote_ip TEXT, android_remote_port INTEGER,

    android_sdk_path TEXT, android_version INTEGER,

    android_device_name TEXT, android_udid TEXT,

    android_adb_connect TEXT, android_automation_name TEXT,

    android_app_fullpath TEXT, android_app_package TEXT,

    android_app_activity TEXT,

    ios_remote_ip TEXT, ios_remote_port INTEGER,

    ios_version INTEGER, ios_automation_name TEXT,

    ios_device_name TEXT, ios_app_fullpath TEXT

);

None of the three tables has a primary key, because each is designed to hold exactly one row. Saving is "clear, then insert one":

await pool.query(`DELETE FROM ${tableName}`)

const fields = Object.keys(data)

const placeholders = fields.map((_, i) => `$${i + 1}`)

const sql = `INSERT INTO ${tableName} (${fields.join(',')})

             VALUES (${placeholders.join(',')}) RETURNING *`

const result = await pool.query(sql, values)

The benefit is schema flexibility: a new field on the page becomes a new key in the body, and the SQL follows. For an internal tool whose config changes often, that saves real work. The costs are equally real. There is no history, so a bad save can only be undone from memory. There is no concurrency control: two saves race, last writer wins, and there is a moment when the table is empty; a pytest process reading config at that moment gets an empty object. There are no type constraints beyond TEXT and INTEGER, so enums, ranges and required fields live only in the frontend. And WiFi passwords, mail addresses and tester names are stored in plaintext, so a database backup is a credential leak.

A better compromise is a single row with JSONB: one config table, fixed id = 1, all values in data JSONB, written with INSERT ... ON CONFLICT (id) DO UPDATE. That keeps flexibility, removes the empty-table window, and allows updated_at for optimistic locking.

Configuration also carries personal data. The tester name and email are personal, the WiFi password is a secret, and the device serial numbers identify hardware. Storing them in one unencrypted table means a database dump is both a privacy and a security event. At minimum, restrict database access to the service account, exclude the config database from broad backups, and encrypt the password column. A JSONB design makes it easier to separate public fields from secrets, because the secret can live in a separate table or a key-vault reference rather than next to the product name.

Dynamic SQL: a table allowlist does not cover columns

The config endpoint validates the table name:

const TABLES = {

  device_config: 'device_config',

  test_config: 'test_config',

  phone_config: 'phone_config',

}

That blocks table-name injection, but not column-name injection. fields comes directly from Object.keys(req.body) and is interpolated into the column position. Values are parameterised; identifiers are not. Any key containing a quote or SQL fragment can change the statement shape. The realistic attacks are not DROP TABLE (Node's pg does not run multiple statements by default), but structural probing: an unknown column produces a 500 that reveals schema information, and a crafted identifier produces syntax errors echoed to the client. If a future version enables multi-statement execution, it gets worse.

Actual risk depends on exposure. On loopback or a trusted LAN it requires prior access. But the service listens on 0.0.0.0 with permissive CORS by default, which section 27 covers. The safer implementation keeps a per-table column allowlist:

const COLUMNS = {

  device_config: ['product', 'product_sn', 'product_name', ...],

  test_config: ['test_name', 'user_name', 'email', 'retry_count', 'timeout'],

  phone_config: ['android_remote_ip', ...],

}

const fields = Object.keys(data).filter(k => COLUMNS[tableKey].includes(k))

Or simpler: store one JSONB blob so column names never enter SQL at all.

One more detail: retry_count and timeout in test_config are never read by server.js or pytest. They appear on the config page and imply that retry and timeout work. They do not. That is the most common way a config table rots: the field is added, the consumer never follows.

There is no migration story for configuration, which is both the point and the problem. Adding a column is easy: add it to schema.sql, add the input to the Vue page, and the dynamic insert follows. But existing deployments do not run schema.sql again, so the column never appears, and the next save fails with "column does not exist". The project handles this by telling operators to run the SQL manually, which works for one machine and fails for three. A lightweight migration table, or a startup check that compares information_schema with the expected columns, would turn a silent failure into a clear message.

Pretest: three checks and an install door

Pretest is one of the most useful ideas in AutoTest. It moves environment failures from "after you click Run" to "before you click Run":

app.get('/api/pretest', async (req, res) => {

  const db = await checkPostgres()       // SELECT 1

  const appium = await checkAppium()     // TCP 127.0.0.1:4723, one-second timeout

  const pyDeps = await checkPythonDeps() // pip list --format=json

  res.json({ db, appium, python: pyDeps })

})

Each check maps to a common failure:

CheckMethodWhat failure really means
DatabaseSELECT 1PostgreSQL down, wrong database/password, pool exhausted
AppiumTCP connect 4723Appium not started, or the port is taken by something else
Python depspip list --format=jsonMissing pytest, appium-python-client, poco

The dependency check only looks at three packages, while a real run also needs pytest-json-report, psutil, requests and selenium. The checklist is smaller than reality, so Pretest can be all green while the run still fails. A better design makes pip install -r requirements.txt the single source of truth, then checks pip check and the key imports instead of hard-coding three names.

The same file also exposes an install endpoint:

app.post('/api/pretest/install', (req, res) => {

  const { packages } = req.body

  const { cmd, args } = pythonModuleExecArgs('pip', ['install', ...packages])

  execFile(cmd, args, { env: PYTHON_ENV_FOR_AUTOTEST }, (err, stdout, stderr) => {

    if (err) return res.status(500).json({ error: stderr || err.message })

    res.json({ message: stdout })

  })

})

It is convenient and it is a remote execution surface. Anyone who can reach port 3000 can make the server run pip install with an arbitrary package. On a personal machine that is fine. On a shared LAN host it is a supply-chain door. At minimum it needs authentication, a package allowlist, and a rule that only packages reported missing may be installed.

A check is only useful if it fails for the right reason. Pretest currently reports "Python dependencies OK" when the three hard-coded packages exist, even if the interpreter is the wrong one or pytest-json-report is missing. That is a false green, which is worse than no check because it teaches users to trust it. A more honest design runs the same command the runner will run, for example python -m pytest --version and python -c "import pytest_jsonreport", and reports the full command and output on failure. The principle is simple: a health check should exercise the real path, not a proxy for it.

Appium 1.x and /wd/hub: one URL decides a 404

build_appium_url is six lines, but it decides whether the project can connect at all:

def build_appium_url(host, port):

    """

    Appium 1.x (e.g. 1.18) requires http://host:port/wd/hub.

    Connecting to http://host:port alone returns 404:

    The URL '/session' did not map to a valid resource.

    """

    host = str(host or "127.0.0.1").strip()

    port = int(port or 4723)

    base = f"http://{host}:{port}".rstrip("/")

    if not base.endswith("/wd/hub"):

        base = f"{base}/wd/hub"

    return base

Appium 1.x serves WebDriver at /wd/hub/session. Appium 2 removed /wd/hub and uses /session. AutoTest targets 1.x, and its error message even suggests npm install -g appium@1.18.3, so every initialisation goes through this function.

The problem is that not every path goes through it. After rebooting a phone, restart_phone() rebuilds the driver with:

self.driver = webdriver.Remote("http://127.0.0.1:4723", options=self.options)

No /wd/hub, and no configured host or port. With Appium 1.x this 404s after every reboot. With Appium 2.x, initialisation 404s instead. The project is pinned to an unmaintained 1.x line. The better design makes the path configurable, probes /status before initialising, and chooses by version, so an upgrade is a config change rather than edits in three places.

adb device discovery: connect, list, then match udid

When Appium says Could not find a connected Android device, the real cause is usually adb, not Appium. ensure_adb_device encodes that troubleshooting knowledge:

def ensure_adb_device(phone_cfg: dict) -> str | None:

    adb = _adb_executable()

    connect_addr = str(phone_cfg.get("android_adb_connect") or "").strip()

    if connect_addr:

        subprocess.run([adb, "connect", connect_addr], capture_output=True,

                       text=True, timeout=20, check=False)



    result = subprocess.run([adb, "devices"], capture_output=True,

                            text=True, timeout=20, check=False)

    devices = [

        line.split()[0]

        for line in (result.stdout or "").splitlines()

        if line.strip() and not line.startswith("List of devices")

        and len(line.split()) >= 2 and line.split()[1] == "device"

    ]

    if not devices:

        raise RuntimeError(

            "adb found no usable Android device (Appium: Could not find a connected Android device).\n"

            "Check: 1) USB debugging on a real phone; "

            "2) start the emulator and set android_adb_connect, e.g. 127.0.0.1:7555; "

            "3) adb kill-server && adb start-server, then retry.\n"

        )



    want = str(phone_cfg.get("android_udid") or "").strip()

    if want and want not in devices:

        raise RuntimeError(f"android_udid={want} not in adb list; current devices: {devices}")

    return want or devices[0]

Three things are worth learning here. First, adb connect must come before adb devices. Emulators such as MuMu and Nox do not appear automatically; they must be connected to something like 127.0.0.1:7555. Putting that address in config removes a command from the user's memory. Second, the error message contains repair steps. It does not just throw "no device"; it lists the three most common causes and their commands. For an internal tool, that matters more than log level. Third, multi-device selection is explicit. If the list has more than one device and no udid is configured, the code warns and uses the first. That avoids the hardest incident to diagnose: a test that ran on someone else's phone.

The boundary is that the parser only accepts the device state. offline and unauthorized are filtered out, and the error says "no usable device" rather than "one device is unauthorized". A better message would include the raw adb output and name the actual state.

Emulators and real devices behave differently enough to deserve separate notes. An emulator is usually connected over TCP and can disappear when the host sleeps; a real device can drop to unauthorized when the debug authorization is revoked. The current error message covers both, but the code does not distinguish them. A small improvement is to record the device transport (USB or TCP) and include it in the log, so a flaky run can be correlated with the connection type. This sounds like polish, but in a device farm it is the difference between a five-minute diagnosis and an afternoon.

Appium process management: why not CREATE_NEW_CONSOLE

tools/appium_server.py starts, detects and stops Appium. It solves several very Windows-specific problems:

def build_appium_popen_cmd(port: int, appium_cmd: str) -> tuple[list[str], str]:

    node = _where_executable("node")

    main_js = _appium_main_js_near(appium_cmd)

    if node and main_js:

        return [node, main_js, "-p", str(port)], f"{node} {main_js} -p {port}"

    if os.name == "nt":

        return ["cmd.exe", "/c", appium_cmd, "-p", str(port)], f"cmd /c {appium_cmd} -p {port}"

    return [appium_cmd, "-p", str(port)], f"{appium_cmd} -p {port}"

It prefers node main.js over appium.cmd. The .cmd path goes through cmd.exe, which in some environments opens a new console window; the parent loses the handle and thinks startup failed. The code comments this directly:

# Do not use CREATE_NEW_CONSOLE: the .cmd runs in another window

# and the parent thinks startup failed.

popen_kw["creationflags"] = subprocess.CREATE_NO_WINDOW

The startup sequence is "probe first, then decide":

is_port_listening(127.0.0.1, 4723)

  |- already listening -> reuse, skip startup

  |- not listening     -> kill old appium -> start -> wait up to 60s

This makes repeated calls idempotent: no duplicate Appium instances. But the kill match is broad:

for proc in psutil.process_iter(["pid", "name"]):

    if "node" in (proc.info["name"] or "").lower():

        cmdline = " ".join(proc.cmdline())

        if "appium" in cmdline.lower() and str(self.port) in cmdline:

            proc.kill()

Any Node process whose command line contains both appium and the port number is killed, including a user's manual debugging instance, another project's Appium, or an unrelated process that happens to carry the port in its arguments. A safer approach uses a PID file or checks psutil create_time, and only kills the instance it started.

AppiumServer.start() also mutates os.environ directly:

for key in ("ANDROID_HOME", "ANDROID_SDK_ROOT", "PATH"):

    if key in run_env:

        os.environ[key] = run_env[key]

That is a library function changing global state. It persists for the rest of the process and can affect later logic. The environment should be passed to the child only, not written back.

Service lifetime is another design question. AutoTest starts Appium per test process and stops it in quit(), which means the service is up and down many times per batch. That is simple and avoids a long-lived process holding a stale port, but it also means every process pays the startup cost and races with any other process that wants the same port. A long-lived service managed by the server, with sessions per test, would be faster and would make the batch lock less about the port. The trade is a supervisor and a health check, which is exactly the kind of complexity a small tool avoids until it has to.

Stress loops: rebuild the session, not the server

The common need is not one run but a hundred. Appium sessions leak, stall and lose context over time, but restarting the whole Appium server is slow. reconnect_appium picks the middle layer:

def reconnect_appium(self, phone_cfg=None):

    """Rebuild the Appium session during stress loops (do not restart Appium)."""

    phone_cfg = phone_cfg or load_config("phone_config")

    if self.driver:

        try:

            self.driver.quit()

        except Exception as exc:

            logging.warning("closing old session: %s", exc)

    udid = ensure_adb_device(phone_cfg)

    if udid and self.options:

        self.options.udid = udid

    url = build_appium_url(

        phone_cfg.get("android_remote_ip"),

        phone_cfg.get("android_remote_port"),

    )

    self.driver = webdriver.Remote(url, options=self.options)

    return self.driver

It quits the old session (ignoring quit errors), re-confirms the adb device (the phone may have dropped), and creates a new session with the same options. The Appium service stays up, so startup cost is avoided.

The layering is worth borrowing. restart_app() kills and reopens the app, for application-state pollution. reconnect_appium() rebuilds the session, for driver-state pollution. restart_phone() reboots the device, for system-level problems. AppiumServer.kill()/start() restarts the service, for a wedged Appium process. Four levels, ordered by cost. Many teams only have "reboot the phone", so a small problem costs three minutes.

Rebooting a phone: adb reboot and boot_completed

restart_phone() is a shell script written in Python. It sends adb reboot, then polls until the device comes back:

def wait_for_device_online(self, timeout=180, check_interval=5):

    while time.time() - start_time < timeout:

        result = subprocess.run("adb devices", shell=True, capture_output=True, text=True)

        device_lines = [line for line in result.stdout.split("\n") if udid in line]

        if device_lines:

            device_status = device_lines[0].split("\t")[-1].strip()

            if device_status == "device":

                boot_check = subprocess.run(

                    f"adb -s {udid} shell getprop sys.boot_completed",

                    shell=True, capture_output=True, text=True,

                )

                if boot_check.returncode == 0 and boot_check.stdout.strip() == "1":

                    return True

        time.sleep(check_interval)

    return False

It checks two layers: the adb state is device (not offline or unauthorized), and sys.boot_completed is 1. That order is correct. Waiting only for adb devices returns at the lock screen, and the following activate_app fails.

But the rebuild after reboot has a clear bug:

self.driver = webdriver.Remote("http://127.0.0.1:4723", options=self.options)

It bypasses build_appium_url and ignores the configured host and port. With Appium 1.x it 404s after every reboot; with a network-connected phone, 127.0.0.1 is the wrong host anyway. This is what happens when one concept has two implementations: initialisation uses the helper, reboot uses a shortcut.

adb reboot is also built with shell=True. The udid comes from config or adb output, so injection risk is low, but subprocess.run([adb, "-s", udid, "reboot"]) is cleaner and removes the question.

A stress loop without observability is a random number generator. The current script logs each cycle and counts successes, but it does not record per-cycle duration, failure reason, or device state. After a hundred cycles, the only question anyone asks is "how many failed", and the answer is a single number with no trend. Adding a structured line per cycle, with timestamp, duration, outcome and a short error code, would make the run log useful without changing the report format. It would also make the difference between "the phone got slower" and "the app started crashing" visible.

Test script conventions: PLATFORM, fixtures, and global mail

The platform asks for exactly three conventions:

# 2) declare the platform at module level

def test_example(app_driver):

    ...

One design detail is worth noting: PLATFORM is a module variable read through request.module. A typo or wrong case falls through to else: raise UnknownObjectException, which is a poor error. Validate against Literal["Android", "iOS"] and print the accepted values.

The reading side: 5-second polls, 3-second polls, and v-html

The frontend splits the report list and a single report into two pages, with different polling. Result.vue uses LIST_POLL_MS = 5000 and only polls while a report is running; when everything finishes, it stops. The README says three seconds; the code says five. That is another documentation drift. TestTable.vue uses POLL_MS = 3000 and polls while status === 'running' or the URL carries live=1, then stops.

Polling only when needed is better than an unconditional interval: a closed tab or a finished batch stops generating requests. It also handles a boundary: live=1 means "I insist on live", so even a report already marked finished can be fetched once more.

A single report draws a pie chart with Chart.js:

import { Chart, PieController, ArcElement, Tooltip, Legend } from 'chart.js'

But chart.js is not in pytest-vue/package.json. Likewise Testbed.vue imports vuedraggable, which is also undeclared. The current environment depends on node_modules that were installed historically and never recorded. A clean npm ci fails. Section 25 covers this.

The log page has a more serious issue:

<span v-html="highlightErrorKeywords(line)"></span>


function highlightErrorKeywords(line) {

  if (!line) return ''

  const keywords = ['NameError', 'TypeError', 'AttributeError', 'IndexError', 'KeyError']

  let highlighted = line

  keywords.forEach(key => {

    const regex = new RegExp(`(${key})`, 'g')

    highlighted = highlighted.replace(regex, '<span class="error-keyword">$1</span>')

  })

  return highlighted

}

v-html renders the string as HTML, and line comes from device or test output. A log line containing <img src=x onerror=...>, or an application that logs user input, executes it. The report UX is intentionally plain: a table, a status colour, a pie chart and a print button. That is appropriate for an internal tool. The one thing missing is a stable deep link per test case. log.html?reportId=&nodeid= is stable as long as the report exists, but report retention is undefined, so links pasted into chat rot. A permalink that includes a content hash, or a small server that proxies old links to an archive, would make reports shareable. For now, the practical advice is to paste the report ID and nodeid rather than the whole URL, and to keep the batch directory until the issue is closed.

Three latent bugs found by reading the code

These are not design trade-offs. They are bugs you can locate by reading. Together they show the gap between "it runs" and "it is maintainable": the gap lives on exception paths.

Bug one: the first line of bind_device_ByBle throws.

def bind_device_ByBle(self):

    ssid = self.config.get("wifi", {}).get("ssid")

    password = self.config.get("wifi", {}).get("password")

self.config is never assigned in AppControl.__init__, and there is no other assignment in app_base.py. The method throws AttributeError on its first line whenever it is called. test_binding.py wraps every cycle in try/except Exception, so the symptom is: every cycle fails immediately, the log shows one AttributeError, and the loop continues. A casual reader blames the device.

The fix is simple: read WiFi from device_config in __init__, or pass ssid/password as arguments. More importantly, do not swallow programming errors with a bare except Exception inside the loop. At least distinguish device exceptions from code exceptions.

Bug two: devices_sn is a string, iterated as a collection.

self.devices_sn = load_config("device_config")["product_sn"]

self.device_num = len(self.devices_sn)

...

for device_sn in self.devices_sn:

product_sn is TEXT in the database. If the config page holds one SN, len() returns the character count and the loop yields characters. The unbind loop then runs "characters + 2" times, and the bind loop tries to match a single character against SN: x. Unless the column stores a JSON array string, and the code never calls json.loads, this logic cannot work.

The fix is to define the format (comma-separated or JSON array), parse it into list[str] when loading, and handle empty and single values.

Bug three: the merged summary overwrites instead of aggregating.

Section 10 broke this down. The UI hides it because the frontend recounts, but mail, scripts and a future API read the wrong numbers. Recompute after merging:

const counts = { passed: 0, failed: 0, skipped: 0, total: total.tests.length }

for (const t of total.tests) {

  if (t.outcome in counts) counts[t.outcome] += 1

}

total.summary = counts

All three bugs live on exception or boundary paths. Walking the happy path through the UI will not reveal them. That is why internal tools need code review, not just "it runs".

Dependency manifests and portability: five undeclared imports

There is a visible gap between the manifests and the imports. The frontend package.json declares axios, body-parser, cors, express, pg, tcp-port-used, vue and vue-router. The Stop button: a POST with no backend

The Testbed top bar has a Stop button. Its implementation is:

async function stopTests() {

  if (!running.value) return

  try {

    await fetch('/stop-tests', { method: 'POST' })

    output.value += '\n===== tests stopped =====\n'

    running.value = false

    if (evtSource) {

      evtSource.close()

      evtSource = null

    }

  } catch (err) {

    console.error(err)

  }

}

Vite proxies /stop-tests to the test server. But server.js has no such route. The POST returns 404, and fetch does not throw on 404 because it is a valid response. The frontend therefore continues: it sets running to false, closes the EventSource and prints "tests stopped".

In reality the pytest child keeps running, Appium keeps tapping, and runTestsStreamBusy is still true. The user sees "stopped", while the next person who clicks Run gets "a batch is already running". This is a textbook composition bug: optimistic frontend update plus a missing backend endpoint.

Real cancellation requires four things on the server: keep references to the current batch's child processes; expose POST /stop-tests; send SIGTERM and escalate to SIGKILL after a timeout; and in settleChild record "stopped by user" as an explicit label and release the batch lock. The frontend should only set running to false after receiving close.

In the current fail-fast model, the honest choice is to rename the button "disconnect output", or remove it. A button that looks like it stops but cannot is worse than no button.

The security boundary: this tool does not belong on the public internet

Listing every security issue in AutoTest produces a long page: app.use(cors()) allows any origin; app.listen(3000, '0.0.0.0') binds every interface; no endpoint authenticates; config holds WiFi passwords, email addresses and tester names; /api/pretest/install can run pip install with arbitrary packages; TestLog.vue renders logs with v-html; finish_report_mail.py hard-codes SMTP credentials; and adb reboot uses shell=True.

Each has an explanation: internal tool, one maintainer, fast delivery. Stacked together they mean one thing: anyone who can reach port 3000 can read the WiFi password, install arbitrary packages on the server, and send mail from the company account.

The minimum hardening order is short. Bind to 127.0.0.1, and put Nginx or Caddy with Basic Auth or SSO in front when LAN access is needed. Disable or allowlist /api/pretest/install; if it stays, only permit packages reported missing. Move credentials out of source and rotate the leaked authorization code. Escape logs before highlighting and drop v-html. Replace permissive CORS with an explicit origin.

One sentence: it is a LAN tool. Do not put it on the public internet. If you must, design it as a service that can execute commands and read company configuration, because that is what it is.

Why does any of this matter beyond one internal tool? Because the same shape appears everywhere: a web console that shells out to a test runner, a data pipeline that shells out to a Python script, an agent that shells out to a CLI. The pattern is always HTTP to process, process to files, files to a report, report to a notification. The failure modes are always the same: buffering hides output, a missing interpreter looks like a test failure, two runs corrupt each other's files, and a "stop" button that only closes a socket. Getting these boundaries right once gives you a template for the next five internal tools.

If I rewrote it, I would change these five things first

I would keep the shape: developer box, test server, SSE. Then I would change five things. First, give each batch a cancellable process table. A Map<reportId, Set<ChildProcess>> plus POST /stop-tests and a single settleChild path. Stopping means signal, wait, write the report, release the lock, not closing a browser connection.

Second, split process logs from test logs. Append to reports/<id>/run.log and tail it over SSE. Attach test logs from pytest_runtest_logreport's capstdout, keyed by nodeid. Collection errors get their own bucket. No lost tracebacks, no N-fold duplication, no full-file rewrite per line.

Third, use ULID for report IDs and aggregate summaries. ULIDs are monotonic and time-sortable, and they remove the "daily counter that is not daily" problem. Recompute counts after merging, and compute exitcode explicitly as "any failure means 1".

Fourth, add a column allowlist to config, and write with UPSERT plus JSONB. A table allowlist is not enough. One config(id, data JSONB, updated_at) row with ON CONFLICT removes the delete-then-insert window. Encrypt credentials, or at least stop storing them in plaintext.

Fifth, put dependencies and case sensitivity in CI. npm ci && npm run build on Linux, python -m pytest --collect-only in a clean venv, and a build step that catches import case mismatches. Internal tools most often die from "it only runs on my machine".

None of these five touches Appium business logic. All of them decide whether a second person can take over.

The order of these changes matters. Cancellation and process logs come first because they affect correctness and diagnosis. Report aggregation and ULID come next because they affect every consumer. Config hardening and CI come last because they are about preventing future regressions rather than fixing current pain. Trying to do all five at once in a codebase this size usually produces a rewrite that is neither the old system nor the new one. A safer path is to add the process table and run log behind a flag, migrate one batch at a time, and delete the old path only after a month of clean runs.

Closing: the cost of turning tests into a service is in the boundaries

AutoTest's value is not "click a button to run pytest"; that is a shell wrapper. Its value is making four kinds of invisible labour explicit. Process boundaries: one pytest per script, with interpreter path, encoding, buffering and Android SDK solved before launch. File boundaries: report directories, sub-report merges, log attachment and counters, where any inconsistency makes results untrustworthy. Human boundaries: batch exclusion, one mail instead of ten, Pretest, and error messages a second person can act on. Security boundaries: no auth, open CORS, executable pip, hard-coded credentials, which together decide that it can only live on a LAN.

If you remember three things: making tests run is Appium; making tests a service is process management. A report is not "pytest's output", it is a data contract you define, and a merge must aggregate rather than let the last writer win. And internal tools fail first on exception paths: the Stop button, collection failures, cross-day counters and Windows case sensitivity are what the next person hits.

What is worth keeping is the part that took the most thought: the five-level interpreter discovery, the clear adb error messages, the single batch lock, the per-script report shard, and the defer-mail environment variable. These are small, unglamorous decisions that encode operational knowledge. A rewrite that replaces them with a framework often loses exactly this knowledge, then rediscovers it as incidents. The lesson is to keep the boundaries explicit and the code boring.
