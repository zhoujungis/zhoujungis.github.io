At deploy time the database rebuilds the whole table

2026-11-03 · 30 min · Stack Frame

Follows the slow query post and the transaction post. The previous one suggested adding an index over the status, the pinned flag and the timestamp; this one is about how that index ships, and why the common way of shipping it locks the table for tens of seconds.

Django with SQLite, matching this site. MySQL and PostgreSQL get a comparison section with their own landmines.

Reading time around 30 minutes. Level: intermediate to advanced.

The cost of one makemigrations

The previous post ended with a to-do:

# backend/articles/models.py -- the current shape, which has a bug
class Article(models.Model):
    class Meta:
        ordering = ["-is_top", "-created_at"]
        indexes = [
            models.Index(fields=["status", "-created_at"], name="articles_status_created_idx"),
        ]

The ordering names two columns and the index holds one of them, with the wrong direction besides. Measured on a million rows, that apparently usable index pushed the list query to 476.50 milliseconds, slower than building nothing at all at 395.92, and aligning the columns and directions brought it to 0.18.

models.Index(fields=["status", "-is_top", "-created_at"], name="articles_status_top_created_idx"),

Then run the two commands. That was the plan. Before pressing enter I did something more careful and asked what SQL the migration would actually become.

python manage.py sqlmigrate articles 0007

The output took my hands off the keyboard, because on this site a migration is never only an index. It also finds wherever the model and the database disagree and adds the field back, and on SQLite adding a field is not an alter table, it is a full rebuild.

So I filled a table to two hundred thousand rows and 789.7 megabytes, matching the real schema including the two large text columns for the body and the rendered HTML, and ran every kind of DDL against it. The numbers were worse than I expected.

One: what sqlmigrate actually says

The command is badly underrated. It does not connect, does not change data, and only renders the migration as SQL. Every migration that ships should go through it first.

Here is a real one from this site. A single boolean field:

migrations.AddField(
    model_name="article",
    name="notification_sent",
    field=models.BooleanField(default=False),
)

BEGIN;
--
-- Add field notification_sent to article
--
CREATE TABLE "new__articles_article" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "notification_sent" bool NOT NULL,
    "title" varchar(200) NOT NULL,
    "slug" varchar(200) NOT NULL UNIQUE,
    "content" text NOT NULL,
    "html_content" text NOT NULL,
    "excerpt" text NOT NULL,
    "status" varchar(16) NOT NULL,
    "is_top" bool NOT NULL,
    "views_count" integer unsigned NOT NULL CHECK ("views_count" >= 0),
    "created_at" datetime NOT NULL,
    "updated_at" datetime NOT NULL,
    "category_id" bigint NULL REFERENCES "articles_category" ("id") DEFERRABLE INITIALLY DEFERRED,
    "cover_image" varchar(200) NOT NULL,
    "likes_count" integer unsigned NOT NULL CHECK ("likes_count" >= 0),
    "scheduled_at" datetime NULL
);
INSERT INTO "new__articles_article" ("id", "title", "slug", ... , "scheduled_at", "notification_sent")
SELECT "id", "title", "slug", ... , "scheduled_at", 0 FROM "articles_article";
DROP TABLE "articles_article";
ALTER TABLE "new__articles_article" RENAME TO "articles_article";
CREATE INDEX "articles_article_category_id_633dad2b" ON "articles_article" ("category_id");
COMMIT;

One boolean field, four operations: create a table, copy everything, drop the old one, rename the new one. Inside a single transaction.

Compare an index migration, which is two statements and touches no rows:

BEGIN;
--
-- Create index articles_status_created_idx on field(s) status, -created_at of model article
--
CREATE INDEX "articles_status_created_idx" ON "articles_article" ("status", "created_at" DESC);
--
-- Create index articles_scheduled_idx on field(s) scheduled_at of model article
--
CREATE INDEX "articles_scheduled_idx" ON "articles_article" ("scheduled_at");
COMMIT;

From here on there is a line in your head:

Migration operationReal SQL on SQLiteRebuilds the table
AddIndex / RemoveIndexCreate or drop an indexNo
AddField, nullable, no defaultAlter table add columnNo
AddField, not null or with a defaultCreate, copy, drop, renameYes
AlterFieldCreate, copy, drop, renameYes
RemoveFieldDrop column on 3.35 and later, or a rebuildDepends
RunSQLWhatever you wroteYour call

That table is the map for the whole post. Python on the left, the real work on the right, and a translation layer in between that nobody has ever read.

Why the command has to become muscle memory

It tells you three things in advance. Whether the table will be rebuilt, which a temporary table name reveals immediately. Whether it quietly changes something else, since the detection pass looks at every drift in every model, not only the one you meant. And whether it can run in a single transaction, which sounds reassuring until the transaction turns out to be the problem.

The second one bit me. I expected one index operation and got a mixed migration, because the index definition in the model disagreed with the ordering and because fields had been edited by hand before. Run the command before you decide whether to press enter.

Two: what plain SQLite can do

Before the 8,381 milliseconds there has to be a baseline. SQLite has supported adding a column for a long time and it is pure metadata, editing one row in the schema table without touching any data, so it should be independent of table size.

sqlite lib version: 3.53.1
  OK   ADD COLUMN nullable (c TEXT)                              7.7 ms
  OK   ADD COLUMN NOT NULL DEFAULT 0 (d INTEGER)                 7.4 ms
  OK   ADD COLUMN NOT NULL DEFAULT '' (e TEXT)                   7.0 ms
  FAIL ADD COLUMN NOT NULL no default (f INTEGER)           OperationalError: Cannot add a NOT NULL column with default value NULL
  FAIL ADD COLUMN non-constant default (g TEXT)             OperationalError: Cannot add a column with non-constant default
  FAIL ADD COLUMN UNIQUE (h TEXT)                           OperationalError: Cannot add a UNIQUE column
  OK   ADD COLUMN CHECK (i INTEGER CHECK(i>=0))                 52.8 ms
  OK   ADD COLUMN REFERENCES (j)                                 7.7 ms
  FAIL ALTER COLUMN / change type (a)                       OperationalError: near "TYPE": syntax error
  OK   ADD CONSTRAINT CHECK (table-level)                       26.3 ms

Look at the second line. A not-null column with a constant default is native, and it costs 7.4 milliseconds, exactly the same as a nullable one. Django spends 8,381 milliseconds on the same operation against similar data, a factor of 1,130.

Three hard limits explain the detour. You cannot add a not-null column without a default, because existing rows have nothing to hold and the engine refuses to guess. The default must be constant, because a constant can live in the schema while anything else would have to be written into every row. And you cannot add a unique column, because uniqueness needs an index and this statement does not build one.

Conversely, not null with a constant default is perfectly legal: the value lives in the schema and is applied when old rows are read, so no row is rewritten. That is the 7.4 milliseconds. A check constraint is supported, at 52.8 because existing rows have to be validated. And altering a column type is not supported at all, which is exactly why any field change forces a rebuild.

In one sentence: the engine can add a not-null column with a default in seven milliseconds; the question is why the framework refuses to.

Three: the rebuild, 8.4 seconds and double the disk

elapsed   : 8381.1 ms    full copy plus every index rebuilt
peak size : 1.5 GB (table 789.7 MB, about 2x)
exclusive : reads queue, writes queue, for the whole duration

Three numbers, each of them fatal on its own.

The copy is linear. A full scan and a full write, with no ceiling: mine is 790 megabytes, an eight gigabyte table starts at eighty seconds, and all of it runs inside one transaction holding the lock.

Peak disk is double. Before the drop both tables exist, so peak usage is twice the table plus the indexes. On a shared host that is an incident by itself: a 512 megabyte quota cannot absorb a migration of a 400 megabyte database, and the failure lands halfway through, inside a transaction, so the rollback frees nothing until the engine gets around to cleaning up.

The table is exclusive, and the lock is database-wide, not per row or per table. Once the write begins no other connection writes, and outside WAL mode readers queue as well. For eight seconds every insert, update and delete waits, every save() in a request stalls, requests time out, the pool drains and the workers fill.

Users do not experience slow. They experience the site being down, while the person who pushed sees one line saying the migration applied.

Four: creating an index, and the write lock

elapsed      : 1594.0 ms
index size   : 7.4 MB

Reasonable for two hundred thousand rows, since it scans, sorts and builds a tree at linearithmic cost. The point is that it also needs a write transaction. During it, writes block, and outside WAL mode reads block too; inside WAL mode reads continue.

Which gives the first practical piece of advice: if the database still uses the default rollback journal, switch it to WAL. Writing still blocks, but reading continues, which turns "the site is down" into "publishing is a bit slower" for a read-heavy blog. The cost is two sidecar files and poor behaviour on network filesystems, which is a net win on a single machine.

Five: how long writes wait behind DDL

baseline INSERT (no DDL)  : 181.1 ms
INSERT during DDL         : 1324.5 ms
CREATE INDEX total        : 1456.2 ms

The baseline is the total for two hundred batched inserts, so read the ratio rather than the absolute. Writes took 7.3 times longer, and the stalled insert's duration is almost identical to the whole DDL, which means it was not slower, it was waiting: blocked until the DDL took the lock, finished and released it.

The lock queue pile-up

Suppose the DDL takes ten seconds. Five writers arrive in the first second and queue. Five more arrive in the second and queue behind them. By the tenth second there are fifty requests waiting, and when the lock releases they all hit the database at once. Instant concurrency goes from zero to fifty, and with a default five second busy timeout the ones at the back fail outright.

What kills the site is often not the DDL but the reverse pressure after it. This is precisely why PostgreSQL has a lock timeout, covered later.

Six: dropping a column costs more

ADD COLUMN   : 1.8 ms
DROP COLUMN  : 1864.4 ms   (3.35 and later still rebuilds)

Adding is metadata, dropping rewrites every record, because rows are stored compactly and removing a column means repacking all of them. Dropping also falls back to a rebuild when the column has an index, is a primary or unique key, appears in a check constraint, a foreign key or a generated expression, or is referenced by a view.

In practice removing a field on SQLite is almost always a rebuild, which means the contract phase of an expand-and-contract migration has to be planned as a real rebuild rather than a casual cleanup.

Seven: the size accounting

File size cannot answer how much space the indexes take, because pages are interleaved. The right tool is the dbstat virtual table, which reports bytes per object by walking pages:

SELECT name, SUM(pgsize) AS bytes FROM dbstat GROUP BY name ORDER BY bytes DESC;

file size   : 1.5 GB
logical sum : 804.3 MB
  articles_article                         783.2 MB   97.4%
  articles_status_top_created_idx            7.4 MB    0.9%
  articles_status_created_probe_idx          7.2 MB    0.9%
  sqlite_autoindex_articles_article_1        4.7 MB    0.6%
  articles_article_category_id_idx           1.8 MB    0.2%
  sqlite_schema                              4.0 KB    0.0%
  sqlite_sequence                            4.0 KB    0.0%

The gap between the file and the logical sum is free pages left by the rebuild, which the engine does not hand back to the operating system until a vacuum. Another operational detail worth remembering: vacuum after a rebuild or the disk stays doubled.

The most valuable line is that the table itself is 97.4 percent and all the indexes together are under two. Two conclusions follow.

Indexes are not a space problem. Seven megabytes buys a two hundred fold improvement, and the write amplification argument from the previous post was about write performance, not storage. Refusing an index on space grounds does not survive arithmetic.

The real weight is in the two large text columns. Nearly eight hundred megabytes is article bodies and rendered HTML, which explains both why the rebuild takes eight seconds and why any rebuild is expensive regardless of how many fields you add.

The inference: if the body and rendered HTML are the bottleneck, moving them to a one-to-one table shrinks the hot table to tens of megabytes, after which every migration is an order of magnitude faster. That is a one-off architectural investment with a permanent return, and it is what I plan to do here next.

Eight: reading the source

Why does a framework spend eight seconds on something the engine does in seven milliseconds? The answer is in the SQLite schema editor, in the field-adding method:

def add_field(self, model, field):
    """Create a field on a model."""
    from django.db.models.expressions import Value

    # Special-case implicit M2M tables.
    if field.many_to_many and field.remote_field.through._meta.auto_created:
        self.create_model(field.remote_field.through)
    elif isinstance(field, CompositePrimaryKey):
        return
    elif (
        # Primary keys and unique fields are not supported in ALTER TABLE
        # ADD COLUMN.
        field.primary_key
        or field.unique
        or not field.null
        # Fields with default values cannot by handled by ALTER TABLE ADD
        # COLUMN statement because DROP DEFAULT is not supported in
        # ALTER TABLE.
        or self.effective_default(field) is not None
        # Fields with non-constant defaults cannot by handled by ALTER
        # TABLE ADD COLUMN statement.
        or (field.has_db_default() and not isinstance(field.db_default, Value))
    ):
        self._remake_table(model, create_field=field)
    else:
        super().add_field(model, field)
ConditionWhen it firesReasonable
primary keyAdding a keyYes
uniqueAdding a unique fieldYes, an engine limit
not nullAny non-null fieldOver-broad
has a Django defaultAny field with a default argumentOver-broad
database default that is not a constantAn expression defaultYes

The first two and the last are fair. The middle two are the problem.

Not null does not have to mean a rebuild

The comment says the alter statement does not support not null, which is incomplete: what it does not support is not null without a default, as the first experiment shows. The framework takes the conservative path because it must handle the general case, where the field is not null and has no default and the statement genuinely cannot do it. Rather than distinguish the cases it rebuilds whenever the field is not null.

The price is the factor of 1,130.

The hidden cost of a default

The comment explains it: a field with a default cannot be handled because dropping a default is not supported in an alter table. Django writes the default into the DDL and then drops it, because it treats defaults as a Python-level concept that does not belong in the database. SQLite has no alter-column syntax at all, so "add and then drop the default" is impossible, and the fallback is a rebuild with no default in the DDL.

# rebuilds, because default=False gives an effective default
models.BooleanField(default=False)

# also rebuilds, because it is not null
models.BooleanField()

# does not rebuild: nullable, no default
models.BooleanField(null=True)

One word, default=False, buys a full rebuild, and nothing warns you.

A database-level default does not save you

models.PositiveSmallIntegerField(db_default=Value(0))

The last condition in the chain is happy with a constant, so it does not fire. But the not-null condition earlier already short-circuited, and control never reaches it, so on SQLite a constant database default cannot avoid the rebuild. I would not have believed that without reading the source; the documentation does not say it.

Nine: four ways out

A: design the column as nullable

migrations.AddField(
    model_name="article",
    name="reading_minutes",
    field=models.PositiveSmallIntegerField(null=True),
)

Nullable with no default makes the whole chain fall through to the real alter, in milliseconds. The cost is that a field which should be required now lies about it, and every later query carries a null branch. Use it only when the field genuinely can be empty.

B: separate the state from the database work

This is the mechanism Django provides for exactly this mismatch: let the model state believe the field was added normally, and let the database execute the cheap statement you wrote.

migrations.SeparateDatabaseAndState(
    # tell the model state the field exists
    state_operations=[
        migrations.AddField(
            model_name="article",
            name="reading_minutes",
            field=models.PositiveSmallIntegerField(default=0),
        ),
    ],
    # tell the database to add it the cheap way
    database_operations=[
        migrations.RunSQL(
            sql=(
                "ALTER TABLE articles_article "
                "ADD COLUMN reading_minutes integer unsigned NOT NULL DEFAULT 0"
            ),
            reverse_sql=(
                "ALTER TABLE articles_article DROP COLUMN reading_minutes"
            ),
        ),
    ],
)

The same operation drops from 8,381 milliseconds to 7.4. Three cautions.

The state definition must match the model exactly, or the next detection pass produces an alter and you are back where you started; the default in Python and the default in SQL must agree. The raw SQL is not portable, since the unsigned modifier and the type names differ per engine, so a cross-database project branches on the vendor. And the statement bypasses the schema editor entirely, so quoting, backend abstraction and transaction wrapping are yours, which means running it against a copy before shipping.

def add_column(apps, schema_editor):
    vendor = schema_editor.connection.vendor
    ddl = {
        "sqlite": "ALTER TABLE articles_article ADD COLUMN reading_minutes integer unsigned NOT NULL DEFAULT 0",
        "mysql": "ALTER TABLE articles_article ADD COLUMN reading_minutes INT UNSIGNED NOT NULL DEFAULT 0, ALGORITHM=INSTANT",
        "postgresql": "ALTER TABLE articles_article ADD COLUMN reading_minutes smallint NOT NULL DEFAULT 0",
    }[vendor]
    schema_editor.execute(ddl)

C: accept the rebuild and treat it as a change

If the field truly must be not null with no sensible default, the rebuild may be unavoidable. Then run it as a real change. Time it against a copy, with the database pointed at the copy. Triple the measured duration as the budget, because production has more rows, more indexes and busier disks. Back up with the database's own backup command rather than a file copy, since the backup command handles a database that is being written to. Run it in a window with the web processes stopped, then vacuum, then start them. And vacuum immediately after, to return the free pages.

D: remove the need to rebuild

class ArticleBody(models.Model):
    article = models.OneToOneField(Article, on_delete=models.CASCADE, related_name="body")
    content = models.TextField()
    html_content = models.TextField()
    excerpt = models.TextField()

The size accounting already pointed at this: nearly eight hundred megabytes of text. Split it out and the article table holds metadata only, tens of megabytes, and every future migration is an order of magnitude cheaper because there is an order of magnitude less to copy. The cost is one join, or a select-related, on detail pages, which is acceptable since list pages never read the body at all.

The takeaway worth carrying: rather than optimising migrations repeatedly, make the table smaller. Table size is the foundation of migration cost.

Ten: MySQL and PostgreSQL

MySQL: instant is real, and Django will not add the hint

ALTER TABLE articles_article
  ADD COLUMN reading_minutes INT UNSIGNED NOT NULL DEFAULT 0,
  ALGORITHM=INSTANT;

The landmine: instant only applies when the column goes at the end of the table. Ask for a position in the middle and it falls back to copying, which is a rebuild. So always append new columns.

PostgreSQL: concurrent builds need a non-atomic migration

class Migration(migrations.Migration):
    atomic = False          # required, or the concurrent build errors out
    dependencies = [("articles", "0006_articlelike")]
    operations = [
        migrations.RunSQL(
            "CREATE INDEX CONCURRENTLY articles_status_top_created_idx "
            "ON articles_article (status, is_top DESC, created_at DESC)",
            reverse_sql="DROP INDEX CONCURRENTLY articles_status_top_created_idx",
        ),
    ]

from django.contrib.postgres.operations import AddIndexConcurrently

class Migration(migrations.Migration):
    atomic = False
    operations = [
        AddIndexConcurrently(
            model_name="article",
            index=models.Index(
                fields=["status", "-is_top", "-created_at"],
                name="articles_status_top_created_idx",
            ),
        ),
    ]

The landmine is that a non-atomic migration loses atomicity: a failure at step three leaves the first two applied, and a failed concurrent build leaves an invalid index that reads ignore but writes still pay for, until it is dropped and retried by hand.

PostgreSQL: not null in two steps

-- step 1: add the constraint without validating, brief exclusive lock
ALTER TABLE articles_article
  ADD CONSTRAINT article_reading_minutes_not_null
  CHECK (reading_minutes IS NOT NULL) NOT VALID;

-- step 2: validate, takes a weaker lock and does not block writes
ALTER TABLE articles_article VALIDATE CONSTRAINT article_reading_minutes_not_null;

From version twelve, if a validated check constraint already proves the column has no nulls, the not-null conversion skips the scan entirely.

Eleven: lock timeout

The queue pile-up is the quietest killer. PostgreSQL has a one-line answer:

SET lock_timeout = '3s';

An alter table needs an exclusive lock that conflicts with every other lock. It queues, and once it is queued every later read queues behind it, because the queue is strictly first come, first served. A sixty second slow query therefore holds the alter table in line for sixty seconds, and the alter table blocks every ordinary query for the same span. One DDL takes the site down.

With a three second timeout, the DDL gives up instead of blocking the queue, and you retry later.

SQLite's equivalent is the busy timeout, with a different semantic because the lock is database-wide and there is no first-come queue. For SQLite the practical setup is:

PRAGMA busy_timeout = 10000;   -- ten seconds, room for DDL
PRAGMA journal_mode = WAL;     -- reads are not blocked by writes

from django.db.backends.signals import connection_created

@receiver(connection_created)
def set_sqlite_pragmas(sender, connection, **kwargs):
    if connection.vendor != "sqlite":
        return
    with connection.cursor() as cursor:
        cursor.execute("PRAGMA journal_mode=WAL;")
        cursor.execute("PRAGMA busy_timeout=10000;")
        cursor.execute("PRAGMA synchronous=NORMAL;")

The normal sync level still guarantees crash consistency under WAL, losing at most the last transaction on a power cut, and buys an order of magnitude on write throughput, which for a blog is the right trade.

Twelve: expand and contract

Everything so far makes one DDL faster. Real zero-downtime migration splits one dangerous change into several safe ones under a single constraint: at every moment, the running code and the running schema must be compatible.

Deployment is not atomic. After a push, old and new code coexist for a while across workers, restarts and caches. If the migration already dropped a column the old code still reads, that is a 500.

A real example, adding a not-null column with a backfill, in five releases.

Release one, expand: add the column as nullable, in milliseconds, invisible to the old code.

migrations.SeparateDatabaseAndState(
    state_operations=[migrations.AddField(
        model_name="article", name="reading_minutes",
        field=models.PositiveSmallIntegerField(null=True),
    )],
    database_operations=[migrations.RunSQL(
        "ALTER TABLE articles_article ADD COLUMN reading_minutes integer unsigned NULL",
        reverse_sql="ALTER TABLE articles_article DROP COLUMN reading_minutes",
    )],
)

Release two, dual write: new code writes both sides and still reads the old field.

def save(self, *args, **kwargs):
    if self.reading_minutes is None:
        self.reading_minutes = estimate_reading_minutes(self.content)
    super().save(*args, **kwargs)

Release three, backfill in batches, as a management command rather than a migration, because a migration that backfills a hundred thousand rows is one transaction as bad as a rebuild and has to start over on failure.

class Command(BaseCommand):
    def add_arguments(self, parser):
        parser.add_argument("--batch-size", type=int, default=200)

    def handle(self, *args, **options):
        size = options["batch_size"]
        qs = Article.objects.filter(reading_minutes__isnull=True)
        while True:
            batch = list(qs.values_list("pk", "content")[:size])
            if not batch:
                break
            for pk, content in batch:
                Article.objects.filter(pk=pk).update(
                    reading_minutes=estimate_reading_minutes(content)
                )
            self.stdout.write(f"backfilled {len(batch)}")
            time.sleep(0.05)      # yield the lock

Release four, switch reads to the new field and drop the dual write.

Release five, contract: tighten the constraint, with an unvalidated check and a separate validation on PostgreSQL, or a timed rebuild on SQLite. Drop the old column only if you are certain there will be no rollback, and preferably one release later, because dropping is irreversible.

Deciding whether a change can roll back

Ask one question: if I roll the code back right after migrating, does it still run?

ChangeRollback safe
Add a nullable columnYes, the old code ignores it
Add an indexYes
Drop a columnNo, the old code looks for it
Change a column typeUsually no
Add a not-null constraintDepends on whether the old code always writes a value

Changes that can roll back ship whenever. The rest go through expand and contract.

Thirteen: checklist

Before any migrate, in order.

  • Render the SQL and look for a temporary table name.
  • Run the plan output, since more than your migration may apply.
  • Test against a copy and record the duration.
  • Back up with the database's own backup command, not a file copy.
  • Check that free space covers twice the database size.
  • Confirm WAL is on.
  • Stop the web processes before a rebuild.
  • Run migrations non-interactively.
  • Run migrations in exactly one place, not on every worker start.
  • Vacuum afterwards.
  • Run the framework's own checks.
  • Open the site and verify the list page, the detail page and the admin.
  • Compare response times against the pre-migration baseline.
  • Move large text columns out of the hot table.
  • For any new not-null field, ask whether it can be nullable or use the separated state mechanism.
  • Put the SQL rendering command in continuous integration so dangerous migrations surface before merge.

Closing

Before writing this I thought of a migration as code that changes a schema. Now I think of it as a git push that rewrites 783 megabytes on disk while holding the whole table.

What changed the model was opening the translation layer between Python and SQL and looking inside. A field addition reads like adding a field; the SQL says rebuilding the table, and the distance between those two sentences is the entire space in which incidents happen.

Three numbers. 7.4 milliseconds for what the engine really costs. 8,381 milliseconds for what the framework pays. 1,130 times between them, entirely from one condition in the schema editor.

On a database with nine articles you will never see any of them. Rebuilding nine rows takes about a millisecond and nobody reads a temporary table name twice. That is the trap: a migration is always safe on a developer machine and becomes an incident only once the data has grown.

The previous post left a to-do about fixing the index in the model. Now I know how: not by running the generator, but by rendering the SQL first to confirm it will not trigger a rebuild along the way, and splitting into an index operation plus a separated state operation if it will.

Look at the SQL before you press enter.
