Preface: why build another browser

NanoBrowser is an open-source project (at zhoujungis/NanoBrowser) that asks a small engineering question: if I refuse to bundle all of Chromium, can I still build a desktop browser that feels like Chrome?

Most "build your own browser" attempts slide toward the same answer: bundle Chromium or Electron, ship an installer that starts at 100 MB, and give every app its own copy of the engine and its own memory footprint. By 2026 nobody wants to pay that for what is, after all, a shell.

NanoBrowser takes the other road: build no engine, only the shell. Rendering is the WebView2 already installed on Windows (the system's Chromium/Edge); the app does tabs, address bar, bookmarks, history, downloads, find-in-page, shortcuts and themes — plus something harder: wiring the DevTools protocol into the process.

The result is two binaries: the visible GUI browser nanobrowser.exe at about 4.52 MB, and the headless automation browser nanoagent.exe at about 4.24 MB. Both share one library crate and one in-process DevTools protocol bridge.

What it does, ordered by how quickly you notice: a Chrome-style tab strip with drag reordering (FLIP-animated), pin/unpin, middle-click close, per-tab context menus, overflow handling and Ctrl+Shift+T to reopen the last closed tab; a complete shell — omnibox with suggestions, bookmarks bar, find in page, download manager, history, zoom, light/dark/system themes and native window buttons; docked DevTools that loads the real DevTools frontend into a child webview of the same window, dockable to the bottom or right, with a draggable splitter — not a popup; nano:// internal pages for new tab, history, bookmarks, downloads, settings and about; and a headless agent exposed both as one-shot CLI commands and as an MCP server over stdio, with redacted traffic capture, trusted input synthesis and screenshots.

Worth noting: the entire front end is hand-written HTML/CSS/JS with no bundler — no npm, no Vite, no framework. That is not novelty for its own sake; it is a deliberate size and complexity trade whose costs are covered later.

The three counter-intuitive decisions

One: build no engine. NanoBrowser contains no rendering engine, no disassembler, no JS engine. It drives the WebView2 already installed on the system. The cost is "Windows only" (the whole stack rests on WebView2's COM interop); the benefit is a size in the single-digit megabytes and automatic sharing of the system's security updates.

Two: never open a debugging port. Neither the GUI nor the agent passes --remote-debugging-port. All CDP traffic goes through the in-process ICoreWebView2::CallDevToolsProtocolMethod. The counter-intuitive part: the DevTools panel does need a WebSocket, but that socket is a loopback service the process opens itself — not a debugging port exposed by the browser. It has an admission requirement, its lifetime is tied to the panel, and nothing outside the process can use it.

Three: hand-write the hard dependencies. The hardest piece — the WebSocket bridge DevTools talks to — is the project's own SHA-1 handshake, base64 accept key and text/close frame codec. No tungstenite, no similar library.

Together they define the project's character: reuse what the system already has, and shrink the self-written surface to the layer that must be written and is worth writing.

Two Tauri features are enabled and both are mandatory:

unstable gates the whole child-webview API surface (add_child, get_webview, per-webview devtools(false)); without it the core topology does not exist. devtools exposes the ICoreWebView2 interop the protocol bridge needs.

Core 1: N+1 webviews in a single window

This is the architectural bedrock. NanoBrowser has exactly one OS window. Inside it live up to three kinds of child webview, each a sibling HWND (not a parent-child relation):

┌─ main window ─────────────────────────────────────────────┐
│  shell webview  (label "shell")   ← y: 0 .. shell_h       │
│    tab strip (40) + toolbar (44) + bookmarks bar (28)      │
├──────────────────────────┬────────────────────────────────┤
│  page webview            │  devtools panel webview        │
│  (label "tab-<id>")      │  (label "devtools")            │
│  one per tab, only the   │  exists only while open;       │
│  active one is visible   │  bottom or right               │
└──────────────────────────┴────────────────────────────────┘
  • shell: the trusted chrome (ui/index.html), holder of every IPC command — the only "trusted" webview in Tauri terms.
  • tab-<id>: one child webview per tab, created lazily, hidden and shown on switch. All tab webviews share one WebView2 user-data directory, so cookies and login state are shared across tabs.
  • devtools: the docked panel, created on first open.

Layout is computed in Rust (tabs.rs::layout) and applied per webview with set_position / set_size. The shell height is derived, not guessed: shell_h = STRIP_H(40) + TOOLBAR_H(44) + (bookmarks_bar ? BM_H(28) : 0) — 84 logical pixels without the bookmarks bar, 112 with it. Everything below is page area. Sizes are logical, scaled by scale_factor, so window coordinates and logical coordinates never get mixed on HiDPI.

AppState sits behind one Mutex: tabs, active, closed (the reopen stack), shell_h, profile, next_id, sys_dark, overlay, devtools_open, devtools_h, devtools_w and win_save_pending. A Tab carries id, label, url, title, loading, pinned, icon, internal, live, zoom index, back/forward flags, navigation counters and an opaque per-tab token (the key to the security model in part two).

The live flag matters: it says whether the tab's real webview exists yet. Tabs can exist logically without a webview, which is why session restore paints instantly.

The shell talks to Rust through 40 #[tauri::command]s: state reads, navigation, tab management, UI (zoom, suggestions, find, overlay, theme), DevTools control, and data (bookmarks, history, settings, downloads folder). Rust pushes state back through Tauri events — tabs-state, omnibox-state, bookmarks-changed, theme-changed, sys-theme, find-result, focus-omnibox, open-findbar, dt-drag. The front end never polls; Rust pushes. Even the window title is composed on the Rust side.

Why sibling HWNDs matter

This is the source of every counter-intuitive pitfall later: child webviews are sibling HWNDs, and later-created ones paint above earlier ones. The shell is created first, page webviews later — so by default the page webview covers the shell. Two consequences: any shell UI that overflows the chrome region (main menu, omnibox suggestions, tab context menu) is clipped by the page webview; and a child webview cannot see pointer movement outside its own bounds, which makes DevTools drag-resizing genuinely awkward. Those are Core 5 and Core 4 below.

Core 2: the in-process CDP core

cdp.rs is the heart, shared by both binaries, and its design is shaped entirely by two properties of CallDevToolsProtocolMethod.

Property one: no {"id": ...} envelope. A debugging-port CDP client is used to sending {"id":7,"method":"Page.navigate","params":{...}} and matching replies by id. CallDevToolsProtocolMethod has no such layer: you pass a method and params, and the completion callback receives that method's result object — no id, no envelope. Replies therefore cannot be matched by id.

The solution: assign each call an incrementing sequence number (AtomicU64), bake it into the callback closure created for that call, and dispatch the result to the matching waiter when the callback fires.

Property two: callbacks run on the WebView2 (UI) thread. This is the deadlier one. Waiting for a callback on that thread is waiting for yourself — an instant deadlock, and one that shows up especially easily in the hidden-window agent. So the calling model is:

  • every call is fire-and-forget: issue and return;
  • the caller is always a worker thread, never the UI thread; it blocks on a Mutex + Condvar until the reply lands in shared state;
  • internally that means AtomicU64 seq + Mutex<Sink> + Condvar + a pending map of callback replies.

Two calling styles are exposed, with a strict split: call / call_raw / call_within block for a reply (30-second default timeout) and are used by the automation agent; send hands the reply to a callback and does not block, used by the DevTools WebSocket bridge, whose service loop runs on its own socket thread and would deadlock if it blocked. The timeout message is fixed: CDP <method> timed out — a trick worth copying, since the method name tells you where it hung.

Other details that matter: empty replies are normalized to null; on_event(event, cb) subscribes via GetDevToolsProtocolEventReceiver, and once registered the subscription belongs to WebView2 — the callback lives as long as the webview, so there is no unsubscribe, only destroying the webview; with_webview must be called off the main thread; and Cdp::webview() is the single entry point resolving both child webviews (tab-<id>, devtools) and a WebviewWindow (nanoagent).

Put together, cdp.rs does one thing: wrap a callback-based, UI-thread-bound COM interface with no request ids into a blocking, any-worker-thread, sequence-correlated Rust API. It is the most infrastructure-like piece in the project.

Core 3: a hand-written WebSocket server

The DevTools front end needs a WebSocket to speak. Rather than pull in tungstenite, the project implements the server in ws.rs.

Handshake, item by item: read HTTP headers from the TCP stream, with two guards — a 2048-byte read buffer and abandoning once headers exceed 16384 bytes; scan byte by byte until \r\n\r\n; take Sec-WebSocket-Key and compute the accept key per RFC 6455 as base64(sha1(key + GUID)), with SHA-1, base64 and the accept helper all hand-written and the fixed GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11; reply 101 Switching Protocols with Sec-WebSocket-Accept.

Framing. take_frame handles masking, 1/2/4-byte length extensions and fragmentation (one logical message across several TCP reads); encode_frame picks the length encoding by payload size and never masks, as the RFC requires for server frames. Text, PONG and CLOSE are supported.

The heartbeat. After reading headers, Ws::accept does one small thing that shapes the whole bridge: s.set_read_timeout(25ms). That is not a failure timeout but the service loop's tick. The loop polls the socket: Ok(0) means the panel left; WouldBlock/TimedOut means no data yet, detected by is_idle(err). One thread therefore handles both panel messages and CDP events without select/epoll.

Tests use an independently written client encoder rather than round-tripping the decoder against itself, and cover: handshake completion with the exact 101 and accept value; a connection without the session key receiving no headers and no bytes at all (the assertion that this is not a public debugging port); a 70 KB payload restored across multiple reads; PING answered with PONG; and CLOSE answered with an empty-payload close frame.

Core 4: the docked DevTools panel

The most complex part of the project, and the most worth reading.

WebView2 does ship the real DevTools front end, but only through OpenDevToolsWindow — a separate window. A Chrome-style docked panel needs another route. Both easier options are rejected: --remote-debugging-port does not work because only the shell webview becomes a CDP target, so the official front end cannot attach to a page webview; and writing a minimal custom panel loses Elements, Console, Network and Sources.

The chosen route: the official front end plus an in-process loopback WebSocket bridge. The panel loads:

devtools://devtools/bundled/inspector.html?ws=127.0.0.1:PORT/devtools/page/<session-id>#nanoSide=bottom|right

devtools://devtools/bundled/ is the bundle WebView2 already ships; the panel speaks CDP over the loopback socket; and the dock side lives in the fragment, not the query string.

Appending a second query key after ?ws= (for example &nanoSide=right) makes WebView2's devtools:// handler fail the whole load, showing Chromium's "this page cannot be reached" error. A fragment is parsed by the browser before that handler, so it is safe.

There is a nastier follow-up: you cannot trust webview.url() while debugging this, because the error page still reports the URL you asked for. The reliable signals are whether the bridge received a client and how many domains it registered.

The bridge has three constraints that make it not a debugging port: it binds a random loopback port; it accepts only the single session id minted for this panel's URL (the path must be /devtools/page/<session-id>); and every CDP request is forwarded to a page webview through CallDevToolsProtocolMethod. A page that scans localhost finds a listener that answers nothing without that id, and the id exists only while the panel does. Nothing outside the process can attach to either browser.

Events expose a protocol gap: Schema.getDomains lists 35 domains but returns no event names, so events cannot be discovered dynamically. The project keeps a static event table and subscribes lazily per domain — only domains the front end actually enabled get subscriptions. Two robustness rules: a single failed subscription is skipped rather than abandoning the domain; and calls WebView2 does not implement (such as Page.startScreencast) are returned as CDP errors rather than breaking the bridge.

The bridge loop also normalizes empty replies to {} (the panel expects an object), wraps errors as JSON-RPC errors, extracts the domain from the method and deduplicates subscriptions per (tab, domain), and fills empty params with {} before pushing {"method":..., "params":...}.

Geometry is computed in devtools.rs::split, which returns the page rectangle and the panel rectangle — and takes state as parameters so docking rules are unit-testable without a window. Six constants: MIN_H 96, DEFAULT_H 320, MIN_PAGE_H 96 for bottom docking; MIN_W 240, DEFAULT_W 480, MIN_PAGE_W 240 for the right side. Bottom: page (content_w, content_h - h), panel (0, shell_h + page_h, content_w, h). Right: page (content_w - w, content_h), panel (page_w, shell_h, w, content_h). clamp_axis keeps both sides above their minimums, so neither can squeeze the other out. And open() lays out the window before making the panel visible, so it never flashes at the previous session's geometry.

Dragging the grip runs into the sibling-HWND limit: a child webview cannot see pointer movement outside itself, so a pointer leaving the panel onto the page is invisible to the panel. The fix routes the pointer through the shell: on pointer down the panel asks Rust for set_overlay(true), which expands the shell webview to the full window and raises it; a full-window capture layer (#dt-grab) forwards clientX/clientY to set_devtools_size; Rust computes devtools_h = clamp(window_h - clientY) for bottom docking or devtools_w = clamp(window_w - clientX) for the right; and pointer up tears the layer down. The same overlay flag serves both this and the menu-clipping fix — one mechanism, two scenarios.

Signalling without an IPC channel. The panel is a devtools:// document, where Tauri's IPC does not exist and window.chrome.webview does not exist either. Both normal channels are cut, so the panel talks to Rust with window.open('https://nano-dt.invalid/<action>', '_blank'): nano-dt.invalid can never resolve, Rust sees the popup request in on_new_window, reads the action from the path, and returns NewWindowResponse::Deny. Nothing navigates, nothing loads — the side effect is the message.

Lifecycle. F12, Ctrl+Shift+I and the main menu all call toggle_devtools; activate and create_tab call devtools::retarget so the panel follows the active tab; close_tab calls devtools::forget; pressing F12 inside the panel closes it; the dock side persists in settings.devtoolsSide, and switching sides reloads the panel so the grip lands on the correct edge. Every webview — shell, tabs and the panel — uses .devtools(false).

That last point deserves emphasis: .devtools(false) disables the native DevTools popup (AreDevToolsEnabled = false) but does not affect CallDevToolsProtocolMethod. So the project kills the native popup while keeping full CDP. That is the precondition for the whole docking approach.

Core 5: z-order and the overlay trick

The mine planted in Core 1: the page webview is created later and covers the shell, clipping every overflowing piece of shell UI. The fix is the chrome_overlay command → tabs.rs::set_overlay: while a menu or suggestion list is open, expand the shell webview to the whole window and raise it with SetWindowPos(HWND_TOP); on close, restore it to shell_h; and after any tab create/activate/close, ensure_shell_top re-asserts z-order, or the new page webview climbs back over the chrome.

SetWindowPos(hwnd, HWND_TOP, 0, 0, 0, 0,
             SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)

Read together: change z-order only — no move, no resize, no focus steal, stay visible. SWP_NOACTIVATE is the one people forget; without it every menu open re-activates the window and focus jumps.

So "expand and raise" is reused by exactly two things: menu overflow and panel grip dragging. One mechanism, two scenarios — one of the few places the abstraction is exactly right-sized.
