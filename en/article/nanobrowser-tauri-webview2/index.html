NanoBrowser, part 1: a Chrome-like browser that ships no engine

2026-10-16 · 25 min · Stack Frame

NanoBrowser is an open-source project at zhoujungis/NanoBrowser. It asks one small question: if I refuse to bundle Chromium, can I still ship a desktop browser that feels like Chrome?

Most attempts at this drift the same way. Chromium or Electron goes into the installer, the download starts at 100 MB, and every app carries its own copy of the engine and its own memory footprint. Nobody wants to pay that for a shell.

NanoBrowser takes the other road: build no engine, only the shell. Rendering is the WebView2 already installed on Windows. The app does tabs, an address bar, bookmarks, history, downloads, find-in-page, shortcuts and themes, plus something harder: it wires the DevTools protocol into its own process.

The result is two binaries. The visible browser nanobrowser.exe is about 4.52 MB. The headless automation browser nanoagent.exe is about 4.24 MB. They share one library crate and one in-process protocol bridge.

This is part one of two. Part two covers the tab engine, the headless agent, the five security layers and the fourteen pitfalls that cost real debugging time.

What it does

BinaryPurposeRelease size
nanobrowser.exeVisible GUI browser~4.52 MB
nanoagent.exeHeadless automation browser (CLI and MCP)~4.24 MB

The browser side covers a full Chrome-shaped surface. Tabs drag to reorder with FLIP animation, pin and unpin, close on middle click, and reopen with Ctrl+Shift+T. There is an omnibox with suggestions, a bookmarks bar, find-in-page, a download manager, history, zoom, light and dark themes, and native window buttons.

The unusual part is DevTools. The real DevTools frontend loads into a child webview of the same window, docked to the bottom or the right, resizable by dragging a splitter. It is not a popup.

Internal pages live under nano://: new tab, history, bookmarks, downloads, settings, about. The agent half runs as one-shot CLI commands or as an MCP server over stdio, with redacted traffic capture, trusted input synthesis and screenshots.

The frontend is hand-written HTML, CSS and JavaScript with no bundler. No npm, no Vite, no framework. That is a size and complexity trade, and the costs show up later.

Three decisions that go against instinct

No engine. The project contains no rendering engine, no disassembler, no JavaScript engine. It drives the WebView2 already on the machine. The cost is Windows-only, because the whole stack rests on WebView2's COM interop. The benefit is single-digit megabytes and the system's security updates for free.

No debugging port, ever. Neither binary passes --remote-debugging-port. All CDP traffic goes through ICoreWebView2::CallDevToolsProtocolMethod inside the process. The DevTools panel does need a WebSocket, but that socket is a loopback service the process opens itself. It has an admission requirement, it lives only while the panel lives, and nothing outside the process can use it.

Hand-write the hard dependencies. The WebSocket bridge behind DevTools is implemented here: SHA-1 handshake, base64 accept key, text and close frame codec. No tungstenite, no equivalent library.

The three add up to a rule: reuse what the system already has, and shrink the self-written surface to the part that must be written and is worth writing.

Two Tauri features are enabled and both are required:

unstable gates the child webview API: add_child, get_webview, per-webview devtools(false). Without it the core topology does not exist. devtools exposes the ICoreWebView2 interop the bridge needs.

The release profile is tuned entirely for size: opt-level = "s", lto = true, codegen-units = 1, strip = true, panic = "abort". That last flag has a consequence worth knowing. There is no catch-unwind safety net, so every panic ends the process, which is why the code returns Option or Err at boundaries instead of writing first and fixing later.

Core 1: N+1 webviews in one window

The architecture rests on one fact. NanoBrowser has exactly one OS window, and inside it live up to three kinds of child webview, each a sibling HWND rather than a true child.

┌─ main window ─────────────────────────────────────────────┐
│  shell webview  (label "shell")   ← y: 0 .. shell_h       │
│    tab strip (40) + toolbar (44) + bookmarks bar (28)      │
├──────────────────────────┬────────────────────────────────┤
│  page webview            │  devtools panel webview        │
│  (label "tab-<id>")      │  (label "devtools")            │
│  one per tab, only the   │  exists only while open;       │
│  active one is visible   │  bottom or right               │
└──────────────────────────┴────────────────────────────────┘

The shell is the trusted chrome at ui/index.html, and it holds every IPC command. Each tab gets its own webview under the label tab-<id>, created lazily and hidden or shown on switch. All tab webviews share one WebView2 user-data directory, so cookies and login state carry across tabs. The DevTools panel is created the first time it opens.

Layout is computed in Rust and applied per webview with set_position and set_size. The shell height is derived, not guessed: STRIP_H(40) + TOOLBAR_H(44) + (bookmarks_bar ? BM_H(28) : 0), which is 84 logical pixels, or 112 with the bookmarks bar. Everything below is page area. Sizes are logical and scaled by scale_factor, so window coordinates and logical coordinates never mix on a HiDPI display.

AppState sits behind a single mutex and holds the tab list, the active id, the reopen stack, the shell height, the profile, the id counter, the system dark flag, the overlay flag, and the DevTools state. A Tab carries its id, label, URL, title, loading state, pin state, icon, internal flag, a live flag, zoom index, back and forward availability, navigation counters, and an opaque per-tab token that the security model depends on.

The live flag is the interesting one. It says whether the tab's real webview exists yet, because a tab can be logically open before it has a webview. That is why session restore paints immediately.

The shell reaches Rust through 40 commands covering state, navigation, tabs, UI, DevTools and data. Rust pushes state back through Tauri events: tab state, omnibox state, bookmark changes, theme changes, find results, focus requests and drag state. The frontend never polls. Even the window title is composed on the Rust side.

Why sibling HWNDs matter

This is the source of every counter-intuitive problem later in the post. Child webviews are sibling HWNDs, and later-created windows paint above earlier ones. The shell is created first and page webviews after it, so by default the page covers the shell.

Two consequences follow. Any shell UI that overflows the chrome area, such as the main menu, the omnibox dropdown or a tab context menu, is clipped by the page webview. And a child webview cannot see pointer movement outside its own bounds, which makes drag-resizing the DevTools panel awkward in a way that has nothing to do with DevTools.

Core 2: the in-process CDP core

cdp.rs is the heart of the project, shared by both binaries, and its shape comes from two properties of CallDevToolsProtocolMethod.

There is no {"id": ...} envelope. A CDP client written against a debugging port sends {"id":7,"method":"Page.navigate","params":{...}} and matches the reply by id. CallDevToolsProtocolMethod has no such layer. You pass a method and params, and the completion callback receives that method's result object. No id. No envelope.

Replies therefore cannot be matched by id. The project assigns each call an incrementing sequence number, bakes it into the callback closure created for that call, and dispatches the result to the matching waiter when the callback fires.

The callback runs on the WebView2 UI thread. This one is worse. Waiting for a callback on that thread means waiting for yourself, which deadlocks immediately, and it happens most easily in the hidden-window agent.

So every call is fire-and-forget, and the caller is always a worker thread, never the UI thread. The caller parks on a condition variable until the reply lands in shared state. Internally that is an atomic sequence counter, a mutex-guarded sink, a condition variable, and a pending map for callback replies.

Two calling styles sit on top, and the split is a hard constraint rather than a preference. The blocking style waits for a reply with a 30-second default timeout and is used by the automation agent. The non-blocking style hands the reply to a callback and is used by the DevTools bridge, whose service loop runs on its own socket thread and would deadlock if it blocked.

The timeout message is CDP <method> timed out. Putting the method name in the error is worth copying, because it tells you where it hung.

A few more details matter. Empty replies are normalized to null rather than an empty string. on_event subscribes through GetDevToolsProtocolEventReceiver, and once registered the subscription belongs to WebView2, so the callback lives as long as the webview and there is no unsubscribe. with_webview must be called off the main thread. And Cdp::webview() is the single entry point that resolves both child webviews and the agent's window.

All of that adds up to one job: turn a callback-based, UI-thread-bound COM interface with no request ids into a blocking, worker-thread-safe, sequence-correlated Rust API. It is the most infrastructure-like piece of the project.

Core 3: a hand-written WebSocket server

The DevTools frontend needs a WebSocket, and the project implements the server itself in ws.rs.

The handshake reads HTTP headers from the TCP stream with two guards: a 2048-byte read buffer, and abandonment once headers exceed 16384 bytes. It scans for the blank line, takes Sec-WebSocket-Key, and computes the accept key as base64(sha1(key + GUID)) against the fixed GUID. SHA-1, base64 and the accept helper are all written here.

Framing handles masking, 1/2/4-byte length extensions, and fragmentation, where one logical message arrives across several reads. Outgoing frames never mask, as the RFC requires of servers. Text, PONG and CLOSE are supported.

After the handshake, accept sets a 25 ms read timeout. That is not a failure timeout. It is the service loop's tick. The loop polls the socket: a zero-byte read means the panel left, and a would-block result means no data yet. One thread therefore handles both panel messages and CDP events without select or epoll.

The tests use an independently written client encoder rather than round-tripping the decoder against itself. They cover a completed handshake with the exact status and accept value, a connection without the session key receiving no headers and no bytes at all, a 70 KB payload reassembled across reads, PING answered with PONG, and CLOSE answered with an empty-payload close.

Core 4: the docked DevTools panel

This is the hardest part of the project and the most worth reading.

WebView2 does ship the real DevTools frontend, but only through OpenDevToolsWindow, which is a separate window. A Chrome-style docked panel needs another route, and both easier options are dead ends. --remote-debugging-port fails because only the shell webview becomes a CDP target, so the official frontend cannot attach to a page. Writing a minimal custom panel loses Elements, Console, Network and Sources.

The route taken is the official frontend plus an in-process loopback WebSocket bridge. The panel loads a devtools://devtools/bundled/inspector.html URL with the socket address in the query string and the dock side in the fragment.

Appending a second query key after ?ws= makes WebView2's devtools:// handler fail the entire load, and the panel shows Chromium's "this page cannot be reached" error. A fragment is parsed by the browser before that handler runs, so it is safe.

There is a nastier follow-up. While debugging this, webview.url() lies, because the error page still reports the URL you asked for. The reliable signals are whether the bridge received a client and how many domains it registered.

Three constraints keep the bridge from being a debugging port. It binds a random loopback port, it accepts only the single session id minted for this panel's URL, and every CDP request is forwarded to a page webview through CallDevToolsProtocolMethod. A page that scans localhost finds a listener that answers nothing without that id, and the id exists only while the panel does.

Events exposed a gap in the protocol. Schema.getDomains lists 35 domains and returns no event names, so events cannot be discovered dynamically. The project keeps a static event table and subscribes lazily per domain, only for domains the frontend actually enabled. Two robustness rules follow: a failed subscription is skipped rather than abandoning the domain, and calls WebView2 does not implement, such as Page.startScreencast, come back as CDP errors instead of breaking the bridge.

Geometry is computed in one function that returns both the page rectangle and the panel rectangle, and takes state as a parameter so docking rules are unit-testable without a window. Six constants bound it: minimum and default panel size for each dock side, plus a minimum page size. The two minimums are enforced together, so neither the panel nor the page can squeeze the other out of existence.

Dragging the splitter runs into the sibling-window limit. A child webview cannot see pointer movement outside itself, so the pointer leaving the panel is invisible to the panel. The fix routes the pointer through the shell. On pointer down the panel asks Rust to expand the shell over the whole window and raise it. A full-window capture layer in the shell forwards coordinates to a command that computes the new panel size. On pointer up the layer is removed. The same overlay flag serves this and the menu-clipping fix, which is one mechanism for two problems.

Signalling needed a trick, because the panel loads a devtools:// document where Tauri's IPC does not exist and window.chrome.webview does not exist either. Both normal channels are cut. So the panel calls window.open with a URL on nano-dt.invalid, a domain that can never resolve. Rust sees the popup request, reads the action from the path, and denies it. Nothing navigates and nothing loads. The side effect is the message.

Lifecycle is small but precise. F12, Ctrl+Shift+I and the main menu toggle the panel. Activating or creating a tab retargets the panel so it follows the active tab. Closing a tab forgets its protocol state. Pressing F12 inside the panel closes it. The dock side persists in settings, and switching sides reloads the panel so the splitter lands on the right edge.

Every webview, including the panel itself, calls .devtools(false). That disables the native DevTools popup and does not affect CallDevToolsProtocolMethod, which is what makes the whole docking approach possible.

Core 5: z-order and the overlay trick

The mine planted in Core 1 needs defusing. The page webview is created later, so it covers the shell and clips every overflowing menu.

While a menu or suggestion list is open, the shell expands to the whole window and is raised with SetWindowPos against HWND_TOP. On close it returns to its normal height. After any tab create, activate or close, a helper re-asserts z-order, because the new page webview would otherwise climb back on top.

SetWindowPos(hwnd, HWND_TOP, 0, 0, 0, 0,
             SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)

The flags read together mean: change z-order only. No move, no resize, no focus steal, stay visible. SWP_NOACTIVATE is the one people forget, and without it every menu open re-activates the window and focus jumps.

So "expand and raise" is used by exactly two things, menu overflow and splitter dragging. One mechanism, two scenarios.
