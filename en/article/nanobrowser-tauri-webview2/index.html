NanoBrowser, part 1: a Chrome-like browser that ships no engine

2026-10-16 · 25 min · Stack Frame

NanoBrowser is an open-source project at zhoujungis/NanoBrowser, and it asks one small engineering question.

If I refuse to bundle all of Chromium, can I still build a desktop browser that works like Chrome?

Most attempts at this slide towards the same answer. Chromium or Electron goes into the package, the installer starts at 100 MB, and every application carries its own copy of the engine and its own memory footprint. As of 2026, nobody wants to pay that for a shell.

NanoBrowser takes the other road: build no engine, only the shell. Rendering is the WebView2 already installed on Windows, which is the system's copy of Chromium and Edge. The application does the shell work: tabs, address bar, bookmarks, history, downloads, find in page, shortcuts and themes. It also does something harder, which is to wire the DevTools protocol into its own process.

The result is two binaries. The visible GUI browser, nanobrowser.exe, is about 4.52 MB. The headless automation browser, nanoagent.exe, is about 4.24 MB. Both share one library crate and one in-process DevTools protocol bridge.

This post does not sell concepts. It takes the implementation apart. The technical density is concentrated in four places: three kinds of sibling window inside one window, speaking CDP with no debugging port, hand-writing a SHA-1 handshake and a frame codec, and loading the official DevTools frontend into a child webview with a draggable docked panel. Each of those has a detail you only learn by trying it.

This is part one of two. Part two covers the tab engine, the headless agent, the five security layers and the fourteen pitfalls.

One minute

A Chrome-shaped browser shell written in Tauri 2, plus a headless browser that AI tools can drive.

BinaryPurposeRelease size
nanobrowser.exeThe visible GUI browserAbout 4.52 MB
nanoagent.exeHeadless automation browser, CLI and MCPAbout 4.24 MB

Browser features, ordered by how quickly you notice them.

  • A Chrome-style tab strip. Drag to reorder with FLIP animation, pin and unpin, middle-click to close, a per-tab context menu, overflow handling, and Ctrl+Shift+T to reopen the last closed tab.
  • A complete shell. An omnibox with a suggestion dropdown, a bookmarks bar, find in page, a download manager, history, zoom, three-state theming (light, dark, follow system), and native window buttons.
  • Docked DevTools. The real official DevTools frontend loaded into a child webview of the same window, dockable to the bottom or the right, with a draggable splitter that resizes it. It is not a popup.
  • Internal pages under the nano:// scheme: new tab, history, bookmarks, downloads, settings and about.
  • A headless agent. One-shot CLI commands and an MCP server over stdio, with redacted traffic capture, trusted input synthesis and screenshots.

One thing is worth noting up front. The entire frontend is hand-written HTML, CSS and JavaScript with no bundler. No npm, no Vite, no framework. That is not novelty for its own sake. It is a deliberate trade of size and complexity, and the costs show up later in this post.

Three decisions that go against instinct

Decision one: no engine. NanoBrowser contains no rendering engine, no disassembler and no JavaScript engine. It drives the WebView2 that is already installed. The cost is Windows only, because the whole stack rests on WebView2's COM interop. The benefit is an application measured in single-digit megabytes that shares the system's security updates for free.

Decision two: never open a debugging port. Neither the GUI nor the agent passes --remote-debugging-port. All CDP traffic goes through ICoreWebView2::CallDevToolsProtocolMethod inside the process. The counter-intuitive part is this: the DevTools panel does need a WebSocket, but that socket is a loopback service the process opens for itself rather than a debugging port exposed by the browser. It has an admission requirement, its lifetime is tied to the panel, and nothing outside the process can use it.

Decision three: hand-write the hard dependencies. The hardest piece, the WebSocket bridge that DevTools talks to, is this project's own SHA-1 handshake, base64 accept key and text and close frame codec. No tungstenite, no similar library.

Together those three define the character of the project. Reuse what the system already provides, and shrink the self-written surface to the layer that must be written and is worth writing.

Two Tauri features are enabled, and both are required.

tauri = { version = "2", features = ["unstable", "devtools"] }

unstable gates the whole child webview API: adding a child, getting a webview, and per-webview devtools(false). Without it the core topology of this project does not exist. devtools exposes the ICoreWebView2 interop that the protocol bridge needs.

The release profile is tuned item by item for size.

[profile.release]
opt-level = "s"    # optimize for size, not speed
lto = true         # link-time optimization, cross-crate inlining and pruning
codegen-units = 1  # slower compiles in exchange for more aggressive optimization
strip = true       # drop symbols
panic = "abort"    # drop unwinding tables

Those lines together are what keeps a Rust and Tauri application at the 4 MB mark. Note the side effect of aborting on panic: there is no catch-unwind safety net, so any panic terminates the process. That is why the code prefers returning an option or an error at boundaries rather than writing first and worrying afterwards.

Two signals in that structure are worth attention.

Core 1: N+1 webviews in a single window

This is the architectural foundation, and the key to everything that follows.

Topology: three kinds of sibling window

NanoBrowser's entire interface is one operating-system window. Inside it live up to three kinds of child webview, and every child is a sibling HWND rather than a true child.

┌─ main window ───────────────────────────────────────────────┐
│  shell webview  (label "shell")   ← y: 0 .. shell_h         │
│    tab strip (40) + toolbar (44) + bookmarks bar (28, optional)
├──────────────────────────┬──────────────────────────────────┤
│  page webview            │  devtools panel webview          │
│  (label "tab-<id>")      │  (label "devtools")              │
│  one per tab, only the   │  exists only while open;         │
│  active one is visible   │  bottom or right                 │
└──────────────────────────┴──────────────────────────────────┘
  • shell. The trusted browser chrome at ui/index.html, holding every IPC command. In Tauri terms it is the only webview that is trusted.
  • tab-<id>. One child webview per tab, created lazily and hidden or shown on switch. All tab webviews share one WebView2 user-data directory, so cookies and login state carry across tabs.
  • devtools. The docked panel, created the first time it opens.

Layout is computed in Rust in tabs.rs::layout and applied to each webview with position and size calls.

Deriving the shell height

The chrome height is derived rather than guessed, from three pieces.

shell_h = STRIP_H(40) + TOOLBAR_H(44) + (bookmarks_bar ? BM_H(28) : 0)

That is 84 logical pixels without the bookmarks bar and 112 with it. The page area is everything below the chrome.

All of it is in logical pixels, Tauri's logical size and position types, with scaling folded in through the scale factor. The window-size helper reads the inner size and divides by the scale factor, so window coordinates and logical coordinates never get mixed on a HiDPI display.

A tab carries its id, label, URL, title, loading state, pin state, icon, an internal flag, a live flag, the zoom index, back and forward availability, navigation counters and pending navigation. It also carries an opaque per-tab token, which is central to the security model in part two.

The live flag deserves a note. It says whether the tab's real webview has been created yet. A tab can exist logically while its webview does not, which is exactly how session restore paints a window full of tabs immediately.

The IPC surface

The shell calls Rust through 40 commands, all in commands.rs and registered with one macro, grouped by purpose.

  • State reads: initial state, tabs, settings, bookmarks, history, downloads, top sites.
  • Navigation: navigate, new tab, activate, back, forward, reload, stop, internal navigation.
  • Tabs: close, toggle pin, move, duplicate, close others, close to the right, reopen.
  • UI: zoom, omnibox suggestions, find query, find move, find close, chrome overlay, system theme changed.
  • DevTools: toggle, set size, set side, drag end.
  • Data: add, remove and update bookmarks, delete and clear history, set settings, open the downloads folder.

Rust pushes state back through events: tab state, omnibox state, bookmark changes, theme changes, system theme, find results, focus requests, open find bar, and drag state.

One detail is worth copying: the frontend never polls and Rust pushes. The tab-state emitter serializes the whole tab list into an array of view models. The omnibox emitter sends the current tab's URL, title, loading state, zoom, star state, back and forward availability and id. Even the window title is composed on the Rust side.

title = current tab title is non-empty ? "<title> - NanoBrowser" : "NanoBrowser"

Why sibling windows matter

This single fact is the source of every counter-intuitive problem later in the post. Child webviews are sibling HWNDs, so a later-created window paints above an earlier one. The shell is created first and page webviews after it, so by default the page covers the shell.

Two consequences follow immediately.

  1. Any shell UI that overflows the chrome region, such as the main menu, the omnibox dropdown or a tab context menu, is clipped by the page webview.
  2. A child webview cannot see pointer movement outside its own bounds, which makes drag-resizing the DevTools panel genuinely awkward.

Those two consequences map to Core 5 and Core 4 below.

Core 2: the in-process CDP core

cdp.rs is the heart of the project, shared by both binaries. Its design is shaped by two properties of CallDevToolsProtocolMethod.

Property one: no request envelope

Anyone who has written a CDP client against a debugging port is used to this shape, with replies matched by id.

{"id": 7, "method": "Page.navigate", "params": {"url": "..."}}

CallDevToolsProtocolMethod has no such layer. You pass a method name and parameters, and its completion callback receives that method's own result object. No id, no envelope.

Replies therefore cannot be matched by id. The project's solution is to give each call an incrementing sequence number, allocated from an atomic counter, and bake that number into the callback closure created for that specific call. When the callback fires, the result is dispatched to the matching waiter.

Property two: callbacks run on the UI thread

The second property is more dangerous. The completion callback runs on the WebView2 UI thread. Waiting for that callback on that same thread means waiting for yourself, which deadlocks immediately, and the bug appears most easily in the hidden-window agent.

So the calling model is this.

  • Every call is fire-and-forget. It is issued and returns without waiting.
  • The caller is always a worker thread, never the UI thread. After issuing the request it blocks on a mutex and condition variable until the reply lands in shared state and wakes it.
  • Internally that is an atomic sequence counter for issuing, a mutex-guarded sink, a condition variable for waiting, and a pending map for callback-style replies.

Two calling styles

Two styles sit on top, with a strict split of purpose.

APIStyleWho uses it
call, call_raw, call_withinBlock for a reply, with a 30-second default timeoutThe automation agent
sendHand the reply to a callback, non-blockingThe DevTools bridge, which must not block because it answers on its own socket thread

That split is not a matter of taste. It is a hard constraint. The DevTools bridge service loop runs on its own thread, and if it blocked while issuing a CDP request it would deadlock against its own replies to the panel.

The default timeout is 30 seconds, and the error message is fixed.

CDP <method> timed out

Putting the method name in the error is worth copying, because when something hangs you can see which protocol method it hung on.

Other details that matter

  • Empty replies become null. Some CDP methods return nothing, so the callback receives an empty value. It is normalized to null rather than an empty string or undefined.
  • on_event subscribes through GetDevToolsProtocolEventReceiver. The important point: once registered, the subscription belongs to WebView2, so the callback lives as long as the webview does. There is no unsubscribe; the webview must go away.
  • with_webview must be called off the main thread. That thread constraint is easy to trip over.
  • Cdp::webview() is the single entry point. It resolves child webviews by label and also resolves a WebviewWindow. One implementation serves the GUI's three child webviews and the agent's main window, which is how "one core, two entry points" is cashed out in code.

Put together, cdp.rs does one job: wrap a callback-based COM interface that runs on the UI thread and has no request ids into a Rust API that can block, can be called from any worker thread, and correlates replies by sequence number. It is the most infrastructure-like piece in the project.

Core 3: a hand-written WebSocket server

The DevTools frontend needs a WebSocket to talk over. Rather than pull in tungstenite, the project writes the server by hand in ws.rs.

The handshake

It is the standard upgrade handshake, implemented item by item.

  1. Read HTTP request headers from the TCP stream, with two guards: a 2048-byte read buffer, and abandonment once headers exceed 16384 bytes, which stops anyone from flooding the port with an enormous header.
  2. Scan the headers byte by byte until the blank line, which is where the header section ends.
  3. Take Sec-WebSocket-Key and compute the accept key per RFC 6455, as the base64 of the SHA-1 of the key plus the fixed GUID. SHA-1 and base64 are both implemented here.
  4. Reply with 101 Switching Protocols and the accept header.

Frame codec

  • Receiving handles masking, the length extensions for one, two and four byte lengths, and fragmentation, where one logical message spans several reads.
  • Sending picks the length encoding by payload size. Server frames are not masked, as the RFC requires.
  • Text, pong and close are supported.

The heartbeat of the service loop

After reading the headers, the accept function does one small thing that decides the shape of the entire bridge.

s.set_read_timeout(25ms)

That is not a failure timeout. It is the service loop's tick. The loop polls the socket: a zero-byte read means the panel left, and a would-block or timed-out result means no data yet, detected by an idle check. One thread therefore handles both panel messages and CDP events, with no need for select or epoll.

Tests

tests/ws_bridge.rs validates the server with an independently implemented client encoder, deliberately not round-tripping the decoder against its own inverse. Coverage includes a completed handshake reporting its session path with the exact status and accept value; a connection without a session key receiving no headers and no bytes at all, which is the assertion that this port is not a public debugging port; a 70 KB payload reassembled across several reads; ping answered with pong; and close answered with an empty-payload close frame.

Core 4: the docked DevTools panel

This is the most complex part of the project and the most worth reading. The README gives it its own chapter.

Why it exists

WebView2 does ship the real DevTools frontend, but exposes it only through OpenDevToolsWindow, which creates a separate window. A Chrome-style panel docked inside the window needs another route.

Two easier routes were rejected.

  • --remote-debugging-port is not viable, because with that port open only the shell webview becomes a CDP target, and the official frontend cannot attach to a page webview.
  • Writing a minimal custom panel was rejected because it loses the complete Elements, Console, Network and Sources experience.

The route taken is the official frontend plus an in-process loopback WebSocket bridge.

The URL and the counter-intuitive fragment trap

devtools://devtools/bundled/inspector.html?ws=127.0.0.1:PORT/devtools/page/<session-id>#nanoSide=bottom|right
  • devtools://devtools/bundled/ is the DevTools bundle WebView2 already ships, so the frontend needs no packaging of its own.
  • It speaks CDP over a loopback WebSocket served by this process.
  • The dock side lives in the fragment, and cannot go into the query string.

That last line is the most valuable non-obvious constraint in the project.

Appending a second query key after ?ws=, for example &nanoSide=right, makes WebView2's devtools:// handler fail the entire load, and the page shows Chromium's "this page cannot be reached" error. A fragment is parsed by the browser before that handler sees it, so it is safe.

The trap has a nastier follow-up. While debugging it, webview.url() cannot be trusted, because the error page still reports the URL you asked for. The reliable signals are whether the bridge received a client, and how many domains it registered.

Admission: this is not a debugging port

The loopback WebSocket has three constraints.

  1. It binds to a random loopback port.
  2. It accepts only the one session id minted for this panel's URL. The request path must match, and anything else gets no response.
  3. Every CDP request is forwarded to a page webview through CallDevToolsProtocolMethod.

Why that is not a debugging port: a page scanning localhost finds a listener that answers nothing without the id, and the id exists only while the panel does. Nothing outside the process can attach to either browser. Combined with never passing the debugging-port flag, this is the "no debugging socket" layer of the security model.

Events: a static table plus lazy subscription

There is a very typical gap in the protocol here. Schema.getDomains reports 35 domains and returns no event names at all, so events cannot be discovered dynamically.

The solution is a static table of event names plus lazy subscription per domain: only the domains the frontend actually enabled get subscriptions. The table covers the common domains, such as runtime console calls, exceptions and execution contexts; debugger script parsed, paused and resumed; profiler start and finish; heap snapshot chunks and progress; console messages; and page lifecycle events including navigation, dialogs, screencast frames and downloads.

Two robustness rules sit on top.

  • A single failed subscription is skipped rather than abandoning the whole domain.
  • Page.startScreencast is not implemented on WebView2, which matters for the agent's screenshots. Calls like that come back to the frontend as CDP errors instead of breaking the bridge.

The bridge loop also normalizes empty replies to an empty object, because the panel expects one; wraps errors as JSON-RPC errors; extracts the domain from the method name and deduplicates subscriptions per tab and domain; and fills empty parameters before pushing an event to the panel.

Geometry: one split function and six constants

Panel sizing lives in one function that returns the page rectangle and the panel rectangle. The benefit is that docking rules can be unit-tested without a real window, because the state is passed in as an argument.

ConstantValueMeaning
MIN_H96Minimum panel height when docked at the bottom
DEFAULT_H320Height on first open at the bottom
MIN_PAGE_H96Minimum height left for the page
MIN_W240Minimum panel width when docked at the right
DEFAULT_W480Width on first open at the right
MIN_PAGE_W240Minimum width left for the page

For bottom docking, the page gets the content width and the content height minus the panel, and the panel sits at the bottom of the content. For right docking, the page gives up the panel width and the panel takes the right edge.

A clamp keeps both sides above their minimums, so a small window never squeezes the page out or the panel out.

There is also a timing detail. Opening computes the window layout before making the panel visible, so it does not flash at the previous session's geometry for one frame.

Dragging the splitter when a child webview cannot see outside itself

The panel edge has a grip. It runs into a physical limit: a child webview cannot see pointer movement outside its own bounds. The panel is only so tall or so wide, and once the pointer leaves it, the panel no longer receives pointer events.

The fix routes the pointer through the shell.

  1. On pointer down, the panel asks Rust to enable the overlay, which stretches the shell webview over the whole window and raises it.
  2. The shell has a full-window capture layer that forwards coordinates to a size command.
  3. Rust computes the new size:
bottom:  devtools_h = clamp(window_h - clientY)
right:   devtools_w = clamp(window_w - clientX)
  1. On pointer up, the capture layer is removed and the overlay is restored.

Note that this chain uses the same overlay mechanism as Core 5. One flag serves both purposes: keeping menus from being clipped, and letting the grip drag across boundaries.

Signalling between the panel and native code

This is the prettiest trick in the project. The panel is a devtools:// document, and in that environment Tauri's IPC does not exist, and WebView2's host object on the window does not exist either.

Both normal channels are cut. So the panel talks to Rust like this.

window.open('https://nano-dt.invalid/<action>', '_blank');

nano-dt.invalid is a domain that cannot exist, so it is never actually visited. Rust sees the popup request in its new-window handler, reads the action from the path, and returns a deny response.

NewWindowResponse::Deny

Nothing navigates and nothing loads. The popup request is the message. It is a textbook use of a side-effect channel as a signal channel.

Lifecycle

  • F12, Ctrl+Shift+I and the main menu all toggle the panel.
  • Activate and create-tab retarget it, so the panel follows the active tab.
  • Close-tab forgets the dead tab's protocol state.
  • Pressing F12 inside the panel closes it.
  • The dock side persists in settings, and switching sides reloads the panel so the grip lands on the correct edge.
  • Every webview, including the shell, the page tabs and the panel itself, calls .devtools(false).

That last line needs spelling out. .devtools(false) turns off the native DevTools popup, but it does not affect CallDevToolsProtocolMethod. So the project can kill the native popup and keep full CDP at the same time. That is one of the pitfalls the README lists, and it is the precondition for the whole docking approach.

Core 5: z-order and the overlay trick

Back to the mine planted in Core 1: the page webview is created later and covers the shell, clipping every piece of overflowing shell UI, including the main menu, the omnibox dropdown and the tab context menu.

The fix is the chrome-overlay command, which does three things.

  1. While a menu or suggestion list is open, stretch the shell webview over the whole window and raise it to the top of the z-order.
  2. On close, restore the shell to its normal chrome height.
  3. After any tab is created, activated or closed, re-assert the z-order, otherwise the newly created page webview climbs back over the chrome.
SetWindowPos(hwnd, HWND_TOP, 0, 0, 0, 0,
             SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)

The four flags together mean: change z-order only, without moving, resizing, stealing focus, or hiding. The one people forget is SWP_NOACTIVATE. Without it, every menu open re-activates the window and focus jumps.

So "stretch and raise" is reused in exactly two places: menu overflow and splitter dragging. One mechanism, two scenarios, and one of the few places in this project where the abstraction is exactly the right size.
