The Complete Guide to Google Matter Smart Home Development: From First Steps to Certification

Introduction

In 2022 the Connectivity Standards Alliance (CSA) formally released the Matter 1.0 specification, and Google, Apple and Amazon announced their support for it at the same time. As the long-awaited "unified" standard for the smart home, Matter set out to fix the ecosystem fragmentation that had dogged the industry for years — letting devices from different vendors interoperate across platforms and ecosystems. This article pulls together Google's official Matter developer documentation, hands-on experience with the ESP-Matter framework, and the field notes of several developers into a single, complete guide to Matter device development.

What Is the Matter Protocol?

1.1 What Is Matter?

Matter is an application-layer protocol built on top of the IPv6 network stack. It runs over the network technologies you already have:
  • Wi-Fi — for high-bandwidth devices (cameras, gateways)
  • Thread — for low-power devices (sensors, switches), based on IEEE 802.15.4
  • Ethernet — for fixed devices (smart speakers, routers)
  • Bluetooth Low Energy (BLE) — used for device commissioning only, never for day-to-day communication
This design lets Matter devices be addressed and controlled uniformly over an IP network, with no extra hub or protocol bridge in the middle.

1.2 Core Characteristics

Feature Description
Multi-Admin A single Matter device can belong to several ecosystems (fabrics) at once — controlled by both Google Home and Apple HomeKit, for example
Local control Device-to-device traffic prefers the local network: low latency, no dependency on the cloud
Security End-to-end encryption, device certificate attestation, and a dual mechanism of passcode-authenticated sessions (PASE, via SPAKE2+) and certificate-authenticated sessions (CASE)
Unified data model Every device uses the standardized Cluster/Attribute/Command model, which is what guarantees interoperability
Zero-touch commissioning A QR code scan or an NFC tap is all it takes to pair the device

1.3 Supported Device Types

The device categories Matter 1.0 covers include:
  • Lighting and electrical (bulbs, switches, dimmers)
  • HVAC (thermostats, air conditioners)
  • Security sensing (contact sensors, occupancy sensors, smoke alarms)
  • Door locks and window coverings
  • TVs and media devices
  • Bridges (bringing non-Matter devices onto a Matter network)

2. The Google Matter Development Ecosystem

Google gives Matter developers a complete toolchain and first-class platform support.

2.1 The Developer Tool Landscape

Tool Purpose Stage

Google Home Extension for VS Code Assistant simulator, cloud log viewer, device debugging Development and debugging
Matter Virtual Device (MVD) A Dockerized virtual Matter device, so you can develop without real hardware Early development

Android Studio Plugin Test Assistant commands and read cloud logs straight from the IDE App development

2.2 Google Play Services Matter API

For Android app developers, Google exposes a Matter API through Play Services. Its core capabilities are:
  • Commissioning — bring a Matter device onto the home network
  • Device Sharing — grant access to a device across apps and ecosystems
  • Operational Discovery — discover Matter devices already commissioned on the network
  • Thread Network API — share Thread network credentials through Play Services

2.3 About VID/PID

Development and production use different vendor identifiers:
  • Test VIDs: 0xFFF1, 0xFFF2, 0xFFF3, 0xFFF4 — for development and debugging only
  • Production VID: you must apply formally to the CSA, and Google has to verify it before it can be used on consumer products

How Do You Set Up a Matter Development Environment?

3.1 Base Environment Requirements

Developing Matter devices requires the following:
  • OS: Ubuntu 20.04 LTS (64-bit) or newer (recommended)
  • Python: 3.8+
  • Git: for cloning the Matter SDK
  • Development board (optional): ESP32-C3/C6/S3, nRF52840, Silicon Labs EFR32MG24, and so on
Note: macOS can build Matter projects too, but the official guidance strongly favors Ubuntu Linux. Windows users can set things up in a VirtualBox VM or under WSL2.

3.2 Cloning the Matter SDK

git clone https://github.com/project-chip/connectedhomeip.git
cd connectedhomeip
git submodule update --init --recursive

3.3 Installing Dependencies

# Ubuntu environment
sudo apt-get update
sudo apt-get install -y 
    git gcc g++ pkg-config libssl-dev 
    libdbus-1-dev libglib2.0-dev 
    libavahi-client-dev ninja-build 
    python3-venv python3-dev 
    unzip libgirepository1.0-dev 
    libcairo2-dev libreadline-dev

# Initialize the Matter build environment
source scripts/activate.sh

3.4 Setting Up the ESP32 Platform (with ESP-IDF)

For developers working with Espressif ESP32 chips: 
# Install ESP-IDF
mkdir -p ~/esp
cd ~/esp
git clone --branch v5.1 --recursive https://github.com/espressif/esp-idf.git
cd esp-idf
./install.sh esp32 esp32c3 esp32c6 esp32s3
source export.sh

# Clone the ESP-Matter SDK
cd ~/esp
git clone https://github.com/espressif/esp-matter.git
cd esp-matter
git submodule update --init --recursive

What Does the Matter Data Model Consist Of?

Understanding the Matter data model is the heart of device development. Matter uses a four-layer hierarchy, and it helps to picture it as a house:

4.1 Node (the "house")

A Node represents a single physical device and is the smallest addressable unit on the network. Every Node has a unique node ID, which corresponds to an IP address at the network layer. One physical device is one Node (a single smart bulb, for example). 
// Create a Matter node
node::config_t node_config;
node_t *node = node::create(&node_config, app_attribute_update_cb, app_identification_cb);
app_attribute_update_cb is the attribute update callback, invoked whenever a control command comes in. app_identification_cb is the identification callback, used to handle Identify commands (blinking the device so you can tell which one it is, for instance).

4.2 Endpoint (the "room")

An Endpoint is a functional unit inside a Node and corresponds to one device type. A Node can have several Endpoints. A smart plug, for example, might contain:
  • Endpoint 0: the reserved endpoint, holding base clusters such as Basic Information, ACL and Network Commissioning
  • Endpoint 1: an On/Off lighting endpoint
// Create the extended color light endpoint
endpoint_t *endpoint = extended_color_light::create(
    node, &light_config, ENDPOINT_FLAG_NONE, light_handle
);

4.3 Cluster (the "furniture")

A Cluster is a functional module: the Attributes, Commands and Events that belong to a single capability are grouped together. Common clusters include:
Cluster Function Sample attribute Sample command
On/Off On/off control OnOff (bool) Toggle
Level Control Brightness and level control CurrentLevel (uint8) MoveToLevel
Color Control Color control ColorTemperatureMireds MoveToHue
Temperature Measurement Temperature measurement MeasuredValue (int16) —
Occupancy Sensing Occupancy detection Occupancy (bitmap) —

4.4 Attribute, Command, Event (the device's "properties")

  • Attribute: a data field holding device state. It may be readable, writable, or read-only.
  • Command: an operation that makes the device perform an action. Issued by the Controller, handled by the Device.
  • Event: a state change or alarm that the device reports on its own initiative.

4.5 Configuring the Data Model: An Example

Taking the extended color light as an example, here is how each cluster's default attributes are configured: 
// On/Off cluster configuration
on_off::config_t on_off_config;
on_off_config.on_off = 0;  // off by default
on_off_config.lighting.start_up_on_off = nullptr;  // restore last state after reboot

// Level Control cluster configuration
level_control::config_t level_config;
level_config.current_level = 64;  // default brightness 25%
level_config.min_level = 1;
level_config.max_level = 254;

// Color Control cluster configuration
color_control::config_t color_config;
color_config.color_mode = EMBER_ZCL_COLOR_MODE_COLOR_TEMPERATURE;
color_config.color_temperature.startup_color_temperature_mireds = nullptr;

5. Hands-On Device Development

Using an ESP32 with the ESP-Matter framework, let's walk through the complete development flow for a Matter lighting device.

5.1 Project Structure

A typical ESP-Matter example project is laid out like this: 
examples/light/
├── main/
│   ├── app_main.cpp      # main entry point
│   ├── app_driver.cpp    # hardware driver layer
│   └── app_priv.h        # private declarations header
├── partitions.csv        # partition table
├── sdkconfig.defaults    # default SDK config
└── CMakeLists.txt

5.2 Initializing the Hardware Drivers

// Initialize the LED driver
app_driver_handle_t light_handle = app_driver_light_init();

// Initialize the button driver
app_driver_handle_t button_handle = app_driver_button_init();

// Register the reset button
app_reset_button_register(button_handle);
app_driver_light_init() initializes every LED pin. The example sets up several LEDs but only uses the first one by default — which is exactly why the sample appears to "control just one bulb".

5.3 Creating the Node and Endpoint

// 1. Create the node
node::config_t node_config;
node_t *node = node::create(&node_config, app_attribute_update_cb, app_identification_cb);

// 2. Configure the endpoint attributes (see section 4.5)

// 3. Create the endpoint (clusters are matched automatically)
extended_color_light::config_t light_config;
// ... set the individual cluster configs on light_config
endpoint_t *endpoint = extended_color_light::create(
    node, &light_config, ENDPOINT_FLAG_NONE, light_handle
);

5.4 Starting the Matter Stack

// Get the endpoint ID
uint16_t light_endpoint_id = endpoint::get_id(endpoint);

// Start the Matter stack
esp_matter::start(app_event_cb);

// Apply the defaults to the hardware
app_driver_light_set_defaults(light_endpoint_id);

5.5 Implementing the Attribute Update Callback

When the user controls the device from the Google Home app or by voice, the attribute update callback fires: 
esp_err_t app_driver_attribute_update(
    app_driver_handle_t driver_handle,
    uint16_t endpoint_id,
    uint32_t cluster_id,
    uint32_t attribute_id,
    esp_matter_attr_val_t *val
) {
    // Match down the endpoint → cluster → attribute hierarchy
    if (cluster_id == OnOff::Id) {
        if (attribute_id == OnOff::Attributes::OnOff::Id) {
            bool power = val->val.b;
            app_driver_light_set_power(driver_handle, power);
        }
    }
    else if (cluster_id == LevelControl::Id) {
        if (attribute_id == LevelControl::Attributes::CurrentLevel::Id) {
            uint8_t brightness = val->val.u8;
            app_driver_light_set_brightness(driver_handle, &brightness);
        }
    }
    else if (cluster_id == ColorControl::Id) {
        // handle color / color temperature changes...
    }
    return ESP_OK;
}

5.6 Reading Cluster and Attribute Values

Reading device state at runtime: 
// Walk down the hierarchy
node_t *node = node::get();
endpoint_t *endpoint = endpoint::get(node, endpoint_id);
cluster_t *cluster = cluster::get(endpoint, LevelControl::Id);
attribute_t *attribute = attribute::get(cluster, LevelControl::Attributes::CurrentLevel::Id);

// Read the value
esp_matter_attr_val_t val;
attribute::get_val(attribute, &val);

// Apply it to the hardware
app_driver_light_set_brightness(handle, &val);

5.7 Deferred Persistence

For attributes that change frequently (brightness, color temperature), use deferred persistence to cut NVM (non-volatile memory) writes and extend the device's lifespan: 
attribute::set_deferred_persistence(current_level_attribute);
attribute::set_deferred_persistence(current_x_attribute);
attribute::set_deferred_persistence(current_y_attribute);

5.8 Building and Flashing

# Set the target chip
idf.py set-target esp32c3

# Build the project
idf.py build

# Flash to the device
idf.py -p /dev/ttyUSB0 flash monitor

6. Custom Data Models

When the standard device types don't cover what you need, Matter supports vendor-specific data models.

6.1 A Custom Endpoint

// Create a custom endpoint (not tied to a standard device type)
endpoint_t *endpoint = endpoint::create(node, ENDPOINT_FLAG_NONE);

6.2 A Custom Cluster

Use a vendor-specific cluster ID (such as 0x131BFC00): 
// Create the custom cluster
uint32_t custom_cluster_id = 0x131BFC00;
cluster_t *cluster = cluster::create(
    endpoint, custom_cluster_id, CLUSTER_FLAG_SERVER
);

6.3 A Custom Attribute

// Add a custom attribute
uint32_t custom_attribute_id = 0x00000000;  // custom attribute ID
attribute_t *attribute = attribute::create(
    cluster,
    custom_attribute_id,
    ATTRIBUTE_FLAG_NONE,
    esp_matter_uint16(default_value)  // 16-bit unsigned integer
);

6.4 A Custom Command

// Command callback
static esp_err_t custom_command_callback(
    const ConcreteCommandPath &command_path,
    TLVReader &tlv_data,
    void *opaque_ptr
) {
    ESP_LOGI(TAG, "Custom command received!");
    // handle the logic...
    return ESP_OK;
}

// Register the custom command
uint32_t custom_command_id = 0x00000001;
command::create(
    cluster,
    custom_command_id,
    COMMAND_FLAG_ACCEPTED,
    custom_command_callback  // callback
);

6.5 Adding Extra Standard Clusters to an Endpoint

You can also attach standard clusters to an existing endpoint dynamically: 
// Add the On/Off cluster to the endpoint
on_off::config_t config;
on_off::create(endpoint, &config, CLUSTER_FLAG_SERVER,
               on_off::feature::lighting::get_id());

// Add the Temperature Measurement cluster
temperature_measurement::config_t temp_config;
temperature_measurement::create(endpoint, &temp_config, CLUSTER_FLAG_SERVER);

7. Google Home Integration and Testing

7.1 Configuring the Google Home Developer Console

  1. Create a project: go to the Google Home Developer Console and create a smart home project
  2. Add a Matter integration: pick the Matter integration type and configure the product's VID and PID
  3. Fill in the device information: name, description, category and so on
  4. Get test credentials: generate the test keys used for debugging during development

7.2 Using the Matter Virtual Device

If you don't have real hardware yet, you can develop against the Dockerized virtual device: 
# Pull and run the Matter Virtual Device
docker run -it --rm 
    --network host 
    us-central1-docker.pkg.dev/gdhome-google-com/matter-virtual-device/matter-virtual-device:latest
The virtual device can be commissioned into a real Google Home fabric and controlled by Assistant voice commands just like a physical device.

7.3 Debugging with the VS Code Extension

Once the Google Home Extension for VS Code is installed, you can do the following inside the IDE:
  • Watch live cloud logs: detailed logs of the two-way conversation, filtered by severity and time
  • Send Assistant commands: exercise voice-command interactions in a scripted way
  • Inspect JSON payloads: see exactly what the device and Google Home exchange

7.4 The Commissioning Flow

The device pairs over BLE first, then switches to Wi-Fi or Thread once commissioning completes: 
User scans the QR code / taps with NFC
    ↓
BLE commissioning channel established (PASE secure session)
    ↓
Device receives Wi-Fi/Thread network credentials
    ↓
Device joins the IP network
    ↓
Certificate-authenticated session established (CASE)
    ↓
Device is added to the Google Home fabric
    ↓
User can control the device from the app or by voice

7.5 Debugging with chip-tool

chip-tool ships with the Matter SDK as a command-line debugging tool: 
# Turn it on/off
./chip-tool onoff on <node-id> <endpoint-id>

# Set brightness
./chip-tool levelcontrol move-to-level 128 10 0 0 <node-id> <endpoint-id>

# Read the temperature value
./chip-tool temperaturemeasurement read measured-value <node-id> <endpoint-id>

# Subscribe to attribute changes
./chip-tool onoff subscribe on-off <node-id> <endpoint-id> --min-interval 1 --max-interval 10

8. Test Suite and Certification

8.1 Google Home Test Suite

Google provides an automated test suite for validating your Matter integration:
  • Start a test run from the Developer Console
  • Automatically checks whether the device conforms to Google Home ecosystem requirements
  • Produces a detailed report showing which checks passed and which failed
  • You must pass before you can move on to a Field Trial or a public launch

8.2 The Certification Path at a Glance

Requirements analysis → Development → Developer Console setup
    ↓
Google Home Test Suite run
    ↓
Field Trial (optional but recommended — validates behavior in the real world)
    ↓
CSA Matter certification (device level, through an authorized test lab)
    ↓
Product launch
2026 update: starting in 2026, every Matter integration and test is required to use the Alliance Interop Test. Keep an eye on the CSA website for the latest.

8.3 A Checklist of Common Certification Items

  • [ ] The device responds correctly to basic commands such as On/Off and Level Control
  • [ ] The BLE commissioning flow is smooth and the QR code scans reliably
  • [ ] Multi-Admin works correctly
  • [ ] The device reconnects properly after a network interruption
  • [ ] Firmware OTA update (where applicable)
  • [ ] State is restored correctly after a reboot
  • [ ] Security credentials (DAC, PAI, CD) are flashed correctly

10. Takeaways and Outlook

Key Takeaways

  1. Matter is an application-layer protocol over IP (Wi-Fi/Thread/Ethernet); BLE is used only for commissioning
  2. The data model is the core: the four-level Node → Endpoint → Cluster → Attribute/Command/Event hierarchy
  3. Google provides an end-to-end toolchain: from the virtual device (MVD) to the VS Code extension to the automated test suite
  4. You have plenty of framework choices: ESP-Matter for fast prototyping, nRF Connect SDK for commercial products, Simplicity Studio for graphical development
  5. Certification is not optional: shipping requires both CSA Matter certification and the Google Home Test Suite

A Suggested Learning Path

Step 1: Read up on the Matter 101 basics (1 day)
Step 2: Set up the development environment and run your first sample (1 day)
Step 3: Get a solid grasp of the data model and cluster configuration (2-3 days)
Step 4: Try the Google Home integration with the Matter Virtual Device (1 day)
Step 5: Build and test the device on real hardware (3-5 days)
Step 6: Validate with the Google Home Test Suite (1-2 days)
Step 7: Prepare for CSA Matter certification
