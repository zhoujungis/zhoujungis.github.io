NanoDB: an embedded document database in Go, with zero dependencies

2026-10-26 · 38 min · Stack Frame

SQLite is two million lines. LevelDB is a compact LSM textbook. MongoDB is a distributed system. Writing another database in 2026 looks like reinventing a wheel.

But nobody builds a wheel to have a wheel. NanoDB answers three specific questions. What is the shortest path to a database with transactions? How many lines does "committed data survives a crash" actually take? And how do a document model, secondary indexes and optimistic concurrency fit on one in-memory data structure?

The answer is about ten thousand lines of Go with zero third-party dependencies and a single go build. More useful than the line count: one person can read any single part of it in an hour. That is not true of SQLite's pager or RocksDB's compaction.

So read this two ways. As a usable tool, to see when it fits. And as an anatomy specimen, to see what to build first if you write your own.

What it is

NanoDB is an embedded document database in Go, currently 0.1.0. Embedded means no daemon and no wire protocol. It is a library in your process, with a CLI, an interactive shell and a REST service wrapped around it.

The trade-off is one sentence: do single-machine, memory-resident, JSON-native well, and give up distribution explicitly. No replicas, no sharding, one process per directory. The README lists all of it rather than leaving it implied.

One detail captures the whole temperament. go build -o bin/nanodb ./cmd/nanodb needs no network, because there is nothing to download.

Five minutes in

go build -o bin/nanodb ./cmd/nanodb

# insert, with a generated _id
./bin/nanodb -db ./data put users '{"name":"Alice","age":30}'

# filter, sort, paginate
./bin/nanodb -db ./data find users '{"age":{"$gte":18}}' -sort age:-1 -limit 10

# update, count, delete
./bin/nanodb -db ./data update users u2 '{"$inc":{"age":1}}'
./bin/nanodb -db ./data count users '{"age":{"$gt":20}}'
./bin/nanodb -db ./data delete users u2

Successful commands print indented JSON. Failures exit 1 with an Error: prefix on stderr, so scripts can branch.

Run without a subcommand and you get a shell. Inside a transaction the prompt changes, and quitting rolls back anything uncommitted.

The REST service is one flag away: serve -addr :8080 -token secret, then requests carry the token header.

All three entry points share one engine. cmd/nanodb/main.go only dispatches arguments, server/server.go only routes and authenticates, and the logic sits in engine/. That is the first decision worth copying: thin entry points, one engine.

The real usage is the library:

db, err := engine.Open("./data", &engine.Options{
    Sync:             true,        // fsync every write
    CompactThreshold: 4 << 20,     // compact when the WAL exceeds 4 MiB
})
if err != nil {
    panic(err)
}
defer db.Close()

doc, _ := db.Insert("users", map[string]any{"name": "Alice", "age": 30})
fmt.Println(doc["_id"])

docs, _ := db.Find("users", engine.Query{
    Filter: map[string]any{"age": map[string]any{"$gte": 18}},
    Sort:   []engine.SortField{{Field: "age", Desc: true}},
    Limit:  10,
})

The API is a flat method table mirroring the CLI: insert, insert many, get, find, count, replace, update, delete, batch, aggregate, query SQL, create and drop index, compact, stats, close.

Two traps are worth knowing. Passing nil for options gives Sync: true, while passing an empty Options literal gives Sync: false, because Go's zero values decide. And every read and write returns a copy, so mutating a returned document never writes back.

Dependencies run one way. cmd and server depend on engine, and engine depends on nothing. There is no interface layer, because there is one implementation, and reserving abstractions for an imaginary second one is how small projects become large ones.

Data model

data/
├── snapshot.json   # full data and index definitions at a point in time
├── wal.log         # operations since the snapshot, JSON Lines
├── LOCK            # exclusive process lock
└── users.json      # optional HTTP accounts

A document is a JSON object. Its _id is a non-empty string, generated when absent as a millisecond timestamp in hex plus random characters. The time prefix keeps generated ids roughly ordered, so inserts do not scatter the index.

Writes deep-copy. Mutating the caller's map afterwards cannot affect the database, and reads return copies. That removes a whole class of concurrency bugs where a shared map is edited somewhere else, at the cost of one copy per operation. For memory-resident data of moderate size, that is cheap insurance.

Field names accept dotted paths for filters, sorts, projections and indexes. Field names starting with $ are operators, a MongoDB habit the README warns about.

JSON typeStoredFilter and sortIndexable
stringYesEquality, regex, lexicographicYes
numberYesNumeric comparisonYes
booleanYesEqualityYes
nullYesOnly $eq: null and $existsNo
arrayYesMultikey, any element matchesPer element
objectYesWhole-object equalityNo

Null and objects staying out of indexes is easy to miss, because an index-driven candidate set can then miss documents. NanoDB marks such indexes incomplete and still runs the full match over the candidate set.

Persistence

Every database reduces durability to one question: what happens if power is lost mid-write? NanoDB's answer has three layers, none longer than a few dozen lines.

{"op":"put","coll":"users","doc":{"_id":"u1","name":"Alice","age":30}}
{"op":"delete","coll":"users","id":"u2"}
{"op":"index.create","coll":"users","field":"age","unique":true}
{"op":"batch","ops":[{"op":"put","coll":"users","doc":{"_id":"u3"}}]}
{"op":"drop","coll":"users"}

There are seven operation types. Puts are also used for updates, batches and transactions are a parent record with children, and that structure is what makes "all or nothing" hold during replay.

JSON Lines is a blunt trade. It is readable, greppable, one record per line, and it costs space and parse time against a binary format. In exchange, crash recovery becomes "parse line by line and truncate the bad tail".

Layer one: a torn record. If the process dies mid-line, the file ends with half a line. Replay returns the length of the valid prefix and the WAL is truncated to it:

func (db *DB) replay(data []byte) (int, error) {
    offset := 0
    for offset < len(data) {
        nl := bytes.IndexByte(data[offset:], '
')
        if nl < 0 {
            return offset, nil   // no newline: the tail is torn, stop here
        }
        if err := json.Unmarshal(line, &rec); err != nil {
            return 0, fmt.Errorf("nanodb: corrupt wal near byte %d: %w", offset, err)
        }
    }
    return offset, nil
}

Two failures are treated differently on purpose. A missing trailing newline is a normal tear: truncate it and keep everything committed before it. A parse failure in the middle is real corruption, and the database refuses to open. Skipping a bad line in the middle would disguise data loss as a successful recovery.

Layer two: the writer undoes its own damage. Recovery alone is not enough, because the writer must not leave half a record for the next recovery to find. If a write or the following fsync fails, the WAL is truncated back to the end of the last complete record. Without that, the next append fuses with the fragment into an invalid line and the database will not open.

There is a Windows trap in the same function. The file is opened without O_APPEND, because that flag removes write access on Windows and later truncation fails. Writes are serialised by the mutex and seek explicitly to the end, which keeps append semantics and keeps truncation possible. Cross-platform is not a slogan, it is decisions like this one.

Layer three: a generation number. The dangerous window in any snapshot plus WAL design is a crash after the snapshot is renamed but before the WAL is cleared. Replay then reapplies records already in the snapshot. For a plain put that is harmless. For a unique index it is a false conflict. For a delete followed by an insert it can resurrect data.

So the snapshot records a generation, compaction increments it, and every WAL record carries the generation it was written in. Replay skips anything older than the snapshot. Whichever step compaction crashed on, either the old records are skipped or the old snapshot replays normally, and both states are consistent. One uint64 and a comparison separate designed correctness from luck.

Compaction order matters too. Write a temporary snapshot, fsync it, rename it into place, then clear the WAL, so a complete snapshot always exists on disk. The compaction check runs from points where the in-memory state is fully applied, never inside the write path, because a snapshot taken there could miss a pending delete or index creation.

The directory lock. A convention of one process per directory fails eventually. NanoDB makes it physical with an OS file lock: LockFileEx on Windows, flock elsewhere. A second process gets an error, and a crash releases the lock automatically, so no zombie lock survives a crash.

Query execution

A find runs through five steps, each with a clear motive: pick an index, compile the filter, match documents, sort, then skip, limit and project.

Pick the smallest candidate set. There is no cost model, no statistics and no histograms. Each usable index is asked for its candidate set, and the smallest wins. For a single-machine in-memory database that is the best value per line of code, because an index lookup is logarithmic and asking four is far cheaper than choosing badly.

One rule is more important than the planner's cleverness. $or and $not cannot produce a candidate set safely, because the union of branches can miss documents, so the planner declines to use an index rather than risk it. Knowing when not to be clever is the main quality of a planner.

The candidate set is also only a pre-filter. The full match always runs afterwards.

Compile the filter once. A naive implementation re-walks the filter map per document and recompiles regexes per document. Both are hoisted above the scan: the map becomes a slice, and regexes are compiled once, with an invalid pattern compiled to "never matches" rather than one error per document. On a hundred thousand documents that is the difference between two thousand allocations and hundreds of thousands.

Sort with a heap when there is a limit. Asking for the first fifty means one pass with a heap of size skip plus limit, then sorting fifty elements. Complexity drops from n log n to n log k. Measured on a hundred thousand randomly ordered documents, that is 6.5 ms against 85.3 ms.

Indexes

An index is an ordered key to document-id map. It supports single fields, compound keys, uniqueness and arrays, where each element is indexed and any element matching counts. Range queries binary-search the boundaries, so cost is logarithmic plus the number of hits.

Compound indexes have one honest limitation. A document containing an array cannot enter a compound index under tuple semantics, so the index is marked incomplete and the planner falls back to a full scan. Slow is better than wrong: a partially visible index treated as complete would silently drop documents, which is worse than one order of magnitude of latency.

Text search covers every string in a document. Alphanumeric runs become lowercase words, and runs of Han characters also emit bigrams, so a query is sliced the same way and ANDed. Chinese search works without a segmentation dictionary.

The limits are stated plainly: no stop words, no stemming, no synonyms, no relevance score, multi-term queries are pure AND, and results are not ranked. It is usable retrieval, not a search engine, and for an embedded database that is the right scope.

Geo stores entries ordered by longitude, so a box query narrows candidates through the ordered structure before running trigonometry. Circles use haversine distance. No polygons, no GeoJSON geometry, no handling of the 180th meridian, and results are not distance-sorted.

Transactions

No lock waits, no deadlocks, no undo chains. The scheme is the plainest one that fits "in memory, one process": a collection snapshot plus version checks.

type Tx struct {
    mu       sync.Mutex
    db       *DB
    snap     map[string]*collection // per-collection snapshot
    versions map[string]uint64      // version when first accessed
    writes   map[string]bool        // collections written in this tx
    walOps   []walRecord
    done     bool
}

Begin takes no lock. On first access to a collection, under a read lock, the transaction records the version and deep-copies the collection. Everything after that works on the snapshot, which gives repeatable read for free and lets the transaction see its own uncommitted writes.

Commit takes the write lock once and validates the whole read set. If any accessed collection changed since it was copied, the transaction aborts with a conflict error, all changes are discarded, and the caller retries. On success, the entire change set becomes one WAL record, the affected collections are replaced, and their versions increment.

Four consequences follow.

Conflicts are at collection granularity. Touching a different document in the same collection still aborts, and that is the acknowledged false conflict. A version comparison is much cheaper than per-document tracking, which is the right trade for low-conflict workloads and a poor one for hot collections.

There are no deadlocks, because there is no lock waiting. The only synchronisation point is the brief commit, and the database stays writable throughout.

Read-only transactions still call commit, because that is what certifies a consistent cross-collection view.

Transaction methods are goroutine-safe, a finished transaction returns an error from every method, and rollback is idempotent.

Batches

Transactions handle multi-step work with rollback. Batches handle "all at once, no intermediate state", and the strategy is to clone and stage.

Every write in the batch runs against clones. Any failure, whether a duplicate id, a unique index conflict, an invalid update or a missing target, discards the whole batch with the real data untouched. On success the whole change set becomes one WAL record, so replay is atomic and there is no half-commit.

Batches span collections. Updating a missing target is an error; deleting a missing target is not, and reports that nothing was deleted.

Cloning costs peak memory and buys atomicity without rollback logic. A failed path throws the clone away, and there is no code that has to undo half-applied index maintenance.

Batches also read from stdin, and because success writes one record, importing a hundred thousand documents costs one fsync instead of a hundred thousand.

SQL and aggregation

engine/sql.go is a hand-written read-only subset: lex, parse, execute. It supports select with from, where, order by and limit or offset, plus count star.

It brings no engine of its own. The parse result becomes the same query structure the REST and CLI paths use, so it runs through the same filter compiler, the same planning and the same Top-N sort. SQL and find performing identically is not a coincidence. They are one pipeline with two front doors.

The boundary is explicit. No joins, no group by, no having, no distinct, no subqueries, no union, no column aliases, and like is case-sensitive.

Aggregation has eight stages and seven accumulators, named to match MongoDB. No lookup, no facet, no window functions, and aggregation does not use indexes.

HTTP service

The REST layer exposes health, CRUD under a versioned collection path with filter, sort, limit, skip, fields and count in query parameters, and a small set of admin endpoints.

Authentication is a shared token header, or per-user tokens limited to admin, write or read with an exact-match collection allowlist.

Transactions are opened by a POST that returns an id, and subsequent requests operate under that id until they commit or roll back. Sessions live in server memory, roll back after thirty idle minutes, and roll back at shutdown, so a forgotten transaction cannot pin snapshot memory indefinitely.

The session layer is only a map from id to transaction. HTTP transactions share the same implementation as library transactions.

Against SQLite: SQLite is relational with full SQL and disk paging and can exceed memory, while NanoDB is a document model that lives in memory and sells native JSON plus friction-free Go embedding. Against the LevelDB family: those are key-value engines with no query language and no index abstraction, and NanoDB sells the layer above them. Against MongoDB: no distributed ambition at all.

Known limits

  • Documents and indexes live in memory, so size is bounded by RAM. The WAL costs more space than a binary format.
  • No replicas, no sharding, no clustering. One process per directory.
  • Isolation is fixed, conflicts are per collection, and there are no savepoints, no DDL inside a transaction and no cross-process transactions.
  • Text search is approximate: bigrams only, no scoring, no ranking.
  • Geo supports boxes and circles only, not polygons, and not the 180th meridian.
  • SQL is a read-only subset, and aggregation does not use indexes.
  • Compound indexes fall back to a scan when a document contains an array.
  • Permissions are coarse: exact-match collection allowlists, no field-level rights, and an 8 MiB request body cap.
  • Posting an array of documents is not atomic. Use a batch or a transaction.

When to use it

Use it for local storage inside Go tools and services: configuration, task queues, crawler state, desktop app data, anywhere you do not want to run a database service to store tens of thousands of JSON rows. Use it for read-heavy workloads whose data fits in memory. Use it for teaching and forking, because ten thousand dependency-free lines with every part present make a good starting point. Use it for edge and single-machine deployment, where one binary with no cgo and no external service is the whole story.

Do not use it for data larger than memory, for multi-process writes to one directory, for transaction-heavy writes on hot collections, or when you need relevance-ranked search, complex SQL analytics or precise geospatial work.

Closing

Back to the three questions.

How short is the shortest path to a transactional database? A transaction struct plus a version-check loop. No lock manager, no undo log, and it still gives repeatable read, lost-update protection and an explicit conflict error the caller can retry.

How many lines is "committed data survives a crash"? Three layers and under a hundred lines of core, plus the thinking about every crash point, which is the real work.

How do documents, indexes and concurrency mesh? Writes maintain every index synchronously, transactions carry those indexes inside the cloned snapshot, and the planner picks the smallest candidate set with a full match as the backstop.

NanoDB will not replace SQLite and has no ambition to replace MongoDB. Its value is putting the black box on the table. The WAL is newline-delimited JSON. A transaction is a version comparison. Planning is picking the smallest candidate set. The mechanisms are plain enough to memorise, and that plainness is why they can be trusted.

If you have ever thought about writing a database, the answer here is yes, and it does not take many lines. The next step is not more papers. Clone it and break replay, commit and planning one at a time, then see whether the tests still pass.
