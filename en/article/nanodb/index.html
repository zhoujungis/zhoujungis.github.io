NanoDB: an embedded document database in Go, with zero dependencies

2026-10-26 · 38 min · Stack Frame

SQLite has two million lines. LevelDB is a compact LSM textbook. MongoDB is a distributed system. Writing another database in 2026 looks like reinventing a wheel.

But the point of building a wheel is never the wheel. NanoDB answers a specific set of questions.

  • What is the shortest path to a database that supports transactions?
  • After removing all the engineering jargon, how many lines does "committed data survives a crash" actually take?
  • How do a document model, secondary indexes and optimistic concurrency control fit together on a single in-memory data structure?

The answer is about ten thousand lines of Go with zero third-party dependencies and one go build. More useful than the line count: every part of it can be read by one person in an hour, which is close to impossible in a real database. How long does SQLite's pager layer take to read? How long does RocksDB's compaction?

So read this two ways. As a usable tool, and as an anatomy specimen. The first tells you when to reach for it. The second tells you, if you write your own, what to build first, what to build later, and what has to be right the first time.

What it is

NanoDB is a lightweight embedded document database written in Go, currently version 0.1.0. Embedded means there is no daemon and no wire protocol. It is a library inside your process, with a CLI, an interactive shell and a REST service wrapped around it.

DimensionDetail
LanguageGo 1.22+, single module nanodb
Third-party dependenciesZero. Standard library only, no cgo

The trade-off in one sentence: do single-machine, memory-resident, JSON-native well, and give up distribution explicitly. No replicas, no sharding, no clustering, and one process per data directory at a time. Those are outside the boundary by design, and the README lists all of them under known limits.

One detail says a lot about the project. go build -o bin/nanodb ./cmd/nanodb needs no network, because nothing has to be downloaded. In an era of dependency trees measured in hundreds of megabytes, that belongs in the introduction.

Five minutes to first query

The one-shot CLI

go build -o bin/nanodb ./cmd/nanodb

# insert, with a generated _id
./bin/nanodb -db ./data put users '{"name":"Alice","age":30}'

# filter, sort, paginate
./bin/nanodb -db ./data find users '{"age":{"$gte":18}}' -sort age:-1 -limit 10

# update, count, delete
./bin/nanodb -db ./data update users u2 '{"$inc":{"age":1}}'
./bin/nanodb -db ./data count users '{"age":{"$gt":20}}'
./bin/nanodb -db ./data delete users u2

Successful commands print indented JSON to stdout. Failures exit with status 1 and write the error to stderr behind an Error: prefix, so a script can branch on the exit code.

The interactive shell

Run without a subcommand and you get a shell. Inside a transaction the prompt becomes nano(tx)>, and quitting or reaching EOF rolls back anything uncommitted.

$ ./bin/nanodb -db ./data
NanoDB 0.1.0 interactive shell. Quote JSON arguments with single quotes.
nano> begin
transaction started
nano(tx)> put users '{"name":"Bob"}'
nano(tx)> commit
transaction committed

The REST service

./bin/nanodb -db ./data serve -addr :8080 -token secret
curl -H 'X-NanoDB-Token: secret' localhost:8080/v1/users

All three entry points share one engine rather than being three implementations. cmd/nanodb/main.go at 722 lines only dispatches arguments. server/server.go at 764 lines only routes and authenticates. The logic sits in engine/. That is the first architectural decision worth copying: thin entry points, one engine.

Go embedding, which is the real usage

For an embedded database, the CLI and the REST service are attachments. The body is the library call.

db, err := engine.Open("./data", &engine.Options{
    Sync:             true,        // fsync every write
    CompactThreshold: 4 << 20,     // compact when the WAL exceeds 4 MiB
})
if err != nil {
    panic(err)
}
defer db.Close()

doc, _ := db.Insert("users", map[string]any{"name": "Alice", "age": 30})
fmt.Println(doc["_id"])

docs, _ := db.Find("users", engine.Query{
    Filter: map[string]any{"age": map[string]any{"$gte": 18}},
    Sort:   []engine.SortField{{Field: "age", Desc: true}},
    Limit:  10,
})
fmt.Println(len(docs))

The API is a flat method table that mirrors the CLI subcommands: insert, insert many, get, find, count, replace, update, update many, delete, delete many, batch, aggregate, query SQL, create index, drop index, compact, stats and close.

Two notes on using it. Passing nil for options gives the default behaviour, which is sync enabled, while passing an empty Options literal actually means you chose sync disabled, because Go's zero values decide. The README calls that trap out explicitly. And every read and write returns a copy, so mutating a returned document never writes back. To change data, go through update or replace.

Data model

The data directory holds only a few files.

data/
├── snapshot.json   # full data and index definitions at a point in time
├── wal.log         # operations since the snapshot, JSON Lines
├── LOCK            # exclusive process lock (empty file, OS-level lock)
└── users.json      # optional: HTTP accounts

The hierarchy is collection to document. A collection resembles a table with no fixed schema. The rules are few, and each one is deliberate.

  • A document must be a JSON object. Its _id must be a non-empty string, and when absent it is generated as a 13-hex-digit millisecond timestamp plus 12 random characters. The time prefix keeps generated ids roughly ordered, so an insert does not scatter the index.
  • Writes deep-copy, so mutating your object afterwards cannot affect the database, and reads return copies as well. That rule eliminates a whole class of concurrency bug where a shared map is edited somewhere else, at the price of one copy per operation. For memory-resident data of moderate size, it is cheap insurance.
  • Field names accept dotted paths for filters, sorts, projections and indexes, while documents themselves stay freely nested.
  • Field names beginning with $ are treated as operators. That is a MongoDB compatibility constraint, and the README warns against using $ for ordinary field names.
  • Numbers written through the CLI or HTTP decode as float64, numbers passed through Go keep their type, and comparisons are numeric either way. Cross-entry type behaviour is defined rather than left to be discovered.
JSON typeStoredFilter and sortIndexable
stringYesEquality, regex, lexicographic orderYes
numberYesNumeric comparisonYes
booleanYesEqualityYes
nullYesOnly $eq: null and $existsNot written to indexes
arrayYesMultikey, any element matchesEach element indexed
objectYesWhole-object equalityNot written to indexes

Null and objects staying out of indexes is easy to overlook: an index-driven candidate set can then miss documents. NanoDB handles the variants with an incomplete flag plus a rule that the candidate set is only a pre-filter, with the full match still running.

Persistence

This is the core of the project. Every durability problem reduces to one question: what happens if power is lost mid-write? NanoDB's answer has three layers, none of them longer than a few dozen lines.

What a record looks like

wal.log holds one complete record per line, in write order.

{"op":"put","coll":"users","doc":{"_id":"u1","name":"Alice","age":30}}
{"op":"delete","coll":"users","id":"u2"}
{"op":"index.create","coll":"users","field":"age","unique":true}
{"op":"batch","ops":[{"op":"put","coll":"users","doc":{"_id":"u3"}}]}
{"op":"drop","coll":"users"}

There are seven operation types: put, delete, drop, batch, tx, index creation and index drop. Updates are written as overwriting puts. Batches and transactions are one parent record with children in an ops array, which is what keeps "all of it or none of it" atomic during recovery too.

JSON Lines is a blunt trade. It is readable, greppable, one full record per line, and it costs more space and parse time than a binary format. For a database aimed at moderate data that is a fair exchange, and it reduces crash recovery to "parse line by line, truncate the bad tail".

Layer one: truncating a torn record

If the process dies mid-line, the file ends with half a line. Replay returns the length of the valid prefix, and the WAL is truncated to that length.

// replay applies the WAL in order and returns the length of the valid prefix.
func (db *DB) replay(data []byte) (int, error) {
    offset := 0
    for offset < len(data) {
        nl := bytes.IndexByte(data[offset:], '\n')
        if nl < 0 {
            return offset, nil   // no newline: the tail is torn, stop here
        }
        ...
        if err := json.Unmarshal(line, &rec); err != nil {
            return 0, fmt.Errorf("nanodb: corrupt wal near byte %d: %w", offset, err)
        }
        ...
    }
    return offset, nil
}

Two failures are treated differently on purpose. A missing trailing newline is a normal tear: truncate it, and everything committed before it stays. A parse failure in the middle is real corruption, and the database refuses to open. Silently skipping a bad line in the middle would disguise data loss as a successful recovery, and that is the one boundary recovery logic must never cross.

Layer two: the writer rolls back its own damage

Recovery alone is not enough. The writer must not leave half a record behind for the next recovery to find, and one function handles it with a comment worth reading in full.

n, err := db.wal.Write(data)
if err != nil || n != len(data) {
    // A failed write may leave half a record at the tail, so roll back to the
    // previous complete record. Otherwise the next append fuses with the
    // fragment into an invalid line, and the database cannot be opened.
    db.rollbackWALLocked()
    ...
}

The rollback truncates to the offset of the last complete record and seeks back to it. That offset is both an in-memory counter and the recovery anchor. The same rollback is attached to a failing fsync.

There is a Windows trap hidden in the open path, and it is worth quoting as written.

// Not O_APPEND: on Windows that flag removes GENERIC_WRITE, so a later
// Truncate fails with Access is denied. Writes are serialized by db.mu, so an
// explicit seek to the end preserves append semantics.
f, err := os.OpenFile(path, os.O_CREATE|os.O_RDWR, filePerm)

"Cross-platform" is usually a claim in a README. Here it is a decision about one flag, made by someone who actually ran the thing on Windows.

Layer three: a generation number for the compaction window

Any snapshot plus WAL design has a dangerous window: a crash after the snapshot is renamed but before the WAL is cleared. Replay would then reapply records already folded into the snapshot. For a plain put that is harmless. For a unique index it is a false conflict. For a delete followed by an insert, it can resurrect data.

NanoDB closes the window with generations. The snapshot records a generation, compaction increments it, and every WAL record carries the generation it was written in. Replay has one rule.

// Records older than the current snapshot generation are already covered.
if rec.Gen < db.walGen {
    offset += nl + 1
    continue
}

Whichever step compaction crashed on, the result is self-consistent: either the old-generation records are skipped, or the snapshot is still the old generation and replays normally. One uint64 and one comparison is all it takes. That is the line between designed correctness and luck.

Compaction order matters too: write a temporary snapshot, fsync it, rename it into place, then clear the WAL. At any moment a complete old or new snapshot exists on disk. The compaction check is also called from points where the in-memory state has been fully applied, such as after a transaction commit or a completed batch. Compacting inside the write path could snapshot a state that is ahead of the data, missing a pending delete or index creation.

The directory lock

"One process per data directory" as a convention eventually fails, and two processes write at once. NanoDB makes it a physical fact with an operating-system file lock: LockFileEx on Windows, flock on Unix. A second process gets a distinct error, and a crashed process releases the lock automatically, so there is no zombie lock after a crash. A few dozen lines per platform, selected by build tags.

Query execution

A find call runs through five steps, each one with a clear motive.

planCandidates   (choose a candidate set from indexes)
    → compileFilter
    → match each document
    → Top-N or full sort
    → skip and limit → projection copy

Step one: the smallest candidate set

// planCandidates picks the index with the smallest candidate set from the
// filter, and returns nil to mean a full scan.
func (c *collection) planCandidates(filter map[string]any) map[string]struct{} {
    ...
    conds := make(map[string][]any, len(filter))
    collectConditions(filter, conds)
    ...
    consider := func(ids map[string]struct{}) {
        if ids == nil { return }
        if best == nil || len(ids) < len(best) { best = ids }
    }
    for _, ix := range c.indexes { consider(ix.lookup(conds)) }
    for _, tx := range c.texts    { consider(tx.lookup(conds["$text"])) }
    for field, gx := range c.geos { consider(gx.lookup(conds[field])) }
    return best
}

No cost model, no statistics, no histograms. Every usable index is asked for a candidate set, and the smallest one wins. For a single-machine in-memory database that is the best planner per line of code, because an index lookup is logarithmic and asking three or four is far cheaper than choosing badly and scanning.

The rule in collectConditions matters more than the cleverness. It gathers top-level conditions and those inside $and. A union of branches under $or cannot be narrowed safely, because a candidate set that is too small silently drops documents, so the planner declines to use an index rather than risk it. The most important quality of a planner is knowing when not to be clever. The chosen set is also only a pre-filter: the full match still runs afterwards as a second safety net.

Step two: compile the filter once

// compileFilter flattens the filter into a slice so per-document matching does
// not allocate map iterators, and precompiles regexes so a scan does not
// recompile the same pattern for every document.
func compileFilter(filter map[string]any) []filterClause { ... }

An invalid regex compiles to a nil matcher that never matches, rather than producing one error per document. On a scan of a hundred thousand documents, those two decisions are the difference between roughly two thousand allocations and hundreds of thousands.

Step four: sort through a heap when there is a limit

if len(q.Sort) > 0 {
    if q.Limit > 0 {
        k := len(out)
        if q.Skip < len(out) && q.Limit < len(out)-q.Skip {
            k = q.Skip + q.Limit
        }
        out = topNSortDocs(out, q.Sort, k)   // max-heap of size k
    } else {
        sortDocs(out, q.Sort)
    }
}

Asking for the first fifty means one pass with a heap of size skip plus limit, where the top of the heap is the worst of the current best k, and then sorting k elements. Complexity drops from n log n to n log k. Measured on a hundred thousand randomly ordered documents, that is 6.5 ms against 85.3 ms.

Sort keys are also extracted up front, so a comparison never has to walk back into nested fields. And skip is handled by fetching skip plus limit rather than sorting the whole result and then slicing.

Indexes

Secondary indexes and the incomplete flag

An index is an ordered key to a set of document ids. It supports single fields, compound keys, uniqueness, and arrays where each element is indexed and any element matching counts. Range queries binary-search the boundaries.

// spanFor binary-searches the entry range for a first-field range condition.
func (ix *index) spanFor(op string, val any) (entrySpan, bool)

That makes a range query logarithmic plus the number of hits instead of a full walk. It is where the measured gap between 3.1 ms indexed and 27.3 ms scanned comes from.

Compound indexes have one honest limitation. A document containing an array field cannot enter a compound index under tuple semantics, so the index is marked incomplete, and lookups against an incomplete index return nil, which means unusable. The planner then falls back to a scan. Slow is better than wrong. A partially visible index treated as complete would silently drop documents, which is far worse than one order of magnitude of latency.

Text indexes: Chinese search without a dictionary

The full-text index covers every string in a document and is queried with $text. The tokenizer is about thirty lines.

// tokenizeText splits on letters and digits, and additionally emits bigrams
// for runs of Han characters, so Chinese queries match fragments without a
// segmentation dictionary.
func tokenizeText(s string) []string {
    ...
    if han && len(word) > 1 {
        for i := 0; i < len(word)-1; i++ {
            out = append(out, string(word[i:i+2]))   // 数据库 -> 数据, 据库
        }
    } else {
        out = append(out, strings.ToLower(string(word)))
    }
    ...
}

Bigrams are a classic dictionary-free approach. A phrase becomes overlapping pairs, a query is sliced the same way, and every term must match. No segmentation dictionary is needed anywhere in the pipeline.

The limits are stated plainly in the README: no stop words, no stemming, no synonyms, no relevance score, multi-term queries are pure AND, and results come back unordered. It is usable retrieval, not a search engine. For an embedded database that is the right scope, because most cases only need the documents containing these words.

Geo indexes: longitude order plus haversine

Geo entries are ordered by longitude and support $geoWithin with a box and a metric circle. Circles use haversine distance.

// haversineMeters returns the great-circle distance between two points.
func haversineMeters(lon1, lat1, lon2, lat2 float64) float64

A box narrows candidates through the ordered structure first, and only then does the circle test run, so the expensive trigonometry is limited to a small set. The limits are equally explicit: no polygons and no GeoJSON geometry, no handling of the 180th meridian, and results are not distance-ordered.

Transactions

No lock waiting, no deadlocks, no MVCC undo chain. NanoDB uses the plainest scheme that fits "in memory, one process": collection snapshots plus version validation.

type Tx struct {
    mu       sync.Mutex
    db       *DB
    snap     map[string]*collection // per-collection snapshot
    versions map[string]uint64      // version when first accessed
    writes   map[string]bool        // collections written in this tx
    walOps   []walRecord
    done     bool
}

The workflow is short.

  1. Begin takes no database lock at all.
  2. The first access to a collection takes a read lock, records the version and deep-copies the whole collection. Everything after that reads and writes the snapshot, which gives repeatable read for free and lets the transaction see its own uncommitted writes.
  3. Commit takes the write lock once and validates the entire read set.
// Validate the whole read set to avoid lost updates and non-repeatable reads;
// read-only transactions validate snapshot consistency the same way.
for name, ver := range tx.versions {
    if tx.db.versions[name] != ver {
        tx.finishLocked()
        return fmt.Errorf("%w: collection %q changed during transaction", ErrConflict, name)
    }
}

If validation passes, the whole change set becomes one WAL record, the affected collections are replaced and their versions increment. If it fails, the caller gets a conflict error, every change is discarded, and it retries from begin.

Four consequences follow from that design.

  • Conflict granularity is the collection. If anyone touched any collection you read, even a different document, the commit fails. That is the acknowledged false conflict. A single version comparison is far cheaper than per-document tracking, which is the right trade for low-conflict workloads and a poor one for hot collections under heavy writes.
  • There are no deadlocks. Nothing waits on a lock. The only synchronization point is the brief commit, and conflicts return an error rather than queueing. Between begin and commit the database stays fully writable.
  • Read-only transactions still call commit. That is what certifies a consistent cross-collection view.
  • Transaction methods are goroutine-safe behind one mutex. After the transaction ends every method returns a done error, and deferred rollback is idempotent.

The canonical example is a transfer.

tx, err := db.Begin()
if err != nil { return err }
defer tx.Rollback() // idempotent; returns a done error after commit

if _, err := tx.Update("accounts", from, map[string]any{"$inc": map[string]any{"balance": -100}}); err != nil {
    return err
}
if _, err := tx.Update("accounts", to, map[string]any{"$inc": map[string]any{"balance": 100}}); err != nil {
    return err
}
if err := tx.Commit(); err != nil {
    if errors.Is(err, engine.ErrConflict) {
        // A related collection changed; Begin again and retry.
    }
    return err
}

Full isolation levels, semantic details and retry advice live in docs/transaction-isolation.md. Keeping transaction semantics in their own document rather than scattering them through comments says something about the project's documentation.

Atomic batches

Transactions cover multi-step work with rollback. Batches cover "all at once, no intermediate state", and the strategy is clone and stage.

  • Every write in the batch runs against clones of the affected collections. Any failure, whether a duplicate id, a unique index conflict, an invalid update expression or a missing target, discards the whole batch with the real data never touched.
  • On success the whole change set is written as one batch record, which is one WAL entry, replayed atomically, so there is no half-commit.
  • Batches span collections. Updating a missing target is an error; deleting a missing target is not, and the result reports that nothing was deleted. Both directions follow what the caller most likely meant.

Cloning costs peak memory during the batch and buys atomicity without rollback logic. A failing path throws the clone away, and there is no code that has to undo half-applied index maintenance, which is the hardest code in a database to get right. The mechanism is the same snapshot family as transactions.

Batches also read from stdin, and because success writes one record, importing a hundred thousand documents costs one fsync instead of a hundred thousand. Under a WAL, batching pays multiplicatively.

Read-only SQL and aggregation

SQL: three stages, same engine

engine/sql.go at 624 lines is a hand-written read-only subset: lex, parse, execute. It supports select with from, where, order by and limit or offset, plus count star.

The important property is that it brings no execution engine of its own. The parse result is translated into the same query structure the REST and CLI paths use, with filter, sort, limit, skip and fields, and then runs through the same filter compiler, the same index planning and the same Top-N sort. SQL and find performing identically is not a coincidence. They are one pipeline with two front doors.

The boundary is explicit, and the cost of that simplicity is stated too: no joins, no group by, no having, no distinct, no subqueries, no union and no column aliases; aggregation supports only count star; and like is case-sensitive. For query convenience on an embedded store, that subset covers most of "pull data out for a script".

Aggregation pipeline

Eight stages: match, group, sort, skip, limit, project, unwind and count. Accumulators are sum, average, minimum, maximum, first, last and push, named to match MongoDB so people who know it need no learning time.

The limits are honest in the same way: no lookup, no facet, no window functions, no out or merge, and aggregation does not use indexes. A match at the head of a pipeline can still benefit from the caller pushing filters down, but the pipeline itself does no index planning.

HTTP service

The server package wraps the engine in REST.

  • Routes. Health, CRUD under a versioned collection path with filter, sort, limit, skip, fields and count carried in query parameters, and admin endpoints such as compaction.
  • Auth. An empty token disables authentication. Otherwise requests carry a token header. The shared token is the admin credential, and per-user tokens can be limited to admin, write or read with an exact-match collection allowlist.
  • HTTP transactions. A post opens a transaction and returns an id, operations run under that id, and the caller commits or rolls back. Sessions live in server memory, roll back after thirty idle minutes, and roll back at shutdown, so a forgotten transaction cannot pin snapshot memory indefinitely.
  • Defensive details. An 8 MiB request body cap, with large imports pushed to the CLI; parameter validation; consistent error codes; and request parsing that never leaves a connection half-open.

HTTP transactions share the same transaction implementation as the Go API. The session layer only maps ids to transactions and reaps the idle ones. Thin entry points, one engine, again.

Measured performance

A hundred thousand documents, with equality and range queries matching a thousand of them. These are local Windows numbers, and they move with the machine and the load.

ScenarioTimeAllocations per op
Equality, indexed3.0 ms2,037
Equality, full scan12.0 ms2,012
Range, indexed3.1 ms2,037
Range, full scan27.3 ms2,012
Projection, indexed3.1 ms2,037
Sort and paginate, 10k hits, skip 500, limit 5012.9 ms208

Random-order full sort, 100k hits85.3 ms6

Four readings from that table.

  1. Indexes are worth four to nine times, and the range case shows the wider gap because a scan recompares per document while an index binary-searches and walks the hit span.
  2. Top-N is worth thirteen times. Never fully sort when you only need the first N.
  3. Allocations per op are more trustworthy than wall time. The README notes that consecutive benchmark runs throttle the CPU and absolute timings can swing by more than 30%, so compare allocation counts.
  4. Sort with pagination allocates only 208 times, because extracting sort keys and using a heap decouples comparison from field lookup.

The tuning advice is just those mechanisms again. Index hot filter fields, but not too many. Project with the fields parameter when you need a subset, since projection copies while copying and costs the same allocations. Pair sort with limit whenever you only need the first N. Accept losing recent writes with the no-sync flag if throughput matters more. And raise the compaction threshold for write-heavy workloads, at the cost of a longer replay on restart.

Tests and engineering quality

go vet ./...
go test ./...
go test -cover ./...
go test -race ./...        # needs cgo and a C compiler
go test ./engine -run '^$' -bench Benchmark -benchmem

All three packages pass: cmd in 0.87 s, engine in 1.08 s, server in 1.58 s. Coverage is about 80% on engine and server, 75% on cmd.

The coverage list shows where the emphasis sits.

  • Engine: CRUD, query operators, sort, paging and projection, four kinds of index and uniqueness, aggregation, SQL parsing and execution, batch atomicity, transaction isolation and conflict, WAL replay, compaction and the directory lock, behaviour after close, and update error paths.
  • Server: auth, roles and allowlists, account storage, routing, method handling, parameter validation, error codes, transaction sessions and timeout reaping, and the body cap.
  • CLI: argument parsing, the full path of a one-shot command, shell transactions and EOF rollback, and starting and stopping the server.

What deserves credit is that crash and boundary scenarios are part of the regular suite rather than a happy-path check. Recovery, compaction, locking and EOF rollback are exactly where durability projects fail in production. Benchmarks use a hundred thousand documents, with a paired A/B between a full sort and Top-N on randomly ordered data.

The git history shows the process being maintained as well: semantic version tags and releases on each commit, normalised line endings, explicit module cache handling. A 0.1.0 project that builds its release pipeline first intends to be around.

The differences in positioning come down to three points.

Against SQLite: SQLite is relational, with full SQL and disk paging, and its data can far exceed memory. NanoDB is a document model that lives in memory, and it sells native JSON plus friction-free Go embedding. For analytical SQL over a lot of data, choose SQLite. For dropping a JSON store into a Go service, NanoDB is less work.

Against the LevelDB family: those are key-value engines with no query language and no index abstraction. Using one for documents means writing the whole layer above it, which is exactly what NanoDB ships.

Against MongoDB: Mongo is a network protocol, replica sets and sharding, with an operational cost in a different category. NanoDB has no distributed ambition. It is a data directory inside your process.

Known limits

This section comes straight from the project's own statement, and a database project that documents its limits more carefully than its features is easier to trust.

  • Memory resident. Documents and indexes live in memory, so data size is bounded by RAM. The WAL is JSON Lines, which costs more space than a binary format.
  • No distribution. No replicas, no sharding, no clustering, one process per directory at a time.
  • Transaction boundaries. Isolation is fixed and not configurable. Conflict granularity is the collection, so false conflicts happen. No savepoints, no DDL inside a transaction, no cross-process transactions.
  • Text search is approximate. Bigram tokenization, no stop words, no stemming, no synonyms, no relevance scoring, multi-term queries are AND, and the indexed field is fixed.
  • Geo is limited. Box and circle only, no polygons or GeoJSON geometry, no 180th meridian, and results are not distance-ordered.
  • SQL is read-only and partial. No joins, group by, having, distinct, subqueries or union. Aggregation is count star.
  • Aggregation skips indexes. No lookup, no facet, no window functions, no out or merge.
  • Compound indexes fall back on arrays. A document containing an array field never enters a compound index, and planning falls back to a scan.
  • Coarse permissions. Collection allowlists are exact match, with no wildcards or field-level rights, and the HTTP body cap is 8 MiB.
  • Array inserts are not atomic. Use a batch or a transaction when atomicity matters.

When to use it, and when not to

A good fit: local storage inside Go tools and services, such as configuration, task queues, crawler state or desktop application data, where you do not want to run a database service to store tens of thousands of JSON rows. Read-heavy workloads whose data fits in memory, where indexes and Top-N give millisecond responses. Teaching and forking, because ten thousand dependency-free lines with every part present make an excellent starting point for changing the WAL format, adding an index kind or practising transactions. And edge or single-machine deployment, where one binary with no cgo and no external service is the entire story.

A poor fit: data larger than memory, or terabyte-scale durability, which belongs to SQLite and the LSM family. Multi-process writes to one directory, or multi-node high availability, which the project explicitly gives up. Transaction-heavy writes on hot collections, where collection-level optimistic conflicts cause large numbers of retries. And production requirements around relevance-ranked search, complex SQL analytics or precise geospatial computation.

Closing

Back to the three opening questions.

How short is the shortest path to a transactional database? A transaction struct plus a version-check loop. The whole file is "collection snapshot plus read-set validation at commit". No lock manager, no undo log, and it still provides repeatable read, protection against lost updates, and an explicit conflict error for the caller to retry.

How many lines is "committed data survives a crash"? Three layers: replay finds the valid prefix and truncates a torn record, the writer rolls back a failed write to the previous complete record, and a generation number makes a crash inside the compaction window self-resolve. Under a hundred lines of core. The hard part is not the code, it is thinking through the state at every crash point.

How do documents, indexes and concurrency fit together? Every write goes through one entry point that maintains all four index kinds synchronously. Transactions carry those indexes inside the cloned snapshot. And planning only chooses the smallest candidate set, with the full match as the backstop.

NanoDB will not replace SQLite, and has no intention of replacing MongoDB. Its value is putting the black box on the table: the WAL is newline-delimited JSON, a transaction is a version comparison, and query planning is picking the smallest candidate set. The mechanisms are plain enough to memorise, and that plainness is exactly why they can be trusted.

If you have ever thought about writing a database, the answer here is yes, and it does not take many lines. The next step is not reading more papers. Clone it and break replay, commit and planning one at a time, then check whether the tests still pass. That is a faster introduction than any article.
