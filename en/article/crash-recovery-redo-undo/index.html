After the Power Cut: How redo, undo and torn pages save the database

2026-11-13 · 28 min · Stack Frame

Who this is for: people who have written a WAL or a storage engine but cannot say what each step of "recovery" actually does; people puzzled that their data was still there after a kill -9; people currently tuning synchronous, innodb_flush_log_at_trx_commit and checkpoint parameters; people who want to know what the doublewrite buffer really protects against. Bottom line first: recovery is not as simple as "replay the log once". It is made of three things: the log reaches disk before the data (write-ahead), idempotent redo replay, and undo rollback of uncommitted transactions. Atomicity comes from the log, durability from fsync, integrity from checksums and doublewrite. Drop any one of them and you end up with "looks recovered, but the data is already wrong". 1. Four failures, four ways to survive

Start with four scenarios that really happen:

  1. The process gets kill -9'd: the OS is still alive, the page cache is still there, the kernel closes the file descriptors. When the database starts next time it may see a half-written WAL, a leftover journal, or nothing at all.
  2. The machine loses power: the page cache in memory is gone, and only part of what was written may have reached the disk; the last WAL frame may be half a frame, and a data page may have only one sector written.
  3. One frame in the middle of the WAL goes bad: bad sectors, a bit flip, or deliberate damage. Every frame after the bad one may still be perfectly good — but is the database still willing to use them?
  4. Only half a page was written (torn page): 2 KB of a 4 KB page made it to disk and the other 2 KB is old data, zeros or garbage. The checksum can detect it — but once detected, what do you repair it with?

These four scenarios map onto four different mechanisms: a process crash mainly tests the log's atomic commit and recovery procedure; a power cut tests fsync ordering and log durability; a bad frame tests checksums and the truncation strategy; a torn page tests doublewrite or full-page images.

Lump them together and you get plausible-sounding nonsense like "the database has a WAL, so it cannot lose data". Let's take them apart one at a time.

2. First, separate the failure models

The easiest mistake to make in recovery experiments is simulating a power cut by "copying the files". That is exactly what we did the first time: the writer process was still running while the parent process copied .db, -wal, -journal and -shm one by one into another directory, then opened the copy. Several of the 25 runs failed outright with database disk image is malformed.

That is not a database bug — it is that copying across files is not an atomic snapshot. On a real power cut, the filesystem guarantees the ordering of each write and fsync; when you copy, the main database, the WAL and the journal are read at different instants and can combine into a state that never physically existed. Any conclusion you draw about recovery logic from such a copy is untrustworthy.

So we split the experiments into three kinds:

  • Process crash: kill the process, wait for it to exit, then copy the files. This simulates "the process is gone but the OS cache and the files are still there", and it validates the recovery procedure and atomicity.
  • Log corruption: flip a single byte at a precise offset in an already-written WAL, then open the database. This simulates bad sectors / bit flips and validates checksums and the truncation strategy.
  • Torn page: use a small page/redo simulator to control which half of the write succeeds and what the other half becomes, validating what doublewrite is responsible for.

The three kinds answer different questions and cannot substitute for each other. Every number below says which kind it came from.

3. The three basic rules of recovery

Whatever the database, crash recovery cannot get around three rules.

Rule one: the log must reach disk before the data.

Before a page is modified, the log describing that modification must already be durable. Otherwise, after a power cut the data page is new and the log is old, and recovery has no idea why the page looks the way it does. SQLite's rollback journal writes the old page image before it writes the data page; WAL appends the new page image to the WAL and fsyncs it before commit (with synchronous=FULL). InnoDB must make sure the corresponding redo is in the log file before it flushes a dirty page.

Rule two: redo must be idempotent.

Replaying the same redo record once and replaying it ten times must give the same result. Physical logging usually records "change the N bytes starting at offset O of page P to X", which is naturally idempotent; logical logging records "add 100 to account A", and replaying that twice adds 200, so logical logs need LSNs or a transaction table to deduplicate. InnoDB's redo is page-level physical logging that records in-page changes; SQLite's WAL is a whole-page image, so replay means overwrite, which is also idempotent.

Rule three: uncommitted transactions must be rollback-able.

Recovery does not only roll forward, it also rolls back. A transaction that was running when the crash hit may already have written part of its data pages, or may have written only to the log. The recovery procedure must be able to tell which transactions committed and which did not, and then undo the changes of the ones that did not. SQLite rolls back using the old page images in the journal; InnoDB rolls back using the undo log, and once the rollback is finished the purge thread cleans up the old versions.

Hold on to these three rules and specific implementations stop being confusing.

4. The SQLite rollback journal: undo with old page images

SQLite's default rollback journal mode works on a very direct idea: before modifying a page, write that page's old contents to the journal file.

A transaction roughly goes like this:

  1. Take a RESERVED lock on the database file and create the -journal file.
  2. Write the journal header: magic, page count, checksum, database size, sector size, page size.
  3. For every page about to be modified, append a record: page number + old page contents + checksum.
  4. Flush the journal to disk (synchronous=FULL) so the old contents are durable.
  5. Modify the pages in the database file; on commit, release the lock and delete the journal.
  6. If it crashes partway through, the next open finds a journal that exists but has no matching lock, treats it as a "hot journal", writes the old page images back page by page, and then deletes the journal.

So the journal is essentially a physical undo log. It records what things looked like before the change, and recovery performs a rollback rather than a replay. It does not need to know anything about transaction logic: restore the pages to their old versions and the uncommitted changes are gone.

That also explains why the journal size depends on "how many existing pages were modified" rather than on "how many rows were inserted". With sequential appends most pages are new, and the only old pages are the one or two rightmost ones, so the journal is just 12.8 KB; with 2000 random updates you touch over a thousand existing pages and the journal grows to 1–7 MB.

PRAGMA synchronous controls how hard the journal is flushed: FULL fsyncs at the critical points, NORMAL reduces the number of syncs, and OFF leaves the ordering to the operating system. OFF can leave you with a corrupt database after a power cut, because the journal may never have reached disk while the data pages were already written.

5. SQLite WAL: redo with new page images

WAL mode turns the direction around: it does not write old pages, it appends new pages to the WAL file.

A WAL file consists of a 32-byte header and a number of frames. Each frame is a 24-byte frame header plus one whole page of data:

WAL header (32 bytes)
├─ magic / version / page_size / checkpoint_seq / salt / checksum
Frame 1
├─ page number (4)
├─ database size after commit (4)   ← non-zero means this is a commit frame
├─ salt1 / salt2 (8)
├─ checksum1 / checksum2 (8)
└─ page data (page_size)
Frame 2 ...

At commit, SQLite appends every page this transaction modified to the WAL as a frame, and writes a non-zero "database size after commit" in the last frame to mark the end of the transaction. To read, it first consults the WAL index (-shm) for the newest frame of each page in the WAL, and only reads the main database file when the page is not there.

The SQLite documentation states the recovery rule plainly: scan the WAL once, sequentially, from the start, verifying the checksum of each frame, and stop at the first invalid checksum; mxFrame is the last valid commit frame. That means WAL recovery is prefix-shaped: commits before the bad frame are valid, and frames after it are not used even if their bytes are intact. The experiment in the next section shows exactly this.

With synchronous=FULL, every commit fsyncs the WAL; with NORMAL, it only syncs at key points such as checkpoint. The difference shows up after a power cut as "whether the last few committed transactions are lost", and is usually invisible after a process crash, because the OS cache is still there.

6. Experiment 1: 55 recoveries after a process crash

Setup: the writer commits every 200 rows and keeps inserting 120-byte random values; once it is in steady-state writing, the parent waits a random 0.15–1.2 seconds, kills it, then copies the database file, WAL and journal, opens the copy, and runs PRAGMA integrity_check plus a count.

Three configurations, 55 runs in total:

Configuration Transaction size Recovered Row count stayed atomic Median recovery time Median log size
rollback journal + FULL 200 rows 20/20 20/20 8.26 ms journal 12.8 KB
WAL + FULL 200 rows 20/20 20/20 3.98 ms WAL 4.13 MB
WAL + NORMAL 200 rows 20/20 20/20 6.76 ms WAL 4.15 MB
rollback journal + FULL 2000 rows 15/15 15/15 6.53 ms journal 12.8 KB
WAL + FULL 2000 rows 15/15 15/15 10.15 ms WAL 4.29 MB

"Row count stayed atomic" means the row count after recovery is always a whole multiple of the transaction size — you never see a transaction with only half of its rows in place. All 55 runs passed, which says that under the process crash failure model, both journal rollback and WAL recovery in SQLite preserve atomicity.

Recovery times are modest: a few milliseconds up to the low teens. The WAL log is much bigger (around 4 MB), yet its recovery time is not notably worse than the journal's, because WAL recovery is fast while the -shm index is still there and only needs a full scan if that index is lost. Note that this measures "time to open the database and execute the first statement", not the full table scan and integrity_check that follow.

The process crash experiment has one important limitation: it does not simulate a power cut. After kill, the OS cache still writes the data back to disk, so what SQLite sees may differ from what it would see after a real power cut. To study power cuts you have to control log corruption, or use storage that can simulate power loss.

7. Experiment 2: transaction shape decides log volume

The second batch changes one variable: the database already holds 300,000 rows, and the transaction no longer appends but randomly updates 2000 rows. Everything else stays the same.

Configuration Recovered Row counts correct Log size Median recovery time
rollback journal + FULL 8/8 8/8 1.2–7.4 MB 92.25 ms
WAL + FULL 8/8 8/8 7.4–7.5 MB 19.61 ms

Same table, same transaction size — the only difference being that we are modifying existing pages — and the journal jumps from 12.8 KB to several MB while recovery time goes from 8 ms to 92 ms. Section 4 already gave the reason: the journal records old page images, and random updates touch a large number of existing pages, whereas sequential inserts only modify the rightmost pages so the old page images are nearly zero.

The WAL log also grows, but its recovery time actually comes out shorter than the journal's. This is not "WAL always recovers faster"; the two do different work during recovery. The journal has to write several MB of old pages back into the main database, while the WAL mostly scans frames and rebuilds an index, and can defer writing the pages back to checkpoint. Log volume and recovery time are not a simple linear relationship — what matters is what the recovery phase actually does.

This set of numbers is useful for capacity planning: if a service is dominated by random updates, the undo/redo volume will be far above what "how much I insert" suggests. Sizing log space by inserted row count tends to underestimate by an order of magnitude.

8. Experiment 3: deliberately corrupting one WAL frame

The third batch damages the WAL directly. First we generate a WAL containing 40 transactions of 200 rows each: 379 frames, 41 commit frames (including the one from creating the table), 1.56 MB. Then we flip one byte at each of three positions:

  • The first frame after the first frame (frame 2): damages the first data frame.
  • A frame in the middle (frame 189): damages the halfway point.
  • The last frame (frame 378): damages the final commit frame.

Results:

Corruption site Frame Rows after recovery Rows expected integrity_check Recovery time
After the first frame 2 0 8000 ok 6.51 ms
Middle 189 3800 8000 ok 8.57 ms
Last 378 7800 8000 ok 10.91 ms

The three results map exactly onto the prefix property of WAL:

  • Corrupting frame 2 leaves recovery able to see only the table-creation commit (frame 1); every data frame after it is discarded, so the table exists with 0 rows.
  • Corrupting frame 189 makes recovery stop at the commit in frame 180 (19 transactions × 200 rows = 3800 rows); the commits after frame 190 are not used even though their bytes are intact.
  • Corrupting the last frame keeps the first 39 transactions (7800 rows) and loses only the final one.

All three integrity_check runs returned ok. That is the crucial part: the database is not "corrupt" — it has simply chosen a consistent version of history. The WAL checksums let recovery stop cleanly at the last trustworthy commit point instead of splicing in the "looks fine to me" data after the bad frame.

Which is why both "a bad WAL means everything is gone" and "WAL has checksums so it cannot lose data" are wrong: checksums guarantee consistency, not completeness. Transactions committed after the bad frame really are lost, but the database will not keep serving with half a transaction in it.

9. InnoDB: redo, undo and the three phases of recovery

The SQLite experiments only tell us about one family of implementations, the "page image log" family. InnoDB's log format is different, and its recovery procedure is more involved.

InnoDB's redo log is page-level physical logging: it records "which page of which tablespace, at what offset, changed to what", not a whole-page image. A modification is written to redo first, and dirty pages are flushed to the data files at an appropriate later moment. Every page has an LSN (log sequence number), and the checkpoint records "changes before which LSN have already reached disk". Recovery starts at the checkpoint and replays everything after it.

The documentation breaks crash recovery into several phases:

  1. tablespace discovery: scan the data directory and find the tablespaces the redo refers to.
  2. redo log application: replay redo from the checkpoint, bringing data pages up to their latest pre-crash state. If all dirty pages had already been flushed when the crash happened, redo application is skipped; if the redo files are missing it is also skipped (but data may be lost).
  3. rollback of incomplete transactions: after the replay, undo the transactions that were uncommitted at the crash. The documentation explicitly warns that rolling back an interrupted transaction can take three to four times as long as the transaction took to execute, depending on server load, and that the rollback cannot be cancelled.
  4. change buffer merge: merge buffered secondary-index changes into the leaf pages.
  5. purge: clean up old row versions that are no longer visible.

Here you can see the division of labour between redo and undo: redo is responsible for restoring all physical changes, committed or not, while undo is responsible for removing the logical transactions that never committed. Roll forward to the latest state, then roll back the part that should not exist. This is a different route from SQLite's rollback journal, which restores old pages directly: the journal is undo-only (it does not replay committed transactions, because the data pages were already in place), and WAL is redo-only (committed transactions are all in the log, and uncommitted ones never write a commit frame).

InnoDB also needs the undo log to support MVCC: a row may have several historical versions, and reads pick a visible version according to the Read View. After crash recovery finishes, undo cannot be deleted immediately — purge can only clean up once no active transaction needs those versions any more. This is why long-running transactions block purge and let the undo tablespace grow.

9.5. Three recovery strategies in one table

SQLite journal, SQLite WAL and InnoDB represent three different sets of trade-offs. Line them up by "what is written before commit, which direction recovery moves, how a bad page is repaired" and the boundaries become much easier to see:

Dimension SQLite rollback journal SQLite WAL InnoDB
Written before commit old page images new page images redo (in-page changes)
Commit marker journal header + sync commit frame (dbsize≠0) commit LSN in redo
Recovery direction undo only redo only redo first, then undo
Uncommitted transactions overwritten by old pages, gone automatically no commit frame, so never seen rolled back by undo
Bad page repair old page from the journal new page from the WAL frame doublewrite + redo
Recovery cost mainly depends on journal size frame count and index state redo volume after the checkpoint + rollback volume
Typical weakness journal balloons under random updates committed work lost after a bad frame slow rollback of long transactions, undo growth

This table answers a common confusion: why does SQLite's journal recovery not need to "decide whether a transaction committed"? Because it never replays transactions at all; it just restores pages to how they looked before the transaction started. An uncommitted transaction never had complete page modifications, so restoring the old pages makes it vanish; a committed transaction's journal was deleted at commit, so it cannot be rolled back. The price is that the journal must reach disk before the data pages, and that the bigger the journal, the more has to be written back during recovery.

WAL makes the opposite choice: it only records new pages, and the commit frame is the transaction boundary. Recovery needs no "rollback", because an uncommitted transaction has no commit frame and mxFrame will never move past it. The price is that the WAL keeps growing and has to be reclaimed by checkpoints, and that a bad frame truncates every commit after it.

InnoDB wants both: redo guarantees "page modifications that already happened are not lost", undo guarantees "logical transactions that did not commit do not take effect". That buys more capability (MVCC, rollback, staying up after a crash) and more complexity (undo tablespaces, purge, long transactions).

9.6. Is redo a physical log or a logical log?

InnoDB's redo is often described as a "physiological log", which is a confusing phrase. Take it apart:

  • Physical: it records "which page, which offset within the page, changed to which bytes", not "which SQL statement ran". So replay needs no query optimiser and no transaction context, and it is fast and idempotent.
  • Logical: at the in-page level it records a set of changes (insert a record, update a field, modify the page header) rather than a whole-page image. Recovery has to apply those changes to the page rather than simply overwrite it.

Contrast that with SQLite WAL's "whole-page image": one WAL frame is one 4 KB new page and replay is an overwrite, while one InnoDB redo record may be only a few dozen bytes describing a single in-page change. The former has high write amplification and simple recovery; the latter has low write amplification and recovery that must understand page structure.

The idempotence of physical logging comes from "recording the final value": change the N bytes at offset O to X, and doing it once or ten times gives the same result. Logical logging is not necessarily idempotent — "add 100 to the balance" run twice is simply wrong. That is why InnoDB's redo must be physical/physiological, whereas a logical log like the binlog needs GTIDs, server_id and log positions to deduplicate.

One more easily missed detail: InnoDB writes redo in units of mini-transactions (mtrs), and a single user transaction may contain several mtrs, each flushing its redo into the shared log buffer when it ends. Recovery replays them in LSN order and does not care which user transaction they belong to; transaction boundaries are determined by undo and by commit records. This layering — mtr at the physical level, transaction at the logical level — is the key to InnoDB achieving high concurrency and crash recovery at the same time.

10. Torn pages: why redo can sometimes fix them and sometimes cannot

Now the most widely misunderstood piece: the torn page.

Say page P's old version is V0 and its new version is V1. The transaction modified some bytes of P, and redo recorded the new values of those bytes. When the dirty page is flushed, the disk only completes half the write: the first 2 KB is V1, the last 2 KB is still V0 (or has become zeros or garbage). After the power cut and restart, recovery reads P and the checksum does not match.

So what happens?

Case one: the unwritten second half still holds V0. Replaying redo writes the modified bytes to their V1 values; the bytes that were never modified were already V0, which agrees with V1. After the replay the page is exactly V1 and the checksum passes. Redo alone repairs this kind of torn write.

Case two: the unwritten second half has become zeros or garbage. Redo only covers the modified bytes; the bytes that were not modified but have been overwritten with zeros appear in no redo record at all. After the replay the page is still incomplete and the checksum fails. Redo cannot repair it — you need a complete copy of V1.

Doublewrite exists for case two. When InnoDB flushes a dirty page it first writes the pages sequentially into the doublewrite area and fsyncs, then writes them to their real location in the data files. During recovery, if a page in the data file fails its checksum, the complete copy is found in doublewrite, written back over it, and redo is applied on top. The documentation points out that doublewrite is a large sequential write plus a single fsync, not two random I/Os per page, so its cost is far below the literal reading of "write everything twice".

We validated this division of labour with a simulator running 4000 trials per group. The model: 4 KB pages with a CRC, redo records the after-image of several byte ranges, a torn write puts V1 in the first half and V0 or zeros in the second, and recovery replays redo and compares the result against V1.

The other half of the torn page Without doublewrite With doublewrite
Keeps the old bytes V0 0% corrupt 0% corrupt
Becomes zeros 100% corrupt 0% corrupt

These numbers say: doublewrite does not protect against "all torn writes", it protects against "the bytes redo cannot cover getting destroyed". If the disk guarantees that unwritten sectors keep their old contents, redo is enough; if it may return zeros or garbage, you need a complete copy. The sector atomicity, write cache and power-loss behaviour of the real hardware decide which cell you land in, which is why enabling doublewrite by default in production is reasonable.

One caveat: this is a model, not InnoDB itself. After a page is modified for the first time, InnoDB also records a full-page image, which shifts the boundary of "can redo repair this by itself"; behaviour also differs between versions and between different innodb_flush_method settings. The model's value is in separating two variables — "what redo covers" and "what the medium actually wrote" — not in producing a percentage that applies to every engine.

11. Configuration, monitoring and recovery drills

Bringing the mechanisms above down to day-to-day operations, you can check them against this list:

Durability configuration

  • SQLite: synchronous=FULL is the floor for power-cut safety; NORMAL in WAL mode only guarantees consistency, and recent commits may be lost; OFF is unsuitable for anything that cannot lose data.
  • InnoDB: innodb_flush_log_at_trx_commit=1 means fsync redo on every commit; =2 only writes to the OS cache, which is faster but may lose the last second; =0 lets a background thread flush once a second, which is riskier still.
  • Log file size: too small a WAL/redo means frequent checkpoints, too large means long recovery. Work backwards from your write rate and acceptable RTO.

Metrics to watch

  • WAL/redo growth rate and checkpoint frequency;
  • recovery time (from start to serving) versus log size;
  • periodic results of integrity_check / CHECK TABLE;
  • the disk's power-loss protection (PLP), write cache policy and sector size;
  • InnoDB's purge lag, history list length and undo tablespace size.

Recovery drills

  1. Backup + log replay: restore from a full backup to a point in time and record the RTO.
  2. Simulated accidental deletion: drop a table, replay from binlog/WAL back to just before the drop, and verify the data is complete.
  3. Simulated bad frame: flip one byte in a copy of the WAL on a test database and confirm the database starts and reports the lost range.
  4. Simulated torn page: exercise the doublewrite path on storage that supports fault injection, or with a simulator.
  5. Record "how many transactions were actually lost" for every drill, instead of only checking "did it start".

Recovery capability is not configured, it is drilled. A backup that has never been restored does not count as a backup.

12. Source map and reproduction scripts

SQLite

  • pager.c: pager_write marks pages dirty, pager_playback replays the journal, sqlite3PagerCommitPhaseOne handles the log writes in the commit phase.
  • wal.c: sqlite3WalFrames/walFrames append frames, walIndexRecover scans the WAL, verifies checksums and sets mxFrame.
  • Official documentation: WAL-mode File Format, Database File Format.

InnoDB

  • log0recv.cc: the main redo recovery flow, scanning and replaying from the checkpoint.
  • buf0dblwr.cc: doublewrite writing and recovery.
  • trx0rec.cc / trx0roll.cc: undo records and transaction rollback.
  • Official documentation: InnoDB Recovery, Doublewrite Buffer.

Minimal scripts that reproduce the experiments:

import os, random, sqlite3, subprocess, sys, time, shutil

BATCH = 200

# writer: commits every BATCH inserts, stops when killed
WRITER = '''
import os, sqlite3, sys
db, mode, sync, ready = sys.argv[1], sys.argv[2], sys.argv[3], sys.argv[4]
con = sqlite3.connect(db)
con.execute(f"PRAGMA journal_mode={mode}")
con.execute(f"PRAGMA synchronous={sync}")
con.execute("CREATE TABLE IF NOT EXISTS kv(id INTEGER PRIMARY KEY, v BLOB)")
con.commit()
open(ready, "w").close()
payload = os.urandom(120)
while True:
    con.execute("BEGIN")
    for _ in range(%d):
        con.execute("INSERT INTO kv(v) VALUES(?)", (payload,))
    con.commit()
''' % BATCH

# parent: wait for ready, random delay, kill, then copy the files
# open the copy and run PRAGMA integrity_check and count(*)

The key to the WAL corruption experiment is parsing the frame layout:

import struct

data = open('db-wal', 'rb').read()
magic, version, page_size = struct.unpack('>III', data[:12])
frame_size = 24 + page_size
frames = (len(data) - 32) // frame_size
for i in range(frames):
    off = 32 + i * frame_size
    pgno, dbsize = struct.unpack('>II', data[off:off + 8])
    # dbsize != 0 means this is a commit frame

Pitfalls we hit:

  1. Do not copy while writes are in flight. Copying across files is not an atomic snapshot and produces states that never physically existed; kill first, then copy.
  2. integrity_check scans the whole table. Folding it into your recovery time gets you the wrong conclusion that "bigger database, slower recovery"; recovery time should only count from opening the database to the first statement.
  3. WAL frame checksums are cumulative. Damage one frame in the middle and every later frame is discarded even though its bytes are intact; that is the design, not a bug.
  4. A process crash is not a power cut. To verify fsync semantics you have to work on real power loss or on storage that can inject faults.

13. Summary: recovery is a chain of time

Compress the whole article into one chain of time:

  1. Before a modification happens, the old pages (journal) or the new pages (WAL/redo) reach disk first — write-ahead.
  2. At commit, an explicit commit point appears in the log — the transaction is either entirely visible or entirely invisible.
  3. After a crash, replay the log from the checkpoint — redo, pushing the physical state to the latest version.
  4. Roll back the uncommitted transactions — undo, pulling the logical state back to a consistent point.
  5. Checksums find bad pages and bad frames; doublewrite or a complete copy repairs torn writes.
  6. Checkpointing and purge clean up, and the database returns to normal service.

SQLite's journal and WAL sit at the two ends, "undo-only" and "redo-only", while InnoDB is the combination "redo + undo". Their concrete formats differ, but the division of responsibility across these six steps is the same.

What you really need to remember is not some function name or parameter, but three questions:

  • Does my log reach disk before my data?
  • Can my recovery state plainly which transactions count?
  • Does my storage guarantee what the unwritten part contains?

Only when you can answer those three do you get to talk about "crash recovery".
