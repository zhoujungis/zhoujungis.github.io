Kth largest with duplicates: the answer can differ by a factor of two

2026-09-04 · 13 min · Stack Frame

The problem

Given an array with duplicates, output the tenth largest value, with attention to validation, boundaries and error handling.

[23, 7, 45, 12, 45, 8, 33, 12, 19, 5, 45, 27, 12, 9, 33, 16, 41, 3]
tenth largest counting duplicates -> 16
tenth distinct value               -> 8

The difficulty is neither the algorithm nor the heap. It is that the phrase tenth largest has two entirely different meanings when duplicates exist.

Ask which convention first

45, 45, 45, 41, 33, 33, 27, 23, 19, 16, 12, 12, 12, 9, 8, 7, 5, 3
                                    ^ the tenth position

Counting duplicates, the tenth position holds sixteen. Counting distinct values, the sequence is forty-five, forty-one, thirty-three, twenty-seven, twenty-three, nineteen, sixteen, twelve, nine, eight, so the tenth is eight.

Sixteen against eight, exactly double, from one unstated assumption. Both readings are defensible: the tenth highest score usually ignores ties, while the tenth largest order amount does not, since each order is its own record.

So the right move in an interview is to ask whether duplicates count once or many times. If the answer is either, write both and test both, which scores better than guessing.

There is a related hidden problem: under the distinct convention there may be no answer. With five identical fives and a request for the third largest, there is one distinct value, so the correct behaviour is a null result or an exception rather than forcing a number out. The counting convention never has this problem as long as the array is long enough.

The size-k min-heap

No sorting is needed. Maintain a min-heap with exactly k slots, whose root is the current kth largest.

  • While the heap is not full, push and sift up.
  • When full and the new value exceeds the root, replace the root and sift down.
  • Otherwise discard it in constant time.
import heapq

def kth_largest(nums, k, dedupe=False):
    if nums is None:
        raise ValueError("nums must not be None")
    if not isinstance(k, int) or k <= 0:
        raise ValueError("k must be a positive integer")
    if len(nums) < k:
        raise ValueError(f"length {len(nums)} is less than k={k}")

    heap = []
    seen = set()
    for v in nums:
        if dedupe and v in seen:
            continue
        if len(heap) < k:
            heapq.heappush(heap, v)
            seen.add(v)
        elif v > heap[0]:
            if dedupe:
                seen.discard(heap[0])
            heapq.heapreplace(heap, v)
            seen.add(v)
    if len(heap) < k:
        raise ValueError(f"only {len(seen)} distinct values, cannot reach k={k}")
    return heap[0]

The distinct convention needs the extra set, because the comparison with the root is not enough. If the heap already contains a twelve and a new twelve exceeds the current root of eight, replacing would put two twelves in the heap. The set blocks values already present.

Choosing among three approaches

ApproachTimeSpaceWhen
Sort and indexLinearithmicConstant or linearEverything in memory, shortest code
Size-k min-heapn log kkThe standard answer when k is much smaller than n
QuickselectLinear average, quadratic worstConstantAverage linearity, input mutation acceptable

The heap is standard here because k is a constant, so the logarithm is a small constant, and because it needs no random access, which makes it work on a stream. Sorting and quickselect both require the whole array.

For the distinct convention there is a shorter alternative: deduplicate with a set first, then run the same heap. It costs linear space and is unusable on a stream, since you cannot know what values will arrive later. The version above keeps only the values currently in the heap, so its space is proportional to k.

Java

public static Integer kthLargest(int[] nums, int k, boolean dedupe) {
    if (nums == null) {
        throw new IllegalArgumentException("nums must not be null");
    }
    if (k <= 0) {
        throw new IllegalArgumentException("k must be positive, got " + k);
    }
    if (nums.length < k) {
        throw new IllegalArgumentException("length " + nums.length + " is less than k=" + k);
    }
    PriorityQueue<Integer> heap = new PriorityQueue<>(k);
    Set<Integer> inHeap = new HashSet<>();
    for (int v : nums) {
        if (dedupe && inHeap.contains(v)) {
            continue;
        }
        if (heap.size() < k) {
            heap.offer(v);
            inHeap.add(v);
        } else if (v > heap.peek()) {
            if (dedupe) {
                inHeap.remove(heap.peek());
            }
            heap.poll();
            heap.offer(v);
            inHeap.add(v);
        }
    }
    if (heap.size() < k) {
        throw new IllegalArgumentException("fewer than " + k + " distinct values");
    }
    return heap.peek();
}

The return type is a boxed integer rather than a primitive so that failure can be represented as null, which is cleaner than a magic value or an exception thrown from deep inside. Designing the impossible case into the type is part of the error handling.

Edges and failures

SituationExpected behaviour
Null inputRaise, rather than returning zero or minus one
Empty arrayRaise, since no kth element exists
Fewer elements than kRaise, rather than silently returning the smallest, which would mislead the caller about the rank
Non-positive or non-integer kRaise
Too few distinct valuesA failure unique to the distinct convention
Null elementsValidate before unboxing, or restrict the signature to primitives
NaN valuesSorting gives silent nonsense because every comparison is false, so reject non-finite input up front
InfinitiesComparable, but decide whether they are meaningful for the business
k of one or k of nDegenerate to maximum or minimum, a single scan
All elements equalThe counting convention answers the value; the distinct convention has one distinct value and may fail
Very large arraysThe heap uses k of memory, which is friendly; sorting needs the whole array

One design principle: insufficient length and insufficient distinct values are different failures, one independent of the convention and one specific to it. Report them separately with the numbers in the message, which saves ten minutes when debugging.

Complexity

Each element triggers at most one push or replacement, and each such operation costs the logarithm of k, so the total is bounded by a constant number of heap operations per element. With k of ten the logarithm is about three, which is more than an order of magnitude faster than sorting in practice.

Common mistakes

  1. Starting to code without asking about the convention. The official sample has no duplicates at the boundary, so both readings return the same value and it cannot distinguish them. Construct a case where they differ.
  2. Putting every element in a max-heap and polling k times, which is linear space and linearithmic time, in other words sorting with extra steps.
  3. Testing only against the root in the distinct convention, which lets a duplicate displace the root and enter twice.
  4. Returning the smallest element silently when the array is too short, which is more dangerous than crashing.
  5. Forgetting that the number of distinct values may be smaller than k.
  6. Feeding NaN to a sort, which silently produces a wrong answer.

How to answer it

Ask about the convention first, which immediately separates you from people who start typing. Then the standard solution with its complexity, then why sorting is unnecessary for small k and streaming, then the linear-time follow-up with its worst case and its mutation of the input. Then the failure modes, distinguishing insufficient length from insufficient distinct values.

Closing

The algorithm is the easy part: a size-k min-heap, linearithmic in k, constant space in k, streaming-friendly. The dividing line is the first sentence out of your mouth, distinct or not, where the answers differ by a factor of two and the official sample cannot tell. The second dividing line is error handling: five failure modes, each with its own correct behaviour, and silent degradation is far more dangerous than a crash.

As with the spiral fill article: align on the convention before discussing complexity.
