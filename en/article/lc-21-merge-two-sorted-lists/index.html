LC 21, merging two sorted lists: what the dummy node carries for you

2026-09-21 · 15 min · Stack Frame

The problem

Merge two ascending lists into one ascending list, reusing the original nodes.

input:  1 -> 2 -> 4   and   1 -> 3 -> 4
output: 1 -> 1 -> 2 -> 3 -> 4 -> 4

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

The word to notice is stitching: not allocating new nodes and copying values, but re-threading the existing ones. No value changes, only the direction of links.

The problem is easy and the pass rate shows it, and yet two failures recur even among people who have done hundreds of these: dropping half a list while stitching, and writing five branches to decide which node becomes the head, then missing one case. Easy problems rarely hide their difficulty in the algorithm; they hide it in the completeness of the boundaries.

Translating merge into pointer work

An array merge copies elements into a new array, because positions are index-based and you cannot attach an element to another array.

In a list the only organisation is the link, so putting a node into the result is one statement: point the tail's next at it. Nothing is copied or moved. That is why the list version needs constant extra space, since the result is made of the original nodes.

Both lists are ascending, so the global minimum can only be at one of the two heads. Compare the heads, take the smaller, advance that list, and repeat until one runs out. Then attach whatever remains of the other in one go, because it is already sorted and every value in it is at least as large as everything already placed.

The two traps

Losing the rest of a list while stitching

A node has one link, so before you overwrite it you have to know whether you still need what it pointed at. The safe order is to attach and then advance: at the moment of attaching, the pointer still refers to the node, and only afterwards does it move.

The failure people actually write is subtler: attaching without advancing the tail. The next node is then attached to the same tail, overwriting the previous one, and the result silently shrinks to one or two nodes with no error at all. The test before touching any link: after this change, can I still get back?

The first node is not known in advance

if l1 is None:
    return l2
if l2 is None:
    return l1

    ...  # identical to the real loop
return head

Four branches plus an initialisation that duplicates the loop body. Duplication means two places to keep in sync, and eventually one of them drifts.

The dummy node

dummy -> ? -> ? -> ?
tail -----^

A dummy holds no data; its only job is to occupy the head position in advance. With it, every attachment is the same ordinary operation, so the first node and the twentieth follow exactly one code path and there is no "is this the first" question anywhere. The real head is the dummy's next, and the dummy itself never enters the result.

The tail maintains the boundary of what has been stitched. Everything happens behind it, and everything in front of it is complete, ordered and never touched again. That is the same idea as the previous pointer in LC 206, which held the boundary of the reversed segment.

The original post animates the thirteen steps of merging the example, colouring nodes by which list they came from and drawing the dummy as a dashed box. Three moments are worth remembering: during a comparison both candidates are highlighted; when a node is taken it moves into the result row, its colour showing its origin; and at the end the leftover node from the other list lights up as a whole and is attached in one step.

Iterative

def mergeTwoLists(l1: ListNode, l2: ListNode) -> ListNode:
    dummy = ListNode(0)
    tail = dummy
    while l1 and l2:
        if l1.val <= l2.val:
            tail.next = l1
            l1 = l1.next
        else:
            tail.next = l2
            l2 = l2.next
        tail = tail.next
    tail.next = l1 if l1 else l2
    return dummy.next

public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0);
    ListNode tail = dummy;
    while (l1 != null && l2 != null) {
        if (l1.val <= l2.val) {
            tail.next = l1;
            l1 = l1.next;
        } else {
            tail.next = l2;
            l2 = l2.next;
        }
        tail = tail.next;
    }
    tail.next = (l1 != null) ? l1 : l2;
    return dummy.next;
}

Attaching then advancing is the safe order for the first trap. Moving the tail is the second half of it, or the next iteration overwrites the node just placed. And the final assignment handles the case the loop exits on, where one list still has a whole chain unattached.

Round five is the one to look at: the loop exits with the second list's four still hanging outside the result. Without the final line the output is missing its last node, which is the single most common wrong answer on this problem.

The edges all fall out of the same code. One empty list means the loop never runs and the other is attached whole, so none of the four branches the dummy-free version needed are required. Both empty returns null. Very different lengths behave like the example. And equal values take the first list, which is a stability habit rather than a requirement here, but the same comparison is what makes merge sort stable, and this loop is the merge step.

Recursive

def mergeTwoLists(l1: ListNode, l2: ListNode) -> ListNode:
    if not l1:
        return l2
    if not l2:
        return l1
    if l1.val <= l2.val:
        l1.next = mergeTwoLists(l1.next, l2)
        return l1
    else:
        l2.next = mergeTwoLists(l1, l2.next)
        return l2

public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    if (l1 == null) return l2;
    if (l2 == null) return l1;
    if (l1.val <= l2.val) {
        l1.next = mergeTwoLists(l1.next, l2);
        return l1;
    } else {
        l2.next = mergeTwoLists(l1, l2.next);
        return l2;
    }
}

Read it as a contract: merge these two ordered lists and return the merged head. With the first list's head no larger, it is the global minimum and therefore the answer's first node; the rest is the merge of the remainder with the whole second list, which is the same problem one node smaller. Attach that result and return the head. The base case is the identity element of the operation: merging anything with an empty list returns it unchanged.

The deepest stack is five frames, which equals the node count, because each level consumes one node.

Python's default recursion limit is about a thousand, which two lists of six hundred nodes exhaust. In production the iterative version wins; the recursion is worth writing in an interview to show you see the self-similar structure, and it is also a part of the divide-and-conquer solution to LC 23.

Complexity

Iterative is linear in time, since each node is touched once and compared once, and constant in space, for two extra pointers. Recursive is the same in time and linear in stack depth. The constant space is worth saying out loud: a list merge needs no auxiliary array, which is why LC 148 demands the list version when it asks for constant space.

Follow-up: k lists (LC 23)

Sequential merging reuses this function repeatedly, combining the first list with the second, then with the third. It works, and the nodes merged early are walked again in every later round, giving quadratic behaviour in the number of lists.

Divide and conquer pairs them up, halving the count each round like a tournament, so there are a logarithmic number of rounds with linear work in each, which is the familiar linearithmic bound.

import heapq

def mergeKLists(lists):
    dummy = ListNode(0)
    tail = dummy
    heap = []
    for i, head in enumerate(lists):
        if head:
            heapq.heappush(heap, (head.val, i, head))
    while heap:
        val, i, node = heapq.heappop(heap)
        tail.next = node
        tail = tail.next
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next

A heap keeps only the k current heads, since the global minimum can only be one of them, which is the same observation as this problem with k instead of two. Each node enters and leaves the heap once, giving the same complexity as divide and conquer with only k extra space. The index in the tuple breaks ties without ever comparing nodes.

Notice how much carries over: dummy, tail, attach then advance, take the smaller. The skeleton is identical, and only the "pick the smallest head" decision changes from a comparison to a heap. Master this problem and two of the three solutions to LC 23 come free.

The real application is LC 148, sorting a list: find the midpoint with two pointers, sort each half recursively, and merge with exactly this function. Constant-space sorting on a list is only possible with the bottom-up merge, whose core is the eight lines above, which is often why an interviewer starts here.

Mistakes to check

  1. Forgetting the final whole-chain attachment, which silently truncates the output on long inputs.
  2. Forgetting to advance the tail, which overwrites nodes and can even create a cycle.
  3. Writing the loop condition with a disjunction, then dereferencing an empty list. It must be a conjunction, leaving the leftover to the final line.
  4. Advancing before attaching, which loses the node.
  5. Using a strict comparison for equal values: the result is still correct, but the stability is gone, and an interviewer may ask why.
  6. Using the recursive version on very long lists and hitting the stack limit.
  7. Allocating new nodes and copying values, which the problem forbids and which costs extra space.

How to answer it

The short version: iterate with a dummy and a tail, compare the two heads, attach the smaller, advance both the source pointer and the tail; when the loop exits one list is empty, so attach the rest of the other, which is ordered and no smaller than what is placed; linear time, constant space, return the dummy's next.

Expect four follow-ups. Why a dummy: because the first node's origin is unknown, and without it the head needs special cases. Is there another way: recursion, three lines, at the cost of stack depth. Which side wins a tie: either, and taking the first keeps the stability that merge sort depends on. And how would k lists work: sequential, then divide and conquer, then a heap holding only k heads. The last comparison worth making is against an array merge: no copying, no auxiliary array, constant extra space, which is exactly what makes LC 148 possible.

Closing

Put this beside LC 206 and the two easy problems teach one thing: pointer work is boundary maintenance. The previous pointer guards the reversed segment, the tail guards the merged segment, and every dangerous operation happens behind the boundary, where nothing already finished can be disturbed.

Writing list problems calmly is not about memorising templates. It is knowing, before each pointer change, which region the pointer belongs to and whether the change closes the road back.
