A list endpoint from 800 milliseconds to 80: pagination, caching and throttling

2026-09-10 · 24 min · Stack Frame

Stack: Django 6, DRF, SQLite, on a free host with no Redis. The code is the real backend settings and views.

Reading time around 24 minutes. What you get: a performance template you can lift straight into production.

An integration test that took the blog down

class ArticlePagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = "page_size"
    max_page_size = 1000  # flexible seemed harmless at the time

A colleague tried a page size of five hundred. The server scanned five hundred rows of Markdown, serialised seven and a half megabytes of JSON and took 860 milliseconds; the free host's CPU saturated and every later request queued; and Vue choked for three seconds on the payload, so users assumed the site was down.

After the rebuild the list endpoint sits at sixty to a hundred milliseconds, and the first page in ten when it hits the cache.

Pagination

A global page size only decides the default slice. It leaves three real problems: a client can ask for ten thousand rows, different endpoints need different treatment, and search over large text columns makes a big page far worse.

So the rule is a global default plus a class per view set, and no pagination at all where the table is tiny.

class ArticlePagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = "page_size"
    max_page_size = 50
    page_size_query_description = "Rows per page, default 10, maximum 50"

class ArticleViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Article.objects.filter(status=Article.Status.PUBLISHED)
    lookup_field = 'slug'
    pagination_class = ArticlePagination

class CategoryViewSet(viewsets.ReadOnlyModelViewSet):
    pagination_class = None

class TagViewSet(viewsets.ReadOnlyModelViewSet):
    pagination_class = None

With no pagination class the response is a bare array instead of an envelope, which saves the front end a layer of parsing on small dictionary tables.

def paginate_queryset(self, queryset, request, view=None):
    page_size = self.get_page_size(request)
    if not page_size:
        return None
    paginator = self.django_paginator_class(queryset, page_size)
    page_number = request.query_params.get(self.page_query_param, 1)
    try:
        self.page = paginator.page(page_number)
    except InvalidPage:
        raise NotFound("Invalid page.")
    return list(self.page)

The size lookup is where the safety lives: a value above the maximum is silently truncated rather than rejected, and a non-numeric or negative value falls back to the default instead of erroring. So a page size of five hundred against a maximum of fifty returns fifty, which is protection rather than a bug.

For a blog, page numbers are enough; cursor pagination matters once a table is large and written frequently, as in a comment stream.

The fix was two things, not one: cap the page size and split the serialisers.

max_page_size = 50

def get_serializer_class(self):
    if self.action == "retrieve":
        return ArticleDetailSerializer
    return ArticleListSerializer

The cap should be computed, not guessed: maximum page size times the size of one list item stays under half a megabyte. At five kilobytes per item, fifty rows is a quarter of a megabyte.

Slim the list, fatten the detail

class ArticleListSerializer(serializers.ModelSerializer):
    category = serializers.SlugRelatedField(slug_field="slug", read_only=True)
    class Meta:
        model = Article
        fields = ["slug", "title", "excerpt", "cover_image",
                  "views_count", "likes_count", "created_at", "category"]

class ArticleDetailSerializer(serializers.ModelSerializer):
    class Meta:
        model = Article
        fields = ["slug", "title", "content", "cover_image",
                  "views_count", "likes_count", "created_at",
                  "category", "tags"]

def get_queryset(self):
    base = Article.objects.filter(status=Article.Status.PUBLISHED)
    if self.action == "list":
        return base.select_related("category").prefetch_related("tags").only(
            "id", "slug", "title", "excerpt", "cover_image",
            "views_count", "likes_count", "created_at", "category",
        )
    return base.select_related("category").prefetch_related("tags")

Restricting the columns is a trap if applied everywhere: touching a field you did not select costs an extra query, so the detail action must use a different queryset or none at all.

Pagination without fixing N+1 makes small pages slower

queryset = (
    Article.objects.filter(status=Article.Status.PUBLISHED)
    .select_related("category")
    .prefetch_related("tags")
)

Ten rows with a category and a tag lookup each is twenty-one queries, which is exactly what the earlier post measured. After the fix the list page should run three: the rows, the tags and the count. The count is the paginator's own aggregate, and it is normal; do not optimise it away.

The selector's largest option must not exceed the server's cap, or a reader choosing a hundred receives fifty and the page arithmetic drifts.

Five pagination traps

  1. Paginating a dictionary table with a dozen rows, which just adds an envelope for the client to unwrap.
  2. Setting the cap to a thousand, which is the same as not having one.
  3. Leaving search unbounded, where a broad term plus a large page is slow squared; give search its own tighter cap.
  4. Sending a page number beyond the end, which correctly returns a not-found rather than a server error; the client should compute the last page from the count.
  5. Unstable ordering, where rows created in the same second repeat or vanish across pages; append the id as a tie-breaker.

class ArticleViewSet(viewsets.ReadOnlyModelViewSet):
    @method_decorator(cache_page(60 * 5))
    def retrieve(self, request, *args, **kwargs):
        return super().retrieve(request, *args, **kwargs)

The page decorator keys on the full URL including the query string and returns the stored response body without entering the view at all. Hand-rolled, it is a get, a miss, a render and a set.

class CategoryViewSet(viewsets.ReadOnlyModelViewSet):
    pagination_class = None

    def list(self, request, *args, **kwargs):
        data = cache.get("api:categories:v1")
        if data is None:
            qs = Category.objects.annotate(
                article_count=Count(
                    "article",
                    filter=Q(article__status=Article.Status.PUBLISHED),
                )
            )
            data = CategorySerializer(qs, many=True).data
            cache.set("api:categories:v1", data, 3600)
        return Response(data)

@receiver([post_save, post_delete], sender=Category)
def clear_category_cache(**kwargs):
    cache.delete("api:categories:v1")

@receiver([post_save, post_delete], sender=Article)
def clear_article_list_cache(**kwargs):
    cache.delete("api:articles:page1")

Putting a version in the key is a cheap trick: a redesign bumps the version and every stale entry becomes unreachable, which is more reliable than deleting them one by one.

A page cache means the view never runs on a hit, so an inline counter stops moving. Small sites accept the delay; large ones use the beacon. Do not trade a cache for an exact counter.

The three cache failures, briefly

Penetration means repeated requests for an identifier that does not exist, fixed by caching the empty result for a minute or a bloom filter. The stampede is one hot key expiring while dozens of requests arrive, fixed by logical expiry or a guarded rebuild, and on a small site by simply not aligning lifetimes. The avalanche is everything expiring at once after a restart, fixed by jitter on the timeout.

The worker trap on a shared host

Production runs several worker processes, and the local memory cache is per process, so one worker clearing a key leaves the others stale for up to one lifetime. For a blog that is invisible; for stock it would not be. If it matters, switch to the database backend, which several workers share and which the free tier supports.

Throttling

A global anonymous limit stops a load test but not thirty spam comments a minute, thirty subscription attempts an hour or thirty likes on one article. Reading and writing differ by orders of magnitude and need separate budgets.

ScopeRateCoversReasoning
Anonymous30 per minuteAll reads by defaultNobody clicks thirty pages in a minute; scrapers get rejected
User100 per minuteReads when logged inRoom for preloading and type-ahead
Comment3 per minutePosting a commentTyping and thinking take longer than twenty seconds
Subscribe5 per hourNewsletter signupA dictionary attack on addresses is locked out
Upload100 per hourImage upload, authenticatedProtects storage; anonymous users cannot upload at all
 
def allow_request(self, request, view):
    self.key = self.get_cache_key(request, view)
    history = self.cache.get(self.key, [])
    now = self.timer()
    while history and history[-1] <= now - self.duration:
        history.pop()
    if len(history) >= self.num_requests:
        return self.throttle_failure()
    return self.throttle_success()

Throttles run before permissions, so a rejected request never reaches business logic. And the counter lives in the cache, which means a per-process cache multiplies the effective limit by the worker count, so real traffic needs a shared backend.

class SubscribeThrottle(AnonRateThrottle):
    scope = "subscribe"

@permission_classes([AllowAny])

Scoped throttles attach a budget to a view set; a named subclass is the clearest form and the one worth copying.

The forwarding header trap

Behind a proxy the remote address is the proxy, so every user looks identical. The framework prefers the forwarded header, which is a comma-separated chain whose left end is whatever the client claimed and whose right end is what the trusted proxy appended.

ip = request.META.get("HTTP_X_FORWARDED_FOR", "").split(",")[0].strip()

Taking the first entry means any client can send any address and evade both the limiter and any per-address deduplication. Take the last one.

xff = request.META.get("HTTP_X_FORWARDED_FOR", "")
if xff:
    ip = xff.split(",")[-1].strip()
else:
    ip = request.META.get("REMOTE_ADDR", "")
ip = (ip or "")[:64]

And the address used for throttling must be the same one used for business deduplication, or the two mechanisms disagree and neither works.

A rejection is a normal flow

api.interceptors.response.use(
  (res) => res,
  async (err) => {
    const { response, config } = err
    if (response?.status === 429 && !config._retried) {
      config._retried = true
      if (config.method === 'get') {
        const wait = Number(response.headers['retry-after'] || 5)
        await new Promise((r) => setTimeout(r, wait * 1000))
        return api.request(config)
      }
      const action = config.url.includes('subscribe') ? 'subscription'
        : config.url.includes('comment') ? 'comment'
        : 'like'
      alert(`Too many ${action}s, try again in a moment`)

The button guard matters because repeated clicking is the largest single source of rejections.

for i in $(seq 1 35); do curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/api/articles/; done
for i in 1 2 3 4 5; do curl -s -X POST http://127.0.0.1:8000/api/comments/ -H "Content-Type: application/json" -d '{"content":"test"}'; echo; done

Tune against a week of logs: a legitimate-user rejection rate above one percent means too tight, any spam comment means too loose. The comment budget here started at ten a minute and was tightened after a night of forty ads.

The finished view set

class ArticlePagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = "page_size"
    max_page_size = 50

class ArticleViewSet(viewsets.ReadOnlyModelViewSet):
    lookup_field = "slug"
    pagination_class = ArticlePagination
    filter_backends = [DjangoFilterBackend, filters.SearchFilter]
    filterset_fields = {"category__slug": ["exact"], "tags__slug": ["exact"]}
    search_fields = ["title", "content"]

    def get_queryset(self):
        base = Article.objects.filter(status=Article.Status.PUBLISHED)
        if self.action == "list":
            return (
                base.select_related("category")
                .prefetch_related("tags")
                .only("id", "slug", "title", "excerpt", "cover_image",
                      "views_count", "likes_count", "created_at", "category")
                .order_by("-created_at", "-id")
            )
        return base.select_related("category").prefetch_related("tags")

    def get_serializer_class(self):
        return ArticleDetailSerializer if self.action == "retrieve" else ArticleListSerializer

    @method_decorator(cache_page(120))
    def list(self, request, *args, **kwargs):
        return super().list(request, *args, **kwargs)

    @method_decorator(cache_page(300))
    def retrieve(self, request, *args, **kwargs):
        return super().retrieve(request, *args, **kwargs)

Checklist

Pagination. Every view set has its own class with a cap of fifty or less. The list serialiser carries no body field. Dictionary tables have no pagination. Ordering has a unique tie-breaker. The client's largest option matches the cap.

Caching. A backend is configured, starting in memory and moving to Redis with one settings change. Categories, detail and the first list page are cached; search and writes are not. Save and delete signals clear the right keys, and keys carry a version. Lifetimes are staggered and jittered. A decision is recorded about views versus a cache.

Throttling. Reads and writes have separate budgets. Only the JSON renderer is enabled in production. The forwarded header is read from the right end, and the address used matches the deduplication key. The client retries reads once and shows a human message for writes with a button guard. The thresholds were verified with a loop and are tuned against logs.

Questions that come up

Ten or twenty per page? Ten on desktop, fifteen to twenty for mobile infinite scroll, decided by first-screen render time rather than by making the number bigger.

Will a cap of fifty annoy anyone? Put a quarter of a megabyte next to seven and a half and nobody complains. Full exports belong in a separate endpoint backed by a background job.

Does losing the cache on restart hurt? It costs speed, not data, and the free tier recycles daily, so the first few minutes are slower.

Does caching conflict with token auth? Not for public reads, which are not cached per user. Never cache per-user endpoints such as the current-user or admin routes.

What if a real user gets rejected? Check for a front-end loop first, which is the usual cause, then the threshold. Thirty a minute is plenty for a person and not for a script, which is the intent.

Is three comments a minute too tight? Almost nobody posts three in a minute. An author replying should be authenticated and on the higher budget.

Should crawlers be exempted? Identifying search engines by user agent is unreliable and unnecessary at this size; the requests being rejected are not the ones you want.

Can SQLite carry this? With read-heavy traffic and these three settings it handles thousands of daily users. Move when writes get heavy or full-text search matters.

Closing

Pagination decides how much, caching decides how often, throttling decides who. There is no magic in any of the three; the work is in the thresholds. Ship conservatively, then read the logs and the rejection rate and adjust. Every value here was set by real traffic rather than by taste, which is why copying them will not go far wrong.
