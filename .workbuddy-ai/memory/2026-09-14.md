### 核心技术发现（文章的主线，也是真实的线上隐患）

`backend/articles/models.py` 里 `Article.Meta`：

```python
ordering = ["-is_top", "-created_at"]                       # 排序列
indexes  = [Index(fields=["status", "-created_at"])]        # 索引缺 is_top
```

- 索引少排序列 `is_top`，SQLite 执行计划出现 `USE TEMP B-TREE FOR ORDER BY`（已在真实 db.sqlite3 上验证）
- 100 万行实测：无索引 395.92ms / 现有索引 476.50ms（更慢）/ 补列但方向错 690.80ms（更慢）/ 方向对齐 0.18ms（约 2600 倍）
- 建议改成 `models.Index(fields=["status", "-is_top", "-created_at"], name="articles_status_top_created_idx")`
- **注意：只写进了文章，`models.py` 尚未改动，也没有 makemigrations。** 这是待办。

## 第二篇：Django 事务深水区（已上线，article id 38）

- 标题：《事务回滚了，邮件照样发出去——Django 事务深水区：atomic、on_commit 与 F() 表达式（含并发实测）》
- slug `django-transaction-atomic-on-commit`，标签全部复用 django/backend-dev/database/performance，阅读时长 25 分钟
- 封面：Unsplash 网图（photo-1614064641938-3bbee52942c7，笔记本+手机+代码）

### 核心实测（8 线程 × 50 次 = 400 期望，Django 6.0.6 / SQLite 3.50.4）

| 写法 | 最终值 | 异常 | 备注 |
|---|---|---|---|
| 读-改-写（autocommit） | 50 | — | **87.5% 静默丢失** |
| 读-改-写 + atomic | 50 | 7/8 线程 `database is locked` | atomic 不防丢失更新 |
| F() 表达式 | **400** | — | 一条 SQL，唯一正确答案 |
| atomic + select_for_update | 50 | 7/8 线程 locked | **SQLite 上 select_for_update 是空操作**（`has_select_for_update=False`） |

E2：`save(update_fields=["views_count"])` 109.04ms vs `.update(F()+1)` 7.40ms = **14.7×**
E3：rollback 时 post_save 跑了，on_commit 没跑——这是 `backend/articles/signals.py` 的真实邮件 bug
E4：atomic 内捕获 IntegrityError 后继续查库 → `TransactionManagementError`；内层 atomic（savepoint）→ 正常

### 三条心智模型

1. 改：`F()` 表达式
2. 多步原子：`atomic`
3. 副作用：`on_commit`

### 新增脚本

- `tools/bench_transaction.py` — 复现 E1/E2/E3/E4，复制 db.sqlite3 到临时目录，跑完自删；**断开 notify_subscribers_on_publish 信号**，不会真的发邮件
- `tools/publish_transaction_article.py` — 沿用 slow-query 那套：slug→name 复用，封面 HEAD 检查

### 核心实测（20 万行 / 789.7 MB，Django 6.0.6 + SQLite 3.50.4）

| 操作 | 耗时 | 备注 |
|---|---|---|
| E1 原始 SQLite `ADD COLUMN`（可空） | **0.7 ms** | 纯元数据 |
| E1b 原始 SQLite `ADD COLUMN NOT NULL DEFAULT 0` | **7.4 ms** | 原生支持！ |
| E2 Django 式整表重建（`AddField` NOT NULL） | **8381.1 ms** | 峰值磁盘 1.5 GB（2×） |
| E3 `CREATE INDEX` | 1594.0 ms | 索引 7.4 MB |
| E4 DDL 期间并发 INSERT | 181.1 ms → **1324.5 ms** | 被写锁挡住，等于 DDL 总时长 |
| E5 `DROP COLUMN` | 1864.4 ms | SQLite 3.35+ 仍是整表重建 |
| E6 体积账（`dbstat`） | 表 783.2 MB (97.4%) / 全部索引 < 2% | 正文 TEXT 才是重建慢的根因 |

**Django 比原生慢 1130 倍**，根因在 `django/db/backends/sqlite3/schema.py:311-325`
的 `or not field.null` —— 只要字段 NOT NULL 就无条件 `_remake_table`，
不去细分"有没有常量默认值"。`db_default=Value(0)` 也救不了（`not field.null` 先短路）。

绕路方案：`SeparateDatabaseAndState`（state 用 `AddField`、database 用 `RunSQL`）。
另有 `sqlmigrate` 必须先跑、`lock_timeout`、Expand/Contract、WAL + `busy_timeout`。

新增脚本 `tools/bench_migration.py`（临时库，不碰 db.sqlite3）。
